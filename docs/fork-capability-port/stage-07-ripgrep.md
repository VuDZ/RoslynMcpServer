# Этап 7. Ripgrep отдельным аргументом

Статус: не начат. Ключ `ripgrep-path` в `RoslynMcp.jsonc` разбирает этап 6. Этот этап только решает, когда им пользоваться.

## Цель

`search_code` умеет звать ripgrep, когда об этом попросили. Обычный вызов, как сейчас, обходит файлы управляемым кодом. На машине без `rg` ничего не меняется и ошибки нет.

## Почему отдельный ключ

Форк при наличии `rg` на `PATH` всегда ищет им, а управляемый обход оставляет запасным. Это другое множество файлов: ripgrep уважает `.gitignore` и прячет скрытые каталоги, а регулярное выражение у него диалект Rust, не .NET. Молчаливая подмена сломает поиск там, где `rg` не установлен ожидаемо, и там, где он установлен случайно.

Аргумент `useRipgrep`, по умолчанию `false`.

- `false`: нынешний обход. `PATH` не проверять, процесс `rg` не запускать.
- `true`: только ripgrep. Нет бинарника — ошибка с текстом, что `useRipgrep` включён, а `rg` не найден, и что обычный поиск доступен без этого аргумента. На управляемый обход при этом не переключаться: иначе агент не отличит пустой gitignore-результат от полного обхода.

Необязательный `ripgrepPath` — полный путь к `rg` или `rg.exe`. Имеет смысл только вместе с `useRipgrep: true`. Без флага путь игнорируется и в ответ пишется, что путь не использован.

Если аргумент `ripgrepPath` опущен, а в конфиге есть `ripgrep-path`, берётся он. Нет ни аргумента, ни ключа — поиск `rg` на `PATH`. Ключ в файле сам по себе поиск не переключает.

## Общее с текущим поиском

Корни те же: `ResolveSearchRoots` (каталог решения и внешние проекты, либо один явный `directoryPath`). Расширения, регистр, `maxResults`, `maxScanSeconds`, отмена — те же аргументы.

Отмена и таймаут убивают дерево процесса `rg`, как другие дочерние процессы сервера. Зависший `rg` не оставлять.

Вывод строк тот же вид, что у управляемого поиска: `файл:строка | текст`. Предел `maxResults` по-прежнему обрезает ответ и пишет, что предел достигнут. Полный дамп во временный файл не делать.

При `useRipgrep: true` в шапке ответа есть строка, что искал ripgrep и что скрытые и gitignore-файлы могли не войти. Регулярное выражение при флаге — синтаксис ripgrep; в описании аргумента `useRegex` это сказать для случая `useRipgrep: true`.

Пакеты корней уложить в лимит командной строки Windows, как в форковом `RipgrepRunner`, если корней много. Код можно взять маленьким куском из `Services/RipgrepRunner.cs` форка (запуск, разбор `path:line:content`, убийство дерева), без подмены поиска по умолчанию и без `WorkspaceConfig`.

## Файлы

- `Tools/UtilityTools.cs` — ветка по `useRipgrep`
- `Services/RipgrepRunner.cs` — новый, только запуск и разбор
- Тесты без настоящего `rg`: флаг выключен не ищет бинарник (подмена резолвера пути или внутренний шов); флаг включён и путь пустой — текст ошибки, управляемый результат не возвращается; разбор строки stdout ripgrep на фиксированной строке. Интеграционный тест с живым `rg` не обязателен и не должен падать на машине без него.

## Контракт

Два новых необязательных аргумента. Старые вызовы `search_code` байт в байт по составу обхода не меняются.

Описание `search_code` и `McpToolHelpCatalog`: по умолчанию управляемый обход; ripgrep только `useRipgrep: true`; отсутствие `rg` для обычного вызова нормально.

`AGENTS.md.sample` — одна фраза в гибридном поиске: текстовый поиск по умолчанию прежний; ripgrep не предполагать установленным.

## Инварианты

Отмена дочернего процесса, предел ответа, корни поиска VuDZ. Конфиг ленивой загрузки и навигационные курсоры не участвуют.
