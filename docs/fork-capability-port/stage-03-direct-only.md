# Этап 3. directOnly у find_symbol_references

Статус: не начат. Делать после этапа 1: фильтр применяется к уже выбранному одному символу, в том числе к единственному объявлению в файле.

Разбор режима — [navigation-definition-references.md](navigation-definition-references.md). Позиционный помощник не менять.

## Цель

У виртуального, абстрактного или переопределённого метода класса можно оставить только прямые вызовы. По умолчанию набор точек тот же, что сейчас, плюс одна строка, если часть из них — виртуальная диспетчеризация.

## Смысл фильтра

Roslyn на такой метод возвращает вызовы всего семейства: любой override, любой статический тип получателя.

Прямой вызов — статический тип получателя равен типу, в котором объявлен запрошенный метод, или наследнику этого типа. Сюда входят `this`, сам тип, наследник и вызов через `?.`. Вызов через переменную базового типа или через соседнюю ветку наследования — виртуальная точка.

Для самого базового виртуального метода наследники являются прямыми, поэтому фильтр ничего не убирает и примечание не нужно. Для обычного невиртуального метода флаг ничего не меняет. Методы интерфейса не классифицировать: в форке условие — метод класса с `IsVirtual`, `IsOverride` или `IsAbstract`. Так и оставить.

Если получателя не удалось понять, точку не выкидывать. Иначе сломанная компиляция молча уменьшит список.

`directOnly: true` без файла (поиск по решению, несколько групп) — ошибка. Там нет одного объявленного типа. С файлом флаг действует и на позицию, и на единственное объявление из этапа 1.

Сравнение типов: сначала `SymbolEqualityComparer`. Если не равны — полное отображаемое имя, включая аргументы дженерика (`SymbolDisplayFormat.FullyQualifiedFormat`). Исходный тип и тот же тип как метаданные из проекта, который ссылается на сборку, для компаратора не равны. Без запасного имени фильтр выкинет настоящие межпроектные вызовы. Ложное совпадение двух разных сборок с одним и тем же полным именем редкое; лишнее сохранение точки лучше лишнего удаления.

Дженерик сравнивать и по `ConstructedFrom`, чтобы вызов на `T<int>` совпал с методом, объявленным на открытом `T<>`.

## Куда встроить

После `SymbolFinder` и дедупликации, до `NavigationListingHelper.AppendCappedLines`. Курсор листает уже отфильтрованный список.

Классификатор — новый внутренний тип в `Services/`, не копия `NavigationTools.cs` форка. Снимок тот, на котором уже посчитаны ссылки.

Текст, когда фильтр выключен и счётчик виртуальных точек больше нуля: сколько точек из скольких являются виртуальной диспетчеризацией, и что `directOnly: true` оставляет прямые.

Текст, когда фильтр включён и что-то отфильтровано: сколько прямых осталось и сколько убрано. Если не осталось ни одной — отдельная ошибка с советом вызвать снова с `directOnly: false`.

## Тесты

Смысл из форка `VirtualReferencesTests` и `DirectOnlyCrossProjectTests`.

На одной компиляции, без MCP:

- получатель-наследник в метаданных совпадает с исходным объявленным типом;
- получатель базового типа не совпадает с типом override;
- внук совпадает;
- открытый и закрытый дженерик совпадают.

На инструменте, минимальное решение из двух проектов или двух компиляций, как проще собрать существующими тестовыми помощниками:

- override: остаются вызовы на свой тип и наследника, уходят базовый тип и сосед;
- базовый virtual: примечание не появляется, `directOnly` ничего не режет;
- обычный метод: `directOnly` ничего не режет;
- поиск по имени без файла и `directOnly: true` — ошибка.

Числа и формулировки можно сделать своими, если набор точек тот же.

## Контракт

Новый необязательный аргумент `directOnly`, по умолчанию `false`. Старый вызов получает те же точки. Может появиться одна строка-примечание. Это совместимое добавление.

Описание инструмента и `McpToolHelpCatalog` обновить. В описании прямо сказать: флаг только вместе с `filePath`, только для виртуального метода класса, межпроектное совпадение типов идёт по полному имени.
