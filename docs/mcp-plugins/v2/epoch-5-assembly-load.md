# Эпоха 5. Загрузка сборки

Статус: сделана.

## Цель

По плану (уже с путём копии, если она была) хост грузит одну входную сборку,
создаёт названный тип и вызывает `Register`. Один битый плагин не отменяет
остальные и не роняет вызывающего. `Program.cs` по-прежнему сам загрузчик не
вызывает: это делает тест и, в следующей эпохе, старт.

Выход `samples/RoslynMcpPlugin` эта эпоха не пересобирает по-другому. Частная
managed-зависимость — `Newtonsoft.Json`: её DLL лежит рядом с entry, тул
шаблона её вызывает. `RoslynMcpServer.dll` и `ModelContextProtocol.dll` в этом
каталоге нет. `deps.json` содержит compile-записи `RoslynMcpServer`,
`ModelContextProtocol` и `Microsoft.CodeAnalysis`: без них эпоха 2 этот выход
пропускает. Файлов этих сборок рядом с entry нет. Шаг 1 резолва отдаёт уже
загруженную сборку хоста и не открывает путь из `deps.json` второй копией.

## Контекст загрузки

Свой `AssemblyLoadContext` на плагин, не collectible. На
`AssemblyLoadContext.Default.Resolving` не подписываться. `LoadUnmanagedDll`
не добавляется. v1 native не резолвит: файл в `runtimes/` P/Invoke не обещает.

Порядок резолва сборки:

1. Контракт хоста. Уже загруженная сборка, если простое имя одно из четырёх
   семейств: `RoslynMcpServer`; `ModelContextProtocol` или начинается с
   `ModelContextProtocol.`; начинается с `Microsoft.CodeAnalysis`; начинается с
   `Microsoft.Extensions.`. Если такой сборки в контексте по умолчанию ещё нет,
   её грузит `AssemblyLoadContext.Default.LoadFromAssemblyName`, не файл из
   каталога плагина.
2. `AssemblyDependencyResolver` плагина от entry (`deps.json` рядом с DLL).
3. Framework / default context.

Промах резолвера на сборке framework пропуском не является. Промах частной
managed-зависимости после этих трёх стадий — пропуск плагина, не привязка
одноимённой сборки из хоста. Как отличают framework/default от отсутствующей
частной сборки, эпоха не нормирует, если исход двух тестов ниже сохранён.
Обхода каталога «найти любой DLL с интерфейсом» нет.

Entry грузится `LoadFromAssemblyPath` по пути из плана. Тип берётся
`GetType(pluginType, throwOnError: false)`. Нет типа, тип не реализует
`IRoslynMcpPlugin`, исключение при создании — пропуск.

Экземпляр плагина создаётся до `Build`, провайдера ещё нет. У типа один открытый
конструктор без параметров — `Activator.CreateInstance`. Конструктор с
параметрами — пропуск с причиной «plugin type constructor must be parameterless».
Синглтоны эвристики и классы тулов получают зависимости в своих конструкторах
уже после `Build`, как встроенные тулы. Конструктор `IRoslynMcpPlugin` их не
принимает. Пример в контракте именно такой.

Дальше, до вызова `Register`: `Name` ординально равно `id` плана. Не равно —
`Register` не вызывать.

`Register` получает контекст эпохи 1 с `toolPrefix` плана. Регистрации этого
плагина не видны общему контейнеру и `tools/list`, пока `Register` не вернулся
нормально и пока `McpServerTool.Create` не успел для каждого принятого метода.
Исключение на любом из этих шагов оставляет контейнер без сервисов и тулов
этого плагина, освобождает имена, пишет пропуск и не роняет процесс. Статуса
«загружен частично» нет. Побочные эффекты вне DI не откатываются. Неуспешный
метод назван в причине пропуска. Общий catch вокруг старта встроенного каталога
не ставится. Буфер дескрипторов до commit либо снятие уже добавленных
дескрипторов до публикации статуса — оба допустимы.

Пропуски имён внутри `AddToolsFrom` остаются пропусками тулов, плагин при этом
загружен.

Результат на плагин: загружен или пропущен, id, путь entry который грузили
(копия, если она была), принятые имена тулов, текст причины. Третьего статуса нет.

## Тесты

Выход шаблона эпохи 4. Загрузчик вызывается на плане с теневой копией этого
выхода и на плане drop-in без копии. Коллекцию и `CurrentToolCount` читать
только после `IOptions<McpServerOptions>.Value`.

- После резолва options в коллекции есть `sample_loaded_workspace`. Экземпляр
  тула получает тот же `SolutionManager`, что провайдер. До `load_workspace`
  метод возвращает `No workspace is loaded.`
- Файл `.cs` изменён на диске, очередь disk watcher не сброшена чужим тулом.
  Плагин или тестовый тул, вызвавший `GetSanitizedPublishedSolutionAsync`, видит
  новый текст. Как тест доставляет событие watcher, эпоха не нормирует.
- `Name`, не равный `id`, — пропуск, тула в коллекции нет. Для этого теста
  достаточно второго плана с тем же entry и чужим `id`: тип шаблона вернёт
  `sample`.
- Несуществующий `pluginType` — пропуск, исключение наружу не идёт.
- Исключение из `Register` или из `Create` принятого метода: тулов и сервисов
  этого плагина в контейнере нет, имя свободно для следующего плагина в том же
  контейнере, причина называет метод.
- Рядом второй битый план не мешает шаблону зарегистрировать тул.
- Повторная загрузка того же id в один `IServiceCollection` не требуется:
  дубли id отсекает эпоха 2.
- Шаблон вызывает BCL и `Newtonsoft.Json`. Промах резолвера на framework не
  пропускает плагин.
- Отсутствующая `Newtonsoft.Json.dll` после трёх стадий — пропуск. Одноимённая
  сборка из хоста не подставляется.
- При удержанном ALC, загруженном из копии: исходный entry перезаписывается;
  загруженный тип жив; второй запуск загрузчика на том же исходном каталоге
  видит новые байты; `Assembly.Location` entry — каталог копии. Как доставляется
  вторая запись байтов, эпоха не нормирует. Отдельный процесс ОС не требуется.
- `Assembly.Location` загруженной `Newtonsoft.Json` — каталог копии.

Тест не оставляет загруженную сборку шаблона в контексте по умолчанию. Ссылка
тестового проекта на шаблон остаётся с `ReferenceOutputAssembly=false`.
