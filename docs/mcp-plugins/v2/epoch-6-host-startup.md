# Эпоха 6. Старт хоста

Статус: не начата.

## Цель

Процесс MCP до `Build` обнаруживает плагины, копирует dev-пути, грузит сборки
и регистрирует тулы. Первый `tools/list` их видит. Битый плагин пишет причину
в stderr и в лог, процесс стартует с остальными тулами.

Поведение инструментов для агента меняется, поэтому после зелёной сборки —
патч `Version`, `AssemblyVersion`, `FileVersion` вместе. Число заранее не
фиксировать: следующий патч от версии в csproj на момент эпохи.

## Старт

В [`Program.cs`](../../../Program.cs) после `AddRoslynMcpServerTools` и до
`builder.Build()` вызывается один метод старта. Ему передают `IServiceCollection`,
уже зарегистрированные настройки, `AppContext.BaseDirectory`, значение
`ROSLYN_MCP_PLUGINS` и stderr. До `Build` метод не обязан получать `ILogger`.

Метод сам вызывает открытие путей (эпоха 2), теневую копию (эпоха 3) и
загрузку (эпоха 5). Исключение одного плагина внутри этих шагов наружу из
метода старта не летит. Исключение самого метода, если оно всё же вышло, —
та же схема, что у сбоя каталога тулов: текст в stderr, ненулевой код, `return`
до `RunAsync`. Ожидаемый пропуск плагина таким сбоем не является.
`ParseFailures` ключа `plugins` падением старта не являются. Общий catch вокруг
старта встроенного каталога не ставится: поломка каталога хоста по-прежнему
валит процесс.

На каждый пропуск stderr получает строку в момент пропуска

`[RoslynMcp] plugin skipped (<id или путь>): <причина>`

Те же строки пишутся в лог хоста сразу после успешного `Build`, одним проходом
по уже собранному отчёту, без второго discovery. Если упал сам `Build`, в файле
лога этих строк может не быть: stderr к этому моменту уже заполнен. Отдельная
фабрика Serilog до `Build` не требуется и не запрещена, если файл лога после
успешного `Build` содержит те же строки и второй обход плагинов не делается.

Успешная загрузка в stderr не расписывает список тулов: его показывает
`get_mcp_server_info`.

Коллекцию `McpRuntimeToolCollection` и `CurrentToolCount` старт читает только
после `IOptions<McpServerOptions>.Value`. Плагины в `McpToolCatalog` не
добавляются. Второго наполнения коллекции из отчёта старта нет. Семантику
`CurrentToolCount` до первого резолва эпоха не меняет.

## Что видит агент

`get_mcp_server_info` дописывает плагины, не заменяя текущие строки. Новая
перегрузка [`McpServerInfoHelper.BuildInfoMarkdown`](../../../Services/McpServerInfoHelper.cs).
Старые перегрузки текст не меняют, пока им не передали отчёт: существующие
тесты снимка остаются зелёными.

Инструмент передаёт отчёт. Нет загруженных и нет пропусков — строка
`- **Plugins:** (none)`. Иначе на каждый загруженный плагин строка с id, путём
entry, который реально грузили, и именами тулов. Пропуски — отдельными строками
с причиной. Число `Registered MCP tools` включает тулы плагинов, потому что они
в той же коллекции. Счётчик читается после резолва
`IOptions<McpServerOptions>.Value`.

Отчёт старта хранит описание и параметры принятых тулов. Источник один: этот
отчёт, снятый с принятого метода (`[Description]` и параметры). Хранить
`MethodInfo` или уже снятый текст — на усмотрение реализации. Help из JSON
Schema SDK не читается. Метаданные discarded-плагина в отчёт и в help не попадают.

`get_tool_help` для имени загруженного плагина читает этот отчёт и возвращает
`[Description]` и параметры. `Kind` и `Group` для плагина — `plugin`. Это не
группа `list_tool_groups`. Статью в `McpToolHelpCatalog` не добавляет. Записи в
`McpToolCatalog` нет. Неизвестное имя по-прежнему даёт близкие имена каталога;
имена загруженных плагинных тулов в этот список близких тоже входят.

`list_tool_groups` имена плагинов не показывает. `lite` и `full` их не снимают.

`samples/RoslynMcpPlugin/plugin.json`: `minHostVersion` становится новой
`Version` хоста. Другие поля не менять.

## Тесты

Временный `baseDirectory` с drop-in `plugins/sample/`, скопированным из выхода
шаблона (DLL, deps, pdb, `plugin.json` с уже новым `minHostVersion`).
In-process тесты `PluginStartup` остаются. Коллекцию читать после резолва
`IOptions<McpServerOptions>.Value`.

- После `PluginStartup`, `Build` и резолва options коллекция содержит
  `sample_loaded_workspace` и прежний набор каталога.
- Info содержит id `sample`, путь entry внутри временного drop-in и имя тула.
- Каталог `plugins` отсутствует — строка `(none)`, хост строится.
- Битый соседний подкаталог даёт строку пропуска в захваченном stderr в момент
  пропуска и в info; тул шаблона на месте. Те же строки есть в `logs/mcp-*.log`
  после успешного `Build`. Приёмка читает этот файл, не только stderr.
- `get_tool_help` по `sample_loaded_workspace` содержит текст `[Description]`
  шаблона и параметры. `Kind` и `Group` — `plugin`. `list_tool_groups` этой
  строки не содержит. Имени нет в `McpToolCatalog` и `McpToolHelpCatalog`.
  Метаданные пропущенного соседа в help не попадают. Близкие имена неизвестного
  тула включают имя загруженного тула шаблона.
- Профиль `lite`, собранный тем же старт-методом, тул плагина не выкидывает.

Обязательный subprocess smoke entry point хоста, не вызов `PluginStartup` в
testhost. Как поднимается процесс и как читается первый `tools/list`, эпоха не
нормирует.

- В окружении только `ROSLYN_MCP_PLUGINS` на dev-выход шаблона.
- Первый `tools/list` содержит тул шаблона. `tools/call` его вызывает.
- Stdout не содержит не-протокольного вывода.

Файл лога проверяет in-process приёмка выше. Smoke файл лога не дублирует и
второй discovery не делает.
