# Эпоха 1. Раннер `auto` | `vstest` | `mtp`

Статус: не начата.

## Цель

Три инструмента запуска тестов принимают необязательный `testRunner`. Молчание равно `auto`: раннер берётся из проекта по правилам ниже. Явный `vstest` оставляет сегодняшнюю команду и сегодняшний разбор, без классификатора. Явный `mtp` включает вторую команду и второй разбор. Итог для агента один: строка раннера, счётчики, упавшие тесты, assertion, stdout и stderr в тех же бюджетах.

`auto` при неясности не запускает процесс и не подставляет VSTest «на всякий случай».

## Параметр

Имя: `testRunner`. Значения: `auto`, `vstest`, `mtp`. Сравнение имён ординальное, без учёта регистра. Пробелы по краям снимаются.

Опущенный аргумент равен `auto`. Любое другое значение — ошибка до процесса. Текст называет параметр и три допустимых значения.

Один и тот же параметр на `run_dotnet_test`, `run_specific_test`, `run_test_by_filter`. На остальных инструментах его нет.

`[Description]` говорит: молчание — `auto`; `vstest` и `mtp` принудительны; номер пакета xUnit сюда не подставляют; при неясном проекте будет ошибка, а не прогон. В `AGENTS.md.sample` абзац сессии не добавлять: агент читает описание инструмента.

## Классификатор `auto`

Читает XML, не оценивает MSBuild. Источники: сам `.csproj` и файлы `Directory.Build.props` / `Directory.Packages.props` от каталога проекта вверх до каталога загруженного workspace включительно. Если workspace не загружен — вверх, пока находится файл, не дальше корня диска. Чужие `Import` не открывать. `PackageReference` и свойства внутри `Condition` не считать голосом. Два безусловных значения одного свойства — неясность.

Голоса, и только они:

| Что увидели | Голос |
|---|---|
| `PackageReference` с именем `xunit` (ровно это имя, не `xunit.v3*`) | VSTest |
| `xunit.v3.mtp-off` | VSTest |
| `xunit.v3`, `xunit.v3.mtp-v1` или другое имя с префиксом `xunit.v3`, кроме `xunit.v3.mtp-off` | MTP |
| Безусловное `UseMicrosoftTestingPlatformRunner` со значением `false` | VSTest |
| То же свойство со значением `true` | MTP |

`xunit.runner.visualstudio` сам по себе голоса не даёт. NUnit, MSTest и проект без пакетов xUnit v3 тоже не дают голоса MTP.

Итог по одному проекту:

- Есть голос VSTest и нет голоса MTP → `vstest`.
- Есть голос MTP и нет голоса VSTest, и рядом нет `xunit.runner.visualstudio` → `mtp`.
- Метапакет MTP и одновременно `xunit.runner.visualstudio`, без безусловного `UseMicrosoftTestingPlatformRunner` → неясность. Так проект может оставаться на VSTest, и угадывание здесь запрещено.
- Оба голоса, нечитаемый файл, пакет только внутри `Condition` → неясность.

Нет ни одного голоса → `vstest`. Так остаются xUnit v2, NUnit, MSTest и проект без тестового пакета.

Неясность одного проекта — ошибка до процесса. Текст перечисляет, какие голоса столкнулись, и просит явный `testRunner`.

Цель `.sln` / `.slnx`: классификатор обходит проекты из файла решения, библиотеки без голосов пропускает. Все оставшиеся — `vstest` → команда VSTest на решении, как сегодня. Все оставшиеся — `mtp` → ошибка до процесса с просьбой передать один `.csproj` (решение на MTP эта эпоха не запускает). Смесь, неясный проект или неразобранный файл решения → ошибка до процесса, со списком проектов. Запасного прогона VSTest нет.

Каталог: ровно один `.csproj` — как этот проект. Иначе ошибка до процесса.

## Команда

`vstest` остаётся на `DotNetTestArguments`: `--logger "console;verbosity=normal"`, `--filter` в синтаксисе VSTest, предварительный `dotnet build`, затем `dotnet test --no-build`, чтобы лог сборки не попадал в парсер. `.sln`, `.slnx`, каталог и `binariesPath` как сейчас. Явный `vstest` классификатор не вызывает.

`mtp` — только путь к одному тестовому `.csproj`. `.sln`, `.slnx` и каталог — ошибка до процесса: в ней есть слово `testRunner` и просьба передать один проект. Смешанное решение двумя запусками не исполняется.

На `mtp` не передаются `--logger` консоли VSTest и `--filter` VSTest. Дополнительные аргументы раннера стоят после `--`. Конкретные флаги фильтра берутся из документации xUnit для версии пакета, на которой снята фикстура лога, и записаны комментарием рядом с фикстурой. Вторую, придуманную синтаксисом, форму не вводить.

`noBuild`, `noRestore`, `configuration`, `platform`, `timeoutSeconds`, прогресс, `includeFullOutput`, `maxOutputChars`, `reportCursor` общие. Предварительная сборка та же, парсер по-прежнему видит только процесс теста. `binariesPath` вместе с выбранным `mtp` — ошибка до процесса: путь к DLL — вход VSTest.

Подпись шага прогресса содержит имя раннера, который реально запущен (`VSTest` или `Microsoft Testing Platform`), не слово `auto`.

Таймаут и отмена убивают дерево процесса так же, как сейчас. Второго процесса эпоха не запускает.

## Фильтры на `mtp`

`run_dotnet_test` без фильтра запускает этот один проект.

`run_specific_test` переводит `className` и `methodName` в фильтр класса и фильтр метода. Скобки и аргументы Theory в фильтр не попадают. Имя метода — то, что агент передал, без `()`.

`run_test_by_filter` принимает только строки, которые целиком совпадают с одним из видов:

- `FullyQualifiedName~Namespace.Type`
- `FullyQualifiedName~Namespace.Type.Method`
- `FullyQualifiedName=Namespace.Type`
- `FullyQualifiedName=Namespace.Type.Method`

Имя типа содержит хотя бы одну точку. Имя метода — последний сегмент после точки и не содержит `(`. Ведущая точка, `Category=`, `Trait=`, подстрока без `FullyQualifiedName` и любой другой фильтр — ошибка до процесса. Ошибка цитирует исходную строку и отсылает к `run_specific_test` либо к `testRunner=vstest`. Ноль тестов из-за непереведённого фильтра успехом не бывает.

## Отчёт

Оба разбора заполняют одну и ту же модель, которой инструменты уже рисуют markdown. Первая строка ответа: `Runner: VSTest` либо `Runner: Microsoft Testing Platform`. Для `auto` к ней добавляется ` (auto)`.

Дальше те же поля, что у текущего отчёта: итог, список упавших, текст assertion, stdout и stderr с теми же бюджетами (`includeFullOutput` / `maxOutputChars`). Агент не учит второй формат.

Успех `mtp` допустим только когда разбор узнал сводку и `Passed + Failed + Skipped = Total`. Код выхода 0 без такой сводки — не успех. Неразобранный лог — ошибка с головой и хвостом сырого вывода, без синтетического `Passed: 0`.

Если `auto` ошибся в сторону VSTest (пакет MTP лежал в непрочитанном `Import`), лог MTP обязан остаться неуспехом нынешнего `VstestOutputParser`. Ослаблять этот парсер, чтобы «хоть что-то сошлось», нельзя.

Строка `Runner:` пишется и на ошибке, которая случилась после выбора раннера. На ошибке «значение `testRunner` неизвестно» и на неясности `auto` процесса нет. В неясности вместо строки раннера — текст, какие голоса столкнулись.

## Фикстуры

Юнит-тесты ветки `mtp` читают сохранённые логи, а не живой `dotnet test`. Пропуск такого теста через `Assert.Skip` не использовать: CI валит джоб на любом skip.

Классификатор проверяется на временных `.csproj` / `Directory.Build.props`, без восстановления NuGet:

- `xunit.v3.mtp-off` → `vstest`, строка аргументов совпадает с явным `vstest` (`--logger`, `--filter`);
- голое `xunit` → `vstest`;
- `xunit.v3` без `xunit.runner.visualstudio` → `mtp`, в аргументах нет `--logger` и нет `--filter` VSTest;
- `xunit.v3` вместе с `xunit.runner.visualstudio` и без свойства → ошибка, процесс не стартует;
- `UseMicrosoftTestingPlatformRunner` `true` / `false` перекрывает пакет;
- свойство только внутри `Condition` голоса не даёт;
- решение, где все тестовые проекты — VSTest → команда VSTest на решении;
- решение со смесью или с одним только MTP-проектом → ошибка до процесса.

В фикстурах логов минимум: сводка с прохождениями, падение с многострочным assertion и stdout, код выхода 0 без сводки, Theory с отображаемым именем метода. Версия пакета, с которой снят лог, указана в комментарии файла. Лог 4.x, если он другой, — отдельная фикстура; один регэксп на оба не выдумывать заранее. Пока фикстуры 4.x нет, описание инструмента не обещает отдельный формат 4.x сверх того, что уже разобрано.

Существующие тесты `VstestOutputParser` и `DotNetTestArguments` не переписывать под MTP. Явный `vstest` даёт историческую строку аргументов. Опущенный параметр на тестовом проекте этого репозитория (`xunit.v3.mtp-off`) даёт ту же строку.

Тестовый проект репозитория остаётся на `xunit.v3.mtp-off` и `xunit.runner.visualstudio`. Шарды CI не меняются.
