# Эпоха 3. Полный поиск, исправление и защита от повторения

Статус: **не начата**. Зависимость: [эпоха 2](epoch-2-general-solution.md).

## Цель и границы поиска

Найти и исправить все проверки в репозитории, которые делают вывод о структуре или семантике
production C# по подстрокам, регулярным выражениям, текстовым окнам и порядку объявлений.
Добавить автоматическую защиту от появления новых таких проверок.

Область — все отслеживаемые исходники тестов, их помощники и скрипты проверок, включая новые
файлы итогового изменения. Поиск не ограничивается четырьмя примерами из README, каталогом
`Services` или тестами, которые уже падают. `bin`, `obj`, внешние зависимости и исторические
архивы документации не являются исполняемыми проверками.

Текстовые ассерты на сообщения, CLI output, форматы файлов и результат генерации, где точный
текст является контрактом, допустимы. Проверка комментария/XML-документации также может быть
текстовым контрактом; это нужно обосновать, а не запрещать любое чтение `.cs`.

## Инвентаризация

1. Найти кандидатов через `rg`: чтение исходников и resources, `IndexOf`/`LastIndexOf`,
   `Contains`/`DoesNotContain`, `Regex`, `Substring`, ranges, `Split`, поиск по строкам,
   окна вокруг совпадений и счётчики вызовов.
2. Проследить помощники, передающие текст в ассерты: строка могла быть прочитана в другом
   методе, файле, fixture или скрипте. Текстовый поиск формирует список кандидатов,
   но сам по себе не доказывает полноту классификации.
3. Проверить обход каталогов: новые тестовые проекты, вложенные папки и partial-файлы
   должны попадать в область инвентаря автоматически.
4. Для каждого кандидата создать запись в `source-check-inventory.md`: устойчивый ID,
   файл и тест/помощник, защищаемый контракт, источник текста, текущий механизм,
   решение, замена, проверяющие мутации и итоговый статус.
5. Классифицировать как «мигрировать», «допустимый текстовый контракт» или «требует решения».
   Последняя категория должна опустеть перед завершением эпохи. Для допустимого текста
   сохранить конкретное основание; наличие зелёного теста не является основанием.

## Миграция

- Перевести структурные проверки на решение эпохи 2; где точнее поведение — заменить
  поведенческим тестом с тем же защищаемым инвариантом.
- Убрать срезы между объявлениями, произвольные окна вроде предшествующих 2000 символов,
  поиск вызовов в комментариях/строках и счётчики подстрок вместо вызовов.
- Для инвентаря семантических входов определить единицу учёта: вызывающий метод и целевой
  символ. Новый вызов в уже известном файле не должен автоматически считаться классифицированным.
- Для границы `TryApplyChanges` проверить конкретный символ и допустимое место вызова по всей
  установленной области production-кода, а не только число строк в одном файле.
- На каждую миграцию сохранить соответствие старых утверждений новым. Удаление дублирующего
  теста допустимо лишь при указании проверки, которая полностью сохраняет его контракт.
- Объединить повторяющиеся обходы и удалить заменённые текстовые помощники. Ошибки анализа
  не маскировать пропуском теста или возвратом пустого списка.

## Постоянная автоматическая защита

Ввести обязательную проверку политики в существующий CI. Если это unit-тест, он должен
выполняться под текущим фильтром `Category!=AnalyzerLifecycle`; отдельный запуск не должен
зависеть от необязательного lifecycle-окружения.

Механизм выбрать и описать по итогам инвентаря. Базовый вариант — централизованный доступ
к production-исходникам через структурный помощник и AST/семантическая проверка тестового
кода, запрещающая обход этого входа и передачу сырого production-текста в структурные ассерты.
Учесть чтение через локальные обёртки, aliases, async API, reader и embedded resources.
Скрипты с аналогичными проверками должны либо войти в защиту, либо быть мигрированы в общий
проверяемый механизм. Один список запрещённых подстрок не считается достаточной защитой.

Для каждого поддержанного способа чтения/обхода зафиксировать детектор и проверяющий пример.
Границы детектора описать честно: он защищает от случайного возврата известных приёмов,
не доказывает невозможность намеренного обхода произвольным кодом.

Исключения разрешаются только для обоснованных текстовых контрактов. Исключение привязано
к конкретной проверке/символу и правилу, содержит причину; wildcard на каталог или весь
тестовый класс недопустим. Устаревшее исключение должно вызывать ошибку. Реестр инвентаризации
сам по себе не является allowlist и не разрешает сохранять структурные текстовые ассерты.

Дополнить руководство по тестам и короткую ссылку на него в `AGENTS.md`: поведение проверять
исполнением, структуру — общим помощником, точный текст — только при текстовом контракте.
Документация дополняет обязательный CI-контроль.

## Проверка защиты и миграций

- Возврат исходного `IndexOf`-среза и запрета подстроки `.Result` блокируется защитой.
- Такой же дефект в новом файле, вложенном каталоге и через локальный helper тоже блокируется.
- Поиск вызовов regex и проверка соседства через текстовое окно блокируются.
- Добавление нового неклассифицированного семантического вызова внутри известного файла
  обнаруживается обновлённым инвентарным тестом.
- Легитимный ассерт на сообщение, вывод CLI или генерируемый текст проходит.
- Комментарий с названием запрещённого API и строковая fixture для теста самого детектора
  не считаются исполняемым нарушением.
- Необоснованное/широкое исключение и оставшееся после удаления теста исключение отвергаются.
- Для каждого мигрированного контракта есть безопасная мутация, сохраняющая успех,
  и нарушающая контракт мутация, дающая отказ. Использовать корпус эпохи 2, дополняя
  специфические случаи; не создавать копии одинаковых тестов помощника.

## Приёмка и результат

Создать `epoch-3-results.md` с областью и командами поиска, итоговыми количествами категорий,
ссылками на инвентарь, миграции, допустимые исключения, настройку CI и результаты мутаций защиты.

Условия завершения:

1. Все найденные структурные текстовые проверки мигрированы; неразобранных кандидатов нет.
2. Повторный поиск не обнаружил кандидатов вне инвентаря; каждый оставшийся текстовый контракт
   имеет обоснование. Полнота относится к зафиксированному состоянию репозитория.
3. Защита обязательна в CI и проверена намеренным добавлением нарушения; обычный зелёный
   прогон без такой проверки не подтверждает, что защита включена.
4. Unit-набор и затронутые lifecycle-проверки проходят в требуемом окружении, без новых skips.
   После миграции всего набора выполнен полный существующий CI test-suite, включая его
   проверку отсутствия skipped-тестов. Посторонние сбои отражены отдельно, не объявлены успехом.
5. Документация показывает рекомендуемый способ написания нового структурного теста,
   механизм исключений и известные ограничения анализа.

Production-поведение и порядок членов ради прохождения новых проверок не менять.
