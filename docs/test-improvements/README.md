# Улучшение тестов: проверки формы кода через Roslyn AST

Дата: 2026-09-28. Статус: **эпохи 1 и 2 выполнены** ([архив](_archive/README.md)); эпоха 3 не начата.

Часть тестов проверяет не поведение, а **форму** production-кода: читает `.cs` как текст и ищет
подстроки, индексы и совпадения регулярных выражений. Такая проверка ломается от перестановки
членов и от появления похожих имён, а не от изменения поведения, и при этом способна пропустить
регрессию, ради которой написана. Тема — исправить известный дефект, выбрать общее решение,
найти и исправить все подобные проверки с защитой от повторения. Исходное направление — Roslyn:
синтаксическое дерево для структуры, семантическая модель для символов, рантайм-страж
там, где статический анализ слеп. [План по эпохам](#2-план-по-эпохам).

Повод: ложное падение `WorkspaceAnalyzerSanitizerTests.GetSanitizedPublishedSolution_takes_workspace_lock_and_async_does_not_call_sync`
на `prepared.Results` вместо `Task.Result`. Эпоха 1 это исправила; план и отчёт — в [архиве](_archive/README.md).
Разбор ниже — исходная диагностика, не описание текущего теста.

## 1. Проблема

### 1.1 Что проверяет красный тест

Тест охраняет контракт двух входов в кэшированный sanitized-снимок. Контракт записан словами в
XML-доке `GetSanitizedPublishedSolution`: лок берётся синхронно (`SemaphoreSlim.Wait()`, не `Task`),
повторный вход под уже взятым локом запрещён (`SemaphoreSlim` не рекурсивный), а async-вход зовёт
приватный хелпер напрямую.

| Утверждение теста | Защищаемый инвариант | Цена нарушения |
|---|---|---|
| `GetSanitizedPublishedSolutionAsync` зовёт `GetOrCreateSanitizedPublishedSolution()`, но не `GetSanitizedPublishedSolution()` | async-вход не ходит через публичный синхронный | Вечное зависание: лок уже взят, `Wait()` ждёт освобождения без таймаута — ни исключения, ни ответа клиенту |
| В синхронном входе есть `_workspaceLock.Wait(` и `_workspaceLock.Release()` | синхронный вход берёт тот же `_workspaceLock` | Гонка с загрузкой и записью: снимок читается во время публикации |
| В синхронном входе нет `.Result` и `GetAwaiter()` | нет sync-over-async | Блокировка потока пула в колбэке, который вызывается из `catch` внутри async-пайплайна; нарушение правила «Async I/O; no `.Result`/`.Wait()`» |

Синхронный вход — не «второй способ получить то же самое»: это колбэк `Func<Solution?>` для
`WithSanitizedRetryAsync`. Он вызывается **посреди уже идущего поиска** `SymbolFinder`, из `catch`,
когда Roslyn упал на checksum `UnresolvedAnalyzerReference`, и обязан быть дешёвым: только лок и
кэш, без сброса очереди диска и без ожидания задач. Девять мест вызова — в `Tools/` (`NavigationTools`,
`UtilityTools`, `TestTools`).

### 1.2 Механика ложного срабатывания

Тест добывает тела методов как **срезы текста файла между двумя объявлениями**:

```csharp
var asyncBody = source[asyncStart..syncStart];    // от async-входа до публичного синхронного
var syncBody = source[syncStart..createStart];    // от публичного синхронного до приватного хелпера
```

Неявное допущение: второй и третий методы лежат сразу после первого, то есть срез и есть тело
метода. В текущем файле это не так:

| Точка | Строка | Расстояние |
|---|---|---|
| `public async Task<Solution?> GetSanitizedPublishedSolutionAsync` | 374 | — |
| `public Solution? GetSanitizedPublishedSolution()` | 445 | 71 строка |
| `private Solution? GetOrCreateSanitizedPublishedSolution()` | 1417 | **972 строки** от предыдущей |

Срез `syncBody` разросся с 263 символов (13 строк — ровно тело метода) до **36 219 символов
(972 строки)**. В него попадает весь приватный блок класса, в том числе `CompletePrepare`:

```csharp
ApplyPublicationPlan(workspaceSolution, shadowRoot, plan, prepared.Results);
```

`prepared.Results` — позиционный параметр `AnalyzerShadowPrepareOutcome`, а `.Results` содержит
подстроку `.Result`, которую и запрещает `Assert.DoesNotContain(".Result", syncBody)`. Это
**единственное вхождение `.Result` во всём `Services/SolutionManager.cs`**.

Прогон подтверждает адрес срабатывания:

```text
Assert.DoesNotContain() Failure: Sub-string found
↓ (pos 22670)
String: ···"Root, plan, prepared.Results);\n        re"···
Found:  ".Result"
   at WorkspaceAnalyzerSanitizerTests.GetSanitizedPublishedSolution_takes_workspace_lock_and_async_does_not_call_sync()
      line 99
Total: 1 · Passed: 0 · Failed: 1
```

Позиция 22670 внутри среза — ровно `prepared.Results`. Остальные утверждения теста проходят.

### 1.3 Когда сломалось

Срез посчитан на каждом коммите, менявшем `Services/SolutionManager.cs`:

Ломающий коммит — `bd53829` «Place SolutionManager with the other public services so plugins bind one
namespace». Он переупорядочил члены файла: публичный API поднят наверх, приватные хелперы
сгруппированы внизу. Публичный синхронный вход уехал 1191 → 445, приватный хелпер 1204 → 1417;
между ними встали ~970 строк чужих членов. Diff этого коммита — один хунк на весь файл
(2482 вставки / 2491 удаление), поэтому `git blame` бесполезен, а `git status` по файлу пуст:
содержимое самого синхронного метода не менялось, изменилось только его окружение.

Тест не менялся с `acd7fa2` (`git diff acd7fa2 HEAD` по файлу пуст). Красный тест уже зафиксирован
как унаследованный в отчёте закрытой серии: `docs/archive/analyzer-shadow-copy-improvements/epoch-7-lifecycle-suite-cut.md` —
«починка вне объёма эпохи».

### 1.4 Почему это ложное срабатывание

Инвариант, который тест охраняет, **выполнен** — это проверено семантикой на загруженном воркспейсе:

- `find_symbol_references` для `SolutionManager.GetSanitizedPublishedSolution` — 9 ссылок, все в
  `Tools/` (`NavigationTools` ×6, `UtilityTools` ×2, `TestTools`), **ни одной внутри `SolutionManager.cs`**;
- `get_call_graph` для `GetSanitizedPublishedSolutionAsync` — каллее: `GetOrCreateSanitizedPublishedSolution`
  (строка 1417), `EnsureWorkspaceFromConfigAsync` (394), `FlushDirtyDocumentsUnderLockAsync` (1951);
  ребра в публичный синхронный вход нет;
- в production-коде (`Services/`, `Tools/`) нет ни одного `.Result` и ни одного `GetAwaiter()`.

Различие `Result` / `Results` семантически однозначно: `prepared.Results` — это член
`IReadOnlyList<RewriteResult>` у `AnalyzerShadowPrepareOutcome`, а запрещён `Task<T>.Result`.
Именно поэтому текстовый ассерт даёт ложное срабатывание, а семантический — не может.

### 1.5 Это класс дефекта, а не один тест

| Проверка | Как устроена | Чем уязвима |
|---|---|---|
| `WorkspaceAnalyzerSanitizerTests.GetPublishedSolutionAfterDiskSyncAsync_still_returns_raw_published_snapshot` | срез между двумя соседними публичными async-методами | Жива только потому, что методы соседствуют: вставка члена между ними расширит срез так же, как в красном тесте |
| `WorkspaceAnalyzerSanitizerTests.GetSanitizedPublishedSolution_takes_workspace_lock_and_async_does_not_call_sync` | срезы между тремя объявлениями | Уже сломана (см. выше) |
| `WorkspaceWriteBoundaryTests.Production_TryApplyChanges_has_single_SolutionManager_call_site` | `IndexOf`-цикл по всему файлу, счёт вхождений `workspace.TryApplyChanges(` | Считает по имени, а не по символу: попадёт упоминание в комментарии или вызов у другого receiver с тем же именем |
| `AnalyzerLifecycle/Epoch1SemanticInventoryTests` (инвентарь семантических входов) | `Regex`/`Contains` по `Tools/*.cs` и `Services/SolutionManager.cs` | Регексп по имени метода не отличает вызов от упоминания; перестановка членов и смена формы записи не отслеживаются |

Общее у всех четырёх: проверяется **написание кода**, а не его структура. Формулировка «вызов метода
M из тела метода N» в терминах подстрок выполнима только при дополнительном допущении о разметке
файла — и это допущение нигде не зафиксировано.

## 3. Уточнения по итогам обсуждения

### AST и сохранение контракта

Тело метода нужно находить в дереве, а не выделять между двумя объявлениями. Проверять
не только имя вызываемого члена, но и receiver: любое `Wait()` не заменяет требование
`_workspaceLock.Wait()`. Даже привязка к типу `SemaphoreSlim` не различает два разных лока.
Освобождение в `finally` и положение захвата также входят в структурную проверку.

Первоначальный эскиз `TypeCallGraph` по именам не является выбранным решением. Он смешивал
перегрузки и чужие receivers, включал невызванные локальные функции/лямбды и пропускал
некоторые формы вызова. Во второй эпохе требуется определить область поддержки, проверить
контрпримеры и не считать неизвестный результат доказательством отсутствия нарушения.

### Семантика без обязательного MSBuild

`SemanticModel` можно получить из `CSharpCompilation` с исходниками и metadata references.
Это не требует загрузки проекта через `MSBuildWorkspace`, но требует корректных source files,
ссылок, global usings, parse options и условных символов. Выполнимость и стоимость для этого
репозитория проверяются в эпохе 2; разделение «имена в unit, символы только в lifecycle»
не принимается заранее.

`CallGraphHelper.TryBuildCallGraphAsync` — кандидат на переиспользование, а не готовое
доказательство полноты архитектурной проверки. Его область анализа и возможные пропуски
нужно сопоставить с конкретным контрактом.

### Проверка зависания

Вызов async-метода может зависнуть синхронно до возврата `Task`, если все предшествующие
`await` уже завершены. Поэтому последовательность «вызвать метод, затем `Task.WhenAny`
с таймером» не защищает от рассматриваемой регрессии. Завершившаяся с исключением задача
также не означает успешную операцию: результат нужно получить и проверить.

Для заведомо зависающей мутации требуется отдельный процесс, внешний таймаут и проверенное
завершение дерева процесса. Детали и приёмка заданы в эпохе 2. Разработку такого стража
не следует включать в точечное исправление эпохи 1.

У установленного `xunit` 2.9.3 есть `FactAttribute.Timeout`. Его XML-документация предупреждает
об ограничениях параллелизации; поддержка async-тестов также описана в
[официальных release notes v2 2.7.0](https://xunit.net/releases/v2/2.7.0).
Наличие этого свойства не заменяет изоляцию зависшего исполнения. Смена раннера или версии
xUnit не входит в данную серию.

### Приёмка проверяет тесты, а не только их зелёный прогон

Основной корпус мутаций — небольшие исходники в памяти, анализируемые тем же помощником,
который используется для production-файлов. Исполняемые мутации должны компилироваться:
у `SemaphoreSlim.WaitAsync()` без результата возвращается `Task`, поэтому `.Result` на нём
не является корректной исполняемой мутацией. Для проверки свойства подходит `Task.FromResult(0).Result`.

Изменения реального production-кода ради мутаций выполняются в изолированной копии.
Ошибка компиляции, отсутствие найденных тестов, skip или ошибка подготовки окружения
не считаются успешным обнаружением нарушения.

## 4. Общие границы серии

- Production-код и порядок его членов не меняются ради удобства структурных тестов.
- Раннер не переключается; MSBuild workspace не добавляется в unit-набор.
- Исходные утверждения сохраняются либо заменяются проверками того же контракта.
- Эпоха 1 ограничена двумя тестами; эпоха 3 охватывает все подобные проверки, а не только §1.5.
- Текстовые проверки сообщений, CLI output и иных текстовых контрактов допустимы.
  Запрет касается вывода о структуре/семантике production C# по его текстовому написанию.
- Исходники с диска и исполняемая сборка — разные объекты проверки. В отчётах фиксируются
  commit, локальные изменения, конфигурация и команды; старые результаты не выдаются за новые.
- Исторические числа и строки в §1 описывают исходную диагностику. Текущий baseline снимается
  в начале реализации; численность набора и единственность исходного падения проверяются заново.
