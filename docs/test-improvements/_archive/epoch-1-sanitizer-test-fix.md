# Эпоха 1. Исправление ложного падения sanitizer-теста

Статус: **выполнена** (2026-09-28). Отчёт: [epoch-1-results.md](epoch-1-results.md); дефект
`this.`-квалификации, найденный на ревью, исправлен — §9 отчёта. Зависимости: нет.

## Цель

Исправить `GetSanitizedPublishedSolution_takes_workspace_lock_and_async_does_not_call_sync`,
который принимает `prepared.Results` из чужого метода за запрещённый `.Result`.
Результат не должен зависеть от порядка членов `SolutionManager`.

## Объём

- Две проверки в `WorkspaceAnalyzerSanitizerTests`, которые выделяют методы срезами между
  объявлениями: sanitized-входы и возврат raw-снимка из `GetPublishedSolutionAfterDiskSyncAsync`.
- Минимальные вспомогательные функции для поиска объявления и проверки его узлов.
- Регрессионные примеры для самого способа проверки.

Production-код, раннер и остальные source-based тесты в этой эпохе не менять.
Обобщённый граф вызовов и рантайм-проверка дедлока относятся к эпохе 2.

## Работа

1. Зафиксировать исходный commit, локальные изменения, версии SDK и пакетов, команду и реальное
   падение целевого теста. Не принимать историческое число тестов за текущий baseline.
2. Читать `SolutionManager.cs` через `CSharpSyntaxTree`. Находить тип по namespace и имени,
   методы — по однозначной сигнатуре. Отсутствие метода, неоднозначность или синтаксическая
   ошибка должны завершаться понятной ошибкой проверки, а не пустым успешным результатом.
3. Ограничить проверку телом выбранного метода. Комментарии, строки и соседние члены не должны
   считаться вызовами. Наличие вызова в невызванной локальной функции или лямбде не должно
   удовлетворять требование к непосредственному телу.
4. Сохранить все исходные утверждения:
   - async-вход непосредственно вызывает приватный helper и не вызывает публичный sync-вход;
   - sync-вход вызывает `Wait` и `Release` именно у `_workspaceLock`, а также приватный helper;
   - запрещённые члены проверяются по полному идентификатору, поэтому `Results` не равен `Result`;
   - raw-вход возвращает `_solution` и не вызывает sanitizer либо публикацию нового снимка.
5. Поддержать эквивалентную квалификацию через `this.`. Для лока проверять также положение:
   захват перед защищённым `try`, обращение к снимку внутри него, освобождение в его `finally`.
6. Разделить тесты, если это сделает сообщения об ошибках точнее. Каждый отказ должен указывать
   исходный метод и нарушенное утверждение, а не только отсутствие строки.

Запрет пользовательского свойства с точным именем `Result` на этом шаге остаётся ограничением
синтаксической проверки. Не заявлять, что тип receiver уже проверен или что транзитивные вызовы
покрыты; эти задачи передаются в эпоху 2.

## Приёмка

На небольших исходниках в памяти тем же кодом проверок воспроизвести следующие изменения:

- Перестановка методов, вставка чужого метода с `prepared.Results`, комментарии и строки
  с запрещёнными именами сохраняют успех.
- Прямой вызов публичного sync-входа из async-входа даёт отказ, включая форму `this.`.
- Удаление `_workspaceLock.Wait()` или `_workspaceLock.Release()` даёт отказ.
- Подмена receiver на другой лок с такими же методами даёт отказ.
- Перенос `Release` из `finally` или захвата после чтения снимка даёт отказ.
- `Task.FromResult(0).Result` и `GetAwaiter().GetResult()` в sync-входе дают отказ.
- Подмена raw-возврата на sanitized-возврат даёт отказ.
- Отсутствующий или неоднозначный целевой метод даёт диагностическую ошибку.

Для синтаксических примеров явно фиксировать границы их проверки. Если пример используется
как исполняемая мутация, он обязан компилироваться; ошибка компиляции не считается обнаружением
регрессии. `SemaphoreSlim.WaitAsync()` без результата возвращает `Task`, поэтому `.Result`
у него не является корректной исполняемой мутацией.

Прогнать целевые тесты и unit-набор из корня репозитория:

```powershell
dotnet test RoslynMcpServer.Tests/RoslynMcpServer.Tests.csproj --filter "FullyQualifiedName~WorkspaceAnalyzerSanitizerTests"
dotnet test RoslynMcpServer.Tests/RoslynMcpServer.Tests.csproj --filter "Category!=AnalyzerLifecycle"
```

Мутации production-файла, если понадобятся, выполнять в изолированной копии. Не откатывать
пользовательские изменения ради восстановления baseline и не запускать зависающий путь в testhost.
