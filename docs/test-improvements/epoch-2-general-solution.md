# Эпоха 2. Поиск и проверка общего решения

Статус: **не начата**. Зависимость: [эпоха 1](_archive/epoch-1-sanitizer-test-fix.md) (выполнена).

## Цель

Выбрать и проверить способ тестирования структурных контрактов C#, который различает
безопасный рефакторинг и нарушение инварианта. Не переносить ошибки текстового поиска
в универсальный обход по именам методов.

## Исследование

Взять несколько разных контрактов: sanitized-входы, единственную границу `TryApplyChanges`,
инвентарь семантических входов. Для каждого записать, что именно он защищает и какой уровень
проверки нужен: поведение, синтаксическая структура, привязка символов или достижимость вызовов.

Сравнить на этих примерах:

1. Узкие AST-проверки receiver, тела метода и структуры `try/finally`.
2. `SemanticModel`/`IOperation` на `CSharpCompilation`, созданной из исходников и metadata
   references без `MSBuildWorkspace`. Проверить получение реальных source files, ссылок,
   global usings, parse options и условных символов, а не полагаться только на упрощённый пример.
3. Переиспользование существующего `CallGraphHelper` в подготовленном workspace: достаточность
   выдачи, точность, ограничения и цена. Проверить, нет ли усечения или пропущенных рёбер,
   недопустимых для отрицательного архитектурного утверждения.
4. Поведенческий тест там, где он непосредственно выражает контракт и устраняет необходимость
   следить за написанием реализации.

Не требуется выбрать один механизм для всех контрактов. Измерить стоимость на одинаковом
наборе исходников: первый запуск, повторное использование компиляции, общее время unit-набора.
Зафиксировать среду и измерения. Загрузку MSBuild-проекта в unit-набор не добавлять.

## Обязательные свойства выбранного решения

- Символы сравниваются по идентичности, а не только по имени. Проверка лока различает конкретное
  поле `_workspaceLock` и другое поле того же типа.
- Область анализа явная: файлы, типы, namespace, конфигурация и активные условные ветки.
  Partial-типы не теряют части молча; совпадающие имена в разных namespace не смешиваются.
- Отсутствующий метод, неразрешённый значимый символ, ошибка входной компиляции или неподдерживаемая
  конструкция не превращаются в доказательство отсутствия запрещённого вызова.
- Прямой вызов, транзитивный путь и упоминание метода различаются. Если проверяется достижимость,
  результат содержит путь до нарушения; циклы завершают обход, перегрузки не смешиваются.
- Явно задана обработка generic-вызовов, conditional access, extension methods, локальных
  функций, лямбд и method groups. Тело невызванной функции не считается выполненным.
- Для делегатов, интерфейсной/виртуальной диспетчеризации и рефлексии записаны ограничения.
  Не обещать общий анализ потоков управления и отсутствие дедлоков.
- Проверка sync-over-async различает `Results`, пользовательский `Result` и `Task<T>.Result`.
  Отдельно определить поддержку `ValueTask`, awaiter-типов, `Task.Wait`/`WaitAll`/`WaitAny`.
  Получение awaiter само по себе и блокирующее ожидание — разные утверждения; действующий
  запрет `GetAwaiter` нельзя незаметно ослабить при переходе на семантику.

## Проверка прототипа

Создать самостоятельный набор небольших исходников с ожидаемыми результатами, независимыми
от реализации помощника. Обязательны положительные и отрицательные пары:

- `Results` и пользовательский `Result` против `Task<T>.Result`;
- нужный лок против другого `SemaphoreSlim`, правильный `finally` против неправильного;
- прямой вызов и приватная цепочка `async → wrapper → sync`;
- одноимённый метод другого receiver и безопасная перегрузка;
- вызванная и невызванная локальная функция или лямбда;
- generic-вызов, conditional access, `this.`, expression body, partial-тип;
- переупорядочивание членов, изменение форматирования, комментарии и строковые литералы;
- неразрешённый символ, неподдерживаемый путь и рекурсивная цепочка.

Для неподдерживаемого случая ожидается явная диагностика, а не зелёный результат.
Далее применить выбранное решение к тестам эпохи 1 и одному иному контракту из исследования.
Массовая миграция остальных проверок относится к эпохе 3.

## Рантайм-проверка дедлока

Добавить проверку конкретного отказа «async-вход повторно захватывает тот же лок через sync».
Вызов должен выполняться в отдельном дочернем процессе; родитель устанавливает внешний
таймаут, при превышении завершает дерево процесса и дожидается выхода. Сначала получить
сигнал готовности хоста, затем ограничивать время операции; запуск хоста тоже имеет предел.

Нормальный сценарий должен подтвердить успешный результат операции, а не просто завершение
задачи. Компилируемая мутация с повторным захватом должна дать ожидаемую ошибку таймаута,
не оставить дочерних процессов и не подвесить последующий тест. Для мутации использовать
изолированную копию сборки/исходников, не переключатель поведения в production API.

`Task.WhenAny` после прямого вызова async-метода не является такой защитой: синхронная часть
метода может зависнуть до возврата `Task`. `Task.Run` позволяет запустить таймер независимо,
но не обеспечивает завершение зависшего исполнения. Эти варианты не заменяют изоляцию.

## Приёмка и результат

- В `epoch-2-decision.md` записаны сравнение вариантов, выбранный API, область гарантии,
  диагностические отказы, источник compilation inputs, стоимость и отклонённые альтернативы.
- В `epoch-2-results.md` записаны проверки прототипа, результаты пилотной миграции и нормального/
  намеренно зависающего сценариев; проверки завершения процессов включены в результат.
- Целевые тесты и unit-набор проходят без новых skips. Если используется lifecycle-host,
  соответствующий прогон выполнен с обязательным окружением; skip не считается проверкой.
- Контракты пилотных тестов сохранены; выбранное решение доступно остальным тестам и имеет
  собственные проверки на контрпримерах.

Без решения и проверенного прототипа массовую миграцию не начинать. Если гипотеза общего
помощника не подтвердилась, выбрать и обосновать набор узких проверок в этой же эпохе.
Следующий шаг — [эпоха 3](epoch-3-migration-and-prevention.md).
