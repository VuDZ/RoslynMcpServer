# Эпоха 1 — Интеграционная проверка жизненного цикла

Статус: **планируется**. Приоритет: первый этап.

## Проблема и цель

Исторический минимальный repro подтвердил исправление исходного случая,
но не устанавливает надёжность повторных обновлений в одном процессе.
Тесты преобразования `Solution` в `AdhocWorkspace` не воспроизводят запись
настоящего `MSBuildWorkspace` и загрузку реального генератора.

Нужен исполняемый baseline: какие сценарии уже работают, какие ломаются и
какие требуют явного ограничения контракта. Гипотезы до проверки не называются
подтверждёнными дефектами.

## Сценарий

Использовать минимальное решение из Generator и Consumer с перенаправленным
`OutputPath` и `ProjectReference OutputItemType="Analyzer" ReferenceOutputAssembly="false"`.
Генератор должен выдавать наблюдаемый маркер версии, например константу `V1`/`V2`.
Семантическая проверка читает значение символа либо generated document;
одного отсутствия ошибок компиляции недостаточно.

В одном процессе сервера последовательно:

1. Собрать решение и сохранить исходные байты файлов проектов.
2. Загрузить workspace с включённым shadow copy, запросить семантическую
   модель Consumer, подтвердить маркер `V1`.
3. Повторить чтение без изменений; затем изменить обычный документ через
   штатный путь редактирования и отдельно через disk-watcher sync.
4. После каждого изменения повторить семантическую проверку `V1`.
5. Выполнить поддерживаемый rename или иной путь сохранения solution,
   полученного из overlay. Проверить сохранение запрошенного изменения.
6. Пока сервер работает, принудительно пересобрать Generator. Не считать
   успешную инкрементальную сборку без записи DLL доказательством отсутствия lock.
7. Изменить генератор на `V2`, пересобрать и выполнить полный reload workspace
   без перезапуска процесса. Проверить, какая версия реально исполняется.
8. Загрузить другое решение и затем решение с выключенным флагом; проверить,
   что состояние overlay не переносится между загрузками.
9. Проверить неизменность `.csproj` и выполнить реальную сборку всего repro.

## Дополнительные случаи

- Нет build output при первом включении; после сборки повторная загрузка.
- Несколько Consumer используют один генератор.
- Генератор с приватной helper DLL; изменение только helper DLL.
- Два генератора с зависимостями одинакового имени разных версий.

Последние два случая формируют baseline эпохи 3, а не обязательство немедленно
поддержать их в этой эпохе.

## Воспроизводимость

Тестовая инфраструктура создаёт временное решение и изолированный shadow root.
Исторический `C:\Scratch\GenRepro` не копируется в репозиторий и не требуется
для запуска. До автоматизации проверить правила репозитория о fixtures;
если fixture нельзя хранить, создавать его программно в temp.

Зафиксировать версии .NET SDK, Roslyn, ОС и команды запуска. Интеграционный
набор должен иметь документированный способ запуска; если требуется SDK
или restore, отсутствие окружения отражается как явный skip с причиной.
Тайминги watcher проверять ожиданием наблюдаемого состояния с timeout, а не
фиксированными задержками.

## Критерии завершения

- Есть воспроизводимые тесты для повторного анализа, редактирования, disk sync,
  сохранения solution, forced rebuild и reload в одном процессе.
- Для каждого сценария записан фактический результат, включая failures.
- Проверки различают правильную версию генерации, отсутствие project-file
  mutation и отсутствие блокировки build output.
- Подтверждённые дефекты сопоставлены следующим эпохам; временно ожидаемые
  failures имеют явную причину и не скрыты ослаблением assertions.

Эта эпоха может завершиться красным baseline: её результат — доказательства
и регрессионные сценарии, а не декларация готовности всего решения.
