# Критика предложения и ревью: Astra

Дата: 2026-09-20.

Историческая запись обсуждения [предложения](../proposed-solution.md) и
[существующего ревью](../review/README.md). Это мнение по результатам чтения,
не принятый план реализации и не изменение нормативных требований.

Сверка: текущее рабочее дерево при HEAD `7c931cb`, в частности
`WorkspaceDocumentDiskSync`, `WorkspaceWriteBoundary`, `SolutionManager`,
`StructuralRefactoringHelper` и `RefactoringTools`. Runtime-воспроизведение и
тесты в рамках этой критики не выполнялись. Производственный код и исходные
документы не менялись.

## Позиция

Поддерживаю A как срочное исправление disk-sync, но предложение ещё не готово
к реализации. Ревью полезное, однако его главный вывод — «убрать общий гейт,
оставить намеренный AddDocument» — недостаточно обоснован.

## 1. Конфликт с refactoring-тулами реален, но последствия описаны неверно

В C-01 существующего ревью сценарий предполагает: сначала сохраняется `.cs`,
затем `Preflight` отклоняет изменение. В коде порядок обратный:
`SolutionManager.ApplyWorkspaceWriteUnderLockAsync` вызывает `Preflight`
до `PersistDocumentChangesAsync` (`Services/SolutionManager.cs:1186`, `:1219`).

Общий гейт действительно запретит `extract_interface(createNewFile=true)`,
но не оставит частично записанный рефакторинг по описанному сценарию.

Более принципиально: намеренность `AddDocument` не делает запись через
MSBuildWorkspace безопасной. Пользователь попросил извлечь интерфейс, но это
не означает, что дублирующий `Compile Include` допустим.

Следует разделить два решения:

- Срочный патч A закрывает конкретно внешнюю синхронизацию.
- Безопасный путь структурных рефакторингов остаётся обязательной отдельной
  задачей.

Сужение гейта допустимо ради ограниченного патча, но это компромисс с известным
оставшимся дефектом, а не окончательная архитектура.

## 2. Удаление не симметрично добавлению

При добавлении workspace не видит новый тип. При удалении вариант A оставляет
в workspace документ и потенциально его старый текст. Семантические тулы
могут продолжать находить удалённый тип.

Последующее изменение этого документа через MCP может создать удалённый файл
заново: `PersistDocumentChangesAsync` использует `File.WriteAllTextAsync`,
проверки существования там нет (`Services/SolutionManager.cs:1323`). Это
сценарий риска предлагаемого поведения, а не результат runtime-проверки.

Нужен явный контракт: что разрешено читать и редактировать после обнаружения
удаления до reload. Одного предупреждения недостаточно для предотвращения
такого восстановления файла. D-07 с уровнем Low здесь недооценён.

## 3. Не определено поведение смешанного flush

Пример одной пачки: существующий `A.cs` изменён, новый `B.cs` появился.

Предложение одновременно говорит «при `Unrepresentable` не выполнять
`TryApplyChanges`» и допускает «обычный путь». Ревью C-02 тоже предлагает не
вызывать write boundary.

Если пропустить всю пачку, изменение `A.cs` потеряется для семантики:
dirty-пути извлекаются из очереди до применения
(`Services/SolutionManager.cs:1638`).

Нужно прямо закрепить: тексты известных существующих документов
синхронизируются; изменения состава отдельно устанавливают stale. Смешанная
пачка требует отдельной проверки.

Связанная деталь: сейчас `alreadyOnDisk` собирается из всех dirty-путей. Если
туда попадёт непринятый новый файл, `ReconcileSavedTextsUnderLockAsync` при
отказе применения завершится на отсутствии `DocumentId`
(`Services/SolutionManager.cs:1397`). Его вход тоже надо согласовать с новым
контрактом.

## 4. Отсутствие DocumentId не доказывает принадлежность проекту

Это может быть файл под `Compile Remove`, неактивной конфигурацией или просто
посторонний исходник. Направление C-04 верное, но формулировку предупреждения
стоит уточнить:

> Обнаружено изменение, которое может влиять на состав компиляции;
> загруженный снимок этого не подтверждает.

Reload может совершенно правильно оставить файл за пределами workspace.
Нельзя обещать «после reload новый файл появится» без оговорки о membership,
определяемом MSBuild.

## 5. Предупреждение не покрывает потерю событий watcher

При ошибке watcher выставляется только `_refreshAllDocuments`
(`Services/SolutionManager.cs:1798`). Но полный refresh в
`WorkspaceDocumentDiskSync.ApplyAsync` перечисляет лишь известные документы.
Потерянное событие создания нового файла таким способом не восстанавливается;
`Unrepresentable` не появится.

Для небольшого патча разумно при потере событий считать состав workspace
потенциально устаревшим и выдавать соответствующий hint. Иначе тест с
доставленным событием будет зелёным, а обещанная наблюдаемость останется
неполной.

## Проверка и рекомендуемое направление

С V-01 согласен полностью: сборка SDK-проекта должна видеть новый файл до
reload MCP. Reload нужен семантическому снимку. Проверять надо отдельно
отсутствие мутации `.csproj`, успешную сборку и видимость символа.

Мой выбор: A с явно определённым поведением смешанных пачек, удалений и потери
событий. Общий C пока нельзя включать без решения для структурных write-тулов,
но и объявлять его принципиально неправильным не следует.

Центральная проблема шире watcher: синхронизация состояния в памяти сейчас
проходит через API, способный записывать проект на диск.
