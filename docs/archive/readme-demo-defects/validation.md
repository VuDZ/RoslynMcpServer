# Проверка дефектов из демонстрации на Jellyfin

**Дата** — 2026-11-20. **Проверенная ревизия** — `0c5cbe3459f03471073b00a10da8174d244008f5`.
Код инструментов в этой ревизии совпадает с тегом `v1.6.0`. **Статус** — разбор завершён.
Исправления и критерии их приёмки описаны в [плане](plan.md).

Собрал `RoslynMcpServer.sln` в `Release` и запустил собранный сервер 1.6.0.0 через stdio на Windows x64.
Подключённый в чате сервер 1.5.21 служил раннером сборки и целевых тестов проекта. Для повторения вызовов
использовались два небольших SDK-проекта (`App` и зависимый xUnit-проект `Specs`), отдельный проект с задержкой
в MSBuild и проект с закреплённым старым SDK. Оригинальный прогон Jellyfin `0503e92` на Linux не повторялся.

## D-01. Незавершённый baseline попадает в счётчик изменений

**Подтверждено воспроизведением.** Фикстура с 400 простыми файлами приложения и 65 файлами тестов,
в каждом по два тестовых метода. Сразу после `load_workspace` поменял возвращаемое число в одном файле
прямой записью, без переименования. Первый `estimate_affected_tests` без `run` сообщил 1001 член в 473 файлах
и 130 напрямую выбранных тестов. Текст ответа занял 135 380 байт UTF-8. Спустя четыре секунды повторный вызов
сообщил 2 члена в 1 файле, 0 напрямую выбранных тестов и занял 993 байта. Для отредактированного файла
сохранилось `Baseline unknown`, что согласуется с правкой до фиксации baseline.

`load_workspace` публикует решение до окончания захвата. Тест `Pending_baseline_is_unknown_and_project_expanded_even_before_capture_finishes`
с управляемой паузой подтверждает, что оценка доступна в этот момент и расширяет план. Взятый в начале вызова
снимок может остаться неполным до конца запроса. `TestImpactEstimator` приравнивает `Pending` к `Unknown`,
`TestImpactComposer` включает соответствующие тесты консервативно, а `TestImpactFormatter` учитывает все
текущие члены таких документов в `Changed since load` и целиком печатает причины и `Not covered`.
[Захват](../../../Services/Testing/Baseline/BaselineSession.cs), [оценка](../../../Services/Testing/TestImpactEstimator.cs),
[форматирование](../../../Services/Testing/TestImpactFormatter.cs), [регрессионная точка](../../../RoslynMcpServer.Tests/Testing/EstimateAffectedTestsTests.cs).

## D-02. Атомарное сохранение помечает граф устаревшим

**Подтверждено воспроизведением через нативный watcher Windows.** После захвата baseline холостой вызов
дал `0 members in 0 files` и `Not covered: none`. Создал файл без расширения рядом с `Provider.cs`,
записал в него изменённую версию `Provider.cs` и вызвал `os.replace(temp, source)`. При следующей оценке
появились `1 members in 2 files`, `Path outside the loaded input map` для исчезнувшего файла и
`The project graph is stale`. `run_specific_test` сообщил, что появился или исчез `.cs`-файл вне снимка.
Набор путей `.cs` до и после замены совпадал.

Причины две. Событие для неиндексированного пути внутри области проекта может выставить `CompositionStale`
через `PotentialMembership`, а распространённая эвристика rename считает путь без расширения в этой области
каталогом даже без подтверждения. Журнал в данном прогоне зафиксировал `directory rename`. Изменение
содержимого целевого `.cs` должно участвовать в синхронизации и оценке независимо от судьбы временного пути.
[Карта входов](../../../Services/Models/WorkspaceInputMap.cs), [классификатор](../../../Services/Workspace/WorkspaceDiskEventClassifier.cs),
[обработчик и журнал](../../../Services/Workspace/SolutionManager.cs).

## D-03. Совпадающие базовые имена скрывают арность

**Подтверждено воспроизведением.** В `Demo` объявил `IProvider`, `IProvider<T> : IProvider` и единственный класс
`Provider : IProvider<string>`. Короткое имя и `Demo.IProvider` вернули два раздела `Demo.IProvider` и итог
`2 type(s)` для одного класса. `Demo.IProvider<T>` вернул `No declaration matches FQN`. Повтор `Provider`
в обоих разделах отражает реальное транзитивное отношение. Дефекты касаются имени раздела, смысла общей суммы
и обещания справочника выбрать одну базу по точному FQN. Общий резолвер строит путь типа из `Name`,
а инструмент суммирует размеры секций.
[Резолвер](../../../Services/Navigation/SymbolDeclarationResolver.cs), [инструмент](../../../Tools/NavigationTools.cs),
[форматирование](../../../Services/Navigation/ImplementationListingFormatter.cs).

## D-04. Скелет печатает внутреннее представление ILSpy

**Подтверждено воспроизведением.** Сигнатура `public Task<Provider?> Fetch(string name, ref int count)`
отображалась в скелете так:

```text
public 02000458 System.Threading.Tasks.Task`1![[02000194 Demo.Provider?]] Fetch(020000BF System.String! name, 02000160 System.Int32& count);
```

`get_decompiled_method_body` той же сборки показал C#-сигнатуру. Скелет использует `IType.ToString()`
для поля, свойства, возвращаемого типа и параметра. Подмена разделителя `/` оставляет токены,
представление generics и служебные маркеры. Размер скелета `TMDbClient` отдельно не измерялся.
[Формирование скелета](../../../Tools/CodeAnalysisTools.cs).

## D-05. Список совпадений и строки xUnit theory

**Подтверждено воспроизведением.** Для класса `Demo.Samples0` с двумя строками theory `InRange` и одним фактом
`CreatesProvider` MCP сообщил три успешных случая и строку `` Matched tests: `Demo.Samples0.InRange', 'Demo.Samples0.CreatesProvider` ``.
Парсер заменяет обратные кавычки уже после вставки разделителя. Прямой запуск VSTest также подтвердил две
разные строки `InRange(value: 0)` и `InRange(value: 1)`. Парсер снимает аргументы theory, поэтому несколько
случаев могут дать одно имя метода несколько раз. Точный источник повтора в исходном прогоне Jellyfin
по одному фрагменту установить нельзя.

В том же прогоне VSTest печатал `[< 1 ms]` для быстрых тестов. Текущий шаблон длительности требует цифру
сразу после `[` и пропускает такие строки. Этим объясняется, почему в ответах на два вызова по одному классу
при одинаковом `Total: 3` были разные списки `Matched tests`.
[Парсер](../../../Diagnostics/VstestOutputParser.cs), [тесты парсера](../../../RoslynMcpServer.Tests/TestRunner/VstestOutputParserTests.cs).

## D-06. Справочник обещает анализаторы

**Подтверждено по контракту и вызовом.** `get_diagnostics_for_file` вернул `CS0246` с координатами для
неразрешённого типа. Обработчик вызывает `SemanticModel.GetDiagnostics()` и не запускает диагностические
анализаторы. При этом английский и русский справочники называют `diagnosticId` идентификатором компилятора
или анализатора и приводят `IDE0001` как пример результата.
[Инструмент](../../../Tools/CodeAnalysisTools.cs), [английский справочник](../../tools.md), [русский справочник](../../tools.ru.md).

## D-07. Совместимость SDK и отдельная ошибка подсказки

**Поведение SDK воспроизведено.** В однопроектной фикстуре закрепил SDK `10.0.201` в `global.json`, добавил
`Microsoft.CodeAnalysis.CSharp.Features.dll` из сборки сервера как `Analyzer` и повысил `CS9057` до ошибки.
`load_workspace` загрузил проект. `run_dotnet_build` вернул `CS9057` с версиями Roslyn `5.9.0.0` и `5.3.0.0`.
Совместимость компилятора с анализатором проверяется при реальной сборке. Условие для примера Jellyfin
уже описано в его инструкции запуска.
[Документация CS9057](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/compiler-messages/source-generator-errors),
[настройка примера](../../readme-examples/README.md#setup).

В этой же фикстуре обнаружилась **ложная `MCP_MSBUILD_SDK_MISMATCH`**. Контекст команды и лог содержали
один SDK `10.0.201`. Путь MSBuild из подробного лога был в кавычках, а ожидаемый путь был без кавычек.
Извлечение оставляет кавычки, и сравнение считает пути разными. Это отдельное исправление диагностики
сборки, связанное с проверкой D-07.
[Извлечение пути](../../../Diagnostics/MsBuildLogHighlighter.cs), [сравнение](../../../Diagnostics/SdkMismatchDiagnostics.cs).

## D-08. Лимит шага сборки нельзя настроить

**Подтверждено воспроизведением.** В SDK-проекте цель перед `CoreCompile` запускала локальный дочерний процесс
с паузой 205 секунд. С `noIncremental: false` `run_dotnet_build` дошёл до цели и вернул `Build timed out`,
`TIMED OUT after 180s` и `MCP_DOTNET_TIMEOUT`. В Windows получен exit `-1`. Сервер закончил вызов примерно
за 181 секунду. Обработчик не передаёт бюджеты в `DotNetBuildProbe`, поэтому действует 180 секунд на шаг
и 300 секунд на пробу. Подсказка с `Get-Process dotnet` формируется общим методом без проверки ОС.
[Инструмент](../../../Tools/BuildTools.cs), [бюджеты](../../../Services/Build/DotNetBuildProbe.cs),
[подсказка](../../../Services/Build/DotNetCliRunner.cs).

## Сборка и целевые тесты

Release-сборка решения прошла. Из 117 целевых тестов по baseline, watcher, навигации, декомпиляции, VSTest
и сборке прошли 116. `DotNetCliRunnerHangTests.RunWithMetadataAsync_times_out_and_kills_long_running_process`
упал на `Assert.True(run.TimedOut)` и повторно упал отдельно. При прямом повторе цели теста MSBuild 11.0.100
не нашёл `ping` в оболочке (`9009`). Из-за `IgnoreExitCode="true"` цель завершилась успешно без паузы.
Таймаут публичного `run_dotnet_build` подтверждён отдельным прогоном с управляемой задержкой, описанным в D-08.
Полная CI-сюита относится к приёмке будущих исправлений.
