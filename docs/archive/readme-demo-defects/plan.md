## 1. D-01 — готовность baseline и объём ответа TIA

В `TestTools.EstimateAffectedTests` проверять `Pending` по тому же снимку, из которого строится план.
Пока захват исходников продолжается, возвращать короткий статус с числом ожидающих документов и предложением
повторить вызов. Это правило действует и для `run: true`: до готовности baseline инструмент не запускает сборки
и тесты. `load_workspace` по-прежнему публикует решение сразу. Использовать существующее состояние `Pending`,
чтобы обойтись без нового API ожидания и без удержания блокировки при захвате.

После окончания захвата сохранять консервативный выбор для `Unknown`, включая изменение до захвата и
прерванный capture. Печатать количество подтверждённых изменений отдельно от числа документов с неизвестной
базой. В `TestImpactFormatter` группировать однотипные причины по проекту и объединять пути в счётчик
с несколькими примерами. Ввести общий лимит текста с явным количеством пропущенных строк. Предлагаемый
порог для стандартного ответа — 32 КиБ UTF-8. При `includeDetails` сохранить ограниченный подробный вывод.
В приоритете итог, статус запуска, причины широкого выбора и предупреждения о покрытии.

**Приёмка.** Детерминированный тест с `BaselineCaptureGate` меняет один файл, пока другой документ остаётся
`Pending`. Оба режима возвращают статус готовности и не создают дочерних процессов. После снятия паузы
неизвестным остаётся только действительно затронутый контекст. Добавить случаи reset/reopen с замороженным
`Unknown`, нормальный план после готового baseline и тест форматтера с сотнями причин. Проверить объём
и неизменность полноты внутреннего плана относительно ограничения текста.

## 2. D-02 — распознавание замены загруженного файла

Обрабатывать пару временный путь → загруженный пользовательский `.cs` как замену содержимого, когда watcher
и текущая карта подтверждают сценарий. Целевой путь был известен до rename и существует после него.
Временный путь отсутствует, не является известным входом и не несёт признаков каталога или изменения входов
MSBuild. Проверять это при сверке ожидающих событий с диском. Пара rename должна перекрывать предшествующие
события Create/Change только для этого временного пути. Провести изменение целевого `.cs` через обычную
синхронизацию. События по целевому документу должны по-прежнему защищать захват baseline от записи после загрузки.

Исключать именно подтверждённый временный путь из журнала причин stale и списка TIA. Для неоднозначных
событий сохранять консервативное поведение. Признак stale по другому событию нельзя сбрасывать при обработке
замены. Событие для пути без расширения само по себе не доказывает, что перемещён каталог.

**Приёмка.** Тест классификации и нативный сценарий с `File.Move(temp, source, overwrite: true)` на Windows
и `sed -i` на Linux. Перед заменой дождаться baseline. Сравнить TIA после обычной записи и атомарной замены
при одинаковых изменениях и одинаково свежих выходных сборках. Ожидать один путь, чистый граф, одинаковый
выбор тестов и отсутствие ложной подсказки в `run_specific_test`. Контрольные случаи сохраняют реакции
на добавление, удаление и перенос `.cs`, замену явного `AdditionalFiles`, реальный rename каталога, правку
`.csproj` в той же серии событий и потерю событий watcher.

## 3. D-08 — настраиваемый бюджет `run_dotnet_build`

Добавить необязательный `timeoutSeconds`. Пропущенный параметр сохраняет 180 секунд на шаг и 300 секунд
на пробу. Положительное значение задаёт общий бюджет всех дочерних шагов, включая restore и повторные
сборки. Каждый следующий шаг получает остаток бюджета. `0` снимает серверный лимит дочерних шагов.
Отрицательные значения отклоняются до запуска. Отмена клиентом продолжает останавливать активный процесс,
в том числе при `0`. Клиентский таймаут `tools/call` остаётся отдельным ограничением. Для общей подсказки
оставить `Get-Process dotnet` на Windows и показать `ps` на Unix. Обновить справочники EN/RU и `get_tool_help`.

**Приёмка.** Проверить схему MCP, прежние значения при пропуске, отрицательное значение, успех при достаточном
бюджете, истечение короткого бюджета внутри шага и перед повторным шагом, режим `0` и отмену. Сохранить
проверку убийства дерева процесса с воспроизводимой задержкой. В существующей Windows-фикстуре устранить
зависимость от поиска `ping` в PATH и сделать ошибку запуска видимой тесту. Проверить тексты подсказок на обеих ОС.
[Инструмент](../../../Tools/BuildTools.cs), [проба](../../../Services/Build/DotNetBuildProbe.cs),
[тесты пробы](../../../RoslynMcpServer.Tests/Build/DotNetBuildProbeTests.cs),
[тесты таймаута](../../../RoslynMcpServer.Tests/Build/DotNetCliRunnerHangTests.cs).

В том же пакете исправить находку из [D-07](validation.md#d-07-совместимость-sdk-и-отдельная-ошибка-подсказки).
Снять парные кавычки при извлечении `MSBuild executable path` из лога, чтобы нормализованное значение
использовалось и в подсказке, и при выборе дополнительного restore. Проверить одинаковый путь с пробелами в
кавычках, реальное несовпадение путей и сохранение `CS9057` с версией SDK. Для самого ограничения SDK достаточно
существующей инструкции запуска Jellyfin. Проверку версий всех анализаторов при `load_workspace` план не добавляет.

## 4. D-03 — различимые базы и точный итог

Для заголовка использовать квалифицированное C#-имя с параметрами типа. Сохранить строки реализаций
в каждом применимом разделе. Общий итог считать по уникальным символам Roslyn. Если важно показать
число строк, подписать их как связи «база → реализация». Добавить в `find_implementations` точный поиск по
выведенному generic FQN, например `Demo.IProvider<T>`. В совпадающей паре `Demo.IProvider` выбирает
необобщённый тип, короткое `IProvider` возвращает обе базы. Оставить старое квалифицированное имя
без параметров рабочим для существующего однозначного generic-типа. Описать это в справочниках EN/RU.

**Приёмка.** Фикстура с двумя арностями и общей реализацией показывает два различимых раздела и один
уникальный класс. Проверить копирование имён в отдельные запросы, `transitive: false`, разные namespaces,
существующий однозначный generic FQN и `maxResults` с overflow. Общий формат имён других навигационных
инструментов менять только при независимой необходимости.
[Форматтер](../../../Services/Navigation/ImplementationListingFormatter.cs),
[резолвер](../../../Services/Navigation/SymbolDeclarationResolver.cs),

## 5. D-04 — сигнатуры C# в скелете

Использовать форматирование сигнатур ILSpy, например `TypeSystemAstBuilder`, для полей, свойств,
возвращаемых типов и параметров. Использовать преобразование объявления параметра для `ref`/`out`/`in`.
Формировать скелет из метаданных без декомпиляции тел. Сохранить отбор public/protected, порядок, отмену
и заметку о неразрешённых зависимостях.

**Приёмка.** Фикстура DLL содержит nullable reference/value types, вложенный generic, массив и by-ref
параметры. Сигнатуры читаются как C#, сохраняют `?` и модификаторы параметров. Проверить отсутствие
служебных токенов, доступность скелета с отсутствующей зависимостью и smoke `RestRequest` из TMDbLib.
[Код скелета](../../../Tools/CodeAnalysisTools.cs), [форматирование типов в ILSpy](https://github.com/icsharpcode/ILSpy/blob/master/ILSpy/Languages/CSharpLanguage.cs),

## Приёмка изменений

Для быстрой обратной связи запускать целевые проверки из каждого пакета. После изменений production C# выполнить
все `RoslynMcpServer.Tests/SourceStructure`. Перед приёмкой собрать решение в Release и прогнать полную основную
сюиту `RoslynMcpServer.Tests` с фильтром `Category!=AnalyzerLifecycle&Category!=RequiresPinnedSdk`, на Linux
добавить `&Category!=RequiresWindows`. Для пакета D-02 отдельно выполнить `AnalyzerLifecycle` с
`ROSLYN_MCP_ANALYZER_LIFECYCLE=1`, поскольку затронут общий путь watcher и публикации workspace. После изменений
только в справочниках D-06 достаточно сверить документацию.

На Linux повторить сценарии TIA и длинной сборки из отчёта на Jellyfin с совместимым SDK, предварительно проверить
чистую сборку и сделать компилируемую правку. Для D-08 зафиксировать поведение с ограничением по умолчанию
и с достаточным `timeoutSeconds`. Для D-01/D-02 сравнить счётчики, причины широкого выбора, размер ответа и
реально запущенные проекты. Записать результаты и статус каждого исправления в каталог дефектов и в индекс.
