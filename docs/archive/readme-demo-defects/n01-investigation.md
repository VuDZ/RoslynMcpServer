# N-01. Пересборка без правок расширяет план TIA

**2026-11-21. Исправление принято.** После полной пересборки без правок план TIA пуст.
Реальная правка перед пересборкой остаётся видимой. Прошли независимое ревью, сквозная проверка
на Jellyfin и Release-сюиты Windows и Linux. [Итоговая проверка](#проверка-исправления).

[Первичный отчёт и сценарий на нативном Linux](linux-recheck.md#n-01-полная-пересборка-расширяет-tia-до-всех-тестовых-проектов).

## Воспроизведение до исправления

WSL2 Ubuntu 24.04 x64, SDK 10.0.404, сервер 1.6.1.0 из `958c3d0`. Коммит `858d6a8`
добавляет отчёт и сценарии, код сервера совпадает. Jellyfin `821b849e61f6bd0fa760c76de2dc1f39400abd44`,
Release, 41 загруженный проект. Перед первой оценкой дождались завершения захвата baseline исходников и
сборок. В копии Jellyfin не было правок отслеживаемых файлов до и после проверки.

Оценка сразу после захвата и после инкрементальной сборки `Jellyfin.Naming.Tests` дала 0 изменённых
файлов, 0 проектов и `Not covered: none`. Затем в том же MCP-процессе выполнили команду:

```sh
dotnet build tests/Jellyfin.Naming.Tests/Jellyfin.Naming.Tests.csproj -c Release \
  --no-incremental --no-dependencies --no-restore
```

Сборка прошла. TIA показала 0 изменённых членов, 1 файл и 1 тестовый проект целиком.
Причина — `Non-C# input changed` для `Jellyfin.Naming.Tests.GeneratedMSBuildEditorConfig.editorconfig`.
Отдельно появился `Project graph stale`. Вызов `run_specific_test` запустил 2 теста `StubTests`, оба
прошли, но в ответе появилась заметка о появлении или исчезновении `.cs`. SHA-256 всех пяти
проверенных файлов `.cs` и `.editorconfig` из `obj/Release/net10.0` совпали до и после сборки,
у четырёх файлов изменилась метка времени.

Повторный `load_workspace` и последовательность `reset_workspace` → `load_workspace` сняли
`Project graph stale`. В обоих случаях остались 1 файл, 1 проект целиком и отметка
`Reload/reopen observation window`. Новый MCP-процесс с тем же решением вернул 0 файлов и
0 проектов без ограничений. `BaselineSession.Interrupt` завершает захват, а `Publish` сохраняет
исходный baseline при повторном открытии того же пути.

В отдельной новой сессии MCP вызов `run_dotnet_build` для всего `Jellyfin.slnx` без параметра
`noIncremental` завершился с `Build succeeded`. Оценка выросла с 0 файлов и 0 проектов до
`0 members in 41 files`, всех 17 тестовых проектов целиком и `Project graph stale`. Это тот же
результат, что на нативном Linux. Предварительная попытка полной сборки через shell с
`--no-restore` завершилась ошибкой Jellyfin `CS0234` в `MediaBrowser.Model`. Успешный прогон MCP
выполнен после обычной подготовки сборки с restore.

## Подтверждённые причины

1. В новой сессии записали только те же байты в сгенерированный `.editorconfig`. TIA выбрала
   1 проект целиком по причине `Non-C# input changed`, состояние графа осталось свежим.
   Входная карта даёт этому пути роль `AnalyzerConfig`. `SolutionManager.QueueDiskPath` записывает
   событие в журнал baseline, а `TestImpactEstimator` берёт путь из `TouchedPaths` без сравнения
   с исходным содержимым. Существующее сравнение в `WorkspaceInputSession.ApplyContentObservation`
   проверяет эхо записи через MCP по её сохранённым байтам. Исходный текст analyzer config в нём
   не участвует.
2. В двух независимых новых сессиях удалили и через 0,6 с восстановили с теми же байтами
   `XunitAutoGeneratedEntryPoint.cs` и `SelfRegisteredExtensions.cs`, по одному файлу за прогон.
   Обе оценки дали 0 изменённых файлов и 0 проектов, но показали `Project graph stale`.
   Диагностический тест прошёл и подтвердил во входной карте живого решения роль `UserInput`
   для обоих файлов. Контрольный `Jellyfin.Naming.Tests.AssemblyInfo.cs` имел роль `Unknown`.
   `WorkspaceDiskEventClassifier.ClassifyKnown` считает отсутствие известного `UserInput` признаком
   изменения состава. Восстановление файла не снимает уже выставленный флаг.

## План исправления

1. **Сверять содержимое analyzer config с baseline.** Сохранить отпечатки загруженных analyzer config
   для первой публикации baseline. При оценке убрать путь из набора изменений TIA, если его текущее
   содержимое стабильно и совпадает с исходным. Переиспользовать проверку стабильности чтения и ревизии
   пути, чтобы запись во время чтения не скрыла изменение. Реальная правка, удаление, недоступный файл
   и неизвестный baseline должны по-прежнему расширять план. Изменение analyzer config должно доходить
   до опубликованного workspace, а настоящие изменения входов должны сохранять инвалидацию результатов сборки.
2. **Учитывать восстановление уже загруженного C#-пути.** Отложить постоянную отметку об изменении
   состава до сверки событий в рамках активной сессии. Для известного ранее присутствовавшего
   файла безопасный случай — восстановление по тому же пути с теми же байтами при сохранённом
   составе проекта и непрерывном наблюдении. Снимать основание только для этого пути. Сохранять
   отметки при реальном удалении, добавлении нового Compile-файла, изменении файла проекта или
   потере наблюдения. Явные `Compile` и `AdditionalFiles` под `obj` остаются учитываемыми входами.
3. **Проверить регрессии и реальную пересборку.** Раздельные тесты должны ловить ложный
   `Non-C# input changed` и ложный `Project graph stale`, даже если второй симптом уже исправлен.
   Контрольные сценарии — настоящий новый текст analyzer config, постоянное удаление известного
   C#-файла, изменение `.csproj` в том же пакете событий и правка одного метода перед пересборкой.
   На Jellyfin после успешной пересборки без правок ожидаются 0 файлов, 0 проектов и отсутствие
   заметки у `run_specific_test`. После правки метода план должен соответствовать этой правке.
   Для приёмки также нужны Release-сборка, `SourceStructure`, основная CI-сюита и `AnalyzerLifecycle`
   при изменении путей публикации workspace.

На выпущенной 1.6.1 для цикла со сборкой перед TIA подходит `run_dotnet_build(noIncremental: false)`.
Если полная сборка уже загрязнила baseline, новый процесс начинает отсчёт с текущего состояния диска.
Поведение `run_dotnet_build` по умолчанию предлагается оставить прежним.

## Реализация

- TIA исключает путь analyzer config из списка изменений только при совпадении исходного
  отпечатка, устойчиво прочитанных байтов и текстов всех документов этого пути в опубликованном
  снимке. Первоначальные отпечатки фиксируются до запуска watcher. События и ревизии входов
  продолжают учитываться, а неизвестное содержимое сохраняет консервативный план.
- Временное отсутствие загруженного C#-файла учитывается отдельно. Возвращение того же пути
  при прежнем составе снимает только его отметку, а возвращённый текст проходит синхронизацию.
  Если запрос успел обработать реальное отсутствие или произошла потеря наблюдения, необходимость
  перезагрузки сохраняется. Отменённая синхронизация возвращает пути в очередь для следующего запроса.
- Независимое ревью и повторная проверка закрыли пять замечаний о задержке событий, сравнении
  с опубликованным снимком, старых байтах собственных записей и отмене синхронизации. Для всех
  пяти сценариев добавлены регрессионные проверки.
