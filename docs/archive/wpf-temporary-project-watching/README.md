# WPF: временные проекты и кеш Solution

Дата: 2026-09-30. Статус: **закрыто 2026-10-01**. Поведение записано в [ARCHITECTURE](../../ARCHITECTURE.md) и product README v1.5.1. GitHub Release этим закрытием не создаётся.

Пожелание 1: сборка WPF-проекта создаёт и удаляет `*_wpftmp.csproj`,
из-за чего следующая загрузка Solution перестаёт попадать в кеш.
Задача серии — убрать эту ложную инвалидацию, сохранив реакцию на реальные
изменения проекта. Достаточно одной [эпохи](epoch-1-ignore-temporary-projects.md).

## Текущее основание

Проверено по исходникам на commit `045b839`, source version `1.5.0`.
Версия сервера коллег и воспроизведение на их Solution пока не получены.

- [SolutionManager.QueueDiskPath](../../../Services/SolutionManager.cs)
  передаёт события любого проектного файла в `MarkProjectGraphStaleFromGraphFile`.
- [WorkspaceDiskPathFilter.IsProjectGraphFile](../../../Services/WorkspaceDiskPathFilter.cs)
  распознаёт `.csproj` по расширению; членство в Solution не проверяется.
- `LoadCoreAsync` использует кеш только при `!_projectGraphStale`.
  Событие выставляет stale; фактическое переоткрытие происходит при следующем
  `load_workspace`, а не немедленно внутри callback.
- Файлы внутри каталогов с именем `obj`/`bin` уже отсекаются. Для описанного
  симптома существенны временные проекты вне этих каталогов. Внутренний
  `BuildProjectFile` обычно пишет промежуточные результаты в `obj`; их события
  и событие самого временного `.csproj` нужно различать.
- В коде есть две независимые причины stale: graph-file и composition.
  `OnDiskWatcherError` выставляет только `_refreshAllDocuments`, но следующий
  `FlushDirtyDocumentsUnderLockAsync` при `refreshAll=true` вызывает
  `MarkProjectGraphStaleFromComposition`, даже без изменений документов.
  Поэтому overflow может косвенно привести к cache miss через semantic flush.
- `LoadCoreAsync` проверяет stale до flush. Один вызов может ещё получить
  cache hit и выставить composition stale при flush; следующий уже переоткроет
  граф. Одного результата `load_workspace` недостаточно для диагностики.

Механизм создания и удаления временного проекта виден в
[GenerateTemporaryTargetAssembly](https://github.com/dotnet/wpf/blob/main/src/Microsoft.DotNet.Wpf/src/PresentationBuildTasks/Microsoft/Build/Tasks/Windows/GenerateTemporaryTargetAssembly.cs).
Это подтверждает правдоподобность причины, но не заменяет воспроизведение
на SDK и проекте коллег.

## Имя и расположение временного проекта

Обычная форма для C# — `{ProjectName}_{random}_wpftmp.csproj`. Отдельный
предикат проверяет расширение `.csproj` и окончание **имени без расширения**
`_wpftmp`, без учёта регистра. Он определяет кандидата для исключения;
принадлежность загруженному графу проверяется отдельно.

`Foo_abc_wpftmp.csproj` подходит по имени; `Foo_wpftmp_Bar.csproj` не подходит.
Разбирать или проверять формат случайного компонента не требуется. Вхождение
`_wpftmp` только в имени каталога тоже не является основанием для исключения.

Обычно временный файл появляется рядом с проектом. В legacy-задаче имя
относительное; в проверенных современных
[Microsoft.WinFX.targets](https://github.com/dotnet/wpf/blob/main/src/Microsoft.DotNet.Wpf/src/PresentationBuildTasks/Microsoft.WinFX.targets)
оно также формируется без абсолютного каталога. Baseline фиксирует фактический
полный путь, CWD команды `dotnet build` и доступные сведения о рабочем каталоге
задачи. Не предполагать, что каталог задачи всегда совпадает со стартовым CWD
команды, и не ограничивать исключение только каталогом исходного проекта.

## Контракт

- `IsProjectGraphFile` сохраняет классификацию `.csproj` как graph file.
  Предикат временного имени отдельный; решение об исключении принимается
  в `QueueDiskPath` до установки graph-file stale.
- Исключение применимо, только если имя соответствует предикату и
  нормализованный полный путь отсутствует в снимке загруженных `Project.FilePath`.
  Created/Changed/Deleted такого временного файла не инвалидируют граф.
- Изменение настоящего проекта, Solution или значимого проектного входа
  сохраняет сегодняшнюю реакцию на stale в пределах существующих фильтров.
- Снимок путей материализуется под `_workspaceLock` при старте watcher,
  до включения событий; пути нормализованы, сравнение соответствует ОС.
  Callback использует неизменяемый снимок своей watcher-сессии, не читает
  текущий `Solution` и не захватывает `_workspaceLock` ради классификации.
- Загруженный проект с суффиксом `_wpftmp` сохраняет приоритет над исключением.
  Deleted и старая сторона Rename проверяются по снимку, без `File.Exists`.
- Обе стороны file Rename проходят правило независимо. Для переименования
  `Loaded_wpftmp.csproj` → `Other_wpftmp.csproj` старая сторона взводит stale,
  если она была загруженным проектом. Выход по условию «оба имени временные»
  до проверки принадлежности запрещён.
- Снимок связан с экземпляром/сессией watcher. После stop/reset/reload поздний
  callback не должен классифицировать старое событие по снимку новой сессии
  или менять её stale-состояние.
- Владелец и generation этой сессии общие с будущей картой входов по
  [input-state-contract](../project-input-watching/input-state-contract.md).
  WPF-фикс может первым создать минимальный token + `loadedProjectPaths` context;
  watcher-серия расширяет тот же источник, не вводя второго session counter.
- Сборка может иметь другие причины инвалидировать snapshot. Серия обещает
  устранить именно ложное событие от временного проекта, а не безусловный
  cache hit после любой сборки.

## Диагностика baseline и предел исправления

При неизменном ключе загрузки разделять graph-file stale, composition stale,
refresh-all pending и факт cache hit/reopen. Снимать состояния до build,
после доставки событий, после semantic flush и повторных загрузок; фиксировать
порядок вызовов, иначе отложенная composition-инвалидация будет пропущена.

Строка `Project graph file changed on disk` с путём временного проекта —
свидетельство нужной причины. Её отсутствие при выключенном Information-логе
или сбое logger ничего не доказывает. Нужны доступный лог и проверка состояний.
Цепочка overflow → refresh-all → composition stale описывается отдельно;
её поведение эта эпоха не исправляет.

Если baseline показывает только настоящую правку `.csproj`,
`Directory.Build.props`, `.sln` или другой вход без инвалидации от временного
проекта, остановить реализацию по WPF-гипотезе и сообщить причину.
При смешанных причинах разделить их и получить изолированный WPF-сценарий:
такой baseline сам по себе не доказывает устранение всего cache miss.
Расширять фильтр на настоящие входы ради успешного cache hit запрещено.

## Границы и порядок

Локальное исправление можно выполнить первым, независимо от двух других серий.
Общий учёт принадлежности файлов появится в
[project-input-watching](../project-input-watching/README.md); классификатор
временных проектов должен переиспользоваться там.

Переиспользование общего предиката имени возможно до закрытия/ship WPF-серии;
это не разрешение объявить её cache-fix проверенным без собственного baseline.

Автосборка перед DLL-тестами описана отдельно в
[test-build-freshness](../../test-build-freshness/README.md). Публикация generated
кода, reload после сборки и analyzer shadow-copy этой серией не меняются.
Долговременный кеш Solution остаётся в
[workspace-load-cache](../../workspace-load-cache/README.md).
