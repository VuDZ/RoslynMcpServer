# Причины и проверка исправлений P1-49–P2-54

Основание — `f82d4ff`. Исходные воспроизведения находятся в [отчёте повторного ревью](review-f82d4ff.md).

## Первопричины

- **P1-49.** Метаданные design-time использовались как доказательство того, как обычный Csc прочитает файл. Это разные вычисления MSBuild. Стабильность первых метаданных сама по себе ничего не говорит о втором вычислении.
- **P1-50.** Нормализация строк была частью и поиска, и записи всего результата. Совпадение в нормализованном тексте позволяет найти диапазон замены. Участки вне диапазона должны попасть в файл из исходного текста.
- **P1-51.** Переименование меняло только объявление `Include`. Другие операции используют то же item-сопоставление. Смена идентификатора ссылки может изменить, какие метаданные и исключения MSBuild к ней применит.
- **P2-52.** Отсутствие строки с именем использовалось как доказательство нулевого количества совпадений. Положительный итог прогона и возможность подтвердить имя имеют разную доказательную силу.
- **P2-53.** Атомарная подмена одного имени меняет соответствие имени файловому объекту. Остальные жёсткие ссылки по-прежнему принадлежат прежнему объекту.
- **P2-54.** Появление имени файла использовалось как сигнал о завершённой записи. Читающий тест мог открыть путь раньше публикации готового списка PID.

P1-49 и P1-50 затрагивают один контракт сохранения исходника. Первая проверяет интерпретацию байтов компилятором, вторая сохраняет границы текстовой замены. P2-53 защищает другую часть той же операции, файловую идентичность. Каждая из этих причин устраняется в своём месте.

## P1-49

Первый вариант проверки вызывал цели MSBuild и мог менять рабочую копию даже при последующем отказе редактора. Оценка проекта теперь отделена от выполнения целей. Дополнительное воспроизведение использует два проекта с разными `CodePage`. Второй включает файл первого только при обычной сборке. Проверка только владельцев из Roslyn пропускала второго читателя, и свежий компилятор получал `0043 0061 0066 00C3 00A9`.

Выбор TFM при `load_workspace` ограничивает снимок, а обычная сборка может собрать все TFM. Регрессии проверяют лишнего читателя, смену `Compile` внутри цели, параметры `ProjectReference` и изменения свойств и элементов, из которых штатная диспетчеризация SDK строит список внутренних сборок. В публичной проверке `-t:_ComputeTargetFrameworkItems -getItem:_InnerBuildProjects` подтвердил добавление второго TFM, а MCP отказал до записи.

## P1-50

Поиск по-прежнему сопоставляет нормализованный текст. Патч переводит границы совпадения в координаты исходного текста, копирует все промежутки из него и применяет правила перевода строк только к замене. Через публичный MCP байты соседнего литерала `41 0A 42` сохранились. Свежая сборка напечатала `0041 000A 0042` и новое значение `Y`.

## P1-51

План сохраняет связь между литеральными операндами `Include`, `Exclude`, `Update` и `Remove`. Проверка на Ubuntu с файловой системой ext4 установила, что сравнение путей MSBuild при оценке элементов не зависит от регистра. Если перенос меняет неоднозначное сопоставление или сопоставление внутри `Target`, инструмент возвращает отказ до перемещения. Через публичный MCP `ReferenceOutputAssembly=false` сохранилось, сборка `App` до и после переименования прошла.

## P2-52

Парсер сверяет строки с именами, сводку и подтверждённые сообщения VSTest для отдельных сборок. Минимальный логгер может подтвердить `1 passed` без имени. Сообщение для другого эффективного фильтра не подтверждает исход запрошенного. Сценарий с `TreatAsLocalProperty` воспроизведён на настоящем VSTest.

В проверках вывода успешной предварительной сборки фикстуры теперь содержат строку выполненного теста. Это позволяет проверять отсутствие диагностического блока при подтверждённом успехе. Для сводки без имён отдельная регрессия проверяет частичный отчёт с сохранёнными счётчиками.

## P2-53

Оба пути записи проверяют количество жёстких ссылок на открытый файл перед заменой. При нескольких ссылках операция отказывает и удаляет подготовленный файл. Публичный MCP на NTFS сохранил `samefile == True` и `before\n` по обоим путям. Проверка на Unix использует `SystemNative_FStat` из целевой .NET 11, которая согласует разные ABI `stat`. Формат `FileStatus` необходимо проверять при смене целевой версии .NET. [Код .NET 11](https://github.com/dotnet/runtime/blob/v11.0.0/src/native/libs/System.Native/pal_io.h)

### Linux self-contained и single-file

26 ноября 2026 года имя импорта исправлено на `libSystem.Native`. Хост .NET сопоставляет имя встроенной библиотеки целиком. В обычной публикации прежнее имя разрешалось через поиск вариантов имени `.so`. [Код хоста .NET 11](https://github.com/dotnet/runtime/blob/v11.0.0/src/native/corehost/hostpolicy/hostpolicy_context.cpp#L54-L68)

SDK 11.0.100 опубликовал полный сервер для `linux-x64` в обычном self-contained каталоге и в режиме `PublishSingleFile=true` с `IncludeNativeLibrariesForSelfExtract=true`. Во второй публикации временное правило MSBuild удаляло оба флага из `ProjectReference` на отдельный BuildHost. В каталоге этой сборки отсутствовали `RoslynMcpServer.dll` и `libSystem.Native.so`. SDK сообщил `NETSDK1236` об исключении из бандла манифестов BuildHost и статической библиотеки SQLite.

В Ubuntu 24.04 под WSL обе сборки запустили настоящий MCP-сервер. `update_file_content` и `apply_patch` заменили существующий файл, сохранив режим `0640`. Проверка подтвердила новый inode и ожидаемые байты после каждой операции. Попытка записать файл с двумя жёсткими ссылками вернула отказ, а оба пути сохранили прежний inode и содержимое. Повторная Release-сборка и все 2 892 теста Windows прошли без пропусков, включая 128 SourceStructure и 13 AnalyzerLifecycle.

## P2-54

Пишущая фикстура закрывает временный файл перед публикацией PID через перемещение в том же каталоге. Управляемая задержка на Windows воспроизвела прежний `0x80070020`. После исправления путь появлялся только после закрытия файла и сразу содержал `123,456`. Оба варианта отмены и тест таймаута используют эту публикацию.

## Release-проверка

25 ноября 2026 года прошла сборка решения `RoslynMcpServer.sln` в Release на Windows с SDK 11.0.100. Набор `Category!=AnalyzerLifecycle` разделён по правилам Windows CI. В основном шарде прошло 2 730 тестов, включая все 128 SourceStructure. В шарде TIA прошло 149 тестов. С `ROSLYN_MCP_ANALYZER_LIFECYCLE=1` прошли все 13 AnalyzerLifecycle. Всего прошло 2 892 теста, без ошибок и пропусков. Отдельный целевой прогон тестов отмены и таймаута в группе TIA прошёл 13/13.

В публичном MCP обе операции P1-49 отказали без записи для несовпадающих кодовых страниц. В публичном сценарии с двумя проектами патч отказал, когда второй читатель был виден только обычной сборке. При одинаковой настройке Latin-1 свежая сборка вывела `0043 0061 0066 00E9`. В реальном VSTest минимальный лог сохранил итог `1 passed` без подтверждённого имени. Обычный лог подтвердил имя, отсутствующий тест дал no-match, а запуск с переопределённым фильтром оставил статус частичным.

В исходной проверке Ubuntu/WSL на ext4 отдельная self-contained проба .NET 11 получила число ссылок 1 → 2 на одном дескрипторе и воспроизвела сбой загрузки `System.Native` в single-file. Исправление проверено [на обеих публикациях полного сервера](#linux-self-contained-и-single-file). Штатный профиль выпуска использует `PublishSingleFile=false`.
