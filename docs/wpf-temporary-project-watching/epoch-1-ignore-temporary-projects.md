# Эпоха 1. Исключение WPF-временных проектов

Статус: **реализация и приёмка завершены 2026-10-01; выпуск не выполнен**. Сложность: небольшая; нужна интеграционная проверка WPF.

## Цель и изменения

Устранить ложную graph-file инвалидацию от WPF-временного проекта. Порядок:
baseline → подтверждение причины → отдельный предикат и снимок → проверки.

## Baseline и проверка гипотезы

1. Загрузить WPF-Solution и собрать его. Fixture вызывает temporary-assembly
   pass, например через XAML со ссылкой на тип из того же проекта.
2. Зафиксировать SDK/ветку WPF, команду и CWD `dotnet build`, watcher roots,
   полный путь временного файла и доступные сведения о CWD задачи. Обычная
   форма имени — `{ProjectName}_{random}_wpftmp.csproj`; относительное имя
   встречается и в legacy-задаче, и в проверенных современных targets.
3. Снять события и состояния до build, после их доставки, после semantic
   flush и повторных `load_workspace` с тем же ключом. Раздельно записать
   graph-file stale, composition stale, refresh-all pending, cache hit/reopen.
4. Проверить Information-лог `Project graph file changed on disk` и путь,
   вызвавший событие. Отсутствие строки без доступного уровня логирования
   или при сбое logger не считать доказательством отсутствия инвалидации.
5. Отделить событие временного `.csproj` от outputs внутреннего
   `BuildProjectFile`, обычно лежащих под `obj` и уже игнорируемых.
   Отдельно проверить overflow: callback выставляет refresh-all, следующий
   flush выставляет composition stale даже без изменений текста. Поскольку
   `LoadCoreAsync` проверяет stale до flush, возможен один cache hit перед miss
   следующего вызова. Это другая причина, не устраняемая WPF-предикатом.

Если временный проект не вызывает graph-file stale, а cache miss объясняется
только настоящими входами или composition, остановить реализацию по этой
гипотезе и сообщить результат. При смешанных причинах получить изолированный
fixture; не объявлять весь симптом исправленным по одному отфильтрованному
событию. Правку настоящего `.csproj`, `Directory.Build.props` или Solution
не добавлять в исключение ради успешного baseline.

## Предикат и снимок принадлежности

- Добавить отдельный предикат временного имени: расширение `.csproj`,
  суффикс имени **без расширения** `_wpftmp`, без учёта регистра. Случайный
  компонент не разбирать. `Foo_wpftmp_Bar.csproj` и путь с `_wpftmp` только
  в имени каталога не подходят. `IsProjectGraphFile` не менять на «не проект».
- При `StartDiskWatcherUnderLock` один раз материализовать нормализованные
  полные `Project.FilePath` из загруженного графа; сравнение путей соответствует
  ОС. Тот же набор использовать для расчёта корней и защиты явных проектов.
  Снимок завершён до `EnableRaisingEvents`; в callbacks не модифицируется.
- Привязать снимок к экземпляру/сессии watcher. После stop/reset/reload позднее
  событие старого watcher не использует новый снимок и не меняет состояние
  новой сессии. Обработчики не читают текущий `Solution` и не берут manager
  semaphore для проверки принадлежности.
- Использовать единый owner/token по
  [общему input-state contract](../project-input-watching/input-state-contract.md).
  Минимальный session context вводится здесь при выполнении WPF-фикса первым;
  будущие revisions/coverage дополняют его, а не создают независимую generation.
  Предикат имени общий и доступен watcher-серии независимо от порядка ship.
- В `QueueDiskPath` после нормализации пути и до установки graph-file stale
  игнорировать кандидата только при отсутствии пути в снимке его watcher.
  Загруженный `.csproj` с таким суффиксом проходит обычную graph-file ветку.
  Deleted и старый путь Rename проверять по снимку, не по существованию файла.
- Сохранить независимые вызовы проверки для старой и новой стороны file Rename.
  Если оба имени оканчиваются на `_wpftmp`, это не основание для раннего выхода:
  любая загруженная сторона всё ещё должна взвести stale.
- Сохранить существующие directory filters, directory Rename/error callbacks,
  обычные graph files, `.cs` и синхронизацию известных документов. Общую
  приоритизацию imports/explicit inputs в игнорируемых деревьях оставить серии
  `project-input-watching`; эта эпоха не обещает новое покрытие этих деревьев.

Сборку целиком подавлять временным флагом нельзя: параллельная внешняя правка
настоящего `.csproj` должна оставаться заметной. Не расширять эпоху до общего
реестра импортов или автоматического reload.

## Проверки и приёмка

- Предикат принимает `Foo_abc_wpftmp.csproj`, включая смешанный регистр,
  и отвергает `Foo_wpftmp_Bar.csproj`, другое расширение и суффикс только
  в имени каталога. `IsProjectGraphFile` по-прежнему распознаёт временный `.csproj`.
- Created/Changed/Deleted кандидата вне снимка загруженных проектов оставляют
  graph stale неизменным. Deleted известного проекта с таким суффиксом
  выставляет graph-file stale, даже когда файла уже нет на диске.
- Rename обычного/временного имени в обе стороны не теряет значимую сторону.
  Для `Loaded_wpftmp.csproj` → `Other_wpftmp.csproj` с загруженным старым
  путём выставляется stale. Проверить обратное направление с загруженной новой
  стороной и пару двух незагруженных временных путей, которая stale не меняет.
- Обычный `.csproj`, `.sln`/`.slnx` и распознаваемый props-файл продолжают
  инвалидировать граф в пределах существующих фильтров; явно загруженный проект
  с суффиксом `_wpftmp` тоже. Внешняя правка настоящего входа, пришедшая
  во время сборки, остаётся заметной.
- Поздний callback после stop/reset/reload не влияет на новую сессию и не
  проверяет принадлежность по её снимку; callback не захватывает `_workspaceLock`.
- Overflow/error → refresh-all → composition stale сохраняет текущее поведение.
  Проверяется причина и последовательность до/после flush; этот сценарий
  не выдаётся за неудачное распознавание временного graph file.
- Реальная сборка WPF не вызывает stale по причине временного проекта.
  Cache hit проверяется в fixture без других релевантных изменений графа,
  composition-инвалидации и смены ключа загрузки. После flush и повторной
  загрузки не остаётся отложенной инвалидации, скрытой первым cache hit.
- Backing `.csproj` и Solution не изменяются сервером ради фильтрации.

Юнит-проверки событий не заменяют WPF-интеграцию. Недоступный Windows/WPF-host
отмечается как непроверенный сценарий, а не успешная приёмка.

## Результат эпохи

Отчёт содержит baseline с полными путями и рабочими каталогами, последовательность
вызовов и событий, раздельные причины graph-file/composition, diff, выполненные
проверки и ограничения. Смешанные или неподтверждённые причины не считаются
успешной приёмкой изолированного WPF-сценария. Источники
и тесты C# менять только после полного чтения `docs/code-style.md`.
Серия закрывается после проверки контракта README и фактического выпуска;
реализацию остальных двух фич эта эпоха не включает.
