## Направление

### N-1

Цель темы — разбивка времени загрузки на решении коллег («несколько минут»), и
README прямо требует: задачи E1 заводятся только под подтверждённый hotspot.
Фактически:

- task-00 `in progress` с 2026-10-09: офисный замер не получен;
- task-01–task-03 (production-логи стадий, сводка design-time build, baseline) `planned`;
- 8 из 12 задач эпохи — спайки параллельной загрузки на прокси PowerToys, Files и
  Roslyn на быстрой машине (Ryzen 9800X3D).

Без данных целевого решения неизвестно, доминирует ли у коллег CPU design-time
build (тогда параллель уместна) или холодный диск и антивирус ([O-1](#o-1)).

Предложение: вернуть приоритет task-00 (при необходимости упростить протокол до
одного запуска `scripts/Measure-WorkspaceLoad.ps1` с холодным и тёплым прогоном) и
task-01/task-02 — они нужны при любом исходе, в том числе для спайков.

### N-2

Замороженная модель task-07.2 до замера предсказала Roslyn cluster N4
**34,211 с** при baseline **43,771 с**, то есть **78,2 %** baseline
([отчёт](epoch-0-stage-measurement/evidence/task-07.2-refusal-fast-planner-roslyn.md#прогноз-roslyn-до-первого-параллельного-замера)).
Это выше порога 75 % ещё до двух ухудшающих факторов task-07.3:

- достоверный evaluated-граф добавляет imported/property-generated рёбра и может
  только увеличить ядро (сейчас 85 проектов, 43,73 % стоимости);
- в wall войдёт цена получения графа. Evaluation — около 40 % положительного
  прироста service time в группах Roslyn (44 % в PowerToys), то есть дешёвой её
  не считать.

Кроме того, в task-07.3 нет предрегистрированного численного порога go для Roslyn —
только формулировка «если получение съело экономию». В task-07.2 порог был задан
до серии.

Предложение до начала task-07.3:

1. Шаг 0 — отдельным процессом замерить цену получения графа выбранным публичным
   механизмом (evaluation-only проход), без параллельной загрузки.
2. Подставить её и ожидаемую долю ядра в модель task-07.2 без перекалибровки.
3. Предрегистрировать численный порог go для Roslyn; если прогноз выше — остановка
   с отрицательным результатом до проверки корректности.

### N-3

В границах темы запрещены disk cache и fork BuildHost. Значит, граф для первой
загрузки получается заново при каждом открытии. Повторное использование ранее
снятого графа с проверкой актуальности входов — по сути задача темы
[B / workspace-state-cache](../workspace-state-cache/README.md). Даже успешная
task-07.3 не даёт production-пути внутри этой темы без пересмотра её границ.
Это стоит явно записать в task-07.3 как ожидаемое ограничение результата.

### N-4

Порог go менялся внутри серии: 50 % baseline в task-04, 75 % с task-07, правило
«отказ до загрузки» с task-07.2. Все изменения задокументированы честно, но каждый
no-go вёл к продолжению. Правило task-03 «отрицательный результат — не повод
расширять замеры» к спайкам не применялось.

Предложение: задать для линии core-first явное правило остановки (например,
«no-go task-07.3 по экономике или корректности закрывает линию до появления данных
целевого решения»).

## BH — BuildHost: факты, варианты и требования на случай снятия запрета

Граница темы «без изменения или fork Roslyn BuildHost» действует. Раздел фиксирует,
что учитывать, если владелец её пересмотрит.

### Факты

Проверено на пакете `Microsoft.CodeAnalysis.Workspaces.MSBuild` 5.9.0 в локальном
кэше NuGet:

- Загрузка двухслойная. В процессе сервера `MSBuildWorkspace`/`MSBuildProjectLoader`
  запускает BuildHost, общается с ним по RPC и собирает `ProjectInfo`/`Solution`.
  BuildHost — дочерний процесс (`BuildHost-netcore` для SDK-проектов,
  `BuildHost-net472` для остальных), выполняет evaluation и design-time build.
- Размеры: `BuildHost.dll` (netcore) 112 KB, общий RPC-контракт
  `Workspaces.MSBuild.Contracts.dll` 52 KB, клиентская `Workspaces.MSBuild.dll`
  135 KB, весь пакет 4,5 MB. MSBuild в пакет не входит.
- `BuildHost-netcore` собран под `net8.0` с `rollForward: Major`: запускается на
  новейшем установленном runtime и берёт MSBuild из SDK пользователя.
- Сервер поставляет свой Roslyn (`RoslynMcpServer.csproj`: `Microsoft.CodeAnalysis.*`
  5.9.0) и не везёт MSBuild (`Microsoft.Build` с `ExcludeAssets="runtime"`).
  Roslyn из VS/SDK пользователя сервер не использует.

Остальной Roslyn (компиляции, символы, рефакторинги) получает от загрузчика только
`ProjectInfo`/`Solution`. Изменение загрузчика локально по коду; наблюдаемые
последствия ограничены результатом загрузки, который проверяет comparator спайков.

### Варианты

| Вариант | Суть | Оценка |
|---|---|---|
| A | Форк только BuildHost под стоковый клиент | Не рекомендуется: протокол внутренний, подмена файлов в `contentFiles` хрупкая |
| B | Форк клиента и BuildHost | Свой загрузчик; клиент, вероятно, использует internal API Roslyn через InternalsVisibleTo, под другим именем сборки доступ пропадёт (**не проверено** — первый вопрос до решения) |
| C | Собственный драйвер design-time build на публичных API | Не форк: многоузловой `BuildManager`, разбор командной строки через публичный `CSharpCommandLineParser`, сборка `ProjectInfo`; все краевые случаи `MSBuildWorkspace` нужно воспроизвести и доказать comparator'ом |

Объём исходников A/B — по оценке порядка нескольких тысяч строк C# (**не проверено**,
оценка по размеру IL). Тащить MSBuild или весь Roslyn не нужно.

### Цена сопровождения

1. **Ребейз при обновлении Roslyn.** Форк привязан к версии пакета, которую поставляет
   сервер, а не к установке пользователя. Работа плановая, сроки выбираем мы.
2. **Прямая совместимость: новый SDK/MSBuild у пользователя.** Если новый MSBuild
   ломает BuildHost (изменение API или поведения, требований к хост-процессу, формата
   данных — аналог binlog v27 из [task-05](epoch-0-stage-measurement/evidence/task-05-profile-guided-partition.md)),
   без форка достаточно поднять версию пакета после фикса Microsoft. С форком фикс
   нужно найти в upstream и перенести. Срочность одинаковая (релиз сервера нужен
   в обоих случаях), различаются объём и предсказуемость работы.
3. **Обратная совместимость: старый SDK, `global.json`, старая VS.** BuildHost собран
   против определённого MSBuild API; вызов отсутствующего в старом MSBuild метода
   ломает загрузку. Сейчас минимальную версию держит Microsoft, с форком — мы.
   Репозитории с pin на старый SDK — частый случай (Files был привязан к
   отсутствующему 10.0.102, сработал fallback сервера). `BuildHost-net472` берёт
   MSBuild из установленной VS — отдельная линия совместимости.
4. Протокол клиент ↔ BuildHost проблемой не является в варианте B: обе стороны
   поставляются в одном релизе.

### Требования, если запрет будет пересмотрен

- **BH-R1.** До решения оценить частоту поломок совместимости по истории каталога
  BuildHost в dotnet/roslyn: число коммитов в год и доля, связанная с новым MSBuild/SDK.
- **BH-R2.** До решения проверить, какие internal API Roslyn использует клиентская
  часть `Workspaces.MSBuild` и доступны ли они вне InternalsVisibleTo (вариант B).
- **BH-R3.** Явная матрица поддерживаемых SDK/MSBuild и VS (для net472) с минимальной
  версией. Оптимизация не должна молча поднимать минимум: вне матрицы — откат на
  стоковый загрузчик или явная ошибка до загрузки.
- **BH-R4.** Стоковый загрузчик остаётся доступным путём отката; результат форка
  проверяется тем же comparator'ом на эквивалентность с ним.
- **BH-R5.** Provenance capture (binlog), analyzer admission и AnalyzerLifecycle
  завязаны на BuildHost; изменение требует полного AnalyzerLifecycle по `AGENTS.md`.
- **BH-R6.** CI должен покрывать границы матрицы BH-R3, а не только SDK машины
  разработчика. Тестовый контур уже чувствителен к SDK:
  `Framework_selection_matches_installed_pack_files_without_loading_analyzers`
  падал на 10.0.401 при 10.0.300-профиле (2026-10-10).
- **BH-R7.** Решение принимать по числам: выигрыш параллельного design-time build и
  доля MSBuild во времени загрузки у коллег ([N-1](#n-1)). Без этих данных
  цена сопровождения не сопоставима с выгодой.
