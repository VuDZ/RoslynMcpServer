## Что меняется и почему

По [task-01](evidence/task-01-graph-and-timings.md) загрузку держит работа host: около 94 % окна на Roslyn.slnx и
около 82 % в офисе, клиент 5.9.0 шлёт запросы строго по одному. Две части, обе — в host форка, клиент и протокол не
меняются:

- **A — одна evaluation на проект.** Клиент собирает проект P раньше, чем загружает проекты, на которые P
  ссылается. Design-time build P вызывает у ссылки R цели `GetTargetFrameworks` и `GetTargetPath`; конфигурации R в
  `BuildManager` ещё нет, и MSBuild оценивает R с диска. Затем клиент загружает R, и host оценивает его ещё раз —
  с теми же глобальными свойствами. В A host, получив запрос сборки P, сначала сам оценивает и собирает ещё не
  собранные ссылки P и хранит их результаты до запросов клиента; вызовы из сборки P попадают в готовые
  конфигурации.
- **B — evaluation наперёд.** Как только проект оценён, его ссылки известны; host начинает их корневые evaluation
  (и, где возможно, извлечение `ProjectFileInfo`) в рабочих потоках, пока сборки идут по одной. Сборки остаются
  последовательными: параллельные сборки в одном `BuildManager` не ускоряют, а узлы out-of-proc заново оценивают
  проекты ([шаг 0](evidence/task-02-step-0.md)).

## Решения и пороги

Решения: `RoslynMcpServer.sln` (Linux), Roslyn.slnx (Windows, основной компьютер владельца), офисное решение как
внешний контроль. PowerToys исключён, как в task-00.

Пороги — до кода, для каждого варианта против форка без оптимизаций, медианы прогрева и трёх раундов:
- **корректность:** identical оригиналу по правилам task-00, comparator не ослабляется; сценарии сбоев task-00
  проходят;
- **go:** загрузка офисного решения короче не менее чем на 10 %, Roslyn.slnx не медленнее более чем на 2 %, пик
  памяти host и клиента — не больше +10 %;
- **A + B** принимается, только если быстрее каждой части отдельно.

Итог: go/no-go/inconclusive по каждому варианту с объяснением и следующим узким шагом.

## Ограничения корректности

- Ключ reuse учитывает effective properties, SDK/toolset, TFM и состояние входов.
  Одинаковый path не доказывает одинаковую задачу.
- Параллельная работа не изменяет общий mutable Project между TFM; защищает
  shared obj/output paths, сохраняет каждый solution entry и правила native entries.
- Не отбрасывать generated sources, compiler args, references/aliases, diagnostics,
  analyzer evidence, cancellation и failure propagation ради измеренного выигрыша.
- Результат, подготовленный заранее, отдаётся клиенту с тем же DiagnosticLog и теми же ошибками, что при обычном
  порядке; запрос клиента к проекту, над которым идёт упреждающая работа, ждёт её, а не начинает вторую.
- Prewarm и долгоживущий процесс считать отдельными режимами; их цену не скрывать
  до таймера. Построение графа, запуск хостов, extraction и merge входят в wall.
- Обычный fallback после потраченного времени fork не превращает failed attempt
  в correctness PASS или ускорение.

Production включение не входит в эту задачу: даже успешный spike требует отдельного
решения об интеграции и совместимости. Отчёт: evidence/task-02-optimization-spike.md.
