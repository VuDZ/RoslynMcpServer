### 2.2. major — проверка «kill → completed» не проверяет загруженное решение

**Место.** `spikes/BuildHostFork/Invoke-BuildHostForkScenarios.ps1:129-135` (`Test-Run`, ветка
`killed`), `:152-161` (`Test-Pair`), `:209` (для kill передаётся `$CompareOutcome = $false`).

**Что не так.** Для сценария убийства host ожидаемый исход — `failed:*` **или** `completed` с
`BuildHostProcesses.count >= 2`. Во второй ветке не проверяются ни `Projects`, ни `Documents`, ни
`Diagnostics`; `Test-Pair` для kill вообще не сравнивает исход, проекты и диагностики. Значит,
форк, который после убийства поднял новый host, но вернул пустой или частичный solution, будет
принят как успешный: `Outcome=completed`, `count=2`, проблем нет, скрипт выходит с кодом 0.

**Сценарий.** Убийство попадает между запросами: `BuildHostProcess_Disconnected` убирает host из
кеша, следующий проект стартует новый host, загрузка завершается. Если новый host форка не отдал
часть проектов (или все), completed-ветка всё равно проходит. В опубликованных прогонах
`scenarios-20261024-130854` kill у обеих сторон закончился `failed: The server disconnected
unexpectedly`; ветка `completed` для форка не наблюдалась, поэтому дефект не был замечен.

**Доказательство.** Код `Test-Run`: `'killed' { $r.Outcome -like 'failed:*' -or
($r.Outcome -eq 'completed' -and $r.BuildHostProcesses.count -ge 2) }`; `Test-Pair` вызывается с
`($disturbed[$i].Mode -ne 'kill-host')` как `$CompareOutcome`, а проверки проектов/диагностик
находятся под этим флагом. В `scenarios-20261024-130854/scenarios.md` для kill нет completed-строки.

**Предлагаемое исправление.** В completed-ветке kill проверять `Projects`/`Documents` против
неотменённой загрузки **той же стороны** (`$loads`) или против известного числа проектов решения;
при completed у обеих сторон дополнительно сравнивать снятый workspace и диагностики. Исход
сторон по-прежнему не сравнивать (он недетерминирован). Добавить прогон, который действительно
попадает в completed-ветку, иначе она так и останется непроверенной.

**Статус.** Незакрытая часть F-03 (F-03 требовал проверять обязательные исходы; ветка completed
осталась без проверки).

### 2.3. major — comparer на JSON старого формата печатает проверку процессов как `ok`

**Место.** `spikes/BuildHostFork/ObservationComparer.cs:130-159` (`ProcessIssues`), `:184`
(строка `BuildHost processes ... ok`), `:36-37` (`processIssues` в `Run`).

**Что не так.** `ProcessIssues` молча пропускает отсутствующие поля: `RemainingBuildHosts` и
`unidentified` проверяются только если есть; если нет `ExpectedHost` или `hosts`, метод делает
`yield break`. В результате старый JSON (без `ExpectedHost`, `RemainingBuildHosts`, `hosts`,
`unidentified`) даёт ноль замечаний, а summary печатает
`BuildHost processes (own folder, none left 10 s after the load): ok` и `result: equivalent`.
Проверка папки host и остатка процессов не выполнялась, но выглядит выполненной.

**Сценарий.** Ревьюер или владелец запускает новый comparer на `results/baseline-20261024-012310`
(или на любом старом прогоне) и читает «host каждой стороны из своей папки, после загрузки ничего
не осталось». В старом формате этих полей нет; утечка host или host из чужой папки не будут
обнаружены. Это именно тот ложно-зелёный сценарий, который просил проверить запрос.

**Доказательство.** Собственный запуск:
`dotnet spikes/BuildHostFork/bin/Release/net10.0/BuildHostFork.dll compare <копия old baseline>` на
`baseline-20261024-012310` дал `**identical**`, `BuildHost processes ... ok`, `result: **equivalent**`;
в `original-round1.json` этого прогона есть только `BuildHostProcesses {count,cpuMs,peakWorkingSetMb}`,
без `ExpectedHost`/`RemainingBuildHosts`/`hosts`/`unidentified`.

**Предлагаемое исправление.** Явно различать «проверено и хорошо» и «не проверено (старый формат)»:
если поле отсутствует, добавить замечание `not checked (old format)` и не делать `Equivalent`
истинным для lifecycle-проверки; либо требовать новые поля для `compare` и называть старые файлы
workspace-only. Строку `runs: ... round 0 ... only its search answer and BuildHost processes are
checked` тоже нужно уточнять для старых файлов.

**Статус.** Новая в области G-03 (проверка процессов) и G-01 (сравнение).

### 2.4. minor — задержка по умолчанию может снова проверять раннюю отмену, а не отмену после старта host

**Место.** `spikes/BuildHostFork/Invoke-BuildHostForkScenarios.ps1:190-204` (расчёт `DelayMs`),
`:136-138` (`not disturbed`), `:126-148` (`Test-Run`).

**Что не так.** `DelayMs` по умолчанию — половина времени неотменённой загрузки оригинала после
появления host. Если эта половина меньше времени инициализации host (на быстрой машине или
маленьком решении), cancel попадает в то же окно, что и early-cancel: клиент ещё не
зарегистрировал host, утечка остаётся, обе стороны ведут себя одинаково. `Test-Run` видит
`DisturbedAtMs != null` и `canceled`, `Test-Pair` видит одинаковый остаток и пишет «upstream»;
скрипт завершается 0. Отличить «отмена после старта host» от «отмена во время инициализации» он
не может.

**Сценарий.** Решение с короткой загрузкой после появления host (например, 200 мс) даёт delay
100 мс; cancel приходит до `_processes.Add`, у обеих сторон остаётся host; отчёт говорит
«all checks passed», хотя нормальный cancel-сценарий фактически не проверил отмену после старта.

**Доказательство.** Код выбора delay и `Test-Run`: проверяется только факт воздействия и исход,
но не то, что host успел быть зарегистрирован/использован. На `RoslynMcpServer.sln` в
`scenarios-20261024-134115` delay был 1039 мс при host на 541 мс и загрузке 2620 мс — там, вероятно,
окно уже пройдено; для меньшего решения это не гарантировано.

**Предлагаемое исправление.** Задать нижнюю границу delay (например, не меньше наблюдаемого
времени инициализации host или 1–2 с), либо проверять прогресс загрузки до cancel (появился хотя
бы один проект/диагностика), либо помечать cancel, попавший в окно инициализации, отдельным
исходом и не считать его проверкой post-start cancellation.

**Статус.** Новая в области F-03 (проверка сценариев).

### 2.6. minor — при несовпадении ответа поиска причина говорит «форк отличается», хотя форк может быть identical

**Место.** `spikes/BuildHostFork/ObservationComparer.cs:38-47`.

**Что не так.** Вердикт `different` ставится при `fork.Unexplained > 0 || answers != 1`. Ветка
`reasons.Add("the fork differs from the original")` срабатывает при любом `different`, включая
случай, когда различаются ответы поиска в прогреве или в измеренных раундах **оригинала**, а
измеренные раунды форка совпадают с эталоном. Причина вводит в заблуждение.

**Доказательство.** Синтетический случай: original round 0 — один `resultSha256`, rounds 1–3 —
другой; fork во всех раундах — второй. Получается `**different**`, `natural 0, unexplained 0`,
`distinct search answers ... 2`, `result: not shown equivalent: the fork differs from the original`.

**Предлагаемое исправление.** Разделить причины: «search answers differ across runs: N» и
«the fork differs from the original»; при `answers != 1` не обвинять форк. Полезно печатать
ответы по раундам/сторонам (хотя бы хеши).

**Статус.** Новая (диагностика результата G-01).

### 2.7. minor — какой второй BuildHost в офисе, по-прежнему не установлено (G-07)

**Место.** `docs/workspace-load-performance/research-buildhost-fork/evidence/task-00-fork-baseline.md:207-209`;

### 2.8. minor — сообщение ошибки внешнего решения сокращается до типа только при наличии пути

**Место.** `spikes/BuildHostFork/Invoke-BuildHostForkScenarios.ps1:223-230` (`Format-Outcome`).

**Что не так.** Для внешнего решения `Format-Outcome` заменяет сообщение на
`failed: <type> (message with paths not shown)` только если в тексте после типа есть `/` или `\`.
Если сообщение называет проект/решение **без пути** (например, `The project 'X' is invalid`),
оно попадает в `scenarios.md` целиком. F-06 требовал не публиковать имена частного решения и его
проектов, а не только пути.

**Сценарий.** Внешнее решение (офис) падает с сообщением, где есть имя проекта, но нет
разделителя пути; таблица `scenarios.md` публикует имя. В записанных после ревью прогонах офисный
сценарий не запускался (только baseline), а Roslyn.slnx — публичное решение; поэтому наблюдения
нет, но путь утечки остаётся.

**Предлагаемое исправление.** Для `External` при `failed:` всегда оставлять только тип
исключения (или явно вычищать имена проектов/решения, а не только пути). Публичные fixtures можно
оставить с текстом отдельно.

**Статус.** Незакрытый остаток F-06.

### 2.10. nit — «deps.json отличается только версией и сателлитами» неточно

**Место.** `docs/workspace-load-performance/research-buildhost-fork/evidence/task-00-fork-baseline.md:51-57`;

### 2.11. nit — комментарий `PROCESS_BASIC_INFORMATION` описывает не ту структуру

**Место.** `spikes/BuildHostFork/ProcessQuery.cs:117-127`.

**Что не так.** Комментарий говорит, что «every member is pointer-sized, ExitStatus included». В
Win32 `ExitStatus` — 4-байтовый `NTSTATUS`, `BasePriority` — 4-байтовый `KPRIORITY`; указательными
являются `PebBaseAddress`, `AffinityMask`, `UniqueProcessId`, `InheritedFromUniqueProcessId`.
Структура из шести `IntPtr` случайно даёт правильные **смещения** используемого
`InheritedFromUniqueProcessId` на x86/x64/ARM64 (padding), но читать `ExitStatus`/`BasePriority`
через неё нельзя, а комментарий обещает обратное.

**Сценарий.** Будущая правка добавит чтение `ExitStatus`/`BasePriority` и получит мусор;
комментарий этому не помешает.

**Предлагаемое исправление.** Либо описать реальную структуру (`NTSTATUS`, указатель,
`KAFFINITY`, `KPRIORITY`, два `ULONG_PTR`) и проверить смещение, либо исправить комментарий:
«размер и смещение InheritedFromUniqueProcessId совпадают на x86/x64/ARM64; остальные поля не
читаются».

**Статус.** Новая (проверка interop).

### 2.12. nit — «другого пути к dll нет» слишком широко

**Предлагаемое исправление.** Уточнить: «в deployed/spike-layout клиент берёт только соседнюю
папку; единственная другая раскладка — NuGet `contentFiles`; после ошибки fallback’а нет».

### 2.14. nit — comparer не проверяет `Status`, в отличие от `compare.py`

### 3.2. `ObservationComparer` против `compare.py`

- Эталон — первый измеренный original (round 1); прогрев исключён из эквивалентности; natural —
  только различия original rounds 1–2; диагностики — симметрическая разность с «presence» как
  значением; раунды 3+ и форк проверяются тем же правилом; ответ поиска — один во всех запусках,
  включая прогрев; процессы проверяются во всех запусках, включая прогрев. Это соответствует
  запросу и сильнее `compare.py` в трёх местах: нет case-only исключения, поиск сравнивается,
  процессы проверяются.
- Поле только у одной стороны, проект только у одной стороны и `-Runs 1` проверены
  синтетическими каталогами: отсутствующее поле/проект дают `different`; присутствие в original
  round 2 даёт `natural variance only`; один измеренный раунд не получает natural-допуска.
- Ключ проекта и сообщение диагностики не сталкиваются: `Classify` использует пару
  `(Key, Category)`, категории `ProjectKeys`/`Diagnostics`/имя поля.
- **Пути, где отличие форка принимается или теряется.** Реального пути, на котором отличие
  молча исчезает в актуальной схеме, не нашёл: отсутствующее поле/проект дают `different`;
  присутствие в original round 2 даёт `natural variance only`; один измеренный раунд не получает
  допуска; ключи не сталкиваются. Два исключения: (а) по определению natural систематическое
  отличие форка, совпавшее со значением original round 2, принимается как разброс — это правило
  E0, которое первый раунд прямо требовал, но natural оценивается по одному переходу 1→2, поэтому
  редкий выброс оригинала может «объяснить» систематическое отличие форка; (б) старый JSON без
  process-полей (2.3).
- **JSON `null` против `""`**: comparer действительно склеил бы их (`Projects` вызывает
  `GetString() ?? ""`), но `SolutionObservation.Add` сериализует каждое значение **в строку**:

  variance) и process-кейсы; не покрывает края из 2.5. Собственный `check` — 8/8.
- Новые поля процесса проверяются; на старом JSON — ложное `ok` (2.3).
- `Status` не проверяется (2.14).

### 3.3. `BuildHostSampler` и `ProcessQuery`

- **Владение процессом.** Учитываются только потомки процесса spike: `IsDescendant` читает
  родителя через `ProcessQuery.TryReadParentId`, идёт до трёх уровней, сверяет время старта
  родителя с ребёнком (защита от переиспользованного PID). Чужие BuildHost не измеряются и не
  убиваются.
- **Linux `/proc`.** `TryReadCommandLine` читает `/proc/<pid>/cmdline`, собирает аргументы с
  кавычками для пробелов; `TryReadParentId` — `/proc/<pid>/stat`, берёт поля после последней `)`,
  поэтому имя процесса со скобками/пробелами не ломает разбор. В этой сессии Linux не запускался;
  проверка по коду.
- **Windows interop.** `NtQueryInformationProcess` класс 0 (`PROCESS_BASIC_INFORMATION`) и класс 60
  (`ProcessCommandLineInformation`); `UNICODE_STRING` — `ushort`, `ushort`, `IntPtr` (16 байт x64,
  8 x86); `ProcessBasicInformation` из шести `IntPtr` даёт правильное смещение используемого
  `InheritedFromUniqueProcessId` (40 x64/ARM64, 20 x86); `ExitStatus`/`BasePriority` типизированы
  неверно, но не читаются (2.11). Класс 0/60 и `SafeHandle` проверены по коду; x86/ARM64 не
  исполнялись.
- **Нечитаемая командная строка.** Потомок `dotnet` без читаемой командной строки попадает в
  `unidentified`, не в host и не в цель kill; ненулевой счётчик проваливает сравнение (проверено
  синтетически: 4 issue).
- **Kill / Wait / Stop.** `Kill` открывает процесс заново и сверяет время старта; `WaitForExitAsync`
  возвращает список живых до добивания; `Stop()` использует `Timer.Dispose(WaitHandle)` и затем
  один `Sample`, поэтому идущий опрос не добавляет процесс после снимка.
- **Гонки.** Процесс, стартовавший и завершившийся между опросами 100 мс, не виден — это
  задокументировано в классе; родитель, завершившийся/переиспользованный, отсекается по времени
  старта (потомок при этом не считается — ложный минус, а не чужой host). Потомок, потерявший
  родителя до опроса, не будет учтён; для текущего клиента host — прямой ребёнок spike.
- **Остаточные риски.** Допуск 1 с на время старта (нужен из-за Linux) теоретически допускает
  переиспользование PID в пределах секунды; `_unidentified` не очищается; `MainModule` net472 при
  отказе доступа пропускается. Это не наблюдалось; см. 2.11.
