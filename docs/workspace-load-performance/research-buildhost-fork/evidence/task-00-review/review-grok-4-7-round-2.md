### R2-02 · major · проект только на одной стороне прячет значения полей

Новое. G-01 закрыт для тех ложных успехов, которые были в первом компараторе; эта дыра скопирована из эталона `compare.py` и self-check её не содержит.

**Где:** `spikes/BuildHostFork/ObservationComparer.cs:76-79`. Эталон: `spikes/ParallelLoad/compare.py:13-15` — тот же `continue` после различия состава проектов.

```76:79:spikes/BuildHostFork/ObservationComparer.cs

            {
                result.Add(new Difference(key, "ProjectKeys", Presence(leftProjects.ContainsKey(key)), Presence(rightProjects.ContainsKey(key))));
```

**Сценарий.** Оригинал, раунд 1: проекта нет. Раунды 2 и 3: проект есть, поле `good`. Форк: проект есть, поле `evil`. Естественная карта для `ProjectKeys` — `absent` и `present`. Значение `evil` ни с чем не сравнивается, потому что поля после различия состава не читаются. `evil` проходит как естественная смена состава.

**Доказательство.** Windows 10.0.26200, `spikes/BuildHostFork/bin/Release/net10.0/BuildHostFork.dll compare` на синтетической папке: exit 0, вердикт форка «natural variance only», результат equivalent. Дыра срабатывает, когда раунды 1 и 2 оригинала расходятся в составе проектов, а форк приносит третье значение поля.

**Как исправить.** При различии состава всё равно сравнивать поля той стороны, где проект есть, с отсутствующим значением, которого нет в естественной паре. Добавить этот случай в `ComparerSelfCheck` с ожиданием `different` и equivalent false.

Поле, которое есть только у одной стороны, при третьем значении уже ловится: объединение ключей полей в C# строже, чем цикл `compare.py` только по полям левого проекта. Синтетика «natural = отсутствует и `good`, форк = `evil`» дала exit 1. `-Runs 1` при отличии поля тоже дал exit 1: единственный измеренный раунд не создаёт естественную карту.

### R2-03 · major · kill принимает неубитую загрузку с двумя BuildHost

Новое. Вопрос запроса: ослабление шире, чем нужно для устойчивости к гонке upstream.

**Где:** `spikes/BuildHostFork/Invoke-BuildHostForkScenarios.ps1:132` и `:209`.

```132:132:spikes/BuildHostFork/Invoke-BuildHostForkScenarios.ps1
        'killed' { $r.Outcome -like 'failed:*' -or ($r.Outcome -eq 'completed' -and $r.BuildHostProcesses.count -ge 2) }
```

`Test-Pair` для `kill-host` вызывается с `CompareOutcome = false` (`:209`). Проекты и документы в этом режиме не сравниваются. Диагностики у всех возмущённых сценариев не сравниваются (`$false` третьим аргументом).

**Сценарий.** Спокойная загрузка офиса уже поднимает 2 процесса BuildHost (`task-00-fork-baseline.md:197`). Такой прогон без убийства даёт `completed` и `count >= 2` и проходит ожидание `killed`. Если обе стороны так завершились, скрипт не сравнит число проектов и документов. Сценарии офиса отчёт не заявляет. Опубликованные сценарии Roslyn.slnx и Linux шли при одном процессе спокойной загрузки: `completed` с count 1 условие `>= 2` не выполняет, их «all checks passed» эта дыра не обеляет.

Равные `RemainingBuildHosts` с обеих сторон записываются как upstream и не валят прогон (`:159-166`). Для task-00 это верно: задача сравнивает стороны, а не чинит клиент. Большее число на одной стороне уже является ошибкой пары.

**Как усилить, не теряя устойчивость.** Порог `completed` — строго больше числа host спокойной загрузки этой стороны (или PID, которого в спокойной загрузке не было). Если оба исхода `completed`, сравнивать проекты и документы. Если оба `failed`, сравнивать тип исключения. Пропускать сравнение исхода только когда одна сторона упала, а другая завершилась: это и есть гонка upstream, описанная в разборе.

Задержка по умолчанию — `floor((LoadMs - FirstHostAtMs) / 2)` (`:194`). Ноль получается только при хвосте короче 2 мс. Если зонд не завершился, скрипт бросает исключение (`:193`). «not disturbed» — ошибка прогона, exit 1 (`:136-137`). Этого пункта запроса дыра задержки не образует.

**Компаратор против `compare.py`.** Естественная карта строится только из измеренных раундов 1 и 2. Различие естественно, когда новое значение входит в эту пару. Диагностики — симметрическая разность, значение — присутствие. Раунды 3+ оригинала идут по тому же правилу и при необъяснённом отличии портят equivalent. Ответ поиска один на все раунды, включая прогрев; расхождение валит прогон (fail-closed; текст причины говорит «fork», даже если разошёлся только прогрев оригинала). `fork.Natural` считает пары (раунд, различие), строка раундов 1–2 — уникальные различия. На equivalent это не влияет.

**Процессы.** Выборка — потомки spike, глубина предков 3, опрос 100 мс. `/proc/pid/stat`: последний `)`, дальше поле state и ppid; скобки и пробелы внутри comm не сдвигают ppid, потому что после закрывающей скобки скобок в stat нет. Класс 0 — `ProcessBasicInformation`. На x86 все поля по 4 байта, `IntPtr` совпадает. На x64 и ARM64 `ExitStatus` и `BasePriority` — 4 байта плюс 4 байта выравнивания, поэтому последовательность из `IntPtr` даёт те же смещения `PebBaseAddress`, `AffinityMask`, `UniqueProcessId` и `InheritedFromUniqueProcessId` (48 байт). Комментарий у структуры говорит, что `ExitStatus` сам размером с указатель; для читаемого поля родителя смещение всё равно верное. Живым вызовом ntdll это не подтверждалось. Убийство и `WaitForExit` сверяют время старта. `Stop` ждёт обработчик таймера и снимает ещё один образец. Процесс, родившийся и умерший между опросами, невидим; это записано.
