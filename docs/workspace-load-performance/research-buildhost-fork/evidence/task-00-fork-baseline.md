  ревизия из nuspec пакета `Microsoft.CodeAnalysis.Workspaces.MSBuild` 5.9.0.

- Минимальная граница форка — только процесс BuildHost-netcore.
  - Клиент (`Microsoft.CodeAnalysis.Workspaces.MSBuild.dll`) берёт BuildHost из папки
    `BuildHost-netcore` рядом с собой (`BuildHostProcessManager.GetBuildHostPath`) и общается с ним

  XML, а не только по TFM: SDK-style проект `net472` идёт через netcore-host, то есть через форк. Проект
  .NET Framework старого формата на Windows идёт в `BuildHost-net472`, а без пригодного Visual Studio
  MSBuild клиент переводит его на netcore-host (`GetBuildHostWithFallbackAsync`) — снова через форк (G-07).

### Что не сравнивается

`SolutionObservation` — снимок из E0, а не полный oracle приёмки task-00 (F-04). Не сравниваются:

- сгенерированные исходники (`GetSourceGeneratedDocumentsAsync`): ни набор, ни содержимое;
- содержимое документов, additional и analyzer config: только пути;
- происхождение анализаторов сверх `AnalyzerReference.FullPath`: версия, хеш, MVID, результат загрузки;
- опции компиляции и разбора вне снятого подмножества: снимаются `OutputKind`, `Platform`,
  `OptimizationLevel`, `CheckOverflow`, `SpecificDiagnosticOptions`, для C# — `Nullable`, `AllowUnsafe`,
  `LanguageVersion`; для разбора — символы препроцессора, `DocumentationMode`, `Features`. Не
  снимаются, например, `WarningLevel`, `GeneralDiagnosticOption`, `Deterministic`, языковые опции VB;
- эффективные свойства варианта проекта (TFM, global properties) отдельным полем: варианты различаются
  ключом «путь + имя»;
- `CompilationOutputInfo.GeneratedFilesOutputDirectory`;
- диагностики компиляции и анализаторов: поле Diagnostics — события `WorkspaceFailed`.

Поиск сравнивает ответ одного запроса, а не всё содержимое. Поэтому «identical» ниже означает
совпадение снятых полей. Изменение в перечисленном BuildHost/task-00 не обнаружит; для task-02 это
ограничение остаётся, расширять снимок — отдельное решение.

Сценарии после ревью (F-03):

  должны совпасть построчно;
- форк без своей dll: загрузка должна упасть с «build host could not be found», без процесса host;
- неотменённая загрузка решения обеими сторонами; по загрузке оригинала выбирается задержка — половина
  времени после появления host;
- отмена и убийство host через эту задержку; отмена сразу после появления host.

Скрипт проверяет ожидаемый исход, факт воздействия, папку host и совпадение сторон, при нарушении
выходит с кодом 1. Host, оставшийся у обеих сторон одинаково, записывается как поведение upstream.

### Локально после ревью, Linux, 2026-10-24

`RoslynMcpServer.sln`, задержка 2 321 мс. Результат: **all checks passed**.

| сценарий | исход | host после загрузки |
|---|---|---|
| фикстура, `observe` | **identical**, 6 проектов, 5 одинаковых Failure | 0 |
| фикстура, загрузка оригинал / форк | `completed`, диагностики совпадают построчно | 0 |
| форк без своей dll | исключение «build host could not be found», host не запускался | 0 |
| загрузка решения, оригинал / форк | `completed`, 5 проектов | 0 |
| отмена через 2,3 с, оригинал / форк | `canceled` | 0 |
| убийство host через 2,3 с, оригинал / форк | `The server disconnected unexpectedly.` | 0 |
| отмена сразу после появления host, оригинал / форк | `canceled` | **1 / 1** — утечка upstream |

- **Ранняя отмена оставляет BuildHost у обеих сторон** (у GPT на Windows так же). Причина в upstream
  `BuildHostProcessManager.NoLock_GetBuildHostAsync`: отмена в `ConfigureGlobalStateAsync` или
  `FindBestMSBuildAsync` срабатывает до регистрации процесса в `_processes`, и его никто не завершает.
  Подробно — в [disposition.md](task-00-review/disposition.md#ранняя-отмена-утечка-buildhost-в-upstream).
- **Исход убийства host в upstream зависит от момента.** В первом прогоне этого дня форк после убийства
  запустил второй host и завершил загрузку, оригинал упал. Повтор, по 4 убийства на сторону: оригинал
  3 раза «server disconnected» и 1 раз `completed` со вторым host; форк 3 раза «server disconnected»
  и 1 раз `Broken pipe`. После разрыва клиент убирает host из кеша и запускает новый для следующего
  проекта; если убийство пришлось на запрос в полёте, загрузка падает. Поэтому скрипт принимает оба
  исхода и не требует их равенства между сторонами по одному запуску. Прежний вывод «host после
  убийства не перезапускается» неверен.
- Повторный запуск с фикстурой прошлого прогона в `results/` собрал spike без ошибок (F-01).
- Те же сценарии на Smoke через `Smoke.slnx` вне репозитория (задержка 999 мс): **all checks passed**,
  ранняя отмена так же оставляет по одному host. Сводка не называет решение и не содержит путей вне
  `<spike>`/`<fixture>` (F-06). Замена путей без учёта регистра проверена и на пути вида
  `e:\private\…` против корня `E:\Private`.
