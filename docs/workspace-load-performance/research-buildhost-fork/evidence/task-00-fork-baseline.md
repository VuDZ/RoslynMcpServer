## Upstream

- `dotnet/roslyn` `35d9211b841e7613c1d2f8f5af6d628ace696c4c` (`release/insiders`, 2026-07-07) —
  ревизия из nuspec пакета `Microsoft.CodeAnalysis.Workspaces.MSBuild` 5.9.0.
- Дословно скопированы 109 файлов, с хешами в `forks/roslyn-buildhost/UPSTREAM.md`:
  - `BuildHost` и `Contracts`;
  - общий проект `src/Dependencies/Contracts`;
  - 16 файлов компилятора, которые подключает проект BuildHost;
  - `License.txt`, `THIRD-PARTY-NOTICES.txt` и `.editorconfig` Roslyn.

  Лицензия MIT. Копия хранится без перевода строк (`.gitattributes`, F-09), поэтому хеши сходятся и в
  свежем Windows-checkout с `core.autocrlf=true` (во втором раунде проверено 109 из 109). Рабочая копия,
  выписанная до этого правила, остаётся с CRLF, пока файлы не выписаны заново:
  `git rm -r --cached forks/roslyn-buildhost/upstream` и `git checkout -- forks/roslyn-buildhost/upstream`.
  Оба ревью первого раунда сверили blob-ы с деревом upstream: 109 из 109.
- Минимальная граница форка — только процесс BuildHost-netcore.
  - Клиент (`Microsoft.CodeAnalysis.Workspaces.MSBuild.dll`) берёт BuildHost из папки
    `BuildHost-netcore` рядом с собой (`BuildHostProcessManager.GetBuildHostPath`) и общается с ним
    JSON по именованному каналу. Вторая раскладка в `GetBuildHostPath` — `contentFiles/any/any/BuildHost-netcore`,
    когда клиент загружен прямо из папки NuGet-пакета; в раскладке spike и сервера её нет. Возврата к dll
    пакета после ошибки нет (проверено обоими ревью по исходникам той же ревизии).
  - Поэтому подмена — это копирование сборки форка в эту папку. Сборка Contracts форка
    используется только процессом BuildHost.
- Не форкаются: клиент, `BuildHost-net472` и Mono. Какой host получает проект, клиент решает по его
  XML, а не только по TFM: SDK-style проект `net472` идёт через netcore-host, то есть через форк. Проект
  .NET Framework старого формата на Windows идёт в `BuildHost-net472`, а без пригодного Visual Studio
  MSBuild клиент переводит его на netcore-host (`GetBuildHostWithFallbackAsync`) — снова через форк (G-07).

## Сборка без Arcade

`forks/roslyn-buildhost/build/`, проекты названы как в upstream:
`Contracts/Microsoft.CodeAnalysis.Workspaces.MSBuild.Contracts.csproj` и
`BuildHost/Microsoft.CodeAnalysis.Workspaces.MSBuild.BuildHost.csproj`.

- Обычный .NET SDK; параметры как у пакета: net8.0, `rollForward: Major`, `MSBUILDWORKSPACE_BUILDHOST`.
- Из upstream `eng/targets/Settings.props`: `LangVersion=preview`, `Nullable`, `Features=strict`,
  `WarningLevel=9999` (последние два добавлены после ревью, G-05). Сборка без предупреждений.
- Ссылки на reference-сборки MSBuild 17.11.48 через `PackageDownload`, как upstream
  `PackageDownloadAndReference`; Microsoft.Build.Locator 1.10.2.
- Ресурсы генерирует SDK вместо Arcade `GenerateSource`. Имя ресурса и обе строки совпадают с пакетом
  (проверено обоими ревью).

Результат:

- состав выходной папки как у `BuildHost-netcore` пакета: BuildHost, Contracts, Locator, `deps.json`,
  `runtimeconfig.json`; у форка есть ещё pdb host;
- `deps.json` отличается версией (`5.9.0` против `5.9.0-1.26357.3`), `fileVersion` Contracts (см. ниже) и
  списком сателлитных ресурсов: у пакета он есть, а самих сателлитов в его папке нет. Лишняя запись `Contracts.Reference`
  появлялась, пока имя файла проекта не совпадало с именем сборки (G-06);
- версия сборки 5.9.0, информационная — `5.9.0-fork+35d9211b…`; FileVersion 5.9.0.0 против
  `5.900.26.35703` у пакета;
- нет strong name и Authenticode: клиент проверяет только наличие файла, Contracts форка грузит только
  процесс host;
- локализованные ресурсы (xlf) не собираются. В папке пакета сателлитов тоже нет, так что на этой
  раскладке сообщения обеих сторон английские.

## Сравнение оригинал / форк

`spikes/BuildHostFork/Invoke-BuildHostForkBaseline.ps1`:

- spike собирается один раз, а его копия `bin-fork` получает форк в `BuildHost-netcore`;
- перед прогонами — самопроверка сравнения (`check`, 19 синтетических случаев);
- раунды чередуют порядок сторон, раунд 0 — прогрев;
- `observe` снимает `SolutionObservation` из `spikes/ParallelLoad`, диагностики workspace, первый
  поиск, CPU и пик памяти клиента сразу после загрузки (G-02), опрос процессов BuildHost каждые
  100 мс. Учитываются только потомки процесса spike (F-02), у каждого host записывается его папка;
- `compare` — правила `compare.py` (G-01): эталон — раунд 1 оригинала; естественный разброс — только
  различия раундов 1 и 2 оригинала; диагностики — симметрическая разность; раунды 3+ оригинала
  проверяются тем же правилом. Строже `compare.py`:
  - нет исключения для путей, отличающихся только регистром;
  - поля проекта, который есть только в одном из запусков, тоже сравниваются, с отсутствующим значением
    на другой стороне: иначе проект, появившийся в раунде 2 оригинала, принял бы у форка любые поля (R2-05);
  - ответ первого поиска одинаков во всех запусках, включая прогрев;
  - каждый запуск завершён (`Status`), процессы BuildHost в нём записаны (R2-04), host из папки своей
    стороны, неопознанных процессов нет и через 10 с после первого поиска не осталось ни одного host (G-03).

  JSON `null` не равен пустой строке. При нарушении `compare` и скрипт завершаются с ошибкой; причина
  называет сторону: отличие форка, нестабильность оригинала (в том числе его ответа поиска) или проверку
  запусков.

До ревью `compare` брал эталоном прогрев и считал естественным разбросом любое значение любого раунда
оригинала (G-01). Опубликованные ниже результаты Roslyn.slnx и офиса получены той версией. Для
Roslyn.slnx GPT пересчитал сохранённые JSON: поля проектов, диагностики и ответ поиска равны во всех
8 запусках, поэтому и по новым правилам результат identical. Офисные JSON у владельца; новая версия
читает и старые файлы, но без полей процессов результат — «not shown equivalent»: старый sampler считал
процессы по имени и не доказывал ни их папку, ни их завершение (R2-04).

### Что не сравнивается

`SolutionObservation` — снимок из E0, а не полный oracle приёмки task-00 (F-04). Не сравниваются:

- сгенерированные исходники (`GetSourceGeneratedDocumentsAsync`): ни набор, ни содержимое;
- содержимое документов, additional и analyzer config: только пути;
- происхождение анализаторов сверх `AnalyzerReference.FullPath`: версия, хеш, MVID, результат загрузки;
- опции компиляции и разбора вне снятого подмножества: снимаются `OutputKind`, `Platform`,
  `OptimizationLevel`, `CheckOverflow`, `SpecificDiagnosticOptions`, для C# — `Nullable`, `AllowUnsafe`,
  `LanguageVersion`; для разбора — символы препроцессора, `DocumentationMode`, `Features`. Не
  снимаются, например, `WarningLevel`, `GeneralDiagnosticOption`, `Deterministic`, языковые опции VB;
- эффективные свойства варианта проекта (TFM, global properties) отдельным полем: варианты различаются
  ключом «путь + имя»;
- `CompilationOutputInfo.GeneratedFilesOutputDirectory`;
- диагностики компиляции и анализаторов: поле Diagnostics — события `WorkspaceFailed`.

Пределы самого сравнения:

- естественный разброс оценивается по одному переходу (раунды 1 и 2 оригинала): редкое значение
  оригинала в раунде 2 объясняет такое же систематическое значение форка;
- процесс, который появился и завершился между опросами (100 мс), не виден; цепочка до процесса spike
  обрывается на уже завершённом промежуточном родителе. BuildHost — прямой потомок spike, поэтому для
  него это не важно, но обобщать sampler на произвольное дерево процессов нельзя;
- выход host проверяется через 10 с после первого поиска, а не после загрузки.

Поиск сравнивает ответ одного запроса, а не всё содержимое. Поэтому «identical» ниже означает
совпадение снятых полей. Изменение в перечисленном BuildHost/task-00 не обнаружит; для task-02 это
ограничение остаётся, расширять снимок — отдельное решение.
