# BuildHost/task-00 — воспроизводимый форк: локальная часть

Дата: **2026-10-24**. Решение владельца 2026-10-23: вариант A — папка `forks/roslyn-buildhost`
в research-ветке; стиль кода форка — Roslyn, не `docs/code-style.md` (записано в `AGENTS.md`

## Upstream

- `dotnet/roslyn` `35d9211b841e7613c1d2f8f5af6d628ace696c4c` (`release/insiders`, 2026-07-07) —
  ревизия из nuspec пакета `Microsoft.CodeAnalysis.Workspaces.MSBuild` 5.9.0.
- Дословно скопированы 109 файлов, с хешами в `forks/roslyn-buildhost/UPSTREAM.md`:
  - `BuildHost` и `Contracts`;

  Лицензия MIT.
- Минимальная граница форка — только процесс BuildHost-netcore.
  - Клиент (`Microsoft.CodeAnalysis.Workspaces.MSBuild.dll`) берёт BuildHost из папки
    `BuildHost-netcore` рядом с собой (`BuildHostProcessManager.GetBuildHostPath`, декомпиляция)
    и общается с ним JSON по именованному каналу.
  - Поэтому подмена — это копирование сборки форка в эту папку. Сборка Contracts форка
    используется только процессом BuildHost.
- Не форкаются: клиент, `BuildHost-net472` (проекты .NET Framework на Windows; в офисном решении
  такие варианты есть, это ограничение до task-02) и Mono.

## Отказные сценарии, локально, 2026-10-24

`spikes/BuildHostFork/Invoke-BuildHostForkScenarios.ps1`, сводка в `scenarios.md`. Linux 2 vCPU,
SDK 10.0.113.

Что изменилось в spike:
- sampler распознаёт BuildHost по командной строке процесса: Linux — `/proc`, Windows —
  `NtQueryInformationProcess`. Поэтому видно, из какой папки запущен host;
- считается и `BuildHost-net472` (отдельный `.exe`). Раньше sampler видел только процессы
  `dotnet`, поэтому в офисной таблице выше net472-host не учтён;
- `observe` после загрузки ждёт до 10 с, пока процессы BuildHost завершатся, и записывает,
  сколько осталось (`RemainingBuildHosts`);
- новые команды `load`, `cancel`, `kill-host`: исход загрузки записывается, а не бросается.

Фикстура генерируется в папке результата. В ней:
- `Ok` (net8.0);
- `MultiTfm` (net10.0;net8.0, ссылка на `Ok`);
- проект со ссылкой на отсутствующий проект;
- F#-проект;
- C++-проект;
- проект с битым XML;
- запись решения на отсутствующий файл.

| сценарий | исход | процессы BuildHost | остались после загрузки |
|---|---|---|---|
| фикстура, оригинал / форк (observe, прогрев + 1 раунд) | **identical**, 6 проектов, 5 одинаковых Failure | 1, из своей папки | 0 |
| форк без своей dll | исключение `The build host could not be found at '<spike>/bin-fork-broken/BuildHost-netcore/…'` через ~1,1 с | 0 | 0 |
| отмена через 1,5 с после старта host, оригинал / форк | `canceled`, через 0,7–0,9 с после отмены | 1 | 0 |
| убийство host через 1,5 с, оригинал / форк | исключение `The server disconnected unexpectedly.` через ~30 мс | 1, перезапуска нет | 0 |

Отмена и убийство host проверялись на `RoslynMcpServer.sln`.

Выводы:
- Отказы обрабатываются одинаково:
  - диагностики фикстуры совпадают построчно;
  - битый, отсутствующий и C++-проект дают `Failure` и остаются в решении;
  - F#-проект загружается как проект без документов;
  - варианты multi-TFM совпадают.
- Перехода на оригинальный host нет:
  - копия форка без dll падает исключением, а не грузится через другой host;
  - в успешных прогонах командная строка показывает, что host запущен из `bin-fork/BuildHost-netcore`.
- Ни в одном сценарии процесс BuildHost не пережил загрузку. Зависаний нет (лимит 5 мин), host
  после убийства не перезапускается.

## Отказные сценарии на Windows, 2026-10-24

Основной компьютер владельца (стенд из раздела Roslyn.slnx). Отмена и убийство host проверялись
на Roslyn.slnx через 5 с после старта host. Сводка передана владельцем.

| сценарий | исход | процессы BuildHost | остались после загрузки |
|---|---|---|---|
| фикстура, оригинал / форк | **identical**, 6 проектов, те же 5 Failure, что и на Linux | 1, из своей папки | 0 |
| форк без своей dll | исключение `The build host could not be found at '<spike>\bin-fork-broken\…'` через 0,4 с | 0 | 0 |
| отмена, оригинал / форк | `canceled`, через 1,4 / 1,1 с после отмены | 1 | 0 |
| убийство host, оригинал / форк | исключение `The server disconnected unexpectedly.` | 1, перезапуска нет | 0 |

- Чтение командной строки через `NtQueryInformationProcess` работает: host каждой стороны
  найден в своей папке.
- После убийства host загрузка заканчивается раньше, чем `Kill` возвращает управление: время
  загрузки на 2–3 мс меньше отметки «disturbed at».
- Выводы локального прогона подтверждаются. В Roslyn.slnx нет проектов .NET Framework, поэтому
  процессов net472-host не было. Они появились бы только в офисе, где этот host не форкнут.
