## Находки

### Major. Ошибка записи трассы становится ошибкой запроса

`forks/roslyn-buildhost/upstream/src/Workspaces/MSBuild/BuildHost/Tracing/BuildHostTrace.cs:38-46`,
`:79-94`, `:132-145`.
`forks/roslyn-buildhost/upstream/src/Workspaces/MSBuild/BuildHost/Rpc/RpcServer.cs:127-181`.

`WriteLine` и `Initialize` не ловят сбой каталога, полного диска и занятого файла.
`Dispose` спана уже выставил `_disposed` и вернул родительский span, затем пишет строку.
Исключение из `Dispose` выходит наружу.

Внутренние `using` (`rpc-invoke`, `reevaluate`, `msbuild-build`, `extract`) стоят внутри
`try` в `ProcessRequestAsync`. Сбой записи дочернего спана ловит этот `catch` и уходит
клиенту как `Response` с исключением, хотя сборка уже прошла. `Initialize` при той же
ошибке роняет процесс до приёма соединения: клиент видит мёртвый host.

Сценарий: `ROSLYN_BUILDHOST_TRACE_DIRECTORY` задан, каталог есть, диск заполняется на
середине `GetProjectFileInfosAsync`. Host до этого отвечал как оригинал. Следующий
дочерний span при `Dispose` бросает `IOException`, клиент получает failure загрузки
проекта. Сравнение с оригиналом расходится. То же при отсутствии прав на каталог —
процесс не стартует.

Без переменной `Start` выходит на `s_writer is null` и объект span не создаёт.
Опубликованные identical-прогоны писали трассу успешно, поэтому их цифры эта дыра
не отменяет.

Исправление: `IOException` / `UnauthorizedAccessException` в `WriteLine` и `Initialize`
глушить, трассу на этот процесс выключать (`s_writer = null`) и не менять ответ RPC.

### Minor. «0 нарушений» не значит «нет запроса вне операции»

`spikes/BuildHostFork/Trace/ClockCheck.cs:21-42`.
Отчёт: `evidence/task-01-graph-and-timings.md:148-150`, `:277-280`.

Кандидат в пару — запрос, который уже удовлетворяет
`Sent >= operation.Start && Received <= operation.End`. Не нашёлся такой запрос —
`unmatched`, не `violations`. Запрос целиком левее или правее операции (сдвиг часов
больше длины операции, пропуск строки) выглядит так же, как проект без трассы.
Запросы, которые не легли ни в одну операцию, счётчик не видит: он идёт от операций,
а не от списка RPC. Один и тот же запрос теоретически может закрыть две перекрывающиеся
операции одного пути; у последовательного клиента 5.9.0 операции одного пути не
перекрываются, так что для этих прогонов двойной зачёт не получается.

Отличить можно только по сырой трассе: есть span `LoadProjectFileAsync` /
`GetProjectFileInfosAsync` этого пути, но он не прошёл фильтр — часы или привязка;
span нет и у прогона два процесса BuildHost — нетрассируемый host. `ClockCheckResult`
этого разделения не пишет, `trace-summary` печатает только три числа.

На Roslyn.slnx unmatched = 0, matched = 2544 = 318 путей × Evaluate/Build × 4 раунда
(434 project id — это сборки по TFM, не 434 операции клиента). Хвосты matched −0,002 мс
и −0,077 мс. Глобальный сдвиг часов при таких хвостах не проходит.

В офисе 1096 + 40 = 142 × 2 × 4, в раунде 1 ровно 274 + 10. Хвост matched −0,204 мс.
Такая решётка (ровно 10 операций на загрузку, остальные внутри на сотые миллисекунды)
не похожа на сдвиг часов: сдвиг вынес бы короткие Evaluate пачкой и сдвинул бы хвост
matched. Чтение «5 проектов net472» с этим согласуется и с двумя процессами task-00.
Инструмент сам проекты не называет. `client.json` в Git нет, список 40 путей я не видел.

Исправление: unmatched делить на «span этого пути нет» и «span есть, но вне операции»;
второе считать нарушением. Печатать пути.

### Minor. Фикстура не закрывает два пункта контракта, и одна проверка дырявая

`spikes/BuildHostFork/Test-BuildHostTrace.ps1:86-103`.
`spikes/BuildHostFork/Trace/LoadGraphBuilder.cs:37-63`.

Четырнадцать `Assert-Trace` пустыми не проходят: нулевое число span или рёбер не равно
ожидаемому, пустой `documents` не даёт `net8 == net10 + 1`. Это проверено чтением
скрипта, не прогоном (прогон ниже).

Контракт просит один путь с разными properties. Фикстура даёт `SetTargetFramework`
на ссылке Second → Lib и проверяет только наличие ребра-элемента. Свойство в ребро
не пишется, отчёт честно говорит, что оно внутри design-time build. Узла «тот же путь,
другой набор global properties» нет. Ключ узла — путь и TFM сборки `build-instance`.
Configuration и Platform берутся из первой корневой `evaluate` этого пути
(`group.First()`), не из evaluation после смены TFM. Другие global properties
(SolutionDir и остальные) в узел не входят. Повторная загрузка того же пути другим
контекстом видна только как `cached` в инвентаре повторов, если host отдал Project
из кеша. Такого случая в фикстуре нет.

Запись решения, которую workspace не грузит (`.vcxproj`, `.shproj`), фикстура не
строит. Native — `.proj` вне решения, узел без сборки и без `SolutionEntryKind`.
Ветка «запись решения, Built=false, Kind задан» остаётся без свидетеля фикстуры.
Офисные 90 таких записей держатся на отчёте прогона, не на этом скрипте.

Дыра в самой проверке output path: утверждается сумма запросов 2 и одно ребро
Second → Native. Ребро App → Native не требуется. Один запрос без Resolve и один
запрос Second дают тот же результат.

Исправление: фикстура с двумя записями одного пути и разными global properties;
`.vcxproj` внутри решения; ребро App → Native. В графе либо хранить global properties
сборки, либо в пределах явно написать, что ключ — только путь, TFM, Configuration
и Platform первой корневой evaluation.

### Nit. Span возврата TFM шире одного `ReevaluateIfNecessary`

`ProjectBuildManager.cs:247-273`.

Порядок upstream тот же: `SetGlobalProperty`, `ReevaluateIfNecessary`, сборка,
затем снятие или возврат global property и ещё одно `ReevaluateIfNecessary`.
Span смены включает `Set` и `ReevaluateIfNecessary`. Span с
`restoresTargetFramework` включает ещё `Remove`/`Set`, `ReevaluateIfNecessary`
и `return results.ToArray()`. Ранний выход одно-TFM проекта по-прежнему без
этих span. На оценке 1,5 с против 6,8 с это не меняет кандидата. В подписи
к цифре стоит сказать, что 1 483 мс — span целиком, не голый вызов
`ReevaluateIfNecessary`.

### Nit. «Очередь RPC» включает разбор JSON запроса

`RpcServer.cs:75-89`. `WallBreakdown.cs:120-123`.

`received` снимается до `JsonSerializer.Deserialize`, span `rpc` начинается
уже в `Task.Run`. Отрезок `rpc-queue` — разбор строки плюс ожидание пула.
На Roslyn.slnx медиана категории 44 мс из 42 394. Имя в отчёте («очередь пула
потоков») уже, чем интервал. На вывод «RPC не узкое место» это не влияет:
вся RPC-группа посчитана отдельно (930 мс на основном компьютере).

### Nit. При выключенной трассе на каждую строку запроса всё же вызывается `GetTimestamp`

`BuildHostTrace.cs:36`. `RpcServer.cs:75-76`.

`Start` при `s_writer == null` возвращает `null` до аллокации. `using` на `null`
порядок MSBuild-вызовов не меняет. `BuildHostTrace.Timestamp` выполняется всегда:
одно чтение QPC / `CLOCK_MONOTONIC` и локальная длина строки, без файла и без
объекта span. Для эквивалентности ответа это шум. Утверждение «ничего не пишет
и не создаёт объектов» для span верно; безусловное чтение часов в тексте
метода стоит назвать.

## Проверено и в порядке

Проверено чтением кода на `a35f682` и сверкой закоммиченных сводок. Сырые
`jsonl` / `client.json` / binlog не перечитывались.

- **Без переменной протокол не меняется.** `git diff ac92063~1 a35f682 --stat`:
  production-проектов нет, только форк, spikes и docs. `Start` ранний выход.
  Аргументы `Set` (imports, документы, ссылки, первая строка RPC) считаются
  только при `span is not null`. В трассу попадает путь и флаг
  `ReferenceOutputAssembly`, не текст исходника: `LoadProject(path, projectContent, …)`
  кладёт в `argument` только первый параметр (`RpcServer.cs:155-156`,
  `AbstractBuildHost.cs:147`). `ConfigureGlobalState` первым аргументом принимает
  `string[]`, в эту ветку не попадает. Стартовая строка — pid, частота, timestamps,
  `FrameworkDescription`; переменных окружения и секретов нет.
- **Вложенность span.** `AsyncLocal` выставляется в `Start` и снимается в `Dispose`.
  Цикл чтения сам span не открывает, каждый запрос уходит в `Task.Run` со снимком
  контекста, где текущий span пуст. Параллельные запросы будут соседями, не
  родителем и ребёнком. Запись JSONL под `s_gate`. Клиент 5.9.0 запросы не
  параллелит: `MSBuildProjectLoader.Worker.LoadAsync` на `35d9211` идёт по
  проектам циклом с `await`. В сводках категория «several host spans at once» —
  медиана 0 мс (максимум 1 мс на основном компьютере, 6 мс на офисном).
- **Порядок смены TFM.** См. nit выше. Подсчёт владельца сходится с категорией:
  медианы раундов 1–3 дают смены 6 819 и возвраты 1 483, сумма 8 302 — медиана
  категории; суммы раундов 8 302 / 8 512 / 8 106 и прогрев 7 917 совпадают с
  min/max/warmup сводки (7 918 — округление `Format`). 245 − 129 = 116 и
  434 сборки − 318 путей = 116. Атрибут `restoresTargetFramework` в коде стоит
  только на span возврата. Сами jsonl я не суммировал.
- **`Report` синхронный.** На `dotnet/roslyn@35d9211`,
  `ProjectLoadProgressExtensions.DoOperationAndReportProgressAsync`:
  `Stopwatch.StartNew`, `await doFunc()`, в `finally` — `Stop()` и сразу
  `progress.Report`. Это не `Progress<T>` и не пост в контекст синхронизации.
  `MSBuildWorkspace.OpenSolutionAsync` передаёт тот же `IProgress` в
  `LoadSolutionInfoAsync`. Spike передаёт `ProgressRecorder`, не `Progress<T>`
  (`Program.cs:85-88`). Конец операции в трассе клиента — `GetTimestamp` внутри
  `Report`, на несколько вызовов позже `Stop`. Допуск 1 мс это покрывает;
  наблюдаемые хвосты — микросекунды и −0,2 мс. Evaluate и Build в
  `BuildHostProjectFileInfoProvider` передают `targetFramework: null` и оборачивают
  весь RPC (`LoadProjectFileAsync` / `GetProjectFileInfosAsync`), поэтому одна
  клиентская Build прячет все TFM. Resolve несёт TFM и внутри себя грузит ссылки.
  Разбивка окна на этом стоит верно.
- **Общие часы.** `TraceReport.Run` бросает, если частота host и клиента разная.
  `Stopwatch` в .NET — QPC на Windows и `CLOCK_MONOTONIC` на Linux, оба общие
  для процессов машины; отдельного двухпроцессного эксперимента я не ставил.
  Проверка на загрузке как раз ловит нарушение этой предпосылки в пределах
  допуска. Старт процесса — оценка: `HostTraceReader` вычитает wall-clock от
  `processStartUtc` до `utc` из timestamp стартовой строки. Отчёт это помечает.
- **Разбивка одного раунда складывается в окно.** `Sweep` идёт от `LoadStart`
  до `LoadEnd`, дырки подписывает. Host-сегмент — span минус объединение детей
  (`Subtract`). Перекрытие exclusive-сегментов host не делится, а уходит в
  отдельную категорию, поэтому двойного счёта нет. Работа span вне окна
  обрезается и в сумму окна не входит. Незакрытый span в файл не пишется
  (строка пишется в `Dispose`): его время остаётся в родителе, если родитель
  закрылся, иначе выглядит как ожидание клиента. Успешный прогон такие span
  не оставляет.
- **Запись строки ребёнка попадает в родителя, не в лист.** `end` снимается до
  `WriteLine`. У `evaluate`, `reevaluate`, `msbuild-build`, `extract` детей нет,
  их категории записью не раздуваются. Запись ложится в exclusive родителя:
  `load-project` («project file read»), `build-instance` / `build-project`
  («build bookkeeping»), `rpc-invoke` («RPC method, other»). На основном
  компьютере медианы этих вёдер 49 + 33 + 88 мс — верхняя граница, если бы
  они целиком были записью трассы. Отчёт величину не оценивает; на порядок
  кандидатов (18 с / 8 с / 6 с) эта граница не влияет.
- **Медианы категорий не обязаны давать медиану окна.** `TraceRounds` берёт
  медиану каждой категории отдельно, пропуск категории в раунде — 0.
  Отчёт пишет 42,5 с против 42,4 с. Пересчёт групп основного компьютера:
  RPC 529+227+88+44+42 = 930; «остальное host» 413+51+49+35+33+4 = 585;
  клиент между/до/после 775+539+91 = 1 405; ожидание 252+38 = 290.
  Сумма всех медиан 42 549 против медианы окна 42 394. Офисный компьютер:
  группы отчёта сходятся, сумма 107 937 против 107 737. Офисное решение:
  13 740+10 381+10 080+670+523+5 242+1 889+970 = 43 495 против 43 379.
  Раунд 1 офиса (10 267 мс корневой evaluation) не подменяет медиану 10 381.
- **Граф не выдаётся за полный.** Узел — путь и TFM сборки плюс Configuration/
  Platform первой корневой evaluation. Рёбра: элемент `ProjectReference`
  (`EvaluatedInclude`, префикс `roa=false|`), загрузка клиента внутри самого
  внутреннего Resolve, output path внутри Resolve. Ссылки, которые MSBuild
  резолвит задачей внутри сборки, в трассу не попадают; комментарий
  `LoadGraphBuilder` это говорит, отчёт тоже. `GraphEdge` — record, `Distinct`
