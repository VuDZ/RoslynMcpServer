# BuildHost/task-01 — разбор ревью раунда 1

Дата: **2026-10-24**. Ревью на commit `a58486a`: [Grok 4.7](review-grok-4-7.md) и
[DeepSeek Flash](review-deepseek-flash.md); запрос — [request.md](request.md). Оба вердикта: блокеров нет,
выводы держатся на коде и сводках; одна major-находка в инструменте у обоих. Ниже — каждая находка, решение и
что сделано. Номера F-xx использует [отчёт task-01](../task-01-graph-and-timings.md).

## Исправлено в коде

| № | Находка | Решение |
|---|---|---|
| F1 | **Major (оба).** Ошибка создания или записи трассы меняет поведение host: из `Initialize` роняет host до подключения клиента, из `Dispose` span внутри `ProcessRequestAsync` превращает выполненный запрос в ответ с ошибкой. | `BuildHostTrace`: ошибка в `Initialize` и при записи строки span выключает трассировку до конца процесса (`s_writer = null` через `CompareExchange`, файл закрывается без исключений), один раз пишется в stderr host; ответ RPC не меняется. Клиентская половина (`client.json`) тоже best effort. Фикстура: загрузка с переменной, указывающей на существующий файл, даёт тот же workspace; с отключённой обработкой ошибки та же загрузка падает (exit code 134) — проверка ловит регрессию. Ошибка записи в середине загрузки не воспроизведена: тот же путь выключения, проверено чтением. |
| F2 | **Minor (оба).** «Unmatched» не отличает проект нетрассируемого host от запроса вне своей операции; запросы вне всех операций не считаются. | `ClockCheck` в обе стороны: операция, чьи запросы есть, но вне неё (`OutsideOperation`), и запрос вне всех операций (`UnclaimedRequests`) — нарушения; операция без единого запроса своего пути и метода — `Untraced`, перечисляется в отчёте по имени и не валит `trace-report`. **Найдено при исправлении:** хвост считался от конца span отправки, а клиент может дочитать ответ раньше, чем host вернётся из `FlushAsync` — на Linux с 2 vCPU это дало −2,62 мс в одном раунде. Хвост теперь считается от начала отправки, раньше которого клиент ответ получить не может. Опубликованные «0 нарушений» получены более строгим правилом и остаются верными. |
| F3 | **Minor (оба).** Фикстура проверяет меньше заявленного: не проверены `restoresTargetFramework`, ребро App → Native, счётчики повторов; нет записи решения без загрузки и отказа трассы. | 19 проверок вместо 14: полнота трассы и часы в обе стороны; ровно одна переоценка с `restoresTargetFramework` и без TFM, смены на net10.0 и net8.0; рёбра output path от App и от Second; единственная загрузка из кеша, ноль повторных evaluation и сборок; запись решения `Cpp.vcxproj` — узел без сборки с видом записи; та же загрузка без трассировки и с неисправным каталогом даёт те же проекты и диагностики. Вместо проверки «без переменной файла нет» (без переменной host не знает каталога) — равенство трассированной и нетрассированной загрузки. «Один путь с разными properties» шире разных TFM фикстура не строит: в 5.9.0 загрузчик других различий не создаёт (F7). |
| F13 | **Minor (DeepSeek m-10).** Повторный `-OutDirectory` смешивает host-файлы прошлого и нового прогонов. | `Invoke-ObserveRounds` удаляет каталог трассы раунда перед запуском; `trace-report` отвергает host-файл, начатый вне окна загрузки `client.json` (проверено подложенным файлом другого прогона). |
| F14 | **Minor (DeepSeek m-11).** Обрезанная трасса (host остановлен посреди span) не обнаруживается, разбивка всё равно сходится. | `HostTraceReader` считает нечитаемые строки, `TraceReport` — span без родителя; отчёт помечает трассу «incomplete», `trace-report` возвращает 1, `trace-summary` не усредняет такие раунды и раунды с нарушениями часов. Проверено на копиях трассы фикстуры: удалённая строка `rpc` даёт 3 span без родителя, обрезанная строка — 1 нечитаемую. |
| F15 | **Minor (DeepSeek m-12).** Заглушки включаются только для решения вне репозитория: внешний проект решения внутри репозитория попал бы в отчёт полным путём. | `PathNames`: путь вне каталога решения (`..` или другой диск) получает заглушку и без `redact`, `names-private.json` пишется при любой заглушке. Проверено: при корне в подкаталоге фикстуры остальные проекты стали заглушками, полных путей в `report.md`, `report.json`, `graph.json` нет. |
| N4 | **Nit (DeepSeek n-3).** Состав раунда берётся из первого; подпись `HostMs`; заглушки локальны для отчёта; медианы Linux не складываются в окно без оговорки. | `trace-summary` показывает все различающиеся значения состава; заголовок таблицы — «host time of the columns below»; в отчёте сказано, что номера заглушек идут по таблице проектов и действуют в пределах отчёта; оговорка о медианах — в `trace-summary` и в разделе Linux. |

## Исправлено в документах

| № | Находка | Решение |
|---|---|---|
| F4 | **Minor (Grok).** «На медленной машине evaluation весит больше сборки» — свойство Roslyn.slnx (116 дополнительных сборок по TFM), а не машины. | Переформулировано: на офисном компьютере evaluation замедляется сильнее сборки (×3,0–3,3 против ×1,9); перевес evaluation над сборкой — у решений с переоценкой TFM. В статусе задачи и README — так же. |
| F5 | **Minor (Grok), nit (DeepSeek n-2).** `project-001` — самый дорогой проект, а не первый; «разогрев ~2,2 с» подан как измерение. | Что это первый проект загрузки офиса, установлено по `client.json` и карте заглушек локально — теперь это сказано; номер заглушки объяснён. 2,3–2,5 с — первый проект целиком; разогрев — гипотеза (у `project-002` корневая evaluation тоже 547 мс). Так же для Linux. |
| F6 | **Minor (DeepSeek m-2).** «61 / 44 / 82 мс на проект» с разными знаменателями. | Знаменатели названы: корневая evaluation — на путь (318), извлечение и сборка — на сборку (434); у офисного решения на путь и на сборку одно и то же (137). |
| F7 | **Minor (оба).** Узел графа не включает global properties, кроме TFM. | Записано в пределах, в методе и в XML-doc `GraphNode`: ключ — путь и TFM, Configuration/Platform — подписи первой корневой evaluation; для 5.9.0 достаточно (один набор global properties на загрузку, host меняет только TFM). Код не менялся. |
| F8 | **Minor (DeepSeek m-6).** «Повторов нет» — это повторы, видимые трассой; для Roslyn.slnx вложенные сборки не разобраны. | Вывод сужен до «повторов, видимых трассой», в пределах — что инвентарь не видит вложенные сборки задачей MSBuild; для офиса они разобраны по binlog, для Roslyn.slnx — нет. |
| F9 | **Minor (DeepSeek m-1).** net472-host не трассируется, потому что это пакетный host, а не форк; объяснение через AppDomain — не та причина. | Пределы, XML-doc `BuildHostTrace` и README форка: эксперименты подменяют только `BuildHost-netcore`; собранный из форка net472-host дал бы только RPC-span. |
| F11 | **Minor (DeepSeek m-3).** `docs/README.md` и `docs/workspace-load-performance/README.md` писали «Roslyn.slnx и офис pending». | Обновлены вместе со статусом задачи. |
| F12 | **Minor (DeepSeek m-8).** «1 435 `GetTargetPath` = 1 435 рёбер, один вызов на ссылку» подано как соответствие 1:1. | Теперь — совпадение итогов двух прогонов; трасса не записывает `BuildReference`/`SkipGetTargetFrameworkProperties`. Вывод «2 740 — только протокол ссылок» от этого не зависит. |
| N1 | **Nit (Grok).** Span возврата TFM шире одного `ReevaluateIfNecessary`. | В отчёте: 1 483 мс — span целиком (снятие или возврат свойства, переоценка, массив результатов). |
| N2 | **Nit (Grok).** «Очередь RPC» включает разбор JSON запроса. | Названо в методе, пределах и подписи отчёта: разбор запроса и ожидание потока пула. Имя категории в коде не менялось, чтобы старые отчёты читались так же. |
| N3 | **Nit (оба).** При выключенной трассировке `RpcServer` всё равно читает часы и длину строки. | XML-doc `BuildHostTrace`, README форка и отчёт: span не создаются и ничего не пишется, часы читаются на каждый запрос. Код не менялся: одно чтение `Stopwatch` на запрос на ответ не влияет. |

  ревьюера, не код задачи; DeepSeek Flash на Windows с SDK 10.0.402 получил 14/14 на тех же коммитах.
