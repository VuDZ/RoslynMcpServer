## Повторные evaluation внутри сборок

Разбор binlog локальной программой на событиях `ProjectEvaluationFinished` и `ProjectStarted`: для каждой
evaluation внутри сборок — её глобальные свойства против глобальных свойств сборки верхнего уровня того же
проекта (это свойства host: значения по умолчанию `ProjectBuildManager` и `SolutionDir`).

| binlog | evaluation внутри сборок | с теми же свойствами, что у сборки верхнего уровня | время |
|---|---|---|---|
| офис, task-00a, `load.binlog` (netcore-host) | 102, 5 281 мс | 100, 5 266 мс | 2 — проекты без сборки в этом потоке, 15 мс |
| `RoslynMcpServer.sln`, Linux, 2026-10-24 | 3, 278 мс | 3, 278 мс | — |

Вложенные запуски офиса — 1 433 `GetTargetPath` и 1 259 `GetTargetFrameworks` с теми же свойствами, ещё 4 — к
проектам без сборки. То есть это не другая конфигурация, а повтор корневой evaluation host: MSBuild оценивает
ссылку внутри сборки проекта, который на неё ссылается, потому что её собственная сборка ещё не начиналась. Оба
binlog писались с логгером, поэтому время evaluation — оценка сверху; в окне трассы офиса (43,4 с) это до ~12 %.

**Roslyn.slnx** (binlog task-00a, основной компьютер владельца, 2026-10-23, commit протокола): 250 evaluation
внутри сборок, 5 424 мс. Для проектов с несколькими TFM host собирает каждый TFM своей конфигурацией, поэтому
сравнение — со всеми сборками верхнего уровня пути и с корневой evaluation (те же свойства без `TargetFramework`):

| совпадает с | evaluation | время |
|---|---|---|
| одной из сборок верхнего уровня пути (по TFM или единственной) | 180 | 4 837 мс |
| корневой evaluation: внешняя конфигурация проекта с несколькими TFM, её спрашивает `GetTargetFrameworks` | 67 | 546 мс |
| ничем: другой `RuntimeIdentifier` или `TargetFramework` у проекта без такой сборки | 3 | 42 мс |

Первую группу убирает порядок «ссылки раньше». Вторую — нет: host никогда не собирает внешнюю конфигурацию
проекта с несколькими TFM, поэтому MSBuild оценивает её один раз внутри сборки, хотя её свойства совпадают с
корневой evaluation host. В офисе проектов с несколькими TFM нет, обе последние группы пусты.

## Проба порядка (`spikes/BuildOrderProbe`)

Проба собирает проекты так же, как host (глобальные свойства, одна `ProjectCollection` без логгеров, один
`BuildManager`, цели design-time build, переключение TFM), в порядках `client`, `references-first` и
`evaluate-ahead` и сравнивает хеши результатов каждой сборки ([README](../../../../spikes/BuildOrderProbe/README.md)).

Первая разовая проба на 5 проектах `RoslynMcpServer.sln` (Linux, 2 vCPU, 2026-10-24):
- клиентский порядок — 4 evaluation внутри сборок, «ссылки раньше» — 0; результаты сборок (`ReferencePath`,
  аргументы компилятора, Compile) совпали;
- все сборки разом в одном `BuildManager` с одним узлом — 5,8 с против ~1,8 с подряд: сборки на узле in-proc
  чередуются, а не идут параллельно; с 4 узлами out-of-proc — 10,6 с, и узлы снова оценивают проекты (3
  evaluation);
- корневые evaluation параллельно в одной `ProjectCollection` и evaluation наперёд одновременно со сборками —
  без ошибок, результаты те же; выигрыша на 2 vCPU нет (2,69 против 2,52 с).

`Invoke-BuildOrderProbe.ps1` на `RoslynMcpServer.sln` (Linux, 2 vCPU, 2026-10-25), прогрев и 2 раунда:

| порядок | потоков | wall, медиана | к client | вложенных evaluation |
|---|---|---|---|---|
| client | — | 3 761 мс | 1,000 | 3 |
| references-first | — | 4 068 мс | 1,082 | 1 |
| evaluate-ahead | 1 | 3 464 мс | 0,921 | 1 |

Результаты всех 9 прогонов identical. Одна вложенная evaluation остаётся и в `references-first`: ссылка, которую
обход по ProjectReference корневой evaluation не видит (см. пределы в README пробы). На машине с 2 vCPU разброс
раундов больше различий порядков; выводы о времени — по прогонам владельца.

## Что следует

- **A обоснована и измерена:** повторы точные, порядок их убирает, результаты не меняются. Офис — −15,9 % wall
  пробы, Roslyn.slnx — −9,6 %. Проба не включает RPC, извлечение `ProjectFileInfo`, клиента и net472-host: в окне
  загрузки сервера (офис 43,4 с, Roslyn.slnx ~42 с) это около −10 % и −8 %. Внешние конфигурации проектов с
  несколькими TFM (Roslyn ~0,5 с) можно добавить к A отдельно: host может сам зарегистрировать внешнюю
  конфигурацию из своей корневой evaluation.
- **B зависит от решения.** В офисе (проекты с одним TFM, evaluation дороже сборок) evaluation наперёд даёт ещё
  −3,7 с; на Roslyn.slnx (434 сборки, 129 проектов с несколькими TFM) — ничего: evaluation в 15 потоках шли в
  3,7 раза дольше каждая. Различие не объяснено; одна из гипотез — переключения TFM и переоценки на потоке
  сборок, которые держат общую блокировку коллекции. Для Roslyn.slnx B в пределах шума (0,913 против 0,904 у A),
  то есть не вредит.
- Вместе для офиса ожидание A + B — около −8 с из 43 (~19 % окна), выше порога task-02 (10 %).

## Разбор B: Roslyn.slnx с перебором потоков и server GC

Основной компьютер владельца, Roslyn.slnx, spike `e8784d0` (шкала шагов), прогрев и 3 раунда, 7 вариантов
([сводка](task-02-step-0/roslyn-home-sweep-summary.md)). Результаты всех 28 прогонов **identical**.

| вариант | wall, медиана | к client | evaluation одновременно | доля времени evaluation со сборками |
|---|---|---|---|---|
| client | 32 064 мс | 1,000 | 1,00 | 0 % |
| references-first | 29 738 мс | 0,927 | 1,00 | 0 % |
| references-first, server GC | 27 152 мс | **0,847** | 1,00 | 0 % |
| evaluate-ahead, 2 потока | 29 875 мс | 0,932 | 1,35 | 13 % |
| evaluate-ahead, 4 потока | 28 928 мс | 0,902 | 1,87 | 11 % |
| evaluate-ahead, 15 потоков | 29 836 мс | 0,931 | 3,78 | 4 % |
| evaluate-ahead, 15 потоков, server GC | 28 233 мс | 0,881 | 3,69 | 17 % |

Разбор шагов раунда 1 (JSON прогонов, локально):

- **Evaluation в одной `ProjectCollection` ждут друг друга, а не сборок.** Медианное замедление evaluation
  наперёд — 1,0, но 52 (4 потока) и 66 (15 потоков) из 318 evaluation идут в 3–94 раза дольше; на них приходится
  6,2 и 20,8 с суммы. Медленные evaluation шли в среднем вместе с 2,35 и 9,44 другими evaluation; нормальные —
  с 0,24 и 0,28. Со сборками медленные совпадали лишь 8 % (с несколькими TFM) и 4–5 % (с одним TFM) своего
  времени. Значит, одновременные evaluation фактически выполняются по одной, и это не переключения TFM на потоке
  сборок; что именно их сериализует в MSBuild, проба не показывает.
- **Поток сборок всё равно ждёт evaluation.** Время вне сборок: 7,6 с в references-first, 5,9–6,6 с в
  evaluate-ahead — спрятать удалось только 1–1,6 с. Обход в глубину начинает evaluation ссылок, когда оценён
  проект, и сразу спускается к первой ссылке, чья evaluation только что началась: опережение — один уровень.
  Evaluation идут пачками, пока сборки стоят (совпадение со сборками 4–17 %).
- **Server GC — отдельный выигрыш:** references-first −8 процентных пунктов (сборки 22,2 → 20,6 с).
  Пик памяти проба не измеряет; для host с server GC его нужно мерить (порог task-02 — +10 %).

Что из этого следует для B: больше потоков не помогает, пока evaluation сериализуются; помочь может только
опережение глубже одного уровня — evaluation всего замыкания ссылок сразу, по 1–2 потокам, чтобы они шли во
время сборок, а не перед ними. Офисное решение получило выигрыш и при опережении в один уровень; без шкалы
шагов (прогон до `e8784d0`) неизвестно, были ли там та же сериализация и простой сборок.

### Вариант с опережением на всё замыкание

Добавлен порядок `evaluate-closure` ([README](../../../../spikes/BuildOrderProbe/README.md)): каждая законченная
evaluation ставит в очередь evaluation своих ссылок, рабочие потоки (по умолчанию 1 и 2) берут сначала самые
глубокие, а поток сборок, дошедший до проекта, чья evaluation не начиналась, оценивает его сам. Цель —
evaluation во время сборок, а не перед ними. В сводке добавлены время вне сборок и число evaluation на потоке
сборок. Проверен на `RoslynMcpServer.sln` (Linux): прогоны identical; время на 2 vCPU о выигрыше не говорит.

### Опережение на всё замыкание: Roslyn.slnx на двух компьютерах

Spike `5ed3f66`, Roslyn.slnx, прогрев и 3 раунда, 7 вариантов на каждом компьютере (сводки:
[дом](task-02-step-0/roslyn-home-closure-summary.md), [офисный компьютер](task-02-step-0/roslyn-office-pc-closure-summary.md)).
Результаты всех 56 прогонов **identical**.

| вариант | дом, wall | к client | офисный компьютер, wall | к client |
|---|---|---|---|---|
| client | 34 553 мс | 1,000 | 86 661 мс | 1,000 |
| references-first | 30 471 мс | 0,882 | 78 342 мс | 0,904 |
| references-first, server GC | 28 160 мс | **0,815** | 73 919 мс | **0,853** |
| evaluate-ahead, 4 потока | 30 719 мс | 0,889 | 78 727 мс | 0,908 |
| evaluate-closure, 1 поток | 31 209 мс | 0,903 | 76 861 мс | 0,887 |
| evaluate-closure, 2 потока | 32 277 мс | 0,934 | 78 834 мс | 0,910 |
| evaluate-closure, 2 потока, server GC | 30 508 мс | 0,883 | 74 922 мс | 0,865 |

- **Evaluation пошли во время сборок, но сборки стали дольше на столько же.** Доля времени evaluation со
  сборками — 22–34 % против 10–12 % у evaluate-ahead; время вне сборок с 1 потоком — дом 7,4 → 5,7 с, офисный
  компьютер 22,5 → 17,5 с. Сборки (сумма) — дом 23,1 → 25,5 с, офисный компьютер 55,8 → 59,6 с. Wall против
  references-first: дом +0,7 с, офисный компьютер −1,5 с, раунды перекрываются (76 357–78 406 против
  77 871–78 553 мс); под server GC — медленнее references-first под server GC на 2,3 и 1,0 с.
- **Сборка стоит, пока в соседнем потоке идёт evaluation.** Разбор шагов раундов 1–3 (JSON прогонов, локально):
  сборки, которые больше 30 % своего времени шли вместе с evaluation рабочих потоков (4–13 на прогон, больше
  всего — Microsoft.CodeAnalysis и Microsoft.CodeAnalysis.CSharp с несколькими TFM), дольше той же сборки в
  references-first на 0,53 (дом) и 0,46 (офисный компьютер) мс на мс перекрытия с 1 рабочим потоком и на
  0,98–1,00 мс с 2 потоками — на обоих компьютерах и в обоих режимах GC. Пример: Microsoft.CodeAnalysis на
  офисном компьютере — 1 020 мс в references-first, 6,1–6,3 с при 5,1–5,3 с перекрытия. Вместе с прежним
  наблюдением (одновременные evaluation ждут друг друга) это значит, что на Roslyn.slnx evaluation и design-time
  build в одном процессе фактически не идут одновременно, и перекрытие оплачивает сборка. С server GC то же, то
  есть это не паузы GC; где сериализация, проба по-прежнему не показывает.
- **Опережение по пути обхода не получается.** Рабочие потоки оценили 109–119 из 318 проектов, остальные — поток
  сборок сам, и 74–86 % этого времени ни одна evaluation рабочих потоков не шла: очередь пуста. Обход в глубину
  узнаёт следующий проект пути только после evaluation текущего и сразу забирает его себе; рабочим остаются
  соседние ветви. По предыдущему пункту полное опережение на Roslyn.slnx тоже ничего бы не дало.

Что следует для B на Roslyn.slnx: ни один вариант (один уровень с 2–15 потоками, всё замыкание с 1–2 потоками, с
server GC и без) не быстрее references-first больше разброса раундов. Время вне сборок (7,4 с дома, 22,5 с на
офисном компьютере) — это все 318 корневых evaluation, но в одном процессе его можно только переложить на сборки.
Решение по B остаётся за офисным решением: опережение в один уровень дало там −3,7 с, но прогон был без шкалы
шагов; прогон `5ed3f66` покажет, идут ли там evaluation рядом со сборками без такой цены. Server GC подтверждён
третий раз: references-first −6,7 п. п. к client дома и −5,1 п. п. на офисном компьютере.

### Причина сериализации в пробе: `ProjectCollection.LoadProject`, 2026-10-25

Трасса опыта масштабирования (`spikes/BuildOrderProbe/Invoke-EvaluationScaling.ps1`, `RoslynMcpServer.sln`,
Linux, 2 потока) показала поток, который 1,7 с из 1,8 с ждёт `WaitHandle` прямо внутри
`ProjectCollection.LoadProject`. Декомпиляция MSBuild (SDK 10.0.113, пакеты 18.6.3 и 18.7.1): `LoadProject(path)`
берёт блокировку записи коллекции и под ней выполняет `new Project(...)`, то есть всю evaluation. Проба оценивала
проекты именно так, поэтому evaluation в рабочих потоках одной коллекции шли строго по одной. На Roslyn.slnx
объединение интервалов evaluation в `evaluate-ahead` равно сумме последовательных (1,00–1,05) — подпись полной
сериализации.

Host evaluation-ит иначе (`ProjectBuildManager.LoadProjectCore`): `ProjectRootElement.Create` из `XmlReader` и
`new Project(xml, …, collection, settings)`. Коллекцию он блокирует только при регистрации проекта.

- **Выводы шага 0 о B на Roslyn.slnx относятся к пробе, а не к host:** «evaluation в одной `ProjectCollection`
  ждут друг друга», «опережение на всё замыкание без выигрыша» и разбор паузы выше. Порядки без рабочих потоков
  блокировка не затрагивала.
- **Офис** при той же блокировке перекрывался частично (объединение 0,74 от последовательной суммы); причина пока
  не ясна.
- **Проба исправлена:** evaluation теперь как у host, с теми же настройками загрузки. На мини-решении и
  `RoslynMcpServer.sln` результаты identical.
- **В опыте масштабирования** путь host с 2 потоками дал ×1,21 к одному потоку, `LoadProject` — ×0,81.
- **Pending:** опыт масштабирования с трассой и повтор пробы на Roslyn.slnx (домашний компьютер владельца).
