# BuildHost/task-02 — повторные evaluation и упреждающая работа в host: отчёт эксперимента

Дата: **2026-10-26**. Статус: **выполнен, 2026-10-26; приёмка владельца — pending.** Итог: A — go, B — go,
A + B — **go, принимается как сочетание**. Контракт: [task-02](../task-02-buildhost-optimization-spike-hi.md).
Production включение в эксперимент не входило и требует отдельного решения.

## Что сделано

- **Шаг 0** ([отчёт](task-02-step-0.md)): по binlog — evaluation внутри сборок повторяют корневые (офис 100 из
  102, Roslyn.slnx 180 из 250); проба `spikes/BuildOrderProbe` показала выигрыш обеих частей и нашла, что B нужны
  записи решения.
- **Этап 1, A — одна evaluation на проект** ([отчёт](task-02-stage-1-references-first.md)):
  `ROSLYN_BUILDHOST_REFERENCES_FIRST=1`. Host, получив сборку проекта, сам оценивает и собирает ещё не собранные
  ссылки, а их логи отдаёт клиенту в том порядке, в каком их записал бы upstream.
- **Этап 2, B — evaluation наперёд** ([отчёт](task-02-stage-2-evaluate-ahead.md)):
  `ROSLYN_BUILDHOST_EVALUATE_AHEAD=<потоки>`. Рабочие потоки оценивают в прямом порядке записи решения и известные
  ссылки; решение host передаёт клиент свойством `RoslynMcpSolutionPath` (решение владельца).
- **Этап 3, замер** ([отчёт](task-02-stage-3-matrix.md)): `Invoke-BuildHostForkMatrix.ps1` — оригинал, форк без
  оптимизаций, A, B, A + B и A + B с трассой в одном прогоне, порядок сторон сдвигается каждый раунд.

## Корректность

Во всех прогонах этапа 3 (три пары компьютер/решение, по три раунда на вариант) ответ каждого варианта
**identical** оригиналу по правилам task-00, comparator не ослаблялся; диагностики совпадают и по порядку выдачи
(офис — 1 775 элементов). Сценарии сбоев task-00 (cancel, kill, ранняя отмена, отсутствующий dll) пройдены с A, с B
и с A + B на Linux; фикстура с `.slnx` и `.slnf` — identical.

## Пороги, по вариантам

Против форка без оптимизаций, медианы трёх раундов этапа 3:

| порог | A | B | A + B |
|---|---|---|---|
| офис короче не менее чем на 10 % | −10,2 % — **да**, на границе | −16,2 % — **да** | −26,8 % — **да** |
| Roslyn.slnx не медленнее более чем на 2 % (офисный / домашний) | −7,3 % / −6,8 % — **да** | −14,5 % / −14,3 % — **да** | −16,5 % / −18,4 % — **да** |
| пик памяти host не больше +10 % (три пары) | ≤ +5,5 % — **да** | +11,0 % в офисе — **нет**, по решению владельца не стоп-фактор | ≤ +9,1 % — **да** |
| пик памяти клиента не больше +10 % | ≤ +0,9 % — **да** | ≤ +1,2 % — **да** | ≤ +0,6 % — **да** |
| A + B быстрее каждой части | — | — | **да** на всех трёх: 0,732 / 0,835 / 0,816 против лучшей части 0,838 / 0,855 / 0,857 |

- **A — go.** Выигрыш небольшой (−7…−10 %), но без цены по памяти и с меньшим CPU host. Офис — ровно на пороге.
- **B — go с оговоркой о памяти.** Быстрее A на всех решениях; CPU host +7…+10 %, пик host в офисе +11,0 % (на
  этапе 2 +13,4 %). Разброс пика между одинаковыми host на офисном компьютере — несколько процентов (оригинал против
  форка без изменений — +6,5 % на Roslyn.slnx), так что точная величина неуверенна. Почему без A пик выше, не
  проверялось.
- **A + B — go, принимается.** Быстрее каждой части везде; пик памяти ниже, чем у одной B. На Roslyn.slnx на
  офисном компьютере запас к B — 2 п. п. медиан, и два раунда A + B задеты помехой; по лучшим раундам −20 % к fork
  против −14 % у B.
- **Цена трассы** (F10 task-01): +1,1 % в офисе, на Roslyn.slnx не видна; трассой можно мерить A + B без поправки.

## Куда ушло время и что осталось

С A + B корневая evaluation на потоке запросов почти исчезла (Roslyn.slnx — 317 из 318 записей наперёд, ожидание
рабочего — до 0,2 с за загрузку). На потоке запросов остаются, по трассе Roslyn.slnx на офисном компьютере:
design-time build 23,2 с, повторная evaluation при смене TFM 21,4 с, извлечение `ProjectFileInfo` 18,9 с; в офисе —
извлечение 10,1 с, сборка 6,9 с и 3,7 с ожидания пакетного net472-host, которого форк не касается.

Открытые вопросы, не блокирующие итог:
- почему сборки удлиняются рядом с evaluation наперёд (шаг 0: GC не объясняет, кандидат — память и кэши);
- почему у одной B пик памяти host выше, чем у A + B;
- помеха в двух раундах `fork-ab` на Roslyn.slnx на офисном компьютере.

## Следующие узкие шаги

Выбор — решение владельца:
1. **Интеграция A + B в сервер** — отдельное решение о совместимости: форк BuildHost в пакете сервера, передача
   `RoslynMcpSolutionPath` из `SolutionManager`, переменные окружения или настройки, fallback на пакетный host.
2. **Повторная evaluation при смене TFM** — самый крупный кусок, который не трогали (около четверти wall на
   Roslyn.slnx): host переоценивает проект для каждого TFM на потоке запросов; её можно делать наперёд так же, как
   корневую.
3. **Извлечение `ProjectFileInfo`** — следующая по размеру работа host на обоих решениях.
