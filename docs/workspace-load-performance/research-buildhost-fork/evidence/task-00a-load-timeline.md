## Промежутки и evaluation

`gaps.csv` даёт промежуток перед каждой сборкой верхнего уровня.

- 434 сборки = 318 файлов проектов + 116 повторных сборок того же файла с другим
  целевым фреймворком.
- Перед **первой** сборкой каждого файла: **19 907 мс**, медиана 48 мс. Перед
  повторными — 3 047 мс, медиана 17 мс.
- Проба `evaluate` выполнила 554 evaluation 318 C#/VB-проектов в одном
  `ProjectCollection`: 41,6 с на Linux VPS (2 vCPU), на Windows (тот же spike,
  только C#: 282 проекта, 501 evaluation) — 15,9 с.
- Корреляция промежутка перед первой сборкой файла (Windows) и времени evaluation
  этого проекта (проба, Linux) по 318 проектам: **r = 0,67**. Самые длинные
  промежутки — перед `Workspaces`, `Features`, `EditorFeatures` и
  `Razor.Language.UnitTests`, которые и в пробе самые дорогие.

Вывод: около половины загрузки Roslyn.slnx (~20 из 40 с) приходится на работу BuildHost
перед первой сборкой каждого проекта. Её размер следует за стоимостью evaluation.
BuildHost не передаёт свои логгеры в evaluation, поэтому её не видно в binlog.
Остаток промежутка (извлечение `ProjectFileInfo`, ответ по RPC, обработка клиентом
и запрос следующего проекта) без spans BuildHost не разделить. Это задача task-01
форка. Промежутки не называются временем IPC.

## Отличие от прежних no-go

Task-04 и task-07–07.2 параллелили целые загрузки несколькими процессами BuildHost:
- ускорение ×1,5–1,8;
- гонки в общих `obj` и расхождения `OutputFilePath`/diagnostics.

Evaluation ничего не пишет в `obj`. Её можно выполнить заранее и параллельно внутри
одного BuildHost, а design-time сборки оставить последовательными. Это требует
форка: клиент не управляет тем, как BuildHost делает evaluation.

## Кандидат для BuildHost/task-02

Параллельная предварительная evaluation всех проектов решения в общем
`ProjectCollection` BuildHost перед первым запросом. Последовательные загрузки
проектов затем находят готовые evaluation.

- Верхняя граница выигрыша на Roslyn.slnx — около 20 с из 40, если промежутки целиком
  состоят из evaluation. Это верхняя граница, а не прогноз.
- Проверить:
  - потокобезопасность evaluation в одном `ProjectCollection`;
  - ключи кеша загруженных проектов: global properties и TFM;
  - эквивалентность `ProjectFileInfo` по comparator task-00.

## Ограничения

- Проба evaluation — отдельный процесс и другая машина; её время только сопоставляется
  с промежутками и не вычитается из них.
- Одна загрузка Roslyn.slnx. Офисная шкала нужна, чтобы проверить ту же картину на
  решении с WPF и 142 проектами (там промежутков около 18 с из 43 с).
