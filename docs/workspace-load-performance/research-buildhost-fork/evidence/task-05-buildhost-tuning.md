# BuildHost/task-05 — Настройка форка: отчёт

Задача: [task-05](../task-05-buildhost-tuning-med.md). Решения владельца 2026-10-27: пик памяти одной B и помеха
`fork-ab` закрыты без замеров, порог памяти GC9 — +15 %.

Отправная точка: сервер 1.5.17 выпущен 2026-10-27 с A + B + C по умолчанию (4 потока B) — опорная сторона
`fork-abc` этой задачи.

## Этап 0 — стенд, 2026-10-27

Изменения `spikes/BuildHostFork`:
- `Invoke-BuildHostForkMatrix.ps1`:
  - флаг `gc` в таблице вариантов: GC-копия host выбирается по нему, а не по имени `fork-ab-gc*`;
  - варианты `fork-abc-gc` (A + B + C на копии host с server GC и ConserveMemory=9), `fork-ac` и `fork-ac-trace`
    (A + C без evaluation наперёд);
  - параметр `-EvaluateAheadWorkers <int[]>`: по варианту `fork-abc-w<N>` на каждое N в тех же раундах. Стороны
    прогона — отдельный список: `-Variants` сохраняет `ValidateSet` при каждом присваивании;
  - `environment.json` записывает `evaluateAheadWorkers`.
- `MatrixSummary`: без сторон `fork` и `fork-ab` отношения считаются к `fork-abc`.

Проверка: Linux, 2 vCPU, SDK 10.0.113, `RoslynMcpServer.sln`, прогрев + один раунд; стороны original, `fork-abc`,
`fork-abc-gc`, `fork-ac`, `fork-ac-trace`, `fork-abc-w2`.
- Все варианты identical по task-00; опорная сторона в `matrix.md` — `fork-abc`.
- Полные RPC всех пяти вариантов совпадают с original с учётом порядка glob-наборов: 0 отличий.
- `fork-ac-trace/trace-summary.md` построен: часы сверены на 20 операциях, 0 вне своей операции.
- Время на этой машине о порогах не говорит (один раунд, 5 проектов).

На Linux список вариантов передаётся через `pwsh -Command`: при `pwsh -File` запись `a,b` приходит одной строкой и
не проходит `ValidateSet`. В PowerShell на Windows команды задачи работают как есть.

Этап 0 выполнен. Дальше — замеры владельца, этапы 1–3 (команды — в задаче, раздел «Запуск»).

### Этап 1 — потоки B

Медианы раундов 1–3 к `fork-abc` (4 потока) того же прогона:

| пара | `fork-abc`, мс | w2 | w6 | w8 | пик host w2 / w6 / w8 |
|---|---|---|---|---|---|
| дом, Roslyn.slnx | 30 105 | **1,030** | 0,996 | 0,989 | 0,996 / 1,003 / 1,001 |
| офис, Roslyn.slnx | 64 098 | 1,011 | 1,010 | 1,014 | 0,957 / 1,011 / 0,941 |
| офис, офисное решение | 28 805 | 0,995 | 1,001 | 1,020 | 1,021 / 1,064 / 1,072 |

- 2 потока не подходят: дома на 3,0 % медленнее при пороге 2 %.
- 6 и 8 потоков подходят на всех трёх парах (не медленнее 2 %, пик host не выше +7,2 %), но ни один не быстрее
  `fork-abc` на 3 %: лучший результат — w8 дома, −1,1 %.
- **Итог: значение по умолчанию остаётся 4.** Лучшего N, разного для машин, нет, вопрос о формуле от числа
  процессоров не возникает.

### Этап 2 — GC9 на A + B + C

`fork-abc-gc` к `fork-abc`:

| пара | загрузка | пик host | CPU host | пик клиента |
|---|---|---|---|---|
| дом, Roslyn.slnx | 0,934 | 1,130 | 1,157 | 1,004 |

- identical и полные RPC — выполнено.
- Roslyn.slnx на обоих компьютерах не медленнее — выполнено, он быстрее на 6,6 и 10,1 %.
- **Загрузка офисного решения быстрее на 6,6 % при пороге 10 %** — не выполнено. Порог ≥10 % в task-04 и task-05
  относится к офисному решению; −10,1 % у Roslyn.slnx на офисном компьютере его не заменяет.
- **Пик памяти host на офисном решении +17,0 %** — выше ориентира +15 %.
- **Итог: no-go по порогам.** Production-профиль host прежний. Выигрыш 6–10 % на всех трёх парах реален;
  включить GC9 вопреки порогу может только отдельное решение владельца.

### Этап 3 — удлинение сборок рядом с evaluation наперёд

Сумма design-time builds (`msbuild-build`) по 318 путям Roslyn.slnx и 139 путям офисного решения, медиана раундов
1–3:

| пара | `fork-ac-trace`, мс | `fork-abc-trace`, мс | отношение | wall abc / ac |
|---|---|---|---|---|
| дом, Roslyn.slnx | 11 898 | 12 495 | **1,050** (1,0502) | 0,843 |
| офис, Roslyn.slnx | 25 627 | 27 274 | 1,064 | 0,816 |
| офис, офисное решение | 8 612 | 9 959 | 1,156 | 0,794 |

Порог задачи (≤ 1,05, дом) не выполнен формально: превышение на 0,02 %. По правилу задачи в отчёт идут разбивка
по проектам и гипотеза.

Разбивка: для каждой сборки `fork-abc-trace` посчитано, какая часть её времени шла одновременно с evaluation
(`evaluate`, `evaluate-ahead`) на других потоках host.

| пара | сборки, перекрытые evaluation больше чем на половину | их отношение abc / ac | остальные сборки | их отношение |
|---|---|---|---|---|
| дом, Roslyn.slnx | 14 проектов | 1,492 (878 → 1311 мс) | 304 | 0,988 |
| офис, Roslyn.slnx | 15 | 1,429 (2616 → 3739 мс) | 303 | 1,022 |
| офис, офисное решение | 32 | 1,451 (2040 → 2960 мс) | 107 | 1,053 |

- Удлинение сосредоточено в сборках, которые идут одновременно с evaluation наперёд: они дольше в 1,43–1,49 раза.
  Остальные сборки — в пределах ±5 %. Дома перекрытые сборки дают +432 мс, остальные −134 мс.
- Гипотеза: конкуренция за CPU и память с параллельными evaluation. Её подкрепляет рост на офисном компьютере
  (6 ядер без SMT, 4 потока B рядом со сборкой) и на офисном решении, где перекрыта почти четверть сборок. Отличить
  её от общих блокировок MSBuild (кеши `ProjectRootElement`, evaluation) эти трассы не могут.
- Цена уже входит в wall: A + B + C быстрее A + C на 16–21 % на всех парах. Меньше потоков её не снимает:
  w2 на офисных парах ×0,995 и ×1,011.
- **Итог:** удлинение — известная цена B, а не дефект. Новой оптимизации из него не следует (по правилу задачи).
