## Что сделано

Форк ([README](../../../../forks/roslyn-buildhost/README.md)): `ProjectBuildManager_ReferencesFirst.cs`, включается
`ROSLYN_BUILDHOST_REFERENCES_FIRST=1`.

- Запрос `GetProjectFileInfosAsync` проекта P сначала обходит ProjectReference из evaluation P (только существующие
  `.csproj`/`.vbproj`), в глубину: каждую ещё не собранную ссылку загружает через `ProjectCollection` (поздняя
  загрузка клиентом получит тот же `Project`), собирает её ссылки, затем её саму, и хранит экземпляры сборки, её
  DiagnosticLog или исключение. Затем собирается P; вызовы `GetTargetFrameworks`/`GetTargetPath` из его сборки
  попадают в существующие конфигурации.
- Первый запрос клиента к собранной наперёд ссылке получает её результат: записи лога добавляются в лог её
  `ProjectFile`, исключение бросается заново. Извлечение `ProjectFileInfo` — при запросе клиента, с его языком;
  `ProjectInstanceReader` берёт у `Project` только путь.
- Клиент 5.9.0 сам загружает каждую ссылку C#/VB из результата сборки, в том числе `ReferenceOutputAssembly=false`
  (`MSBuildProjectLoader.Worker.ResolveReferencesAsync`), поэтому собранное наперёд он запрашивает.
- Ссылка, которая не оценилась, оставляется загрузке клиента — та сообщит ту же ошибку. Отмена во время сборки
  наперёд возвращает проекту его `TargetFramework` и снимает отметку «собран»; другая ошибка сохраняется как
  результат и оставляет проект в том состоянии, в котором его оставил бы запрос клиента.
- Запросы в этом режиме обслуживаются по одному; клиент 5.9.0 и так шлёт их по одному.

Стенд: ключ `-ReferencesFirst` у `Invoke-BuildHostForkBaseline.ps1` и `Invoke-BuildHostForkScenarios.ps1` ставит
переменную только на стороне форка; оригинал остаётся эталоном ответа. В фикстуру сценариев добавлен первый проект
решения `Consumer` со ссылками на `MultiTfm` и на `Noisy` (повторный импорт — предупреждение evaluation, цель с
`<Warning>` перед `CoreCompile`): клиент собирает `Consumer` раньше, чем загружает их, а форк с A собирает их
наперёд.

### Известное расхождение: предупреждения evaluation ссылок

Устранено [вариантом 1](#вариант-1-логи-как-у-upstream); описание ниже — состояние на commit `dbe9e4b`.

Оригинал на расширенной фикстуре выдаёт:

```text
Failure: Msbuild failed when processing the file '' with message: "<fixture>/Noisy/Noisy.props" cannot be imported again. It was already imported at "<fixture>/Noisy/Noisy.csproj (1,106)". This is most likely a build authoring error. This subsequent import will be ignored.
```

Это предупреждение evaluation `Noisy`. Upstream показывает его только через повторную evaluation `Noisy` внутри
сборки `Consumer`: логгер сборки ловит предупреждения этой evaluation. Корневая evaluation host идёт в
`ProjectCollection` без логгеров, поэтому у самого `Noisy` оно не показывается нигде. A убирает повторную
evaluation, и диагностика исчезает. Предупреждение сборки `Noisy` (`Noisy build warning`) отдаётся одинаково.
Проба шага 0 этого не видела: она сравнивала результаты сборок, а не логи.

Решение владельца (2026-10-25): сначала замер на Roslyn.slnx и в офисе — время A в форке и есть ли такое
расхождение там; затем точное воспроизведение upstream (вариант 1): host ловит предупреждения своих корневых
evaluation и переоценок по TFM, по событиям сборки видит, к каким конфигурациям ссылок она обращается, и при
отдаче результата вставляет предупреждения тем проектам, у которых upstream оценил бы ссылку внутри сборки, в те
же места лога. Comparator не ослабляется.

Для варианта 1 отсюда: предупреждение вставляется один раз, в лог той сборки, которая в порядке клиента первой
обратилась бы к конфигурации ссылки, собранной наперёд; конфигурации, которых A не собирает (net472-host, другие
глобальные свойства), остаются со своей настоящей evaluation и не дублируются. Comparator сравнивает диагностики как
множество строк (`spikes/BuildHostFork/ObservationComparer.cs`, `Diagnostics`), поэтому позиция и кратность им не
проверяются; вариант 1 сохраняет их по решению владельца.

## Вариант 1: логи как у upstream

Реализация — в том же `ProjectBuildManager_ReferencesFirst.cs`; в upstream-файле `ProjectBuildManager.cs` одна
добавленная строка — вызов `AddReferencesFirstLoggers` в конструкторе. Без переменной режима логгеры не
подключаются.

**Опыт перед кодом** (одноразовая программа с той же сессией MSBuild, что у host, и логгером, печатающим контексты
событий; мини-решение: `A` на два TFM и `B`, оба с двойным импортом, `C` и `D` ссылаются на них, `E` — только на
`C`):

- предупреждение evaluation приходит с контекстом evaluation (`EvaluationId` есть, `ProjectContextId` нет) и с
  теми же полями — у корневой evaluation host (логгер на `ProjectCollection`) и у вложенной в сборке;
- каждое обращение сборки к конфигурации — дочерний `ProjectStarted` с id конфигурации, id evaluation за ней и
  контекстом родителя, в том числе повторное, когда цели уже в кеше;
- вложенная evaluation внешней конфигурации `A` (`GetTargetFrameworks`) вызывает evaluation обеих внутренних
  (`GetTargetFrameworksWithPlatformForSingleTargetFramework`), но только при первом запуске цели; позже цель
  отвечает из кеша без вложенных обращений;
- `ProjectCollection.OnlyLogCriticalEvents`, выставленный после создания `BuildParameters`, событий сборки не
  убирает.

**Модель.** В режиме A host подключает регистратор событий к `BuildManager` и к `ProjectCollection` (только
критические события). Он записывает:

- ошибки и предупреждения каждой evaluation по её id;
- для каждой сборки — дерево запросов: запрос к конфигурации (id конфигурации, id evaluation, список целей) с его
  ошибками и предупреждениями и запросами, которые сделали его цели;
- первый запуск каждого списка целей на каждой конфигурации.

При выдаче сборки клиенту, в его порядке, её лог пишется из дерева:

- элементы, которые host добавил сам (нет цели, исключение сборки), остаются на своих местах;
- запрос к конфигурации, до которой не доходила ни одна выданная раньше сборка: перед ним — ошибки и предупреждения
  evaluation за этой конфигурацией;
- запрос целей, которых выданные раньше сборки у этой конфигурации не вызывали: дальше — содержимое их первого
  запуска, где бы он ни был в форке, с тем же правилом для вложенных запросов;
- собственная сборка конфигурации обнуляет набор её вызванных целей: `BuildManager` получает новый
  `ProjectInstance` и сбрасывает закешированные результаты.

Последнее правило найдено на мини-решении: в upstream `GetTargetPath` у `B` исполнился второй раз (с предупреждением
цели) в сборке `D` после собственной сборки `B`.

**Чего модель не размещает.** Сборка получает свой лог без перестановки, а трасса отмечает span `upstream-log` с
`aligned=false`, если:

- в сборке есть ошибка или предупреждение без контекста проекта и вне evaluation;
- вложенная evaluation не дала конфигурации (упала);
- запрос пришёл с неизвестным родителем;
- событие пришло до начала submission.

Предупреждения evaluation берутся у evaluation host, а вложенная evaluation upstream идёт с настройками загрузки
`BuildManager` по умолчанию. Если эти настройки (пропуск отсутствующих или пустых импортов и т. п.) меняют
evaluation ссылки, у A расходятся уже результаты сборки, и это ловит comparator.

**Стенд.**

- Наблюдение пробы получило поле `DiagnosticsInReportOrder` — диагностики в порядке, в котором их сообщил клиент.
- В `summary.md` и `scenarios.md` добавлена строка «diagnostics in report order (not part of the result)»: сколько
  раундов оригинала и форка совпали с эталоном по порядку. В вердикт эквивалентности она не входит; comparator
  по-прежнему сравнивает множество.
- Фикстура сценариев:
  - первый проект решения — `Outer`, который ссылается только на `Consumer`;
  - у `MultiTfm` двойной импорт;
  - у `Noisy` предупреждение в цели после `GetTargetPath`.
- Сценарий kill признаёт потерей соединения и «Failed to deserialize response from build host»: при прогоне без A
  оригинал из пакета, убитый посреди записи ответа, получил оборванную строку JSON. Прежний шаблон это не учитывал,
  и прогон упал на стороне оригинала.
