## Почему до форка

Офис, 1.5.14
([прогон](../epoch-0-stage-measurement/evidence/office-first-search-2026-10-23.md#третий-прогон-сервер-1514-с-кешем-индексов-20182029)):

- открытие MSBuild занимает 43,9 с, binlog покрывает 42,8 с;
- design-time сборки 142 проектов (2882 запуска проектов) дают в сумме лишь 17,8 с,
  записанные evaluation — 7,2 с;
- самая дорогая цель — `_GetProjectReferenceTargetFrameworkProperties`: 142 вызова,
  8,3 с;
- около 18 с внутри binlog — не сборка и не evaluation.

Сводка в `runs.json` — только агрегаты. Где эти 18 с, видно лишь на временной шкале:
между проектами, внутри одного проекта или в параллельных узлах. Для этого форк
не нужен, достаточно сохранить binlog обычной загрузки.

## Что сделать

1. Spike, который открывает решение тем же `MSBuildWorkspace`, что и сервер
   (`spikes/ParallelSearch/SolutionLoader`), с `BinaryLogger` в постоянный файл.
   Записать время открытия по часам клиента.
2. Анализатор binlog. Он строит:
   - интервалы evaluation, сборок проектов (с контекстом и global properties),
     целей и задач;
   - объединение занятых интервалов и промежутки между ними;
   - распределение промежутков: перед первой сборкой, между сборками, после последней;
   - повторы: один путь с разными global properties и одинаковые запросы.
3. Прогнать на Roslyn.slnx (Windows-стенд, публичный) и на офисном решении. Офисный
   binlog содержит внутренние пути и передаётся владельцем вне репозитория. В Git
   идут только агрегаты.
