## Вопрос

Какие значения настроек форка дают лучшую загрузку на обоих стендах при identical-ответе и приемлемой памяти host?
Опорная точка — production-сочетание A + B + C с 4 потоками B (`fork-abc`).

Задача отвечает на перенесённое из приёмок:
- task-02: подбор числа рабочих потоков B; удлинение сборок рядом с evaluation наперёд; пик памяти у одной B; помеха
  в раундах `fork-ab` ([приёмка task-02](evidence/task-02-optimization-spike.md#приёмка-2026-10-27));
- task-04: GC9 (server GC + ConserveMemory=9 только в host) — офисный порог ≥10 % и production-активация pending
  ([приёмка task-04](evidence/task-04-projectfileinfo-extraction.md#приёмка-2026-10-27)).

## Что известно

- A + B + C к A + B: Roslyn.slnx дома ×0,819, офис ×0,901 ([матрицы task-04](evidence/task-04-projectfileinfo-extraction.md#матрица-c-roslynslnx-домашний-компьютер-2026-10-27)).
- GC9 мерили только на A + B: дома загрузка −6,0 %, host +13,6 %, CPU +12,5 %; офис не мерили.
- Число потоков B мерили только в шаге 0 пробой, не в форке: окно из 4 следующих записей давало тот же выигрыш, что
  всё замыкание ([итог B](evidence/task-02-step-0.md#итог-b-после-шага-0-2026-10-25)).
- Удлинение сборок рядом с evaluation наперёд видно на Roslyn.slnx и почти не видно в офисе; GC его не объясняет,
  кандидат — память и кеши. В матрице task-04 сумма design-time builds с C стала ×0,918, но трассы `fork-ab` рядом
  не было.

## Этапы

0. **Стенд.** В `spikes/BuildHostFork/Invoke-BuildHostForkMatrix.ps1`:
   - варианты `fork-ac` и `fork-ac-trace` — A и C без evaluation наперёд, для вопроса об удлинении сборок;
   - вариант `fork-abc-gc` — A + B + C с GC9 в копии host (`bin-fork-gc`), как `fork-ab-gc`;
   - параметр `-EvaluateAheadWorkers <int[]>`: варианты `fork-abc-w<N>` для каждого N в одном прогоне, с той же
     ротацией сторон; `fork-abc` остаётся N = 4;
   - `MatrixSummary` берёт опорной стороной `fork-abc`, если её нет — прежние правила.
   - Проверки стенда: Linux, `RoslynMcpServer.sln`, прогрев + один раунд всех новых вариантов — identical;
     self-check сводки.
1. **Потоки B.** Варианты `fork-abc-w2`, `fork-abc` (4), `fork-abc-w6`, `fork-abc-w8`; прогрев + три раунда:
   - домашний компьютер, Roslyn.slnx;
   - офисный компьютер, Roslyn.slnx и офисное решение.
   Число ядер и логических процессоров каждой машины записывается в отчёт.
2. **GC9 на A + B + C.** `fork-abc`, `fork-abc-gc`; прогрев + три раунда, те же три пары машина × решение. Полные RPC
   снимает стенд.
3. **Удлинение сборок.** `fork-ac-trace` и `fork-abc-trace` в одном прогоне на Roslyn.slnx дома: сумма и медиана
   design-time builds, окно потока запросов, корневые evaluation на воркерах. Можно объединить с этапом 1.
4. **Пик памяти одной B и помеха `fork-ab`.** Новых замеров не требуют, если владелец согласится закрыть их (см.
   «Решения владельца»).

## Пороги (заданы до замеров)

Медианы раундов 1+ к `fork-abc` той же машины и решения.

**Потоки B.** Кандидат N подходит, если на всех трёх парах:
- identical по task-00;
- загрузка не медленнее `fork-abc` более чем на 2 %;
- пик памяти host не выше +10 %.

Значение по умолчанию меняется с 4, только если подходящий N быстрее `fork-abc` не менее чем на 3 % хотя бы на одной
паре. Из нескольких таких — наименьший N в пределах 1 % от лучшего. Если лучший N на офисном компьютере и дома
разный, формула от числа процессоров — решение владельца, а не этой задачи.

**GC9.** go для production, если:
- identical по task-00 и полные RPC без отличий сверх естественного порядка Excludes/Removes и регистра путей на
  Windows (решение владельца 2026-10-27);
- офисная загрузка быстрее не менее чем на 10 %;
- Roslyn.slnx на обоих компьютерах не медленнее более чем на 2 %;
- пик памяти host — ориентир +15 % (дома на A + B было +13,6 %, владелец счёл приемлемым).

**Удлинение сборок.** Вопрос закрыт, если сумма design-time builds `fork-abc-trace` к `fork-ac-trace` ≤ 1,05.
Иначе в отчёт идёт разбивка по проектам и гипотеза причины; новая оптимизация из этого не следует автоматически.
