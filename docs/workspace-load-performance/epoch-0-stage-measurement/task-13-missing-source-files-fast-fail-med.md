## Вопрос

Можно ли убрать ожидание повторных чтений исходных файлов, которых нет на диске,
не меняя ответов сервера? Решение владельца 2026-10-23: завести задачу.
Форк Roslyn не делается; используется только публичный API.

## Основания

Офисный прогон 2026-10-23: сервер 1.5.11, workstation GC, 4 замера, первый поиск
`MainViewModel` — медиана 31,4 с. Сводка исключений task-10 показала причину,
которую task-09 не мог доказать:

- 11–14 проектов включают `_generated\x64\include\version\VersionInfo.cs`
  (и вариант `net472`). Файл создаёт нативная сборка, на машине его нет.
- Каждое чтение даёт 18 `FileNotFoundException` и длится около 1 с.
  Малые проекты (5–45 документов) тратят по ~1 с почти только на ожидание.
  private_project читает файл 5 раз (90 исключений), это около 5 с из его 12,9 с.
- Эти проекты занимают 23,5–25,4 с из 31–33 с поиска. Остальные 130 проектов —
  около 7 с.
- В thread-time trace потоки пула около 75% времени ждут сигнала, заметной нагрузки
  на CPU нет.

Механизм Roslyn 5.9.0 проверен декомпиляцией 2026-10-23. Внутренний
`TextLoader.LoadTextAsync` ловит любой `IOException`, включая `FileNotFoundException`,
и повторяет `LoadTextAndVersionAsync` до 6 раз с `Task.Delay(RetryDelay)` (200 мс).
Затем он возвращает пустой текст с сообщением ошибки (`CreateFailedText`).
`InvalidDataException` он не повторяет и сразу возвращает тот же пустой текст.
По task-09, ошибка чтения не попадает ни в `SyntaxTree.GetDiagnostics`, ни в
`Compilation.GetParseDiagnostics`. Итог для отсутствующего файла — пустой документ,
только через секунду.

Оценка эффекта: первый поиск в офисе около 15 с вместо 31 с. Это оценка, а не измерение.

## Границы

- Затрагиваются только документы, файла которых нет на диске в момент чтения.
  Существующие файлы, временно заблокированные файлы и ошибки кодировки
  по-прежнему проходят через повторы Roslyn: эти повторы полезны при сборке
  и сохранении из IDE.
- Не оборачивать loader всех документов. `FileTextLoader` переопределяет внутренние
  члены `TextLoader` (перечитывание текста, хранение в памяти), которые наследник вне
  Roslyn повторить не может. Обёртка всех документов изменила бы поведение памяти
  на 50 тысячах документов.
- Ответы инструментов, состав проектов и документов, пути и порядок результатов
  не меняются.
- Форк Roslyn, reflection по внутренним (`internal`) членам и изменение повторов
  для BuildHost вне задачи. Защищённые члены публичного `Workspace` — контракт Roslyn
  для наследников; уточнение 2026-10-23, см. «Реализация».

## Реализация

- После загрузки (и после каждого пути, который заново создаёт документы:
  reload, refresh, повторное открытие графа) найти документы C# и дополнительные
  документы, чей `FilePath` не существует. Для них заменить loader через
  `Solution.WithDocumentTextLoader` и аналоги для additional/analyzer config documents,
  если они читаются тем же механизмом.

  **Уточнение при реализации, 2026-10-23.** Замену нельзя делать в опубликованном
  снимке. Инструменты пишут через `ApplySolutionChangesToDiskAsync` с кандидатом
  от опубликованного снимка. Roslyn 5.9.0 `Workspace.ApplyChangedDocument` считает
  документ изменённым по ссылке на источник текста, без сравнения содержимого
  (`TextDocumentState.HasTextChanged`). `MSBuildWorkspace.ApplyDocumentTextChanged`
  записал бы пустой текст на диск, то есть создал бы отсутствующий файл. Поэтому
  loader меняется в самом `MSBuildWorkspace` сразу после открытия, до первой
  публикации:
  - используются защищённые `Workspace.OnDocumentTextLoaderChanged`,
    `OnAdditionalDocumentTextLoaderChanged`, `OnAnalyzerConfigDocumentTextLoaderChanged`;
  - вызов идёт через reflection, потому что у `MSBuildWorkspace` нет доступного
    конструктора для наследника;
  - если члены не найдены, loader не меняется, и лог пишет `installed: false`.
- Новый loader при каждом вызове `LoadTextAndVersionAsync` проверяет существование
  файла:
  - файла нет — бросить `InvalidDataException` с текстом, которым Roslyn описывает
    отсутствующий файл. Roslyn сразу вернёт пустой текст с этим сообщением,
    без повторов: тот же итог, что сейчас после шести попыток;
  - файл появился — делегировать исходному `FileTextLoader` того же пути, кодировки
    и checksum algorithm. Реализовано как новый `FileTextLoader(path, null)`: кодировка
    проекта, которую мог передать MSBuildWorkspace, не публична, поэтому определение
    идёт как у обычного `FileTextLoader`.
- Если файл создан после загрузки, текст документа должен совпасть с диском после
  обычной синхронизации. Сейчас её делает `WorkspaceDocumentDiskSync` по событию
  watcher. Нужно проверить, что событие Created для известного пути классифицируется
  как изменение содержимого.
- Лог: одна строка на загрузку с числом документов без файла и до 10 путей
  (с той же редакцией, что в прочих логах), чтобы офисный отчёт показал эффект.
  Повторяющиеся исключения не логировать.

## Проверки

- Документ без файла:
  - текст пустой, как у Roslyn без замены;
  - поиск и компиляция дают тот же результат, что без замены;
  - время чтения меньше 100 мс, а не около 1 с (сейчас воспроизводится локальным probe task-09).
- Файл появился после загрузки:
  - после синхронизации с диском текст документа совпадает с файлом;
  - ни reload, ни reset для этого не нужны.
- Файл существует, но временно заблокирован: повторы Roslyn сохраняются.
- Документы с существующими файлами сохраняют исходный `FileTextLoader`.
- После production-изменений:
  - весь SourceStructure;
  - Release build решения;
  - полный main CI по [AGENTS.md](../../../AGENTS.md).
- AnalyzerLifecycle прогнать, если изменение затрагивает путь загрузки и публикации,
  которым пользуется lifecycle.
