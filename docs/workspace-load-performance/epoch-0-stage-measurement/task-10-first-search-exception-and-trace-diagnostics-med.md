## Вопрос

Есть ли в офисном первом поиске MainViewModel ошибки чтения документов, которые
Roslyn повторяет шесть раз с паузами 200 мс, и где уходит CPU private_project?
Task-09 воспроизвела механизм локально, но офисный пакет не содержит ни исключений,
ни профиля. Эта задача готовит инструменты следующего офисного прогона; выводы
о причине делаются в task-09 по полученным данным.

Решение владельца 2026-10-23: сервер сам пишет сводку исключений, а скрипт замера
получает необязательный режим `dotnet-trace` только для первого поиска.

## 1. Сводка исключений в сервере

Версия сервера — следующий patch (1.5.11 на этой ветке).

- На время цикла поиска в `SymbolDeclarationResolver` подписаться на
  `AppDomain.CurrentDomain.FirstChanceException` и отписаться в `finally`,
  включая cancellation и failure. Поведение поиска и ответы не меняются.
- Атрибуция: текущий проект хранить в `AsyncLocal`, обработчик читает его на потоке
  исключения. Исключения без проекта (другая работа процесса, потерянный
  ExecutionContext) считать отдельно как unattributed, не приписывать поиску.
- Группировать по типу исключения, проекту и пути. Путь брать из
  `FileNotFoundException.FileName` и аналогов; для прочих IOException — из сообщения,
  обрезанного до ограниченной длины. Для остальных типов — только тип и число.
- Одна структурированная строка `workspace_search_exceptions` на поиск:
  `searchId`, общие числа, ограниченный top групп (count, тип, проект, путь,
  смещение первого появления от начала поиска). Без stack trace и содержимого файлов.
- Цена обработчика: измерить на Smoke и локальном probe с ошибочным документом;
  обработчик не должен блокироваться и не должен бросать.

Скрипт `Measure-WorkspaceLoad.ps1` разбирает новую строку по `searchId`,
редактирует пути тем же способом, что и прочие (`<repo>`, `<user>`, `<machine>`),
добавляет секцию в `summary.md` и полные данные в `runs.json`. Старый сервер даёт
явную надпись об отсутствии сводки.

## 2. Режим trace в скрипте

- Новый параметр, например `-TracerExe <путь к dotnet-trace.exe>` (single-file сборка
  с официальной страницы). Без параметра поведение скрипта прежнее.
- Trace снимается только в **отдельном дополнительном прогоне** после обычных:
  его времена не входят в baseline и сравниваются отдельно, чтобы оценить overhead.
- После ответа `load_workspace` запустить `collect -p <pid>` с CPU sampling и
  событиями исключений рантайма, дождаться начала сессии, вызвать поиск, остановить
  trace штатно. Неудачный старт trace — явная ошибка прогона, не тихий пропуск.
- `.nettrace` остаётся у коллег: в нём сообщения исключений с путями. В протоколе
  описать, что присылать (summary и, по согласию, trace) и как его открыть.

## 3. Один скрипт для офисного прогона

Решение владельца 2026-10-23: на офисной машине обновляется дерево нужной ветки
из Git, дальше всё делает один скрипт, например `scripts/Invoke-FirstSearchDiagnostics.ps1`.

- Вход: путь к решению, имя типа для первого поиска; необязательно
  `-Configuration`/`-Platform`/`-TargetFramework` (как у `Measure-WorkspaceLoad.ps1`),
  число прогонов, `-Note`, отказ от trace.
- Подготовка сервера: `dotnet publish` из этого же дерева, `-c Release -r win-x64`,
  в **отдельную** папку, не используемую Cursor (заблокированные DLL и смешение
  версий EXE/DLL). Записать версию сервера и commit дерева; грязное дерево — явное
  предупреждение в отчёте.
- Подготовка `dotnet-trace`: найти уже установленный или поставить в локальную
  папку инструмента (`dotnet tool install --tool-path`), не глобально. Если NuGet
  недоступен — понятная ошибка с указанием скачать single-file `dotnet-trace.exe`
  и параметром для пути к нему.
- Прогоны: обычный `Measure-WorkspaceLoad.ps1` (warmup + три замера + RAM hit),
  затем отдельный trace-прогон; оба из того же дерева.
- В конце — список того, что прислать, и путь к папке результатов. Скрипт не
  отправляет данные сам и не трогает настройки Cursor.
