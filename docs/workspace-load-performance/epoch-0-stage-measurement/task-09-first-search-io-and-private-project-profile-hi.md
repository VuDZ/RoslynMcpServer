## Уже установлено

Офисный первый поиск 1.5.9 — медиана 34,175 с. private_project с 2985 документами
занимает 11,93–13,03 с. 138 проектов без совпадений — суммарно 19,19–20,51 с.
12–14 вызовов имеют длительность 900–1200 мс; сумма 12,42–14,53 с.
Это вложенная часть общего поиска, её нельзя ещё раз прибавлять к 34 с.

Проверенный Roslyn 5.9.0 ждёт индексирования всех документов проекта; при найденном
имени получает compilation. TextLoader на IOException делает шесть попыток чтения
с пятью паузами по 200 мс. Локальный probe воспроизвёл ~1,03 с для одного
нечитаемого документа и ~3,06 с для трёх последовательных проектов.
Повторный поиск на том же snapshot быстрый. SyntaxTree.GetDiagnostics и
Compilation.GetParseDiagnostics в missing-file probe не показывают ошибку чтения.

Предварительная проверка имени в Roslyn 5.9.0 (`Project.ContainsAsync` через
`ContainsDeclarationAsync`) обходит только обычные `Documents`: source generators
на этом шаге не запускаются, секундные вызовы малых проектов ими не объясняются
(декомпиляция 2026-10-23).

Это механизм основного процесса сервера, не BuildHost. Наличие IOException,
конкретные пути и влияние антивирусов у коллег **не доказаны**.

## Что исследовать следующим прогоном

Инструменты для пунктов 1–3 готовит [task-10](task-10-first-search-exception-and-trace-diagnostics-med.md):
сводка исключений в сервере и необязательный `dotnet-trace` первого поиска.
Кандидат «ограниченный параллельный поиск» проверяется отдельно в
[task-11](task-11-parallel-project-search-spike-hi.md).

1. В том же офисном процессе получить исключения чтения с типом, безопасно
   редактируемым путём и временем либо отдельную проверку доступности Compile
   documents. Не записывать source text, environment или secrets.
2. Для private_project снять CPU stacks и отдельно оценить холодное построение declaration
   indexes, получение compilation/dependencies и повторный поиск.
   Возможный диагностический порядок: заведомо отсутствующее имя → MainViewModel
   → повтор MainViewModel. Такой прогрев меняет эксперимент; его время не выдавать
   за baseline обычного первого поиска.
3. Сравнить ответы, CPU, wall, working set/peak RAM и GC. Сохранить fresh-process
   контроль, тот же SDK/configuration/platform/TFM; trace overhead измерять отдельно.
4. Если найдены отсутствующие/заблокированные файлы, установить их происхождение:
   Compile items, generated/obj, linked paths, временные файлы. Исправлять причину
   либо оформлять отдельный обоснованный эксперимент; не отбрасывать документы молча.

## Потенциальные оптимизации

- Устранение подтверждённых ошибок чтения и несогласованной генерации исходников.
- Ограниченный параллельный поиск по 2–4 проектам с сохранением порядка объединения,
  результатов, cancellation и проверкой пика памяти.
- Повторное использование уже построенных индексов/compilation в живом workspace.
- Фоновый прогрев после load — только с метрикой load + first useful query:
  перенос работы между вызовами сам по себе не является ускорением.
- Более дешёвый отбор кандидатов — только после профиля и проверки эквивалентности
  регистронезависимого поиска, Unicode/escaped identifiers, FQN, linked и generated sources.

## Критерии завершения

Подтвердить или опровергнуть I/O гипотезу конкретными событиями; объяснить основную
стоимость private_project профилем и выделить следующий проверяемый кандидат. Непокрытый остаток
назвать неизвестным. Сумма секундных строк не является обещанием экономии 12–14 с.

Production изменения в этой задаче не считаются уже разрешённым изменением контракта.
Если потребуется код: полный code style, patch bump, focused behavioral tests,
весь SourceStructure, Release solution build и main CI; AnalyzerLifecycle
дополнительно при влиянии на load/prepare/analyzer lifecycle.
