## Что сделать

### 1. Отказ до загрузки

Планировщик возвращает либо план, либо отказ с причиной. При отказе spike
выполняет обычный `LoadSolutionInfoAsync`; wall строки = планирование + обычная
загрузка. Причины и пороги фиксируются **до** первого замера и потом не меняются:

| Причина | Условие |
|---|---|
| `balance-infeasible` | нет разбиения с `max(group) ≤ (1 + ε) · mean`, ε = 0,15 |
| `no-expected-gain` | прогноз параллельной загрузки ≥ 0,9 × оценки обычной |
| `memory-budget` | оценка пика памяти BuildHost при N > 4 GB |
| `planning-budget` | за бюджет планирования не найдено ни одного допустимого плана |

- Прогноз считается по модели task-07.1 с её **неизменёнными** параметрами
  (`h1`, остаток прогрева, коэффициент конкуренции `c`, баланс `b`) и профилем
  стоимости текущего решения. Перекалибровка модели по данным этой задачи до
  решения об отказе запрещена.
- Оценка обычной загрузки — время baseline той же серии (в production это было бы
  время прошлой загрузки). Оценка памяти — по пику baseline той же серии; формула
  записывается в отчёт.
- Каждое решение планировщика пишется в JSON прогона: причина, входы и прогноз.

**Отказ после загрузки** (`plan-violation`, ошибка или timeout группы) — **не**
допустимый исход: строка считается проваленной, даже если spike затем выполнит
обычную загрузку. Откат после загрузки реализуется и измеряется (время
потраченной параллельной фазы плюс обычная загрузка), но в порог как успех не идёт.

Флаг `--force-parallel` обходит отказы `no-expected-gain` и `memory-budget`
(не `balance-infeasible`) для диагностики решения об отказе.

### 2. Быстрый планировщик

- Та же цель и ограничения, что у `cluster` в task-07.1: минимальная стоимость
  ядра при ε = 0,15, замкнутость ядра вниз, правило общего каталога.
- Бюджет поиска — 500 мс; чтение XML и профиля в бюджет не входит, но входит в wall.
  По истечении бюджета берётся лучший найденный допустимый план; если его нет —
  отказ `planning-budget`.
- Способ ускорения — на выбор исполнителя (битовые множества замыканий,
  инкрементальный пересчёт ядра); детерминизм обязателен.
- Проверка: на PowerToys N=4 ядро не хуже, чем у `cluster` task-07.1
  (12 проектов, 10,38 % стоимости), время поиска в пределах бюджета. Иначе отчёт
  показывает обе цифры и причину.

### 3. Из чего состоит прогрев BuildHost

Диагностические прогоны, вне медиан и порога скорости, но с проверкой эквивалентности:

- обычная загрузка с `BinaryLogger` и одна параллельная загрузка с `BinaryLogger`
  на фазу 1 и каждую группу — на PowerToys (N=4) и на Roslyn (N=4);
- время каждого проекта по `ProjectLoadProgress` (`Operation`, `ElapsedTime`)
  во всех прогонах серии — без binlog.

Для одних и тех же проектов сравнить группу и обычную загрузку: evaluation,
SDK resolvers, targets и tasks с наибольшим приростом, отдельно первые три
проекта каждой группы и остальные. Результат — разложение остатка примерно в 5 с
по основным источникам с долями и ответ на вопрос: это стоимость первых проектов
холодного процесса или равномерная надбавка на каждый проект. Средства против
прогрева в этой задаче не реализуются; кандидаты предлагаются со ссылкой на
найденные числа.

### 4. Roslyn

Корпус: `<bench>/clones/roslyn-deep`, commit `013d3a758df6c137497ff37a93f0d4bed103853a`,
решение `Roslyn.slnx`. HEAD проверяется перед серией.

- `global.json` требует SDK 10.0.301 с `rollForward: patch`; глобально его нет.
  SDK ставится **локально** — официальным `dotnet-install.ps1 -Version 10.0.301
  -InstallDir <bench>/dotnet` либо `restore.cmd` репозитория в `<clone>/.dotnet`. Глобальная установка и
  правка `global.json` запрещены. Регистрация MSBuild и BuildHost должны
  использовать именно этот SDK; фактическая регистрация записывается из снимка.
  Если этого добиться нельзя — стоп с причиной, без подмены SDK.
- Restore — штатным `restore.cmd` репозитория (Arcade); команда, exit code и лог —
  в artifacts.
- Global properties — те, которые сервер передаёт для `load_workspace` без
  `configuration`/`platform`/`targetFramework` (`Configuration=Debug`, без Platform);
  источник значений указывается.
- Профиль стоимости — из binlog обычной загрузки этой серии инструментом task-05.1.
- **Предварительная проверка:** одна обычная загрузка. Если она не завершилась
  или длится дольше 20 минут — матрица Roslyn не снимается, отчёт с причиной.
- **Прогноз до замера:** по профилю и неизменённой модели task-07.1 исполнитель
  записывает в отчёт прогноз wall для N=4 и N=8 и решение планировщика **до**
  первого измеренного параллельного прогона; в отчёте сохраняется время записи.
  После замера прогноз сравнивается с медианой. Это первая held-out проверка модели.

### Матрица

Прогрев и n = 3, каждый замер — новый процесс spike.

- Roslyn: `baseline`; `xml` × `cluster` × N ∈ {4, 8}; `xml` × `greedy` × N=4;
  если планировщик отказал — та же комбинация с `--force-parallel`.
- PowerToys: `baseline`; `xml` × `cluster` × N=4.
- Files: `baseline`; `xml` × `cluster` × N=2 — ожидается отказ до загрузки.
- Диагностика прогрева — по одному прогону, раздел 3.

## Результат

`evidence/task-07.2-refusal-fast-planner-roslyn.md`:

- правила и пороги отказа, зафиксированные до замеров, и решение планировщика в
  каждой строке;
- быстрый планировщик: время поиска и ядро против task-07.1;
- таблица медиан как в task-07.1, плюс колонка решения планировщика;
- Roslyn: предварительная загрузка, прогноз до замера, измерение, ошибка прогноза;
  при отказе — `--force-parallel` и было ли решение об отказе верным;
- разложение прогрева BuildHost;
- вердикт go или no-go.

Порог go задан заранее:

1. **Корректность во всех измеренных строках:** у выполненных параллельных
   загрузок ноль unexplained, ноль `plan-violation`, ноль ошибок и timeout групп.
   Строка с отказом до загрузки — обычная загрузка; она тоже сравнивается с
   baseline и обязана совпасть.
2. **Скорость:** на PowerToys `cluster` N=4 с быстрым планировщиком — медиана wall
   не больше 75 % baseline, включая планирование.
3. **Отказ не вредит:** в каждой строке с отказом до загрузки медиана wall не
   больше 105 % baseline.
4. **Память:** пик BuildHost выполненных параллельных загрузок не больше 4 GB;
   прогоны с `--force-parallel` в этот пункт не входят, их пик записывается.

Roslyn в порог скорости не входит: его результат — ускорение либо обоснованный
отказ, проверенный `--force-parallel`. Отказ, который `--force-parallel`
опроверг (параллель на самом деле быстрее 90 % baseline), — находка, которую
отчёт обязан назвать.

Если go — раздел для задачи E1, как в task-07.1, плюс: правила отказа, откуда
production берёт оценку обычной загрузки и памяти, бюджет планирования.
