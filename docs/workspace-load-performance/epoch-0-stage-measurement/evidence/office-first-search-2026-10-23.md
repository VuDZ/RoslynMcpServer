### Профиль 1.5.14 с тёплым кешем (trace-прогон, 15,0 с)

Метод тот же, что для профиля 1.5.13 ниже. CPU за окно trace — 46,7 с. Стеки
вложены и пересекаются:

| стек | CPU | прочее время потоков |
|---|---|---|
| `DeclarationFinder.AddCompilationSourceDeclarations…` (private_project) | ~5,2 с | ~2,6 с |
| из него построение compilation (`RegularCompilationTracker.GetCompilationAsync`) | ~3,5 с | — |
| из него генераторы (`GeneratorDriverInitializationCache.CreateAndRunGenerators`) | ~1,6 с | ~0,3 с |
| сверка контрольных сумм для индексов (`AbstractSyntaxIndex.GetChecksumsAsync`, `TextDocumentState.ComputeChecksumsAsync`) | ~3,9 с | ~2,5 с |
| разбор C# (почти весь — документы private_project для compilation) | ~7,6 с | — |
| чтение файлов (`FileTextLoader`) | ~11,9 с | ~4,9 с |

- Поток финализатора снова около 12 с CPU без управляемых кадров; причина не
  установлена.
- Почему ответ без compilation меняет контракт. `find_symbol_definition` печатает
  `ISymbol.ToDisplayString(MinimallyQualifiedFormat)` — тип возвращаемого значения,
  контейнер, разрешённые типы и имена параметров — и все места символа, включая
  partial-части из сгенерированных файлов. Индекс синтаксиса (`DeclaredSymbolInfo`)
  хранит имя, вид, контейнер, место и число параметров, но не разрешённые типы.
  Части, созданные генераторами, в индексе обычных документов отсутствуют. Ответ
  по индексу без compilation изменил бы текст ответа и для некоторых partial-типов
  список мест. Это изменение контракта, решение за владельцем.

## Профиль первого поиска на 1.5.13 (trace, server GC)

Источник — trace-прогон второго пакета: первый поиск под dotnet-trace шёл 17,0 с против
медианы 16,1 с без trace. Профиль `dotnet-sampled-thread-time` переведён в speedscope.
Время каждого стека посчитано отдельно для псевдокадров `CPU_TIME` и
`UNMANAGED_CODE_TIME` (ожидание или нативный код). Суммы вложены друг в друга
и пересекаются, их нельзя складывать.

- CPU за окно trace (18,4 с) — 54,4 с, в среднем около 3 ядер из 6.
- Самые дорогие стеки по CPU:

  | стек | CPU |
  |---|---|
  | `AbstractSyntaxIndex.GetIndexWorkerAsync` — индексы имён для предварительной проверки `ContainsAsync` | ~18,9 с |
  | `AbstractSyntaxIndex.GetChecksumsAsync` — контрольные суммы документов для ключа индекса | ~17,1 с |
  | `FileTextLoader.LoadTextAndVersionAsync` — чтение и декодирование файлов | ~12,7 с |
  | из него `SerializableBytes.CreateReadableStreamAsync` — копирование файла в память | ~8,6 с |
  | разбор C# (`CSharpSyntaxTree.ParseText`) | ~10,4 с |
  | `DeclarationFinder.AddCompilationSourceDeclarations…` — compilation private_project с совпадением | ~8,4 с |

- Ожидание при открытии файлов (`OSFileStreamStrategy..ctor` под `FileTextLoader`) —
  около 4,3 с потоков. Вероятно, это антивирус на открытии файла; отдельно не проверялось.
- Не объяснено:
  - `GC.RunFinalizers` занимает около 11,7 с CPU потока финализатора без управляемых кадров ниже;
  - медленный путь `RuntimeHelpers.GetHashCode` (~9,8 с) приходится в основном на разбор
    (`SyntaxNodeCache`, `LexerCache`).

  Точность распределения времени по стекам при переводе в speedscope не проверена.
  Эти два пункта нужно подтвердить другим инструментом (PerfView), прежде чем на них
  опираться.
- Persistent storage индексов Roslyn (SQLite) в процессе недоступно: 5 раз не найден
  `SQLitePCLRaw.batteries_v2` (Roslyn 5.9.0 ссылается на сборку версии 2.3.5.0),
  и путь кеша в `AppData` не существует. Поэтому каждый новый процесс заново читает,
  хеширует и разбирает все документы. Индексы прошлого процесса могли бы снять
  разбор и построение индексов; чтение файлов для контрольных сумм, вероятно, осталось бы.
  Это гипотеза, она не проверена.
