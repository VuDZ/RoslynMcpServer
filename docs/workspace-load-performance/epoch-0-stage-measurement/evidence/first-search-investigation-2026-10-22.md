## Проверен фактический Roslyn 5.9.0

Декомпилирован пакетный `Microsoft.CodeAnalysis.Workspaces.dll`, net10.0,
SHA-256 `E405CBE085BB8F1A3FCC7308AF0DC6C5B3BE495196046A1840607B17BABE13A0`.
Копия исследованных методов: `artifacts/search-investigation-20261022/roslyn-methods.txt`.

Наш resolver обходит проекты последовательно. Для текущего C# запроса
ignoreCase=true библиотека сначала проверяет имена объявлений через
TopLevelSyntaxTreeIndex. Project.ContainsAsync ожидает Task.WhenAll для
документов проекта: найденное имя не завершает весь проход досрочно.
Первый вызов поэтому включает ленивое чтение, checksum, разбор и создание
индексов. При найденном имени затем запрашивается compilation и перечисляются
символы. Compilation может включать работу с зависимостями проекта.

Следствия для private_project:

1. 2985 документов требуют первого прохода, а не одного сравнения имени.
2. Найденный MainViewModel включает получение compilation.
3. 12–13 с нельзя объявлять временем исключительно собственных файлов,
   исключительно compilation или исключительно I/O: текущий лог их не разделяет.

Старый FindDeclarationsAsync дополнительно проверял project references и metadata.
Он мог раньше прогреть часть той же работы и отнести её стоимость к другой
проектной строке. Сдвиг private_project с 8,84 до 12,88 с при уменьшении полного поиска
и падении private_project_4 с 5,23 до 1,04 с согласуется с этим механизмом. Конкретное
распределение по рёбрам офисного графа не измерено.

## Подтверждён механизм секундной задержки

TextLoader при IOException делает шесть попыток чтения: после первых пяти
ставит Task.Delay на 200 мс. При исчерпании попыток возвращает пустой текст
с внутренней диагностикой. Все документы одного проекта проверяются параллельно,
но наши проекты — последовательно.

Локальный изолированный probe использует тот же Roslyn 5.9.0 и
FindSourceDeclarationsAsync; контрольный документ содержит MainViewModel.
Синтетический TextLoader всегда выбрасывает IOException:

- Без ошибочного документа: первый поиск **1,38 мс**.
- Один ошибочный документ: **1033,14 мс**, **6** вызовов loader.
- Восемь ошибочных документов одного проекта: **1018,62 мс**, **48** вызовов.
- Три проекта, по одному ошибочному документу: **3061,00 мс**, **18** вызовов.
- Повторный поиск на том же snapshot: **0,02–0,12 мс**.
- Отдельный реальный FileTextLoader на отсутствующий .cs: **1030,26 мс**.
  При этом SyntaxTree.GetDiagnostics и Compilation.GetParseDiagnostics пусты:
  добавление только этих диагностик не обнаруживает проблему.

Assert-проверки кандидатов, числа попыток и отсутствия контрольного файла прошли.
Это доказывает механизм библиотеки; **не доказывает наличие отсутствующих
или заблокированных файлов в офисном решении**. IOException может иметь разные
причины. В текущем офисном пакете нет нужного профиля исключений/путей документов.

Воспроизведение: `artifacts/search-investigation-20261022/Probe.csproj`,
`Program.probe`, `probe-results.json`. Release build отдельного probe через

попадали в основной glob. Этот obj удалён; IntermediateOutputPath probe перенесён
в корневой obj/search-investigation-probe, исключённый SDK glob. После исправления
Release solution build и main CI 1426/0/0 прошли; [checkpoint](commit-2026-10-22.md).

## Что делать дальше

Первый приоритет — получить имена и причины ошибок чтения в том же офисном
процессе: профиль исключений IOException/FileNotFoundException/
DirectoryNotFoundException и CPU stacks либо явная диагностика доступности
документов с отделённым временем проверки. Проверять источник Compile items,
generated/obj и linked paths по фактическим найденным путям. Если гипотеза
подтвердится, исправлять входы или генерацию файлов. Сумма секундных строк
12–14,5 с показывает масштаб кандидата, но не обещает такую же экономию.

Второй приоритет — отдельный диагностический прогон private_project: сначала поиск
заведомо отсутствующего имени (прогрев declaration indexes без compilation
при отрицательном результате), затем MainViewModel и его повтор на том же
snapshot. Последний должен совпасть по ответу. Это изменяет порядок прогрева,
поэтому диагностические времена не подменяют baseline обычного первого поиска.
CPU trace показывает, какая часть остатка приходится на parsing/indexing,
compilation/dependency binding, generators или GC.

После этого можно измерять ограниченный параллельный поиск по 2–4 проектам
с сохранением порядка объединения, cancellation и эквивалентности ответов.
Он способен перекрывать ожидания разных проектов; индексатор уже параллелит
документы, поэтому неограниченный Task.WhenAll на 142 проекта может увеличить
конкуренцию CPU и пик RAM. Ускорение заранее не известно.

Переключение поиска на чувствительность к регистру, отбрасывание документов или
обход только заранее выбранных проектов меняет публичную семантику и не является
проверенной оптимизацией в этом scope. Roslyn уже кеширует повторные запросы,
но это не устраняет стоимость первого запроса свежего процесса.

При самом исследовании основной CI не перезапускался: production/test код
не менялся, проверялся только локальный probe. Позднейший предкоммитный прогон
22 октября записан в checkpoint выше. Офисное содержимое документов
и CPU trace отсутствуют; окончательная причина 12–13 с private_project остаётся открытой.

Сохранённый воспроизводимый исходник: [spikes/FirstSearchProbe](../../../../spikes/FirstSearchProbe/README.md). Он использует тот же механизм; данные первоначального probe и их hashes выше остаются историческим receipt.
