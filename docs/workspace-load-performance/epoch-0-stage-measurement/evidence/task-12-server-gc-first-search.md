## Анализ результатов, 2026-10-23

Медианы DOP 1 по 5 измерительным раундам посчитаны по сырым JSON
в `spikes/ParallelSearch/results/gc-20261023-133122/`.

| запрос | GC | сборки gen0/gen1/gen2 | первый поиск без пауз, мс | загрузка + первый поиск, с | куча GC после поиска, МБ | committed, МБ | working set, МБ |
|---|---|---|---|---|---|---|---|
| match | workstation | 203 / 203 / 6 | 13 035 | 62,3 | 4743 | 4800 | 5442 |
| match | server | 30 / 13 / 6 | 11 067 | 51,0 | 4975 | 5389 | 6194 |
| missing | workstation | 200 / 200 / 6 | 9 719 | 58,4 | 4672 | 4713 | 5320 |
| missing | server | 30 / 12 / 5 | 8 223 | 48,0 | 5117 | 5676 | 6318 |

- Основной выигрыш — меньше сборок. У workstation каждая сборка доходит до gen1:
  при живом наборе около 4,7 ГБ это около 200 продвижений за поиск. У server
  gen0-бюджет 200 МБ против 48 МБ, поэтому сборок 30, из них до gen1 — 12–13.
  Остаток без пауз тоже быстрее на 15%. Это согласуется с тем, что server GC
  выделяет память в нескольких кучах параллельно и сборки идут на нескольких потоках,
  но отдельно не измерялось.
- Для пользователя важна сумма загрузки и первого поиска: 62,3 → 51,0 с
  и 58,4 → 48,0 с, около −18%. Загрузка ускорилась меньше (0,93): тяжёлая часть
  проходит в BuildHost, отдельном процессе со своим GC.
- Память: живая куча после поиска +5…+10%, committed +12…+20%, working set
  +14…+19%. Это память, которую сервер продолжит держать после поиска. Вернёт ли
  DATAS её в простое, матрица не проверяет: процесс завершается сразу после второго
  поиска. Для долгоживущего сервера это остаточный риск. Его проверяет офисный
  контроль после включения и наблюдение за рабочим набором в простое.
- Порядок величин переносим, проценты — нет. Офисная машина на 6 ядрах даст
  server GC меньше параллельных потоков сборки и, при DATAS, возможно меньше куч
  и меньший суммарный gen0-бюджет. Ожидаемое ускорение там меньше; величину покажет
  только офисный замер.
