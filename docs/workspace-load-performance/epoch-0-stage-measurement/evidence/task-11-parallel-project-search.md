## Ограничения загрузки и приёмки

**Загрузка не была безошибочной:** каждый процесс записал `workspaceFailures=44`.
После матрицы отдельная временная утилита вне репозитория вызвала тот же
`SolutionLoader.LoadAsync` из собранного spike и прочитала `MSBuildWorkspace.Diagnostics`.
Она воспроизвела те же 434 проекта, 50 201 документ и 44 Failure:

- 41 — `.shproj` не связан с отдельным языком и не открыт как самостоятельный проект;
- 3 — XAML не находит `AbstractOptionPageControl`: два сообщения для
  `Microsoft.VisualStudio.LanguageServices.CSharp.csproj`, одно для
  `Microsoft.VisualStudio.LanguageServices.VisualBasic.vbproj`;
- дополнительно 43 Warning: 34 о дублирующихся source files и 9 о project
  references без matching metadata reference (`csc`, `vbc`, `VBCSCompiler`,
  по три сообщения).

[Полный диагностический inventory](task-11-parallel-project-search/workspace-diagnostics.json)
сохранён с относительными путями. Детали получены отдельной загрузкой после
замеров; в 48 исходных процессах сохранены только счётчики. Стабильные размеры
workspace и хеши ответов не доказывают полноту загрузки. Численный no-go относится
к этому стенду; результат не объявляется успешной загрузкой полного Roslyn или
готовностью production. Исправление XAML-окружения в этот запуск не входило.

Release build серверного solution, main CI, SourceStructure и малый контроль
`RoslynMcpServer.sln` в этом запуске не выполнялись; AnalyzerLifecycle не запускался.
Это запуск существующего benchmark, а не приёмка изменений C#/tests из другого
агента. Task-11 и эпоха не помечены accepted. Коммит фиксирует сырые измерения,
отчёт, сводки, диагностику и статусы этого прогона; публикация в remote не выполнялась.

## Анализ результатов, 2026-10-23

Анализ выполнен на Linux-машине по копии в `spikes/ParallelSearch/results/20261023-113651/`.
99 из 101 файла inventory совпали побайтно; два отсутствующих — transcript и исходный
diagnostic JSON, которые по отчёту оставлены на стенде.

**Wall gate не пройден из-за пауз GC, а не из-за последовательного цикла по проектам.**
Медианы по 5 измерительным раундам; пауза — из сводки скрипта, доля и остаток
посчитаны по каждому раунду, затем взята медиана:

| запрос | DOP | GC pause, мс | pause / wall | wall − pause, мс | ratio без пауз |
|---|---|---|---|---|---|
| match | 1 | 8323 | 0,40 | 12 350 | 1 |
| match | 2 | 8835 | 0,48 | 9 369 | 0,76 |
| match | 4 | 9237 | 0,55 | 7 581 | 0,61 |
| match | 8 | 9631 | 0,58 | 6 957 | 0,56 |
| missing | 1 | 8041 | 0,46 | 9 699 | 1 |
| missing | 2 | 8364 | 0,54 | 7 261 | 0,75 |
| missing | 4 | 8872 | 0,60 | 5 861 | 0,60 |
| missing | 8 | 9177 | 0,62 | 5 606 | 0,58 |

- Часть поиска вне пауз GC масштабируется: при DOP 4 остаётся 0,60–0,61 от DOP 1.
  Паузы при этом не сокращаются, а растут с 8,0–8,3 до 9,2–9,6 с, и при DOP 8 занимают
  58–62% wall. Поэтому общий ratio упирается в 0,80–0,85.
- За один первый поиск происходит около 200 сборок. Каждая из них не младше gen1
  (`gcCollections` 203/203/6 для match при DOP 1), средняя пауза около 40 мс.
  Working set растёт с 0,8 до 5,4 ГБ: syntax trees и индексы 50 201 документа
  остаются живыми, и каждая сборка продвигает большой объём.
- Spike и сервер используют GC по умолчанию: ни в `ParallelSearch.csproj`, ни в
  `RoslynMcpServer.csproj`/`Directory.Build.props` нет настроек GC. Значит, измерен
  режим, совпадающий с production: workstation concurrent GC, где блокирующие
  gen0/gen1 сборки выполняет один поток.
- Даже при DOP 1 занято 2,9–3,1 ядра: Roslyn уже параллелит работу внутри проекта.
  DOP 8 добавляет 44–63% CPU (match: 59,5 → 97,0 с; missing: 55,5 → 80,0 с) ради −17…−20% wall.
- Критический путь не ограничивает DOP 8. Самый длинный проект,
  `Microsoft.CodeAnalysis.CSharp(net10.0)` с 1168 документами, занимает 2,7 с из
  21,4 с суммы при DOP 1; десять самых длинных — 37% суммы.
- Из 44 Failure 41 относятся к `.shproj`: их файлы входят в workspace через
  `.projitems` ссылающихся проектов. Ещё 3 — XAML VS-проектов. Workspace одинаков
  во всех 48 процессах, поэтому сравнение DOP это не искажает. Абсолютные числа
  относятся к workspace без этих VS-проектов.

Вывод: численный no-go подтверждается для измеренной конфигурации GC.
Ограниченный параллелизм как отдельное изменение production не оправдан.

Гипотеза для следующего шага не входит в task-11 и не разрешена:
режим GC (Server GC с DATAS или увеличенный gen0 budget) может сократить около 8 с
пауз и в последовательном поиске. Пересматривать DOP имеет смысл только после этого.
Проверка дешёвая — та же матрица с `DOTNET_gcServer=1` в окружении, его наследуют
дочерние процессы. Перед таким прогоном spike должен записывать в результат режим GC
(`GCSettings.IsServerGC`, `GCSettings.LatencyMode`), иначе прогоны неразличимы.
Пороги памяти нужно сравнивать с workstation-baseline этого отчёта, а не только с DOP 1
того же режима.
