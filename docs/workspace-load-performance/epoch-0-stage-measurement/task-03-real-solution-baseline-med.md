## Цель

Получить воспроизводимый baseline по стадиям на опубликованной версии с
task-01/task-02 и решить, какие кандидаты E1 подтверждены.

## Входы и границы

[Тема](../README.md), протокол [task-00](task-00-current-version-log-measurement-low.md),
записи `workspace_load_stages` и `workspace_load_designtime`.

Два контроля:

- **SamplePlugin** (`samples/RoslynMcpPlugin/RoslynMcpPlugin.csproj`) — воспроизводимый
  локальный контроль, тот же, что в E0 workspace-state-cache;
- **решение коллег** — протокол task-00, обновлённый под новые записи.

На каждом контроле: один warmup и не менее пяти успешных попыток с новым PID,
отдельно RAM hit и первый семантический запрос. Ошибки, таймауты и повторы
сохраняются в сыром виде. Решения и пути коллег в репозиторий не попадают:
только обезличенные записи лога и сводка.

## Конкретный результат

`evidence/task-03-baseline.md`:

- медиана, минимум и максимум каждой стадии и time-to-first-useful;
- сводка design-time build и `unattributedOpenMs`;
- вердикт по каждому кандидату E1 из [README темы](../README.md#маршрут):
  подтверждён, не подтверждён или не измерим;
- доля времени, которую сняли бы C (повторная загрузка становится RAM hit) и
  B (холодный старт), — вход для решений по этим темам;
- не больше двух предлагаемых задач E1 с метрикой приёмки.

Правило, заданное до замера: кандидат подтверждён, если его стадия выполняется
в процессе сервера и её медиана не меньше 20% медианы time-to-first-useful на
решении коллег. Порог после замера не меняется.

## Проверки

- Сравниваются только попытки одной версии сервера и одних аргументов загрузки.
- Числа task-00 (оценки по меткам) и task-03 (измеренные spans) не смешиваются.
- Отрицательный результат («наш процесс не hotspot») фиксируется как результат,
  а не как повод расширять замеры.

Docs и evidence: link и diff checks. Если для замера правится код — полная
validation по правилам [эпохи](README.md#общие-правила-эпохи).
