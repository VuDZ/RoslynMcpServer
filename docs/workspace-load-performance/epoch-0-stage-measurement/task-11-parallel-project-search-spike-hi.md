## Вопрос

Сокращает ли обход 2–8 проектов одновременно время первого поиска по имени
без изменения ответа и с приемлемым пиком памяти? Решение владельца 2026-10-23:
сначала отдельный spike, production не меняется до go/no-go.

## Основания

Офисный первый поиск 1.5.9 — медиана 34,175 с; 138 проектов без совпадений
занимают вместе около 20 с. CPU сервера в среднем 1,2 ядра из шести
([task-09](task-09-first-search-io-and-private-project-profile-hi.md)). `SymbolDeclarationResolver`
обходит `solution.ProjectIds` последовательно. Перегрузка Roslyn 5.9.0
`FindSourceDeclarationsAsync(Solution, …)` тоже последовательная
(`DeclarationFinder.FindSourceDeclarationsWithNormalQueryInCurrentProcessAsync`
перебирает `solution.Projects` в `foreach`; проверено декомпиляцией 2026-10-23),
поэтому готового параллелизма нет. Внутри проекта Roslyn уже параллелит документы.

## Границы

- Только standalone `spikes/ParallelSearch` и evidence. Production, Version,
  CHANGELOG и параметры MCP не менять.
- Тот же Roslyn 5.9.0, та же регистрация MSBuild и загрузка через MSBuildWorkspace,
  что у сервера; тот же вызов `FindSourceDeclarationsAsync(project, name, ignoreCase: true, filter)`.
- Фоновый прогрев, кеши индексов между процессами и сужение набора проектов — вне задачи.
- Перед C# правками прочитать полный [code style](../../code-style.md) и [AGENTS.md](../../../AGENTS.md).

## Реализация spike

- Режимы: последовательный (DOP 1, эталон) и ограниченный параллельный DOP 2, 4, 8.
- Результаты собирать в массив по индексу проекта и склеивать в исходном порядке
  `solution.ProjectIds`: итоговый список символов должен совпадать с DOP 1.
- Первая ошибка отменяет остальные проекты и пробрасывается исходным исключением,
  не `AggregateException`; cancellation снаружи останавливает все проекты.
- Проектные тайминги, как в `workspace_search_project`: путь, документы, elapsed,
  кандидаты, outcome; плюс время ожидания слота.

## Стенд и порядок измерений

- Основной стенд: полный Roslyn.slnx, commit 013d3a758df6c137497ff37a93f0d4bed103853a,
  на Linux с SDK 10.0.301 рядом в `~/.dotnet` (требование его `global.json`),
  Configuration=Debug. Контроль малого размера — `RoslynMcpServer.sln`.
- Запросы: имя с одним-двумя объявлениями (требует compilation проекта)
  и заведомо отсутствующее имя (только индексы).
- Новый процесс на каждый прогон: warmup + n=5 на каждый DOP, порядок DOP чередовать.
  Load не входит в измерение поиска, но записывается.
- Измерять wall первого поиска, CPU процесса, пик working set, число GC и паузы,
  сумму проектных времён. Второй поиск в том же процессе — отдельной строкой.

## Эквивалентность и решение

- Для каждого прогона сохранить упорядоченный список (индекс проекта, FQN, kind,
  locations) и его SHA-256; все DOP обязаны совпасть с DOP 1. Несовпадение — no-go
  для этого DOP независимо от скорости.
- Проверки: cancellation посреди поиска, исключение одного проекта, пустое решение,
  проект без документов.
- Пороги заданы до измерений и не подгоняются: **go**, если медиана wall первого
  поиска при DOP 2 или 4 ≤ 0,70 от DOP 1 на обоих запросах Roslyn, пик working set
  ≤ 1,25 от DOP 1 и все ответы совпали. Иначе no-go или inconclusive с причиной.
- Локальный стенд не воспроизводит офисные ошибки чтения (task-09/task-10) и антивирус;
  офисный прогон после интеграции — отдельный внешний контроль.
