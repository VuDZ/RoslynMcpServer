## Цель

Продолжение task-07. Устранить два известных источника расхождений с обычной
загрузкой, уменьшить общее ядро кластерным разбиением корней и выяснить, почему
группы при параллельной работе идут в 1,5–1,66 раза медленнее профиля. Итог —
go или no-go по прежнему порогу. Вердикт и evidence task-07 не переписываются.

## Почему продолжение

[Task-07](evidence/task-07-core-first-parallel-spike.md): XML N=4 — 22,453 с против
41,350 с (1,84×), повторов проектов нет, generated documents не потеряны. No-go
только по эквивалентности. Механизмы найдены в
[разборе](evidence/task-07-core-first-parallel-spike/graph-and-load-mode.md):

1. **`OutputFilePath` у 15 тестовых проектов.** Их `OutputPath` строится от
   `$(SolutionDir)`. Декомпиляция 5.9.0: `LoadSolutionInfoAsync` вызывает
   `SetSolutionProperties`, который записывает в публичный `Properties` ровно одно
   свойство — `SolutionDir` = каталог solution плюс разделитель, если каталог
   существует. `LoadProjectInfoAsync` этого не делает.
2. **94 diagnostics `Cannot open project ... .vcxproj`** есть только в baseline:
   обычная загрузка запрашивает native-проекты solution, группы — нет.
3. **Snapshot-граф** содержит compilation references и не видит ссылок
   `ReferenceOutputAssembly=false`, которые Roslyn загружает. Отсюда все
   `plan-violation` snapshot-плана.

Неоптимальное в самом плане:

- Жадная раскладка корней по стоимости разводит по группам корни с общими
  зависимостями. В N=4 тесты cmdpal попали в разные группы, и расширения
  `Microsoft.CmdPal.Ext.*` оказались в ядре: 35 проектов, 21 % стоимости.
- Фаза 1 идёт последовательно: 7,6 с из 22,5 с.
- Группы N=4 по профилю стоят 6,6–8,6 с, измерено 12,4–14,3 с; занято в среднем
  3,6 логического ядра из 16. Причина не установлена.

## Что сделать

### Шаг 0 — эквивалентность

1. Загрузчикам групп задать `Properties["SolutionDir"]` тем же значением, которое
   `SetSolutionProperties` вычисляет для исходного solution. Проверить, какое
   значение получает фаза 1 при загрузке `.slnf`: каталог исходного solution или
   каталог `.slnf`. Оба значения записываются в отчёт и должны совпасть с baseline.
2. Native и другие незагружаемые проекты solution включить в `.slnf` фазы 1, чтобы
   они были запрошены ровно один раз в том же режиме, что в baseline. Проверить,
   что группы не дают на них лишних diagnostics.
3. Если после 1–2 остаются расхождения diagnostics, найти механизм (режим
   requested/discovered, `SkipUnrecognizedProjects`, `LoadMetadataForReferencedProjects`)
   и устранить его только допустимыми входами загрузки.

Проверка шага 0: Files N=2 и PowerToys XML N=4, по одной загрузке; сравнение с
двумя свежими baseline. Результат — identical либо только объяснённый регистр
путей Windows, как в task-04. Если это недостижимо, матрица не снимается: отчёт
с оставшимися расхождениями и их механизмом, вердикт no-go.

### Источник графа

Основной — `xml` (буквальные `ProjectReference`, включая `ReferenceOutputAssembly=false`).
Дополнительно `snapshot-load` — compilation references baseline-снимка плюс XML-рёбра
`ReferenceOutputAssembly=false`. Он проверяет, достаточно ли этих рёбер графу
прошлой загрузки; в production такой граф дали бы host (C) или снимок (B).

### Кластерное разбиение

Новый режим `--partition cluster`; жадный режим task-07 остаётся как `greedy`.

- Цель: минимальная стоимость ядра при ограничении на баланс — стоимость самой
  тяжёлой группы не больше `(1 + ε)` от средней (ε задаётся аргументом, по
  умолчанию 0,15).
- Подход по выбору исполнителя, например агломеративная кластеризация корней по
  стоимости общего замыкания с проверкой баланса. Алгоритм, ε и причина выбора — в отчёт.
- Правило общего каталога проекта и проверка, что ядро замкнуто вниз, — как в task-07.
- Для каждого N отчёт сравнивает `greedy` и `cluster`: число проектов и долю
  стоимости ядра, стоимость групп.

### Рекурсивное ядро

Флаг `--core-depth 2`: та же схема применяется к ядру. Сначала одним BuildHost
грузится ядро ядра, затем группы ядра параллельно поверх его карты, затем основные
группы поверх карты всего ядра. Снимается только для лучшей комбинации N ≤ 4 и
только если фаза 1 в ней занимает больше 25 % wall. Иначе отчёт фиксирует, что
шаг не нужен.

### Причина замедления групп

Режим `--phase2 isolated`: тот же план, что у лучшей комбинации N=4, но группы
фазы 2 идут по одной, каждая в своём BuildHost. По каждой группе сравниваются:

- изолированное время и стоимость по профилю — цена холодного процесса;
- параллельное время и изолированное — цена конкуренции.

Дополнительно для параллельного и изолированного прогона — CPU каждого BuildHost
и доля времени без CPU (ожидание). Вывод о причине — только по этим данным;
непроверенная гипотеза (антивирус, кэши imports) так и называется.

### Матрица

Прогрев и n = 3, каждый замер — новый процесс spike.

- PowerToys: `baseline`; `xml` × `greedy`/`cluster` × N ∈ {2, 4, 8};
  `snapshot-load` × `cluster` × N=4; `--core-depth 2` по условию выше;
  `--phase2 isolated` для лучшей комбинации N=4.
- Files: `baseline`; `xml` × `cluster` × N ∈ {2, 4}.

Метрики task-07 сохраняются; добавляются CPU каждого BuildHost и время каждой
подфазы рекурсивного ядра.

### Модель

Модель task-07 пересчитывается по измеренным параметрам: холодный BuildHost,
доля ядра, коэффициент конкуренции из изолированного прогона. Прогноз для
загрузки 120 с и 300 с при доле ядра 5 %, 22 % и 50 % — с той же оговоркой,
что это не измерение.

## Результат

`evidence/task-07.1-core-first-equivalence-and-partition.md`:

- шаг 0: какие расхождения устранены, каким входом загрузки и чем это доказано;
- таблица медиан как в task-07 плюс колонка разбиения;
- сравнение `greedy` и `cluster`;
- изолированный и параллельный прогоны групп и вывод о причине замедления;
- рекурсивное ядро или причина, почему не снималось;
- обновлённая модель и прогноз;
- вердикт go или no-go.

Порог go — прежний, task-07:

1. ни одного unexplained расхождения и ни одного `plan-violation` во всех
   измеренных прогонах обоих решений;
2. на PowerToys есть комбинация с N ≤ 4, у которой медиана wall не больше 75 %
   baseline;
3. пиковая память BuildHost не больше 4 GB.

Прогоны `--phase2 isolated` диагностические и в порог скорости не входят, но
обязаны проходить эквивалентность. На Files вердикт не выносится; условие
автоматического отказа от параллели уточняется по новым данным.

Если go — раздел для задачи E1, как в task-07, плюс: какие входы загрузки
(`SolutionDir`, состав запросов фазы 1) обязан воспроизводить production и откуда
production берёт граф загрузки с рёбрами `ReferenceOutputAssembly=false`.
