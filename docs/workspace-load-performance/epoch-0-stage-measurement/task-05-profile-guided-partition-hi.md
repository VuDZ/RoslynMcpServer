## Цель

Выяснить, достигает ли параллельная загрузка порога task-04 (ускорение не меньше 2×
при N ≤ 4 без unexplained расхождений), если группы строить не по порядку
проектов, а по измеренной стоимости проектов и графу ссылок, не допуская
повторной загрузки проектов с XAML/markup в разных группах.

Работа идёт в два шага с ранним выходом: сначала офлайн-модель и симуляция,
реальные загрузки — только если симуляция предсказывает проход порога.
Production-код сервера не меняется.

## Почему это проверяется

[Task-04](evidence/task-04-parallel-loader-spike.md): round-robin N=4 — 1,51×,
N=8 — 1,69×; cluster — 1,03×, потому что у PowerToys один связный компонент
на 241 из 248 проектов. Время групп round-robin N=4 — 27,3 / 27,4 / 19,3 / 21,4 с
при 117 / 121 / 92 / 93 загруженных проектах. Идеальное выравнивание той же
суммы даёт около 1,75×: одного баланса мало.

Основная потеря — повторная загрузка. Группа загружает свои проекты и их
транзитивные ссылки (`LoadSolutionInfoAsync` не берёт metadata вместо
ссылок на проекты вне фильтра): 423 загрузки вместо 248 при N=4. CPU растёт
с ~58 с (baseline, 1,40 busy cores) до ~199 с (N=8, 8,07 busy cores).
Повторы же вызвали гонку: у FancyZonesEditor (N=4) и ColorPickerUI (N=8)
пропали generated WPF/WinUI documents, MSBuild сообщил о занятых общих
`obj/x64/Debug/input.json` / `output.json`.

Гипотеза: разбивка, которая держит модуль вместе с его тестами и повторяет только
общее ядро без markup, сокращает повторы и убирает гонку. Профиль строится из
binlog, который сервер и так пишет при каждой загрузке; устаревший профиль
ухудшает только скорость, не результат.

## Шаг 1 — профиль, модель, симуляция

### Профиль

Новый режим spike `profile --solution PATH --output PATH`: одна обычная загрузка
(`baseline-binlog`), binlog сохраняется рядом с `--output`, затем replay через
`BinaryLogReplayEventSource` (тот же класс использует provenance replay сервера).
Если формат binlog не читается установленным reader, это результат с причиной.

По каждому проекту решения (ключ — `FilePath` и `Name`, как в task-04):

- время evaluation (`ProjectEvaluationStarted`/`Finished`);
- собственное время design-time build верхнего уровня без вложенных вызовов
  `MSBuild` task на другие проекты (`GetTargetPath`, `GetTargetFrameworks` и
  подобные учитываются у вызывающего, но вычитаются из цели вызова);
- порядок проекта внутри BuildHost: первые проекты платят прогрев кэша импортов,
  это не стоимость самого проекта;
- признак markup: выполнены цели `MarkupCompilePass1`, `MarkupCompilePass2`,
  `GenerateTemporaryTargetAssembly`, `XamlPreCompile` или task `CompileXaml`,
  либо design-time build запускал `XamlCompiler.exe`. Список целей и task
  проверяется по binlog PowerToys и Files и записывается в отчёт; проекты,
  у которых в task-04 пропали documents, обязаны попасть в этот набор.

Граф — `ProjectReferences` загруженного решения (ссылки на C++ проекты не входят).
Итог — `profile.json` без путей машины и профиля пользователя.

### Модель

Время группы `g` моделируется как

`t(g, N) = h + c(N) · Σ w(p)` по проектам `p` в замыкании ссылок запрошенных проектов группы,

где `w(p)` — стоимость проекта из профиля, `h` — фиксированная цена BuildHost
(старт и прогрев), `c(N)` — коэффициент конкуренции за CPU. Другая форма модели
допустима, если она объяснена и проходит ту же проверку.

### Калибровка

- Состав каждой группы task-04 восстанавливается без новых загрузок: round-robin
  и cluster детерминированы порядком проектов в `.slnx`, замыкание — по графу из снимка.
- `h` и `c(N)` подгоняются на прогонах **round-robin** N ∈ {2, 4, 8}; проверка —
  на **cluster** N ∈ {2, 4, 8} и обратно (две раздельные подгонки). Подгонка и
  проверка на одних и тех же прогонах не считаются проверкой.
- Порог годности модели: медиана абсолютной ошибки времени группы ≤ 15 %,
  ошибка wall (максимум групп) ≤ 10 % в каждой проверочной комбинации.
- Если снимков task-04 нет или профиль снят в другом окружении, калибровочные
  round-robin и cluster N ∈ {2, 4, 8} перемеряются spike task-04 (прогрев и n = 3).

Модель, не прошедшая порог, — результат: шаг 1 заканчивается отчётом
«модель непригодна» с ошибками по комбинациям, шаг 2 не выполняется.

### Разбивка

Новый режим spike `plan --profile PATH --workers N --output PATH` строит группы
и пишет `plan-N.json` (запрошенные проекты по группам и прогноз). Алгоритм:

- корни — проекты, на которые нет ссылок внутри решения (приложения, тесты);
- корни раскладываются по убыванию стоимости замыкания, каждый — в группу,
  где прирост `t(g, N)` минимален; уже загруженные в группе зависимости бесплатны;
- **жёсткое ограничение:** проект с признаком markup входит в замыкание ровно
  одной группы. Корни, чьи замыкания делят markup-проект, идут в одну группу;
- некорневые проекты, не попавшие ни в одно замыкание, добавляются в группу
  с наименьшим `t`.

Другой алгоритм допустим, если ограничение markup то же и он объяснён в отчёте.
Для сравнения симулируется тот же `t` для round-robin и cluster.

### Решение по шагу 1

На PowerToys для N ∈ {2, 4, 8} в отчёте — прогноз wall, ускорение к baseline,
число повторных загрузок, размер общего ядра (проекты в замыкании больше одной
группы) и каждый повтор markup (должно быть 0).

Шаг 2 выполняется, только если модель прошла калибровку и прогноз хотя бы
для одного N ≤ 4 — не больше 50 % медианы baseline с запасом 10 % (прогноз
≤ 45 %). Иначе — no-go с основанием; шаг 2 не начинается.

## Шаг 2 — реальные загрузки по плану (условно)

Новая стратегия `parallel --strategy plan --plan PATH`: группы берутся из
`plan-N.json`, остальное — как в task-04 (временные `.slnf`, отдельный загрузчик
на группу, слияние, `AdhocWorkspace`, монитор процессов).

- PowerToys: `baseline` и `parallel --strategy plan` для каждого N, прошедшего
  отбор шага 1, плюс N = 8; на Files — `baseline` и `plan` N ∈ {2, 4}.
- Прогрев и n = 3, каждый замер — новый процесс; baseline перемеряется в той же
  сессии, медиана task-04 не переиспользуется.
- Метрики и эквивалентность — как в task-04, тем же компаратором; два baseline
  между собой сравниваются заново.
- В таблице дополнительно: прогноз модели против измерения по каждой группе.

Порог go — как в task-04: на PowerToys есть N ≤ 4 с медианой wall ≤ 50 %
нового baseline, без unexplained расхождений, пиковая память BuildHost ≤ 4 GB.
Любой пропавший generated document — unexplained, даже если markup-повторов в
плане нет: значит, модель риска неполна, это записывается как причина.

## Результат

`evidence/task-05-profile-guided-partition.md`:

- профиль: распределение стоимости проектов, доля прогрева, набор markup и
  основание для списка целей; доля общего ядра в суммарной стоимости;
- калибровка: параметры, ошибки по проверочным комбинациям, вердикт годности;
- симуляция: прогноз для plan, round-robin и cluster при N ∈ {2, 4, 8};
- если выполнялся шаг 2 — таблица медиан как в task-04, прогноз против измерения,
  эквивалентность по комбинациям;
- вердикт go или no-go и что помешало.

Тяжёлые артефакты (binlog, снимки `*.json.gz`, TRX) в `docs` не кладутся:
только `<repo>/artifacts/parallel-load/task-05-evidence/`. В `docs` — отчёт,
`profile.json`, планы, сводка сравнения и хэши исходников.

Если go — раздел для будущей задачи E1, без её реализации: всё из раздела
«Если go» task-04, а также где хранится профиль, чем он ключуется, что делает
первая загрузка без профиля (обычная последовательная), как профиль обновляется
после загрузки и почему устаревший профиль не меняет результат.
