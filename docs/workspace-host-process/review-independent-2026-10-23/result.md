## Summary

- Handoff при смене собственного проекта `mcp1` сформулирован отдельно от перехода proxy: `mcp2`/`mcp3` сохраняют descriptor проекта1, старый host прекращает admission и согласует текущие вызовы, один преемник получает владение до своей ordinary-загрузки. Перенос прогретого Roslyn не обещается.
- Потерянный release, crash в середине handoff, отказ преемника, смерть кандидата до readiness и отсутствие пригодного кандидата включены в исследование. Граница отказа загрузки проекта2 и отсутствие обещанного автоматического rollback явно вынесены в task-01.
- Предотвращение лавины загрузок сформулировано через владение до тяжёлой инициализации, одну разделяемую попытку, общий отказ, cancellation isolation, поколения, bounded backoff и запрет автоматического replay. Task-04 требует наблюдаемые счётчики и реальные процессы; один конечный PID не считается доказательством.
- TDD требует поведенческого red, отличает его от ошибки сборки/среды и сохраняет команды/результаты. Fake/unit не заменяют multi-process, ACL, Roslyn и измерения. Task-02 переносит обязательные переключения/recovery на настоящий workspace и включает analyzer lifecycle validation.
- Текущие ограничения DI, destructive load, SDK stdio lifetime, analyzer CLR lifetime и publish не выданы за уже решённые. Для draft исследования это корректно выделенные открытые задачи, а не самостоятельные дефекты плана.

## Highest risks

Это оставшиеся риски исследования, уже назначенные задачам, а не дополнительные findings:

1. **Совмещённый host и stdio lifetime.** Штатный SDK single-session hosted service останавливает application при завершении сессии; клиентский stdio transport управляет дочерним процессом. Нужно доказать выбранную политику EOF/idle/handoff и предел гарантий при kill harness. Shadow bootstrap без блокировки source publish также пока не доказан: task-04 → task-01 → task-02.
2. **Demotion и analyzer identity.** Освобождение workspace не выгружает CLR assemblies. Бывший host может оставаться тяжёлым и не быть пригодным для нового analyzer поколения; это влияет на реальную экономию и eligibility. План требует инвентаризацию, design choice и измерения, не обещает полную выгрузку: task-00/task-01/task-02.
3. **Отказ на границах handoff.** Успешный release проекта1 не гарантирует успешного load проекта2 или преемника. До реализации нужны конкретные state transitions, deadlines и наблюдаемый результат каждой стадии; тесты должны следовать принятому design: task-04/task-01/task-02.
4. **Реальное владение и отсутствие replay.** Lock/поколение должны охватывать интервал до MSBuild open, смерть кандидата, поздние ответы и повторные ошибки. Fake load либо один PID в конце этого не доказывают: реальные multi-process барьеры/счётчики task-04 и Roslyn-интеграция task-02 остаются обязательными.

## Questions / uncertainties

- Точный descriptor/ключ, host eligibility, механизм исключительного владения и способ выпуска нового поколения ещё выбираются в task-01.
- Какой результат получает host-клиент при уже переданном проекте1 и отказе load проекта2; что происходит при отсутствии преемника и исчерпании recovery budget — открытые design choices с обязательными критериями проверки.
- Какая политика сохраняет idle host при штатном закрытии stdio и какие гарантии достижимы с конкретным harness, который убивает процесс, пока не установлено.
- Цена демотированного процесса, совместимость разных analyzer identities, last-waiter cancellation, session defaults и общие reset/stop требуют принятых решений, а не неявных defaults.
- D/E0/task-01 в этом checkout имеет статус planned. Нужные `workspace_load_stages` ещё не являются текущим API; зависимость task-02 должна быть реально удовлетворена до его принятия.

Эти вопросы уже перечислены или назначены планом. Отсутствие ответа на стадии draft не повышено до дефекта готового production контракта.

## Suggested spikes

Дополнительный независимый spike сверх предусмотренных планом не требуется по результатам этого ревью. Для принятия существенных решений необходимы уже запланированные:

- task-03: фактический SDK seam фасада, изоляция двух сессий, request id/progress/cancellation и subscription behavior обеих версий.
- task-04: совмещение ролей, EOF против forced kill, shadow bootstrap/publish, управляемый handoff с потерей release/отказом преемника, single-owner recovery и crash budget в реальных процессах.
- task-02: те же критические переходы с настоящим Roslyn, наблюдение MSBuild open до/после promotion, watcher/write/analyzer correctness, memory/latency по всем процессам.

Реальная platform/security проверка остаётся экспериментом; непроверенная ОС не получает pass.

## Overall assessment

- **Обоснованно:** роли MCP вместо обязательного отдельного daemon; стабильный фасад вместо прозрачного байтового relay; descriptor/generation вместо чужого mutable current workspace; один владелец и одна попытка; отказ от heap migration и replay.
- **Требует изменения:** доказанных обязательных изменений текста этого draft не выявлено.
- **Требует проверки:** все существенные runtime свойства, перечисленные выше; наличия критериев в плане недостаточно для implementation acceptance.
- **Требует human decision:** выбор владельца по U-C-01…U-C-06 и принятие design после независимого review, как уже требует task-01. Если spike не выполнит согласованный scope, изменение scope должно быть явным.
