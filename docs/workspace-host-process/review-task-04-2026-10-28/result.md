### Главное

**Вердикт: требуются исправления.** Три замечания `major` относятся к полноте обязательных проверок; одно `minor` — к устаревшей строке статуса. Подтверждённого дефекта рабочего механизма при этом ревью не найдено; принимать всю заявленную матрицу пока рано.

Финальные Windows/Linux JSON подтверждают приведённые счётчики: по 32 записи, 20 cold и 20 recovery rounds на ОС; 76 owner/initialization, 72 load-start, максимум один load на поколение, четыре ожидаемых load-failure и ноль fatal. Оставшиеся пробелы — переключение инициатора при живых клиентах A, управляемая гонка подключения с выходом и доказательство фактической отмены всех backend load waiter.

База: `07224d1a8e49627aded77fb401d4c7059a9f3ef9`, незакоммиченный diff task-04, production 1.5.18. Дата: 2026-10-28. Рецензент: отдельная сессия Codex `/root/task04_research_review`; точный ID модели недоступен. Другие review-каталоги до формирования findings не читались.

Решения владельца от 2026-10-28 учтены: выделенный host; роли/handoff/promotion/demotion и idle workspace unload отложены; обычный proxy без workspace; короткий grace без цели переживать клиентов; Windows breakaway не используется. Это ревью не выбирает production design и не принимает эпоху. Нулевой вариант остаётся контролем; RAM-выигрыш этим spike не измеряется.

### Проверка решающих claims в исходнике

1. **OS lease предшествует initialization — подтверждено.** `DedicatedHost.cs:13` получает `host.lock`, при отказе выходит, и только затем создаёт state и пишет owner/initialization. `HostDiscovery.cs:40–74` держит launch lock через подготовку и запуск ребёнка; смерть launcher до lease и проигравший ребёнок отдельно представлены в raw startup. Counts пересчитаны независимо.
2. **Одна общая попытка load на поколение, включая отказ — подтверждено.** `FakeWorkspace.cs:41–75`: `_load ??= Initialize()` под gate, cached Task не сбрасывается, индивидуальный token передан в `WaitAsync`, общий deadline связан с lifetime. Сам выбранный результат политики all-waiters следует из кода; её процессное доказательство неполно по F-03.
3. **Привязка меняется после успешного B; текущий A-вызов сохраняет соединение — подтверждено.** `RoutingSession.cs:19–35`, `:85`, `:179–185`: commit после результата load, active calls удерживают retired connection. Собственный process probe убил B после `load-start` во время switch: клиент получил `IsError`, следующий count вернул прежний A/generation и counter 2. F-01 относится к другому обязательному сценарию.
4. **Прерванная операция не replay-ится — подтверждено в проверенном контроле.** В `RoutingSession.cs:107–145` нет повторной отправки после начала tools/call; completion/исключение дают ошибку. `RoutingChecks.cs:247–256` наблюдает эффект до kill и одну запись после recovery. Request/progress IDs создаются на соединении (`RoutingSession.cs:93–112`), поколения проверяются handshake (`RouteConnection.cs:24–31`); старый transport не переназначается новому. Отдельная инъекция запоздалого кадра в этом ревью не выполнялась.
5. **Host выходит сам после последнего proxy; admission и exit используют общий gate — подтверждено в исходнике и обычных EOF/kill сценариях.** `DedicatedHost.cs:100–113`, `:129–158`, `:71–76`; Linux старт через setsid — `ShadowImage.cs:32–49`. F-02 ограничивает доказательство конкретной гонки closing. Новый `codex_lifecycle.py:72–83` убивает только MCP и проверяет живой backend; raw подтверждает двух живых детей спустя 2 с и cleanup. Наблюдение не распространяется на другие harness.
