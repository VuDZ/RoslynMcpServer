# Долгоживущий процесс workspace

Создано: **2026-10-09**. Обновлено: **2026-10-23**.
Статус: **scope согласован в обсуждении; план draft, код не начат**.
Происхождение: решение владельца H-003 из обсуждения workspace-state-cache, вариант C.
Черновики H-003/варианта B находятся в отдельном рабочем контексте cache и не
входят в эту ветку; для реализации C они не являются неявной зависимостью.

## Зачем

Основная цель — схлопывать дубликаты тяжёлого Roslyn workspace при работе
нескольких чатов и агентов над одним проектом с совместимой конфигурацией.
Мотивирующий пример владельца: harness может запустить около 20 MCP-процессов,
занимающих суммарно 10–20 ГБ. Это постановка проблемы, а не результат замера темы.

Ожидаемая модель: при работе над 2–3 проектами с совместимыми настройками —
2–3 тяжёлых host и много лёгких прокси. Несовместимые конфигурации одного
проекта могут потребовать дополнительных host; их число и память измеряются.
Дополнительная цель — переживать Reload и отключение клиента без новой
ordinary-загрузки. Внутри процесса уже есть RAM reuse и disk watchers (с 1.1.0).

## Идея

**Host и proxy — роли MCP-процесса, а не обязательно отдельные виды процессов.**
Первый `mcp1`, запущенный чат1, загружает проект1 и становится его host:
держит `SolutionManager`, watchers и тяжёлые данные, обслуживает свой чат и
подключения других MCP. `mcp2` из чат2 с совместимым проектом1 подключается к
`mcp1` как лёгкий proxy и не загружает второй Roslyn workspace.

Каждый MCP держит **стабильный клиентский MCP-фасад** независимо от своей роли:
исполняет вызовы локально как host либо направляет их выбранному host по
локальному каналу. Процесс может сменить роль. Обязательный отдельный daemon
на каждый проект не является согласованной моделью этой темы.

Публичные имена и параметры инструментов, успешные результаты анализа и
default-режим сохраняются. Диагностика host/proxy, ошибки восстановления и
семантика lifecycle-инструментов уточняются в design и документируются явно.

Сейчас сервер поднимает ровно один stdio-транспорт
(`RoslynMcpServiceCollectionExtensions.AddRoslynMcpServerTools`), а общие сервисы
регистрируются отдельно (`AddRoslynMcpCoreServices`). Это точка разделения,
но текущая core-регистрация смешивает workspace и состояние MCP-инструментов;
переиспользовать её без разделения нельзя.

## Границы

- Opt-in. По умолчанию остаётся текущий режим «один процесс на клиента».
- Подключение относится к определённому workspace descriptor и поколению host,
  а не к произвольно меняющемуся «текущему проекту» чужого MCP-процесса.
  При смене workspace процессом-владельцем прежние клиенты остаются на своём
  проекте через согласованную передачу роли host.
- Изменение cwd в runtime, изолированные ветви `Solution` внутри процесса,
  перенос прогретого Roslyn между процессами и OS fork вне scope. Роль host
  может перейти другому MCP; без миграции RAM новый владелец делает ordinary load.
- Разные чаты/PID не разделяют совместимые workspace. Различия harness и его
  настроек учитываются через контракт совместимости, а не через идентификатор чата.
- Disk cache здесь нет. Холодный старт host — обычная загрузка; его ускоряет
  отдельный отложенный вариант B (optimistic restore), вне этой research-ветки.
- Roslyn BuildHost не меняется.
- Канал доступен только текущему пользователю ОС.
- Windows, Linux и macOS живут по одному контракту; платформенное отличие
  допустимо только с той же гарантией на всех ОС (как в pitfall 27).
- Write boundary, analyzer admission, watcher policy и гарантии свежести RAM
  reuse сохраняются. Совместимость host — дополнительная проверка, не замена
  существующему matcher или проверкам перед публикацией и записью.
- Прокси не обмениваются полными списками соседей. Один новый host выбирается
  из подходящих MCP через общий механизм владения ключом; уведомление о
  плановом освобождении приходит от текущего host, не требует P2P-сети.

## Предварительный выбор владельца, 2026-10-10

История предварительного выбора; это не принятый design. Пункт о прозрачной
ретрансляции заменён решением от 2026-10-23 ниже; остальные ограничения сохранены.

- Конфигурация клиента не меняется: клиент запускает тот же stdio-бинарь.
  Исходно предполагался мост с отдельным host. **Уточнено 2026-10-23:** первый
  MCP может сам быть host и обслуживать последующие proxy; см. scope ниже.
- Канал мост ↔ host — локальный (named pipe / Unix domain socket), не HTTP.
  HTTP возможен позже как дополнительный вход для клиентов, подключающихся по URL.
- Мост по возможности — прозрачная ретрансляция байтов MCP; тогда U-C-05
  решается без разбора сообщений. **Superseded, 2026-10-23:** переключение host
  внутри живой MCP-сессии требует MCP-фасада и маршрутизации вызовов.
- Host живёт, пока есть клиенты, и завершается после простоя, а не сразу:
  Reload в Cursor переподключается через секунды. Сохранение снимка при выходе —
  вопрос отдельного варианта B, не E0 этой темы.
- Host запускается из теневой копии бинаря, чтобы publish не упирался в
  заблокированные DLL (pitfall 13). Совмещение host с MCP, запущенным harness,
  требует проверки bootstrap/теневой копии в task-04/task-01; готового решения нет.

## Согласованный scope, 2026-10-23

Зафиксирован по обсуждению с владельцем. Это требования к обновлённому плану,
а не приёмка design, spike, реализации или разрешение production rollout.
[Отчёт об обновлении и проверках](evidence/2026-10-23-plan-update.md).

### Совместимость и обнаружение

Новый прокси находит host по нормализованному дескриптору совместимости:
пользователь ОС, идентичность сборки сервера, стартовый рабочий контекст,
путь workspace и значимые параметры/настройки. Точный состав и правила для
пропущенных параметров — U-C-01; настройки другого клиента не наследуются молча.
Версия пакета или hash только apphost exe не считаются достаточным доказательством
идентичности всей сборки: design учитывает изменяемые DLL и плагины.

Детерминированный ключ/каталог обнаружения избавляет от обязательного опроса
всех процессов. При подключении host подтверждает дескриптор и своё поколение;
наличие записи, PID или совпадение имени канала не доказывает готовность.
Если workspace неизвестен при старте, выбор откладывается до явного
`load_workspace` или lazy load из конфигурации; алгоритм определяет task-01.

### Переключение прокси и передача роли host

**Уходит proxy-клиент:** `mcp1` держит проект1, `mcp2` использует его как proxy.
Чат2 вызывает `load_workspace` для проекта2. `mcp2` подключается к совместимому
host проекта2 либо сам получает право стать его host и загружает проект2.
После успешной загрузки меняет привязку; при отказе сохраняет привязку к
проекту1, если прежний host жив. `mcp1` и его клиенты продолжают проект1.

**Уходит сам host-клиент:** чат1/`mcp1` загрузил проект1, чат2/`mcp2` и
чат3/`mcp3` работают с проектом1 через `mcp1`. Затем чат1 загружает проект2.
До замены workspace `mcp1` сообщает об освобождении роли проекта1. Клиенты,
которым по-прежнему нужен проект1, через координацию ключа выбирают одного
нового владельца, например `mcp2`. Он становится host проекта1, остальные
подключаются к нему. `mcp1` работает с проектом2 локально или как proxy его host.
Запросы чат2/чат3 не исполняются на проекте2 без их собственного переключения.

Плановая передача допускает паузу на одну ordinary-загрузку проекта1 у нового
владельца; бесшовный перенос прогрева не обещается. Старый владелец прекращает
приём работы для освобождаемого ключа, согласует выполняющиеся запросы и
освобождает владение; новый начинает тяжёлую загрузку только после получения
владения. Нет параллельной холодной загрузки во всех proxy и скрытой подмены
workspace при сохранении старого поколения/канала.

Потерянное уведомление об освобождении обрабатывается через проверку
дескриптора/поколения и механизм recovery. Design задаёт границы запроса смены
проекта, дедлайны, поведение при отказе преемника/загрузки проекта2 и гарантии
доступности. Сохранение прежней привязки после неудачного proxy-перехода не
означает автоматического rollback уже переданного host workspace.

Несовместимость и освобождение — внутренние сигналы до исполнения вызова на
неверном workspace, а не инструкция агенту вручную переподключиться.
Параметры повторного load определяются контекстом сессии и явно описанными
defaults, а не текущими настройками случайно найденного host.

MCP-фасад сохраняет negotiated protocol, progress/cancellation, подписки и
список инструментов клиента при переключении и восстановлении. В текущем коде
`enable_tool_group` расширяет `lite` в runtime; в `full` это no-op. План исходит
из состояния активации на подключение; фактический DI/SDK seam проверяет E0.

### Падение и восстановление

После падения host несколько прокси восстанавливают доступ к одному ключу:

1. Проверяют наличие готового совместимого host и участвуют в координации владения.
2. Один подходящий MCP становится новым host; остальные ограниченно ждут готовности.
   Клиент, уже обслуживающий несовместимый workspace, не вытесняет его ради promotion.
   Правила пригодности кандидата и случая без кандидатов определяет design.
3. Host получает исключительное владение ключом до тяжёлой инициализации.
   Смерть кандидата между получением роли и readiness не допускает второго
   одновременного владельца и не блокирует восстановление навсегда.
4. Совпадающие запросы загрузки присоединяются к одной выполняющейся попытке.
   Её отказ не превращается в очередь повторных полных загрузок от каждого клиента.
5. Каждое новое владение ключом получает новое поколение, даже при повторной
   роли в том же PID. Старые ответы и привязки не принимаются за текущее
   состояние. RAM погибшего host не восстанавливается этой темой.

В общем режиме недоступность host не запускает автономную загрузку в каждом
прокси: promotion выполняет только победитель координации. Используются
ограниченное ожидание, согласованные повторы с задержкой
и явная ошибка при исчерпании бюджета. Отдельный автономный default-режим сохраняется.
Повторяющееся падение не должно порождать бесконечную серию стартов.

MCP-сессии выживших процессов остаются живыми; сессия чата в убитом MCP не
считается пережившей смерть процесса. Запросы, прерванные падением,
получают явный результат отказа; операции записи не переигрываются автоматически.
Повтор запроса допустим только при доказанном отсутствии начала его исполнения.
Отмена одного ожидающего клиента не отменяет общую загрузку остальных;
политику последнего ожидающего клиента определяет design.

## Открытые вопросы

Решаются в [E0/task-01](epoch-0-design-and-spike/task-01-architecture-decision-hi.md);
конкретные механизмы ещё не приняты; решения должны выполнять scope выше.

- **U-C-01 — совместимость и ключ host.** Канонизация путей, точная идентичность
  сборки/плагинов, cwd, env/config, Configuration/Platform/TFM, analyzer policy;
  defaults, неизвестный при старте workspace, проверка дескриптора и обнаружение.
- **U-C-02 — состояние сессии и процесса.** Сейчас на весь процесс общие:
  включённые группы инструментов (`McpRuntimeToolCollection`, `enable_tool_group`),
  профиль lite/full, harness session id в логе, `ROSLYN_MCP_WORKSPACE` как cwd,
  `RoslynMcp.jsonc`, плагины, build args/proofs, `stop_mcp_server` и `reset_workspace`.
  Нужно разделение host/session и явная семантика общих reset/stop, в том числе
  restart-required после обновления analyzer. Перезапуск одного прокси не
  выгружает analyzer из host.
- **U-C-03 — одновременные клиенты и смена host.** Одна попытка загрузки на ключ,
  ожидание/отмена, гонки load/reset/write, атомарная смена привязки после успеха,
  сохранение прежней привязки при отказе proxy-перехода; release/handoff, admission
  новых вызовов, переходы host↔proxy, пригодность кандидата и отказ преемника.
- **U-C-04 — жизненный цикл.** Idle timeout; смена версии после publish
  (`publish-and-verify.ps1`, pitfall 13); исключительное владение, готовность,
  поколения, смерть кандидата при promotion, закрытие stdio первого чата,
  crash loop, stale discovery и cleanup. Проверка bootstrap/теневой копии при
  совмещённых ролях без допущения обязательного отдельного daemon.
- **U-C-05 — MCP-фасад и внутренний протокол.** Маршрутизация, отсутствие
  автоматического replay, `notifications/progress`, отмена, `tools/list_changed`,
  подписки и версии `2025-11-25` / `2026-07-28` при смене host и его падении.
- **U-C-06 — память.** Host живёт долго; что происходит с RAM большого решения
  между сессиями, нужна ли выгрузка по простою.

## Разработка через TDD

Согласовано 2026-10-23: поведенческие контракты проверяются через цикл
red → green → refactor. Сначала воспроизводимый тест нужного поведения/гонки
и подтверждённый отказ на отсутствующем или неверном механизме, затем
минимальная реализация и повторный запуск. В evidence сохраняются команды,
причина ожидаемого red и результат green; ошибка сборки или отсутствие среды
не считаются доказательством red нужного поведения.

Task-03/task-04 начинают с лёгкого стенда без Roslyn: один владелец ключа,
одна загрузка, переход proxy, handoff владельца и recovery. Контролируемые
барьеры и счётчики проверяют гонки, multi-process тесты — реальное владение
и аварии. Task-02 переносит те же сценарии на настоящий workspace.

Fake load не доказывает корректность Roslyn/SDK/ОС: нужны реальные интеграционные
прогоны. Проверка доступности API до теста допустима. Память, задержки и
платформенная безопасность проверяются замерами/экспериментами; зелёный unit
тест их не заменяет. TDD не отменяет обязательную финальную validation.
