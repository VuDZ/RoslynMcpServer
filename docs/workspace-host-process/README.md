## Зачем

Основная цель — схлопывать дубликаты тяжёлого Roslyn workspace при работе
нескольких MCP-подключений/процессов к одному проекту с совместимой конфигурацией.
Мотивирующее наблюдение владельца на этом компьютере под Codex: 20+ MCP-процессов
одновременно, суммарно 10–20 ГБ (уточнено владельцем 2026-10-28). Ситуация реальная,
но её исторический per-PID состав не восстановлен: неизвестно,
какая часть памяти приходится на дубликаты совместимого workspace, а какая — на
разные проекты, несовместимые настройки и простаивающие процессы
([task-05](epoch-0-design-and-spike/task-05-applicability-checks-med.md)).
Пустой MCP без workspace, по наблюдению владельца, занимает около 18 МБ;
наблюдение могло быть сделано до включения Server GC в 1.5.12, поэтому на текущей базе
его перепроверяет task-05 в обоих режимах GC.

Ожидаемая модель: при работе над 2–3 проектами с совместимыми настройками —
2–3 тяжёлых host и много лёгких прокси. Несовместимые конфигурации одного
проекта могут потребовать дополнительных host; их число и память измеряются.
**Процессы не переживают клиентов. Решение владельца, 2026-10-28.** Цели переживать
Reload или закрытие harness нет; записанная ранее дополнительная цель снята. Когда
harness закрыт, все его MCP и host завершаются, а не держат память. Host живёт, пока
к нему подключён хотя бы один клиент; после ухода последнего он завершается после
короткой паузы, которая нужна только против гонки с новым подключением. Ни одна
модель не обходит управление процессами клиента (Job, группы процессов). В Codex
на Windows прежняя цель была бы и недостижима: выход приложения завершает весь Job
(task-05, [ревью F-02](review-task-03-05-2026-10-28/result.md)). Быстрый старт после
перезапуска клиента — задача темы [D](../workspace-load-performance/README.md) и
workspace-state-cache, не этой темы. Внутри процесса уже есть RAM reuse и disk
watchers (с 1.1.0).

### Наблюдения task-05 и решение владельца, 2026-10-28

Пустой 1.5.18: около 60 MiB working set, private bytes 23,3 / 18,4 MiB для
Server / Workstation GC. Синтетические 20 MCP (8 + 8 двух descriptor, 4 пустых)
дали 2606,4 MiB private bytes; это не состав прежних 10–20 ГБ.
В Codex app-server MCP и detached child находятся в Job с kill-on-close;
breakaway запрещён, выход/crash app-server завершил всех. Reload Window недоступен
в production Codex. После ручного выхода/перезапуска desktop прежний MCP
завершён, workspace в этом чате не загружен. Дополнительные UI-наблюдения
сохраняются с ограничениями; оставшиеся UI-сценарии не требуют заполнения.
[Scope и первичные данные](epoch-0-design-and-spike/evidence/task-05-applicability.md).

Подтверждение на настоящих subagent Codex Desktop: два агента загрузили тот же
workspace Release, завершились, а два отдельных MCP **1.5.16** остались живы
минимум 121 с после подтверждённого completed, 435,5 MiB private bytes вместе.
После замера они явно остановлены координатором; исходный worker сохранён.
Это не закрытие desktop-чата или Reload и не восстановление состава прежних 20+ MCP.

**Выбор моделей:** task-04 проверяет выделенный host, совмещение ролей отложено
([решение 2026-10-28](#сравниваемые-модели-и-проверки-применимости-2026-10-23)). Пережить harness процессам не нужно
([решение 2026-10-28](#зачем)). Отложенный HTTP-вариант этим не возобновлён.

## Граница клиентского поведения, уточнение 2026-10-28

Чат, MCP-подключение и процесс не имеют обязательного соответствия 1:1.
По наблюдению владельца, Cursor переиспользует MCP, что приводило к конфликтам,
Codex запускает новые процессы, а `dsh` держит один; эти сведения не являются
новой сравнительной проверкой клиентов. Исправление клиентских политик запуска
и полная матрица действий с чатами вне этой темы.

Контракт темы опирается на MCP-подключение/сессию, явную привязку к workspace
и владение процессом host. Чат не служит ключом совместимости или сигналом
отключения. EOF, разрыв подключения и смерть процесса проверяются непосредственно
в стенде task-04; UI-событие само по себе не означает ни одного из них.
Workspace после закрытия клиента не удерживается ([решение 2026-10-28](#зачем)).
[Основание и validation](evidence/2026-10-28-task-05-scope.md).

## Идея

> **Изменено 2026-10-28:** host — выделенный процесс, совмещение с первым MCP
> отложено как оптимизация ([решение владельца](#сравниваемые-модели-и-проверки-применимости-2026-10-23)). Ниже — исходная идея.

**Host и proxy — роли MCP-процесса, а не обязательно отдельные виды процессов.**
Первый `mcp1` загружает проект1 и становится его host:
держит `SolutionManager`, watchers и тяжёлые данные, обслуживает своё клиентское
подключение и другие MCP. `mcp2` с совместимым проектом1 подключается к
`mcp1` как лёгкий proxy и не загружает второй Roslyn workspace.

Каждый MCP держит **стабильный клиентский MCP-фасад** независимо от своей роли:
исполняет вызовы локально как host либо направляет их выбранному host по
локальному каналу. Процесс может сменить роль. Обязательный отдельный daemon
на каждый проект не является согласованной моделью этой темы. Модель ролей —
основной кандидат, но не принятый design: task-01 сравнивает её с отдельным
host и нулевым вариантом ([сравниваемые модели](#сравниваемые-модели-и-проверки-применимости-2026-10-23)).

Default-режим и прежние имена инструментов сохраняются. Явное дополнение владельца
2026-10-29 для shared: forceFresh/--force_fresh, reused-only actual context и
инструкция в load_workspace; граница parity среды описана в [O-05](#o-05-context).
Остальные результаты анализа, ошибки recovery и lifecycle уточняются в design.

Сейчас сервер поднимает ровно один stdio-транспорт
(`RoslynMcpServiceCollectionExtensions.AddRoslynMcpServerTools`), а общие сервисы
регистрируются отдельно (`AddRoslynMcpCoreServices`). Это точка разделения,
но текущая core-регистрация смешивает workspace и состояние MCP-инструментов;
переиспользовать её без разделения нельзя.

## Границы

- Opt-in. По умолчанию остаётся текущий автономный stdio-режим; процессами распоряжается клиент.
- Подключение относится к определённому workspace descriptor и поколению host,
  а не к произвольно меняющемуся «текущему проекту» чужого MCP-процесса.
  При смене workspace процессом-владельцем прежние клиенты остаются на своём
  проекте через согласованную передачу роли host.
- Изменение cwd в runtime, изолированные ветви `Solution` внутри процесса,
  перенос прогретого Roslyn между процессами и OS fork вне scope. Роль host
  может перейти другому MCP; без миграции RAM новый владелец делает ordinary load.
- Разные чаты/PID сами по себе не разделяют совместимые workspace; исключение —
  явно выбранный private fresh по [O-05](#o-05-context). Различия harness и его
  настроек учитываются через контракт совместимости, а не через идентификатор чата.
- Disk cache здесь нет. Холодный старт host — обычная загрузка; его ускоряет
  отдельный отложенный вариант B (optimistic restore), вне этой research-ветки.
- Roslyn BuildHost не меняется в рамках этой темы. Актуальная база 1.5.17 уже
  включает production fork netcore с A+B+C; он принят в теме производительности
  и используется здесь без доработок. Это не standalone spike и не новый MCP-host.
- Канал доступен только текущему пользователю ОС.
- Windows, Linux и macOS живут по одному контракту; платформенное отличие
  допустимо только с той же гарантией на всех ОС (как в pitfall 27).
- Write boundary, analyzer admission, watcher policy и гарантии свежести RAM
  reuse сохраняются. Совместимость host — дополнительная проверка, не замена
  существующему matcher или проверкам перед публикацией и записью.
- Прокси не обмениваются полными списками соседей. Один новый host выбирается
  из подходящих MCP через общий механизм владения ключом; уведомление о
  плановом освобождении приходит от текущего host, не требует P2P-сети.

## Предварительный выбор владельца, 2026-10-10

История предварительного выбора; это не принятый design. Пункт о прозрачной
ретрансляции заменён решением от 2026-10-23 ниже; остальные ограничения сохранены.

- Конфигурация клиента не меняется: клиент запускает тот же stdio-бинарь.
  Исходно предполагался мост с отдельным host. **Уточнено 2026-10-23:** первый
  MCP может сам быть host и обслуживать последующие proxy; см. scope ниже.
- Канал мост ↔ host — локальный (named pipe / Unix domain socket), не HTTP.
  HTTP возможен позже как дополнительный вход для клиентов, подключающихся по URL.
- Мост по возможности — прозрачная ретрансляция байтов MCP; тогда U-C-05
  решается без разбора сообщений. **Superseded, 2026-10-23:** переключение host
  внутри живой MCP-сессии требует MCP-фасада и маршрутизации вызовов.
- Host живёт, пока есть клиенты, и завершается после простоя, а не сразу:
  Reload в Cursor переподключается через секунды. Сохранение снимка при выходе —
  вопрос отдельного варианта B, не E0 этой темы. **Уточнено 2026-10-28:** пауза
  короткая и нужна только против гонки подключения; цели переживать Reload нет ([«Зачем»](#зачем)).
- Host запускается из теневой копии бинаря, чтобы publish не упирался в
  заблокированные DLL (pitfall 13). Совмещение host с MCP, запущенным harness,
  требует проверки bootstrap/теневой копии в task-04/task-01; готового решения нет.

## Согласованный scope, 2026-10-23

Зафиксирован по обсуждению с владельцем. Это требования к обновлённому плану,
а не приёмка design, spike, реализации или разрешение production rollout.
[Отчёт об обновлении и проверках](evidence/2026-10-23-plan-update.md).

### Совместимость и обнаружение

По уточнению владельца 2026-10-29 новый proxy находит host по небольшому WorkspaceKey
path/Configuration/Platform/TFM и отдельному namespace пользователя/сборки/протокола.
Environment/cwd/settings — общий контекст создателя; reused load показывает actual
context и инструкцию private fresh ([O-05](#o-05-context)). Правила omitted — U-C-01.
Версия пакета или hash только apphost exe не считаются достаточным доказательством
идентичности всей сборки: design учитывает изменяемые DLL и плагины.

Детерминированный ключ/каталог обнаружения избавляет от обязательного опроса
всех процессов. При подключении host подтверждает дескриптор и своё поколение;
наличие записи, PID или совпадение имени канала не доказывает готовность.
Если workspace неизвестен при старте, выбор откладывается до явного
`load_workspace` или lazy load из конфигурации; алгоритм определяет task-01.

### Переключение прокси и передача роли host

**Уходит proxy-клиент:** `mcp1` держит проект1, `mcp2` использует его как proxy.
Чат2 вызывает `load_workspace` для проекта2. `mcp2` подключается к совместимому
host проекта2 либо сам получает право стать его host и загружает проект2.
После успешной загрузки меняет привязку; при отказе сохраняет привязку к
проекту1, если прежний host жив. `mcp1` и его клиенты продолжают проект1.

**Уходит сам host-клиент:** чат1/`mcp1` загрузил проект1, чат2/`mcp2` и
чат3/`mcp3` работают с проектом1 через `mcp1`. Затем чат1 загружает проект2.
До замены workspace `mcp1` сообщает об освобождении роли проекта1. Клиенты,
которым по-прежнему нужен проект1, через координацию ключа выбирают одного
нового владельца, например `mcp2`. Он становится host проекта1, остальные
подключаются к нему. `mcp1` работает с проектом2 локально или как proxy его host.
Запросы чат2/чат3 не исполняются на проекте2 без их собственного переключения.

Плановая передача допускает паузу на одну ordinary-загрузку проекта1 у нового
владельца; бесшовный перенос прогрева не обещается. Старый владелец прекращает
приём работы для освобождаемого ключа, согласует выполняющиеся запросы и
освобождает владение; новый начинает тяжёлую загрузку только после получения
владения. Нет параллельной холодной загрузки во всех proxy и скрытой подмены
workspace при сохранении старого поколения/канала.

Потерянное уведомление об освобождении обрабатывается через проверку
дескриптора/поколения и механизм recovery. Design задаёт границы запроса смены
проекта, дедлайны, поведение при отказе преемника/загрузки проекта2 и гарантии
доступности. Сохранение прежней привязки после неудачного proxy-перехода не
означает автоматического rollback уже переданного host workspace.

Несовместимость и освобождение — внутренние сигналы до исполнения вызова на
неверном workspace, а не инструкция агенту вручную переподключиться.
Параметры повторного load определяются контекстом сессии и явно описанными
defaults, а не текущими настройками случайно найденного host.

MCP-фасад сохраняет negotiated protocol, progress/cancellation, подписки и
список инструментов клиента при переключении и восстановлении. В текущем коде
`enable_tool_group` расширяет `lite` в runtime; в `full` это no-op. План исходит
из состояния активации на подключение; фактический DI/SDK seam проверяет E0.

### Падение и восстановление

После падения host несколько прокси восстанавливают доступ к одному ключу:

1. Проверяют наличие готового совместимого host и участвуют в координации владения.
2. Один подходящий MCP становится новым host; остальные ограниченно ждут готовности.
   Клиент, уже обслуживающий несовместимый workspace, не вытесняет его ради promotion.
   Правила пригодности кандидата и случая без кандидатов определяет design.
3. Host получает исключительное владение ключом до тяжёлой инициализации.
   Смерть кандидата между получением роли и readiness не допускает второго
   одновременного владельца и не блокирует восстановление навсегда.
4. Совпадающие запросы загрузки присоединяются к одной выполняющейся попытке.
   Её отказ не превращается в очередь повторных полных загрузок от каждого клиента.
5. Каждое новое владение ключом получает новое поколение, даже при повторной
   роли в том же PID. Старые ответы и привязки не принимаются за текущее
   состояние. RAM погибшего host не восстанавливается этой темой.

В общем режиме недоступность host не запускает автономную загрузку в каждом
прокси: promotion выполняет только победитель координации. Используются
ограниченное ожидание, согласованные повторы с задержкой
и явная ошибка при исчерпании бюджета. Отдельный автономный default-режим сохраняется.
Повторяющееся падение не должно порождать бесконечную серию стартов.

MCP-сессии выживших процессов остаются живыми; сессия чата в убитом MCP не
считается пережившей смерть процесса. Запросы, прерванные падением,
получают явный результат отказа; операции записи не переигрываются автоматически.
Повтор запроса допустим только при доказанном отсутствии начала его исполнения.
Отмена одного ожидающего клиента не отменяет общую загрузку остальных;
политику последнего ожидающего клиента определяет design.

## Сравниваемые модели и проверки применимости, 2026-10-23

Добавлено после независимого ревью по обсуждению с владельцем. Требования
scope выше не меняются; отклонение от них возможно только явным выбором владельца.

Модель ролей сама порождает основную сложность плана: handoff при смене проекта
host-клиентом, promotion, demotion с остаточной CLR-памятью и analyzer identity,
зависимость от stdio lifetime и от того, как harness завершает процессы.
Удерживать host после закрытия harness не требуется ([решение 2026-10-28](#зачем)).
Bootstrap совмещённого host из теневой копии ещё не доказан: ограничения проверенного
запуска записаны в task-05, механизмы проверяет task-04. Поэтому task-01 выбирает модель сравнением, а не по умолчанию:

1. **Роли в MCP** — scope выше; был основным кандидатом, с 2026-10-28 —
   отложенная оптимизация поверх выделенного host (см. решение ниже).
2. **Отдельный host.** Первый MCP запускает отделённый host-процесс ключа из
   теневой копии; MCP всех чатов — proxy; host живёт, пока к нему подключены proxy,
   и завершается после короткой паузы без клиентов.
   Handoff и demotion не нужны; recovery сводится к тому, что получивший
   владение ключом запускает новый host. Host не переживает клиентов: на Windows
   его держит Job клиента, на Unix он завершается сам по уходу последнего proxy;
   проверяет task-04 с учётом ограничений запуска из task-05. Расходится со scope выше и
   допустим только по явному выбору владельца.
3. **Нулевой вариант.** Текущий автономный stdio-режим без IPC — исходный
   контроль. Отдельно оценивается его возможное улучшение: выгрузка workspace
   по простою (U-C-06), которая может экономить память простаивающих процессов,
   но оставляет дубликаты активных; отложена до выбора модели ([U-C-06](#открытые-вопросы)).
   Быстрый холодный старт через вариант B —
   отдельная перспективная альтернатива вне этой ветки; её выгоды не включаются
   в измеренный результат текущего режима или idle unload без проверки B.

**Выбор моделей для task-04. Решение владельца, 2026-10-28.** Обе shared-модели —
один механизм: MCP находит подходящий host по ключу и подключается к нему; различие
только в том, кто host — один из MCP или выделенный процесс. Общая часть: ключ
совместимости, обнаружение и владение ключом, handshake с идентичностью сборки,
фасад, восстановление после смерти host, разделение состояния по task-00.
Task-04 проверяет общую часть и **выделенный host**. Модель ролей — это выделенный
host плюс совмещение host с первым MCP, чтобы одиночный клиент не платил за лишний
процесс и IPC; ради этого нужны handoff, promotion и demotion. Совмещение отложено
как возможная оптимизация: к нему возвращаются, только если замеры покажут, что
лишний процесс и IPC мешают одиночному клиенту, или выделенный host упрётся в
блокер какого-то harness. Нулевой вариант остаётся контролем. Изменяет уточнение
2026-10-23 «первый MCP может сам быть host».

**Отложено владельцем, 2026-10-28:** общий HTTP-сервер (Streamable HTTP) с
реестром workspace и состоянием на MCP-сессию. Он убирает самописный фасад,
handoff и promotion, но требует автозапуска сервера, корня сессии вместо cwd,
защиты localhost-порта и упирается в одну регистрацию MSBuild и общий загрузчик
анализаторов на процесс. В сравнение E0 не входит; возврат к нему — отдельным
решением владельца.

Критерии сравнения: память на реальном распределении процессов (task-05,
task-02), число механизмов (IPC, handoff, promotion, demotion), поведение при
отключении MCP-подключения и завершении процессов, платформенные риски,
стоимость реализации и сопровождения.

Общие гарантии обеих shared-моделей — один workspace на совместимый ключ,
изоляция клиентов, переключение привязки, согласованное восстановление,
поколения и отсутствие replay. Handoff при смене проекта host-клиентом,
promotion proxy в host и demotion относятся только к модели ролей. В модели
отдельного host все MCP остаются proxy; смена проекта любого чата не передаёт
владение прежним workspace. Применимость сценариев task-03/task-04/task-02
фиксируется по проверяемой или выбранной модели, без снятия общих гарантий.
Выбор отдельного host по-прежнему требует явного решения владельца.
Если выбран нулевой вариант, task-02 и E1 shared-режима не запускаются;
невыполненные задачи отмечаются отложенными с причиной после решения владельца,
а реализация shared-режима не объявляется принятой.

**Проверки применимости до spike механизмов** —
[task-05](epoch-0-design-and-spike/task-05-applicability-checks-med.md):
разбор памяти наблюдаемой ситуации с ~20 MCP, стоимость пустого процесса/GC
и ограничения проверенных способов запуска host. Политика запуска MCP по чатам
и UI-матрица клиентов не являются критериями завершения. После task-05 владелец решает, продолжать ли
тему и какие модели проверять в task-04.

**Proxy — тот же серверный процесс без workspace. Решение владельца, 2026-10-28.**
Прежнее требование «чистого proxy» (не регистрировать MSBuild, не загружать Roslyn
и plugins) снято. Proxy стартует как обычный сервер, но workspace не загружает;
тяжёлое состояние — только workspace в host. Основание: SDK-proxy task-03 по памяти
равен пустому серверу task-05 (около 20 MiB private на Windows), разница в working
set — единицы MiB, в основном общие страницы DLL-образов
([ревью F-05](review-task-03-05-2026-10-28/result.md)). Следствия: bootstrap seam,
манифест инструментов и отдельный путь plugins для proxy не нужны; `tools/list` proxy
строит как сейчас; инструменты без workspace (`get_code_skeleton` и подобные) могут
исполняться в proxy локально. Режим GC фиксируется при старте процесса, а proxy
может стать host, поэтому GC одинаков во всех процессах (Server GC по умолчанию,
около +5 MiB private на proxy). Demotion — освобождение workspace; загруженные
сборки analyzer и их identity остаются ограничением процесса.

**Владение ключом.** Базовая гипотеза для task-04 — блокировка уровня ОС,
которую ОС снимает при смерти процесса (файловый lock или named mutex), с
поколением, записанным под этой блокировкой. Собственный протокол координации
вводится, только если гипотеза не выполняет scope на какой-то ОС.

**Граница маршрутизации.** В host направляются инструменты, которым нужен
workspace. Build, test, `execute_dotnet_command` и другие инструменты,
запускающие процессы, — кандидаты на исполнение в proxy: у них свой cwd, а
падение host не должно само по себе обрывать уже запущенный CLI-процесс.
Граница может проходить внутри инструмента: разрешение проекта, defaults и
build proofs требуют workspace-контекста, а запуск CLI может оставаться в proxy.
Например, DLL-маршрут тестов сейчас использует Roslyn Solution и
`SessionBuildState`; перенос инструмента целиком заранее не предписан.
Task-00 инвентаризирует этапы, task-01 определяет их размещение и поведение при
смене проекта/поколения или падении host до, во время и после CLI-прогона.
Успех CLI сам по себе не подтверждает свежесть build proof нового поколения.
Общий host делит CPU между клиентами; задержку при параллельной тяжёлой работе
измеряет task-02.

## Открытые вопросы

Решаются в [E0/task-01](epoch-0-design-and-spike/task-01-architecture-decision-hi.md);
конкретные механизмы ещё не приняты; решения должны выполнять scope выше.

- **U-C-01 — совместимость и ключ host.** Канонизация путей, точная идентичность
  сборки/плагинов, cwd, env/config, Configuration/Platform/TFM, analyzer policy;
  defaults, неизвестный при старте workspace, проверка дескриптора и обнаружение.
- **U-C-02 — состояние сессии и процесса.** Сейчас на весь процесс общие:
  включённые группы инструментов (`McpRuntimeToolCollection`, `enable_tool_group`),
  профиль lite/full, harness session id в логе, `ROSLYN_MCP_WORKSPACE` как cwd,
  `RoslynMcp.jsonc`, плагины, build args/proofs, `stop_mcp_server` и `reset_workspace`.
  Нужно разделение host/session и явная семантика общих reset/stop, в том числе
  restart-required после обновления analyzer. Перезапуск одного прокси не
  выгружает analyzer из host.
- **U-C-03 — одновременные клиенты и смена host.** Одна попытка загрузки на ключ,
  ожидание/отмена, гонки load/reset/write, атомарная смена привязки после успеха,
  сохранение прежней привязки при отказе proxy-перехода; release/handoff, admission
  новых вызовов, переходы host↔proxy, пригодность кандидата и отказ преемника.
- **U-C-04 — жизненный цикл.** Idle timeout; смена версии после publish
  (`publish-and-verify.ps1`, pitfall 13); исключительное владение, готовность,
  поколения, смерть кандидата при promotion, закрытие клиентского stdio,
  crash loop, stale discovery и cleanup. Проверка bootstrap/теневой копии при
  совмещённых ролях без допущения обязательного отдельного daemon.
- **U-C-05 — MCP-фасад и внутренний протокол.** Маршрутизация, отсутствие
  автоматического replay, `notifications/progress`, отмена, `tools/list_changed`,
  подписки и версии `2025-11-25` / `2026-07-28` при смене host и его падении.
- **U-C-06 — память.** Host живёт долго; что происходит с RAM большого решения
  между сессиями, нужна ли выгрузка по простою. Reset без GC память не возвращает;
  reset + `GCCollectionMode.Aggressive` на малом решении возвращает около 2/3
  прироста от загрузки ([ревью F-01](review-task-03-05-2026-10-28/result.md)).
  **Решение владельца, 2026-10-28:** выгрузка по простою отложена до выбора модели.
  С общим workspace дубликатов нет и выгружать почти нечего; на малом решении экономия
  мала, на большом повторная загрузка заметно ухудшает работу. Если владелец выберет
  нулевой вариант, idle unload возвращается как основное смягчение. Политика простоя
  host, к которому подключены только простаивающие клиенты, — вопрос task-01.
  Принудительная выгрузка — aggressive GC после явного `reset_workspace` и разбор
  20–25 MiB живого heap, переживающих reset и GC, — обсуждается после окончания
  исследования.
- **U-C-07 — модель процессов.** Для task-04 выбран выделенный host, роли отложены
  ([решение 2026-10-28](#сравниваемые-модели-и-проверки-применимости-2026-10-23)); окончательно — выделенный host или нулевой вариант;
  данные task-05 и критерии из [сравнения моделей](#сравниваемые-модели-и-проверки-применимости-2026-10-23).
- **U-C-08 — маршрутизация и конкуренция клиентов.** Какие инструменты исполняются
  в host, какие локально в proxy (proxy — обычный процесс без workspace); влияние
  тяжёлых запросов одного клиента на остальных.

### Решение владельца O-05, 2026-10-29

<a id="o-05-context"></a>
**Выбрано:** WorkspaceKey = absolute path + Configuration + Platform + TFM.
Environment/cwd/toolset/settings — контекст создателя host, не дополнительные
workspace keys. Namespace текущего пользователя и проверка verified image/plugin/
protocol остаются отдельной границей admission; они не заменяются совпадением пути.
Полная parity индивидуальной среды proxy не обещается; CLI сохраняет свою среду.

--force_fresh создаёт **новый private host только для инициирующего proxy**.
Он не публикуется для остальных и не заменяет shared host. Для агента планируется
load_workspace(forceFresh=true) с тем же результатом; повторный обычный load
сохраняет private. Proxy остаётся proxy без in-process workspace.

**Уточнение вывода:** дополнительный actual context и инструкция forceFresh в
load_workspace появляются только у MCP, присоединившегося к существующему host.
Создатель нового host этого блока не получает. Reused/created — происхождение
attachment, не cached load; cached/brief output не скрывают блок у reused клиента.
Path/global properties/toolset/cwd/config origin/policy показываются фактически,
без env values/credentials и без заявления о доказанной environment parity.
[Решение, границы и validation](evidence/2026-10-29-task-01-owner-context.md).

Прежние варианты canonical-v1/strict после раунда 5 заменены этим решением.
O-02/O-03/O-04 выбраны ниже; O-01 открыт. Task-06 completed, 2026-10-29: Linux/Claude Code и Windows/Codex приняты в сокращённом preflight scope, 2 раунда / 5 подтверждённых исправлений; объём сокращён, механизмы перенесены в task-02; [отчёт task-06](epoch-0-design-and-spike/evidence/task-06-environment-and-deployment-preflight.md).
Task-02 не начат, design целиком не принят.

<a id="o-02-reset-options"></a>
**O-02 — выбрано, 2026-10-29: global retire.** Reset редок: в Linux-логах за неделю
нет ни одного вызова, на двух Windows-компьютерах основной разработки — 4 вызова около
двух недель назад. Поэтому выбран самый надёжный путь: shared `reset_workspace`
завершает общий host, следующий вызов поднимает новый generation одной загрузкой.
Чистые read-стадии соседей отменяются с просьбой повторить; load/prepare/MSBuild и
принятые записи завершаются в drain budget с явным исходом либо неопределённостью
эффектов. Metadata readOnly не доказывает чистоту. Proxy CLI не прерывается,
следующий вызов сообщает агенту о перезапуске.
Soft reset и предложенный ранее локальный reset в private host
([запись варианта](evidence/2026-10-29-task-01-reset-options.md)) отвергнуты.
[Решение, данные и правила для соседей](evidence/2026-10-29-task-01-reset-decision.md).

<a id="o-03-dev-publish"></a>
**O-03 — выбрано, 2026-10-29:** publish с остановкой — сценарий разработки.
Сохраняется текущая схема: остановить найденные MCP из текущего каталога разработки/
publish и попытаться обновить. При автоматическом respawn со стороны dsh/другого
harness допустим отказ; владелец при необходимости вручную остановит harness/MCP.
Скрипт, launcher и непрерывное обновление ради этого не дорабатываются. Другие
checkout/установки не входят в область остановки. [Решение и validation](evidence/2026-10-29-task-01-dev-publish.md).

<a id="o-04-plugins-deferred"></a>
**O-04 — выбрано, 2026-10-29:** реальную поддержку plugins отложить. Первый shared
spike без них; Sample — возможный лёгкий контроль, без редизайна plugin API и audit
всех плагинов. Неподдерживаемый plugin даёт явный отказ shared, ordinary остаётся.
При общих неизменившихся настройках наборы обычно совпадают; частые расхождения не
предполагаются. Сейчас loader фиксирует exe/cwd config, drop-in и env при startup,
а не перечитывает plugins при load_workspace. Multi-client singleton state — другой
вопрос, проверка совместимости передана последующему E1 scope.
**Требуемое поведение после уточнения владельца:** читать список из global config
и конфига рядом с выбранным solution/project, независимо от startup cwd. При смене
workspace использовать проектный источник нового пути. Это отложенное изменение
P-01 для E1; текущий loader пока работает по прежним правилам.
[Решение и source сверка](evidence/2026-10-29-task-01-plugins-deferred.md).

<a id="l-01-launcher"></a>
**L-01 — внешний Linux launcher включает вложенные RID outputs.** Open, 2026-10-29;
owner — сопровождающий Linux launcher владельца, `~/.local/share/roslyn-mcp/launch.sh`
вне этого checkout. Snapshot 2.0G/4868 файлов против 93M/392 выбранного build output —
[наблюдение раунда 5](review-task-01-round-5-2026-10-29/linux-env-and-image-probe.json),
не новый локальный замер. Task-06 проверяет file set/reuse и передаёт исправление
владельцу launcher; скрипт здесь не читался/не менялся. Нельзя просто исключить
все subdirectories: runtime/native/BuildHost/plugin dependencies должны сохраниться.
Аудит task-06, 2026-10-29, read-only: собственный file set сервера — 105,9 МиБ / 231 файл;
identity snapshot — size/mtime двух файлов без манифеста; согласованность копии
проверяется только по ним же; lease `flock` на fd 9 наследуется всеми потомками .NET,
включая `setsid`. Reuse snapshot — no-go, host строит свой образ.
[Аудит](epoch-0-design-and-spike/evidence/task-06-environment-and-deployment-preflight.md#7-аудит-launcher).

## Разработка через TDD

Согласовано 2026-10-23: поведенческие контракты проверяются через цикл
red → green → refactor. Сначала воспроизводимый тест нужного поведения/гонки
и подтверждённый отказ на отсутствующем или неверном механизме, затем
минимальная реализация и повторный запуск. В evidence сохраняются команды,
причина ожидаемого red и результат green; ошибка сборки или отсутствие среды
не считаются доказательством red нужного поведения.

Task-03/task-04 начинают с лёгкого стенда без Roslyn: один владелец ключа,
одна загрузка, переход proxy, handoff владельца и recovery. Контролируемые
барьеры и счётчики проверяют гонки, multi-process тесты — реальное владение
и аварии. Task-02 переносит те же сценарии на настоящий workspace.

Fake load не доказывает корректность Roslyn/SDK/ОС: нужны реальные интеграционные
прогоны. Проверка доступности API до теста допустима. Память, задержки и
платформенная безопасность проверяются замерами/экспериментами; зелёный unit
тест их не заменяет. TDD не отменяет обязательную финальную validation.
