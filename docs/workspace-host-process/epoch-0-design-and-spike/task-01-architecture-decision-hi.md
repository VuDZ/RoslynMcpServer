## Цель

`design.md` в корне темы: выбор модели процессов и её design. Основной
кандидат — MCP-процессы, совмещающие свой клиентский фасад с ролью host либо
работающие proxy, с передачей роли при смене проекта. Ответы на U-C-01…U-C-08,
проверенные механизмы схлопывания/восстановления и явный список решений для владельца.

Обязательные разделы:

0. **Выбор модели** (U-C-07). Сравнение ролей в MCP, отдельного host и нулевого
   варианта по критериям README темы на данных task-05, task-03 и task-04:
   память, число механизмов, отключение MCP-клиента и смерть процессов, платформенные риски,
   стоимость. Рекомендация и явный выбор владельца. Разделы ниже описывают
   выбранную модель; требования, нужные только модели ролей (handoff, promotion,
   demotion), для другой модели помечаются неприменимыми с причиной.
   Текущий режим служит исходным контролем; idle unload оценивается отдельно,
   вариант B — перспективная внешняя альтернатива без зачёта недоказанных выгод.
   При выборе нулевого варианта фиксируется решение не запускать task-02/E1
   shared-режима и причина отложения невыполненных задач, без приёмки реализации.
1. **Процессная модель и совместимость** (U-C-01). Точный дескриптор и ключ,
   нормализация путей, сборки и plugins, env/config и load options. Исключить
   чат/PID как причину дублирования. Разрешение пропущенных параметров и lazy
   load, неизвестный при старте workspace, подтверждение совместимости host.
   Чистый proxy не регистрирует MSBuild и не загружает сборки Roslyn и plugins;
   источник списка инструментов plugins в proxy. В модели ролей:
   первый MCP обслуживает своё клиентское подключение и remote proxy как host. Смена собственного
   проекта освобождает прежнюю роль с handoff; один proxy может стать новым host.
   Случай отсутствия пригодных кандидатов и влияние host→proxy на CLR lifetime.
2. **Транспорт.** Named pipe / Unix domain socket, имя канала, ACL текущего
   пользователя, внутренний handshake с дескриптором, версией протокола и
   поколением host. Граница MCP-фасад/host и внутренний протокол маршрутизации.
   API MCP C# SDK проверяется по установленной сборке (`explore_assembly`,
   `decompile_type`), а не по памяти; варианты DI оцениваются по task-00/task-03.
3. **Сессии** (U-C-02, U-C-03): что переносится в сессию, что остаётся общим,
   как сериализуются операции нескольких клиентов. Активация групп — на клиенте;
   общие reset/stop и restart-required analyzers описаны явно. Смена host после
   успешного load, сохранение прежней живой привязки при отказе, согласование
   перехода с выполняющимися запросами и правила изменения session defaults.
   Только для модели ролей — переход host-клиента: release notification,
   прекращение admission, завершение/отмена текущих вызовов, освобождение ключа,
   promotion одного преемника и поведение при отказе на каждой стадии. Нельзя перенаправить
   клиентов проекта1 на проект2 только из-за смены workspace в прежнем процессе.
   Граница маршрутизации (U-C-08): размещение инструментов и отдельных этапов
   по таблице task-00. Для build/test разделить разрешение проекта/defaults,
   admission/build proofs, запуск CLI и обработку результата. Описать смену
   привязки/поколения и падение host до, во время и после CLI: уже запущенный
   процесс не обрывается только из-за потери host, но его успех не становится
   доказательством свежести нового поколения. Влияние тяжёлых запросов одного
   клиента на остальных также оценивается.
4. **Жизненный цикл** (U-C-04, U-C-06): запуск по требованию, idle timeout,
   смена версии, падение host, выгрузка памяти. Обнаружение без опроса всех
   процессов, координация запуска и владение до тяжёлой инициализации (по
   результату проверки блокировки ОС в task-04), смерть
   кандидата до readiness, stale entries, проверка готовности, поколения и cleanup.
   Потерянное release notification, закрытие клиентского stdio при remote-клиентах и
   предел гарантий при принудительном завершении процесса harness.
5. **MCP-фасад** (U-C-05): стабильная клиентская сессия, negotiated protocol,
   прогресс, отмена, `tools/list_changed`, подписки и их сохранение при смене
   host/восстановлении. Корреляция запросов и изоляция ответов разных поколений.
6. **Восстановление и отказ.** Одна попытка восстановления/загрузки на ключ,
   присоединение ожидающих клиентов, общий результат ошибки, отмена одного и
   последнего ожидающего клиента, бюджеты и согласованный backoff при crash loop.
   Нет автономной загрузки в каждом прокси и автоматического replay операций
   записи. При неопределённом исходе операции — явная ошибка, а не ложный успех.
7. **Наблюдаемость.** Какой процесс пишет какой лог; harness session id сессии.
8. **Влияние на документацию и публикацию**: `publish-and-verify.ps1`,
   README, `AGENTS.md.sample`, логи исходного/теневого каталога. Исходный publish
   можно обновить; живые host старой сборки не принимаются за новую сборку.
   Доказать bootstrap/теневую копию при совмещении ролей, а не предполагать,
   что запущенный harness MCP автоматически стал отдельным shadow daemon.

Каждый раздел содержит рекомендацию, отвергнутые альтернативы и риск.

## Проверки

- Модель выбрана сравнением на данных task-05, а не по умолчанию; цель
  «пережить Reload» достижима в выбранной модели или явно снята владельцем.
- Каждый конфликт из task-00 имеет решение или вынесен владельцу.
- Публичные параметры и успешные результаты анализа, default-режим и write
  boundary сохранены; изменения lifecycle/диагностики shared-режима перечислены.
- Сценарии «10 прокси / один проект», переход чат2 на проект2 при живом чат1,
  отказ перехода, падение host и смерть кандидата/запускающего процесса до
  readiness имеют проверяемые последовательности состояний и критерии отсутствия
  дублирующей загрузки для обеих shared-моделей. Уход самого host-клиента на
  проект2 и отказ преемника проверяются только в модели ролей; в модели отдельного
  host смена проекта любого чата не требует handoff прежнего workspace.
- Согласованный scope отражён без P2P-сети клиентов и миграции Roslyn heap.
  В модели ролей смена workspace владельца допустима только с release/handoff
  и новым поколением; descriptor подключённых клиентов нельзя подменить молча.
- Гарантии одинаковы на Windows, Linux и macOS либо отличие явно ограничено.
- Независимое ревью design до task-02; выбор владельца записывается в README темы.
