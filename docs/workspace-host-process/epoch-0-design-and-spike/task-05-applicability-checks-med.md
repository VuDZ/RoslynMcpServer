## Цель

До spike механизмов получить факты, от которых зависят выбор модели процессов
(U-C-07) и объём task-04:

1. из чего состоит память наблюдаемой ситуации с ~20 MCP-процессами и какую
   часть могут устранить общий workspace или простое улучшение текущего режима;
2. какова стоимость пустого процесса и влияние режима GC;
3. какие ограничения ОС и проверенного способа запуска нужно учесть в task-04.

## Что сделать

1. **Ограничения запуска host.** В доступном изолированном стенде на Windows
   и Linux при наличии среды проверить EOF stdio и завершение запускающего
   процесса. Зафиксировать:
   - что получает сам MCP-процесс: EOF stdin, сигнал или kill, время до завершения;
   - судьбу обычного дочернего процесса MCP;
   - судьбу отделённого процесса: на Windows — входит ли MCP в Job object, разрешён
     ли breakaway (`CREATE_BREAKAWAY_FROM_JOB`) и что происходит без него; на Unix —
     новая сессия (`setsid`) и группа процессов;

   Вывод относится к проверенному способу запуска. Ограничения передать в
   task-04 для проверки механизма host; один неудачный detach не отвергает
   все модели. Отключение stdio и принудительное завершение процесса различаются.
   Полная матрица клиентов и действий с чатами не требуется.
2. **Разбор памяти наблюдаемой ситуации.** На компьютере владельца, где было
   ~20 MCP, для каждого процесса: workspace path, профиль и параметры load,
   память (private bytes и working set; метод указать), есть ли загруженный
   workspace, время простоя. Источники — список процессов и `logs/mcp-*.log`
   (`HarnessSessionId`, `load_workspace`). Сгруппировать: дубликаты одного workspace
   с одинаковыми параметрами (приближение ключа совместимости до U-C-01), разные
   проекты, процессы без workspace, простаивающие. Если ситуация недоступна,
   воспроизвести её и указать, чем воспроизведение отличается. Записать версию
   сервера каждого процесса: с 1.5.12 сервер работает с Server GC
   (`RoslynMcpServer.csproj`, по замеру темы производительности +14–19% working set
   на загруженном решении), и процессы разных версий не сравниваются напрямую.
3. **Пустой процесс.** Тем же методом проверить наблюдение владельца (~18 МБ
   для MCP без workspace) на текущей версии и записать, какие сборки Roslyn,
   MSBuild и plugins загружены к этому моменту. Это исходная точка для proxy,
   который не грузит ничего лишнего. Наблюдение могло быть сделано до Server GC
   (1.5.12), поэтому оно не переносится на текущую базу без замера.
4. **Режим GC.** Повторить замеры п. 3 и, на одном загруженном решении, п. 2 с
   `DOTNET_gcServer=1` (текущий default) и `DOTNET_gcServer=0`: working set и
   private bytes пустого процесса, процесса с workspace и простаивающего после
   работы. Если Workstation GC заметно дешевле для пустых и простаивающих
   процессов, это смягчение для нулевого варианта и для чистых proxy без IPC;
   цену в задержке первого поиска брать из замеров темы производительности, не
   выдавать за новый замер.
