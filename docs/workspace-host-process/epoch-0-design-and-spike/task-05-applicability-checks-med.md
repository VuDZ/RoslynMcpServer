## Цель

До spike механизмов получить факты, от которых зависят выбор модели процессов
(U-C-07) и объём task-04:

1. переживает ли процесс, запущенный MCP-сервером, закрытие чата, Reload и
   аварийный выход реальных harness;
2. из чего состоит память наблюдаемой ситуации с ~20 MCP-процессами.

## Что сделать

1. **Жизнь процессов под harness.** Для доступных harness (Cursor, Claude Code,
   Codex) и ОС (Windows обязательна; Linux при наличии среды; macOS — если
   доступна) зафиксировать при закрытии чата, Reload окна, штатном выходе harness
   и его аварийном завершении:
   - что получает сам MCP-процесс: EOF stdin, сигнал или kill, время до завершения;
   - судьбу обычного дочернего процесса MCP;
   - судьбу отделённого процесса: на Windows — входит ли MCP в Job object, разрешён
     ли breakaway (`CREATE_BREAKAWAY_FROM_JOB`) и что происходит без него; на Unix —
     новая сессия (`setsid`) и группа процессов;
   - сколько MCP-процессов harness запускает на чат, окно и subagent.

   Вывод: достижима ли цель «пережить Reload» в модели ролей и возможен ли
   отдельный host без дополнительных действий пользователя.
2. **Разбор памяти наблюдаемой ситуации.** На компьютере владельца, где было
   ~20 MCP, для каждого процесса: workspace path, профиль и параметры load,
   память (private bytes и working set; метод указать), есть ли загруженный
   workspace, время простоя. Источники — список процессов и `logs/mcp-*.log`
   (`HarnessSessionId`, `load_workspace`). Сгруппировать: дубликаты одного workspace
   с одинаковыми параметрами (приближение ключа совместимости до U-C-01), разные
   проекты, процессы без workspace, простаивающие. Если ситуация недоступна,
   воспроизвести её и указать, чем воспроизведение отличается.
3. **Пустой процесс.** Тем же методом подтвердить наблюдение владельца (~18 МБ
   для MCP без workspace) и записать, какие сборки Roslyn, MSBuild и plugins
   загружены к этому моменту. Это исходная точка для proxy, который не грузит
   ничего лишнего.
