## Цель

На лёгком контроле без Roslyn проверить модели, оставленные владельцем после
task-05: переход proxy, а для модели ролей — также совмещение host/клиентского
фасада в первом MCP и передачу роли при смене его собственного проекта.
**Решение владельца, 2026-10-28:** проверяются общий механизм и выделенный host;
модель ролей отложена, её специфичные проверки (handoff из п. 4, promotion,
demotion) не выполняются ([README](../README.md#сравниваемые-модели-и-проверки-применимости-2026-10-23)).
Дубликаты сходятся к одному владельцу ключа, а десять прокси после
падения выполняют одну общую попытку восстановления и загрузки. Получить evidence для
[task-01](task-01-architecture-decision-hi.md), не выбирать production design заранее.

## Что проверить

1. **Discovery и совместимость.** Ключ включает пользователя, сборку, стартовый
   контекст и эффективный workspace descriptor. Chat/PID не входят. Host
   подтверждает дескриптор и новое поколение на handshake. Несовпадение не меняет
   его workspace. Stale запись не доказывает готовность; опрос всех процессов
   и P2P-протокол прокси не требуются.
2. **Запуск и владение.** В модели ролей один подходящий MCP получает роль host;
   в модели отдельного host один MCP инициирует его запуск, все MCP остаются
   proxy и ждут с deadline. Исключительное владение ключом установлено до имитации
   тяжёлой инициализации. Смерть кандидата или запускающего процесса до readiness
   не допускает двух владельцев/тяжёлых инициализаций и не оставляет ключ
   заблокированным навсегда.
   Для отдельного host проверить также его смерть до readiness и непрерывность
   исключительного владения на границе запускающий MCP → host. В модели ролей
   кандидат с несовместимым собственным workspace не вытесняет его ради чужого
   recovery. Пригодность кандидата и отсутствие кандидатов описать в отчёте.
   Механизм проверяется на доступных ОС; один контроль не подменяет другую модель.
   Первая проверяемая гипотеза — блокировка уровня ОС, которую ОС снимает при
   смерти процесса (файловый lock или named mutex), с поколением, записанным под
   ней. Собственный протокол координации — только если гипотеза не выполняет
   scope на какой-то ОС; причина фиксируется в отчёте.
3. **Одна загрузка.** Совместимые запросы присоединяются к одной попытке load,
   получают её успех/отказ. Отмена одного ожидающего не отменяет остальных.
   Для случая без оставшихся ожидающих выбрать и явно проверить политику.
4. **Переключение.** Два клиента используют A/проект1. Второй запрашивает проект2:
   подключается к существующему B либо участвует в согласованном создании B по
   проверяемой модели и после успешного load меняет привязку. При отказе B
   остаётся на живом A. Первый клиент продолжает
   работу с A, его счётчики/сессия не сбрасываются. Проверить выполняющийся
   запрос во время перехода и выбранный порядок его завершения/отмены.
   **Только модель ролей — handoff владельца:** чат1/`mcp1` сам держит проект1,
   `mcp2`/`mcp3` используют его как proxy. При запросе чат1 загрузить проект2
   `mcp1` сообщает release, прекращает admission по проекту1, согласует текущие
   вызовы и освобождает ключ.
   Один из оставшихся клиентов получает роль host проекта1 и делает одну
   загрузку; остальные ждут/переподключаются. Проверить, что `mcp1` может затем
   загрузить проект2, а чат2/чат3 не получают его результаты. Потерянное release,
   crash в середине handoff и отказ преемника проходят через recovery. Порядок
   и наблюдаемые ошибки/пауза фиксируются; миграция прогретого heap не обещается.
   **Только отдельный host:** переключить чат, первым инициировавший запуск A,
   на проект2. A сохраняет владение и обслуживает остальных без handoff и нового load.
5. **Crash recovery.** После убийства host десять живых прокси сходятся к одному
   новому владельцу/поколению и одной попытке load. MCP-сессии выживших процессов
   сохраняются; сессия чата в убитом MCP не объявляется пережившей его смерть. Ошибки
   прерванных вызовов не скрываются. Запоздавшие сообщения старого поколения
   не принимаются. Старое session activation/subscription state остаётся в фасаде.
6. **Повторный отказ.** Управляемый crash loop и отказ load завершаются в рамках
   бюджета ожидания/повторов с общей координацией задержек. Нет десяти автономных
   workspace и очереди полных загрузок от каждого клиента после одного отказа.
   Точные бюджеты и правила следующей явной попытки записать в отчёте.
7. **Replay.** Убить host после наблюдаемого побочного эффекта, но до ответа.
   Клиент получает неопределённый исход/ошибку, операция не исполняется снова.
   Внутренний redirect допускается только до начала исполнения; отдельно
   проверить, что его не видит агент как требование переподключиться.
8. **Жизненный цикл и publish.** Закрытие клиентского stdio при remote proxy:
   в модели ролей проверить политику сохранения host или release/handoff;
   для отдельного host — отключение любого proxy, включая инициатора запуска.
   В runner непосредственно вызвать EOF/разрыв подключения и завершение процесса;
   связь UI-чата с MCP не предполагается и матрица клиентов не требуется.
   Учитывать ограничения проверенных запусков из task-05. Принудительное убийство
   процесса не объявлять обычным отключением; тогда работает recovery.
   После последнего клиента — короткая пауза против гонки подключения, затем выход;
   новое подключение отменяет завершение. Host не переживает клиентов
   ([решение 2026-10-28](../README.md#зачем)): для отдельного host на Unix (`setsid`)
   проверить самостоятельный выход, когда все proxy ушли, в том числе по SIGKILL.
   Гонка с выходом не создаёт второго владельца. Проверить bootstrap/теневую
   копию для каждой проверяемой модели и обновление исходного publish; если гарантия
   недостижима в прототипе, явно зафиксировать fail/open question для task-01,
   не подменять проверяемую модель другой без решения владельца.
   Неполная копия не запускается.

## Матрица и evidence

- Холодный старт десяти прокси: не меньше 10 повторов; один владелец и одна
  тяжёлая инициализация/load на ключ. Разные ключи дают независимые host.
- То же после падения готового host; плановый release — только для модели ролей.
  Дополнительно смерть кандидата/запускающего процесса до readiness, а для
  отдельного host — его смерть до readiness; stale discovery, несовместимый
  descriptor, crash loop, отказ load и отсутствие пригодного кандидата в модели ролей.
- Переход A → готовый B и A → новый B, отказ B, progress/cancellation и
  `tools/list_changed`/подписки после перехода и recovery на обеих версиях MCP
  из task-03; агент не выполняет повторный initialize.
- Только модель ролей: смена проекта самим host-клиентом при двух remote proxy,
  потерянное уведомление, отказ преемника. Только отдельный host: смена проекта
  инициатором запуска без handoff и нового load прежнего workspace.
- Обе модели: закрытие stdio клиента, idle grace, race подключения с завершением,
  обновление source publish и cleanup по п. 8.
- Все сценарии имеют deadlines и завершают созданные процессы. Для проверки
  гонок используются управляемые барьеры/наблюдения, не только sleep.

`evidence/task-04-routing-and-recovery-spike.md`: pass/fail, команды runner,
проверенные ОС, ключи и поколения, число одновременных владельцев, тяжёлых
инициализаций и load attempts, события переходов, бюджеты, ограничения и
рекомендации для task-01. Непроверенные платформы перечисляются, а не получают pass.
