## Поправки к прежним утверждениям

1. **S09 / «BuildHost не меняется».** В baseline уже production fork netcore,
   а net472 остаётся из пакета. [BuildHostFork.targets](../../../../forks/roslyn-buildhost/build/BuildHostFork.targets)
   заменяет Content `BuildHost-netcore` для build/publish/pack и проверяет версию
   клиента 5.9.0. `Compile Remove=forks/**` исключает исходники из MCP assembly,
   но **не** исключает отдельную сборку fork из продукта. Для темы C прежняя
   граница означает «не дорабатывать этот BuildHost в рамках C», а не «его нет».
2. **S05–S07/S13.** К jsonc/env добавлены prewarm и BuildHost settings. Host
   identity должна учитывать весь server distribution, fork DLL/Contracts,
   runtimeconfig, SQLite native assets и plugins, а не apphost/version string.
   Совпадение load matcher не доказывает одинаковость settings разных клиентов.
   Exact key остаётся task-01. Передача settings через workspace properties,
   а не SetEnvironmentVariable, уже предотвращает их process-wide запись из load.
3. **S10/S31/S33 / demotion.** Clear теперь сначала отменяет и ограниченно ждёт
   prewarm. Static MEF/Locator, loaded analyzers/plugins и sanitized cache refs
   остаются; обещания полного unload по-прежнему нет. Плюс появились child worker
   threads и persistent storage. Таймаут prewarm не является successful drain.
4. **S25–S26/S32 / диагностика.** Добавились search exception windows, process
   GC counters, BuildHost trace files/stderr. Это не клиентские подписки MCP.
   Диагностика не является proof исполнения, завершения или совместимости.
5. **Таблица инструментов.** Имена/параметры и этапы CLI/test не изменились.
   У load добавлены settings→fork, missing loaders и background prewarm; у reset
   — stop/wait prewarm; у navigation — persistent indexes и diagnostics scope;
   у server info — новые merged/effective settings; у decompile — per-call refs.
   Ни один из этих этапов не разрешает загружать Roslyn/fork/plugins в pure proxy.

Не сняты N01–N08 исходного отчёта: descriptor, SDK seam, CLI/proof placement,
harness behavior, handoff/recovery, память, arbitrary plugins, bootstrap/ACL.
Дополнительные вопросы для task-01/02/04/05: политика разного prewarm/B worker
count у клиентов, допустимый drain при release, child ownership для reaper,
конкурентный cache access и повторный memory/latency baseline на 1.5.17.
Классификация не навязывает включение всех performance settings в один ключ.

## Влияние на порядок работ

Причина ждать окончания старой performance-ветки **снята для этой принятой
базы**: production-изменения уже в main и перенесены сюда. Продолжать task-05 и
standalone task-03 можно на одной зафиксированной версии. Перед дальнейшей
production-интеграцией заново проверяются эти дополнительные lifetime/settings
границы; старые memory/performance numbers не используются как новые измерения.
Это не выбор модели ролей/daemon и не снятие зависимостей task-01/task-04.
