## Цель

Проверить вне сервера лёгкий MCP-фасад: клиентская сессия живёт в прокси,
выполнение инструментов направляется host через локальный канал. Один host
разделяет состояние счётчика между несколькими прокси; MCP-состояние клиентов
изолировано. Получить рабочую основу для [task-04](task-04-proxy-routing-and-recovery-spike-hi.md)
и данные для design [task-01](task-01-architecture-decision-hi.md).

## Почему так

По [scope 2026-10-23](../README.md#согласованный-scope-2026-10-23) прокси должен
переключать host без нового MCP initialize от агента. Поэтому исходная гипотеза
прозрачной ретрансляции байтов снята. Named pipe / Unix domain socket сохранены;
HTTP не добавляется. Task-03 проверяет транспорт и границу сессий на фиксированном
host, task-04 — маршрутизацию, автозапуск, переключение и падение.

`ModelContextProtocol.Core` 2.2 (сборка из output решения, 2026-10-10) содержит
публичные `ModelContextProtocol.Server.StreamServerTransport` и
`ModelContextProtocol.Protocol.StreamClientTransport`. Это историческое наблюдение,
не готовая архитектура фасада. Сигнатуры, tool forwarding и возможность оставить
session state в прокси проверяются по установленной сборке (`explore_assembly`,
`decompile_type`), а не по памяти. Отдельно фиксируется, какие сервисы и сборки
реально загружаются в чистый proxy без роли host: второго Roslyn workspace в
нём быть не должно. Первый MCP может совмещать фасад своего чата с ролью host.

## Входы и границы

[Тема](../README.md), [карта эпохи](README.md), pitfalls 13, 26 и 27 из
`.cursor/rules/roslyn-mcp-pitfalls.mdc`. Перед первой C# правкой —
[AGENTS.md](../../../AGENTS.md) и полный [code style](../../code-style.md).

- Код — консольный проект `spikes/PipeRelay/PipeRelay.csproj`, `net10.0`, та же
  версия `ModelContextProtocol`, что в `RoslynMcpServer.csproj`. Один exe в двух
  ролях: `auto` (по умолчанию: локальный host либо proxy) и тестовый `host`.
  Host умеет одновременно обслуживать локального MCP-клиента и remote proxy;
  обязательный отдельный daemon не вводится. Историческое имя каталога PipeRelay
  сохраняется. Корневой csproj уже исключает
  `spikes\**`. В solution, CI и publish не входит; сервер не меняется,
  version bump и `CHANGELOG.md` не нужны.
- Три инструмента без Roslyn: `count` выполняется в host и меняет общий счётчик;
  `slow` выполняется в host N секунд с progress и отменой; `toggle` меняет
  видимость дополнительного инструмента только в MCP-сессии вызывающего прокси
  и вызывает `tools/list_changed`. Это проверка seam, а не реализация production
  `enable_tool_group`.
- Канал: `NamedPipeServerStream` / `NamedPipeClientStream` с
  `PipeOptions.CurrentUserOnly`. На Linux и macOS .NET реализует их через Unix
  domain socket; это проверяется, а не предполагается.
- Идентичность сборки учитывает exe и исполняемые DLL spike; несовместимые сборки
  не подключаются друг к другу. Точная production identity остаётся task-01.

## TDD

Сначала SDK-клиентом воспроизвести тест forwarding, изоляции сессий и обрыва
с ожидаемым red, затем реализовать минимальный фасад до green. Допустима
предварительная проверка API SDK. Red должен объясняться нарушением нужного
контракта, не ошибкой сборки/окружения. Команды и результаты до/после — в evidence.

## Что сделать

1. **Подключение.** Локальный handshake: версия внутреннего протокола,
   дескриптор совместимости, поколение host и harness id (pitfall 26). Не
   передавать/логировать командную строку родителя или environment целиком.
   Фрейминг, лимиты и deadlines внутренних сообщений фиксируются в отчёте.
2. **MCP-фасад.** Фасад держит negotiated protocol, tool collection и подписки;
   запросы/ответы host коррелируются с нужным клиентом и поколением. Подтвердить
   передачу progress и cancellation, изоляцию одинаковых request id клиентов.
3. **Совмещение ролей.** Тестовый runner выбирает один MCP host с локальным
   клиентом и подключает к нему proxy. Workspace key в этом тесте не меняется;
   координация promotion, handoff и idle — task-04.
4. **Обрыв.** Убитый host завершает ожидающие вызовы явной ошибкой без зависания
   и автоматического replay. Клиентская stdio MCP-сессия остаётся доступной
   для tools/list и последующего подключения; восстановление реализует task-04.

## Матрица проверок

Клиент — MCP C# SDK `McpClient` через `StdioClientTransport`, запускающий прокси.
Дополнительно, по возможности, — реальный harness с прокси в его MCP-конфигурации.

- Протоколы `2025-11-25` и `2026-07-28`: `tools/list`, `count`, `slow` с progress,
  отмена `slow` клиентом, `toggle` → клиент получает `tools/list_changed`
  (для `2026-07-28` — после `subscriptions/listen`).
- Две одновременные сессии: общий `count`; progress, отмена, `toggle`, подписки
  и одинаковые request id одной не затрагивают другую.
- Убитый host — шаг 4; операции не переигрываются, tools/list фасада отвечает.
- Канал недоступен другому пользователю ОС: проверка на Windows обязательна;
  Linux — если есть среда (WSL или CI); непроверенные платформы перечисляются.
- Накладные расходы: p50 и p95 времени 200 вызовов `count` напрямую по stdio
  (host в режиме stdio) и через фасад. Зафиксировать память прокси и host,
  метод измерения и факт отсутствия Roslyn workspace в прокси.
