# Task-01: выбор владельца O-02 — global retire

## Главное

- **Решение владельца, 2026-10-29:** reset бывает крайне редко, поэтому выбирается самый надёжный вариант, а не самый сложный. Shared `reset_workspace` при binding завершает общий host (global retire); следующий вызов любого клиента поднимает новый generation одной общей загрузкой.
- Soft reset (общая очистка с новой epoch в том же процессе) и локальный reset инициатора с уходом в private host отвергнуты. Restart-required analyzer, неисправимое admission и обычный reset закрываются одним путём.
- По вопросу владельца о соседях design задаёт отмену чистых read-стадий с просьбой повторить; начатые load/prepare/MSBuild и записи завершаются в drain budget с явным исходом либо неопределённостью эффектов. Metadata `readOnly` не доказывает чистоту стадии (исправление R10-F01); proxy CLI не прерывается, следующий вызов сообщает о перезапуске.
- Обновление graph после изменений на диске идёт не через reset: graph-stale load и epoch invalidation после package/rename от O-02 не зависят.
- Docs-only, база `ecb930b`, production 1.5.18. O-02/O-03/O-04/O-05 выбраны, O-01 открыт; task-01 in progress, task-06/task-02 planned. Реализация и production activation не разрешены.

Запись и уточнение правил — `claude-opus-5-5` (Claude Code) по обсуждению с владельцем.

## Основание: частота reset

| Источник | Период | Вызовы `reset_workspace` |
|---|---|---|
| Linux, Claude Code, `~/.cache/roslyn-mcp/logs` этой машины | 2026-10-21…28, 468 tool calls | 0 (явных `load_workspace` тоже 0; сервер 12 раз подсказал перезагрузку после нового `.cs`) |
| Windows, два компьютера основной разработки, проверка владельца | около двух недель назад | 4 на оба компьютера |

Подсчёт по Linux — `"name":"reset_workspace"` в строках `tools/call` лога сервера;
текстовые упоминания reset в подсказках инструментов не считались вызовами.
Данные Windows сообщены владельцем, сами логи в репозиторий не копировались.
Выборка мала и не является измерением для N=10 клиентов, но порядок частоты —
единицы вызовов за недели — снимает риск постоянного перезапуска общего host.

## Сравнение вариантов

| Вариант | Плюсы | Минусы | Итог |
|---|---|---|---|
| Global retire | Один путь; новый процесс снимает graph, CLR/analyzer history и сломанное admission; механизмы те же, что для crash host. | Соседи теряют прогрев, их вызовы прерываются. | **Выбран.** При наблюдаемой частоте цена приемлема. |
| Soft reset | Сохраняет процесс; одна общая загрузка. | Не сохраняет прогрев graph; restart-required всё равно требует retire — два пути. | Отвергнут как более сложный без выигрыша при редком reset. |
| Локальный reset в private host | Не трогает соседей. | Плодит workspace; соседи остаются на устаревшем graph; явный private host уже даёт `forceFresh` O-05. | Отвергнут. |

## Что получают соседи

Агент узнаёт о событиях только из ответа на свой вызов: server notifications модели
в harness не показываются. Поэтому в [design §7](../design.md#7-lifecycle-load-attempts-и-восстановление--u-c-03u-c-04u-c-06)
контракт задан текстами ответов: чистая read-стадия после load/prepare — отмена и
просьба повторить. Отсутствие эффектов утверждается только для доказанно чистой
стадии без предшествовавших effectful стадий вызова. `readOnly` из каталога этого не
доказывает: explicit/lazy load может создавать binlog и запускать MSBuild tasks/generators.
Load/prepare/MSBuild и принятая запись завершаются в drain budget с фактическим исходом;
при неизвестном исходе — явная неопределённость эффектов и просьба проверить результат;
proxy CLI — фактический результат без confirmation; следующий вызов — однократное
уведомление о перезапуске и времени перезагрузки. Автоматический повтор read-only
в proxy отвергнут: холодная загрузка внутри одного вызова может упереться в timeout harness.

Изменены §7 (reset, budgets), «Главное», таблицы §1/§5/§10, сценарии 7, 8, 20, 24 и
O-02 в §12; task-02 сценарий 5. Пересмотр — если reset станет частым.
