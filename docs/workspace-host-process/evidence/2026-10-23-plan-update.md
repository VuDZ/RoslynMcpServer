## Зафиксировано

- Первый MCP может быть host своего workspace и обслуживать remote proxy;
  следующий совместимый MCP работает как лёгкий proxy со своей MCP-сессией.
  Обязательный отдельный daemon не предполагается. Числа 20 MCP / 10–20 ГБ — пример
  владельца, не измеренный результат. Замер памяти добавлен в task-02.
- Поиск по дескриптору/ключу с подтверждением совместимости и поколения.
  Конкретные env/config/defaults и механизм межпроцессного владения выбирает task-01.
- При load другого проекта proxy-клиентом переходит только запросивший прокси; привязка
  меняется после успешной загрузки, при отказе сохраняется прежний живой host.
- Уточнение владельца в ходе обновления: `mcp1` сам держит проект1 и обслуживает
  `mcp2`/`mcp3`. При загрузке проекта2 в чат1 нужен release/handoff проекта1:
  один из оставшихся proxy становится новым host проекта1. Это заменяет
  первоначально внесённое ошибочное допущение «host всегда отдельный и фиксированный».
  Другие клиенты не переключаются на проект2 вслед за владельцем процесса.
- MCP-фасад заменяет гипотезу прозрачного побайтового моста; progress,
  cancellation, подписки и runtime activation `enable_tool_group` изолированы
  по клиенту и сохраняются при переключении.
- Один владелец ключа до тяжёлой инициализации и одна разделяемая попытка load;
  promotion одного из proxy координируется по ключу, без P2P-сети. Плановая
  передача не переносит RAM: новый владелец делает одну холодную загрузку.
- Падение, смерть кандидата до readiness, stale discovery, поколения, crash loop,
  budgets/backoff и отсутствие автоматического replay включены в spike.
  Массовый autonomous fallback запрещён; загрузку выполняет только победитель promotion.
- RAM погибшего процесса не переносится. Смена cwd host, миграция прогретого
  Roslyn и ветвление workspace внутри процесса остаются вне scope. Bootstrap,
  shadow copy, host→proxy CLR lifetime и отказ handoff требуют решения task-01.
