# Task-01: выбор владельца O-06 — происхождение исполняемого кода

## Главное

- **Решение владельца, 2026-10-29:** отдельного prelaunch proof и нового verified bootstrap нет. Смешанную сборку под живым proxy исключают действующие схемы развёртывания: на Windows O-03 (publish сначала останавливает MCP и отказывает, если они не завершились), на Linux — snapshot launcher, который после публикации не меняется.
- Совместимость proxy и host проверяется по identity из памяти процесса: версия внутреннего протокола, hash каталога инструментов со schemas, MVID загруженной сборки сервера. Расхождение — отказ attach с указанием перезапустить proxy. Disk hash после старта как identity кода не используется.
- Host по-прежнему работает из своего образа в StorageRoot: hash при копировании, сверка до запуска. Reuse snapshot launcher как образа host отклонён аудитом task-06.
- Остаточный риск принят: ручная подмена файлов под живым proxy может дать смешанную сборку, как и в ordinary-режиме сегодня.
- Попутно уточнён §3: Windows-корни создаются с защищённым DACL только владельца, без наследования.
- Docs-only, база `30989ca`, production 1.5.18. O-02…O-06 выбраны, O-01 открыт; task-01 in progress, task-02 planned.

Запись — `claude-opus-5-5` (Claude Code) по обсуждению с владельцем.

## Почему вопрос возник

R6-N01 (task-01, раунд 6) потребовал для shared доказанную неизменяемость bundle
proxy от момента до запуска процесса; без неё — `deployment-unverified` и отказ shared.
Task-06 показал, что ни одна реальная схема владельца этого не даёт:

- Windows: MCP Codex исполняются прямо из каталога in-place publish
  `bin\Release\net10.0\win-x64\publish` ([данные](../epoch-0-design-and-spike/evidence/task-06-data/windows-preflight-facts.json)).
- Linux: snapshot launcher не прошёл аудит — identity по size/mtime двух файлов,
  манифеста нет, неизменяемость по соглашению
  ([аудит](../epoch-0-design-and-spike/evidence/task-06-environment-and-deployment-preflight.md#7-аудит-launcher)).

Новый launcher или bootstrap §9 design исключал. Требование было невыполнимо по
построению: task-02 гарантированно получил бы no-go, и это была скрытая цена O-01.

## Варианты

| Вариант | Плюсы | Минусы | Итог |
|---|---|---|---|
| Действующие схемы развёртывания + identity из памяти | Без нового компонента; тот же уровень защиты, что у ordinary сегодня; проверка совместимости дешёвая | Не доказывает отсутствие любых различий кода при нарушенной схеме | **Выбран** |
| Verified bootstrap на обеих ОС: неизменяемый образ и lease до запуска процесса | Формально строгое происхождение кода | Новый компонент развёртывания на двух ОС ради уже закрытого риска | Отвергнут |

## Windows DACL

Факты task-06: родительский `LocalAppData` наследует ACE `CodexSandboxUsers` (чтение и
исполнение) и capability SID песочницы Codex с FullControl. Каталог, созданный с ACL по
умолчанию, унаследует их. Процесс в песочнице получил бы запись в образ host, который
исполняется вне песочницы от имени пользователя: подмена ещё не загруженной DLL дала бы
исполнение кода с полными правами. Поэтому корень создаётся с защищённым DACL только
владельца, а существующий корень с любым чужим ACE отклоняется. Проверка — task-02.
