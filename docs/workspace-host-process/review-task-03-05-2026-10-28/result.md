## Вердикт

Обе задачи можно использовать: данные собраны аккуратно, ограничения названы,
цифры сходятся с исходными JSON. Но **два вывода сформулированы так, что
владелец примет решение не на тех фактах**, и их нужно поправить до выбора моделей:

1. Вывод task-05 «reset не возвращает память» получен без единой сборки мусора
   после reset. На 1.5.18 reset вместе с `GCCollectionMode.Aggressive` возвращает
   около 2/3 прироста памяти от загрузки (F-01). Idle unload недооценён.
2. Task-03 намерил proxy размером с пустой текущий сервер, но не сопоставил это
   с task-05. Требование «чистый proxy без MSBuild/Roslyn/plugins» по памяти
   почти ничего не даёт (F-05). Самая сложная часть модели ролей переоценена.

Обязательной рекомендации task-05 «какие модели оставить для task-04/task-01» нет (F-02).

## Главное

- **Idle unload работает, если после reset вызвать GC.** Linux, 1.5.18, решение
  из пяти проектов. Server GC: anon RSS 163 MiB после загрузки, через 30 с после
  reset — 163 (gen2 не было ни одной), после forced compacting GC — 128, после
  `Aggressive` — **63**; пустой процесс — 12–14. Workstation: 134 → 100 → **60**.
  Живой managed heap после reset и GC — 20–25 MiB против 1,5–2,7 у пустого: часть
  состояния переживает reset. [Данные](gc-probe-linux.json), n=1 на режим.
- **Proxy по памяти равен пустому серверу.** SDK-proxy task-03 на Windows:
  19,9–21,9 MiB private / 53,3–55,6 MiB WS. Пустой 1.5.18 из task-05: 18,4 / 61,0
  (Workstation) и 23,3 / 59,8 (Server). Сборки Roslyn — mapped images, общие
  между процессами; приватной памяти они почти не добавляют. Bootstrap seam
  «proxy не грузит лишнего» экономит единицы MiB на процесс.
- **Накопление MCP в Codex — проблема простаивающих процессов.** Сабагенты
  завершаются, а их MCP с загруженным workspace остаются жить (task-05). Idle unload
  бьёт ровно в это и не зависит от модели; shared-модели нужны только для
  одновременно активных дубликатов.
- **«Пережить Reload» в Codex недостижимо ни для одной модели.** Reload в production
  Codex нет, а выход app-server убивает весь Job, включая detached child.
- Найденные дефекты spike (C03-01, C03-02) исправлены и отслежены. У C03-01 причина
  частично установлена: SDK шлёт отмену сам, но fire-and-forget (F-08).
- Для task-04 появились три не учтённых входа: TMPDIR в пути Unix socket (F-07),
  непроверенная на Linux проверка UID через `CurrentUserOnly` (F-06) и параметры
  стенда, которые нельзя переносить (F-09).

## Рекомендации владельцу

1. **Idle unload — первым и отдельно от shared-режима:** выгрузка workspace
   (reset + `GCCollectionMode.Aggressive`) после N минут простоя. Это нулевой
   вариант с улучшением, он нужен любой модели как политика idle host и прямо
   решает наблюдаемое удержание сабагентских MCP в Codex. Перед этим нужен
   короткий замер на Windows и на большом решении, плюс разбор остатка heap
   после reset.
2. **Решить по требованию чистого proxy (F-05).** Если его снять, модель ролей
   заметно дешевеет: proxy — тот же процесс без workspace.
3. **Снять для Codex цель «пережить Reload»** как недостижимую в любой модели.
4. Task-04 запускать после выбора моделей, передав ему F-06, F-07 и F-09.
