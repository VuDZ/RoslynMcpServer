## Зачем

После правки агент обычно запускает либо один тест, который сам вспомнил, либо весь
suite. Полный main suite идёт минуты, поэтому в рабочем цикле агент его избегает и
пропускает косвенные поломки. Транзитивное замыкание «кто зависит от этого метода»
агент вручную через `get_call_graph` и `find_symbol_references` строит плохо: берёт
один-два уровня и останавливается.

Rapid TIA (test impact analysis) — инструмент, который по изменениям с момента загрузки
solution оценивает, какие тесты стоит запустить, и отдаёт готовый фильтр для
`run_test_by_filter` или по флагу сам запускает этот набор одним вызовом. Ещё одна польза — память сессии: после сжатия контекста агент
теряет список своих правок, а сервер его хранит.

Инструмент **не гарантирует точность**. Он может пропустить тест или включить лишний.
Полный прогон и CI остаются обязательными; ответ инструмента должен это поддерживать,
а не размывать.

## Что программа не делает

- Не заменяет финальную валидацию по `AGENTS.md` и не меняет её правила.
- Не смотрит изменения до загрузки solution: на момент загрузки всё считается исправным.
  Сравнение с git HEAD остаётся у `get_changed_files`.
- Не заглядывает внутрь NuGet-сборок и другого метаданных-кода.
- Не собирает покрытие во время выполнения (динамический TIA отклонён: требует
  прогона с покрытием на baseline).
- Не решает, что агенту запускать перед коммитом.

## Дизайн

### Baseline и обнаружение изменений

- Старый `Solution` целиком не хранится: это дорого по памяти (см. 1.5.18, освобождение
  предыдущего solution). Хранится лёгкий снимок: путь → checksum текста; хеш содержимого
  файла вне членов (директивы `using`, alias, `global using`, объявления namespace,
  атрибуты сборки); для каждого члена типа — синтаксический ключ и хеш его синтаксиса.
- **Синтаксический ключ члена:** вид члена; путь объемлющих типов с generic-арностью
  каждого; имя; generic-арность члена; синтаксис параметров; интерфейс явной реализации.
  Объявления `partial`-члена в разных файлах хранятся все, а не затирают друг друга:
  член изменён, если изменилось любое из них.
- Текущее состояние сравнивается со снимком. Правки через MCP и правки на диске мимо MCP
  (их подтягивает disk watcher, [WorkspaceDocumentDiskSync](../../Services/Workspace/WorkspaceDocumentDiskSync.cs))
  обрабатываются одинаково.
- Изменённые члены определяются **синтаксически**, без semantic model: это работает и на
  некомпилируемом промежуточном коде. Синтаксический ключ сопоставляется с узлом графа
  через факты: при извлечении фактов ключ записывается рядом с идентификатором узла
  (раздел «Хранение»), идентификатор из исходного текста заново не вычисляется. Пока
  фактов нет, ответ проектный. Ключ, который не сопоставился с узлом однозначно, даёт
  все узлы файла.
- Правка только комментариев и пробелов — не изменение. Правка, которую затем вернули
  к тексту baseline, — не изменение. Смысл директив препроцессора при отбрасывании
  trivia сохраняется.
- `load_workspace` / `reset_workspace` того же solution в том же процессе baseline **не
  сбрасывают**: иначе перезагрузка после правки csproj стирает историю изменений. Новый
  baseline — при загрузке другого solution или перезапуске сервера. Отдельной операции
  сброса нет (R-03, R-13).

**Фиксация baseline текстов.** `Solution` неизменяем, но тексты документов в нём
загружаются лениво: `FileTextLoader` читает диск при первом обращении, и если файл к этому
моменту уже изменён, прочитается правка, а не baseline. Поэтому:

- снимок хешей — первый шаг фоновой задачи, до извлечения фактов; он только читает и
  хеширует тексты, без компиляции, и не ждёт прогрева поиска;
- путь, для которого событие записи (MCP или disk watcher) пришло раньше, чем записан
  его хеш baseline, получает состояние **baseline неизвестен**;
- то же состояние получает путь, у которого при чтении снимком время последней записи
  файла позже момента публикации загруженного solution;
- изменение пути с неизвестным baseline обрабатывается на уровне 0 и попадает в
  «Not covered»; такой путь никогда не считается неизменённым;
- reset или reload до завершения снимка сохраняет уже записанные хеши; оставшиеся пути
  получают состояние «baseline неизвестен».

### Уровень 0: по проектам

Изменённые пути → затронутые проекты → тестовые проекты, транзитивно зависящие от них
(`ProjectDependencyGraph`). Уже он даёт ответ «запусти эти два тестовых проекта».
Отображение пути на проекты:

- **C#-документ solution** — проекты, в которые он входит (документ бывает в нескольких
  проектах: multi-targeting, linked files).
- **Новый `.cs`, которого ещё нет в workspace.** Disk watcher не добавляет его в solution
  до reload. Проект — тот, в каталоге которого лежит файл (ближайший); ответ советует
  reload, чтобы новые тесты стали видны поимённо.
- **Файл графа проектов** (`.csproj`, `.sln`/`.slnx`, `Directory.Build.props`/`.targets`,
  `Directory.Packages.props`, `global.json`). Watcher помечает граф проектов устаревшим,
  а `ProjectDependencyGraph` до reload остаётся прежним. Поэтому до reload ответ — **все
  тестовые проекты** загруженного solution, а строка состояния говорит, что граф проектов
  устарел. После reload — обычное отображение по уже обновлённому графу.
- **Прочий не-C# путь** (json, resx, данные тестов). Проекты берутся из карты входов
  workspace ([WorkspaceInputMapBuilder](../../Services/Workspace/WorkspaceInputMapBuilder.cs)).
  Путь, который карта ни к одному проекту не относит, не расширяет ни один проект и
  попадает в «Not covered» с именем файла: неизвестный путь не доказывает, что он ни на
  что не влияет, и агент видит это явно.
- Restore-входы (`project.assets.json`, `packages.lock.json`, `nuget.config`) — слепая зона
  уровня 0, записанная в описании инструмента.

### Состав ответа

Ответ — объединение трёх частей:

1. **Новые и изменённые тесты сами.** Тестовые методы, которых нет в baseline или
   которые изменены относительно него (включая метод, ставший тестовым, и
   переименованный тест), выделяются по текущему синтаксису **до** любой отсечки по
   графу и включаются напрямую. Корни тестового класса (конструктор, setup, фикстуры),
   изменённые или новые, включают все тесты класса.
2. **Тесты, чьи битсеты содержат изменённый или удалённый узел.** Узлы удалённого
   члена или файла берутся из baseline, а не из текущего solution. Файл без узлов,
   достижимых из тестов, отбрасывается только на этом шаге и только если части 1 и 3
   его не затрагивают.
3. **Проектное расширение (уровень 0)** — только в перечисленных случаях: не-C# путь,
   путь с неизвестным baseline, файл, который не разбирается до членов, изменение
   `global using` и прочие случаи R-14, граф уровня 1 ещё не готов или устарел.

**Проектное расширение проекта P** — одно определение для всего документа: сам P, если в
нём есть тесты, плюс все тестовые проекты, которые от P зависят **транзитивно**
(`ProjectDependencyGraph.GetProjectsThatTransitivelyDependOnThisProject`). Тестовый
проект, который видит P только через промежуточный проект (Library → App → App.Tests),
входит. Везде, где ниже сказано «уровень проекта» или «проект и зависимые тестовые
проекты», имеется в виду это замыкание.

**Без графа (эпоха 1 и пока граф не готов).** Часть 2 пуста, поэтому любое изменение,
добавление или удаление обычного члена C# даёт проектное расширение его проекта. Одно
исключение сужает ответ: если в тестовом проекте изменены **только** тестовые методы и
собственные корни тестовых классов (конструктор, инициализаторы полей, setup и teardown
самого класса), **эти изменения** проектного расширения тестового проекта не дают —
по ним в ответ входят только эти тесты (часть 1): изменённый член исполняют только
они. Исключение гасит лишь расширение от изменений внутри самого тестового проекта.
Если тот же тестовый проект попадает в проектное расширение другого изменённого
проекта (например, вместе с тестом изменён метод библиотеки, от которой он зависит),
он входит целиком: ответ — объединение частей. Изменение типа фикстуры
(`IClassFixture<T>`, `ICollectionFixture<T>`), вспомогательного члена или любого другого
нетестового члена тестового проекта — проектное расширение: такой член может вызываться
из многих классов, а без графа это не проверить.

Уровень 1 сужает ответ по изменённым членам C#, но не заменяет проектное расширение
там, где оно предписано. Термины: «откат на CHA» — только переход диспетчеризации к
CHA по R-05; правка, вернувшая текст baseline, так не называется; переход ответа к более
грубому уровню (файл, проект) называется расширением или деградацией.

### Уровень 1: прямой граф от тестов

**Почему граф на baseline достаточен.** Если правка добавила новый вызов в метод M, M
изменён, и все тесты, достигавшие M в baseline, попадут в ответ. Новые методы вызываются
только из изменённых, новые тесты включаются сами (часть 1 «Состава ответа»). Поэтому
граф после правок не перестраивается; исключения перечислены в разделе «Изменения
связывания».

**Узлы** — члены типов из исходников solution. Гранулярность — член, а не тип: тип вроде
`SolutionManager` достижим почти из любого теста. Уровень типа — только запасной.

**Корни тестового класса:**

- тестовые методы (распознаются [TestAttributeMatcher](../../Services/Testing/TestAttributeMatcher.cs));
- конструкторы класса и базовых классов, инициализаторы полей;
- xUnit `IAsyncLifetime`, `Dispose`/`DisposeAsync` тестового класса;
- xUnit `IClassFixture<T>` на самом тестовом классе — тип фикстуры `T`;
- xUnit collection fixture: `[Collection("имя")]` на тестовом классе →
  `[CollectionDefinition("имя")]` с тем же именем → его `ICollectionFixture<T>` → тип
  фикстуры `T`. Определение не найдено — запись ограничения, а диспетчеризация в
  этом классе без найденных реализаций идёт по CHA;
- у типа фикстуры `T` (class и collection) корни те же, что у жизненного цикла тестового
  класса: конструкторы, инициализаторы полей, `IAsyncLifetime.InitializeAsync`/`DisposeAsync`,
  `Dispose`. Асинхронная подготовка фикстуры — обычное место, где создаётся реализация;
- NUnit `[SetUp]`, `[TearDown]`, `[OneTimeSetUp]`, `[OneTimeTearDown]`;
- MSTest `[TestInitialize]`, `[TestCleanup]`, `[ClassInitialize]`, `[ClassCleanup]`;
- источники данных `MemberData`, `ClassData`, `TestCaseSource`, `DynamicData`.

Тесты, объявленные в абстрактном базовом классе, раскрываются в конкретные классы-наследники:
иначе фильтр их не запустит.

**Ребра:**

- вызовы, get/set свойств, индексаторы, операторы, неявные преобразования, события;
- инициализаторы полей и статические конструкторы — к конструкторам и к первому обращению к типу;
- чтения `const` и значения параметров по умолчанию (встраиваются в место использования);
- тела лямбд, анонимных методов и локальных функций относятся к объемлющему методу;
  method group — ребро к методу;
- синтезированные члены record — к объявлению record.

Опыт обхода делегатов есть в [ReachabilityAnalysis](../../RoslynMcpServer.Tests/SourceStructure/ReachabilityAnalysis.cs)
(тестовый код SourceStructure). Он сознательно не раскрывает виртуальные вызовы, поэтому
обход для TIA — отдельный код; логику по делегатам можно заимствовать.

**Виртуальные и интерфейсные вызовы (R-05).** Для каждого тестового класса — неподвижная
точка: достижимые методы дают созданные типы, созданные типы дают цели виртуальных вызовов,
цели дают новые достижимые методы. Созданием типа считаются `new T`, `typeof(T)` и
generic-аргументы (например `AddSingleton<IFoo, Foo>()`).

- Мок интерфейса (`Mock<IFoo>`, `Substitute.For<IFoo>()`) считается созданием
  **реализации без тела**: в production-код вызов не идёт, и откат на CHA для `IFoo` в
  этом контексте не срабатывает. `Mock<Foo>` от класса считается созданием `Foo`
  (`CallBase`). Лямбды в `Setup(...).Callback(...)` — обычные тела. Библиотеки моков
  распознаются по полному имени типа (`Moq.Mock<T>`, `NSubstitute.Substitute`,
  `FakeItEasy.A`).
- Нет ни одной созданной реализации, включая моки, — CHA плюс ограничение. Так
  покрываются DI-сканирование сборок, `Activator.CreateInstance` и реализации за
  границей графа.
- `typeof(T)` считается созданием сознательно: так выглядят DI-регистрации
  `AddSingleton(typeof(IFoo), typeof(Foo))`. Цена принята: если в контексте класса
  есть `typeof` одной реализации, а другая создаётся через `Activator` по строке или
  по типу из данных, CHA для интерфейса не включается и вторая реализация не видна.
  Вызов `Activator` при этом остаётся записанным ограничением.
- В битсет достижимых узлов попадает и **объявленная цель** виртуального вызова
  (член интерфейса или базового класса), а не только выбранные RTA реализации. Иначе
  пометка базового члена из правил связывания ниже не нашла бы ни одного теста.

**Изменения связывания (R-14).** Эти правки меняют поведение неизменённого кода. Граф
baseline хранит ребро к прежней цели вызова, поэтому правило должно пометить именно
прежнюю цель или расширить ответ до файла или проекта. Где точное правило этого не
гарантирует, выбрано расширение:

- новый метод в обычном типе (перегрузка, сокрытие) — изменёнными считаются одноимённые
  члены типа и его иерархии и **все одноимённые extension-методы в исходниках solution**,
  без ограничения видимостью: вытесненный extension бывает объявлен в проекте-потребителе
  (например в тестовом проекте), который из проекта типа не виден. Прежняя цель из
  метаданных (extension из NuGet или BCL) узлом не является и в битсетах её нет (R-02),
  поэтому условие проверяется по **ребрам фактов**: у ребра вызова к символу из
  метаданных хранится ключ листа — идентификатор документации без проекта solution.
  Проектное расширение проекта типа — только если есть ребро вызова, у которого
  baseline-цель — одноимённый extension из метаданных, а получатель — новый тип или
  его наследник. Одноимённый лист где-то ещё в solution (другие тесты вызывают
  `Enumerable.Count`) расширения не даёт. Проектное расширение на любой новый метод не
  выбрано: добавление метода — самая частая правка, и ответ огрубел бы почти всегда;
- новый extension-метод — проектное расширение его проекта (определение в «Составе
  ответа»). Точечное правило здесь не работает: прежняя цель вызова обычно
  лежит выше по ссылкам — в проекте-библиотеке, на который ссылается проект нового
  метода, или в NuGet (лист графа), — и пометка одноимённых членов её не находит.
  Иерархия статического класса тоже ничего не даёт: прежняя цель в другом классе;
- новый или изменённый пользовательский оператор или преобразование — проектное
  расширение его проекта: в месте использования `a + b` нет имени, по которому можно
  найти вызывающих;
- изменение содержимого файла вне членов (`using`, `using static`, alias, namespace) —
  все узлы этого файла; изменение `global using` — уровень проекта;
- изменение атрибутов сборки или модуля (`[assembly: …]`, `[module: …]`, например
  `InternalsVisibleTo`) — проектное расширение проекта. Узлы файла здесь не годятся:
  в отдельном `AssemblyInfo.cs` их может не быть вовсе, а атрибут меняет доступность и
  связывание во всех проектах, которые видят эту сборку;
- новый override или новая реализация интерфейса — изменённым считается базовый член
  (он есть в битсетах как объявленная цель);
- изменение атрибутов, `partial`, базового типа или списка интерфейсов — изменённым считается весь тип.

Стенд полноты считает, как часто срабатывает расширение и какую долю suite оно
добавляет; по этому замеру правила можно сузить.

**Хранение: факты по документам и выводимая достижимость.** Граф делится на две части:

- **Факты** — то, что извлекается из одного документа его semantic model: для каждого
  объявленного в нём члена — связанные вызовы и обращения, точки виртуальных вызовов,
  созданные типы, чтения `const`; для каждого объявленного типа — базовый тип, интерфейсы,
  overrides; корни тестов. Узел идентифицируется парой «проект + `ISymbol.GetDocumentationCommentId()`»:
  идентификатор документации публичный и стабильный между процессами, но сам по себе
  неуникален — один документ входит в несколько проектов Roslyn при multi-targeting и
  linked files, а одинаковое полное имя бывает в разных сборках. Проект задаётся
  стабильным между процессами ключом экземпляра — путь проекта, конфигурация, платформа,
  target framework, как
  [SnapshotProjectKey](../../Services/Workspace/StateCache/Models/SnapshotProjectKey.cs),
  а не `ProjectId`. Факты документа хранятся отдельно для каждого проекта, в который он
  входит. Ребро к символу другого проекта разрешается по сборке, из которой символ пришёл.
  Ребро к символу из метаданных (NuGet, BCL) хранит ключ листа — идентификатор
  документации без проекта solution; лист не узел и в битсеты не входит, ключ нужен
  только правилам связывания R-14.
  Для каждого узла хранится и синтаксический ключ (раздел «Baseline и обнаружение
  изменений»), для `partial` — все его объявления. Лямбды и локальные
  функции свёрнуты в объемлющий член, поэтому своих идентификаторов не требуют.
- **Достижимость** — выводится из фактов в памяти: RTA по тестовому классу и битсеты
  достижимых узлов для каждого тестового класса и метода. Пример объёма: 20k узлов × 3k
  тестов ≈ 7.5 МБ.

Запрос: изменённые узлы → тесты, чьи битсеты их содержат, плюс кратчайшая цепочка «почему».
Факты локальны для документа: это делает возможной частичную актуализацию сохранённого
графа (раздел «Построение и сохранение графа»).

### Построение и сохранение графа (R-08, R-09)

Синхронное построение при загрузке отклонено: это semantic model всего достижимого из
тестов кода, порядка полной компиляции solution, а загрузка и так главная боль
([workspace-load-performance](../workspace-load-performance/README.md)). Ленивое
построение по первому запросу отклонено: запрос ждал бы десятки секунд и упирался бы в
таймауты MCP-клиентов.

**Фон после публикации загруженного solution**, по образцу
[SearchIndexPrewarm](../../Services/Navigation/SearchIndexPrewarm.cs):

- Фоновая задача захватывает опубликованный `Solution` в момент загрузки. `Solution`
  неизменяем, но тексты в нём читаются лениво, поэтому граф соответствует baseline
  только для путей, чей baseline зафиксирован снимком (раздел «Фиксация baseline
  текстов»); для остальных действует состояние «baseline неизвестен». Захваченный
  `Solution` держится только до конца работы.
- Блокировка workspace берётся только на захват `Solution` при старте.
- Снимок хешей стартует сразу. Извлечение фактов — после прогрева индексов поиска (если
  прогрев выключен — сразу), а не параллельно с ним, с ограниченным
  параллелизмом по проектам, чтобы не отнимать CPU у инструментов. Компиляции, которые
  создаёт извлечение фактов, Roslyn переиспользует в текущем solution для неизменённых
  проектов; это может ускорить навигацию, но удерживает память — нужен замер.
- Ошибки и отмена — одна строка лога, как у прогрева; инструмент тогда работает на уровне 0.
- **Поколение загрузки.** Каждая загрузка получает номер поколения, задача знает свой.
  Подменить граф может только задача текущего поколения; задача, завершившаяся после
  следующей загрузки, результат отбрасывает. Так граф одного solution не попадает в
  ответы по другому.
- **Reset во время извлечения (R-15).** `reset_workspace` и свежая загрузка отменяют
  задачу и не ждут её: компиляция проекта может не заметить отмену быстро. Задача
  проверяет отмену между документами и проектами. Пока она не завершилась, захваченный
  `Solution` в памяти, и reset пишет это в лог, а не обещает освобождение. Это
  сознательное ослабление гарантии 1.5.18 только на время фоновой компиляции: reset
  редок.

**Сохранённый граф (R-09).** На диск пишутся факты по документам, не достижимость:
достижимость дешево выводится в памяти, а факты можно обновлять по одному документу.

Содержимое файла:

- версия формата, версия сервера, версия Roslyn; несовпадение — файл не используется;
- для каждого проекта — хеш того, что влияет на связывание: путь, target framework,
  символы препроцессора, compilation options, список ссылок (пути и их хеши или версии);
- для каждого документа — хеш содержимого, его факты, **хеш поверхности объявлений**
  (сигнатуры членов, иерархия типов, атрибуты) и компактный набор используемых имён
  (например фильтр Блума по идентификаторам).

Запись атомарная: временный файл и переименование. Повреждённый файл отбрасывается.
Если тот же solution открыт двумя серверами, побеждает последняя запись. Пример объёма:
20k членов по ~10 ребер — единицы мегабайт.

**Последовательность после загрузки:**

1. Читается сохранённый граф (если есть и версии совпадают). По хешам содержимого
   определяются устаревшие документы: изменённые, новые, удалённые, а также все документы
   проектов, чей хеш связывания изменился.
2. Достижимость выводится из сохранённых фактов, инструмент сразу отвечает по ним.
3. В фоне актуализация: заново извлекаются факты устаревших документов. Если у устаревшего
   документа изменилась поверхность объявлений, заново извлекаются и документы, в наборе
   имён которых есть имена изменённых объявлений: новая перегрузка или сменившаяся
   сигнатура меняет связывание кода, текст которого не менялся. Набор имён не видит
   операторы, преобразования, директивы `using` и атрибуты сборки: изменение
   `global using`, оператора, преобразования или атрибута сборки делает устаревшими все
   документы самого проекта и **всех** проектов, которые от него транзитивно зависят,
   включая промежуточные без тестов (App в цепочке Library → App → App.Tests): вызов,
   который перепривязался, может лежать именно там. Это множество шире проектного
   расширения R-14: расширение ответа оставляет из него только тестовые проекты,
   каскад фактов не фильтрует.
4. Достижимость пересчитывается, граф подменяется атомарно, файл перезаписывается.
5. Нет сохранённого графа или сработала политика полной перестройки (O-06) — полное
   извлечение фактов в фоне. Полная перестройка нужна, потому что каскад по набору имён
   приблизителен и без неё ошибки накапливаются между сессиями.

Частичная актуализация компилирует только проекты устаревших документов (зависимости
дают декларации, тела не связываются) и связывает только тела устаревших документов.
После обычного `git pull` на десятки файлов это секунды, а не время компиляции solution.

**Ответ на сохранённом графе до актуализации.** Устаревший документ портит не только свои
члены, но и пути через них: его старые факты могут не содержать ребра к изменённому члену.
Поэтому до актуализации:

- изменённые члены в устаревших документах обрабатываются на уровне файла и проекта, а не
  по ребрам из старых фактов;
- исходящие ребра членов устаревших документов считаются неизвестными: тест, достигающий
  такого члена, добавляется, если проект изменённого члена **равен проекту устаревшего
  документа или входит в его транзитивные зависимости**. Равенство названо отдельно:
  `ProjectDependencyGraph.GetProjectsThatThisProjectTransitivelyDependsOn` сам проект не
  возвращает, а фабрика и её реализации чаще всего лежат в одном проекте.

Ответ называет состояние и число устаревших документов.

**Запрос никогда не ждёт.** Строка состояния в ответе:

- `Call graph: ready.`
- `Call graph: cached, refreshing (37 stale documents); stale parts are file- and project-level.`
- `Call graph: building (12/40 projects); project-level result only.`
- `Call graph: failed: <reason>; project-level result only.`

Агент получает полезный ответ в любой момент и может повторить запрос позже.

**Reload или reset в сессии.** Baseline изменений (R-03) сохраняется. Если граф уже
готов, он остаётся: он соответствует baseline. Если фоновая работа не закончена, она
отменяется и продолжается актуализацией по новому загруженному solution, а ответ помечает
`graph built after edits`. На любом пути baseline от корня теста до первого изменённого
члена все члены не менялись, и их ребра те же, поэтому этот изменённый член остаётся
достижимым. Но такой граф остаётся графом сессии до перезапуска: следующий reload его не
заменит, baseline-solution уже нет. Поэтому его слабые места закрываются обязательными
правилами, а не оговоркой:

- вызов из неизменённого кода, который не связался (член сменил сигнатуру), даёт ребро
  ко всем `CandidateSymbols`; без кандидатов — запись ограничения;
- член, синтаксический ключ которого отличается от baseline (сменилась сигнатура), и
  член, удалённый относительно baseline, обрабатываются на уровне проекта;
- документы, текст которых при построении отличался от baseline, считаются устаревшими
  по правилу «Ответ на сохранённом графе до актуализации»: их исходящие ребра неизвестны.
  Это же покрывает тип, создание которого правка убрала.

Держать старый `Solution` до конца построения не предлагается: это две копии solution в
памяти, то, что убрал 1.5.18.

**Уровень 0 от фона не зависит.** Список затронутых путей с момента загрузки ведётся по
событиям записи через MCP и disk watcher и доступен сразу. Снимок хешей членов (чтобы
отбрасывать правки, вернувшие текст baseline, и правки комментариев, и для уровня 1)
считается той же фоновой задачей по захваченному `Solution` — это только синтаксис, без
компиляции, и идёт первым (раздел «Фиксация baseline текстов»).

**Граф не обновляется при правках в сессии**: достаточно baseline (раздел «Уровень 1»).
Актуализация выше — только между состоянием сохранённого графа и состоянием на момент
загрузки.

### Слепые зоны

Анализ не видит: reflection, регистрации по строкам и соглашениям, файлы данных, запуск
процессов, source generators, тесты, читающие исходники как файлы. Распознаваемые
конструкции (`Activator.CreateInstance(Type)`, `Type.GetType(string)`, откаты на CHA)
записываются как ограничения с местом в коде. Остальное перечисляется в описании
инструмента.

### Поверхность инструментов (R-13)

**Один инструмент `estimate_affected_tests` в группе `core`.**

Возможные отдельные инструменты и почему они не нужны:

| Что | Как покрывается |
|---|---|
| Затронутые тесты по изменениям с момента загрузки | Основной режим, без параметров |
| Оценка охвата до правки («от этого метода зависят 340 тестов») | Необязательный параметр символа (`symbolId` или имя, как у навигации). Отдельный инструмент дублировал бы описание и предупреждения |
| «Почему затронут этот тест» | Необязательный параметр теста: цепочка вызовов для него. В основном ответе — только сводка |
| Полный список тестов и изменённых членов | Необязательный параметр подробности; по умолчанию — сводка и фильтр |
| Запуск затронутых тестов | Флаг `run` того же инструмента (ниже). Отдельный инструмент не нужен |
| Сброс baseline | Не нужен: новый baseline — при загрузке другого solution или перезапуске сервера |
| Состояние графа | Строка состояния в каждом ответе |

**Почему `core`.** Польза инструмента — в частом вызове в рабочем цикле, а инструменты групп
агент без явного `enable_tool_group` обычно не видит. Тестовые `run_dotnet_test`,
`run_specific_test`, `run_test_by_filter` и `get_changed_files` уже в `core`. Цена — один
инструмент в каждом списке `lite` (15 инструментов и 19 411 байт `tools/list` на 1.5.18,
по корневому README). По
[mcp-tool-surface-evolution](../mcp-tool-surface-evolution/README.md) новый инструмент —
minor-версия.

**Флаг `run`.** Без флага инструмент только оценивает. С `run: true` он сам запускает
выбранный набор одним вызовом MCP, последовательно, через общий сервис запуска тестов
(выбор `vstest`/`mtp` — по
[test-runner-selection](../test-runner-selection/epoch-1-explicit-runner.md)): на
VSTest-проект — один процесс с фильтром набора, на MTP-проект — по плану ниже. Без
флага агенту пришлось бы сделать по вызову `run_test_by_filter` на каждый тестовый
проект из ответа, а для MTP — на каждый класс; ради этого инструмент и стоит в `core`.

**Сборка (решение владельца, 2026-10-30).** `run` сам собирает проект, чтобы прогон
проверял текущий код, а не DLL до правки. Для каждого тестового проекта одна
последовательность:

- первый процесс проекта идёт со сборкой (`noBuild: false`); сборка тестового проекта
  собирает и его зависимости;
- каждый следующий процесс того же проекта идёт с `noBuild: true`;
- проект целиком — один процесс со сборкой, без фильтра (путь `run_dotnet_test`;
  `run_test_by_filter` пустой фильтр не принимает);
- значение по умолчанию `run_test_by_filter` («опущенный `noBuild` пропускает сборку»)
  на `run` **не переносится**;
- сборка упала — тесты этого проекта не запускаются, ответ пишет `build failed` с
  диагностикой в бюджете вывода, остальные проекты обрабатываются дальше.

Флаг-признак «проект уже собран», чтобы пропускать сборку, сознательно не вводится:
это переусложнение, а инкрементальная сборка уже собранного проекта дешёвая.

**План для MTP-проекта.** Раннер `mtp` принимает только фильтр, целиком равный одному
из видов `FullyQualifiedName~/=` с типом или с типом и методом, без `|`. Дизъюнкция и
свёртка `Namespace.Class.` с точкой на конце остаются для VSTest. Для MTP-проекта
инструмент строит план:

- **по процессу на класс**: класс с одним выбранным методом — фильтр
  `FullyQualifiedName~Namespace.Class.Method`, иначе `FullyQualifiedName~Namespace.Class`;
- **проект целиком, без фильтра** — если выполнено любое из условий:
  1. процессов получилось больше **4**;
  2. выбранные классы — половина или больше тестовых классов проекта;
  3. два или больше выбранных класса входят в одну xUnit-коллекцию с
     `ICollectionFixture<T>`: процесс на класс поднимал бы фикстуру коллекции (например
     контейнер с базой) заново в каждом процессе, а прогон проекта — один раз;
  4. имя класса не укладывается ни в один разрешённый вид (вложенный или generic класс,
     формат которого раннер не принимает);
  5. для проекта действует уровень 0 (граф не готов, не-C# путь и другие случаи
     «Состава ответа»).

Почему такие условия. Процесс на класс выгоден, пока `(k − 1) · S < T_проекта −
T_выбранного`, где `k` — число процессов, `S` — накладные расходы одного процесса
(старт test host, обнаружение тестов, фикстуры). Сборка в модель не входит: по
последовательности из раздела «Сборка» она одна и та же и для прогона по классам
(первый процесс), и для проекта целиком. Оценка `S` для xUnit v3 MTP с `noBuild`
после первого процесса — 1–3 с; это оценка, а не замер. Предел 4 ограничивает
дополнительные расходы примерно 3–9 с, меньше полного прогона типичного тестового
проекта; условие 2 срабатывает раньше на маленьких проектах, где экономии нет. Предел —
константа в коде, а не настройка, чтобы не расширять поверхность; эпоха 1 замеряет `S`
на реальном xUnit v3 MTP-проекте именно для этой последовательности (сборка в первом
процессе, дальше `noBuild`) и при необходимости меняет число. Процессы идут
последовательно: параллельный запуск классов одного проекта ломает изоляцию коллекций
xUnit.

План виден и **без** флага: ответ для каждого MTP-проекта называет режим и причину,
например `Bar.Tests (MTP): whole project — 6 classes, limit 4` или
`Baz.Tests (MTP): 2 processes by class`. Агент заранее знает, что запустится.

**Резерв C — один процесс с несколькими фильтрами.** Если накладные расходы процесса
на класс окажутся велики, следующий шаг — научить раннер `mtp` дизъюнкции разрешённых
видов и переводить её в повторяющиеся флаги фильтра xUnit v3 (`--filter-class`,
`--filter-method`). Тогда `run` переходит на один процесс на MTP-проект, условия 1–3
отпадают, а формат ответа не меняется. Это изменение грамматики соседней программы
[test-runner-selection](../test-runner-selection/epoch-1-explicit-runner.md), а не этой.
Предусловие — проба на реальных версиях xUnit v3: как флаги одного и разных видов
сочетаются между собой («или» либо «и») и как это зависит от версии пакета. Ошибка
сочетания даёт тихо пропущенные тесты, поэтому без пробы вариант не включается.

**Сбои и таймаут прогона.**

- `timeoutSeconds` относится к каждому процессу отдельно, как у `run_*`.
- Упавшие тесты или ненулевой код выхода одного процесса не останавливают остальные:
  агент должен видеть все поломки набора за один вызов.
- В ответе у каждого процесса один из исходов, и они не смешиваются: `passed`/`failed`
  со счётчиками; `build failed`; `timed out` — процесс убит по таймауту, со счётчиками,
  которые раннер успел разобрать; `cancelled` — процесс уже шёл и убит отменой;
  `not run` — процесс не стартовал. Убитый процесс никогда не попадает в упавшие тесты:
  его ненулевой код выхода — не падение тестов.
- **Таймаут процесса** при живом запросе: остальные процессы идут дальше, ответ
  полный, с исходом `timed out` у этого процесса.
- **Отмена MCP-запроса**: текущий процесс убивается вместе с деревом, следующие не
  стартуют, итог (исходы всех процессов) пишется одной строкой в лог сервера. Ответ на
  отменённый запрос отправляется **по возможности**: спецификация MCP рекомендует не
  отвечать на отменённый запрос, а клиент перестаёт ждать, поэтому доставка не
  гарантирована. Восстановление отчёта новым запросом не вводится.

- Ответ прогона начинается той же строкой-предупреждением, затем по каждому проекту —
  что запущено (фильтр или проект целиком) и счётчики, затем упавшие тесты в бюджетах
  вывода инструментов `run_*`, затем «Not covered». Так прогон не выдаёт себя за полную
  проверку: ранний довод против «оценить и запустить» был именно в этом, и его закрывает
  формат ответа, а не отдельный инструмент.
- Параметров прогона минимум, чтобы не раздувать описание в `tools/list`: таймаут;
  конфигурация и платформа наследуются от `load_workspace`, как у `run_*`. Тонкая
  настройка — через ответ без флага и `run_test_by_filter`.
- Если граф уровня 1 не готов, `run` запускает набор уровня 0 (проекты целиком), и
  строка состояния это говорит.

### Ответ инструмента

Описание инструмента (текст в коде — на английском, черновик):

Эпоха 1, без графа (поставляется с уровнем 0):

```
Rapid test impact analysis (approximate). Estimates which tests may be affected
by changes made since the solution was loaded: changed and new tests by name,
other changes at the level of the test projects that depend on the changed code.
Results are a hint for choosing what to run next, not a guarantee: tests can be
missed (reflection, data files, process launches, source generators) or included
unnecessarily. It never replaces running the full test suite or CI before
accepting or committing a change. With run=true it builds and runs the estimate.
```

С эпохи 3, когда появляется граф (описание меняется вместе с поведением):

```
Rapid test impact analysis (approximate). Estimates which tests may be affected
by changes made since the solution was loaded, using a static call graph built
at load time. Results are a hint for choosing what to run next, not a guarantee:
tests can be missed (reflection, DI by convention, data files, process launches,
source generators) or included unnecessarily. It never replaces running the full
test suite or CI before accepting or committing a change.
```

Начало ответа — сводка, детали по запросу:

```
Approximate result (rapid TIA): not a substitute for the full test suite or CI.
Changed since load: 7 members in 3 files. Likely affected: 42 tests in 2 projects.
Run: Foo.Tests.csproj with filter ...; Bar.Tests.csproj whole project (project-level).
Not covered: 2 dispatch sites fell back to all implementations; non-C# changes in 1 file (project-level only).
```

**Что запускать — по тестовым проектам.** Ответ даёт для каждого тестового проекта либо
фильтр, либо «проект целиком» (уровень 0, превышение порога O-03 или слишком длинный
фильтр). Причины:

- Фильтр набора — дизъюнкция `FullyQualifiedName~<имя>` по каждому тесту, с
  экранированием [TestFilterHelper](../../Services/Testing/TestFilterHelper.cs). Оператор
  `~` выбран по той же причине, что в помощнике: к имени `Theory` адаптер дописывает
  параметры, а `()` в `=` VSTest читает как группировку. Следствие записывается явно:
  фильтр выбирает **надмножество** — тест, чьё имя содержит имя выбранного
  (`Check` и `CheckExtra`), тоже запустится. По R-01 это допустимо.
- Фильтр из сотен имён упирается в длину командной строки
  (на Windows 32 767 символов). Тесты класса, затронутые все, сворачиваются в
  `FullyQualifiedName~Namespace.Class.`; при превышении бюджета длины — проект целиком.
  В эпохе 1 это единственный предел: порог O-03 появляется вместе с уровнем 1.
- Имена вложенных и generic тестовых классов в адаптерах (`Outer+Inner`, арность)
  `TestFilterHelper` сейчас не переводит. Формат сверяется на xUnit, NUnit и MSTest в
  эпохе 1 и записывается в каталог случаев.
- [Явный раннер тестов](../test-runner-selection/epoch-1-explicit-runner.md) на `mtp`
  принимает только один `.csproj` и фильтр одного вида `FullyQualifiedName~/=` без `|`.
  Для MTP-проектов ответ даёт план по классам или проект целиком по правилам раздела
  «План для MTP-проекта».

- Первая строка с предупреждением — в каждом ответе: после сжатия контекста агент помнит
  ответ, а не описание инструмента.
- «Not covered» — конкретные места текущего анализа, а не общие оговорки.
- Пока в изменённых документах есть ошибки компиляции, ответ это называет.
- Охват выше порога (O-03, с уровнем 1) — ответ предлагает запустить тестовые проекты
  целиком.
- Фильтр должен запускать все выбранные тесты, в том числе во вложенных и generic
  тестовых классах и параметризованные; лишние тесты допустимы только из-за вхождения
  имени.
- Тот же запрос без изменений, по символу, даёт оценку охвата до правки
  («от этого метода зависят 340 тестов»).

## Проверка

В продуктовых эпохах проверки пишутся раньше кода (R-16): каталог граничных случаев и
интеграционные тесты задачи — это её red-фаза.

### 1. Каталог граничных случаев (main suite, в памяти)

Фикстуры собираются через `AdhocWorkspace`, без MSBuild. Атрибуты тестов сопоставляются по
имени, поэтому `[Fact]`, `[Test]`, `[TestMethod]` объявляются заглушками в исходнике
фикстуры. Типы фикстур xUnit и библиотек моков распознаются по полному имени, поэтому
заглушки объявляются в тех же пространствах имён (`Xunit`, `Moq`, `NSubstitute`). Каждый случай: baseline-исходник, правка, **точное** множество ожидаемых тестов и
**точный** перечень ограничений — по тому же принципу, что перечень ограничений в
SourceStructure. Изменение в любую сторону должно быть осознанным.

Группы случаев:

- **Обнаружение изменений:** тело, сигнатура, переименование, добавление и удаление члена;
  `partial` с объявлениями в двух файлах и правкой каждого; generic-перегрузки с разной
  арностью; явная реализация интерфейса; добавление, удаление, переименование файла;
  только комментарии и пробелы; правка, вернувшая текст baseline; сломанный синтаксис;
  правка `using` и alias при неизменных членах; файл только с `global using`.
- **Состав ответа:** новый тест в существующем файле; новый тестовый файл до и после
  reload; переименованный тест; обычный метод, ставший тестовым; удалённый член и
  удалённый файл (узлы из baseline).
- **Уровень 0:** не-C# путь из карты входов; путь вне карты — «Not covered»; правка
  csproj с новой `ProjectReference` до reload — все тестовые проекты и состояние
  «граф проектов устарел»; `Directory.Build.props` над несколькими проектами.
- **Фиксация baseline:** путь, изменённый до записи его хеша, — «baseline неизвестен»,
  уровень 0, не «без изменений».
- **Корни:** тестовый метод; конструкторы с базовыми; `IClassFixture` и `IAsyncLifetime`;
  collection fixture через `[Collection]` и `[CollectionDefinition]`, в том числе без
  найденного определения; реализация, созданная в `InitializeAsync` фикстуры, при
  другом создании в том же контексте; setup-атрибуты NUnit и MSTest; абстрактный
  базовый тестовый класс; источники данных.
- **Ребра:** все виды из раздела «Ребра».
- **Диспетчеризация:** реализация создана в тесте, в поле из конструктора, через фабрику,
  через DI-регистрацию; нет созданной реализации; мок интерфейса; мок класса с `CallBase`;
  default interface methods. **Проверки исключения:** тест соседнего класса с другой
  реализацией не попадает в результат.
- **Изменения связывания:** новая перегрузка, override при неизменном вызывающем коде;
  новый extension-метод в другом статическом классе, чем прежняя цель; три проекта
  Library → App → Tests: прежняя цель extension в Library, новый extension в App —
  тест в ответе через уровень проекта; новый extension-метод и новый оператор в Library,
  тестовый проект ссылается только на App — тест в ответе через транзитивное замыкание;
  новый метод экземпляра, скрывающий extension, в том числе extension, объявленный в
  тестовом проекте, при новом методе в другом `partial`-файле типа; новый метод
  вытесняет extension из метаданных (ребро с ключом листа) — проектное расширение, и
  отрицательный случай: другие тесты вызывают одноимённый extension из метаданных,
  вытесняемых вызовов нет — расширения нет; новый оператор и implicit-преобразование;
  смена alias и `global using`; `AssemblyInfo.cs` без членов, добавление и удаление
  `InternalsVisibleTo` при неизменном вызове (extension → internal-метод) — проектное
  расширение.
- **Каскад сохранённого графа:** оператор в Library, вызов в App без тестов, тесты в
  App.Tests — факты App устаревают и переизвлекаются.
- **Сохранённый граф до актуализации:** тело фабрики изменено до загрузки (документ
  устарел), реализация, которую фабрика теперь создаёт, изменена после загрузки — тест
  фабрики попадает в ответ; два размещения: фабрика и реализация в одном проекте и
  реализация в отдельном проекте-зависимости.
- **Граф после правок (`graph built after edits`):** смена сигнатуры до построения —
  вызывающие находятся через `CandidateSymbols` или уровень проекта.
- **Распознаваемые слепые зоны** дают запись ограничения.
- **Формат ответа:** строка-предупреждение; фильтр для вложенных, generic и
  параметризованных тестов и экранирование синтаксиса фильтра; `Check` и `CheckExtra`
  (ожидаемое надмножество); свёртка по классу и переход на проект целиком при превышении
  бюджета длины.
- **План MTP-проекта:** один класс с одним методом — фильтр метода; несколько классов —
  процесс на класс, каждый фильтр совпадает с разрешённым видом раннера; каждое из
  условий 1–5 перехода на проект целиком и причина в ответе.
- **Прогон `run`:** падение в первом проекте не останавливает остальные; таймаут на
  процесс; первый процесс проекта со сборкой, следующие с `noBuild`, проект целиком —
  со сборкой и без фильтра; `build failed` не запускает тесты проекта и не останавливает
  другие; каждый исход (`passed`/`failed`, `build failed`, `timed out`, `cancelled`,
  `not run`) отдельно, убитый процесс не попадает в упавшие тесты.
- **Идентификаторы узлов:** один документ в двух target framework; одинаковое полное имя
  типа в двух проектах.

### 2. Интеграционные тесты (main suite)

4–6 тестов на существующей инфраструктуре: реальная загрузка через MSBuild; правка на
диске мимо MCP; правка через MCP; reset/reload с сохранением baseline; внешняя правка
файла при удержанной до первого чтения фоновой задаче — путь получает «baseline
неизвестен», а не «без изменений»; прогон полученного фильтра через
`run_test_by_filter` и тот же набор через `run: true`. Критерий прогона: запущены все
ожидаемые тесты, лишние — только из-за вхождения имени. Ещё два случая для `run`:
исходники изменены после последней сборки, старые бинарники на месте — `run`
исполняет новый код (тест, который на старой DLL проходит, падает); отмена
`tools/call` через MCP-клиент, а не прямой вызов обработчика, — процессы
останавливаются, итог есть в логе, доставка ответа не требуется.

### 3. Стенд полноты (вне CI)

Стенд — вызов будущего инструмента так, как его вызывает агент, с baseline по R-03.
Для каждого исторического коммита:

1. загрузить родительский коммит и дождаться готовности графа;
2. применить изменения коммита как правки сессии и вставить `throw` в изменённые члены;
3. вызвать инструмент и сравнить предсказание с тестами, реально упавшими при прогоне.

Коммиты, где правка только меняет связывание неизменённого кода (`using`, новый
extension-метод, перегрузка), — отдельная выборка: `throw` в изменённом члене её не
измеряет. Для неё `throw` вставляется и в **добавленные** члены: тест, который после
правки перепривязался на новую перегрузку или extension-метод, упадёт и станет
ожидаемым. Известный предел стенда: правки только `using` и alias без нового члена
`throw` не получают, вставлять его некуда, поэтому их полнота на истории не
измеряется; такие случаи держит каталог граничных случаев. Метрики — полнота (recall,
главная), доля suite, которую не пришлось запускать, и доля ответов, где сработало
расширение R-14. Сравниваются CHA и RTA. Стенд
запускается по требованию, результаты — в evidence программы. Ориентир: полнота заметно
ниже ~90% без учёта известных слепых зон означает, что уровень 1 не окупается.

На истории этого репозитория CHA и RTA почти не различаются: тесты здесь мало держат
реализации за интерфейсами и DI. Корпус для решения по VTA и порогу O-03 — открытый
вопрос O-08.
