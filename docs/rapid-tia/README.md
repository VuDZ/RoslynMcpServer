# Rapid TIA: подсказка о затронутых тестах

Создано: **2026-10-29**. Статус: **программа записана по итогам обсуждения с владельцем, код не начат**.

## Зачем

После правки агент обычно запускает либо один тест, который сам вспомнил, либо весь
suite. Полный main suite идёт минуты, поэтому в рабочем цикле агент его избегает и
пропускает косвенные поломки. Транзитивное замыкание «кто зависит от этого метода»
агент вручную через `get_call_graph` и `find_symbol_references` строит плохо: берёт
один-два уровня и останавливается.

Rapid TIA (test impact analysis) — инструмент, который по изменениям с момента загрузки
solution оценивает, какие тесты стоит запустить, и отдаёт готовый фильтр для
`run_test_by_filter`. Ещё одна польза — память сессии: после сжатия контекста агент
теряет список своих правок, а сервер его хранит.

Инструмент **не гарантирует точность**. Он может пропустить тест или включить лишний.
Полный прогон и CI остаются обязательными; ответ инструмента должен это поддерживать,
а не размывать.

## Что программа не делает

- Не заменяет финальную валидацию по `AGENTS.md` и не меняет её правила.
- Не смотрит изменения до загрузки solution: на момент загрузки всё считается исправным.
  Сравнение с git HEAD остаётся у `get_changed_files`.
- Не заглядывает внутрь NuGet-сборок и другого метаданных-кода.
- Не собирает покрытие во время выполнения (динамический TIA отклонён: требует
  прогона с покрытием на baseline).
- Не решает, что агенту запускать перед коммитом.

## Решения владельца (2026-10-29)

| ID | Вопрос | Решение |
|---|---|---|
| R-01 | Точность | Rapid TIA: приблизительный результат, помогает агенту не потеряться. Не гарантирует полноту и не заменяет полный прогон тестов и CI. |
| R-02 | Граница анализа | Только исходники solution. Сборки из NuGet и прочий metadata-код — листья графа. |
| R-03 | Baseline | Состояние на момент загрузки solution (или восстановления из workspace state cache). Изменения раньше не учитываются. |
| R-04 | Основной подход | Прямой граф от тестов, построенный на baseline, плюс множество изменённых членов. Не обратный поиск `FindReferences` по текущему solution. |
| R-05 | Виртуальные вызовы | RTA в контексте тестового класса: цель вызова — только реализации, созданные в этом контексте. Нет ни одной созданной реализации — откат на CHA (все реализации) с записью ограничения. VTA (поток типов по полям и переменным) — только если замер покажет необходимость. |
| R-06 | Подача результата | Имя инструмента говорит о приблизительности (рабочее имя `estimate_affected_tests`). Предупреждение — в описании инструмента и в первой строке каждого ответа. |
| R-07 | Тесты фичи | Каталог граничных случаев в памяти в main suite, без отдельной категории и гейта (в отличие от `AnalyzerLifecycle`). Несколько интеграционных тестов. Замер полноты — отдельный стенд, не CI. |
| R-08 | Когда строить граф | Всегда в фоне после загрузки, не блокируя загрузку и инструменты. Не синхронно при загрузке и не лениво по первому запросу. |
| R-09 | Сохранение графа | Граф сохраняется на диск. После загрузки сохранённый граф сразу даёт рабочий ответ, а актуализируется в фоне: для больших solution построение с нуля занимает порядка компиляции. |
| R-10 (бывший O-01) | Тесты, которые статически не видны, но обязательны (в этом репозитории — `SourceStructure`) | Инструмент для них ничего не делает: ни настройки «всегда запускать», ни отдельного блока. Если такие тесты перечислены в `AGENTS.md` или другой инструкции проекта, агент запускает их сам. |
| R-11 (бывший O-02) | Аварийное отключение фона | Переменная среды только для диагностики (по образцу `ROSLYN_MCP_SEARCH_PREWARM`), не обычная настройка: по R-08 фон работает всегда. |
| R-12 (бывший O-04) | Где хранить сохранённый граф | Подкаталог `tia/` каталога пользователя сервера, как статистика использования в ветке `usage-statistics`: Windows — `%LOCALAPPDATA%\RoslynMcpServer\tia\`, Linux — `$XDG_STATE_HOME/roslyn-mcp/tia/` (по умолчанию `~/.local/state/roslyn-mcp/tia/`), macOS — `~/Library/Application Support/RoslynMcpServer/tia/`. Файл на solution по хешу полного пути. Не в репозитории пользователя, от workspace state cache не зависит. |

## Дизайн

### Baseline и обнаружение изменений

- Старый `Solution` целиком не хранится: это дорого по памяти (см. 1.5.18, освобождение
  предыдущего solution). Хранится лёгкий снимок: путь → checksum текста; для каждого члена
  типа — ключ (тип, имя, синтаксис параметров) и хеш его синтаксиса.
- Текущее состояние сравнивается со снимком. Правки через MCP и правки на диске мимо MCP
  (их подтягивает disk watcher, [WorkspaceDocumentDiskSync](../../Services/Workspace/WorkspaceDocumentDiskSync.cs))
  обрабатываются одинаково.
- Изменённые члены определяются **синтаксически**, без semantic model: это работает и на
  некомпилируемом промежуточном коде.
- Двухступенчатый фильтр:
  1. изменённые файлы → узлы графа из этих файлов; файл без узлов, достижимых из тестов,
     отбрасывается сразу;
  2. внутри оставшихся файлов — изменённые члены. Если файл не разбирается до членов,
     берутся все его узлы (деградация до уровня файла, не отказ).
- Правка только комментариев и пробелов — не изменение. Правка с последующим откатом —
  не изменение.
- `load_workspace` / `reset_workspace` того же solution в том же процессе baseline **не
  сбрасывают**: иначе перезагрузка после правки csproj стирает историю изменений. Новый
  baseline — при загрузке другого solution или перезапуске сервера. Отдельной операции
  сброса нет (предложение O-05).

### Уровень 0: по проектам

Изменённые документы → их проекты → тестовые проекты, транзитивно зависящие от них
(`ProjectDependencyGraph`). На этот уровень попадают изменения не в C# (csproj, props,
json, resx) и все случаи отката. Уже он даёт фильтр «запусти эти два тестовых проекта».

### Уровень 1: прямой граф от тестов

**Почему граф на baseline достаточен.** Если правка добавила новый вызов в метод M, M
изменён, и все тесты, достигавшие M в baseline, попадут в ответ. Новые методы вызываются
только из изменённых, новые тесты сами изменены. Поэтому граф после правок не
перестраивается; исключения перечислены в разделе «Изменения связывания».

**Узлы** — члены типов из исходников solution. Гранулярность — член, а не тип: тип вроде
`SolutionManager` достижим почти из любого теста. Уровень типа — только запасной.

**Корни тестового класса:**

- тестовые методы (распознаются [TestAttributeMatcher](../../Services/Testing/TestAttributeMatcher.cs));
- конструкторы класса и базовых классов, инициализаторы полей;
- xUnit `IClassFixture<T>`, `ICollectionFixture<T>`, `IAsyncLifetime`, `Dispose`/`DisposeAsync`;
- NUnit `[SetUp]`, `[TearDown]`, `[OneTimeSetUp]`, `[OneTimeTearDown]`;
- MSTest `[TestInitialize]`, `[TestCleanup]`, `[ClassInitialize]`, `[ClassCleanup]`;
- источники данных `MemberData`, `ClassData`, `TestCaseSource`, `DynamicData`.

Тесты, объявленные в абстрактном базовом классе, раскрываются в конкретные классы-наследники:
иначе фильтр их не запустит.

**Ребра:**

- вызовы, get/set свойств, индексаторы, операторы, неявные преобразования, события;
- инициализаторы полей и статические конструкторы — к конструкторам и к первому обращению к типу;
- чтения `const` и значения параметров по умолчанию (встраиваются в место использования);
- тела лямбд, анонимных методов и локальных функций относятся к объемлющему методу;
  method group — ребро к методу;
- синтезированные члены record — к объявлению record.

Опыт обхода делегатов есть в [ReachabilityAnalysis](../../RoslynMcpServer.Tests/SourceStructure/ReachabilityAnalysis.cs)
(тестовый код SourceStructure). Он сознательно не раскрывает виртуальные вызовы, поэтому
обход для TIA — отдельный код; логику по делегатам можно заимствовать.

**Виртуальные и интерфейсные вызовы (R-05).** Для каждого тестового класса — неподвижная
точка: достижимые методы дают созданные типы, созданные типы дают цели виртуальных вызовов,
цели дают новые достижимые методы. Созданием типа считаются `new T`, `typeof(T)` и
generic-аргументы (например `AddSingleton<IFoo, Foo>()`).

- Нет ни одной созданной реализации — CHA плюс ограничение. Так покрываются
  DI-сканирование сборок, `Activator.CreateInstance` и реализации за границей графа.
- Мок интерфейса (`Mock<IFoo>`, `Substitute.For<IFoo>()`) реализацию не создаёт.
  `Mock<Foo>` от класса считается созданием `Foo` (`CallBase`). Лямбды в
  `Setup(...).Callback(...)` — обычные тела.

**Изменения связывания.** Эти правки меняют поведение неизменённого кода и обрабатываются
отдельно:

- новая перегрузка или extension-метод — изменёнными считаются одноимённые члены типа и его иерархии;
- новый override или новая реализация интерфейса — изменённым считается базовый член;
- изменение атрибутов, `partial`, базового типа или списка интерфейсов — изменённым считается весь тип.

**Хранение: факты по документам и выводимая достижимость.** Граф делится на две части:

- **Факты** — то, что извлекается из одного документа его semantic model: для каждого
  объявленного в нём члена — связанные вызовы и обращения, точки виртуальных вызовов,
  созданные типы, чтения `const`; для каждого объявленного типа — базовый тип, интерфейсы,
  overrides; корни тестов. Узлы идентифицируются `ISymbol.GetDocumentationCommentId()`:
  публичный, стабильный между процессами формат. Лямбды и локальные функции свёрнуты в
  объемлющий член, поэтому своих идентификаторов не требуют.
- **Достижимость** — выводится из фактов в памяти: RTA по тестовому классу и битсеты
  достижимых узлов для каждого тестового класса и метода. Пример объёма: 20k узлов × 3k
  тестов ≈ 7.5 МБ.

Запрос: изменённые узлы → тесты, чьи битсеты их содержат, плюс кратчайшая цепочка «почему».
Факты локальны для документа: это делает возможной частичную актуализацию сохранённого
графа (раздел «Построение и сохранение графа»).

### Построение и сохранение графа (R-08, R-09)

Синхронное построение при загрузке отклонено: это semantic model всего достижимого из
тестов кода, порядка полной компиляции solution, а загрузка и так главная боль
([workspace-load-performance](../workspace-load-performance/README.md)). Ленивое
построение по первому запросу отклонено: запрос ждал бы десятки секунд и упирался бы в
таймауты MCP-клиентов.

**Фон после публикации загруженного solution**, по образцу
[SearchIndexPrewarm](../../Services/Navigation/SearchIndexPrewarm.cs):

- Фоновая задача захватывает опубликованный `Solution` в момент загрузки. `Solution`
  неизменяем, поэтому правки агента во время работы на результат не влияют: граф
  соответствует ровно baseline. Захваченный `Solution` держится только до конца работы.
- Блокировка workspace берётся только на захват `Solution` при старте.
- Запуск после прогрева индексов поиска, а не параллельно с ним, с ограниченным
  параллелизмом по проектам, чтобы не отнимать CPU у инструментов. Компиляции, которые
  создаёт извлечение фактов, Roslyn переиспользует в текущем solution для неизменённых
  проектов; это может ускорить навигацию, но удерживает память — нужен замер.
- Ошибки и отмена — одна строка лога, как у прогрева; инструмент тогда работает на уровне 0.

**Сохранённый граф (R-09).** На диск пишутся факты по документам, не достижимость:
достижимость дешево выводится в памяти, а факты можно обновлять по одному документу.

Содержимое файла:

- версия формата, версия сервера, версия Roslyn; несовпадение — файл не используется;
- для каждого проекта — хеш того, что влияет на связывание: путь, target framework,
  символы препроцессора, compilation options, список ссылок (пути и их хеши или версии);
- для каждого документа — хеш содержимого, его факты, **хеш поверхности объявлений**
  (сигнатуры членов, иерархия типов, атрибуты) и компактный набор используемых имён
  (например фильтр Блума по идентификаторам).

Запись атомарная: временный файл и переименование. Повреждённый файл отбрасывается.
Если тот же solution открыт двумя серверами, побеждает последняя запись. Пример объёма:
20k членов по ~10 ребер — единицы мегабайт.

**Последовательность после загрузки:**

1. Читается сохранённый граф (если есть и версии совпадают). По хешам содержимого
   определяются устаревшие документы: изменённые, новые, удалённые, а также все документы
   проектов, чей хеш связывания изменился.
2. Достижимость выводится из сохранённых фактов, инструмент сразу отвечает по ним.
3. В фоне актуализация: заново извлекаются факты устаревших документов. Если у устаревшего
   документа изменилась поверхность объявлений, заново извлекаются и документы, в наборе
   имён которых есть имена изменённых объявлений: новая перегрузка или сменившаяся
   сигнатура меняет связывание кода, текст которого не менялся.
4. Достижимость пересчитывается, граф подменяется атомарно, файл перезаписывается.
5. Нет сохранённого графа или сработала политика полной перестройки (O-06) — полное
   извлечение фактов в фоне. Полная перестройка нужна, потому что каскад по набору имён
   приблизителен и без неё ошибки накапливаются между сессиями.

Частичная актуализация компилирует только проекты устаревших документов (зависимости
дают декларации, тела не связываются) и связывает только тела устаревших документов.
После обычного `git pull` на десятки файлов это секунды, а не время компиляции solution.

**Ответ на сохранённом графе до актуализации.** Изменённые члены в документах, устаревших
относительно сохранённого графа, обрабатываются на уровне файла и проекта, а не по ребрам
из старых фактов. Ответ называет состояние.

**Запрос никогда не ждёт.** Строка состояния в ответе:

- `Call graph: ready.`
- `Call graph: cached, refreshing (37 stale documents); stale parts are file- and project-level.`
- `Call graph: building (12/40 projects); project-level result only.`
- `Call graph: failed: <reason>; project-level result only.`

Агент получает полезный ответ в любой момент и может повторить запрос позже.

**Reload или reset в сессии.** Baseline изменений (R-03) сохраняется. Если граф уже
готов, он остаётся: он соответствует baseline. Если фоновая работа не закончена, она
отменяется и продолжается актуализацией по новому загруженному solution, а ответ помечает
`graph built after edits`. Такой граф почти так же пригоден: на любом пути baseline от
корня теста до первого изменённого члена все члены не менялись, и их ребра те же, поэтому
этот изменённый член остаётся достижимым. Ослабление в двух местах: вызовы из неизменённого
кода в член с изменённой сигнатурой могут не связаться (нужны `CandidateSymbols`), и RTA
может потерять тип, создание которого правка убрала. Держать старый `Solution` до конца
построения не предлагается: это две копии solution в памяти, то, что убрал 1.5.18.

**Уровень 0 от фона не зависит.** Список затронутых путей с момента загрузки ведётся по
событиям записи через MCP и disk watcher и доступен сразу. Снимок хешей членов (для
отбрасывания откатов и правок комментариев и для уровня 1) считается той же фоновой
задачей по захваченному `Solution` — это только синтаксис, без компиляции, и идёт первым.

**Граф не обновляется при правках в сессии**: достаточно baseline (раздел «Уровень 1»).
Актуализация выше — только между состоянием сохранённого графа и состоянием на момент
загрузки.

### Слепые зоны

Анализ не видит: reflection, регистрации по строкам и соглашениям, файлы данных, запуск
процессов, source generators, тесты, читающие исходники как файлы. Распознаваемые
конструкции (`Activator.CreateInstance(Type)`, `Type.GetType(string)`, откаты на CHA)
записываются как ограничения с местом в коде. Остальное перечисляется в описании
инструмента.

### Поверхность инструментов (предложение O-05)

**Один инструмент `estimate_affected_tests` в группе `core`.**

Возможные отдельные инструменты и почему они не нужны:

| Что | Как покрывается |
|---|---|
| Затронутые тесты по изменениям с момента загрузки | Основной режим, без параметров |
| Оценка охвата до правки («от этого метода зависят 340 тестов») | Необязательный параметр символа (`symbolId` или имя, как у навигации). Отдельный инструмент дублировал бы описание и предупреждения |
| «Почему затронут этот тест» | Необязательный параметр теста: цепочка вызовов для него. В основном ответе — только сводка |
| Полный список тестов и изменённых членов | Необязательный параметр подробности; по умолчанию — сводка и фильтр |
| Запуск затронутых тестов | Не нужен: фильтр из ответа передаётся в существующий `run_test_by_filter`. Инструмент «оценить и запустить» скрыл бы от агента, что набор приблизительный |
| Сброс baseline | Не нужен: новый baseline — при загрузке другого solution или перезапуске сервера |
| Состояние графа | Строка состояния в каждом ответе |

**Почему `core`.** Польза инструмента — в частом вызове в рабочем цикле, а инструменты групп
агент без явного `enable_tool_group` обычно не видит. Тестовые `run_dotnet_test`,
`run_specific_test`, `run_test_by_filter` и `get_changed_files` уже в `core`. Цена — один
инструмент в каждом списке `lite` (19 инструментов на v1.3.24). По
[mcp-tool-surface-evolution](../mcp-tool-surface-evolution/README.md) новый инструмент —
minor-версия.

### Ответ инструмента

Описание инструмента (текст в коде — на английском, черновик):

```
Rapid test impact analysis (approximate). Estimates which tests may be affected
by changes made since the solution was loaded, using a static call graph built
at load time. Results are a hint for choosing what to run next, not a guarantee:
tests can be missed (reflection, DI by convention, data files, process launches,
source generators) or included unnecessarily. It never replaces running the full
test suite or CI before accepting or committing a change.
```

Начало ответа — сводка, детали по запросу:

```
Approximate result (rapid TIA): not a substitute for the full test suite or CI.
Changed since load: 7 members in 3 files. Likely affected: 42 tests in 2 projects.
Filter: ...
Not covered: 2 dispatch sites fell back to all implementations; non-C# changes in 1 file (project-level only).
```

- Первая строка с предупреждением — в каждом ответе: после сжатия контекста агент помнит
  ответ, а не описание инструмента.
- «Not covered» — конкретные места текущего анализа, а не общие оговорки.
- Пока в изменённых документах есть ошибки компиляции, ответ это называет.
- Охват выше порога (O-03) — ответ предлагает запустить тестовые проекты целиком.
- Фильтр строится по правилам [TestFilterHelper](../../Services/Testing/TestFilterHelper.cs)
  и должен работать для вложенных и generic тестовых классов и параметризованных тестов.
- Тот же запрос без изменений, по символу, даёт оценку охвата до правки
  («от этого метода зависят 340 тестов»).

## Проверка

### 1. Каталог граничных случаев (main suite, в памяти)

Фикстуры собираются через `AdhocWorkspace`, без MSBuild. Атрибуты тестов сопоставляются по
имени, поэтому `[Fact]`, `[Test]`, `[TestMethod]` объявляются заглушками в исходнике
фикстуры. Каждый случай: baseline-исходник, правка, **точное** множество ожидаемых тестов и
**точный** перечень ограничений — по тому же принципу, что перечень ограничений в
SourceStructure. Изменение в любую сторону должно быть осознанным.

Группы случаев:

- **Обнаружение изменений:** тело, сигнатура, переименование, добавление и удаление члена;
  `partial`; добавление, удаление, переименование файла; только комментарии и пробелы;
  правка и откат; сломанный синтаксис; не-C# файл; csproj.
- **Корни:** тестовый метод; конструкторы с базовыми; fixtures и `IAsyncLifetime`;
  setup-атрибуты NUnit и MSTest; абстрактный базовый тестовый класс; источники данных.
- **Ребра:** все виды из раздела «Ребра».
- **Диспетчеризация:** реализация создана в тесте, в поле из конструктора, через фабрику,
  через DI-регистрацию; нет созданной реализации; мок интерфейса; мок класса с `CallBase`;
  default interface methods. **Проверки исключения:** тест соседнего класса с другой
  реализацией не попадает в результат.
- **Изменения связывания:** новая перегрузка, extension-метод, override при неизменном
  вызывающем коде.
- **Распознаваемые слепые зоны** дают запись ограничения.
- **Формат ответа:** строка-предупреждение; фильтр для вложенных, generic и
  параметризованных тестов и экранирование синтаксиса фильтра.

### 2. Интеграционные тесты (main suite)

3–5 тестов на существующей инфраструктуре: реальная загрузка через MSBuild; правка на
диске мимо MCP; правка через MCP; reset/reload с сохранением baseline; прогон полученного
фильтра через `run_test_by_filter`, который выбирает ровно эти тесты.

### 3. Стенд полноты (вне CI)

Прогон по историческим коммитам этого репозитория: в изменённые члены коммита вставляется
`throw`, реально упавшие тесты сравниваются с предсказанными. Метрики — полнота (recall,
главная) и доля suite, которую не пришлось запускать. Сравниваются CHA и RTA. Стенд
запускается по требованию, результаты — в evidence программы. Ориентир: полнота заметно
ниже ~90% без учёта известных слепых зон означает, что уровень 1 не окупается.
