## Остатки прежних замечаний

ID: E2-03
Severity: High
Category: Measurement

Target:
[План task-01](../task-01-forward-reverse-probe-hi.md), «Годность пары прогонов», строки 174–193;
«Единица сравнения», строки 197–206.

Claim:
Пара годна, если в результатах мутации есть исход для каждой отображённой **единицы** контрольного прогона,
skipped совпадают и каждый завершившийся процесс выполнил больше нуля тестов.
Параметризованный метод при этом является одной единицей.

Evidence:
Сборка, timeout/crash/cancel, нулевые прогоны, N/A для пустого O и достаточность выборки теперь предусмотрены.
Но критерий строк 180–181 проверяет покрытие методов, а не всех ожидаемых runtime cases.
В [catalog.json task-06](../../epoch-1-project-level/evidence/task-06-adapter-names/catalog.json),
`Adapters[Adapter=xunit-v2].Cases`, у `ParameterTests.Rows` два разных `Id` и одинаковый FQN.
Один оставшийся результат покрывает единственную единицу, хотя результат второй строки отсутствует.
Совпадение skipped этого не обнаруживает: оба набора skipped могут быть пустыми.
Существующий [Collect-Evidence.ps1](../../../../spikes/AdapterTestNames/Collect-Evidence.ps1), строки 24, 48–69,
сверяет case-level количества/исходы и связывает результаты с discovery Id; переход к одной единице
не должен удалять эту проверку пригодности данных.

Failure scenario:
1. В baseline обе строки `Rows(1)` и `Rows(2)` прошли и отображены в одну единицу.
2. В отчёт мутации попал только passing-результат `Rows(1)`; результат `Rows(2)` потерян при discovery,
   выполнении или сборе результатов. Процесс завершился сам, выполнен хотя бы один тест, skipped нет.
3. Проверка по единицам проходит, и отсутствующая строка не делает пару негодной.
   Если именно она обнаружила бы дефект, O занижается; при других зарегистрированных падениях получается
   непустой, но неполный эталон. Это остаток исходной проблемы missing results, а не новая единица метрик.

Suggested change:
Проверять полноту пары **до агрегации** по ожидаемым отображённым runtime cases baseline:
каждый должен иметь сопоставленный терминальный исход, с контролем пропусков/дубликатов и skipped.
Отсутствие результата отдельной строки делает пару негодной с `missing results`, даже если её метод
представлен другими строками. Полноту алгоритма по-прежнему считать в выбранных единицах-методах.
Добавить к самопроверке стенда случай «две baseline-строки, один результат мутации».

Confidence:
High

ID: E2-05
Severity: Medium
Category: Measurement

Target:
[План task-01](../task-01-forward-reverse-probe-hi.md), «Режим замера цены», строки 215–227;
«Цена», строки 260–262.

Claim:
Ряд «первый запрос после загрузки» допускает «свежий процесс на член, либо фиксированный порядок с записью»;
для этого ряда отдельно считаются медиана, p95 и максимум времени на член.

Evidence:
Влияние прямого графа на reverse устранено: процессы раздельные, своего прямого графа в reverse нет,
prewarm/cache оговорены, собственная подготовка и память учитываются.
Оставшаяся альтернатива в строке 222 допускает последовательный обход членов в одном reverse-процессе.
После загрузки первым является только один запрос; следующие могут использовать компиляции предыдущих.
Запись порядка делает этот факт видимым, но не превращает последующие запросы в первые после загрузки.
Переиспользование компиляций описано в [каноне](../../README.md), строки 359–365.

Failure scenario:
1. После загрузки отдельного reverse-процесса исполнитель идёт по выборке из 25 членов в фиксированном порядке.
2. Первый запрос подготавливает нужные компиляции. Следующие члены из тех же проектов их переиспользуют;
   свежих процессов для них разрешённый альтернативный вариант не требует.
3. Распределение всего прохода маркируется как «первый запрос», хотя 24 наблюдения сделаны после других запросов.
   Его p95 не характеризует latency первого обращения к произвольному члену после загрузки.

Suggested change:
Развести два допустимых эксперимента: для распределения первого запроса каждый учитываемый замер должен быть
первым в свежем процессе; проход в одном процессе — отдельная последовательность, где первый запрос выделен,
а остальные относятся к последующим. Фиксированный порядок можно сохранить для обоих экспериментов.
Не смешивать эти наблюдения под общей меткой/p95 первого запроса. Менять разрешённый владельцу порог цены не требуется.

Confidence:
High
