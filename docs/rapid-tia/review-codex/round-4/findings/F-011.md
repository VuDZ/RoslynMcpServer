# F-011 — Изменение assembly-атрибута сводится к пустому набору узлов AssemblyInfo.cs

Severity: major

Category: correctness

Confidence: high

## Target

docs/rapid-tia/README.md:67–69, 134–152, 226–250 — хеш контекста вне членов, состав ответа и изменения связывания.

## Claim

Assembly-атрибуты явно входят в отслеживаемый контекст, но для изменения вне членов задано только расширение до узлов файла. В отдельном AssemblyInfo.cs членов типов может не быть вообще. Добавление InternalsVisibleTo меняет доступность уже существующего instance-метода и связывание неизменённого теста, однако не создаёт изменённого member-узла и не запускает перечисленные правила проектного расширения.

## Evidence

- Строки 67–69 включают «атрибуты сборки» в хеш содержимого файла вне членов.
- Строки 246–247 расширяют такие изменения до «всех узлов этого файла»; проектное расширение отдельно задано только для global using.
- Строка 250 обрабатывает изменение атрибутов через весь тип. У assembly-атрибута нет объемлющего типа.
- Правило 231–237 относится к **новому** обычному методу. В следующем сценарии метод существует в обеих версиях; меняется только его доступность из Tests.
- [InternalsVisibleToAttribute](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.compilerservices.internalsvisibletoattribute?view=net-10.0) применяется к сборке и разрешает доступ к internal-членам из указанной friend assembly.
- Проба на Roslyn 5.9.0 с неизменными App.cs и Tests.cs и единственным edit в отдельном AssemblyInfo.cs подтвердила:

    before: Tests / M:ConsumerExtensions.Render(Shared.Widget)
    after: App / M:Shared.Widget.Render

  Обе конфигурации компилируются без ошибок. Методика и полный stdout — в [recheck.md](../recheck.md).

## Why it matters

Это статически разрешимый source-only вызов, а не reflection или метаданные вне solution. Снимок обнаружит содержательную правку, но последующее file expansion даст пустое множество и потеряет тест, для которого реально изменилась выполняемая цель.

## Failure scenario

1. App.cs содержит public Widget с явным конструктором и уже существующим internal Render, возвращающим 2.
2. Tests ссылается на App и объявляет public ConsumerExtensions.Render(this Widget), возвращающий 1. TestA вызывает new Widget().Render(); baseline-цель — extension из Tests.
3. В существующем, уже зафиксированном baseline-документе AssemblyInfo.cs нет членов типов. После готовности baseline туда добавляется assembly: InternalsVisibleTo("Tests"). Проектный файл не меняется, новый путь не появляется.
4. Неизменённый TestA теперь вызывает internal Widget.Render из App.
5. Member hashes App.cs и Tests.cs прежние; нового метода/override/типа нет. В AssemblyInfo.cs нет узлов членов типов, а type-level attribute expansion неприменим. Проектное расширение для assembly-атрибута не предписано, поэтому TestA отсутствует в подсказке.

## Violated requirement / constraint

Явное отслеживание assembly-атрибутов в 67–69 и R-14: изменение связывания должно пометить прежнюю цель либо консервативно расширить ответ. R-01 не объявляет этот случай слепой зоной.

## Recommended change

Отдельно задать для изменения assembly-атрибутов проектное расширение проекта-владельца и его зависимых тестовых проектов, уже определённое в 147–152. Применить согласованное правило инвалидации при восстановлении фактов из кеша. Достаточно консервативного расширения для этой редкой правки; semantic diff на запросе не требуется.

Добавить fixture: существующий AssemblyInfo.cs без member-узлов, добавление/удаление InternalsVisibleTo, неизменный тест с extension/instance rebinding.
