# F-005 — Прежняя extension-цель в библиотеке-зависимости всё ещё не инвалидируется

Severity: major

Category: correctness

Confidence: high

Статус раунда 2: **остаётся открытым; исправлено частично**. Это продолжение [F-005 раунда 1](../../findings/F-005.md), а не новая находка.

## Target

docs/rapid-tia/README.md:211–220 — «Изменения связывания (R-14)»; ответ автора Codex F-005 в docs/rapid-tia/review-round-1-responses.md:31.

## Claim

Новая формулировка правильно убрала ограничение иерархией extension-контейнера, но ограничила пометку членов проектом нового метода и проектами-потребителями. Прежняя extension-цель может принадлежать исходникам библиотеки, от которой эти проекты зависят. Такой узел по-прежнему не помечается.

## Evidence

- Строки 211–214 требуют пометить прежнюю baseline-цель либо расширить ответ до файла/проекта.
- Строки 218–220 помечают одноимённые члены только «в его проекте и проектах, которые от него зависят».
- Хранение различает owner узла по исходному проекту и сборке (238–246). Член Library не становится членом App или Tests только потому, что виден в их компиляциях.
- На установленном Roslyn 5.9.0 проверены три отдельные компиляции: Library, App, Tests; App ссылается на Library, Tests — на обе. При неизменном вызове Render на string результат binding:

    before: Library / M:Shared.OldExtensions.Render(System.Object)
    after: App / M:Shared.NewExtensions.Render(System.String)

  Все компиляции в обеих конфигурациях не имеют ошибок. Детали — в [recheck.md](../recheck.md).

## Why it matters

Это обычная source-only зависимость между проектами, а не metadata leaf или reflection. Новая цель отсутствует на baseline-пути, старая расположена за пределами описанной пометки. Поэтому explicit exception к достаточности baseline всё ещё не выполняет свой контракт.

## Failure scenario

1. Library объявляет OldExtensions.Render(this object) в namespace Shared.
2. App уже ссылается на Library; в нём есть NewExtensions.Existing, достижимый из отдельного TestB.
3. Неизменённый TestA из Tests вызывает Render на string и в baseline достигает Library.OldExtensions.Render.
4. В существующий NewExtensions.cs проекта App добавляется Render(this string). Ранний pruning не является причиной сбоя: файл уже содержит достижимый Existing.
5. Правило помечает одноимённые члены в App и Tests. Узел Library.OldExtensions.Render туда не входит; ни существующий TestA, ни его baseline-узлы не изменены. TestA пропущен, хотя компилятор уже выбирает новую цель App.

## Violated requirement / constraint

R-14 и явное требование строк 211–214 пометить прежнюю цель либо консервативно расширить ответ. R-02 включает исходники Library в анализ; это не принятая слепая зона.

## Recommended change

Для нового extension-метода использовать предусмотренное R-14 расширение до его проекта и зависимых тестовых проектов либо помечать прежние цели соответствующих baseline call sites, независимо от проекта-владельца цели. Если сохраняется пометка по имени, её scope должен включать подходящие цели из библиотек-зависимостей. Добавить трёхпроектный fixture Library → App → Tests с прежней целью в Library.

## Notes for arbitration

Исходный одно-проектный пример исправлен, что признаётся в перепроверке. Но смена контейнера и владельца проекта не меняет root cause F-005, поэтому отдельный F-008 не заводится. Выбор VTA, пересмотр R-05 или полная перестройка графа не нужны; консервативное расширение уже разрешено владельцем.
