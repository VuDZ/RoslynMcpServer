# F-006 — Fallback устаревшего документа не включает собственный проект

Severity: major

Category: recovery

Confidence: high

Статус раунда 2: **остаётся открытым; исправлено частично**. Это продолжение [F-006 раунда 1](../../findings/F-006.md), а не новая находка.

## Target

docs/rapid-tia/README.md:330–338, 364–366 — ответ на сохранённом графе и повторное использование правила для graph built after edits; ответ автора Codex F-006 в docs/rapid-tia/review-round-1-responses.md:32.

## Claim

Новое правило учитывает влияние исходящих рёбер stale-документа, но проверяет только транзитивные зависимости его проекта. Проект не зависит от самого себя. Поэтому случай, где фабрика и новая реализация находятся в одном production-проекте, остаётся без fallback.

## Evidence

- Строки 336–338 добавляют достигающий stale-члена тест, только если проект изменённого члена входит «в транзитивные зависимости проекта устаревшего документа».
- Проверка равенства проектов не названа, хотя в других местах документа явно используется формулировка «его проект и зависимые» (221–222, 318–320).
- [ProjectDependencyGraph.GetProjectsThatThisProjectTransitivelyDependsOn](https://learn.microsoft.com/en-us/dotnet/api/microsoft.codeanalysis.projectdependencygraph.getprojectsthatthisprojecttransitivelydependson?view=roslyn-dotnet-5.0.0) возвращает зависимости проекта. На установленном Roslyn 5.9.0 это отдельно проверено для графа Tests → App:

    Deps(App) contains App: False
    Deps(Tests) contains App: True

- Для документа, изменённого до построения graph built after edits, строки 364–366 применяют то же правило, поэтому пробел относится и к этому режиму.
- Ответ автора разбирает расположение B в зависимостях фабрики; вариант B и фабрика в одном проекте не рассмотрен.

## Why it matters

Фабрики и их реализации часто находятся в одном проекте. Поэтому пропуск затрагивает основной сценарий исходного finding, а не редкую форму dependency graph. Уточнение маленькое, но без него кеш может скрыть реально затронутый тест в заявленно поддержанной части анализа.

## Failure scenario

1. App содержит Factory.cs, A.cs и B.cs. Сохранённые факты Factory.Make создают A.
2. TestA вызывает Factory.Make().Run(); другой тестовый класс TestB создаёт B напрямую.
3. До load Factory.Make меняется на создание B. После load Factory.cs stale, а B.cs соответствует сохранённому тексту.
4. Пока refresh удержан, после load меняется B.Run. Старые битсеты выбирают TestB, но не TestA.
5. TestA достигает stale Factory.Make, однако проверка App ∈ Deps(App) ложна. Описанное расширение не добавляет TestA. При этом на текущем baseline он исполняет именно B.Run.

## Violated requirement / constraint

R-03/R-04 и обещание безопасного консервативного расширения stale paths в строках 330–338. Исключение собственного проекта не является принятым ограничением R-01.

## Recommended change

Явно определить условие: проект изменённого члена равен проекту stale-документа **или** входит в его транзитивные зависимости. В каталог F-006 добавить оба размещения: фабрика/реализация в одном проекте и реализация в отдельном проекте-зависимости. То же условие применять в graph built after edits.

## Notes for arbitration

Если под «транзитивными зависимостями» автор имел в виду рефлексивное замыкание, намерение достаточно записать явно. Стандартный Roslyn API его не даёт; противоположное прочтение реализуемо напрямую и пропускает основной пример. Общий подход исправления принят, полный redesign cached reachability не требуется.
