# F-010 — Отчёт not run нельзя гарантировать в ответе отменённого MCP-запроса

Severity: minor

Category: integration

Confidence: high

## Target

docs/rapid-tia/README.md:476–483, 607–608 — «Сбои и таймаут прогона» и проверка отмены.

## Claim

План обещает перечислить не стартовавшие процессы в ответе после отмены самого MCP-запроса. Такой ответ не является гарантированным каналом доставки: cancellation прекращает ожидание результата и может запрещать отправку ответа SDK. Это отличается от таймаута дочернего процесса при ещё активном tools/call.

## Evidence

- В строках 481–483 явно названа «отмена MCP-запроса», а не внутреннее прекращение batch.
- [MCP cancellation, 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/cancellation) рекомендует получателю не отвечать на отменённый запрос, а инициатору игнорировать поздний ответ. Это поддержанная в репозитории версия: RoslynMcpServer.Tests/Support/McpInitializeHandshake.cs:11.
- В закреплённом [C# SDK v2.2.0, McpSessionHandler](https://raw.githubusercontent.com/modelcontextprotocol/csharp-sdk/v2.2.0/src/ModelContextProtocol.Core/McpSessionHandler.cs) HandleRequestAsync отправляет ответ с request token; SendMessageAsync проверяет отмену. На клиенте ожидание прекращается тем же token; pending request удаляется. Возврат строки из tool handler не гарантирует доставку.
- Версия ModelContextProtocol в RoslynMcpServer.csproj:104 — 2.2.0.
- Services/Build/DotNetCliRunner.cs:222–225 убивает дерево процесса и пробрасывает отмену. Tools/TestTools.cs:725–730 формирует строку при отмене, но это остаётся внутренним результатом метода, не доказательством ответа клиенту.

## Why it matters

Implementer может написать тест, вызывающий C# handler напрямую, и принять delivery contract, который не работает через реальный MCP client. Агент не получит обещанный список not run и не сможет восстановить фактически выполненную часть batch из отменённого ответа.

## Failure scenario

Batch закончил первый проект и выполняет второй. Клиент отменяет tools/call; остальные процессы не стартуют. Handler останавливает текущий процесс и строит отчёт, но request token уже отменён, а клиент перестал ждать результат. Требуемый not run не отображается, хотя unit-тест метода с return string может выглядеть корректным.

## Violated requirement / constraint

Обещание отчёта в строках 481–483 и acceptance отмены в 607–608. Протокол не даёт указанной гарантии доставки.

## Recommended change

Разделить timeout процесса и cancellation MCP-запроса. Для timeout при активном запросе возвращать частичный отчёт. Для MCP cancellation требовать остановку, отказ от старта оставшихся процессов и локальную фиксацию состояния; доставку обычного ответа считать best effort. Если восстановление отчёта после отмены обязательно, отдельно определить чтение сохранённого результата новым запросом через имеющийся механизм отчётов.

## Notes for arbitration

Новая операция stop, фоновое выполнение MCP tasks и отдельный инструмент не обязательны. Минимальное исправление — корректный delivery contract и транспортный тест вместо одной проверки return value handler. Полный runtime-прогон SDK в этом review не выполнялся; вывод основан на первичном протоколе, исходниках закреплённого SDK и текущем runner.
