# F-008 — Новый instance-метод не инвалидирует extension, объявленный в потребителе

Severity: major

Category: correctness

Confidence: high

## Target

docs/rapid-tia/README.md:77–82, 219–238, 588–592 — сопоставление новых членов и правило «новый метод в обычном типе».

## Claim

Для нового обычного метода помечаются одноимённые extension-методы, видимые из проекта изменённого типа. Но вытесненный extension может быть объявлен в проекте-потребителе, который ссылается на этот тип. Из production-проекта такой extension не виден, поэтому прежняя baseline-цель остаётся непомеченной.

## Evidence

- Строки 224–225 ограничивают extension scope видимостью «из проекта типа», а не из проекта вызывающего кода.
- R-14 требует помечать именно прежнюю цель или применять консервативное расширение (219–222).
- Новое правило уровня проекта в строках 226–230 относится к добавлению extension-метода; здесь добавляется обычный instance-метод.
- Каталог прямо обещает случай «новый метод экземпляра, скрывающий extension» (591).
- Семантическая проба на Roslyn 5.9.0 с двумя компиляциями App и Tests дала для неизменного вызова:

    before: Tests / M:ConsumerExtensions.Render(Shared.Widget)
    after: App / M:Shared.Widget.Render

  App содержит два отдельных syntax trees, App.cs и Widget.More.cs; все компиляции обеих конфигураций имеют 0 ошибок. Методика — в [recheck.md](../recheck.md).

## Why it matters

Проект библиотеки не может видеть extension, объявленный её потребителем, хотя такой вызов совершенно обычен и статически разрешим. Это конкретный пропуск внутри заявленного правила связывания, без reflection, NuGet или динамического создания.

## Failure scenario

1. App.cs объявляет partial Widget с явным конструктором. Widget.More.cs уже содержит Widget.Existing, используемый другим тестовым классом.
2. Tests ссылается на App и объявляет ConsumerExtensions.Render(this Widget). TestA вызывает new Widget().Render(); baseline ведёт в extension из Tests.
3. В Widget.More.cs добавляется обычный Widget.Render(). Неизменённый TestA теперь вызывает его.
4. В иерархии Widget прежнего Render нет; ConsumerExtensions не виден из App. Пометка строк 224–225 не находит прежнюю цель из Tests.
5. Fallback для несопоставленного нового ключа до всех узлов Widget.More.cs не спасает: TestA достигает конструктора в App.cs и extension в Tests, но не Existing из Widget.More.cs. Изменения partial-заголовка нет. TestA пропущен.

## Violated requirement / constraint

R-14, правило нового обычного метода в строках 224–225 и обещанный fixture instance-over-extension в строке 591.

## Recommended change

Для нового обычного метода учитывать extension-цели baseline call sites в проектах-потребителях либо применять уже разрешённое R-14 расширение до проекта типа и зависимых тестовых проектов. Не ограничивать поиск extension видимостью из production-проекта. Проверить случай с extension в Tests и добавлением instance-метода в другой partial-файл App.

## Notes for arbitration

F-005 закрывается: его правило добавления нового extension теперь расширяет ответ до проекта и устраняет прежний контрпример Library/App/Tests. F-008 относится к другой ветви — добавлению обычного метода — и не дублирует активный F-005. В первых раундах упоминался общий instance-over-extension случай; подтверждённый здесь обратный scope потребителя ранее отдельно не проверялся.
