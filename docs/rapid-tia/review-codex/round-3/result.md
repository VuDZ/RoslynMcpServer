- F-005 исправлен проектным расширением для нового extension; F-006 — явным equality проектов. К пяти ранее подтверждённым исправлениям добавляются ещё два, всего **7 собственных первоначальных IDs**.

## Highest risks

1. Корректный static call после добавления instance-метода не попадёт в выбранный набор, потому что прежний extension находится в Tests и вне названного visibility scope.
2. Тесты выбраны верно, но run показывает passed на старой DLL. Приблизительность dependency analysis не оправдывает этот execution gap.
3. После отмены batch агент не получает обещанного перечня не выполненных процессов через уже отменённый request.

## Questions / uncertainties

- Для добавления обычного метода будет консервативное project expansion или пометка старых целей из call-site scopes потребителей?
- Что обязан делать run перед тестовыми процессами: pre-build, проверка существующих outputs либо явный precondition внешней сборки? Выбор сейчас не определён.
- Требуется ли гарантированно восстанавливать batch report после cancellation новым запросом или достаточно best-effort/local logging?
- Значения O-03/O-06/O-07/O-08 не выбираются этим review; отсутствие замеров не заменяется reviewer preference.

## Suggested spikes

Новая большая исследовательская программа не требуется:

- binding-предпосылка F-008 уже проверена; достаточно перенести двухпроектный partial-case в планируемый каталог;
- для F-009 нужен интеграционный случай с намеренно старыми binaries и изменённым production-body;
- для F-010 проверять cancellation через MCP client, а не только return value tool handler.

Замеры MTP process overhead и гипотезы cache/RTA остаются в предусмотренных эпохах.

## Overall assessment

Обоснованы приблизительная подача, source-only scope, обязательность main CI, явный уровень 0, неизвестный baseline вместо поздно прочитанного «нулевого diff», состав ответа с прямыми test roots, owner-scoped facts и stale fallback с self.

Новые run/MTP условия теперь достаточно конкретны для проверки: один MCP-вызов не смешивается с одним процессом, причины whole-project видны заранее, резерв C закрыт до spike. Требуется дополнить именно build freshness и delivery cancellation, а не пересматривать выбранный владельцем process-per-class.

До закрытия F-008/F-009 план требует исправлений. F-010 — локальная корректировка transport contract. Полная [граница проверки](coverage.md) отделяет API-пробу от будущей runtime-приёмки.
