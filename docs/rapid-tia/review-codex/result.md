## Verdict

Направление пригодно для приблизительной подсказки, однако описанный алгоритм теряет несколько обычных, явно входящих в scope изменений. До реализации соответствующих эпох нужно уточнить захват baseline, включение новых тестов, обработку связывания, идентичности графа и границу доверия к сохранённой достижимости.

Найдено **6 major и 1 minor**. Blocker не выставлен: имеются локальные исправления или консервативные откаты до уровня 0; менять принятое владельцем направление целиком не требуется.

## Summary

- Неизменяемость Solution не фиксирует ещё не прочитанные тексты. У delayed baseline отсутствует определённый протокол acquisition/retention при edit и reset.
- Сам факт изменения нового теста не включает его в baseline-битсеты. Ранний pruning дополнительно отбрасывает новые документы.
- Member-only diff пропускает using aliases/global usings; правило extension invalidation не достигает прежних целей в других контейнерах.
- Documentation ID без project owner и синтаксический ключ без generic arity могут склеивать разные узлы.
- Stale facts влияют на RTA других документов; fallback только по месту нового edit недостаточен.
- Точное множество integration roundtrip не согласовано с contains-фильтром helper.

Эти замечания не требуют полноты статического анализа. Reflection, metadata leaves, source generators и SourceStructure остаются сознательно принятыми границами R-01/R-02/R-10. Отсутствие динамического покрытия само по себе не является дефектом плана.

## Highest risks

1. Для ранних эпох: обычная правка исчезает из памяти сессии или новый регрессионный тест не включается в подсказку. R-01 допускает ошибку оценки зависимости, но не обосновывает эти противоречия собственным правилам обнаружения изменений.
2. Для эпохи 2/формата эпохи 4: незафиксированная составная идентичность ведёт к переделке фактов, edges и persistence.
3. Для эпохи 4: немедленный cached-ответ использует неверный RTA за пределами stale-файла, хотя ответ обещает fallback для устаревших частей.

## Questions / uncertainties

- Как фиксируется baseline для ещё не прочитанного файла, если обычная загрузка и инструменты не должны ждать фоновое построение?
- Что сохраняется при reset, если синтаксический снимок baseline ещё не завершён? Как обозначаются неизвестные исходные тексты?
- Каков owner каждого persisted document/node и как syntactic key однозначно отображается на declaration ID?
- До refresh недоверие относится только к stale document или ко всему зависимому тестовому контексту?
- Интеграция фильтра должна запускать точное множество или явно разрешённое надмножество?
- O-03/O-06 и необходимость VTA обоснованно оставлены до измерений. Их численные значения этим review не выбираются.

## Suggested spikes

- Перед реализацией acquisition baseline: ordinary load на Roslyn 5.9.0 с удержанным прогревом до первого чтения, внешним edit и reset до завершения снимка. Проверить исходные хеши и сохранность событийного уровня 0.
- В уже запланированном прототипе уровня 1: stale-cache контрпример из F-006 и owner-scoped graph для linked source/двух проектов с одинаковыми FQN. Эти небольшие проверки должны предшествовать большой матрице recall/performance.

Отдельная новая исследовательская программа не предлагается; остальные findings достаточно закрепить точными fixtures в существующем каталоге граничных случаев.

## Overall assessment

Обоснованы: приблизительное позиционирование инструмента, обязательное предупреждение, сохранение полного CI, отдельный уровень 0, использование source-only графа, RTA по тестовому классу и замеры до production уровня 1.

Требуют изменения: правила из F-001–F-006 и несогласованный acceptance из F-007. Первые три замечания затрагивают подготовку ранних эпох; вопросы идентичности нужно закрыть до закрепления модели фактов, cached-fallback — до эпохи 4.

Требуют проверки: реальные пределы памяти/CPU, стоимость восстановления reachability и выигрыш частичной актуализации. Эти измерения review не выполнял.

Требуют выбора владельца только при необходимости: компромисс точной фиксации baseline с задержкой загрузки, если он не решается без изменения R-03/R-08. Ревью не меняет принятые R-* и не выполняет арбитраж.
