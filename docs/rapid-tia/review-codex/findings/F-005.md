# F-005 — Инвалидация extension-вызовов ограничена неверной иерархией

Severity: major

Category: correctness

Confidence: high

## Target

docs/rapid-tia/README.md:89–92, 133–138, 329–330 — достаточность baseline и правило новой перегрузки/extension-метода.

## Claim

Добавление extension-метода может изменить цель неизменённого вызова на метод из другого статического класса, не связанного иерархией с прежним контейнером. Пометка одноимённых членов только типа и его иерархии не захватывает прежнюю baseline-цель. Именно по ней битсет хранит зависимость теста.

## Evidence

- План признаёт изменения связывания исключением из доказательства достаточности baseline.
- Для нового extension-метода в строке 136 предписано помечать одноимённые члены типа и его иерархии.
- Extension-кандидаты могут находиться в разных статических классах одного импортированного namespace. Эти классы не составляют иерархию, а extension-метод не становится членом типа получателя.
- Каталог случаев обещает extension-метод при неизменном вызывающем коде (329–330), но описанное правило не покрывает этот обычный случай.

## Why it matters

Неизменённый тест начинает выполнять новый метод, однако новый метод отсутствует в baseline-пути, а старый метод не помечен изменённым. Это конкретный незакрытый случай внутри явно обещанной поддержки binding changes.

## Failure scenario

Baseline: в одном namespace существует OldExtensions.Render(this object); TestA вызывает Render на string и достигает OldExtensions.Render.

В существующий NewExtensions.cs добавляется Render(this string). В этом файле уже есть другой метод, достижимый из TestB, поэтому файл проходит ранний фильтр и сценарий не зависит от F-002. Новый, более подходящий extension выбирается неизменённым вызовом TestA. NewExtensions и OldExtensions не находятся в одной иерархии; одноимённых baseline-членов в NewExtensions нет. TestA не включается.

## Violated requirement / constraint

Явное правило обработки новой перегрузки или extension-метода и обещание соответствующего граничного случая. R-01 разрешает неточность, но не делает описанное правило достаточным для заявленного случая.

## Recommended change

Для новых extension-кандидатов учитывать соответствующие baseline call sites/прежние цели в допустимом scope поиска либо консервативно откатываться до проекта и зависимых тестовых проектов. Не ограничивать invalidation наследованием контейнера. Добавить тест с двумя разными extension-классами и неизменённым вызывающим кодом; отдельно определить shadowing extension-вызова новым instance-методом.

## Notes for arbitration

Полная перестройка графа на каждый edit не обязательна; локальный откат допустим для rapid TIA. Нужно уточнить, какой именно «тип» имеется в виду в строке 136: ни контейнер нового extension, ни receiver type с его иерархией сами по себе не перечисляют все прежние extension-цели.
