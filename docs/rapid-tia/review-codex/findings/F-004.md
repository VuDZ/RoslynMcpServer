# F-004 — Предложенные ключи не различают все члены и контексты проектов

Severity: major

Category: isolation

Confidence: high

## Target

docs/rapid-tia/README.md:61–63, 142–150, 182–187 — ключ синтаксического члена, идентификатор узла и сохранение фактов.

## Claim

GetDocumentationCommentId сам по себе не является уникальным идентификатором узла в solution: он не включает сборку/проект. Путь документа также не определяет его semantic context. Кроме того, описанный синтаксический ключ «тип, имя, синтаксис параметров» не различает generic-перегрузки с разной арностью. Не определена составная идентичность и её отображение между синтаксическим baseline и persisted graph.

## Evidence

- В строке 145 именно DocumentationCommentId объявлен идентификатором узла, без project-instance scope.
- [C# documentation ID format](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/documentation-comments#d42-id-string-format) содержит вид сущности, namespace/type/member и параметры; assembly identity в этом формате нет.
- Консольная проба на Roslyn 5.9.0 с двумя компиляциями First и Second, каждая с Shared.Helper.Run, дала в обоих случаях один ID: M:Shared.Helper.Run.
- В существующем Services/Models/LoadedProjectInstance.cs прямо зафиксировано, что идентичность — ProjectId, а не имя или путь проекта. Services/Models/InputOccurrence.cs хранит ProjectId и DocumentId отдельно от пути.
- RoslynMcpServer.Tests/Workspace/WorkspaceSharedSourceSyncTests.cs:41–79 проверяет один физический файл в двух проектах с разными parse options и разным набором членов.
- Уже существует стабильный project-context key: Services/Workspace/StateCache/Models/SnapshotProjectKey.cs — ProjectPath, Configuration, Platform, TargetFramework.
- Два корректных метода Run<T>() и Run<T, U>() в одном типе имеют одинаковые «тип, имя, синтаксис параметров» из строки 63, но являются разными членами.

## Why it matters

Слияние идентичностей может перезаписать факты одного проекта фактами другого, смешать RTA-created types и тесты, а также потерять изменённый член. После выбора дискового формата исправление потребует изменения схемы и всех ключей; это нужно решить до прототипа хранения.

## Failure scenario

Два тестовых проекта компилируют linked Shared.cs с Shared.Helper.Run, но разными #if. Оба узла имеют M:Shared.Helper.Run. Без owner key объединение фактов/битсетов или обновление одного документа не может однозначно выбрать нужный экземпляр. Независимый локальный пример — две generic-перегрузки Run с разной арностью, попадающие в один синтаксический ключ.

## Violated requirement / constraint

R-02 — граница всего solution, без ограничения на уникальные полные имена между проектами; частичная актуализация по документам; RTA в контексте конкретного тестового класса. Неявный / отсутствует — требуется уточнение составной идентичности узлов и документов.

## Recommended change

Определить graph node как минимум в scope стабильного project instance плюс declaration ID; document facts — в scope проекта и документа, с поддержкой нескольких memberships одного пути. Зафиксировать отображение синтаксического ключа на baseline-node, включая generic arity, вид члена и явную реализацию интерфейса; при неоднозначности нужен определённый консервативный откат. Переиспользовать имеющиеся представления контекста там, где они подходят.

## Notes for arbitration

Хеш связывания проекта в файле кеша не устраняет коллизию, если project owner не участвует во всех ссылках на узлы и при объединении фактов. Finding снимается явным owner-scoped contract, а не обязательным выбором конкретного класса DTO. Проверить два проекта с одинаковыми FQN, linked source с разными symbols и generic-перегрузки.
