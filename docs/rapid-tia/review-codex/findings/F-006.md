# F-006 — Устаревшие факты меняют достижимость и в свежих документах

Severity: major

Category: recovery

Confidence: high

## Target

docs/rapid-tia/README.md:122–128, 193–214, 218–219 — RTA, немедленный ответ по сохранённым фактам и fallback для stale documents.

## Claim

Понижение до уровня файла/проекта только для изменённых членов, находящихся в stale documents, не изолирует устаревшую достижимость. Старое тело фабрики может задать неверное множество created types для всего тестового класса. Поэтому правка после загрузки в другом, свежем документе будет оценена по неверному RTA без обещанного fallback.

## Evidence

- Created types и виртуальные цели вычисляются неподвижной точкой в контексте тестового класса (122–128).
- Сначала достижимость выводится из сохранённых фактов и используется для немедленного ответа; обновление фактов идёт позже (195–203).
- Строки 212–214 задают fallback именно для «изменённых членов в документах, устаревших относительно сохранённого графа».
- Такая классификация относится к месту edit, но не к происхождению битсета теста. Правило недоверия к тестовым контекстам, которые использовали stale facts, отсутствует.
- Даже эвристическая инвалидация по поверхности объявлений здесь не помогает: в следующем сценарии меняется только тело фабрики.

## Why it matters

Статус «cached, refreshing; stale parts are file- and project-level» создаёт неверную границу доверия: старые части уже влияют на вывод о свежих. Это относится к корректности использования кеша до актуализации, а не к точности CHA против RTA.

## Failure scenario

1. В сохранённых фактах TestA вызывает Factory.Make().Run(); Make создаёт A. Класс B с другой реализацией Run существует и используется TestB из другого тестового класса.
2. До следующей загрузки тело Factory.Make меняется на создание B. Изменён только Factory.cs; B.cs и тесты имеют прежние тексты.
3. Новая загрузка устанавливает baseline уже с B, но до refresh использует старые факты фабрики. Factory.cs отмечен stale; в старом RTA TestA создаёт A.
4. После загрузки меняется тело B.Run. B.cs не stale относительно сохранённого файла, поэтому описанный fallback к нему не применяется.
5. Выбирается TestB; TestA пропущен. Между тем на текущем baseline он прямо выполняет B.Run. У фабрики нет изменений «since load», поэтому её stale-статус сам по себе не запускает уровень 0 по описанному правилу.

## Violated requirement / constraint

R-03/R-04 — подсказка о правках относительно загруженного baseline; заявленный fallback для устаревших частей в строках 212–219.

## Recommended change

Задать единицу доверия к cached reachability. Минимальный вариант: до обновления фактов stale-проекта понижать до уровня 0 также зависящие от него тестовые проекты, независимо от того, в каком документе сделана новая правка. Более точный вариант — отслеживать тестовые контексты, чьи выводы использовали stale facts, и применять fallback к ним. Добавить проверку «изменение фабрики до load + изменение реализации после load».

## Notes for arbitration

Если под «на уровне проекта» уже подразумевался весь dependency closure stale-проекта при любом запросе, это нужно сказать явно: текущая фраза ограничена местом изменённого члена. Такой контракт устранит finding. Порог полной перестройки O-06 не заменяет правило немедленного ответа до её завершения.
