# F-001 — Захват Solution не фиксирует baseline текстов на момент загрузки

Severity: major

Category: lifecycle

Confidence: high

## Target

docs/rapid-tia/README.md:61–79, 167–175, 225–238 — «Baseline и обнаружение изменений», «Фон после публикации», «Reload или reset в сессии».

## Claim

Неизменяемость объекта Solution ошибочно приравнена к наличию снимка содержимого всех файлов. Если текст ещё не прочитан, его loader может прочитать диск уже после правки. Фоновый расчёт checksum и хешей членов тогда принимает правку за baseline. Не определено и сохранение ещё не достроенного снимка при reset.

## Evidence

- R-03 определяет baseline как состояние на момент загрузки; строки 167–169 обещают именно этот baseline благодаря неизменяемости Solution.
- Хеши текстов и членов считаются в фоне, после публикации и прогрева (171, 235–238). Барьер материализации исходных текстов или протокол сохранения их предыдущих версий не описан.
- В текущем SolutionManager.LoadCoreAsync публикация и StartSearchPrewarm происходят отдельно (Services/Workspace/SolutionManager.cs:2181–2212); SetPublishedSolution не материализует тексты C# (1404–1418).
- Roslyn читает файл в FileTextLoader.LoadTextAndVersionAsync; TextDocumentState может хранить ленивый источник текста. Это видно в первичных исходниках [FileTextLoader](https://source.dot.net/Microsoft.CodeAnalysis.Workspaces/Workspace/Solution/FileTextLoader.cs.html) и [TextDocumentState](https://source.dot.net/Microsoft.CodeAnalysis.Workspaces/Workspace/Solution/TextDocumentState.cs.html).
- Консольная проба на установленном Roslyn 5.9.0: записать «before», создать FileTextLoader, записать «after», впервые вызвать LoadTextAndVersionAsync. Получено: «Captured FileTextLoader first read: after». Это проверка loader API, а не интеграционный прогон будущей фичи.
- Строки 225–233 разрешают отменить незавершённую работу и продолжить на новом Solution после reset. Если синтаксическая часть тоже не завершилась, описанного источника исходных хешей уже нет.

## Why it matters

Теряется заявленная память изменений с момента загрузки. Это ошибка границы baseline, а не ожидаемый пропуск reflection или другого статически невидимого вызова. Один и тот же edit может учитываться или исчезать в зависимости от расписания фоновой задачи.

## Failure scenario

1. Загрузка большого solution закончилась; прогрев ещё не дошёл до файла A.cs.
2. Внешний редактор изменяет тело A.Run.
3. Фон впервые читает A.cs через loader захваченного Solution и получает уже новый текст.
4. Новые хеши принимаются за baseline. Сравнение с текущим состоянием не обнаруживает edit; обещанное исключение откатов дополнительно позволяет убрать путь из результата.

Вариант: reset отменяет фон до завершения синтаксического снимка; новый Solution уже содержит правку, а старый снимок восстановить не из чего.

## Violated requirement / constraint

R-03; обещание точной привязки графа к baseline в строках 167–169; сохранение baseline при reload/reset в строках 76–79. R-08 при этом запрещает просто перенести тяжёлую работу в синхронную загрузку.

## Recommended change

Определить протокол фиксации и владения лёгким baseline независимо от semantic graph: когда гарантированно зафиксирован каждый исходный текст, что происходит при edit до его чтения и при reset до завершения. Для путей с неизвестным исходным текстом сохранять событийный уровень 0 и явное ограничение; не объявлять их неизменёнными по сравнению с поздно прочитанным текстом. Добавить детерминированный тест с удержанным фоном перед первым чтением.

## Notes for arbitration

Проба подтверждает поведение FileTextLoader 5.9.0; отдельно требуется проверить ordinary load с удержанным прогревом и внешней записью. Доказательство, что все тексты уже материализованы до публикации во всех поддержанных load paths, снимет первую часть finding. Если точный baseline требует дополнительного I/O при загрузке, выбор между этим и явно неполным baseline должен быть записан владельцем; неизменяемость Solution сама по себе его не решает.
