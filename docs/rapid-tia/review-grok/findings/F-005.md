# F-005 — Уровень 0 не задаёт, какой проект порождает не-C# путь, и читает устаревший граф зависимостей

Severity: major

Category: architecture

Confidence: high

## Target

`docs/rapid-tia/README.md`, «Уровень 0» и абзац «Уровень 0 от фона не зависит». Код наблюдения за диском: `WorkspaceDiskPathFilter`, `WorkspaceDiskEventClassifier`, `SolutionManager`.

## Claim

Уровень 0 — это «изменённые документы → их проекты → тестовые проекты по `ProjectDependencyGraph`», и на него же возложены csproj, props, json и resx. Эти пути часто не являются документами загруженного solution, а общий props не принадлежит одному проекту. Пока watcher уже пометил проектный граф устаревшим, `ProjectDependencyGraph` ещё старый, но ответ уровня 0 обещан сразу и без оговорки о staleness.

## Evidence

- Текст уровня 0 прямо включает изменения не в C#: csproj, props, json, resx. Отдельный список путей ведётся по событиям записи MCP и disk watcher и «доступен сразу».
- Проектный файл, `Directory.Build.props`, `Directory.Build.targets`, `Directory.Packages.props` и `global.json` классифицируются как graph file и помечают граф устаревшим, а не как грязный исходник (`WorkspaceDiskPathFilter.IsProjectGraphFile`, `SolutionManager` около обработки `decision.GraphFile` и `MarkProjectGraphStaleFromGraphFile`). Зависимости обновляются при следующей загрузке, не в момент события.
- `LoadAsync` не переиспользует workspace, если `_projectGraphStale`. До этой загрузки текущий `ProjectDependencyGraph` не содержит новую `ProjectReference`.
- Walk-up props наблюдаются точечно, импорт не вычислен: `WorkspaceInputMapBuilder`, категория walk-up — «Existence is recorded; import is not evaluated». Один файл выше корня влияет на много проектов. Правило «документ → его проект» не говорит, какие.
- resx / xaml / razor не синхронизируются как текст: их C# появляется из сборки (`WorkspaceDiskEventClassifier.SyncsNonCSharpDocumentText`). Json данных теста часто не является ни `Document`, ни additional file. В карте входов у неизвестного пути `ProjectId` пустой.
- Restore-входы (`project.assets.json`, `packages.lock.json`, `nuget.config`) в той же карте не индексируются как полный набор. Каталог случаев уровня программы включает «не-C# файл» и csproj с точным ожидаемым множеством.

## Why it matters

Уровень 0 — единственный ответ, пока графа нет, и единственный ответ для не-C#. Эпоха 1 сдаёт его вместе с каталогом точных множеств. Без правила «путь → проекты» и без реакции на устаревший граф зависимостей эти случаи нельзя реализовать одинаково, а немедленный ответ после правки csproj систематически молчит о новом тестовом проекте.

## Failure scenario

Агент добавляет `ProjectReference` тестового проекта на изменённую библиотеку и сразу вызывает инструмент, не дожидаясь reload. Событие csproj есть в списке путей. `ProjectDependencyGraph` ещё без этого ребра. Фильтр не содержит новый тестовый проект. Агент запускает прежний набор.

Второй случай: правка `Directory.Build.props` над несколькими тестовыми проектами. Один реализующий относит файл к ближайшему каталогу и возвращает один проект, другой — ко всем загруженным тестовым проектам. Оба чтения согласуются с текущим текстом.

Третий: правка json-фикстуры, которая не входит в граф документов. Событие watcher есть, проекта у пути нет. Инструмент не расширяет ни один проект либо расширяет все.

## Violated requirement / constraint

Уровень 0 обещает фильтр по затронутым тестовым проектам для не-C# сразу после события. Существующий watcher сознательно не обновляет граф проектов до reload (то же ограничение, из-за которого csproj не применяется из обработчика watcher). Текст программы это ограничение не переносит в контракт ответа.

## Recommended change

Разделить два отображения.

- Graph file (csproj, sln, props, targets, `global.json`): до reload, который снимет staleness, уровень 0 — все тестовые проекты загруженного solution, а строка состояния говорит, что граф проектов устарел. После reload — обычный `ProjectDependencyGraph` по уже обновлённым проектам.
- Прочий не-C# путь: если карта входов даёт проекты, брать их. Если нет — явное правило (каталог проекта-владельца или «не отнесён ни к одному проекту» плюс запись в `Not covered`). Не оставлять это реализационной догадкой.

Restore-входы либо включить в тот же список, либо явно назвать слепой зоной уровня 0.

## Notes for arbitration

Стоит сверить с уже принятой моделью покрытия входов: неизвестный путь не является доказательством, что он ни на что не влияет. Для TIA из этого следует грубый ответ или честный `Not covered`, но не тихий пропуск, если каталог случаев обещает точное множество.
