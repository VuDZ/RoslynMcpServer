## Цель

Чистая функция «синтаксическое дерево документа → снимок документа»: из чего потом
сравнение (task-02) находит изменённые члены. Без semantic model и без workspace.

## Входы и границы

[Программа](../README.md), раздел «Baseline и обнаружение изменений». Перед первой
правкой C# прочитать [code style](../../code-style.md) целиком.

Только модель и построение снимка одного документа. Жизнь снимка в сессии — task-03,
сравнение — task-02.

## Конкретный результат

- Снимок документа: checksum текста; хеш содержимого вне членов, раздельно по видам —
  обычные `using`/`using static`/alias/namespace, `global using`, атрибуты сборки и
  модуля; для каждого члена — синтаксический ключ и хеш синтаксиса.
- Синтаксический ключ: вид члена; путь объемлющих типов с generic-арностью каждого;
  имя; generic-арность члена; синтаксис параметров; интерфейс явной реализации.
- Объявление `partial`-члена хранится в снимке своего документа как обычный член с
  признаком `partial`. Снимок — один документ: сведение объявлений из разных файлов —
  не эта задача (task-02 сравнивает каждый документ, task-03 хранит снимки по
  документам, без схлопывания по ключу).
- Хеш не зависит от комментариев и пробелов, но сохраняет смысл директив препроцессора.
- Документ, который не разбирается до членов, помечается так, а не даёт пустой снимок.

## Порядок работы — TDD (R-16)

1. Сначала тесты из раздела «Проверки»: они пишутся до production-кода и падают по
   ожидаемой причине (red). Чтобы тест компилировался, допустимо завести пустой
   контракт — типы и сигнатуры с `NotImplementedException`; падение из-за ошибки
   компиляции или фикстуры красным прогоном не считается.
2. Затем минимальная реализация до зелёного прогона (green), затем рефакторинг при
   зелёных тестах.
3. Красный прогон фиксируется в отчёте задачи: какие тесты написаны первыми и вывод
   focused-прогона до реализации. В коммит идёт только зелёное состояние: main suite
   перед коммитом — по [AGENTS.md](../../../AGENTS.md).
4. Тест, добавленный после реализации, отмечается в отчёте отдельно с причиной.

## Проверки

Каталог случаев в памяти (`CSharpSyntaxTree.ParseText`, без MSBuild):

- generic-перегрузки `Run<T>()` и `Run<T, U>()` дают разные ключи;
- явная реализация интерфейса и обычный метод с тем же именем — разные ключи;
- объявление `partial`-члена получает ключ и признак `partial`;
- правка только комментария или пробелов не меняет хеши;
- правка внутри `#if` меняет хеш;
- изменения `using`, `global using` и `[assembly: …]` меняют соответствующий хеш вне
  членов и не меняют хеши членов.
