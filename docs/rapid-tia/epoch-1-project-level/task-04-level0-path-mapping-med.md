## Цель

Сервис «изменённый путь → затронутые проекты → тестовые проекты» и одно определение
проектного расширения, на которое ссылаются все правила программы.

## Входы и границы

[Программа](../README.md): разделы «Уровень 0: по проектам» и «Состав ответа»
(определение «Проектное расширение проекта P»). Перед первой правкой C# прочитать
[code style](../../code-style.md) целиком.

Существующие механизмы используются повторно:
[WorkspaceInputMapBuilder](../../../Services/Workspace/WorkspaceInputMapBuilder.cs),
`WorkspaceDiskPathFilter.IsProjectGraphFile`, признак устаревшего графа проектов в
`SolutionManager`. Распознавание тестового проекта — как в существующем обнаружении
тестов.

## Конкретный результат

- Проектное расширение проекта P: P, если в нём есть тесты, плюс все тестовые проекты
  из `ProjectDependencyGraph.GetProjectsThatTransitivelyDependOnThisProject`.
- Отображение путей:
  - C#-документ — все проекты, в которые он входит;
  - новый `.cs`, которого нет в workspace, — ближайший проект по каталогу и признак
    «нужен reload»;
  - файл графа проектов — до reload все тестовые проекты загруженного solution и
    состояние «граф проектов устарел»;
  - прочий не-C# путь — проекты из карты входов; без проектов — запись для «Not
    covered» с именем файла;
  - вывод сборки: путь под игнорируемым каталогом (имена из `WorkspaceDiskPathFilter`, например
    `bin`, `obj`), которого нет в карте входов, — без расширения и без записи для «Not covered».
    Префикс пути, общий с каталогом solution, не считается: в репозитории внутри каталога
    `artifacts` обычный не-C# путь вне карты остаётся «Not covered», а при solution в `build/`
    вывод сборки `src/App/bin` остаётся выводом сборки. Журнал task-03 такой вывод сохраняет, отбор
    здесь ([ревью task-03, раунд 5](evidence/task-03-review-round-5.md),
    [раунд 9](evidence/task-03-review-round-9.md), [раунд 11](evidence/task-03-review-round-11.md));
  - restore-входы — слепая зона, без расширения.

## Порядок работы — TDD (R-16)

1. Сначала тесты из раздела «Проверки»: они пишутся до production-кода и падают по
   ожидаемой причине (red). Чтобы тест компилировался, допустимо завести пустой
   контракт — типы и сигнатуры с `NotImplementedException`; падение из-за ошибки
   компиляции или фикстуры красным прогоном не считается.
2. Затем минимальная реализация до зелёного прогона (green), затем рефакторинг при
   зелёных тестах.
3. Красный прогон фиксируется в отчёте задачи: какие тесты написаны первыми и вывод
   focused-прогона до реализации. В коммит идёт только зелёное состояние: main suite
   перед коммитом — по [AGENTS.md](../../../AGENTS.md).
4. Тест, добавленный после реализации, отмечается в отчёте отдельно с причиной.
