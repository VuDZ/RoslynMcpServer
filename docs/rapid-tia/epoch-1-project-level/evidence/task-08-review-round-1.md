## R1-001 — удаление загруженного C#-файла теряет путь до reload

- Место: [`TestImpactEstimator.cs:69`](../../../../Services/Testing/TestImpactEstimator.cs), `DocumentsAsync`, строки 67–89 рассмотренного состояния; связанный путь — `WorkspaceDocumentDiskSync.ApplyAsync`.
- Сценарий: загрузить solution, дождаться Known baseline, удалить на диске обычный C#-файл production-проекта с зависимым тестовым проектом, дождаться события watcher и вызвать инструмент **до reload**.
- Причина: disk sync намеренно не меняет состав solution при удалении — он оставляет старый `Document` и отмечает путь `Unrepresentable`. Однако estimator сначала удаляет все пути inventory из `changedPaths`, затем сравнивает прежний cached syntax tree с baseline. При равных снимках удалённый путь не возвращается. Mapper не получает причину расширения, а флаг изменения состава сам по себе не означает `ProjectGraphStaleFromGraphFile`.
- Неверный результат: пустой план вместо зависимого тестового проекта. Совет reload может присутствовать, но он не исправляет неверный перечень запуска.
- Минимальная правка: сохранить удаление как значимое изменение с консервативным расширением, даже когда workspace ещё содержит старый документ; добавить regression на публичный инструмент до reload. Имеющийся тест удаления проверяет только ответ после reload.
- Фактическое воспроизведение: координатор выполнил Release regression `Native_deleted_known_source_selects_its_dependent_tests_before_reload` через настоящий MSBuild load, Known baseline, native `File.Delete` и доставленное событие watcher. **1 выполнен, 1 failed** на ожидании `Specs.csproj` в публичном ответе; fixture preconditions прошли. Прогон до production-исправления, не ошибка setup. Исходный MCP output сохраняется в [RED раунда 1](task-08-review-round-1-red.md).

## R1-002 — проект только с унаследованными тестами отсутствует в обычном расширении

- Место: [`TestImpactEstimator.cs:25`](../../../../Services/Testing/TestImpactEstimator.cs), строки 25–38 рассмотренного состояния; [`ProjectImpactMapper.cs:119`](../../../../Services/Testing/ProjectImpactMapper.cs), `FindTestProjectsAsync`.
- Сценарий: в проекте A объявлен abstract `Base` с `[Fact] Inherited`; тестовый проект B содержит только `Derived : Base` и не объявляет собственных тестовых методов. Baseline известен, разрыва наблюдения нет. Изменить `Base.Inherited` либо обычный production-член зависимости B.
- Причина: mapper распознаёт тестовый проект только по собственным объявлениям методов с тестовыми атрибутами, поэтому B не попадает в `TestProjectIds`. Новый runtime inventory уже способен включить `B/Derived/Inherited`, но строится после `Compose` и присоединяет свои project ID к расширению только внутри `RequiresFullScan`.
- Неверный результат: план не содержит B, хотя VSTest исполняет унаследованный тест в B. В случае изменения abstract base прямой выбор относится к проекту объявления A и не заменяет запуск B.
- Минимальная правка: учитывать найденные runtime-классы при идентификации тестовых проектов в обычном пути отображения и расширения; regression должен явно исключать `RequiresFullScan`, который иначе маскирует дефект.
- Фактическое воспроизведение: Release regression `Real_MSBuild_inherited_only_test_project_is_selected_after_base_or_production_edit`, оба значения `editBase`. Реальный MSBuild load содержит source-связь `Specs/Derived → Library/Base`; precondition независимо проверяет наличие `Derived.Inherited` в runtime inventory. В обеих строках precondition прошёл, а **финальная** проверка `Specs.csproj` в ответе упала на строке 89 теста. Начальный вариант fixture, не прошедший inventory precondition из-за подготовки ссылок, был исправлен при неизменённом production и не считается доказательством дефекта.

## R1-003 — аргументы NUnit-фикстуры, унаследованные от базы, не попадают в runtime identity

- Место: [`VstestTestInventory.cs:97`](../../../../Services/Testing/VstestTestInventory.cs), `RuntimeIdentity`, строки 97–111 рассмотренного состояния.
- Сценарий: абстрактная база несёт `[TestFixture(42)]` либо `[TestFixtureSource]`, конкретный `Derived` наследует её, принимает соответствующие аргументы конструктора и объявляет собственный `[Test] Own`. Изменяется только `Derived.Own`, поэтому R-17 не требует расширения из-за правки самой базы.
- Причина: `type.GetAttributes()` возвращает непосредственно объявленные атрибуты. В отличие от обхода тестовых методов в `TestsOf`, поиск fixture metadata по `BaseType` не выполняется. `HasFixtureArguments` ошибочно остаётся false, а runtime-имя принимается за обычное `Ns.Derived`.
- Неверный результат: фильтр `FullyQualifiedName~Ns.Derived.Own` либо свёртка `Ns.Derived.` для фактического имени с аргументами фикстуры. Такой фильтр может выбрать ноль вместо изменённого теста; требуется явный whole-project fallback по T07-C1/T06-C1.
- Фактическое воспроизведение: координатор независимо выполнил discovery NUnit **4.3.2** / NUnit3TestAdapter **5.0.0** на двух валидных фикстурах и подтвердил `DerivedArgument(42).Own` и `DerivedSource(1).Own`. После правки `Own` публичный инструмент выдал фильтры `FullyQualifiedName~AdapterNames.NUnit.DerivedArgument.` и `FullyQualifiedName~AdapterNames.NUnit.DerivedSource.`. Настоящий MCP `run_test_by_filter` с `noBuild=true` в обоих случаях выбрал **0** тестов: NUnit discovered 0 of 0, exit 0 / partial. Это **не успешные тестовые прогоны**. Предупреждения об неизвестной identity или whole-project fallback не было.
- Исходные MCP zero-match outputs и протокол сохранены в [RED раунда 1](task-08-review-round-1-red.md#r1-003-унаследованные-аргументы-nunit). Локальные ignored доказательства координатора: `TestResults/task-08-smoke/inherited-plans.json`, `NUnitInherited-inherited-constructor.txt`, `NUnitInherited-inherited-source.txt`, `nunit-inherited.discovery.log`; изолированные fixture-проекты — `spikes/AdapterTestNames/artifacts/task08-NUnitInherited`. Рецензент самостоятельно прочитал оба ответа, raw discovery и сохранённые исходные MCP outputs.
- Минимальная правка: учитывать унаследованную fixture metadata либо явно считать такую runtime identity неизвестной; не угадывать имя класса без аргументов.
