### Вход из task-03

`BaselineSessionSnapshot.RequiresFullScan` отмечает разрыв наблюдения: reset и reopen,
переполнение буфера или ошибку watcher, сбой его запуска, отсутствующий каталог и настоящее
переименование каталога ([R2-001](evidence/task-03-review-round-2.md), уточнение
[R5-003, R5-004](evidence/task-03-review-round-5.md)). Каталог, исчезнувший без `Renamed`, даёт известные
входы в журнале либо флаг ([R14-001](evidence/task-03-review-round-14.md), закрыт). Обычные `git add` и `git commit` флаг не
поднимают, а разрыв до публикации не отменяет снимок. При нём `TouchedPaths` объединяет событийные пути и консервативные C#
кандидаты исходного/текущего inventory, а не доказывает полный список записей всех
входов проекта. Неизменённые Known C# снимки отбрасываются сравнением task-02;
отсутствие их дельты само по себе не подтверждает отсутствие изменений прочих входов.
Этот пробел наблюдения — вход существующей обработки «Not covered» и консервативного
проектного расширения ([контракт реализации и ограничения](task-03-implementation-report.md)).
Флаг не сбрасывается до загрузки другого solution, а наблюдение за не-C# входами после разрыва
не восстанавливается, поэтому после первого reload оговорка «Not covered» в ответе постоянна:
её вид проектируется с учётом этого, чтобы она оставалась полезной.
Известные границы ([раунд 21](evidence/task-03-review-round-21.md)): каталог с не-C# входом вне проекта, наблюдаемый
только собственным watcher, при выносе за пределы дерева не даёт никакого сигнала, это записанное ограничение;
после удаления и восстановления каталога правки не видны до reload, поэтому признак устаревшего графа в ответе
скрывать нельзя; на Linux при лимите 128 экземпляров inotify флаг в средних solution может быть поднят с загрузки.
R21-001 закрыт: пустой Deleted не обходит карту; массовое удаление node_modules50/200 не даёт ложного gap ([приёмка22/validation](evidence/task-03-final-validation-round-22.md)). Это не отменяет перечисленных ограничений. Массовое удаление из `obj` и при сотнях проектов из любого каталога всё ещё может поднять флаг ([раунд 22, второй рецензент](evidence/task-03-review-round-22-claude.md)). После готовности инструмента он прогоняется на проектах владельца: замеряется, как часто поднимается флаг и теряются ли тесты ([R-18](../README.md#решения-владельца-2026-10-29)).
Условия T04-C1 и T04-C2 ([второй рецензент task-04](evidence/task-04-review-round-1-claude.md)) исправлены в [task-05](task-05-response-composition-med.md#передача-из-task-04-обязательные-условия); здесь вызывающий код передаёт настоящие признаки устаревшего графа, а регрессии на настоящем watcher проходят через инструмент: новый файл в каталоге проекта не даёт все тесты, сразу после reload нет совета reload из-за удалённого `.cs`. Полная пересборка без правок даёт все тесты, это ограничение T04-C3. Внутренние механизмы приняты 2026-11-05: [ACCEPT task-05](evidence/task-05-review-round-1.md), [validation](evidence/task-05-final-validation.md); сквозные обязательства вызывающего кода task-08 остаются её scope.

## Передача из task-07 (обязательные условия)

[Второй рецензент раунда 1 task-07](evidence/task-07-review-round-1-claude.md): `VstestRunPlanner` имена не переводит,
он доверяет входу `VstestTestClass`. Правила [«Ответа инструмента»](../README.md#ответ-инструмента) по
[task-06](evidence/task-06-adapter-names.md) реализует вызывающий код здесь; способ выбирает исполнитель.

- **T07-C1.** Вход планировщика строится по фактическим runtime-именам, не по исходнику:
  - вложенный класс — через `+` (`Outer+Inner`);
  - унаследованный тест — под каждым конкретным неабстрактным наследником в тестовом проекте, не под базой;
  - generic-класс — только в измеренной закрытой форме (закрытый наследник у xUnit/MSTest, `GenericTests<Int32>` у
    NUnit `[TestFixture(typeof(int))]`); иначе имя неизвестно (`UnresolvedReason`);
  - `HasFixtureArguments` — для NUnit `[TestFixture]` с аргументами конструктора и `[TestFixtureSource]` (T06-C1);
  - `IsComplete` — только если инвентарь включает унаследованные тесты и все части `partial`;
  - всё неизвестное или неоднозначное передаётся как unresolved, без угадывания.
- Регрессия: через инструмент на фикстурах [spikes/AdapterTestNames](../../../spikes/AdapterTestNames/README.md) изменение
  каждого случая (вложенный, generic, унаследованный, параметризованный, фикстура с аргументами) даёт план, который
  выбирает этот тест, а не ноль. Пользовательские `TestName`/`DisplayName` и generic-методы фильтр метода не ломают
  (измерено вторым рецензентом), их отдельно помечать не нужно.

Лимит и критерий возврата — [R-18](../README.md#решения-владельца-2026-10-29).

## Раунд 3: R2-001 (решение владельца)

[Второй рецензент раунда 2](evidence/task-08-review-round-2-claude.md#r2-001--после-настоящего-reload-ответ-навсегда-все-тестовые-проекты-целиком):
настоящий reload того же solution поднимает `RequiresFullScan`, и инструмент до загрузки другого solution отвечает
«все тестовые проекты целиком», в том числе после отката всех правок. Исправить; способ выбирает исполнитель.

- Обычный reload того же solution не расширяет ответ до всех тестовых проектов; возможная незамеченная правка не-C#
  входа за время reload — строка в «Not covered». C#-документы сравниваются заново, как сейчас.
- Расширение всех тестовых проектов остаётся только для настоящих разрывов наблюдения (переполнение или ошибка watcher,
  сбой запуска, настоящее переименование каталога, ошибка снимка); reload его не сбрасывает.
- Регрессии на настоящем watcher и настоящем, не кешированном reload: после reload по совету инструмента (новый `.cs`,
  правка `.csproj`) независимый тестовый проект не попадает в план, правка теста снова даёт фильтр, после отката план пуст.

Это последний раунд по [R-18](../README.md#решения-владельца-2026-10-29); дальше решает владелец.

## Порядок работы — TDD (R-16)

1. Сначала тесты из раздела «Проверки»: они пишутся до production-кода и падают по
   ожидаемой причине (red). Чтобы тест компилировался, допустимо завести пустой
   контракт — типы и сигнатуры с `NotImplementedException`; падение из-за ошибки
   компиляции или фикстуры красным прогоном не считается.
2. Затем минимальная реализация до зелёного прогона (green), затем рефакторинг при
   зелёных тестах.
3. Красный прогон фиксируется в отчёте задачи: какие тесты написаны первыми и вывод
   focused-прогона до реализации. В коммит идёт только зелёное состояние: main suite
   перед коммитом — по [AGENTS.md](../../../AGENTS.md).
4. Тест, добавленный после реализации, отмечается в отчёте отдельно с причиной.
