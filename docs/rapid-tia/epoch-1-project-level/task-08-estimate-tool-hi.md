## Конкретный результат

- `estimate_affected_tests` в группе `core`; описание — черновик программы **для
  эпохи 1, без графа** (раздел «Ответ инструмента»): проектная оценка и её ограничения,
  без обещания графа вызовов. Описание с графом появляется в эпохе 3 вместе с ним.
- Ответ: первая строка — предупреждение; сводка изменений с момента загрузки; план по
  тестовым проектам с причинами; «Not covered» — конкретные места (пути вне карты
  входов, «baseline неизвестен», устаревший граф проектов, нужен reload); строка
  состояния `project-level result only`.
- Параметр подробности: полный список изменённых членов и тестов; по умолчанию —
  сводка.
- Пока в изменённых документах есть ошибки компиляции, ответ это называет.
- Новая minor-версия; изменение размера `tools/list` для `lite` записано.

## Порядок работы — TDD (R-16)

1. Сначала тесты из раздела «Проверки»: они пишутся до production-кода и падают по
   ожидаемой причине (red). Чтобы тест компилировался, допустимо завести пустой
   контракт — типы и сигнатуры с `NotImplementedException`; падение из-за ошибки
   компиляции или фикстуры красным прогоном не считается.
2. Затем минимальная реализация до зелёного прогона (green), затем рефакторинг при
   зелёных тестах.
3. Красный прогон фиксируется в отчёте задачи: какие тесты написаны первыми и вывод
   focused-прогона до реализации. В коммит идёт только зелёное состояние: main suite
   перед коммитом — по [AGENTS.md](../../../AGENTS.md).
4. Тест, добавленный после реализации, отмечается в отчёте отдельно с причиной.
