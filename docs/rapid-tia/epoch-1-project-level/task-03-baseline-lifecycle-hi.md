## Цель

Встроить baseline в [SolutionManager](../../../Services/Workspace/SolutionManager.cs):
когда снимок создаётся, как фиксируются тексты, что происходит при правках, reload и
reset. Плюс список затронутых путей с момента загрузки.

## Входы и границы

[Программа](../README.md): R-03, разделы «Фиксация baseline текстов», «Фон после
публикации», «Уровень 0 от фона не зависит», «Reload или reset в сессии». Перед первой
правкой C# прочитать [code style](../../code-style.md) целиком.

Извлечения фактов и графа нет (эпоха 3). Поколение загрузки вводится здесь, потому что
к нему привязан baseline; публикация графа по поколению — эпоха 3.

## Конкретный результат

- Список затронутых путей с момента загрузки — по событиям записи через MCP и disk
  watcher, доступен сразу, без фона.
- Фоновая задача после публикации загруженного solution: первым шагом читает и
  хеширует тексты захваченного `Solution` (task-01), не ждёт прогрева поиска, не
  компилирует. Блокировка workspace — только на захват.
- Состояние «baseline неизвестен» у пути, если событие записи пришло раньше записи его
  хеша или время последней записи файла позже момента публикации.
- Момент публикации фиксируется и снимок начинается только после старта disk watcher.
- Потеря наблюдения (`NoteCoverageUnknown`: переполнение буфера и ошибка watcher, сбой
  запуска, отсутствующий каталог; а также настоящее переименование каталога): незавершённые
  пути — «baseline неизвестен», `RequiresFullScan` поднят. Флаг, поднятый до первой
  публикации, её переживает, но захват выполняется; разрыв прежнего solution новый baseline
  не наследует. Имя файла без расширения само по себе разрывом не считается; такой
  неигнорируемый файл остаётся обычной записью журнала. Игнорируемые каталоги репозитория
  (`.git`, выход сборки вне карты входов) не поднимают разрыв и через обработчик переименования в
  журнал не попадают. У пути не учитывается только префикс, общий с каталогом solution: репозиторий
  внутри каталога `artifacts` наблюдается как обычный, а `obj` и `.git` вне каталога solution
  остаются игнорируемыми. Переименование пути из карты входов
  журналируется и под игнорируемым каталогом. Каталог, исчезнувший без `Renamed` (вынесен за пределы
  дерева, перенос между родителями на Windows): каждый известный вход под ним попадает в журнал либо
  поднимается флаг, в том числе для входов вне проекта. Обычное удаление каталога с файлами и каталог
  без известных входов флаг не поднимают.
- Снимки хранятся по документу (путь документа + ключ члена), без схлопывания
  одинаковых ключей разных документов — так объявления `partial` из разных файлов не
  затирают друг друга.
- `load_workspace` и `reset_workspace` того же solution baseline не сбрасывают; reload
  и reset до конца снимка сохраняют **уже записанные** хеши, остальные пути — «baseline
  неизвестен». Новый baseline — при загрузке другого solution или перезапуске сервера.
- Номер поколения загрузки. Записанный хеш baseline никогда не отбрасывается из-за
  смены поколения внутри того же solution. Задача прежнего поколения, завершившаяся после
  reload, не дописывает хвост: её незаписанные пути остаются «baseline неизвестен», а
  тексты, прочитанные после reload, baseline не становятся. При загрузке другого
  solution отбрасывается весь результат прежнего поколения.
- Отключение фона переменной среды (R-11) для этой задачи не требуется: снимок дешёвый;
  переменная вводится в эпохе 3 вместе с извлечением фактов.

## Порядок работы — TDD (R-16)

1. Сначала тесты из раздела «Проверки»: они пишутся до production-кода и падают по
   ожидаемой причине (red). Чтобы тест компилировался, допустимо завести пустой
   контракт — типы и сигнатуры с `NotImplementedException`; падение из-за ошибки
   компиляции или фикстуры красным прогоном не считается.
2. Затем минимальная реализация до зелёного прогона (green), затем рефакторинг при
   зелёных тестах.
3. Красный прогон фиксируется в отчёте задачи: какие тесты написаны первыми и вывод
   focused-прогона до реализации. В коммит идёт только зелёное состояние: main suite
   перед коммитом — по [AGENTS.md](../../../AGENTS.md).
4. Тест, добавленный после реализации, отмечается в отчёте отдельно с причиной.

## Проверки

- Интеграционный тест: фоновая задача удержана до первого чтения, файл изменён
  снаружи — путь получает «baseline неизвестен», а не «без изменений».
- Правка через MCP и правка на диске мимо MCP дают одинаковый результат.
- Защита по времени записи проверяется отдельно: файл изменён снаружи, событие watcher
  не доставлено (watcher отключён или событие подавлено в тесте) — путь получает
  «baseline неизвестен» по времени последней записи.
- Защита по событию проверяется отдельно: событие записи пришло до записи хеша, время
  файла не изменилось — тот же исход.
- `partial`-член с объявлениями в двух документах: правка каждого объявления даёт
  изменение члена в своём документе и не теряется из-за того же ключа в другом
  документе — хранение снимков по документу без схлопывания.
- Reload того же solution после правки csproj сохраняет baseline и список путей.
- Запоздалое завершение снимка после reload того же solution: записанные до reload
  хеши сохранены, хвост прежнего поколения не дописан и остаётся «неизвестен».
- Эти сценарии на реальной загрузке через MSBuild — red-фаза этой задачи; task-11
  только повторяет их в доказательствах приёмки.
- Reset до завершения снимка: записанные хеши сохранены, остальные — «неизвестен».
- Загрузка другого solution создаёт новый baseline; результат задачи прежнего
  поколения отброшен.
- Разрыв наблюдения ([раунд 2 ревью](evidence/task-03-review-round-2.md)): переполнение буфера,
  сбой запуска watcher до первой публикации, переименование каталога с документом — журнал
  неполон, `RequiresFullScan` поднят; событие закрытой сессии флаг не меняет.
- Окно публикации: правка уже записанного файла в момент старта watcher не теряется;
  запись между стартом watcher и публикацией даёт «baseline неизвестен». Проверка не зависит от
  гонки и sleep. Guard: обычная запись без разрыва флаг не поднимает; cached load не прерывает
  захват; записанный `Known` при разрыве не теряется.
- Ложный разрыв и разрыв до публикации ([раунд 5 ревью](evidence/task-03-review-round-5.md)):
  реальные `git add`, `git commit`, переименование файла в имя без расширения — флаг не поднят,
  `.git/*` нет в журнале; сбой запуска до первой публикации — флаг поднят, документы `Known`.
  Guard: настоящее переименование каталога и `rename_project` поднимают флаг.
- Solution в подкаталоге ([раунд 11 ревью](evidence/task-03-review-round-11.md)): `build/All.slnx` —
  переименование каталога в `obj` соседнего проекта и в `.git` флаг не поднимает, `git add` и
  `git commit` не пишут `.git` в журнал; настоящее переименование каталога в `src/App` флаг поднимает.
- Переименования в журнале ([раунд 9 ревью](evidence/task-03-review-round-9.md)): репозиторий
  внутри каталога `artifacts` — переименование `.cs` даёт оба пути в журнале, настоящее
  переименование каталога поднимает флаг, `git add` и `git commit` его не поднимают; явный вход
  под `obj` — переименование и сохранение через временный файл дают путь в журнале.
- Каталог без `Renamed` ([раунд 14 ревью](evidence/task-03-review-round-14.md)): вынесен за пределы дерева —
  `Compile` по маске и явный, подключённый ссылкой каталог, в том числе с собственным watcher; перенос между
  родителями на Windows настоящим запуском; подставленные `Deleted` и `Created` каталога — известный вход в
  журнале либо флаг поднят. Guard: рекурсивное удаление с файлом в журнале, каталог без входов и каталог
  под `obj` флаг не поднимают.
- Устойчивость на Linux: не менее трёх полных прогонов main suite без падений; порядок
  «переименование каталога, затем `Semantic_sync…`» с заранее прочитанным текстом закреплён
  детерминированной регрессией; причина падения `Cached_load…` записана и устранена.

Это focused минимум; Release build, main suite и SourceStructure — по
[AGENTS.md](../../../AGENTS.md). Изменение пути загрузки и публикации может затронуть
lifecycle: оценить по AGENTS.md, нужен ли прогон `AnalyzerLifecycle`. Дата, scope,
evidence и фактические модели записываются в шапку и README эпохи после ревью и
validation.
