# Критика реализации usage-statistics

Создано: **2026-10-30**. Статус: **fixed** для F-001 и F-002 в версии 1.5.20; F-003 **resolved** уточнением измерений и модели M2 — см. [`.status`](.status), [результат исправлений](result.md#исправления-1520) и [уточнение F-003](result.md#уточнение-f-003).

Это не ревью спецификации. Спека [README.md](../README.md) и [schema.md](../schema.md) остаются нормой.
Пакет фиксирует расхождения кода версии **1.5.19** с этой нормой. Автоматизированный
[отчёт validation](../implementation.md) их не закрывает: синтетика `Test-McpUsage.ps1` однопроцессная,
а тест декомпилятора закрепляет нынешний флаг `requires_workspace`.

## Исходные указания для исправления F-001 и F-002

1. Прочитать [result.md](result.md) и findings. Менять код только по F-001 и F-002.
2. F-003 не чинить заодно. Это развилка: код сознательно расходится с одним предложением M2,
   и отчёт validation называет это намеренным. Ждать выбора владельца.
3. Спеку, схему и критерии решения не переписывать. Не ослаблять проверки, чтобы текущее поведение стало «зелёным».
4. После правки F-001/F-002: точечные тесты из findings, затем `scripts/Test-McpUsage.ps1` (прежние сценарии остаются).
   Перед приёмкой — правила репозитория: SourceStructure и основной CI-набор. Patch-версия и `CHANGELOG.md`,
   если меняется поведение записи или отчёта.
5. По окончании правки сменить `.status` на `fixed` и дописать в [result.md](result.md) версию и что прогнано.
   Findings не удалять. Приёмку пакета этим не объявлять.
6. Проверку настоящих harness и сбор данных не начинать, пока F-001 и F-002 не закрыты:
   иначе M2 и M1/M3 уже испорчены в сыром ряду или в первом отчёте.

Вне пакета, не трогать попутно: формат ключа, набор счётчиков памяти, fail-open писателя,
ротация, приватность агрегатов, отсутствие автовыбора стратегии.
