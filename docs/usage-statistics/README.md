принят, production-кода темы нет.

Реализация подготовлена в ветке `usage-statistics` для вливания в main. Ветка исследования потом получает

## Ключ workspace

Ключ статистики совпадает с WorkspaceKey общего host: абсолютный путь `.sln`/`.slnx`/
`.csproj` плюс Configuration, Platform и TargetFramework. Пересечения копий (M3) тогда
прямо отвечают на вопрос о host. Каноническая строка ключа, по которой процессы сравниваются:

| Компонент | Правило |
|---|---|
| Путь | Как в [InputPathCanon](../../Services/Workspace/InputPathCanon.cs): `Path.GetFullPath`, разделители нормализованы, конечный separator убран, корень сохранён. На Windows — одно invariant-case представление. Symlink и junction не раскрываются и не склеиваются. |
| Свойства | **Фактически удерживаемые** после наследования пропущенных аргументов от прежней загрузки и конфига, а не аргументы вызова. |
| Platform | Канонический вид: `Any CPU` → `AnyCPU` ([DotNetConfigurationArguments](../../Services/Build/DotNetConfigurationArguments.cs)). |
| Пропущенное свойство | Явный токен «не передано MSBuild», а не подставленный `Debug` или первый TFM. |
| Не входят | `buildArgs`, среда, analyzer policy, настройки сервера. |

Сериализация — поля в фиксированном порядке с длиной каждой строки, без JSON с
произвольным порядком свойств.

| Пара | Ключи |
|---|---|
| `C:\Src\App.sln` и `c:/src/app.sln` на Windows | равны |
| `/src/App.sln` и `/src/app.sln` на Linux | не равны |
| `Release / Any CPU` и `Release / AnyCPU` | равны |
| Configuration пропущен и явный `Debug` | не равны |
| `net10.0` и `net8.0` | не равны |

В событии `load` пишутся оба ключа: запрошенный и удерживаемый после попытки. При
отказе удерживаемый — тот, что остался у процесса, или отсутствие ключа.

## Что уже есть в логах

- Текстовый лог Serilog: `<каталог логов>/mcp-YYYYMMDD.log`, один файл на день для
  всех процессов с этим каталогом (`shared: true`), хранится 14 файлов
  ([Program.cs](../../Program.cs#L43)). До 1.5.19 каталог логов — `<каталог exe>/logs`,
  с 1.5.19 — `logs/` [каталога пользователя](../user-data-directory/README.md) или
  `ROSLYN_MCP_LOG_DIR`.
- Тег процесса `[harness-xxxx]`: имя harness по непосредственному родителю и случайный
  суффикс ([HarnessSessionId](../../Diagnostics/HarnessSessionId.cs),
  [HarnessNameResolver](../../Diagnostics/HarnessNameResolver.cs)). Распознаются cursor,
  claude, codex, opencode, dsh; остальное — `cli`.
- Каждое входящее JSON-RPC сообщение с параметрами до 8000 символов
  ([McpInboundProtocolLogger](../../Diagnostics/McpInboundProtocolLogger.cs)) и строка
  SDK `Server (...), Client (имя версия)` при initialize.
- Итог каждого инструмента: краткая сводка, длина ответа, выделенные строки ответа
  ([ToolTelemetry](../../Diagnostics/ToolTelemetry.cs)).
- Working set при `workspace_load` и `workspace_load_cached`
  ([SolutionManager](../../Services/Workspace/SolutionManager.cs#L2336)), события
  `workspace_search_prewarm` и `workspace_load_designtime`.

Текстовый лог не заменяет структурированные события выхода процесса, начала вызова,
длительности загрузки, ключа workspace, периодических снимков памяти и памяти BuildHost:
они записываются в отдельный поток JSONL, описанный ниже. Текст лога содержит параметры
и фрагменты ответов — пути, код, имена проектов, — поэтому с чужих проектов его собирать нельзя.

## Поток статистики

Отдельный файл JSONL в стабильном каталоге пользователя, общем для всех версий сервера.
Каталог exe для этого не подходит: при установке через npx сервер лежит в кеше npm
(`npm-cache\_npx\<hash>\node_modules\roslynmcp-<платформа>\RoslynMCP`), и при обновлении
пакета каталог заменяется целиком: hash каталога `_npx` остаётся прежним, а логи старой
версии стираются (проверено владельцем 2026-10-29). Кроме того, кеш npm может быть очищен.

Это подкаталог `usage/` каталога пользователя сервера из отдельной задачи
[«Каталог пользователя сервера»](../user-data-directory/README.md): та же проблема npx
касается логов, глобального конфига и plugins.

| ОС | Каталог |
|---|---|
| Windows | `%LOCALAPPDATA%\RoslynMcpServer\usage\` |
| Linux | `$XDG_STATE_HOME/roslyn-mcp/usage/`, по умолчанию `~/.local/state/roslyn-mcp/usage/` |
| macOS | `~/Library/Application Support/RoslynMcpServer/usage/` |

Правила файла:

- `usage-YYYYMMDD-N.jsonl`; одна строка — одно событие, записанное одним системным
  вызовом append. Длина строки ограничена 4 KiB. Append и ротация сериализуются
  межпроцессной блокировкой; один размер строки не гарантирует атомарности обычного файла.
  Порванная последняя строка при разборе пропускается.
- На пределе 32 MiB файла начинается следующий номер того же дня; запись не
  останавливается.
- Хранение — по возрасту файла, 60 дней, а не по числу файлов: при ротации в день бывает
  несколько файлов, а сбор может растянуться до месяца. Перед анализом каталог копируется в постоянное
  место; единственная копия ряда в cache не считается корпусом.
- Сбор включён по умолчанию (O-01); отключение — переменная среды.

### Отказ статистики не ломает MCP

- Ошибки создания каталога, сериализации, записи и таймера снимков
  обрабатываются внутри статистики. Инструмент возвращает свой результат, host не
  останавливается, процесс не падает.
- Запись не берёт workspace lock и не ждёт MSBuild; ожидание записи при выходе
  ограничено (1 с).
- После ошибки запись пробуется снова на следующих событиях. Пропуски видны
  по разрыву `seq` (см. общие поля).
- Факт отказа и код ошибки — одной строкой в текстовый лог, без путей и аргументов.

### Общие поля

| Поле | Смысл |
|---|---|
| `v` | Версия схемы; первая опубликованная — `1` |
| `ts` | UTC с миллисекундами |
| `proc` | Случайный id процесса; pid переиспользуется, id — нет |
| `seq` | Порядковый номер события в процессе; разрыв = потерянные события |
| `pid`, `ppid` | Для склейки с деревом процессов |
| `harness` | Имя из HarnessNameResolver; полный путь и командная строка родителя не пишутся |
| `ver` | Версия сервера |
| `ev` | Тип события |

### События

| `ev` | Когда | Поля |
|---|---|---|
| `start` | Старт процесса | cwd, режим GC, ядра, профиль инструментов |
| `client` | Идентичность клиента из initialize или metadata ревизии 2026-07-28 | имя и версия клиента, версия протокола |
| `load` | Каждая попытка загрузки, включая lazy и отказ | ключ запрошенный и удерживаемый после, успех, `cacheHit`, источник (explicit / lazy / path-аргумент list/graph), признак graph-stale, длительность открытия без ожидания чужого lock, ожидание lock отдельно, число проектов |
| `reset` | `reset_workspace` | ключ, время с последней загрузки |
| `tool_start` | Приём вызова | ID вызова, имя, время начала, ключ на момент начала, нужен ли workspace; позволяет восстановить незавершённый вызов |
| `tool` | Конец вызова | имя, время начала, длительность, успех, ключ на момент начала, нужен ли инструменту workspace, был ли lazy load внутри |
| `mem` | Раз в минуту и после load/reset | память процесса и BuildHost (ниже), удерживаемый ключ, число выполняющихся вызовов, секунд с последней активности |
| `exit` | Нормальный выход | причина: EOF stdin, `stop_mcp_server`, исключение |

«Нужен ли workspace» — статическое свойство инструмента из каталога (semantic и
graph-инструменты — да; `get_tool_help`, чтение файла, git — нет) плюс фактический lazy
load. Активностью считаются приём и завершение вызова; при выполняющихся вызовах
секунды простоя в `mem` равны нулю.

### Память

Снимок не вызывает GC.

| Счётчик | Windows | Linux | Роль |
|---|---|---|---|
| Основной ряд процесса | private bytes (`PrivateMemorySize64`) | `RssAnon` + `VmSwap` из `/proc/self/status` | Входит в M1 и M3 |
| BuildHost | число прямых дочерних BuildHost и сумма тех же счётчиков | то же | Входит в M1 и M3 вместе с процессом |
| Working set | `WorkingSet64` | `VmRSS` | Диагностика; не суммируется как уникальная RAM |
| Managed heap и committed | `GC.GetGCMemoryInfo` | то же | Диагностика |

BuildHost-потомки определяются тем же правилом, что у
[UnregisteredBuildHostReaper](../../Services/Workspace/UnregisteredBuildHostReaper.cs):
только прямые дети этого процесса, без чужих host и без деревьев `dotnet test` /
`dotnet run`. Основные ряды Windows и Linux не равны друг другу, поэтому результаты
оцениваются отдельно по машине и напрямую между ОС не сравниваются. В основном ряду нет разделяемых
отображений файлов, так что сумма по копиям не складывает общие страницы дважды.

Точные имена полей и единицы — в [схеме v1](schema.md).

### Приватность

- Сырой поток не обезличивается: пути, cwd и ключи workspace пишутся открытым текстом,
  как в текстовом логе. Поток локальный и нужен только для обработки на машине.
- Никаких аргументов инструментов, текстов ответов, имён символов, среды и командных строк.
- Агрегаты, которые можно коммитить, не содержат ни путей, ни хешей: ключи заменены
  порядковыми метками `K1`, `K2`… в пределах машины. Сырые файлы с проектов коллег
  остаются у них или в приватном хранилище и сюда не коммитятся.
- Поток локальный и ничего не передаёт, как и текущий лог. В `PRIVACY.md` и README
  добавляется короткий раздел о каталоге статистики, его содержимом, отключении и
  удалении — по образцу раздела о локальном кеше индексов.

### Эволюция схемы

- Добавленное поле: старые строки остаются допустимыми; отсутствующее поле не
  превращается в ноль. Метрика, которой без поля нельзя верить, считается с даты версии,
  где поле появилось, и отчёт это указывает.
- Изменение смысла поля — новая `v`; отчёт не перечитывает старые строки по-новому.

## Инструмент подсчёта

Инструмент — скрипт PowerShell (O-02); на Linux запускается через `pwsh`. Вход — копии каталогов `usage/` с одной или нескольких машин, каждая с меткой машины.
Все файлы машины читаются как одна лента, процессы склеиваются через границу суток.
Выход — JSON с метриками по машине и короткий Markdown-отчёт; суммы по машинам в
правило решения не входят.

### Восстановление интервалов

- **Жизнь процесса** — от `start` до последнего события. Без `exit` конец — нижняя
  граница (правое цензурирование), а не точное время смерти.
- **Годное наблюдение процесса** — время, когда процесс жив, находится вне своего
  пробела и его память известна по годному `mem`. Годный снимок содержит удерживаемый
  `workspace_key` (null допустим), известные `memory_bytes`, `buildhost_bytes`,
  `active_calls` и `idle_seconds`. Неизвестный счётчик не заменяется нулём.
- **Пробел наблюдения процесса** — разрыв `seq`, отсутствие годного `mem` дольше двух
  интервалов (120 с) или неполное наблюдение/переход по правилам [схемы](schema.md#обработка).
  При heartbeat-разрыве исключается весь интервал между годными снимками; хвост от
  последнего снимка до конца наблюдения обрабатывается так же. До первого годного
  снимка процесс не входит в интегралы: само ожидание до 120 с включительно не
  образует пробел; более долгое — пробел от начала процесса до снимка. У процесса без единого
  годного снимка вся наблюдаемая жизнь является пробелом. Пробел не продлевает простой
  и не обрывает жизнь процесса.
- **Исключение из интегралов** — M1 не учитывает память процесса в его собственном
  пробеле или без известной памяти. Чужой пробел не отменяет M1 годного процесса.
  M3/M3a/M3r не учитывают ключ на интервале, если хотя бы одна его живая копия находится
  в своём пробеле или имеет неизвестную память. При неизвестном переходе учитываются
  возможные прежний, запрошенный и восстановленный ключи. Другие ключи продолжают
  участвовать в расчёте.
- **`usable_hours`** — длительность объединения годных наблюдений всех процессов
  машины. Интервал входит в знаменатель один раз, если годен хотя бы один процесс;
  полное покрытие всех живых процессов одновременно не требуется.
- **`gap_hours` / `gap_count`** — отдельная диагностика: длительность и число
  интервалов объединения процессных пробелов после слияния пересекающихся и
  соприкасающихся интервалов. Они не вычитаются из `usable_hours`: в это же время
  другой процесс может оставаться годным.
- **Удержание ключа** — от успешного `load` до следующей попытки load, `reset` или конца
  жизни. Неуспешная попытка берёт удерживаемый ключ из самого события.
- **Активность** — объединение интервалов вызовов [начало, конец]; невыполненный вызов
  убитого процесса тянется до конца жизни. «Активны одновременно» — пересечение этих
  интервалов у двух процессов.
- **Простой** — время без активности при удерживаемом ключе. Для порога T в M1 идёт
  только хвост после первых T минут каждого эпизода: именно его освободила бы выгрузка
  с таймаутом T.

Например, A имеет годные снимки все 10 минут, а у B внутри этого окна минутный
пробел. Тогда одновременно верны `usable_hours = 10/60` и `gap_hours = 1/60`.
Вклад A в M1 сохраняется; M3/M3a/M3r общего с B ключа за эту минуту не считаются.
Если ключи разные, здоровая группа ключа A продолжает участвовать в M3/M3a/M3r.

### Метрики

Память — основной ряд процесса плюс его BuildHost. Метрики памяти выдаются в GiB·h
и как среднее GiB: `GiB·h / usable_hours`. Это общий знаменатель машины для M1, M3 и
M3r по правилу объединения годных процессов выше; диагностический `gap_hours` из него
не вычитается. При `usable_hours = 0` интегралы и средние недоступны, а не равны нулю.
T ∈ {5, 15, 30, 60} мин.

| Метрика | Определение | Отвечает на |
|---|---|---|
| M1(T) | Σ память × хвост простоя после T | Q-03: потолок выгоды trim или выгрузки |
| M2(T) | Оценка дополнительного времени загрузок из-за выгрузки по таймауту T: число эпизодов «простой дольше T, затем вызов, которому нужен workspace и который сам не выполняет некешированное открытие» × длительность полного открытия этого ключа. Одна загрузка на эпизод, сколько бы вызовов ни пришло. Длительность — медиана измеренных успешных некешированных открытий ключа на этой машине; без измерений эпизод выводится отдельно как «цена неизвестна» | Q-03: оценка добавочной цены выгрузки с таймаутом T |
| M3 | Σ память лишних копий × время, когда ≥ 2 живых процесса держат один ключ. Лишние — все копии, кроме одной с наибольшей памятью. Отдельно M3a — время, когда ≥ 2 копии активны одновременно | Q-02: потолок выгоды общего процесса |
| M3r(T) | Остаточная память лишних копий после моделируемой выгрузки с таймаутом T: из оставшихся копий исключается одна с наибольшей памятью | Q-02/Q-03: остаток для общего процесса после выгрузки |
| M4 | Число процессов, время жизни, harness, распределение копий одного ключа | Q-01 |
| M5 | Новый процесс с ключом, уже удерживаемым другим живым простаивающим процессом того же harness | Q-04 |
| M6 | Частоты и длительности инструментов, доля lazy load, частота reset и повторных load по машинам и harness | Q-05, Q-06 |

Начало, завершение и длительность вызова записываются фактически (`tool_start` /
`tool`); событие `load` содержит начало попытки, длительность и ожидание lock отдельно.
Фактическая загрузка остаётся в сыром ряду и счётчиках отчёта независимо от M2.
Вызов, который и без таймаута уже выполняет некешированную попытку открытия,
не добавляет эпизод M2, включая неуспешную попытку и смену ключа. Только успешные
некешированные открытия участвуют в медиане цены; cache hit после простоя может
потребовать дополнительного открытия при моделируемой выгрузке.

M2 — модель дополнительной задержки, а не измеренная задержка работающей выгрузки.
Точную добавочную задержку можно получить сравнительным экспериментом после реализации
выгрузки по таймауту. M6 и `median_fresh_load_seconds` описывают фактические наблюдения;
M2 и M3r показывают оценки для рассматриваемых таймаутов.

M5 — эвристика. На Windows root- и subagent-MCP Codex — дети одного app-server, а id
треда в их среде нет; одинаковый harness почти не отличает subagent от второго окна.
В критерии M5 не входит.

### Проверка инструмента

Синтетические ленты с заранее известным ответом для каждой метрики:

- убитый процесс без `exit` и с невыполненным долгим вызовом;
- долгий вызов плюс параллельный короткий;
- поочерёдная активность двух копий чаще, чем T;
- смена суток и ротация файла внутри дня;
- два процесса с одним pid в разное время;
- разрыв `seq` и порванная последняя строка;
- cache hit без единого полного открытия ключа;
- смесь версий схемы;
- граничные пары ключей из таблицы выше.

Промежуточный прогон — через 2–3 дня реального сбора, чтобы рано найти недостающие поля.

## Критерии решения

Решение владельца по O-03, 2026-10-30: численные пороги выгоды и допустимой задержки
заранее не задаются. Отчёт показывает метрики по каждой машине и всем T, а владелец
выбирает стратегию по результатам сбора. Сравнение — по средним GiB на машину и по
каждому T. Таблица ниже задаёт ориентиры анализа; автоматического выбора стратегии
по фиксированным порогам нет.

| Наблюдение | Возможное направление |
|---|---|
| M1 и M3 малы по среднему GiB | Оставить как есть |
| M1 велико, M3 мало | Trim по простою; выгрузка — при T, где M2 приемлема |
| M3 велико, M3r(T) мало при T с приемлемой M2 | Выгрузка по простою снимает и дубликаты; общий процесс не нужен |
| M3 велико, M3r(T) велико при всех T с приемлемой M2 | Общий host или шаренный MCP; размораживается исследование, выбор между ними — там |
| M1 и M3 велики одновременно | Сначала строка по M3r, затем по M1 |

## Проверка по harness

До сбора каждый harness проверяется на версии с логированием: поток пишет `start`,
`client`, `tool`, `mem`, а имя harness и клиента распознаны верно. Отдельно —
как harness запускает MCP для subagent и что остаётся в дереве процессов.

| Harness | Кто проверяет |
|---|---|
| Claude Code | Исполнитель задачи |
| Codex | Исполнитель задачи |
| Cursor | Исполнитель задачи |
| dsh | Исполнитель задачи |
| OpenCode | Владелец, отдельно |

Пять названных harness должны писать свои имена. Остальные запуски остаются
категорией `cli` и участвуют в M3 и M4. Если проверка покажет устойчивый ложный
`cli` у одного из пяти, это дефект резолвера, который исправляется до сбора.
