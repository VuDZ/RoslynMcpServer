# Статистика использования MCP

Создано: **2026-10-29**. Статус: **черновик спецификации для ревью владельца; код не начат**.

Тема собирает данные о реальном использовании сервера, чтобы выбрать, как бороться
с дублированием памяти между копиями MCP: общий workspace host, шаренный MCP (роли),
выгрузка или trim по простою — или оставить как есть. Исследование общего host
заморожено до этих данных в ветке `research/workspace-host-process`
(`docs/workspace-host-process/evidence/2026-10-29-freeze.md` в этой ветке).

Логирование и инструмент подсчёта делаются в main. Ветка исследования потом получает
их обычным merge.

## Вопросы

| ID | Вопрос | Для какого решения |
|---|---|---|
| Q-01 | Сколько копий MCP живёт одновременно, из какого harness (Claude Code, Codex, Cursor, dsh, OpenCode) и как они запускаются? | Масштаб проблемы |
| Q-02 | Держат ли несколько живых процессов один workspace одновременно, и активны ли они в это время? | Общий host / шаренный MCP |
| Q-03 | Сколько времени процесс простаивает с загруженным workspace — против времени загрузки и потребляемой памяти? | Выгрузка или trim по простою |
| Q-04 | Запускает ли subagent свой MCP, пока MCP родителя не используется? | Выгрузка по простою в родителе |
| Q-05 | Какие инструменты вызываются, сколько длятся, какие запускают lazy load? | Размещение инструментов, цена перезагрузки |
| Q-06 | Как часто вызываются `reset_workspace` и повторные `load_workspace`? | Цена общего reset (O-02 исследования) |

«Workspace» здесь — ключ: абсолютный путь `.sln`/`.slnx`/`.csproj` плюс Configuration,
Platform и TargetFramework. Это ключ, выбранный владельцем для общего host.

## Что уже есть в логах

- Текстовый лог Serilog: `<каталог exe>/logs/mcp-YYYYMMDD.log`, один файл на день для
  всех процессов из этого каталога (`shared: true`), хранится 14 файлов
  ([Program.cs](../../Program.cs#L40)).
- Тег процесса `[harness-xxxx]`: имя harness по непосредственному родителю и случайный
  суффикс ([HarnessSessionId](../../Diagnostics/HarnessSessionId.cs),
  [HarnessNameResolver](../../Diagnostics/HarnessNameResolver.cs)). Распознаются cursor,
  claude, codex, opencode, dsh.
- Каждое входящее JSON-RPC сообщение с параметрами до 8000 символов
  ([McpInboundProtocolLogger](../../Diagnostics/McpInboundProtocolLogger.cs)) и строка
  SDK `Server (...), Client (имя версия)` при initialize.
- Итог каждого инструмента: краткая сводка, длина ответа, выделенные строки ответа
  ([ToolTelemetry](../../Diagnostics/ToolTelemetry.cs)).
- Working set при `workspace_load` и `workspace_load_cached`
  ([SolutionManager](../../Services/Workspace/SolutionManager.cs#L3126)), события
  `workspace_search_prewarm` и `workspace_load_designtime`.

Чего нет: выхода процесса, длительности загрузки как отдельного события, ключа
workspace в каждом вызове, периодических снимков памяти и простоя, managed heap и
private bytes. Лог лежит в каталоге exe: на Windows при in-place publish это каталог
publish, на Linux launcher держит общий каталог логов. Текст лога содержит параметры
и фрагменты ответов — пути, код, имена проектов, — поэтому с чужих проектов его
собирать нельзя.

## Поток статистики

Отдельный JSONL-файл рядом с текстовым логом не годится: нужен стабильный каталог
пользователя, который переживает publish и общий для всех версий.

| ОС | Каталог |
|---|---|
| Windows | `%LOCALAPPDATA%\RoslynMcpServer\usage\` |
| Linux | `$XDG_CACHE_HOME/roslyn-mcp/usage/`, по умолчанию `~/.cache/roslyn-mcp/usage/` |
| macOS | `~/Library/Caches/RoslynMcpServer/usage/` |

Файл `usage-YYYYMMDD.jsonl`, одна строка — одно событие, запись с общим доступом
нескольких процессов. Хранение и предел размера — по аналогии с текстовым логом
(14 дней), плюс ограничение на файл, чтобы зациклившийся процесс не забил диск.
Отключение — переменная среды; включение по умолчанию — решение владельца (O-01).

### Общие поля

| Поле | Смысл |
|---|---|
| `v` | Версия схемы |
| `ts` | UTC с миллисекундами |
| `proc` | Случайный id процесса; pid переиспользуется, id — нет |
| `pid`, `ppid` | Для склейки с деревом процессов |
| `harness` | Имя из HarnessNameResolver |
| `ver` | Версия сервера |
| `ev` | Тип события |

### События

| `ev` | Когда | Поля |
|---|---|---|
| `start` | Старт процесса | хеш cwd, режим GC, ядра, имя родителя, профиль инструментов |
| `client` | MCP initialize | имя и версия клиента, версия протокола |
| `load` | Конец загрузки или cache hit | ключ workspace, `kind` (fresh / cached / lazy / graph-stale), длительность, число проектов, успех, память после |
| `reset` | `reset_workspace` | ключ, время с последней загрузки |
| `tool` | Конец вызова | имя инструмента, длительность, успех, ключ workspace, был ли lazy load внутри |
| `mem` | Раз в минуту и после load/reset | private bytes, working set, managed heap, committed, загружен ли workspace, ключ, секунд с последнего вызова |
| `exit` | Нормальный выход | причина: EOF stdin, `stop_mcp_server`, исключение |

Убитый процесс `exit` не пишет: его конец — последний `mem`, с точностью до минуты.

### Приватность

- Пути, cwd и ключи workspace — только HMAC-SHA256 с секретной солью, которая лежит
  в каталоге статистики и создаётся один раз на пользователя. Простой SHA-256 пути
  восстанавливается подбором известных путей. Пересечения нужны только внутри одной
  машины, поэтому общая соль между машинами не нужна.
- Никаких аргументов инструментов, текстов ответов, имён символов, среды и командных строк.
- В репозиторий попадают только агрегаты инструмента подсчёта. Сырые файлы с проектов
  коллег остаются на их машинах или в приватном хранилище и сюда не коммитятся.

## Инструмент подсчёта

Вход — каталоги `usage/` с одной или нескольких машин, каждый помечается меткой машины.
Выход — JSON с метриками и короткий Markdown-отчёт. Пути не раскрываются: инструмент
работает с хешами.

| Метрика | Определение | Отвечает на |
|---|---|---|
| M1 — простой | Σ по процессам: память × время, когда workspace загружен, а вызовов нет дольше T; T ∈ {5, 15, 30, 60} мин | Q-03: потолок выгоды trim или выгрузки |
| M2 — цена возврата | Число вызовов после простоя дольше T × время загрузки этого ключа | Q-03: цена выгрузки с таймаутом T |
| M3 — параллельные копии | Σ память × время, когда ≥ 2 живых процесса держат один ключ; отдельно — когда оба активны в одном окне | Q-02: потолок выгоды общего процесса |
| M4 — состав | Число процессов, их время жизни и harness; распределение копий одного ключа | Q-01 |
| M5 — subagent | Новый процесс с ключом, уже загруженным в другом живом процессе, который простаивает, и тот же родитель или harness | Q-04 |
| M6 — инструменты | Частоты, длительности, доля lazy load, reset и повторные load | Q-05, Q-06 |

M5 — эвристика. На Windows root- и subagent-MCP Codex — дети одного app-server,
а id треда в их среде нет. Надёжно отличить subagent может не получиться;
это проверяется на первых днях данных.

Проверка инструмента — синтетические логи с заранее известным ответом для каждой
метрики, включая убитый процесс без `exit`, смену суток, два процесса с одним pid
в разное время и пересечения на границе T. Промежуточный прогон — через 2–3 дня
реального сбора, чтобы рано найти недостающие поля.

## Критерии решения — черновик

Записываются до сбора, чтобы данные не подгонялись под вывод. Числа — предложение
для обсуждения (O-03).

| Наблюдение | Вывод |
|---|---|
| M1 и M3 малы в абсолютных ГБ на машине | Оставить как есть |
| M1 велико, M3 мало по сравнению с M1 | Trim по простою; выгрузка — если M2 при выбранном T приемлема |
| M3 велико, копии одного ключа в основном активны одновременно | Общий host или шаренный MCP; размораживается исследование |
| M3 велико, но одна из копий почти всегда простаивает | Trim или выгрузка решают и это; общий процесс не нужен |

## Проверка по harness

До сбора каждый harness проверяется на версии с логированием: поток пишет `start`,
`client`, `tool`, `mem`, а `harness` и имя клиента распознаны верно. Отдельно —
как harness запускает MCP для subagent и что остаётся в дереве процессов.

| Harness | Кто проверяет |
|---|---|
| Claude Code | Исполнитель задачи |
| Codex | Исполнитель задачи |
| Cursor | Исполнитель задачи |
| dsh | Исполнитель задачи |
| OpenCode | Владелец, отдельно |

Нераспознанный harness (`unknown`) — дефект логирования до начала сбора, а не
категория в отчёте.

## Порядок работы

1. Ревью этой спецификации владельцем, ответы на O-01…O-04.
2. Логирование в main: схема, запись, тесты; версия и publish. Проверка по harness.
3. Инструмент подсчёта и синтетические тесты — вместе с пунктом 2.
4. Сбор около двух недель на машинах владельца (Linux и Windows), при согласии — у коллег.
   Промежуточный прогон через 2–3 дня.
5. Отчёт с метриками и решение по таблице критериев.
