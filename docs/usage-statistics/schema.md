# JSONL usage schema v1

Первый публичный формат — `v=1`. Сырые файлы локальные; поля ключей и cwd содержат пути.
Сбор отключается `ROSLYN_MCP_USAGE=0` или `false` перед запуском процесса.
Имена полей — `snake_case`; длительности — миллисекунды, память — байты, timestamp — UTC ISO 8601.

## Общий конверт

Каждая строка содержит `v`, `ts`, `proc`, `seq`, `pid`, `ppid`, `harness`, `ver`, `ev`.
`proc` — случайный идентификатор процесса, не PID. `seq` присваивается до попытки записи;
пропуск означает потерянное наблюдение. Неизвестный счётчик памяти — null, не ноль.

## События

- `start`: `cwd`, `gc`, `cores`, `profile`.
- `client`: `name`, `version`, `protocol`; legacy initialize либо request metadata ревизии 2026-07-28. Повтор одной идентичности не дублируется.
- `tool_start`: `call`, `name`, `start_ts`, `workspace_key`, `requires_workspace`.
- `tool`: те же поля идентичности вызова, `duration_ms`, `success`, `lazy_load`.
- `load`: `call`, `start_ts`, `requested_key`, `workspace_key` после попытки, `success`, `cache_hit`,
  `source`, `graph_stale`, `duration_ms`, `lock_wait_ms`, `projects`; с 1.5.23 — `watchers` и
  `watcher_failures`: число запущенных disk watcher и отказов их старта у удерживаемого
  workspace после попытки ([disk-watcher-inotify](../disk-watcher-inotify/README.md), O-04).
  Добавленные поля, `v` остаётся 1; у более старых строк их нет, и анализатор считает такие
  загрузки неизвестными, а не нулевыми. `null` — попытка не дошла до снятия состояния.
- `reset`: прежний `workspace_key`, `resident_key` после попытки, `success`,
  `start_ts`, `seconds_since_load`.
- `mem`: удерживаемый `workspace_key`, `active_calls`, `idle_seconds`,
  `memory_bytes`, `buildhost_bytes`, `buildhost_count`, `working_set_bytes`,
  `managed_heap_bytes`, `committed_bytes`.
- `exit`: `reason`.

Отдельное `tool_start` сохраняет начало вызова, который не успеет записать `tool`
перед kill; `call` связывает начало и конец внутри процесса. Ключ в событии инструмента
относится к началу вызова. Lazy load и его ключ дополнительно видны в `load`.
У `tool` поле `ts` фиксирует завершение, а `duration_ms` измеряется монотонными часами.
Событие `load` записывается после попытки: `start_ts` — её начало, `ts` — время записи
результата; `duration_ms` исключает `lock_wait_ms`. `call` связывает загрузку с вызовом
инструмента и равен null для попытки вне такого вызова. Отдельного `load_start` нет;
при прерывании процесса сохраняется `tool_start`, если попытка шла внутри инструмента.
Длительности в JSONL — фактические измерения; M2 в агрегированном отчёте — оценка
дополнительных загрузок от будущей выгрузки по таймауту.
Неуспешный reset не означает выгрузку: используется `resident_key`.

Ключ — канонический кортеж пути и фактически удерживаемых Configuration, Platform,
TargetFramework с фиксированным порядком и длинами полей. Отсутствующее свойство
отличается от явного Debug; symlink/junction не раскрываются.

## Обработка

Файлы всех ротаций/суток одной машины составляют одну ленту. Разрыв seq и пропуск
годных периодических снимков создают пробелы отдельного процесса. M1 исключает вклад
этого процесса; M3/M3a/M3r исключают ключ с неполной живой копией. Годные процессы
и независимые ключи продолжают учитываться. `usable_hours` — объединение годных
наблюдений процессов; `gap_hours` / `gap_count` — отдельная диагностика объединения
пробелов, которая не вычитается из знаменателя. Нормативные границы и пример:
[Восстановление интервалов](README.md#восстановление-интервалов).
Нет exit — известна только нижняя граница жизни. Последняя порванная строка не разбирается как событие.
Неизвестная версия/недоступное обязательное поле отмечаются в покрытии, а не заменяются нулём.

В экспортируемых JSON/Markdown нет исходных ключей/cwd или их хешей: только метки K1,
K2 в пределах машины. GiB·h и средние GiB применяются к метрикам памяти; M2 имеет
единицы секунд и числа эпизодов, M4–M6 — соответствующие счётчики/длительности.
Численные пороги и автоматический выбор стратегии отсутствуют.

Неполные переходы load/reset делают residency неизвестной до следующего полного mem.
Неизвестная потребность вызова в workspace делает M2/M3r недоступными;
отсутствующий lazy_load учитывается отдельно от false. Отчёт сохраняет known/unknown samples.
