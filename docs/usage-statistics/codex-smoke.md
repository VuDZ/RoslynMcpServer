# Codex smoke и статистика реального прогона

Дата: **2026-10-30**, Europe/Moscow. Ветка: `usage-statistics`. Версия: **1.5.21**.
Статус: **PASS для контролируемой проверки Codex на Windows**. Длительный сбор и
проверки остальных harness этим прогоном не закрываются.
[Машиночитаемое подтверждение](codex-smoke-validation.json).

## Подключение и выполненный scope

Сервер собран self-contained win-x64 и подключён в конфигурации Codex; после перезапуска
приложения `get_mcp_server_info` подтвердил **1.5.21.0** и загруженное решение из пяти
проектов. Сбор статистики включён; используются стандартные пользовательские `logs/`
и `usage/`. Таймаут инструмента **1200 с** сохранён. Подключение оставлено активным.
Другие работающие установки MCP не заменялись.

Через подключённый MCP выполнены:

- Release build — PASS; основной CI-набор
  `Category!=AnalyzerLifecycle&Category!=RequiresPinnedSdk` — **1487/1487 PASS**.
  SourceStructure включён в этот набор; inventory известных limits не ослаблялся.
- Lifecycle с `ROSLYN_MCP_ANALYZER_LIFECYCLE=1` — **13/13 PASS**, без skips.
- Два сабагента: `UsageWorkspaceInstrumentationTests` — **5/5 PASS**,
  `UsageJsonlWriterTests` — **3/3 PASS**, `UsageMemorySamplerTests` — **2/2 PASS**.
  У сабагентов были собственные MCP; тесты запускались без build/restore.
- Поиск ссылок, список тестов и граф проектов — успешно. Проверены cache hit,
  reset и повторное полное открытие. После прогона workspace восстановлен.

Родитель отправил main и lifecycle через `Promise.allSettled`, но фактические
`tool_start` / `tool` показали последовательное выполнение внутри его MCP.
У двух сабагентов также не было наложения внутри одного процесса. Наложение произошло
между тремя разными MCP: **до 3 активных вызовов**, **12,51455 с** суммарно при ≥2 вызовах.
Параллельное выполнение внутри одного MCP этим экспериментом не подтверждено.

## Найденный и исправленный дефект

Первый живой прогон версии **1.5.20** прошёл тесты, но записал три успешных тестовых
вызова как `success=false`: общий `ToolLogAnalyzer` воспринимал любое `Failed:` как
ошибку, включая `Failed: 0` и Markdown `Failed: **0**`.

В **1.5.21** исправлен общий классификатор, используемый и текстовым логом, и usage
filter. Добавлен один regression test с **10 входами**: успешные raw/Markdown-итоги,
ненулевые и смешанные failure counters, текст ошибки и partial-результат. Регрессия
воспроизвела дефект до исправления; после него класс фильтров прошёл **3/3**, полный
основной набор — **1487/1487**, изолированный EXE/stdout/analyzer probe — **823 checks PASS**.

После подключения исправленного EXE все **18 реальных вызовов** родителя и сабагентов
записаны с `success=true`, включая main, lifecycle и три запуска `run_specific_test`.
Исходная выборка 1.5.20 сохранена без подмены флагов; она не смешана с итоговой.

## Полученные наблюдения

Область — MCP родителя и двух сабагентов этого чата с одним workspace K1. Фоновые
запуски с другим cwd исключены. Данные скопированы из пользовательского JSONL с
сохранением исходных строк, `proc` и `seq`; агрегация выполнена штатным
`scripts/Measure-McpUsage.ps1`. В отчётах raw-пути, ключи и process IDs отсутствуют.

Окно: **15:22:38–15:35:41 MSK**, около **13,05 мин**.
**85 событий**, **18 завершённых вызовов**, **37/37 полных снимков памяти**;
**5 load attempts** (4 fresh, 1 cache hit), 1 успешный reset.
Пропусков seq, heartbeat gaps, неполных переходов и незавершённых вызовов нет.
Все три процесса живы на границе копии, поэтому время их жизни ограничено справа.

- Измеренная медиана свежего открытия K1 — **1,48956 с**.
- Пики private bytes отдельных MCP — **0,314 / 0,290 / 0,227 GiB**.
  Это отдельные пики, их сумма не объявляется одновременным измерением памяти.
- Расчёт M3 по принятой формуле — **0,055646 GiB·h**, среднее **0,25586 GiB**
  за окно; M3a — **12,24 с** одновременной активности копий одного ключа.
- При T=5 мин M1 — **0,022603 GiB·h**, M3r — **0,034961 GiB·h**.
  Это оценки возможной выгоды, фактическая выгрузка в сервере не включалась.
- M2 — 0 эпизодов в этой выборке: после превышения порога не было подходящих
  возвратов. Это не измерение нулевой цены будущей выгрузки.

Короткий управляемый прогон подтверждает работу сбора и выявил ошибку классификации.
Он не определяет стратегию памяти и не заменяет корпус длительностью 2 недели–месяц.
