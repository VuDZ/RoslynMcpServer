# Independent Review

## Verdict

Черновик попадает в открытый вопрос исследования: какая доля памяти нескольких MCP — дубликат одного workspace, простой и цена возврата. Схему событий и разделение сырого файла от текстового лога можно реализовывать только после двух поправок, которые задним числом из JSONL не восстановить: что именно считается памятью, включая BuildHost, и какая каноническая строка уходит в HMAC. Таблица решений в текущих единицах к своим метрикам не применяется. Ссылка на заморозку общего host указывает на файл, которого в ветке нет; политика reset там уже выбрана.

## Summary

Сбор локального JSONL, хеш путей с солью, набор вопросов Q-01…Q-06 и синтетика на убитый процесс, смену суток, повтор pid и границу T — рабочая основа. Метрики M1–M3 и таблица критериев эту основу обгоняют: интеграл не определён, счётчик не назван, ребёнок BuildHost, уже исключённый из сумм task-05, снова не входит в схему, ключ workspace не сериализован так, как его уже записал владелец.

Q-06 не открывает O-02 общего host. Этот выбор (global retire при редком reset) записан 2026-10-29. Исследование не заморожено названным файлом. Живой пробел task-05 — невосстановленный состав 10–20 ГБ — как раз закрывается M1–M4, если ряд памяти и ключ зафиксировать до publish.

## Highest risks

Двухнедельный ряд нельзя пересчитать, если в нём нет памяти прямых BuildHost и нет одной канонической строки ключа. M3 тогда либо не видит копии одного workspace, либо оценивает не ту память, и таблица «оставить как есть / общий host» опирается на заниженный или несравнимый интеграл.

Второй риск — простой, посчитанный по концу вызова. Долгий `dotnet test` выглядит как простой, и выгрузка по T бьёт по занятому процессу.

Третий — корпус: перемешанные строки нескольких процессов, остановка записи на пределе размера и окно хранения в 14 дней на сбор той же длины.

## Questions / uncertainties

- Какой ряд является порогом O-03. Task-05 уже считал Windows private bytes и отдельно предупредил, что сумма working set — не уникальная RAM, а Linux-счётчик private bytes не равен. Выбор ряда остаётся за владельцем; молчаливое «память» — нет.
- Какая частота reset за окно сбора заново открывает global retire. В исследовании сказано только «если станет частым».
- M5 спека сама называет эвристикой. Одинаковый harness почти не отличает subagent от второго окна. В таблицу критериев M5 не входит. Task-05 уже видел два MCP Codex, пережившие завершение subagent; систематическая доля за две недели по-прежнему не посчитана.
- Строка «общий host или шаренный MCP» склеивает две архитектуры. M3 может разморозить тему и не выбирает между ними.
- Пики BuildHost в спайках не равны плато простоя. Направление пробела подтверждено task-05 («в суммы не включён»); величину в простое эти спайки не дают.

## Suggested spikes

Отдельный спайк, чтобы разрешить замечания, не нужен. Прямой ребёнок BuildHost уже определяется репером на Windows и Linux; в схему достаточно внести его счётчики и запрет принудительного GC.

Короткое наблюдение имеет смысл только если владелец считает, что после возврата `load_workspace` BuildHost уже не держит память. Пока `MSBuildWorkspace` жив, код host не отпускает. Это проверка посылки F-001, не развилка дизайна.

Проверка дерева процессов пяти harness, уже записанная в спеке, остаётся нужной для Q-04 и не заменяет определения M1–M3.

## Overall assessment

Выглядит обоснованным:

- отдельные события вместо разбора текстового лога с путями и кусками ответов;
- каталог пользователя, общий для версий, а не каталог publish;
- HMAC пути и отказ писать аргументы, ответы и командную строку;
- вопросы Q-01…Q-05 как разложение неизвестного состава памяти из task-05;
- синтетические случаи: нет `exit`, смена суток, повтор pid, граница T;
- O-01, пороги и сбор у коллег оставлены владельцу, а не зашиты в метрику.

Требует изменения до реализации записи:

- состав `mem` и имя ряда для M1/M3, включая прямых детей BuildHost (F-001);
- каноническая строка ключа по уже выбранному WorkspaceKey и исключительное создание соли (F-003);
- интервалы простоя, удержания ключа и пересечения активности (F-002);
- формула M2 и раздельные признаки `load` (F-004);
- единицы и недостающая клетка таблицы критериев (F-005);
- атомарная строка, поведение предела размера, копия корпуса длиннее сбора (F-006);
- граница отказа писателя (F-007);
- правка PRIVACY/README и запрет полного пути родителя в JSONL (F-008);
- статус ветки общего host и порог пересмотра O-02 (F-011).

Требует проверки на первых днях, не вместо определений выше:

- распознавание пяти harness; `cli` оставить категорией (F-009);
- чтение смеси `v` после промежуточного прогона (F-010);
- эвристика M5 по реальному дереву процессов.

Требует решения владельца:

- O-01 вместе с новым текстом приватности, не вместо него;
- числовые пороги O-03 после того, как единицы и предикативы таблицы названы;
- частота reset, которая отменяет global retire;
- остаётся ли равенство ключа статистики тем же, что WorkspaceKey общего host.
