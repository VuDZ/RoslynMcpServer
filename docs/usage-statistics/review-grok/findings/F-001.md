# F-001 — Снимок памяти не покрывает стоимость загруженного workspace

Severity: blocker

Category: correctness

Confidence: high

## Target

`docs/usage-statistics/README.md`, события `load` и `mem`; метрики M1 и M3; вопрос Q-03.

## Claim

Решение о trim, выгрузке и общем host принимается по «памяти», но схема снимает только счётчики процесса MCP и не называет, какой из них входит в M1/M3. Большая доля стоимости загруженного workspace живёт в дочернем BuildHost, а уже записанные четыре ряда родителя отвечают на разные вопросы.

## Evidence

- В `mem` перечислены private bytes, working set, managed heap и committed. M1 и M3 используют одно слово «память» (`docs/usage-statistics/README.md`, события и таблица метрик).
- BuildHost — отдельный процесс, который этот сервер сам запускает и держит, пока жив `MSBuildWorkspace`. `UnregisteredBuildHostReaper` описывает прямого ребёнка (`dotnet`, net472 exe или mono) и прямо запрещает путать его с BuildHost чужого процесса или с деревом `dotnet test` / `dotnet run`.
- `SolutionManager.LogProcessWorkingSet` пишет `Process.GetCurrentProcess().WorkingSet64`. Managed heap тем более относится только к текущему процессу.
- На одном и том же прогоне пик клиента и пик BuildHost разного порядка. Roslyn, 434 проекта: клиент около 757 МБ, крупнейший BuildHost около 1448 МБ (`docs/workspace-load-performance/research-buildhost-fork/evidence/task-04/windows-roslyn-fork-ab-trace-summary.md`). Офисное решение, 142 проекта: клиент около 268 МБ, крупнейший BuildHost около 530 МБ, процессов BuildHost два (`docs/workspace-load-performance/research-buildhost-fork/evidence/task-02-stage-3/office-fork-ab-summary.md`). Это пики спайка, не плато простоя production-сервера; они показывают, что вклад ребёнка достаточно велик, чтобы сдвинуть порог «в абсолютных ГБ».
- Замер, на котором уже стоит вопрос общего host, тот же пробел зафиксировал явно. Task-05 на ветке `research/workspace-host-process`: синтетические 20 MCP дали 2606,4 MiB private bytes и 4096,9 MiB суммы working set; «BuildHost в эти суммы не включён»; сумма working set не равна уникальной физической RAM; Linux-счётчики не равны Windows private bytes (`docs/workspace-host-process/epoch-0-design-and-spike/evidence/task-05-applicability.md` на этой ветке). Исторические 10–20 ГБ у 20+ процессов так и не разложены на дубликаты одного workspace, разные проекты и простой. Новая схема, которая снова не называет ряд и снова не видит ребёнка, этот вопрос не закрывает.
- После поиска ряды родителя уже расходятся: для server GC куча 4975 МБ, committed 5389 МБ, working set 6194 МБ. Тот же отчёт прямо говорит, что тяжёлая часть загрузки идёт в BuildHost со своим GC и что возврат памяти DATAS в простое не измерялся (`docs/workspace-load-performance/epoch-0-stage-measurement/evidence/task-12-server-gc-first-search.md`). Сервер по умолчанию на server GC (`RoslynMcpServer.csproj`, `ServerGarbageCollection`).
- Поле «память после» на `load` снимается в точке нынешнего `workspace_load` / `workspace_load_cached`, до завершения фонового `SearchIndexPrewarm` и до первой семантической компиляции. Удерживаемый объём появляется позже и виден только на минутных `mem`, если интеграл берёт их, а не снимок load.

## Why it matters

Сырой JSONL без счётчиков ребёнка нельзя пересчитать задним числом: исследование — двухнедельное окно реальной работы, а не эксперимент, который легко повторить. Q-03 и развилка «trim / выгрузка / общий host» отвечают на разные физические величины. Trim и DATAS видны по working set и committed родителя. Общий host убирает ещё и BuildHost. Сумма working set нескольких процессов дважды считает разделяемые страницы рантайма и завышает экономию одного процесса.

## Failure scenario

1. Две живые копии держат одну solution. У каждой свой BuildHost с пиком того же порядка, что и клиент, или больше.
2. В файл попадают только ряды `GetCurrentProcess` и куча GC. M1/M3 считают один неназванный ряд.
3. По клиенту дублирование выглядит умеренным, и таблица критериев даёт «оставить как есть», хотя как раз host и есть предмет замороженного исследования. Либо в интеграл берётся managed heap: в простое working set уже вернулся ОС, куча нет, и trim выглядит бесполезным.

## Violated requirement / constraint

Q-03 (простой с загруженным workspace против загрузки и занимаемой памяти) и цель темы: выбрать между общим host, шаренным MCP, выгрузкой, trim и «оставить как есть». Неявное допущение: стоимость копии равна одному счётчику процесса MCP.

## Recommended change

Зафиксировать в схеме отдельные ряды и правило интеграла.

- Для родителя хранить все четыре счётчика. Для решения продолжить ряд task-05: private bytes (`PrivateUsage` на Windows) отдельно от working set. Working set не суммировать как уникальную RAM. Managed heap оставить диагностическим. Linux-поле назвать отдельно: оно не равно Windows private bytes, порог O-03 на каждой машине свой и в абсолютных гигабайтах между ОС не переносится.
- В тот же `mem` добавить число прямых дочерних BuildHost и их working set и private/committed, тем же правилом, что уже есть у reaper: только прямые дети этого процесса, без чужих host и без дерева `dotnet test` / `dotnet run`.
- Сэмпл не вызывает сборку GC.
- M1/M3 интегрируют минутные сэмплы, а не «память после» на `load`.
- Экономия общего процесса считается по памяти, которая исчезнет вместе с лишней копией, без повторного сложения разделяемых отображений.

## Alternatives

Снимать только родителя и сузить вопрос исследования до «сколько держит in-process Roslyn». Это честный меньший вопрос, но он не отвечает на развилку общего host, ради которой тема открыта.

## Notes for arbitration

Пики BuildHost взяты из спайков загрузки и поиска, не из многочасового простоя production MCP. Если владелец считает, что в простое host уже завершён и не держит память, это надо показать отдельным наблюдением до фиксации схемы: `MSBuildWorkspace` на время загруженного workspace host не отпускает. Какой ряд является пороговым для O-03 — выбор владельца; отсутствие любого ряда ребёнка выбором не лечится.
