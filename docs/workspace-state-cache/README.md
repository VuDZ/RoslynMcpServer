# Workspace state cache — заморожено

Статус: **заморожено 2026-11-21 решением владельца**. Документы, экспериментальный код
`Services/Workspace/StateCache/` и тесты `RoslynMcpServer.Tests/WorkspaceStateCache/` удалены из `main`.
Полная история хранится в теге
[`archive/research-workspace-state-cache`](https://github.com/VuDZ/RoslynMcpServer/tree/archive/research-workspace-state-cache/docs/workspace-state-cache)
(коммит `ff7b54b`). В том же теге лежит более ранняя отложенная программа
[workspace load cache v2](../backlog/workspace-load-cache/README.md) с тестами `WorkspaceLoadCache`.

Production-поведение не менялось ни в одной задаче серии: disk cache в сервере не появлялся.

## Что пробовали

Цель — быстрее получить первый полезный семантический запрос в новом процессе за счёт
сохранения описания загруженного решения на диск: проекты, options, документы, references и индекс
входов. Roslyn `Solution`, compilation и тексты не сериализовались. План: E0 snapshot round-trip,
E1 disk cache MVP, E2 content refresh, E3 project refresh — 38 задач.

- **E0, 9 задач, приняты 2026-10-07…09.** Схема, capture, codec, изолированный hydrate,
  настоящий round-trip между процессами. На контроле `samples/RoslynMcpPlugin` (2 проекта):
  первый полезный запрос 2,32 → 1,41 с, из них hydrate 1,13 с при обычной загрузке 1,43 с;
  capture стоит ещё 3,04 с. BTCPay — `unsupported` из-за генераторов.
- **E1.** S-002 (task-11) — partial: design-time binlog не покрывает корневые evaluation,
  restore config/lock closure не доказана. Task-00.1 (дополнительный collector) — partial,
  task-00.3 — отрицательный аудит контракта свежести, task-00.4 — no-go для оптимизации
  обычной загрузки. Manifest (task-00) остался blocked, остальные задачи E1–E3 не начаты.
- **E1b, черновик без задач.** Ответы из непроверенного снимка, пока в фоне всегда идёт
  обычная загрузка; хеши известных входов служат фильтром, а не доказательством. Требовало
  решения владельца об обещании свежести (H-004), не начиналось.
- Решения владельца H-001 (XML-документация бинарных зависимостей вне гарантии) и H-002
  (strong-name, вариант B) приняты 2026-10-07. Текст развилки H-003 (варианты B, C, D)
  в репозитории так и не был записан; на неё ссылаются только производные темы.

## Почему остановились

1. Disk hit разрешался только после доказательства полноты входов MSBuild. Для произвольного
   build graph такое доказательство недостижимо, и S-002 упёрся именно в это.
2. Кэш строил собственную модель Roslyn `Solution`. Отсюда вопросы паритета (XML, strong-name,
   генераторы), которых обычный путь загрузки не создаёт.
3. Выгоду мерили только на проекте из двух проектов. На целевых решениях она не измерена, а
   первый семантический запрос (compilation) кэш не ускоряет совсем.
4. Процесс был несоразмерен: три ревью, защита и арбитраж спецификации, 21 раунд ревью ради E0.

После заморозки картина изменилась. Форк BuildHost, исключённый 2026-10-09, разрешён
2026-10-22; оптимизации A + B + C сократили загрузку офисного решения примерно с 49 до 29 с,
первый поиск — с 31 до 13,6 с ([workspace-load-performance](../workspace-load-performance/README.md)).

## Если возвращаться

Начинать с замера на целевом решении и частоты холодных загрузок
([статистика использования](../usage-statistics/README.md)), а не с плана эпох. Кандидаты:

- фоновая загрузка решения из `workspace-path` сразу при старте процесса и прогрев compilation;
- кэш результатов design-time build по проектам на уровне BuildHost с инвалидацией по
  фактическому списку imports evaluation; клиент строит workspace обычным путём;
- проверка после факта, как в E1b, вместо доказательства до публикации.

Раннер обычной загрузки [`ordinary_baseline.py`](../../scripts/workspace-state-cache/README.md)
остаётся в `main`: его использует замер Rapid TIA 2.
