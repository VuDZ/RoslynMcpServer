# F-003 — Неизменность metadata reference inventory нельзя вывести из неизменности путей

Severity: major

Category: correctness

Confidence: medium

## Target

- [E2 spec — Правила dirty](../../epoch-2-content-refresh/spec.md), metadata binary.
- [E2/task-00 — классификация diff](../../epoch-2-content-refresh/task-00-startup-diff-roles-hi.md).
- [E2/task-03 — fresh metadata references](../../epoch-2-content-refresh/task-03-fresh-metadata-references-med.md).

## Claim

E2 разрешает пересоздать metadata reference после изменения DLL при неизменном evaluated inventory, но не определяет, как доказать эту предпосылку без re-evaluation. Замена bytes существующей DLL может изменить само решение MSBuild reference resolution, даже если csproj, HintPath и все известные пути прежние. Нужен более узкий support predicate, чем changed binary плюс unchanged graph files.

## Evidence

- E2 spec требует свежий reference с сохранёнными properties; изменение пути/набора — graph dirty. E2/task-03 повторяет условие неизменного evaluated inventory, но его проверки охватывают aliases, EmbedInteropTypes и public shape, а не условия resolution.
- [E0/task-02](../../epoch-0-snapshot-roundtrip/task-02-snapshot-schema-hi.md) описывает portable reference properties; они не определяют MSBuild `SpecificVersion`, search/resolution constraints.
- [ResolveAssemblyReference — Assemblies/SpecificVersion](https://learn.microsoft.com/en-us/visualstudio/msbuild/resolveassemblyreference-task?view=visualstudio) требует совпадения указанной assembly identity при `SpecificVersion=true`. Поэтому DLL по прежнему HintPath после смены identity может перестать быть допустимым resolved reference. Документация проверена 2026-10-07.
- Локальный SDK `C:/Program Files/dotnet/sdk/10.0.300/Microsoft.Common.CurrentVersion.targets`, строки 2459–2504, использует ResolveAssemblyReference. При этом dependency traversal в design-time не следует считать всегда включённым: строка 2414 задаёт условное `_FindDependencies=false`. Finding не опирается на предположение об обязательном полном обходе dependencies.

## Why it matters

Свежие bytes в Roslyn reference не гарантируют соответствия свежей ordinary загрузке. Cache может предоставить assembly, которую ordinary resolution уже отвергает или заменяет, и вернуть другие symbols/diagnostics.

## Failure scenario

1. Проект имеет file reference с точной identity A версии 1, `SpecificVersion=true` и HintPath `lib/A.dll`; ordinary load успешно его разрешает.
2. Во время остановки сервера DLL заменяют A версии 2 по тому же пути. Project/import/restore files не меняются; других подходящих A версии 1 нет.
3. Content-only classifier видит только changed metadata binary и пересоздаёт reference к A версии 2.
4. Fresh ordinary resolution не удовлетворяет исходный exact-version reference; набор разрешённых references и diagnostics отличается.

Точный сценарий на выбранном будущем real control не запускался. Confidence medium отражает зависимость от ещё не выбранного support profile, а не предположение о неизбежности проблемы для всех metadata updates.

## Violated requirement / constraint

E2 требует сравнения mutations со fresh ordinary semantic result; graph/reference inventory change должен приводить к fallback. Не определён достаточный критерий неизменности evaluated inventory после смены binary identity.

## Recommended change

Разрешать metadata refresh только для профиля, который доказывает сохранение relevant resolution constraints при такой мутации. В MVP достаточно явно fallback для identity/resolution-sensitive изменений и сохранять положительный контроль безопасного content update. Добавить negative control с exact-version reference и заменой DLL; не выводить unchanged inventory только из старого DTO.

## Alternatives

Принимаемый более широкий профиль может выполнять bounded resolution verification. Полный повтор MSBuild resolution остаётся корректным fallback и не должен называться no-DTB metadata reuse.

## Notes for arbitration

Проверить actual design-time reference resolution выбранного профиля: если exact-version file references уже гарантированно excluded, оформить predicate и test, после чего сузить или снять finding. Spike нужен только если автор намерен поддержать этот класс без ordinary fallback. Для E1, где binary change даёт whole-request miss, это не блокирует направление.
