# F-001 — Post-load probe не связывает manifest с поколением evaluated graph

Severity: major

Category: correctness

Confidence: high

## Target

- [E1 spec — Store и поведение](../../epoch-1-disk-cache-mvp/spec.md), строки 54–61.
- [E1/task-00 — manifest](../../epoch-1-disk-cache-mvp/task-00-input-manifest-hi.md), capture evidence.
- [E1/task-06 — load/capture](../../epoch-1-disk-cache-mvp/task-06-load-save-and-restore-hi.md), stable base capture.
- [Общий README](../../README.md), «Сначала ordinary load, затем stable base capture».

## Claim

Два одинаковых probe после ordinary load доказывают стабильность диска во время capture, но не то, что именно эти bytes породили сохранённые options, references и memberships. Контракт не определяет начало защищаемого интервала до MSBuild evaluation или другое свидетельство соответствия evaluated graph поколению inputs. Слово stable допускает несовместимые реализации этого существенного условия.

## Evidence

- E1 spec требует повторный probe для сдвига inputs **за время capture**, а capture начинается после prepare. E1/task-00 получает paths из ordinary evidence, но не требует evidence прочитанных при evaluation bytes.
- В [SolutionManager.cs](../../../../../Services/Workspace/SolutionManager.cs) `LoadCoreAsync`, строки 2043–2055, ordinary open выполняется через `OpenAndCaptureAsync`; `StartDiskWatcherUnderLock` вызывается только на строке 2098. Изменение inputs во время open может предшествовать watcher session.
- В [AnalyzerProvenanceCaptureService.cs](../../../../../Services/Analyzers/AnalyzerProvenanceCaptureService.cs) `OpenAndCaptureAsync` сначала открывает workspace, затем replay; `ReplayOne` сохраняет project properties/analyzer items, но не содержит обязательного снимка bytes всех evaluation inputs. Временные binlogs удаляются в `finally`. Этот механизм сам по себе не закрывает недостающую гарантию.
- [E2/task-04](../../epoch-2-content-refresh/task-04-refreshed-envelope-capture-med.md) отдельно требует связь с реально consumed bytes. Аналогичная явная связь нужна уже для первого E1 envelope.
- В existing experiment [HydrateHostExperiment.cs](../../../../../RoslynMcpServer.Tests/WorkspaceLoadCache/HydrateHostExperiment.cs), `CaptureAsync`, строки 61–69, сравниваются held document characters и admitted bytes; [тест](../../../../../RoslynMcpServer.Tests/WorkspaceLoadCache/HydrateHostExperimentTests.cs) `Capture_refuses_stale_source_text_against_current_independent_bytes` фиксирует этот класс несоответствия для source. Это пример механизма, а не доказательство защиты production evaluation inputs.

## Why it matters

Несогласованный envelope может оставаться валидным при каждом последующем restart: checksum и новые hashes верны, но относятся к старому графу. Это persistent false hit, а не обычное кратковременное отставание live watcher.

## Failure scenario

1. Ordinary MSBuild читает `Directory.Build.props` A с одним набором `DefineConstants`.
2. До завершения open и запуска watcher файл заменяют версией B с другим набором. Файл далее стабилен.
3. Capture сохраняет options из A, а оба post-load probe записывают/подтверждают hash B. Manager lock не блокирует внешнюю запись.
4. Новый PID видит B и envelope с hash B, выдаёт disk hit, но использует parse options A. Fresh ordinary load получил бы B.

Это анализ допустимого interleaving; исполняемый race-test в рамках review не запускался.

## Violated requirement / constraint

Согласованное восстановление ранее загруженного описания; E1 обнаруженное значимое изменение должно вести к ordinary fallback. Отсутствует точный contract generation binding для исходного ordinary capture.

## Recommended change

Зафиксировать, какое evidence связывает evaluated graph с capture inputs, начиная с evaluation, и запретить запись envelope при отсутствии такого evidence. Для нового обнаруженного import/region определить bounded повторную загрузку/проверку либо отказ capture. Добавить тест с изменением props после его consumption, но до первого post-load probe. Простого третьего post-load hash недостаточно.

## Alternatives

Допустимы observed input generation в процессе ordinary capture либо консервативный capture protocol для поддержанного профиля с проверкой интервала evaluation. Выбор механизма остаётся автору; универсальный filesystem snapshot не требуется.

## Notes for arbitration

Вывод снимается, если stable base уже имеет конкретный обязательный consumed-generation contract и соответствующий negative test; необходимо указать его точный источник. Новый общий live freshness layer не предлагается. Исправление относится к E1/task-00 и task-06, до разрешения сохранять пригодный для restart envelope.
