# F-004 — Content-only не определяет target, который зависит от bytes уже известного source

Severity: major

Category: requirements

Confidence: medium

## Target

- `docs/workspace-state-cache/epoch-2-content-refresh/spec.md`, «Результат» и «Правила dirty»
- `docs/workspace-state-cache/epoch-2-content-refresh/task-00-startup-diff-roles-hi.md`
- `docs/workspace-state-cache/README.md`, граница custom targets

## Claim

E2 запрещает считать content-only правку source, если custom target или condition зависит от bytes этого source, но не задаёт, как это отличие получить. Исполнитель либо обновит текст и оставит старые options, либо снимет весь выигрыш E2 с любого проекта, где есть свой target.

## Evidence

- E2 spec: для custom targets/conditions, зависящих от source bytes, правило content refresh не применяется автоматически; неподдержанный случай — fallback.
- E2/task-00: «source bytes-dependent custom target вне content-only»; при этом классификатор строится по manifest diff и не создаёт отдельную модель MSBuild tasks.
- README: custom targets с неизвестными дополнительными inputs не поддержаны. Это другой случай. Здесь новый путь не появляется: меняются bytes уже учтённого `.cs`, а target читает их и меняет properties/options.
- Публичный workspace и текущий analyzer binlog не описывают тела targets. `WorkspaceInputMapBuilder` для custom tasks: «Not available on the public Roslyn workspace», `CompletenessKnown: false`.

## Why it matters

Content refresh обещает восстановить base и наложить новые тексты без ordinary MSBuild open. Если options зависят от содержимого файла, semantic result разойдётся со fresh ordinary load, а probe при этом честно увидит только смену уже известного text input.

## Failure scenario

Target читает признак из существующего `.cs` или связанного source и выставляет `DefineConstants` / `AllowUnsafe`. Файл уже есть в manifest. После offline-правки E2 классифицирует изменение как existing source content, обновляет текст на hydrated host и не переоткрывает проект. Константа в compilation options остаётся старой. Fresh ordinary load константу меняет. Task-00 требует не считать это content-only, но не даёт наблюдаемого признака, по которому классификатор это узнает.

## Violated requirement / constraint

E2 spec: неподдержанный source-bytes-dependent target ведёт к fallback. E2/task-00: такой target вне content-only. Операционного признака в пакете нет.

`Неявный / отсутствует — требуется уточнение`, как отличить поддержанный SDK compile item от target, который интерпретирует те же bytes.

## Recommended change

Записать замкнутое правило до реализации E2. Практичный MVP-вариант: content-only разрешён только для проекта, чей captured import/target set входит в явно поддержанный профиль; любой другой custom target/import делает source edit graph-dirty и ordinary fallback. Не требовать от task-00 анализа тел targets.

## Alternatives

- Allowlist SDK-профиля, как выше. Реальные проекты с собственными targets не получают content hit; E1 fallback сохраняется.
- Пытаться анализировать targets. Это отдельная MSBuild-модель, которую пакет прямо не хочет делать prerequisite, и она легко ошибается на условиях и вызовах tasks.

## Notes for arbitration

Нужен human choice, входит ли проект с любым пользовательским `.targets` в content-only. Если владелец готов признать такие проекты всегда graph-dirty, finding закрывается одной нормой в E2 spec. Spike «можно ли надёжно увидеть чтение файла внутри target» не следует начинать: пакет уже отказывается от общей модели MSBuild tasks.
