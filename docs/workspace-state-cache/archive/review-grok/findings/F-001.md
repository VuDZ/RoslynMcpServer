# F-001 — Ordinary capture реального проекта не проходит публичные metadata/options

Severity: blocker

Category: correctness

Confidence: high

## Target

- `docs/workspace-state-cache/epoch-0-snapshot-roundtrip/spec.md`, «Поддерживаемый срез» и «Приёмка»
- `docs/workspace-state-cache/epoch-0-snapshot-roundtrip/task-00-current-seams-and-controls-med.md`
- `docs/workspace-state-cache/epoch-0-snapshot-roundtrip/task-03-ordinary-capture-med.md`
- `docs/workspace-state-cache/epoch-0-snapshot-roundtrip/task-06-real-cross-process-roundtrip-med.md`

## Claim

Контракт E0 одновременно требует положительный ordinary capture реального проекта и запрещает silent defaults для значений, которые у stock MSBuild reference/options нельзя прочитать публичным API. На обязательном контроле с metadata references легального успешного capture нет.

## Evidence

- E0 spec: непредставимые options дают отказ capture; public getters `StrongNameProvider` / `DocumentationProvider` — точное представление либо отказ, без private reflection и silent defaults. Приёмка требует реальный ordinary capture, а не synthetic DTO.
- E0/task-00 требует контроль с реальными metadata/project references. E0/task-03 требует проверить stock metadata reference и options на реальном ordinary capture и запрещает silent defaults. E0/task-06 сверяет значимый compile option.
- Текущий capture эксперимента отказывает на любом `PortableExecutableReference`, который не является собственным `OwnedMetadataReference`: `unsupported-options: metadata documentation provider is not publicly observable` (`RoslynMcpServer.Tests/WorkspaceLoadCache/HydrateHostExperiment.cs`, capture metadata references). Тот же метод отказывает на `DesktopStrongNameProvider`, потому что search paths не имеют public getter.
- Публичный скелет Roslyn 5.9.0 `Microsoft.CodeAnalysis.PortableExecutableReference`: есть `FilePath` и `MetadataReferenceProperties`; `DocumentationProvider` снаружи не читается, `CreateDocumentationProvider()` protected. `DesktopStrongNameProvider` имеет только конструкторы с `keyFileSearchPaths` и equality; getter путей нет.
- `Microsoft.CodeAnalysis.Workspaces.MSBuild.dll` 5.9.0 содержит строки `DesktopStrongNameProvider` и `KeyFileSearchPaths`. Обычный loader создаёт именно stock reference, не тестовый `OwnedMetadataReference`.
- Отчёт эксперимента `docs/backlog/workspace-load-cache/epoch-0-feasibility/evidence/task-01-hydrate-host.md` фиксирует те же два предела и прямо говорит, что положительный ordinary capture этим не доказан. Новый пакет сам отсылает к этому эксперименту как к ограничению, но не выбирает, какой semantic subset после отказа всё ещё считается успехом.

## Why it matters

Это не пожелание более полного DTO. Два обязательных исхода E0 исключают друг друга: отказ на нечитаемом поле и положительный capture проекта, у которого такие поля есть всегда. Реализация либо нарушит запрет silent defaults, либо не сможет закрыть приёмку E0 и тем самым E1.

## Failure scenario

Task-00 выбирает неизменённый SDK-проект, как требует пакет. Task-03 снимает DTO с ordinary `MSBuildWorkspace`. У проекта есть хотя бы `System.Runtime` или аналогичный file reference. Capture доходит до stock `PortableExecutableReference` и обязан вернуть отказ. Если исполнитель подставит `DocumentationProvider.Default` или соседний `.xml` без публичного доказательства, что loader выбрал именно его, это silent default, запрещённый task-03. Дополнительно compilation options с `DesktopStrongNameProvider` дают второй отказ на том же проекте. E0/task-06 и benchmark E0 не получают рабочий real round-trip, от которого зависит старт E1.

## Violated requirement / constraint

E0 spec, приёмка «реальный ordinary capture», вместе с правилом «точное представление либо отказ, без silent defaults». E0/task-00: контроль содержит реальные metadata references. E0/task-03: stock metadata reference на реальном ordinary capture, silent defaults запрещены.

## Recommended change

До реализации E0 явно сузить semantic contract положительного среза. Зафиксировать, что identity `DocumentationProvider` и search paths `DesktopStrongNameProvider` в E0 не наблюдаемы. Перечислить, какие проверки положительного контроля обязательны без этих полей (project/document inventory, aliases, `EmbedInteropTypes`, публично читаемые compilation/parse options, выбранный symbol). Не называть это полной эквивалентностью XML-doc или strong-name resolution. Либо оставить полный отказ и убрать требование положительного real ordinary capture, пока public getter не появится.

## Alternatives

- Оставить отказ и считать E0 успешным только как negative harness. Тогда формулировку «рабочий capture реального проекта» нужно снять из результата эпохи: иначе E1 не от чего стартовать.
- Сузить положительный срез, как в recommended change. XML documentation и поиск ключа подписи остаются вне эквивалентности, пока API их не отдаёт.

Выбор меняет, что считается cache hit в E1. Его нельзя вывести из текущего текста.

## Notes for arbitration

Проверить на одном ordinary load выбранного контроля фактический runtime type `CompilationOptions.StrongNameProvider` и что каждый `MetadataReference` — stock `PortableExecutableReference`. Если какой-то реальный контроль не содержит ни одного file reference и не использует `DesktopStrongNameProvider`, вывод о «всегда» ослабнет; task-00 такой контроль запрещает. Spike нового API не нужен: скелет Roslyn 5.9.0 уже показывает отсутствие getter. Нужен human choice, какой смысл у «положительного» capture.
