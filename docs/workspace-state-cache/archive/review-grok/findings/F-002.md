# F-002 — Evaluated imports и restore inputs не из чего снять

Severity: major

Category: correctness

Confidence: high

## Target

- `docs/workspace-state-cache/README.md`, «Индекс входов»
- `docs/workspace-state-cache/epoch-1-disk-cache-mvp/spec.md`, «Стартовая проверка»
- `docs/workspace-state-cache/epoch-1-disk-cache-mvp/task-00-input-manifest-hi.md`

## Claim

Manifest требует реально импортированные `.props`/`.targets` и restore inputs по фактическим путям. Единственные источники, которые задача разрешает переиспользовать, этих путей не содержат. Две реализации разойдутся: ложный disk hit либо отказ всем обычным SDK-проектам.

## Evidence

- README серии: в индекс входят реально импортированные `.props`/`.targets`, а не только стандартные walk-up имена; restore inputs — assets, lock/config и импортируемые `*.nuget.g.props/targets` по реальным путям. Неразрешённый import даёт fallback.
- E1 spec: imported paths извлекаются из ordinary load evidence. E1/task-00: переиспользовать `WorkspaceInputMapBuilder` и current provenance/binlog capture; проверка «actual imports/restore inputs не подменены одними csproj».
- `WorkspaceInputMapBuilder` прямо записывает обратное. Imports: «Not available. The public workspace does not list evaluated Import items», `CompletenessKnown: false`. Restore inputs: «Not available. project.assets.json, packages.lock.json, and nuget.config are not project documents», тоже `CompletenessKnown: false`. Walk-up индекс — только `Directory.Build.props`, `Directory.Build.targets`, `Directory.Packages.props`, `global.json`.
- Binlog provenance пишется с `ProjectImports=None` (`AnalyzerProvenanceCaptureService`). Replay сохраняет `ProjectStarted` (файл проекта и properties) и task output только типа `Analyzer`. Import closure и путь assets file в snapshot не попадают.

## Why it matters

Сегодня новый PID всегда заново выполняет MSBuild, поэтому правка импорта видна. Disk hit — первое состояние, в котором эта правка может быть проигнорирована. Стоящий пробел live watcher здесь становится ложной неизменностью графа, а не отложенным замечанием до следующего load.

## Failure scenario

В репозитории есть `<Import Project="build\PackageVersions.props" />` или условие, которое меняет `DefineConstants`. Файл не является walk-up именем и не является document workspace. После capture MCP перезапускается. Реализация, которая честно использует только public workspace и текущий binlog, не видит файл: probe считает inputs неизменными и публикует старые parse options. Реализация, которая считает любой невидимый import неподдержанным, не может отличить его от неявного `Microsoft.NET.Sdk` и уводит в fallback каждый реальный SDK-проект. Оба исхода совместимы с текущим текстом задачи и несовместимы друг с другом. Проверка task-00 «imports не подменены одними csproj» не имеет источника данных.

## Violated requirement / constraint

README, «Индекс входов»: реально импортированные `.props`/`.targets` и restore inputs по реальным путям. E1 spec: imported paths из ordinary load evidence; неразрешённый import даёт fallback. E1/task-00: actual imports/restore inputs не подменяются csproj.

## Recommended change

Назвать отдельный evidence source evaluated import closure и фактического assets/lock/nuget path. Не считать им текущий analyzer binlog, пока у него `ProjectImports=None`. Отдельно записать консервативное правило для того, что source не вернул: такой request — `unsupported`, а не hit. Неявные imports SDK закрывать fingerprint версии SDK, как уже сказано, и не требовать обхода каталога SDK.

## Alternatives

- Второй binlog или evaluation только ради manifest, не меняя `ProjectImports=None` у analyzer provenance.
- Расширить существующий logger до сбора imports. Это меняет объём и содержимое текущего binlog, включая текст импортируемых файлов. Это отдельное решение владельца provenance, не локальная деталь manifest.

## Notes for arbitration

Факт `ProjectImports=None` и состав replay проверены по коду. Spike нужен только если кто-то утверждает, что список imports уже лежит в `ProjectStarted` properties текущего лога: тогда достаточно одного ordinary binlog и списка имён properties. Пока такого утверждения в spec нет. Выбор между вторым evidence channel и сменой существующего logger — human choice из-за стоимости и содержимого binlog.
