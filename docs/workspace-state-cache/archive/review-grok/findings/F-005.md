# F-005 — Состав disk request key не перечислен

Severity: minor

Category: requirements

Confidence: medium

## Target

`docs/workspace-state-cache/README.md`, «Поведение первого MVP»

## Claim

Ключ диска описан как normalized path, effective load properties и «semantic modes», но список аргументов `load_workspace`, которые входят в ключ и которые не входят, не зафиксирован. От этого зависит, смешаются ли разные published graphs.

## Evidence

- README: ключ включает normalized workspace path, фактически effective load properties и semantic modes; absent/requested/effective хранятся отдельно; разные графы не склеиваются одним hash; `BuildArgs` не входят в graph identity. Overlay не переносится как старая session: новый PID и new key получают новую session и текущий prepare.
- Действующие аргументы load, которые меняют или не меняют граф: `configuration`, `platform`, `targetFramework` — properties; `shadowCopyInSolutionAnalyzers` переписывает in-solution analyzer references и включает другой admission (`SolutionManager` публикует ordinary solution только когда флаг выключен; при включении требуется suitable provenance). `buildArgs` spec уже исключает. `briefOutput` и `logProjectOutputDiagnostics` на граф не влияют.
- «Semantic modes» и «overlay mode» не сопоставлены этим аргументам.

## Why it matters

Один и тот же path и configuration с разным `shadowCopyInSolutionAnalyzers` — разные analyzer references и разный publication gate. Общий envelope отдаст тень туда, где просили обычные references, или обычные references туда, где prepare обязателен. Обратная ошибка — включить в ключ чисто диагностический флаг и сделать лишние misses. Оба прочтения текста возможны.

## Failure scenario

Первый PID вызывает `load_workspace` с `useDiskCache=true` и `shadowCopyInSolutionAnalyzers=true`, capture сохраняется под ключом path+configuration. Второй PID вызывает тот же path без shadow-copy. Lookup находит envelope и публикует граф с shadow paths либо, наоборот, пропускает prepare, который для этого флага обязателен. Либо реализация кладёт `logProjectOutputDiagnostics` в ключ, и два семантически одинаковых запроса не делят cache.

## Violated requirement / constraint

README: разные графы не объединяются одним hash key. Состав ключа при этом не задан.

`Неявный / отсутствует — требуется уточнение`, какие параметры load входят в key.

## Recommended change

В разделе поведения MVP перечислить включённые и исключённые аргументы. Как минимум включить effective configuration/platform/target framework и `shadowCopyInSolutionAnalyzers`. Исключить `buildArgs`, `briefOutput`, `logProjectOutputDiagnostics` и сам флаг `useDiskCache` как identity графа. Requested и effective values по-прежнему писать отдельно, как уже сказано.

## Alternatives

Нет. Это закрытый список текущего tool surface, не новый abstraction layer.

## Notes for arbitration

Если владелец считает `shadowCopyInSolutionAnalyzers` уже покрытым фразой «overlay mode», достаточно явно приравнять их в тексте. Отдельный spike не нужен: различие графов видно по текущему load path.
