# F-007 — Host seam не учитывает единственную разрешённую точку Workspace.TryApplyChanges

Severity: minor

Category:
testability

Confidence:
high

## Target

- `docs/workspace-state-cache/epoch-1-disk-cache-mvp/task-04-manager-host-ownership-hi.md`
  («Минимальная host abstraction/adapter и изменения ownership в SolutionManager»).
- `epoch-0-snapshot-roundtrip/task-05-isolated-hydrate-hi.md`,
  `epoch-1-disk-cache-mvp/task-05-fresh-session-preparation-hi.md`.
- `docs/workspace-state-cache/execution.md` («Не ослаблять exact structural limit
  inventory»).

## Claim

План вводит host seam (non-MSBuild host, Adhoc), но не фиксирует, что материализация
восстановленного решения обязана пройти через единственную разрешённую точку
`Workspace.TryApplyChanges` внутри `SolutionManager.TryApplyWorkspaceChanges`. Естественный
дизайн «host владеет своим workspace и сам применяет Solution» добавляет второй call site
и ломает существующий структурный контракт, ослаблять который запрещено.

## Evidence

- `RoslynMcpServer.Tests/SourceStructure/WriteBoundaryChecks.cs:1-109`: ровно один call
  site `Microsoft.CodeAnalysis.Workspace.TryApplyChanges` во всём объявленном production
  scope, и он обязан находиться в `SolutionManager.TryApplyWorkspaceChanges`; неразрешённая
  ссылка на `TryApplyChanges` считается diagnostic; отдельный helper для отката overlay
  (`RevertAnalyzerReferenceOverlayForApply`) запрещён.
- Существующий wrapper — приватный метод менеджера:
  `private bool TryApplyWorkspaceChanges(Microsoft.CodeAnalysis.Workspace workspace, Solution cleaned)`
  (`Services/Workspace/SolutionManager.cs`, skeleton).
- AGENTS.md: «Preserve exact inventories of known structural-analysis limits. When
  production changes legitimately add a limit, explain it and update the expected identity
  and kind; do not merely loosen the count».
- Серия README: hydrate/prepare/publication остаются под одним manager acquisition, но ни
  одна задача не формулирует это как ограничение на владение `TryApplyChanges`.

## Why it matters

Проверка исполняется по всему production-дереву, поэтому она падает не на новой задаче, а
на интеграции. Исполнитель либо обнаружит это поздно и разрежет E1/task-04 заново, либо
ослабит структурную проверку, что прямо запрещено проектными инструкциями.

## Failure scenario

1. E1/task-04 выносит владение host в новый тип (например,
   `Services/Workspace/StateCache/WorkspaceHost.cs`).
2. Hydrate materialize-ит решение через `host.TryApplyChanges(hydrated)`.
3. `SourceStructure` падает с «2 reference sites … the write boundary must be single»;
   правка откатывается, host seam переделывается, evidence задачи инвалидируется.

## Violated requirement / constraint

AGENTS.md («Preserve exact inventories…»), execution.md («Не ослаблять exact structural
limit inventory»), а также неявный инвариант «публикация остаётся под manager
acquisition».

## Recommended change

Записать в E1/task-04 границу ответственности: host abstraction владеет ресурсами,
dispose, diagnostics и preparation-входами, но материализация Solution выполняется только
через `SolutionManager.TryApplyWorkspaceChanges`; в проверках задачи добавить прогон
`SourceStructure` write-boundary как обязательный.

## Notes for arbitration

- Проверить, не планирует ли автор иначе трактовать Adhoc-host (например, создание
  workspace сразу из `SolutionInfo`/`ProjectInfo` без `TryApplyChanges`) — тогда finding
  закрывается одной фразой в spec, ограничивающей допустимый способ materialization.
