# F-003 — Обязательный real positive capture может быть недостижим: нет gate и contingency

Severity: major

Category:
requirements

Confidence:
medium

## Target

- `docs/workspace-state-cache/epoch-0-snapshot-roundtrip/spec.md`, разделы
  «Поддерживаемый срез» и «Приёмка».
- `docs/workspace-state-cache/epoch-1-disk-cache-mvp/spec.md`, раздел «Стартовая проверка».
- `docs/workspace-state-cache/epoch-0-snapshot-roundtrip/task-00-current-seams-and-controls-med.md`,
  `task-03-ordinary-capture-med.md`; `epoch-1-disk-cache-mvp/task-00-input-manifest-hi.md`.
- `docs/workspace-state-cache/preparation-report.md`, «Открытые вопросы для независимого
  ревью».

## Claim

План сохраняет правило «точное представление либо отказ, без private reflection и silent
defaults» и одновременно требует настоящий положительный результат на реальном проекте
(«Synthetic DTO-only успех не закрывает эпоху»; «support detector, отказывающий всем, не
считается MVP»). Ограничения public API, зафиксированные в эксперименте, который план сам
называет отправной точкой, делают отказ на обычной MSBuild-загрузке вероятным. При этом ни
одна задача не проверяет заранее, что выбранный реальный контроль вообще капчурится, и не
определено, что делать, если он не капчурится.

## Evidence

- `docs/backlog/workspace-load-cache/epoch-0-feasibility/evidence/task-01-hydrate-host.md:188-209`
  («Конкретные ограничения public API»):
  - `DesktopStrongNameProvider.KeyFileSearchPaths` не является публичным getter в
    установленном Roslyn 5.9.0 → capture возвращает `unsupported-options` и не подменяет
    provider значением null/default;
  - у stock `PortableExecutableReference` нет публичного getter
    `DocumentationProvider` → capture такого reference даёт явный отказ;
  - несколько same-path inner-TFM instances нельзя однозначно связать → ambiguity
    отвергается; «positive ordinary multi-TFM capture здесь не доказан».
- E0 spec: «Непредставимые options или неоднозначный TFM дают явный отказ capture»,
  «Нельзя удалить references ради положительного результата».
- E1 spec: «Нужен хотя бы один положительный реальный request; support detector,
  отказывающий всем, не считается MVP».
- E0 spec §Приёмка: «Нужны реальный ordinary capture, round-trip в новом PID, независимый
  expected semantic result… Synthetic DTO-only успех не закрывает эпоху».
- Известный крупный кандидат уже помечен как невалидный для прежнего профиля:
  `docs/backlog/workspace-load-cache/btcpay-candidate.md:3` — «текущий `sdk-project-v1` не
  допускает request» (исторический статус, не нормативен, но показывает, что «реальный
  проект» не гарантирован).
- `preparation-report.md` выносит это в открытые вопросы: «можно ли получить real positive
  capture с известными public API representability ограничениями», то есть доказательства
  нет и по признанию автора.

## Why it matters

E0 нельзя принять без реального round-trip, E1 — без положительного поддержанного request.
Если отказ срабатывает на выбранном контроле, эпоха останавливается уже после реализации
capture/codec/hydrate. При этом очевидный способ «починить» — ослабить правило
(молча потерять provider reference или удалить reference) — прямо запрещён спекой, то есть
требуется возврат в spec.

## Failure scenario

1. E0/task-00 выбирает реальный контроль; E0/task-03 снимает DTO и получает
   `unsupported-options` или отказ по reference.
2. E0/task-05…06 не могут выполнить real round-trip; E0 не принимается; E1 зависит от
   E0/task-07 и не стартует.
3. Альтернативный, худший исход: исполнитель трактует «свежие metadata references» как
   разрешение молча потерять provider — правило «no silent defaults» нарушено, но нигде не
   записано как принятое ограничение.

## Violated requirement / constraint

E0 spec §Приёмка и E1 spec §Стартовая проверка (обязательный положительный реальный
контроль) — при отсутствии проверки достижимости этого требования.

## Recommended change

Добавить в E0/task-00 явный шаг «capture-ability gate» до реализации codec и hydrate: снять
реальный ordinary capture выбранного контроля и записать точный набор непредставимых
options/references и отказов. В spec E0/E1 зафиксировать, что отказ на выбранном контроле —
это blocked epoch с возвратом в spec (а не ослабление правила), и отдельно решить,
допустима ли потеря `DocumentationProvider` при пересоздании reference с диска как
документированное representability-ограничение.

## Alternatives

- Расширить «поддерживаемый срез» явным allow-list непредставимых полей (provider-ы
  игнорируются декларативно): быстрее, но снимает часть проверяемости semantic equality.
- Искать контроль, гарантированно не содержащий проблемных options/references: MVP
  становится работоспособным, но доказательство переносимости ослабляется.

## Notes for arbitration

- Нужен spike: это самая дешёвая проверка (ordinary capture одного реального решения), и
  без неё нельзя принимать E0.
- Факты, которые изменят вывод: обычная MSBuild-загрузка вообще не создаёт
  reference-level `DocumentationProvider` и не ставит `StrongNameProvider` вне подписанных
  проектов, тогда как выбранный контроль подписан или имеет XML-doc рядом с зависимостью.
- Human decision возможен: принять одно representability-ограничение явно вместо отказа
  либо вместо silent default.
