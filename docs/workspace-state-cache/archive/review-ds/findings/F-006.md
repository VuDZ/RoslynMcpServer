# F-006 — E0 валидирует DTO/codec в Tests assembly, а E1 поставляет другую реализацию

Severity: minor

Category:
maintainability

Confidence:
high

## Target

- `docs/workspace-state-cache/execution.md`: «Предложенные пути новых cache компонентов —
  `Services/Workspace/StateCache/` и `RoslynMcpServer.Tests/WorkspaceStateCache/`; …
  Existing эксперимент остаётся источником опыта, production код не зависит от Tests
  assembly».
- `docs/workspace-state-cache/README.md` (E0: «Production path ещё не меняется»).
- `epoch-0-snapshot-roundtrip/task-02-snapshot-schema-hi.md`,
  `task-04-snapshot-codec-low.md`; `epoch-1-disk-cache-mvp/task-03-atomic-envelope-store-med.md`
  («использовать E0 codec»).

## Claim

План не говорит, что артефакты E0 (schema, codec, hydrate) переносятся в production: E0
живёт в тестовом проекте, E1 вводит production-компоненты. Значит, границы, версии и
проверки codec в E1 — новая реализация, а evidence E0 (bounded decode, malformed payload,
aggregate bounds) относится к другой сборке. Формулировка E1/task-03 «использовать E0
codec» при этом невыполнима буквально.

## Evidence

- execution.md задаёт два разных каталога и запрет зависимости production от Tests assembly.
- E0/task-04 ограничивает scope: «Только serialization/validation; без cache directory,
  locking, file scan и manager интеграции» — то есть codec остаётся в изолированном
  прототипе.
- E1/task-03: «Store и codec integration; использовать E0 codec; без многопоколенного
  каталога…» — прямое указание переиспользовать E0 codec внутри production store.
- Серия README: E0 «Production path ещё не меняется», то есть перенос кода не планировался
  явно; ни один документ не описывает миграцию или повторную валидацию.

## Why it matters

Двойная реализация критичного формата — источник расхождений: проверки bounds/version/
checksum, доказанные в E0, не описывают production codec. Приёмка E1 может ссылаться на
E0-evidence, которого для фактически поставленного кода нет.

## Failure scenario

1. E0 принимает codec с лимитом (например, 16 MiB) и набором отказов при malformed payload.
2. E1 пишет собственный codec/store; aggregate bound проверяется иначе, версия схемы
   читается без строгой проверки.
3. Регрессия на повреждённом envelope проявляется только после поставки; при разборе
   выясняется, что заявленное E0-evidence относится к тестовому прототипу.

## Violated requirement / constraint

`execution.md` («production код не зависит от Tests assembly») в конфликте с E1/task-03
(«использовать E0 codec»).

## Recommended change

Зафиксировать один вариант и убрать противоречие: (а) DTO/codec из E0 переносятся в
`Services/Workspace/StateCache/`, их тесты — в `RoslynMcpServer.Tests/WorkspaceStateCache/`;
или (б) production codec пишется заново, и E1 обязан повторить malformed/bounds suite
против production-кода, а E0-evidence не цитируется в приёмке E1.

## Notes for arbitration

- Проверить замысел автора: «использовать E0 codec» может означать «использовать
  зафиксированную schema», а не код.
- Факт, который изменит вывод: явное указание в spec E1, что E0-код переносится как есть
  или что E1 повторяет его suite.
