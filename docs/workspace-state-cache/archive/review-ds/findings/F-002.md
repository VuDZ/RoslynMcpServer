# F-002 — Overlay mode не может получить fresh provenance на hydrated host: disk hit недостижим и не заявлен как ограничение

Severity: major

Category:
integration

Confidence:
high

## Target

- `docs/workspace-state-cache/epoch-1-disk-cache-mvp/spec.md`, разделы «Результат»,
  «Интеграция»: «Analyzer/generator preparation получает новую session и реальные
  bindings. Старый provenance snapshot не ребиндится простой заменой ID. При отсутствии
  допустимого fresh admission весь request идёт на ordinary load».
- `docs/workspace-state-cache/README.md`, раздел «Поведение первого MVP»: «Overlay mode
  не переносится как прежняя активная session: новый PID/new key получает новую session и
  текущий prepare».
- `docs/workspace-state-cache/epoch-1-disk-cache-mvp/task-05-fresh-session-preparation-hi.md`.
- `docs/workspace-state-cache/benchmark.md`, «Сценарии по эпохам» (E1-сценарии не содержат
  overlay-режима, хотя compare key его включает).

## Claim

План требует «fresh admission» для analyzer/generator preparation на восстановленном
host, но единственный существующий механизм, дающий допустимый provenance snapshot,
сам выполняет полный MSBuild open. На hydrated host такого snapshot нет, значит при
`shadowCopyInSolutionAnalyzers=true` disk hit недостижим by construction. Это следствие
нигде не заявлено как ограничение MVP, не входит в benchmark-сценарии и не проверяется
приёмкой; при этом реализация обязана не доводить дело до `Unavailable`, а заранее
уходить на ordinary load — отдельное требование, которого нет ни в одной проверке задачи.

## Evidence

- `AnalyzerProvenanceCaptureService.OpenAndCaptureAsync(MSBuildWorkspace workspace, …)`
  принимает workspace и сам вызывает `OpenSolutionAsync` / `OpenProjectAsync` с
  `BinaryLogger` (`Services/Analyzers/AnalyzerProvenanceCaptureService.cs:181-284`).
- `AnalyzerProvenanceCaptureGate.TryGetUnsuitableReason`: `null` snapshot →
  `provenance-capture-missing` (`Services/Analyzers/AnalyzerProvenanceCaptureGate.cs:19-38`).
- `SolutionManager.LoadAndPrepareAsync`: при `shadowCopyInSolutionAnalyzers=false` выход
  сразу; при unsuitable capture — `EnterUnavailablePublication`
  (`Services/Workspace/SolutionManager.cs:901-923`). Публикация `Unavailable` видна
  пользователю как «Semantic workspace is unavailable» (`Tools/WorkspaceTools.cs:161-166,
  197-200`).
- Провенанс-снимок создаётся только внутри `LoadCoreAsync` через MSBuild-open
  (`Services/Workspace/SolutionManager.cs:2045-2078`); на hydrate-пути MSBuild не
  запускается по определению эпохи.

## Why it matters

`shadowCopyInSolutionAnalyzers` — документированный session-sticky режим
(`Tools/WorkspaceTools.cs:34, 50`). Если он включён, вся выгода MVP исчезает, а поведение
«hit невозможен» неотличимо от «кэш сломан». Кроме того, разница между «честный fallback»
и «Unavailable» наблюдаема пользователем: первое — обычная загрузка, второе — отказ
semantic workspace.

## Failure scenario

1. PID A: `load_workspace(sln, useDiskCache: true, shadowCopyInSolutionAnalyzers: true)` →
   capture и envelope записаны.
2. PID B: те же аргументы. Hydrate не может получить provenance (MSBuild open не
   выполняется) → либо `Unavailable` (пользователь видит отказ), либо ordinary fallback.
3. В обоих случаях измеряется miss, а не hit. E1/task-10 обязан показать улучшение useful
   median на поддержанном real control, но overlay-сценария в его списке нет; E1/task-09
   тоже не проверяет комбинацию `useDiskCache=true` + overlay.

## Violated requirement / constraint

- E1 spec §Результат: «Неизменный реальный request даёт disk hit» — без оговорки про
  overlay mode.
- E1 spec §Интеграция: «При отсутствии допустимого fresh admission весь request идёт на
  ordinary load» — требование, не отражённое в проверках задач E1.

## Recommended change

Записать в spec E1 ограничение: «disk hit не поддерживается при активном overlay mode;
запрос уходит на ordinary load до publication, без состояния Unavailable и без удаления
references». Добавить в E1/task-09 или E1/task-10 negative-контроль
`useDiskCache=true` + `shadowCopyInSolutionAnalyzers=true` с ожидаемым ordinary fallback,
и не заявлять cache hit для overlay compare key.

## Alternatives

- Поддерживать hit в overlay mode: потребуется новый механизм fresh admission (например,
  валидация сохранённого bind-log evidence + повторная проверка binding-ов без MSBuild
  open). Это отдельный spike и отдельный scope, не покрытый текущими 33 задачами.
- Запретить комбинацию параметров явной ошибкой API (проще, но хуже UX).

## Notes for arbitration

- Требуется решение владельца: overlay + disk hit — обязательный сценарий MVP или
  документированное ограничение.
- Если ограничение принимается, оно должно попасть в ответ/лог (`bounded fallback reason`)
  и в `docs/workspace-state-cache/review/README.md`-стиль список пределов MVP.
- Проверить, считается ли overlay mode частью «поддержанного реального контроля» в
  E1-приёмке.
