# F-001 — Ключ disk cache не определяет сравнение omitted и effective load properties в новом PID

Severity: major

Category:
correctness

Confidence:
medium

## Target

- `docs/workspace-state-cache/README.md`, раздел «Поведение первого MVP»:
  «Disk request key включает normalized workspace path, фактически effective load
  properties и semantic modes; absent/requested/effective значения фиксируются отдельно».
- `docs/workspace-state-cache/epoch-1-disk-cache-mvp/spec.md`, раздел «Store и поведение».
- `docs/workspace-state-cache/epoch-1-disk-cache-mvp/task-06-load-save-and-restore-hi.md`,
  проверка «request/effective args не смешиваются».
- `docs/workspace-state-cache/epoch-1-disk-cache-mvp/task-10-mvp-benchmark-med.md`,
  compare key.

## Claim

Не определено, по какому набору свойств сохранённый envelope сравнивается с новым
запросом, когда запрос опускает `configuration` / `platform` / `targetFramework`.
Формулировка одновременно требует включать в ключ «фактически effective» значения и
хранить absent/requested/effective отдельно. В новом PID effective значения неизвестны
без MSBuild evaluation, поэтому буквальный «ключ по effective» невыполним, а «ключ по
requested» меняет уже действующий контракт сопоставления загрузок.

## Evidence

- Текущий код различает два разных правила и явно предупреждает о разнице:
  `MsBuildWorkspaceProperties.MatchesPassedLoadArguments` (пропущенный аргумент не
  сравнивается и не очищает уже загруженное значение) против `IsSameLoadCache`;
  XML-doc: «Do not use `IsSameLoadCache` for this path — it treats an omitted argument
  as unequal to a loaded value and would reopen without that property»
  (`Services/Workspace/MsBuildWorkspaceProperties.cs:33-100`).
- Правило «omitted не очищает» опирается на состояние процесса
  (`LoadedConfiguration` / `LoadedPlatform` / `LoadedTargetFramework` в
  `SolutionManager.LoadCoreAsync`, `Services/Workspace/SolutionManager.cs:1963-1994`).
  В новом PID такого состояния нет, а effective `Configuration` для `.sln` определяет
  MSBuild/SolutionConfiguration, не запрос.
- Tool-контракт сегодня описывает именно процессное правило: «Compares only arguments you
  passed: omitted configuration/platform/targetFramework do not clear already-loaded
  values» (`Tools/WorkspaceTools.cs:28`).
- План нигде не задаёт поведение запроса без `configuration`, если на диске лежит
  envelope, снятый с явным `configuration=Release`.

## Why it matters

Это контракт попадания: от него зависит, получит ли пользователь тот же semantic graph,
что дала бы ordinary загрузка. Ошибка здесь не диагностируется — `load_workspace`
вернёт успех и `baseGraphSource=disk`.

## Failure scenario

1. PID A: `load_workspace(sln, configuration: "Release")` → envelope сохранён с
   requested=Release, effective=Release.
2. PID B: `load_workspace(sln)` без `configuration`. Если реализация сравнивает
   effective сохранённого envelope с effective, выведенным из запроса, либо нормализует
   «не задано» к сохранённому значению (как RAM matcher), запрос попадает в ключ
   Release-графа.
3. Проект с `#if DEBUG` / условными `Compile` items отдаётся как Release-граф, тогда как
   ordinary load в этом PID дал бы Debug. Ответ сообщает успех и disk hit.

## Violated requirement / constraint

`Неявный / отсутствует — требуется уточнение`.

Обнаруженное assumption: «effective load properties вычислимы до чтения envelope в новом
PID и совпадают с тем, что вычислил бы MSBuild для того же запроса».

## Recommended change

Зафиксировать в spec E1 и в E1/task-06 три правила: (а) preimage ключа — нормализованный
путь + requested-значения с явным маркером «не задано» + semantic modes; (б) сохранённые
effective значения не участвуют в сопоставлении, они только диагностика; (в) попадание
допустимо лишь при совпадении requested-набора, иначе miss с bounded reason.

## Alternatives

- Строгое равенство (`IsSameLoadCache`): безопаснее, но запрос без `configuration` не
  попадёт в envelope, снятый с явным configuration; для MVP это допустимо.
- Разрешить попадание по effective, вычисленному из envelope: даёт больше попаданий, но
  требует явного правила, что ordinary загрузка с тем же запросом дала бы тот же граф.

## Notes for arbitration

- Проверить, что понимал автор под «фактически effective load properties» в ключе.
- Вывод меняется, если в spec будет написано, что ключ строится только по requested-набору
  с маркером отсутствия; тогда finding закрывается без изменения архитектуры.
- Spike не нужен; нужен один абзац нормативного текста.
