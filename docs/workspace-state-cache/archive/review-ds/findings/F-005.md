# F-005 — Config-driven lazy load не может включить disk cache: путь и владелец флага не определены

Severity: minor

Category:
scope

Confidence:
medium

## Target

- `docs/workspace-state-cache/README.md`, раздел «Поведение первого MVP»: «Proposed
  `load_workspace`: `useDiskCache=false`; `forceReload=false`. … При `useDiskCache=false`
  диск не читается и capture/write cache не выполняются».
- `docs/workspace-state-cache/epoch-1-disk-cache-mvp/spec.md`, §Результат.
- `docs/workspace-state-cache/epoch-1-disk-cache-mvp/task-06-load-save-and-restore-hi.md`
  («Только manager/load tool wiring»).

## Claim

Флаг включения задан только как аргумент инструмента `load_workspace`, тогда как штатный
сценарий этого сервера — ленивая загрузка из `RoslynMcp.jsonc` (`workspace-path`) при
первом semantic-вызове. У этого пути нет ни аргументов запроса, ни ключа конфигурации,
поэтому не определено: читается ли диск, пишется ли envelope и какой ключ используется,
когда configuration/platform/TFM вообще не передавались.

## Evidence

- `Tools/WorkspaceTools.cs:25-52` — параметры `load_workspace`; `useDiskCache` объявлен как
  proposed аргумент инструмента.
- `SolutionManager.EnsureWorkspaceFromConfigAsync` — тот же `LoadAndPrepareAsync`, но без
  аргументов запроса (XML-doc: «First semantic call with no published solution and a config
  `workspace-path`: same `LoadAndPrepareAsync` path as `load_workspace`»).
- Конфигурационная поверхность знает только `workspace-path`
  (`Config/RoslynMcpFileSettings.cs`: ключ `workspace-path`, `WorkspacePath`,
  `ResolveWorkspacePathAgainstWorkingDirectory`); ключа управления кэшем нет.
- `README` серии: «При `useDiskCache=false` диск не читается и capture/write cache не
  выполняются» — при конфиг-загрузке значение флага неоткуда взять.

## Why it matters

Пользователь, у которого workspace задан конфигом (документированный способ работы этого
сервера: первый semantic-вызов сам загружает workspace), не получает ни hit, ни capture и
не может включить функцию иначе как вручную вызвав `load_workspace`. При этом бенчмарк и
приёмка E1 опираются на раннер, который вызывает инструмент явно, поэтому этот пробел в
них не виден.

## Failure scenario

1. Пользователь задаёт `RoslynMcp.jsonc: workspace-path` и работает только semantic-
   инструментами.
2. Envelope никогда не создаётся (нет вызова с `useDiskCache=true`), ускорения нет, при
   этом help/README описывают кэш как работающую возможность.
3. В статистике и benchmark эффект выглядит достигнутым, потому что контролем управляет
   раннер с явными аргументами.

## Violated requirement / constraint

E1 spec §Результат: «ordinary load сохраняет snapshot и manifest; новый PID проверяет их» —
не ограничено явным `load_workspace`; конфиг-загрузка тоже является ordinary load.

## Recommended change

Выбрать и записать одно из двух: (а) добавить ключ конфигурации (например,
`use-disk-cache`) и правило ключа для запроса без properties; (б) явно указать в spec E1,
что поддержан только явный `load_workspace`, а config-driven lazy load не читает и не
пишет диск, и отразить это в help/ответе (`disabled`/`not-attempted` с причиной).

## Alternatives

- Включить диск по умолчанию для конфиг-пути: даёт эффект «zero-touch», но расширяет
  default-поведение, которое владелец пока не менял.

## Notes for arbitration

- Проверить, входил ли config-driven путь в замысел MVP или сознательно вынесен.
- Факт, который изменит вывод: наличие решения владельца о default/конфиг-ключе, не
  попавшего в пакет.
