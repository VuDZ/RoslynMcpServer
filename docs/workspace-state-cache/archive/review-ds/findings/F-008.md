# F-008 — Role evidence документов (IsGenerated) не переносится из DTO в hydrated input map

Severity: minor

Category:
correctness

Confidence:
medium

## Target

- `docs/workspace-state-cache/README.md`, раздел «Индекс входов» (роли, owners, «Файл с
  двумя ролями получает более строгую evaluation роль»).
- `epoch-1-disk-cache-mvp/task-00-input-manifest-hi.md` («Source/additional/config/shared
  paths имеют всех owners») и `task-07-existing-watcher-attachment-hi.md` («Подключить
  existing input map/session/watchers к hydrated candidate»).
- `epoch-0-snapshot-roundtrip/task-02-snapshot-schema-hi.md` («document roles/paths/encoding»).

## Claim

Роли входов, на которых строятся решения о dirty, выводятся builder-ом из живого документа
(`DocumentInfo.IsGenerated`), а не из сохранённого DTO. Документ, добавленный в hydrated
workspace без этого признака, даёт `false`, а для части имён — `Unknown`. Поэтому карта
hydrated host может отличаться от ordinary по ролям generated-документов, хотя план
требует подключать «existing input map» и сохранять единый смысл ролей.

## Evidence

- `WorkspaceInputMapBuilder.AddDocument` / `RoleForDocument` читают
  `RoslynDocumentBuildSideEffect.TryGetIsGenerated(document)`
  (`Services/Workspace/WorkspaceInputMapBuilder.cs:142-204`): `null` → `Unknown`,
  `true` → `Generated`, иначе `UserInput` (кроме имён вида `*.g.cs`, `AssemblyInfo.cs`,
  `AssemblyAttributes.cs`, которые уходят в `Unknown`).
- `RoslynDocumentBuildSideEffect` читает `IsGenerated` через private reflection по
  `Document.State` / `State.Attributes`; в XML-doc сказано: «MSBuildWorkspace sets that
  flag from the evaluated item» (`Services/Workspace/RoslynDocumentBuildSideEffect.cs:6-36`).
- Роль реально влияет на решения: `WorkspaceDiskEventClassifier` считает dirty по
  `InputRole.UserInput` (`Services/Workspace/WorkspaceDiskEventClassifier.cs:53, 95, 189-192,
  252`) и связывает producer-а только для `InputRole.Generated or Output` (строка 257).
- E0/task-02 требует хранить роли документов в DTO, но ни один документ не требует
  восстанавливать их в Roslyn-признак при hydrate; E1/task-07 говорит лишь «подключить
  existing input map».

## Why it matters

Расхождение ordinary/hydrated по ролям означает, что один и тот же файл классифицируется
по-разному в зависимости от того, был ли hit. Для generated-файлов это меняет решение
«dirty/не dirty» и атрибуцию producer-проекта, то есть наблюдаемое поведение live-синхронизации.

## Failure scenario

1. Ordinary загрузка помечает сгенерированный документ под `obj` (имя без суффикса `.g.cs`)
   как `Generated` по признаку из MSBuild evaluation.
2. Hydrated host строит карту из DTO и добавляет документ без `isGenerated` → роль
   становится `UserInput`.
3. Событие watcher по этому файлу теперь считается изменением пользовательского source
   (`InputRole.UserInput`) вместо build-артефакта: лишний dirty/reconcile, а в E2 — попытка
   content-refresh файла, который ordinary путь считает generated.

## Violated requirement / constraint

README §Индекс входов (единые роли/owners) и E1/task-07 («existing input map» на hydrated
candidate); явного требования о round-trip роли в DTO нет — `Неявный / отсутствует —
требуется уточнение`.

## Recommended change

Явно записать, что DTO-роль документа восстанавливается в Roslyn-признак
(`DocumentInfo.IsGenerated` и/или role-таблица input map), и добавить в E1/task-07 (или
E1/task-00) проверку сравнения ролей одного и того же дерева для ordinary и hydrated
загрузки.

## Notes for arbitration

- Проверить, планируется ли строить input map hydrated host из DTO целиком (тогда проблема
  снимается), или переиспользовать `WorkspaceInputMapBuilder` на восстановленном Solution
  (тогда нужен явный перенос признака).
- Факт, который изменит вывод: наличие в DTO поля роли и явного правила его применения при
  hydrate.
