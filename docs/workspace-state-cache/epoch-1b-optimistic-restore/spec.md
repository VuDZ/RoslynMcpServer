# E1b — Оптимистичное восстановление с фоновой проверкой

Статус: **draft, 2026-10-09**. Не контракт и не разрешение реализации; условия
старта — в [README эпохи](README.md#условия-старта).

## Идея

E1 пытался доказать до публикации, что сохранённый graph совпадает с тем, что
дала бы свежая ordinary-загрузка. Это требует полного manifest входов MSBuild
и доказательства потреблённой generation (P-004, P-011), чего при текущих
ограничениях получить нельзя ([task-00.1](../epoch-1-disk-cache-mvp/evidence/task-00.1-supplemental-source.md),
[task-00.3](../epoch-1-disk-cache-mvp/evidence/task-00.3-contract-scope.md)).

E1b не доказывает свежесть заранее. Ordinary-загрузка выполняется **всегда** и
остаётся единственным источником истины. Сохранённый снимок только позволяет
отвечать на запросы чтения, пока она идёт.

## Поведение

1. При `load_workspace` с включённым режимом и найденным envelope сервер
   выполняет дешёвую проверку известных входов (по возможности — probes из
   [E1/task-01](../epoch-1-disk-cache-mvp/task-01-text-and-directory-probe-med.md)
   и [E1/task-02](../epoch-1-disk-cache-mvp/task-02-binary-fast-probe-med.md)).
   Обнаруженное изменение — обычная загрузка без окна, как сейчас.
2. Иначе снимок восстанавливается принятым E0 hydrate и публикуется как
   **непроверенный**. Одновременно стартует обычная загрузка в фоне.
3. В окне до её завершения работают только инструменты чтения из матрицы допуска.
   Каждый ответ помечен `baseGraphSource=disk-unverified`.
4. Записи, рефакторинги, code fixes, build, test, run и analyzer execution ждут
   завершения фоновой загрузки, либо получают явный отказ, если ожидание не разрешено.
5. После фоновой загрузки публикуется её результат — **всегда**, без исключений.
   Снимок сравнивается с результатом (проекты, документы, options, references,
   analyzer references); расхождение попадает в ответ ближайшего вызова и в лог.
6. Capture нового envelope выполняется после ответа, вне критического пути.

## Уточнение владельца, 2026-10-10: хеш-фильтр

Из обсуждения оптимизаций. Черновик, не контракт.

- Проверка шага 1 — хеши известных входов, сохранённые в envelope: загруженные
  `.sln`/`.slnx` и `.csproj`, `Directory.Build.props/targets`,
  `Directory.Packages.props`, `global.json`, применимые `NuGet.Config`,
  `obj/project.assets.json` и `*.nuget.g.props/targets` каждого проекта,
  отпечаток SDK/MSBuild/Roslyn и схемы envelope.
- Сторонние сборки отдельно не хешируются: считается, что они приходят из NuGet,
  а изменение версии или состава пакетов меняет `project.assets.json`; папка
  пакетов NuGet неизменяема. Ручные DLL-ссылки вне NuGet — известное ограничение
  фильтра, его закрывает обязательная фоновая загрузка.
- Хеши — фильтр, а не доказательство свежести: совпадение разрешает окно с
  непроверенным снимком, фоновая загрузка выполняется всё равно (шаг 2).
  Несовпадение — обычная загрузка без окна, как в шаге 1.
- Сравнение на шаге 5 пишет в лог, были ли хеши совпавшими. Накопленная частота
  расхождений при совпавших хешах — evidence для возможного будущего решения
  пропускать фоновую загрузку; без такого решения она обязательна.
- Направление по U-B-02: генераторы в окне поддерживаются. Генераторы выполняет
  Roslyn после hydrate, их результат не сериализуется. Ограничение профиля E0
  пересматривается при создании задач.
- Фоновая загрузка может идти по плану групп из графа снимка, если
  [D/E0/task-07](../../workspace-load-performance/epoch-0-stage-measurement/task-07-core-first-parallel-spike-hi.md)
  даст go.

## Чем это проще E1

- P-004 не нужен: envelope — подсказка, а не основание для публикации без проверки.
- P-011 и полнота manifest не нужны: ошибку полноты ловит обязательная фоновая
  загрузка, а не probe.
- Записей на восстановленном host нет, поэтому не нужны E1/task-07 (watchers на
  hydrated host) и E1/task-08 (hydrated `.cs` write). Watchers подключаются к
  результату обычной загрузки.
- Capture не удлиняет ответ load.

## Что сохраняется из E1 и серии

- H-001 и H-002, профиль поддержки E0. Запрос вне профиля (генераторы, multi-TFM,
  signing-dependent, Release) получает обычную загрузку без окна.
- Ordinary write boundary, analyzer admission и watcher policy без изменений.
- RAM matcher, force и opt-in семантика из README серии.
- Store: один versioned envelope на key, атомарная замена, отказ cache I/O
  не превращает успешную загрузку в ошибку.

## Что требует решения владельца

Будущее **H-004** — изменение обещания свежести:

- в окне фоновой загрузки ответы чтения могут отражать устаревший graph
  (новый или удалённый проект, изменённые options или references, новый файл
  проекта); исходники при этом читаются с диска;
- длина окна примерно равна времени обычной загрузки;
- расхождение раскрывается после факта, а не предотвращается.

Без H-004 E1b не стартует.

## Открытые вопросы

- **U-B-01 — матрица допуска.** Какие инструменты чтения допустимы в окне;
  диагностики, зависящие от analyzers, вероятно, нет.
- **U-B-02 — генераторы.** E0 hydrate отказывает проектам с source-generated
  документами. Расширение профиля — отдельный вопрос; без него на типичном
  enterprise-решении окно получит только часть проектов либо не получит вовсе.
- **U-B-03 — ресурсы.** Hydrate и фоновая загрузка одновременно: пик памяти и CPU
  на большом решении.
- **U-B-04 — отношение к C.** При наличии host E1b работает внутри host на его
  холодном старте; без host — в обычном процессе сервера.
