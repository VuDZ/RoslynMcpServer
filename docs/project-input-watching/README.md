# Наблюдение за файлами проектов, linked и shared входами

Дата: 2026-09-30. Статус: **эпоха 1 принята; эпохи 2–3 не начаты**. Источник evidence — загруженный граф Roslyn; полное покрытие целевого графа не заявлено.

Пожелание 3: отслеживать файлы, принадлежащие проектам загруженного Solution,
включая внешние проекты и linked/shared файлы. Расположение `.sln` не задаёт
полную область зависимостей.

## Текущее основание

Проверено на commit `045b839`, source version `1.5.0`:

- [ComputeWatchRoots](../../Services/Workspace/SolutionManager.cs) уже объединяет
  каталог `.sln`/`.csproj` и каталоги загруженных проектов, удаляя вложенные
  дубликаты. Внешние проекты покрыты; это проверяют
  [SolutionManagerWatchRootsTests](../../RoslynMcpServer.Tests/Workspace/SolutionManagerWatchRootsTests.cs).
- Корни не строятся по `Document.FilePath`; внешний linked-файл может не
  попасть ни в один watcher. Физическое размещение проекта этого не решает.
- `QueueDiskPath` принимает любые `.cs` под корнями, даже не включённые в проект.
  Неизвестный существующий файл затем может пометить композицию как stale.
- [WorkspaceDocumentDiskSync](../../Services/Workspace/WorkspaceDocumentDiskSync.cs)
  ищет первый `DocumentId` по пути. Обновление всех memberships общего файла
  нужно проверить и обеспечить, не полагаясь на первый найденный документ.
- [WorkspaceDiskPathFilter](../../Services/Workspace/WorkspaceDiskPathFilter.cs)
  исключает `obj`, `bin`, `artifacts` и другие каталоги по имени сегмента.
  Это политика фонового обхода; она не доказывает нерелевантность явного входа.

## Целевой контракт

Логическая единица наблюдения — нормализованный физический путь и **все**
его memberships в фактически загруженном графе: проекты, project instances,
документы и роли входа/выхода.
Физический watcher может наблюдать каталог и фильтровать события по этой карте.
По одному watcher на каждый файл не требуется.

Общий источник состояния и форма consumer API закреплены в
[input-state-contract.md](input-state-contract.md): pull-снимок generation,
revisions, owners/roles, membership и coverage. Callback не вызывает подписчика;
состояние хранится в сессии и до первого появления build-freshness consumer.

- Изменение известного пользовательского `.cs` обновляет все документы этого
  пути в загруженном Solution, включая linked-файл в нескольких проектах.
  Дополнительные TFM instances не создаются ради индекса: карта соответствует
  реально загруженному внутреннему TFM/графу. Неподтверждённые условные входы
  другого TFM означают coverage unknown на весь граф.
- Создание/удаление/переименование потенциального project item обнаруживается
  и требует проверки состава MSBuild. Список известных файлов не является
  доказательством, что новый вход отсутствует.
- Отсутствие пути в обратном индексе не доказывает нерелевантность. Новый `.cs`
  внутри каталога SDK-проекта по-прежнему консервативно значим как возможный
  glob-item. Ignore допустим только при доказанном исключении из membership;
  конкретное членство подтверждается новой оценкой, а не watcher.
- Состав проекта не меняется через `AddDocument`/`RemoveDocument` и не
  записывает `<Compile Include>` в backing `.csproj`; сохраняется решение
  [disk-sync-csproj-mutation](../archive/disk-sync-csproj-mutation/README.md).
- Семантическая синхронизация и уведомления о build-input changes независимы.
  Семантический flush не поглощает изменения, нужные для
  [test-build-freshness](../test-build-freshness/README.md).
- Generated intermediates и outputs текущего build не являются изменением
  исходных входов этого build и не увеличивают их revisions. Путь в `obj`
  и присутствие в Compile сами по себе не доказывают пользовательский вход.
  Явный пользовательский input в `obj` сохраняется при подтверждённой роли;
  неоднозначная роль даёт unknown. Все роли одного пути учитываются раздельно,
  включая подтверждённый input другого проекта. Изменение/утрата output может
  обесценить build result, но не маскируется под input edit производящего build.
- Собственные успешные записи MCP тоже порождают изменения проектных входов.
  Протокол сравнивает снимок фактически сохранённых байтов, включая encoding/BOM,
  со стабильным чтением диска при обработке события. Callback FSW не содержит
  байтов события. `TickCount`-окно не служит доказательством echo; несовпадение,
  ошибка/нестабильность чтения и более новое событие сохраняют pending/unknown.
- Неполное покрытие, ошибка watcher и потеря событий явно отражаются как
  неизвестная полнота наблюдения. Для потребителя build freshness это причина
  выполнить сборку, а не использовать старое подтверждение.
- Rename каталога внутри области потенциального membership переводит покрытие
  в unknown; одного refresh известных текстов недостаточно. Возврат в полное
  покрытие возможен только после новой оценки membership/imports через reload
  или выбранный в эпохе 1 источник evidence, с восстановленными watchers.

## Область watcher и поиска

- Рекурсия разрешена для каталогов проектов и областей потенциального
  membership внутри них. Для файла вне project directories, linked-пути,
  импортированного файла или walk-up props используется нерекурсивный watcher
  на каталог самого файла с адресной фильтрацией либо точечное наблюдение.
- Рекурсивно наблюдать каталог предка ради одного props/import запрещено.
  Объединение подписок не повышает нерекурсивную подписку до рекурсивной и
  не захватывает чужое дерево. Известное отсутствие walk-up файла тоже требует
  обнаружения его появления; простая проверка только существующих файлов
  не подтверждает полноту.
- Внешний рекурсивный glob не разрешает расширить рекурсию на чужое дерево.
  Если точечные/нерекурсивные подписки и источник evidence не подтверждают
  появление новых вложенных inputs, coverage остаётся unknown.
- Корни поиска и описатели watcher — разные списки/API. `search_code`
  сохраняет текущую область: каталог загруженного workspace плюс project
  directories с удалением вложенных дубликатов; явный `directoryPath` и
  fallback без workspace остаются прежними. Linked-файлы и ancestor props
  не расширяют и не сужают поиск.

## Решение по не-C# входам

Эта серия выбирает обнаружение изменений и уведомление по подтверждённым ролям
для AdditionalFiles, analyzer configs, XAML/resources и evaluation inputs.
Полнота каждой категории зависит от evidence эпохи 1; неизвестные роли и
непокрытые inputs не считаются нерелевантными.

Текстовая синхронизация `AdditionalDocument` и `AnalyzerConfigDocument`
остаётся в [non-csharp-input-tracking](../non-csharp-input-tracking/README.md).
Эта серия её не реализует и не выбирает общий reload/build/restore policy для
semantic reads. Generated/graph роль не обходится обновлением обычного C# текста.
