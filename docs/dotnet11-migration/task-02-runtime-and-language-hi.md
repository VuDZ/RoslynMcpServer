# Этап 2. Runtime .NET 11 и язык сервера C# 15

- Рекомендуемые модели: gpt-6.2-astra.
- Рекомендуемый reasoning: high.
- Примерная сложность: 4/5.
- Риск ошибки: высокий — TFM затрагивает test hosts, плагины, SDK discovery и требования к поставке.
- Необходимые способности: .NET SDK/runtime, dependency loading, cross-platform tests, performance.
- Статус: accepted, 2026-11-20. Проверка точного pin при двух установленных SDK 11 отложена по решению владельца.
- Depends on: [этап 1](task-01-roslyn-and-buildhost-hi.md).
- Модель, реализовавшая задачу: Codex, координатор и сабагенты.
- Модели, проводившие ревью: независимый сабагент Codex.
- Количество раундов ревью: 1 по совместимости путей SDK и поставки.
- Количество исправлений после ревью: 1, путь публикации в профиле FolderProfile.
- Отчёт о реализации, ревью и validation: [совмещённый кандидат и причина смены порядка](evidence/task-01-roslyn-and-buildhost.md).
- Принятый scope и дата приёмки: 2026-11-20, сервер на .NET 11/C# 15, точный SDK `11.0.100`, совместная установка с SDK 10, явный отказ без закреплённого SDK, совместимость потребительских проектов и нативная Release-матрица B2. [Подтверждение](evidence/task-01-roslyn-and-buildhost.md).

Общий контракт: [план перехода](README.md). Версия Roslyn и патчи форка фиксируются
на результате этапа 1, чтобы B2/B1 измерял смену runtime, а не ещё одно обновление compiler.

Этап не начинается, пока gate этапа 0 не пройден, и не сужает потребительские строки.
См. [нерешённый gate](UNRESOLVED-v2.md). Закрытие AR-18 в этот этап не входит.

## Реализация

1. Перед C# изменениями прочитать [code-style.md](../code-style.md) полностью.
   Перевести сервер на `net11.0`; согласовать TFM Tests, LifecycleTestHost
   и DeadlockWitnessHost, иначе project references/testhost окажутся несовместимы.
   Проверить sample plugin и его shape/load tests: старый net10 plugin должен продолжать
   загружаться в новом host при прежнем API; sample, ссылающийся на сервер, собирается совместимо.
2. Использовать штатный стабильный C# 15 от SDK 11 без `LangVersion=latest/preview`.
   Сначала добиться корректной сборки без синтаксической переработки. Новые конструкции
   применять только когда они сокращают конкретное изменяемое место и понятны SourceStructure.
   Memory-safety preview и массовая миграция моделей/циклов не входят в scope.
   Библиотека `netstandard2.0` из матрицы не является поводом поднимать язык исходников
   сервера раньше этого правила.
3. Обновить существующий корневой `global.json` на pin сборки репозитория.
   Сейчас в нём `10.0.100` и `latestFeature`; такой файл удерживает CLI на SDK 10.
   - Записать один точный стабильный SDK 11, `rollForward` `disable`, `allowPrerelease` false.
     `11.0.100` остаётся кандидатом. В файл попадает номер, который проверен как установленный
     на Windows x64, Linux x64 и macOS ARM64. Плавающий `11.0.x` при `disable` не использовать.
   - CI устанавливает этот точный номер и отдельно потребительские SDK 9 и 10,
     которые нужны строкам матрицы.
     Установка только SDK 11 потребительские строки не закрывает.
   - `release.yml` записывает тот же номер и `rollForward` `disable`. Перезапись checkout
     допустима, расхождение с корневым файлом — нет.
   - Для приёмки toolchain репозитория рядом установлены SDK 10 и точный SDK 11.
     Сборка репозитория, `dotnet --version` в корне, MSBuild workspace и build/test
     через MCP выбирают закреплённый SDK без ложного `MCP_MSBUILD_SDK_MISMATCH`.
     Отсутствие точного SDK приводит к явному отказу. Потребительские строки проверяются отдельно.
   - Отложенная регрессионная проверка, **pending** по решению владельца от 2026-11-20.
     После выхода следующего релизного SDK 11 повторить эти сценарии с SDK 10,
     закреплённым `11.0.100` и более новым SDK 11 в одной установке. Подтвердить выбор
     `11.0.100` при обоих SDK 11 и явный отказ после удаления закреплённого SDK.
   - Закрытие AR-18 и поддержка нестрогих политик в этот пункт не входят.
     Пользовательские `global.json` вне репозитория не переписываются.
4. Проверить зависимости Microsoft.Extensions.*, MCP, Serilog, test SDK и SQLite
   на runtime 11. Повышать версии только при доказанной необходимости; проверить
   NuGet audit, transitive conflicts, assembly load и native assets.
   Учесть runtime/SDK/Hosting breaking changes, включая поведение shutdown и watchers.
   Список breaking changes .NET 11 не содержит включения MSBuild Server по умолчанию;
   политика дочернего CLI берётся из матрицы, а не только из этого списка.
5. Обновить только собственные output paths и ожидания runtime: build/test discovery,
   host launch, sample plugin tests, publish-and-verify, CI/release scripts и инструкции.
   Прочитать все найденные `net10.0`/SDK 10 места; не делать глобальную замену:
   пользовательские multi-TFM/pinned/older-framework fixtures сохраняют свой смысл.
   `PinnedSdk.Version` `10.0.300` этой заменой не затрагивается.
   Ожидания `RawImportEvidenceFixture` обновить явно: после смены корневого pin
   копия остаётся слепком toolchain репозитория и не доказывает строки
   `10.0.1xx`, `10.0.300` и `10.0.4xx`.
6. BuildHost остаётся отдельным процессом с подтверждённым upstream TFM/roll-forward.
   Не переводить его на net11 просто вместе с сервером. Факт `runtimeconfig` кандидата
   (`net8.0`, `rollForward` `Major`) это правило подтверждает, а не отменяет.
   Если изменение TFM host обязательно, выделить причину и сравнение, повторить
   RPC/scenario gates этапа 1. Обязательность нового shared runtime для дочернего host
   допустима только как результат наблюдаемого процесса, не как следствие TFM сервера.

## Проверки

- Полная [матрица совместимости](README.md#матрица-совместимости) после смены TFM:
  прежний net10 проект, новый net11/C# 15 проект, библиотека `netstandard2.0`
  с языком 15 и контролем языком 14, generators на поддерживаемых TFM,
  старые и новые plugin assemblies, build/test через MCP и reload.
  Языковая проверка использует уже расширенную матрицу. Библиотека не поднимает
  `LangVersion` сервера отдельно от пункта 2.
- Проверки «SDK 10 по точному pin», полосы `10.0.1xx` / `10.0.300` / `10.0.4xx`,
  «SDK 11», «обе версии», чужой cwd и архитектура `dotnet` подчиняются правилу
  ближайшего файла. Рабочий каталог каждого запуска назвать в отчёте.
  `dotnet --version` в корне репозитория потребительскую строку не закрывает.
  SDK 10 по точному pin при установленном runtime 11; SDK 11; обе версии рядом;
  чужой cwd, PATH с x86 dotnet на Windows, native ARM64 dotnet на macOS.
  Runtime сервера не должен заставить selector проигнорировать SDK пользовательского проекта.
- Отдельно повторить `net9.0` с точным `9.0.314` после перехода сервера на runtime 11.
  Проверить, что CLI и новый форк выбирают SDK 9 по ближайшему `global.json`, повторить
  сборку и семантические проверки, записать фактический runtime BuildHost.
- Политика дочернего CLI — правило наблюдения MSBuild Server из матрицы.
  Сначала текущий runner без нового opt-out, вместе с унаследованным окружением.
  Пока прогон на SDK 11 не показал, что `MSBUILDDISABLENODEREUSE=1` не оставляет
  постоянный сервер, дочерний процесс получает `DOTNET_CLI_USE_MSBUILD_SERVER=false`
  и только его; если унаследованный `MSBUILDUSESERVER` при этом всё ещё поднимает сервер,
  тому же процессу ставится `MSBUILDUSESERVER=0`. Окружение машины не меняется.
  Доказанная достаточность текущего флага второй механизм не добавляет.
  `/nr:false` допустим только если прогон показал, что названные переменные сервер
  не гасят, а этот ключ гасит. Ноль BuildHost этот gate не закрывает.
  Повторить затронутые тесты окружения и отмены процессов.
  Если режим переиспользования MSBuild Server изменился, связанные серии замеров
  повторить в одном и том же режиме.
- AnalyzerLifecycle с opt-in, full SourceStructure и точным inventory limits:
  новые синтаксические формы не могут молча выпасть из обхода transitive calls/lambdas.
  Также focused build/test runner, SDK diagnostics, disk sync/watchers,
  process cancellation/cleanup, index storage и snapshot roundtrip.
- Release build и полный main/lifecycle на трёх native платформах.
  Проверить новые предупреждения, не глушить их общим NoWarn.
- B2 против B1 на одинаковом SDK проекта и тех же настройках GC/A+B+C,
  в одном записанном режиме MSBuild Server. Тёплый сервер не относить к эффекту
  смены runtime. Раздельные измерения server/BuildHost runtime и памяти.
  Если сравниваются разные runtime host, отдельно указать этот фактор.
- Проверить минимальные OS/CPU/runtime требования по официальным
  [breaking changes .NET 11](https://learn.microsoft.com/en-us/dotnet/core/compatibility/11)
  и по источникам MSBuild Server, названным в матрице.
  Любое повышение требований отражается в документации и следующем этапе smoke.
  Повышение минимальной полосы потребительского SDK этим пунктом не выполняется.

## Приёмка и откат

Gate — поддерживаемый stable TFM/язык, корректные dependency/assembly loads,
сохранённые потребительские строки SDK в границах gate этапа 0, один toolchain
репозитория без ложного `MCP_MSBUILD_SDK_MISMATCH`, все обязательные tests/замеры
в пределах порогов. Нет новых публичных возможностей только по факту успешного `dotnet build`.
Приёмка не объявляет AR-18 закрытым и не заменяет ближайший pin потребительской строки
корневым SDK 11.

При откате вернуть одновременно server/test-host/sample TFM, корневой `global.json`,
CI/release SDK, output paths и связанные dependencies к checkpoint этапа 1.
Не оставлять net11 test host с net10 тестами или C# 15 исходники, которые старый SDK не соберёт.
Приёмка исходников этого этапа не означает готовность публичного выпуска: её закрывает этап 3.
