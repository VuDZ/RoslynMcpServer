## Работа

1. Зафиксировать SHA, чистоту checkout, OS/architecture, `dotnet --info`,
   `--list-sdks`, `--list-runtimes`, workloads, global.json контрольных решений,
   NuGet sources без credentials и настройки A/B/C/GC. Не использовать dirty checkout
   с несвязанными изменениями как воспроизводимый baseline.
   В baseline выбора CLI и MSBuild включить фактический корневой `global.json`
   (`10.0.100`, `latestFeature`, `allowPrerelease` false) и поведение reader.
   Не записывать, что reader исполняет `latestFeature`. Зафиксировать расхождение:
   при установленной папке `10.0.100` reader держит её, а CLI с `latestFeature`
   может уйти на более высокий band `10.0`.
2. Скачать выбранные стабильные пакеты Roslyn (кандидат 5.12.0), записать версии,
   package hash и source commit из nuspec. Убедиться в наличии согласованного набора
   CSharp, CSharp.Workspaces, CSharp.Features, Features, Workspaces.MSBuild и их closure.
   Проверить TFM, dependencies, release notes и breaking changes.
   Совпадение со [стартовыми фактами кандидата](README.md#проверенная-отправная-точка)
   подтверждается скачанным пакетом. Расхождение перепроверяет затронутые факты
   и не даёт права пропустить прогоны.
3. Сопоставить BuildHost/Contracts и client с текущим upstream:
   RPC methods/DTO, новые linked compiler files, runtimeconfig/deps, TFM host,
   roll-forward, MSBuild reference assemblies и Locator. Сверка включает
   `_MsbuildVersion`, TFM, `rollForward` и `runtimeconfig` поставляемого host.
   Не выводить совместимость одного профиля из другого. Три профиля:
   - compile-time зависимость клиента, включая `Microsoft.Build.Framework` >= 18.7.1
     и прямые pin `18.6.3`;
   - reference-пакет форка: `MsbuildReferenceVersion` `17.11.48`, его PackageDownload
     и четыре `Reference` на `ref\net8.0` (Microsoft.Build, Microsoft.Build.Framework,
     Microsoft.Build.Tasks.Core, Microsoft.Build.Utilities.Core) в
     `forks/roslyn-buildhost/build/BuildHost`;
   - MSBuild, который Locator загружает из каталога SDK в процессе host.
   Правило Locator (major/minor пакета MSBuild не выше минимально поддерживаемого
   toolchain) применять только к компоненту, который компилируется против этого пакета
   и загружает его через Locator. К форку, пока его reference-версия `17.11.48`,
   правило не применять. PackageDownload форка не переводить на 18.7.1 из-за
   зависимости клиента.
   Проверить процессы на каждой обязательной строке
   [матрицы](README.md#матрица-совместимости), а не на одном склеенном «SDK 10».
   Для точных `10.0.100`, `10.0.300` и `10.0.402` снять загрузку и семантические
   операции новым клиентом и новым host, с записанными путём MSBuild и ближайшим
   `global.json`. Прогон на `10.0.402` две другие строки не закрывает.
4. Проверить минимум Microsoft.Build.Framework >=18.7.1 нового пакета против
   прямых pins 18.6.3 в сервере и тестах как факт профиля клиента.
   Составить точный согласованный набор Microsoft.Build*, StringTools и Locator;
   runtime MSBuild по-прежнему поставляет SDK. Сохранить `ExcludeAssets=runtime`/PrivateAssets
   и security pin Pkcs, если их изменение не подтверждено составом новой closure и audit.
   Нижняя граница 18.7.1 сама по себе не записывается как наблюдаемый отказ MSBuild 18.0
   или 18.6 и не меняет reference-пакет форка.
5. Составить список всех потребителей версий/TFM: сервер, Tests, LifecycleTestHost,
   DeadlockWitnessHost, sample plugin, forks/build, spikes/BuildHostFork,

   `RawImportEvidenceFixture` отметить как копию корневого pin, а не как

6. Проверить риски: SQLite identity/native assets, MEF/reflection/internal Roslyn API,

   Reaper не расширять на произвольные процессы `dotnet`.
7. Подтвердить наличие исправления `2624f5c156` в выбранном client по исходникам/истории

## Результат и gate

Отчёт содержит inventory затрагиваемых файлов, точные package/source/runtime версии,
baseline tests/замеры, ссылки на raw evidence и решение о порядке этапов.
Для каждой названной строки матрицы в отчёте есть номер или band, `rollForward`,
фактические версия и путь MSBuild, ближайший `global.json`, рабочий каталог и результат.

Сохраняется запрет зелёного gate через смену RPC guard, скрытое требование runtime
и тихое отключение старого сценария. Установленный SDK 11 не доказывает работу
на машине с одним SDK 10. Успех только на `10.0.402` не закрывает строки
`10.0.1xx` и `10.0.300`.

Исходы полос, не сводимые друг к другу:

- Прежний профиль подтверждён прогоном каждой названной строки, включая точные
  `10.0.100`, `10.0.300` и `10.0.402` новым клиентом и новым host. Gate полос пройден.
  Минимум по-прежнему не назначается: подтверждение профиля не записывает
  `10.0.4xx` как новый минимум.
- Названная ранее положительная строка не проходит. Gate продолжения не пройден.
  В отчёте лежат измерения и причина. Исполнитель не поднимает минимум и не начинает
  этапы 1–3. Минимум меняется только отдельным решением владельца, которое называет
  полосу явно. После записи этого сужения этапы 1–3 могут начаться в названных границах
  и дальше их не сужают. Отказ владельца означает no-go обновления и этапы 1–3 не открывает.
  Формулировка «SDK 10.0.4xx и новее» без такой записи не используется.
  Переписывание `PinnedSdk.Version` этим решением не требуется и ради зелёного прогона
  не выполняется.
- Несовместимость полосы SDK или версии MSBuild не называется «host требует runtime 11».

Смена порядка этапов из-за runtime host остаётся отдельным, самостоятельно доказанным
исходом и не подменяет три исхода выше. Для кандидата 5.12.0 поставляемый host —
`net8.0`, `rollForward` `Major`; одного этого факта для смены порядка недостаточно.
Если наблюдаемый процесс host действительно требует runtime 11 раньше сервера,
сначала описать минимальное изменение порядка и границ с причиной.

Продолжение к этапам 1–3 допустимо, когда зависимости и протокол подтверждены,
обязательные строки имеют реальные результаты, B0 воспроизводим, обязательные исходные
проверки текущего продукта имеют реальные результаты и либо все ранее положительные
строки прошли, либо владелец явно назвал сужение и оно записано в отчёте.
No-go это продолжение не открывает. Непройденная ранее положительная строка без записи
владельца оставляет gate непройденным. Перечисление проблемы без этой записи решением
не является. Дальнейшая реализация на этом этапе не начата. Изменившиеся версии upstream
требуют повторной проверки затронутых фактов.
