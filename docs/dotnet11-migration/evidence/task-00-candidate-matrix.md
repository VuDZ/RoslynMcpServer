# Этап 0 — Roslyn 5.12.0 и штатный BuildHost

Дата прогона 2026-11-18. Предмет проверки — пакетный `MSBuildWorkspace` 5.12.0 и поставляемые с ним BuildHost на Windows x64, с повтором ранней отмены на Ubuntu 24.04 x64 в WSL 2. Стенд собран как приложение `net10.0` на SDK `10.0.402` из временной копии [BuildHostFork](../../../spikes/BuildHostFork/BuildHostFork.csproj). В копии заменены ссылки на Roslyn `5.12.0` и Microsoft.Build/Framework/StringTools `18.7.1`, Locator `1.11.2` сохранён. Fixture, probe и полные логи находятся в локальном игнорируемом каталоге `artifacts/dotnet11-candidate`. Сводка с исходными путями, результатами, stack trace и выдержками hostfxr сохранена в [raw JSON](raw/task-00-candidate-matrix.json).

Release-сборка стенда и restore завершились с кодом 0. Пакетный клиент сообщил `5.12.0-1.26502.2+1324e1d34a0490454837a22370e75bbaeecffb87`. SHA-256 реально запущенного netcore host `E37884C7258FF597C32E3234E912D59E475C5327C7FA4CA15896FB2409E0D67D` совпал с DLL из `.nupkg`. По `runtimeconfig` host таргетирует `net8.0` с framework `8.0.0` и `rollForward=Major`. Клиент передал host процессу `--roll-forward LatestMajor`, и `hostfxr` зафиксировал реально выбранный shared framework. Для точных SDK `10.0.100` и `10.0.300` SHA-512 скачанных ZIP совпал с [Microsoft release metadata](https://builds.dotnet.microsoft.com/dotnet/release-metadata/10.0/releases.json). Системные SDK `10.0.402` и `11.0.100` использовались напрямую и в отдельных каталогах с доступными им ref packs. [Raw JSON](raw/task-00-candidate-matrix.json)

## Точные потребительские SDK

Каждый успешный запуск открыл `.slnx`, нашёл `Smoke.Value` и его definition и reference, переименовал символ через `Renamer` и заново проверил компиляцию. На перечисленных ниже трёх точных строках workspace и обе компиляции не выдали ошибок. Отдельный RPC-клиент существующего стенда получил `FindBestMSBuild`, `HasUsableMSBuild` и полный `ProjectFileInfo` одной фикстуры. Фактический MSBuild внутри design-time build подтверждён `MSBuildToolsPath` и `MSBuildVersion`, записанными `Directory.Build.targets`. Версия RPC `MsBuild.version` является номером SDK. Версия `dotnet msbuild -version` и версия MSBuild во время design-time build приведены отдельно в raw JSON.

В следующих строках `A` обозначает `E:\Devel\dotnet11-migration-plan\artifacts\dotnet11-candidate`. Каждый Windows-процесс запущен с cwd `A\win-results\<имя строки>` и ближайшим `global.json` непосредственно в этом cwd. `allowPrerelease` равен `false`, `rollForward` равен `disable`, кроме явно названной строки. Путь MSBuild означает `<каталог ниже>\MSBuild.dll`.

- **`only10-100`** — `A\sdk\10.0.100\dotnet.exe`, единственный SDK `10.0.100`. MSBuild `18.0.2` (`18.0.2.52411` у CLI) из `A\sdk\10.0.100\sdk\10.0.100`. Клиент и host работали на `.NET 10.0.0`. Загрузка, семантика и RPC прошли.
- **`only10-300`** — `A\sdk\10.0.300\dotnet.exe`, единственный SDK `10.0.300`. MSBuild `18.6.3` (`18.6.3.23102` у CLI) из `A\sdk\10.0.300\sdk\10.0.300`. Клиент и host работали на `.NET 10.0.8`. Загрузка, семантика и RPC прошли. Тесты продукта с `RequiresPinnedSdk` учитываются отдельно от этой экспериментальной фикстуры.
- **`only10-402`** — `A\sdk\10.0.402\dotnet.exe`, единственный SDK `10.0.402`. MSBuild `18.9.15` (`18.9.15.50611` у CLI) из `A\sdk\10.0.402\sdk\10.0.402`. Клиент и host работали на `.NET 10.0.15`. Загрузка, семантика и RPC прошли.

Все три точных SDK загрузились с новым клиентом и новым host на Windows без shared runtime 11. Эти результаты отделяют работоспособность runtime MSBuild 18.0, 18.6 и 18.9 от compile-time зависимости NuGet `Microsoft.Build.Framework >= 18.7.1`. Наблюдение не даёт оснований переносить переход runtime сервера перед переходом Roslyn.

Отдельная строка `net9.0` с точным SDK `9.0.314` прошла на Windows x64 с MSBuild `17.14.43` и BuildHost на .NET `9.0.16`. [Методика и результаты дополнительного прогона](task-00-baseline-and-dependencies.md#net90-с-точным-sdk-90314).

## Ранняя отмена и жизненный цикл

На Windows использован `only10-402`. На Ubuntu x64 использованы `/usr/lib/dotnet/dotnet`, точный SDK `10.0.115` с MSBuild `18.0.37` (`18.0.37.53008` у CLI) из `/usr/lib/dotnet/sdk/10.0.115`, рабочий каталог `/tmp/roslyn512-task00-zjCNit/fixture`, `global.json` с `rollForward=disable`. Клиент и host Linux работали на `.NET 10.0.15`. Штатная загрузка и семантический запрос прошли. Linux-прогон относится к сценарию отмены и ещё одному представителю `10.0.1xx`. Точный `10.0.100` подтверждён отдельной строкой Windows.

Сценарий `cancel ... 0` из [существующего стенда](../../../spikes/BuildHostFork/FailureScenario.cs) повторён трижды на каждой платформе. Самплер увидел один дочерний BuildHost на каждом запуске, затем токен отменился в `BuildHostProcessManager.NoLock_GetBuildHostAsync` после начала RPC. Диагностика подтвердила `Failed to initialize BuildHost process`. После ожидания оставалось **0** PID во всех шести прогонах. Самплер сообщает число до возможной аварийной очистки. При отмене с задержкой 500 мс на обеих платформах запрос отменился после initialization, оставалось 0 host. При `kill-host ... 500` на обеих платформах `OpenSolutionAsync` вернул решение и `Failure` с PID убитого host. Осталось 0 host, повторная инициализация отдельным PID не наблюдалась. Заранее отменённый токен на Windows завершил запрос до запуска host. [Raw JSON](raw/task-00-candidate-matrix.json)

На Windows выполнены два дополнительных сценария с параллельным экземпляром BuildHost. В первом ранняя отмена завершилась `canceled`. Во втором `kill-host ... 100` завершился ошибкой `The server disconnected unexpectedly`. В каждом сценарии тот же клиентский процесс повторил загрузку в новом workspace, увидел новый PID, подтвердил чистую семантику с rename и вызвал `Dispose`. После повторов оставалось 0 собственных host. Независимый клиент `58576` получил после обоих вмешательств ответ от своего BuildHost `60304` по первоначальному pipe и штатно завершился. [Raw JSON](raw/task-00-candidate-matrix.json)

Эти результаты и анализ исходников подтверждают клиентское исправление `2624f5c156`. Старый reaper и статус старой задачи остаются предметом её собственной приёмки. Перезагрузка и shutdown MCP-сервера с новым production-клиентом требуют интеграции этапа 1. [Проверка исходников](task-00-dependencies.md), [MSBuild Server `/nodemode:8`](task-00-msbuild-server.md)

## Дополнительные сценарии и границы проверки

- В Windows на `10.0.402` прошли открытие проекта `.csproj` и решений `.sln`, `.slnx`, `.slnf`, семантический запрос и rename с перекомпиляцией. На WPF-примере CLI создал `Smoke_uostqjuw_wpftmp.csproj` и собрал `net10.0-windows`. Затем пакетный workspace загрузил проект с чистой компиляцией. Сохранение графа watcher при параллельной сборке проверяется на продукте.
- В Windows старый проект `net472` без SDK собран Visual Studio MSBuild `18.12.2.51402`. Roslyn 5.12 запустил `BuildHost-net472\Microsoft.CodeAnalysis.Workspaces.MSBuild.BuildHost.exe` и получил рабочую семантику на C# 7.3. Design-time build использовал `C:\Program Files\Microsoft Visual Studio\18\Enterprise\MSBuild\Current\Bin\amd64`, MSBuild `18.12.2`, `MSBuildRuntimeType=Full`. Установлен .NET Framework release `0x82405`. Пакетный net472 host подтвердил `HasUsableMSBuild=True` на отдельном прямом RPC. Применимость `FindBestMSBuild` ограничена netcore host, что подтвердил `NotImplementedException` при вызове этого метода у net472.
- SDK `11.0.100` собрал `net11.0` с union types, closed hierarchy, collection expression arguments, extension indexer и labeled `break`/`continue`. Тестовый цикл дал одно предупреждение `CS0162`. Workspace 5.12 на shared runtime 10 дал `ParseOptions=15.0`, compilation без ошибок, definition, references и rename с перекомпиляцией. [Синтаксис C# 15](https://learn.microsoft.com/en-us/dotnet/csharp/whats-new/csharp-15)
- Отдельная библиотека `netstandard2.0` с явным `LangVersion=15.0` содержит невиртуальный статический метод интерфейса с телом и вызов на интерфейсе. CLI и workspace успешны, `ParseOptions=15.0`, `CS8701` и другие ошибки отсутствуют, definition и reference видны, rename перекомпилировался. При единственном изменении `LangVersion=14.0` та же проверка воспроизвела прежнее ограничение и актуальный diagnostic `CS9327` как в CLI, так и в workspace. Это конкретный ID Roslyn 5.12 для ограничения языка 14.
- На Windows `10.0.402` граф из `net10.0;netstandard2.0` проекта и `net10.0` библиотеки дал три чистые компиляции. Связанный файл из shared `.projitems` присутствовал на обоих TFM в папке `Shared`. Условный project reference появился только для `net10.0`. `Directory.Build.props` добавил ожидаемый define. `Directory.Build.targets` добавил файл в `Project.AdditionalDocuments`. Корневой `.editorconfig` обнаружен в `AnalyzerConfigDocuments` каждого проекта. Увидены и обычные SDK-generated AssemblyInfo документы в `obj`.
- Контрольный граф с отсутствующим проектом и повреждённым XML вернул явные диагностики `Project file not found` и `Unexpected end of file`. F#-запись попала в граф с двумя SDK-generated документами. Пакетный workspace не предоставил для неё parse options, compilation и отдельную диагностику неподдерживаемого языка. Обработка чужих языков на MCP-границе требует продуктового прогона.
- Применимые IDE code actions, семантика source generators после publication/rebuild/reload, watcher при изменении и удалении файлов, SQLite cold/warm, snapshot/codec и plugin/analyzer admission требуют дальнейшей validation. Новый форк и production `SC`/`FDD` на runtime 11 относятся к этапам 1–3. Нативного стенда macOS arm64 для этой серии нет.
