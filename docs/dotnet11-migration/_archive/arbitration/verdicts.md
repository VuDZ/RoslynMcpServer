## Утверждение Grok

Отправная точка плана неверно говорит, что корневого pin нет, и этап 2 запрещает добавлять корневой `global.json`. При сохранённом файле `10.0.100` / `latestFeature` CLI остаётся на SDK 10 и не собирает сервер `net11.0`. Замена того же файла на `11.0.100` / `latestFeature` снова расходится с reader и даёт ложный `MCP_MSBUILD_SDK_MISMATCH`, если рядом есть более новый SDK 11. Нужен точный SDK 11 с `rollForward: disable` либо предварительное закрытие AR-18.

## Ответ Astra

ACCEPT. Назвать фактический pin. В этапе 0 не приписывать reader поддержку `latestFeature`. В этапе 2 обновить существующий файл на точный стабильный SDK 11, `rollForward: disable`, `allowPrerelease: false`; тем же номером закрепить CI и release. AR-18 этим не закрывать. Пользовательские `global.json` не переписывать.

## Проверка

Фактическая ошибка отправной точки подтверждена файлом на диске. По [правилам global.json](https://learn.microsoft.com/en-us/dotnet/core/tools/global-json) `latestFeature` берёт наивысшие feature band и patch той же major.minor не ниже запрошенной версии и при отсутствии такого SDK завершается ошибкой. На major 11 эта политика не переходит. Пока установлен любой SDK 10.0 не ниже `10.0.100`, перевод проекта на `net11.0` этим файлом не собирается. Сценарий отказа этапа 2 верен.

Утверждение, что `disable` — единственная политика, которую reader исполняет так же, как CLI, шире кода. При установленной названной папке с ней совпадает и `patch`: CLI оставляет названную версию, reader возвращает ту же папку. Они расходятся, когда названной папки нет: `patch` уходит на более новый patch, reader закрепление теряет. `latestFeature`, `latestPatch` и `feature` расходятся ещё и при установленной названной папке, если есть более высокий patch или band. Для pin репозитория нужен именно `disable`: отсутствующий точный SDK даёт явный отказ CLI, а не тихий переход. Это и есть предложенное исправление; оговорка не отменяет его.

Вариант «сначала закрыть AR-18» для этой миграции не требуется. Цель владельца — перевести собственную сборку и затем runtime, сохранив проверяемые потребительские сценарии. Строгий pin совпадает с уже принятым приёмом release (`10.0.402`, `disable`) и с тем, что reader реально делает. Реализация всех политик `rollForward` остаётся открытым AR-18 и не входит в объём перехода.

Дополнения Astra про этап 0, одинаковый номер в CI/release и правку устаревшей фразы ARCHITECTURE нужны, чтобы закрыть тот же сценарий отказа. `test-suite.yml` без `global-json-file` всё равно подчиняется корневому файлу. `release.yml` перезаписывает checkout; если там останется `10.0.402`, сборка `net11.0` снова пойдёт чужим SDK. `allowPrerelease: false` уже стоит в файле и сохраняется: reader это поле не читает, но при точной стабильной версии оно не пускает prerelease в выбор CLI.

Проверка приёмки, предложенная защитой, следует из требования: при одновременно установленных SDK 10, точном SDK 11 и более новом SDK 11 сборка репозитория, `dotnet --version`, workspace и build/test через MCP выбирают один toolchain и не дают ложного `MCP_MSBUILD_SDK_MISMATCH`. Нет точного SDK — воспроизводимый отказ, без подмены другим номером.

Номер `11.0.100` остаётся кандидатом из этапа 2. В pin попадает тот точный стабильный SDK 11, который реально есть на Windows x64, Linux x64 и macOS ARM64. Плавающий `11.0.x` при `disable` не является этим pin.

## Что менять

См. `normative-change-set.md`, правки R-01. Изоляция потребительских сценариев от нового корневого pin — отдельное требование NEW-ARB-001, не замена этой правки.

## Граница

Host кандидата 5.12.0 собран как `net8.0` с `rollForward` `Major` и в исходниках commit `1324e1d` по-прежнему ссылается на `17.11.48`, а не на 18.7.1. Правило Locator — major/minor compile-time пакета не выше минимально поддерживаемого MSBuild — применяется только к той сборке, которая реально загружает MSBuild через Locator. ## Почему граница такая

Дефект текста плана подтверждён. Матрица действительно говорит об одном «SDK 10». Gate этапа 0 действительно называет только случай «host требует runtime 11» и запрещает получить зелёный результат отключением старого сценария. При реальном отказе одной полосы у исполнителя нет честного исхода: либо он назовёт `10.0.402` всем «SDK 10», либо объявит отказ потребностью runtime 11, которую runtime 11 не лечит, потому что MSBuild 18.0 и 18.6 лежат в каталоге SDK 10.

Вывод, что этот отказ уже доказан полом 18.7.1, не следует из требований и противоречит составу кандидата. Nuspec 5.12.0 фиксирует зависимость библиотеки клиента. Процесс, который загружает MSBuild SDK, — отдельный BuildHost; его поставляемый контракт и reference-пакет другие. Ссылка `ref\net8.0` ломается на пакете 18.7.1, но план и upstream-проект кандидата не направляют форк на этот пакет. Предписание «указать путь на TFM нового пакета 18.7.1» само создало бы несовместимую сборку host.

Рекомендация Locator верна как ограничение обещания для того компонента, который компилируется против нового MSBuild и загружает его. Она не переносит номер 18.7.1 на host, собранный против 17.11.48, и не заменяет прогон. Поэтому предложенный минимум `10.0.4xx` не входит в план ни как решение, ни как «консервативный кандидат нового минимума». Полосы остаются отдельными строками с открытым результатом. Какая из них останется поддерживаемой, записано в `unresolved.md`.

Поддержка Microsoft тоже не равна обещанию сервера: у `10.0.3xx` срок полосы уже закончился, у `10.0.1xx` — нет. Это причина не склеивать строки, а не причина вычеркнуть `10.0.1xx` заранее. Цель владельца — сохранить ранее проверенные сценарии SDK, пока измерение и решение владельца не скажут иное.

## Утверждение Grok

Критерий «после отмены, kill, shutdown и обрыва stdin не осталось своих BuildHost» не видит MSBuild Server. С SDK 11 он включён по умолчанию, живёт до 15 минут простоя, а прежнее безусловное `MSBUILDUSESERVER=0` CLI больше не пишет. Runner ставит `MSBUILDDISABLENODEREUSE=1` и не ставит документированный opt-out. Дерево процесса и reaper этот сервер не покрывают. Пока прогон не показал, что текущий флаг его гасит, runner должен передавать документированный opt-out. Ноль BuildHost не заменяет эту проверку.

## Ответ Astra

PARTIALLY ACCEPT. Отдельный gate нужен. Текущий runner сначала проверяется как есть, вместе с унаследованным окружением. Если флаг не обеспечивает политику или это не доказано, дочернему процессу задаётся `DOTNET_CLI_USE_MSBUILD_SERVER=false`. Утечка и блокировка файлов прогоном не доказаны, поэтому план не утверждает, что они уже есть. `dotnet build-server shutdown` не становится production-очисткой: команда может задеть чужие серверы. Reaper не расширяется на произвольные процессы `dotnet`.

## Граница

Меняется:

- В матрице и в native smoke этапа 3 появляется отдельное наблюдение MSBuild Server. Процесс сервера — `dotnet` с `MSBuild.dll` и `/nodemode:8`. Worker node reuse — `/nodemode:1`. Workspace BuildHost узнаётся по сборке `Microsoft.CodeAnalysis.Workspaces.MSBuild.BuildHost`. Ноль BuildHost не является PASS этого gate.
- Наблюдение снимается после обычных build/test, отмены, timeout, неуспешной сборки и shutdown: создание, повторное использование или отказ от сервера. Записываются PID, командная строка и время старта. Унаследованное окружение входит в проверку: SDK 11 больше не записывает `MSBUILDUSESERVER=0`, когда `DOTNET_CLI_USE_MSBUILD_SERVER` не задан.
- Этап 2 не отсылает исполнителя только к списку [breaking changes .NET 11](https://learn.microsoft.com/en-us/dotnet/core/compatibility/11). Этого пункта там нет. Обязательные источники — разделы «MSBuild server enabled by default» и «MSBuild server and OpenTelemetry environment variables» страницы [what's new in the SDK](https://learn.microsoft.com/en-us/dotnet/core/whats-new/dotnet-11/sdk) и страница [MSBuild Server](https://learn.microsoft.com/en-us/visualstudio/msbuild/msbuild-server).
- Сначала выполняется прогон текущего runner без нового opt-out. `MSBUILDDISABLENODEREUSE=1` ни одна из этих страниц не называет opt-out нового сервера. Страница сервера говорит, что `/nr:false` выключает сервер, потому что сервер — форма node reuse; эквивалентность переменной этому ключу на SDK 11 не доказана. Пока прогон не показал, что текущий флаг не оставляет постоянный сервер, дочерний процесс получает `DOTNET_CLI_USE_MSBUILD_SERVER=false`. Если при этом унаследованный `MSBUILDUSESERVER` всё ещё поднимает сервер, тому же дочернему процессу дополнительно ставится `MSBUILDUSESERVER=0`. Окружение машины не меняется. Второй механизм не добавляется, если прогон доказал достаточность уже стоящего флага.
- `dotnet build-server shutdown` допустим только как очистка изолированной тестовой среды после уже записанного наблюдения. Сама очистка не превращает неуспешный lifecycle в PASS. В поставке и в обычной работе сервера эта команда не вызывается: она не ограничена деревом собственного процесса.

Не меняется:

- План не утверждает, что текущий runner уже оставляет сервер и блокирует следующий publish. Такого прогона на SDK 11 нет.
- `UnregisteredBuildHostReaper` не начинает завершать произвольные `dotnet`, MSBuild Server и worker nodes. Чужой сервер сборки и BuildHost другой сессии по-прежнему не завершаются.
- `/nr:false` не добавляется вместе с переменными «на всякий случай». Он допустим только если прогон показал, что названные переменные сервер не гасят, а этот ключ гасит.

## Почему граница такая

Расхождение критерия приёмки с новым поведением SDK подтверждено документацией и кодом. Прежний CLI сам подавлял сервер. SDK 11 этого не делает. Runner подавление не ставит. Успешный `dotnet build` завершается, а сервер остаётся вне дерева, которое убивается только при timeout или cancel. Reaper ищет другую сборку. Список breaking changes, на который указывает этап 2, этот пункт не содержит, поэтому исполнитель, читающий только его, gate не увидит.

Требование немедленно вписать opt-out, не оставив прогона текущего флага, сильнее доказательств. Флаг может оказаться достаточным, и тогда второй механизм не нужен. Недоказанность при этом не даёт права принять этап: исход «не проверено» не является PASS, и тогда opt-out обязателен. Это совпадает с проверяемой частью критики и не объявляет сбой уже воспроизведённым.

Глобальный shutdown как способ пройти приёмку противоречит уже записанному правилу не завершать процессы других сессий. Наблюдение до очистки это правило сохраняет.

## Утверждение

После исправления R-01 корневой `global.json` выбирает точный SDK 11. Поиск `global.json` у CLI и у сервера начинается с разных точек, и оба идут вверх к предку. Сценарий «SDK 10 по точному `global.json`», запущенный из корня репозитория, молча становится сценарием SDK 11.

## Доказательство

[Документация global.json](https://learn.microsoft.com/en-us/dotnet/core/tools/global-json) разделяет два поиска. Muxer CLI начинает с текущего рабочего каталога, а не с каталога проекта. Резолвер SDK проекта начинает с каталога solution, если он есть, иначе с каталога проекта.

Сервер задаёт рабочий каталог дочернего `dotnet` через `WorkspaceRootResolver.ResolveDotNetWorkingDirectory` (`Services/Workspace/WorkspaceRootResolver.cs:10-23`): от каталога проекта вверх до ближайшего предка с `global.json` (`:49-61`). `GlobalJsonSdkReader` читает тот же ближайший файл. Если фикстура лежит внутри репозитория и своего `global.json` ближе корня нет, и CLI, и reader видят корневой pin. Если команда `dotnet` запущена с рабочим каталогом — корень, muxer видит корневой pin даже тогда, когда рядом с файлом проекта лежит другой `global.json`: поиск не спускается в каталог проекта.

`RawImportEvidenceFixture` копирует корневой `global.json` в временный каталог намеренно, чтобы временные проекты шли тем же SDK, что и reader (`RoslynMcpServer.Tests/WorkspaceStateCache/RawImportEvidenceFixture.cs:24-26`). После смены корневого pin эта копия следует за SDK репозитория. Она не является потребительским случаем SDK 10.

Матрица уже говорит «SDK 10 по точному `global.json`» и упоминает cwd, но не фиксирует, какой файл при двух pin оказывается ближайшим. Без этого правила зелёная строка SDK 10 после R-01 не доказывает сохранность прежнего сценария. Это прямо бьёт по цели владельца.

## Что менять

Для каждой потребительской строки матрицы ближайший `global.json` к фактическому рабочему каталогу CLI и к каталогу, от которого сервер ищет pin, — файл этого случая, а не pin сборки репозитория. Записанные путь `dotnet`, версия SDK и путь MSBuild берутся из этого запуска. `dotnet --version` в корне репозитория эту строку не закрывает. Копия корневого файла в `RawImportEvidenceFixture` после смены pin остаётся слепком toolchain репозитория; ожидания этой фикстуры обновляются явно и не используются как доказательство строки SDK 10.

Пользовательские `global.json` вне репозитория не переписываются. Реализация политик `rollForward` по-прежнему не входит в миграцию.
