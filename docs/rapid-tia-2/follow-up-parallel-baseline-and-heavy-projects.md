# Уровень 0 при параллельном запуске и тяжёлые тестовые проекты

Статус **accepted 2026-11-19**. Разобраны два тяжёлых проекта по девяти прежним правкам, выполнены четыре
пары L0-C и TIA-C и два справочных прогона `depth: direct`. Тестовый этап TIA-C короче на 4,59 с,
полный цикл дольше на 1,91 с по медиане парных разниц. [Отчёт по полному Jellyfin](mvp/evidence/parallel-baseline-2026-11-19.md).
Менять инструкцию агенту или `run: true` владелец решает по цифрам отдельно.

## Почему

[Замер способов запуска](mvp/evidence/test-run-strategy-2026-11-19.md) показал на полном Jellyfin:

- параллельный запуск выбранных проектов сократил тестовый этап Rapid TIA с 61–67 до 42–46 с;
- тестовый этап теперь почти равен самому долгому процессу, `Jellyfin.Server.Integration.Tests`
  (42–46 с). Этот проект и `Jellyfin.Server.Implementations.Tests` выбраны во всех девяти пробах и заняли
  91,7% тестового этапа Rapid TIA;
- медиана процесса `Jellyfin.Server.Integration.Tests` у Rapid TIA 44,5 с, у уровня 0 43,8 с: фильтр
  его не ускоряет.

Выигрыш Rapid TIA до сих пор измерялся против уровня 0, который запускал проекты по очереди. Уровень 0
выбирает те же два тяжёлых проекта. Его остальные проекты по оценке укладываются в окно
`Integration.Tests` на 8 ядрах, поэтому при параллельном запуске разница с Rapid TIA может стать
малой. Это расчёт по медианам процессов, не замер.

## Шаг 1. Разбор уже собранных данных

Новые прогоны тестов не нужны. Источники — `artifacts/rapid-tia-profile/strategy-history.json`,
TRX [замера цикла](mvp/evidence/jellyfin-edit-test-cycle-2026-11-19.md) и сохранённые ответы
`NN/estimate_affected_tests.txt`.

- Для `Jellyfin.Server.Integration.Tests` и `Jellyfin.Server.Implementations.Tests` по каждой из девяти
  правок: сколько тестов выполнено у Rapid TIA и у уровня 0, «целиком» или по фильтру, с какой причиной.
- С какой ступени `depth` (`changed`, `direct`, `di`, `all`) эти проекты попадают в план. Если сохранённые
  ответы ступени не показывают, повторить `estimate_affected_tests` с `run: false` для каждой ступени на
  правках № 1 и № 3: оценка занимает секунды, тесты не запускаются.
- Для `Integration.Tests`: какая часть окна TRX уходит на подъём хоста, а какая на сами тесты. Оценка —
  разница между началом окна и началом первого теста, сумма `duration` и время самых долгих тестов.

## Шаг 2. Уровень 0 параллельно

На правках № 1 и № 3, по две пары, с той же методикой, что в
[замере способов запуска](mvp/evidence/test-run-strategy-2026-11-19.md): одна сборка, вариант C
(параллельно, не больше числа физических ядер, отдельный каталог результатов у каждого процесса).

| Вариант | План |
| --- | --- |
| L0-C | Все тестовые проекты уровня 0 целиком, параллельно |
| TIA-C | Живой ответ `estimate_affected_tests` с `depth: all`, параллельно |

Порядок вариантов меняется между повторами. Если шаг 1 покажет, что тяжёлые проекты приходят только со
ступеней `di` или `all`, добавить TIA-C с `depth: direct` как справочный вариант.

## Что записать

Отчёт `mvp/evidence/parallel-baseline-<дата>.md`:
- машина, SDK, SHA сервера и Jellyfin, командные строки;
- итог шага 1: таблица по двум тяжёлым проектам и ступени, с которых они приходят;
- по вариантам шага 2: тестовый этап и полный цикл, число процессов, выполненные, упавшие и пропущенные
  тесты, самый долгий процесс;
- парная разница L0-C и TIA-C;
- загрузка процессора, если она заметно меняет время самого долгого процесса между вариантами.

Сырые TRX и логи остаются локально, в репозиторий попадают только сводки.

## Вне задачи

- Изменение `run: true`, инструкции в [`AGENTS.md.sample`](../../AGENTS.md.sample) или правил графа.
- Другие solution. Если на Jellyfin выигрыш при параллельном запуске окажется малым, выбор следующего
  корпуса решает владелец.
