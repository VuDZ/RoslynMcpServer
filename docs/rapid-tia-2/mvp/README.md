## Цель

По D-07 инструмент подсказывает агенту, какие тесты имеет смысл запустить после правки, и не заменяет CI. Он
должен находить значительную часть затронутых тестов и выбирать не слишком много лишнего. Числа, на которых
принято решение, — в [критерии](../README.md#критерий).

## Как это работает

1. **Загрузка solution.** Сервер читает выходные сборки проектов solution и запоминает снимок: отпечаток
   каждого типа верхнего уровня (хеш его скомпилированного кода) и зависимости между типами. Тесты не
   запускаются, MSBuild и семантика Roslyn не участвуют.
2. **Агент правит код и собирает.** MSBuild перезаписывает часть сборок.
3. **Агент вызывает `estimate_affected_tests`.** Сервер перечитывает сборки, файл которых изменился, и
   сравнивает отпечатки типов со снимком. Получается список типов, код которых действительно изменился.
4. **Ответ.** Для каждого тестового проекта из ответа эпохи 1 сервер находит тестовые классы, которые зависят
   от изменившихся типов, и отдаёт их ступенями. Тестовые классы, код которых изменился сам, идут первыми.
   Зависимость ищется по графу до правки и по графу после неё: правка может убрать саму связь.

Пересобранные сборки подсказывают, где искать изменения. Какие тесты затронуты, говорит граф зависимостей:
[опыт 2026-11-15](../evidence/il-build-diff-self-2026-11-15.md) показал, что правка тела метода не
перекомпилирует ни один зависимый проект.

### Ступени ответа

| Ступень | Тестовый класс попадает в неё, если |
| --- | --- |
| 0. Изменившиеся тесты | изменился код самого тестового класса: правка теста, вписанная компилятором константа, вызов, переключившийся на другую перегрузку. Сюда же входят новые и изменённые тесты эпохи 1 |
| 1. По ссылкам | он доходит до изменившегося типа по ссылкам в коде (слой `references` спайка) |
| 2. Через DI | он доходит до него через типы, которые находит контейнер или фреймворк (слой `discovery`) |
| 3. Через загрузку по имени | он доходит до загрузки сборки по имени; тогда он зависит от всех сборок solution, которые лежат в выходном каталоге его тестового проекта (слой `discoveryWithLoads`, каталог — по M-06) |

Каждая ступень включает предыдущие. Правила слоёв описаны в
[README спайка](../../../spikes/TestImpactIlProbe/README.md#layers). Слои `wholeAssembly`, `referencesWithLoads`
и `discoveryWithNamedLoads` в продукт не переносятся.

### Когда ответ не сужается

Для тестового проекта остаётся ответ эпохи 1 («проект целиком») с причиной в тексте, если:

- снимка до правки нет: при загрузке сборок не было на диске, либо сборка перезаписана раньше, чем сервер
  успел её прочитать в первый раз. Сборка, которую агент делает после этого чтения, снимок не отменяет;
- сборки после последней правки не пересобраны: файл сборки не новее изменённого исходника. Это проверяется
  при каждом вызове, а не только для первой правки сессии;
- тестовая сборка не пересобрана после изменения формы зависимости (собран только проект-зависимость);
- причина выбора проекта не в C#-коде: не-C# вход, файл проекта, устаревший граф проектов, разрыв наблюдения;
- сборка не читается, либо тестовый класс не удаётся сопоставить с именем для фильтра VSTest;
- фильтр не укладывается в бюджет длины эпохи 1.

Сужение никогда не добавляет тестовый проект, которого нет в ответе эпохи 1.

Отдельный случай — сужение удалось, а ступени пусты (M-05). Если отпечатки не изменились, ответ говорит, что
код в сборках не изменился. Если типы изменились, а тестовый класс до них не дошёл, ответ называет эти типы и
говорит, что тестов для них граф не нашёл. Проект целиком в обоих случаях не подставляется.

## Что берётся из спайка и что нет

Берётся чтение метаданных и IL, граф между типами верхнего уровня и три слоя
([`Reading`](../../../spikes/TestImpactIlProbe/Reading) и [`Graph`](../../../spikes/TestImpactIlProbe/Graph),
около 1800 строк). Не берётся: PDB и сопоставление файла с типами (типы даёт сравнение отпечатков), обход
каталогов `bin` в поисках сборок (пути выходных сборок сервер знает из загруженных проектов), покрытие,
`recall`, отчёты. Спайк остаётся измерительным инструментом и продуктом не используется.

Правило загрузки по имени в спайке опиралось на обход каталогов: он показывал, какие сборки лежат рядом с
тестовой. В продукте это заменяет карта соседства: одно перечисление файлов в выходном каталоге каждого
тестового проекта ([task-01](task-01-il-graph-in-product-med.md), M-06). Код сборок читается один раз, из
выходной сборки проекта, копии не читаются.

Следствие: PDB продукту не нужен. Ограничения спайка «только portable PDB» и «только Debug» на MVP не
переходят; при смене конфигурации снимка для новых путей нет, и ответ не сужается.

## Вне MVP

- Тесты из проектов, которых нет в ответе эпохи 1 (модуль, скопированный рядом без ссылки проекта).
- Сохранение снимка между сессиями.
- Точность до метода.
- MTP-проекты: как в эпохе 1, отдельно не распознаются.
- Целевые платформы, которых нет в загруженном workspace (M-07): их сборки не читаются, правка только под
  такую платформу выглядит как «код не изменился».
- Оценка по времени прогона вместо числа классов.
- Правила для типов, названных строкой или в конфигурации, и для тестов, запускающих другой процесс (Q-04).

## Поверхность инструмента

Предложение исполнителя, взято на пробу по M-03; подробности — в [task-05](task-05-tool-answer-and-run-hi.md).

- Один инструмент, как сейчас: `estimate_affected_tests`. Новый параметр `depth` выбирает ступень: `changed`
  (0), `direct` (до 1), `di` (до 2), `all` (до 3, по умолчанию).
- Ответ всегда показывает размер каждой ступени, в том числе шире выбранной. Агент видит, сколько классов
  добавит расширение, и решает сам.
- План запуска и `run: true` относятся к выбранной ступени.
- Для проекта, который остаётся целиком, причина названа одной строкой, как в эпохе 1.

Сужение без сборки по именам типов из синтаксиса возможно, но не видит константы и требует отдельного
сопоставления имён; по M-04 это улучшение после MVP.

## Известные риски

- **Молчаливая потеря теста** возможна тремя путями, и каждый закрыт своей задачей. Отпечаток пропускает
  изменение — task-02: список по фактам, проверка на каждый факт, полнота по таблицам метаданных. Ответ сужен
  по старой сборке — task-04: проверки свежести при каждом вызове. Правка убрала связь, по которой тест
  находился, — task-04: поиск по графам до и после правки.
- **Гонка снимка со сборкой.** Агент может собрать solution сразу после загрузки, пока идёт первое чтение.
  Правило task-03 делает такую сборку неизвестной до конца сессии, и ответ для зависимых не сужается.
  [Windows-проверка task-06](task-06-implementation-report.md#windows--сборка-во-время-фонового-чтения)
  воспроизводит гонку. В сериях замеров клиент дожидался первого чтения, поэтому они не измеряют частоту гонки.
- **Ступень 3 у́же измеренного слоя.** Спайк считал соседями и сборки из чужих каталогов, куда скопирована
  тестовая сборка; продукт по M-06 — только из выходного каталога тестового проекта. Полнота ступени 3 на
  открытых корпусах с этим правилом не перемерена; task-01 сверяет ответы со спайком на этом репозитории.
- **Блокировка файла на время чтения на Linux.** .NET держит рекомендательную блокировку, пока файл открыт,
  при любом режиме доступа. `dotnet build` копирует сборку поверх без ошибки; писатель из другого
  .NET-процесса с исключительным доступом или `File.Copy` с перезаписью в это окно получит ошибку. Окно —
  миллисекунды на сборку. Ревью task-01 выявило риск. Практический прогон task-06 выполнен на Windows.
- **Проект без ссылочной сборки.** Если агент собрал только проект-зависимость, тестовый проект остаётся
  целиком при любой правке, в том числе тела. В замере task-06 после каждой правки выполнялась сборка solution.
- **Экономия времени меньше экономии в классах.** Тесты, которые поднимают хост, попадают в ступень 3 почти
  для любой правки и стоят дороже остальных. В трёх дополнительных парах task-06 число классов уменьшилось
  на 43–71%, а запуск занял на 22–43% больше времени. [Условия замера](task-06-implementation-report.md#дополнительные-пары-с-фактическим-уменьшением-числа-классов).
