# MVP/task-06 — Сквозные проверки и замер на solution владельца

- Рекомендуемые модели: Claude Opus 5.5; альтернатива: GPT-6.1 Sol.
- Рекомендуемый reasoning: GPT: medium; для альтернатив — применимый режим, если поддерживается.
- Примерная сложность: 3/5; класс `med`.
- Риск ошибки: средний — приёмка по фикстурам без замера на настоящем solution повторяет ошибку
  предшественника, где способ опроверг первый же реальный замер.
- Необходимые способности: `независимая_проверка`, `измерение_производительности`, `документация`.
- Статус: **accepted 2026-11-19**. Приняты сквозные проверки на Windows, замер 20 правок в пяти проектах,
  девять правок на полном solution владельца и сравнение времени для трёх суженных пар в дополнительном
  тестовом solution. Обнаруженные дефекты вынесены в отдельные задачи. [Отчёт](task-06-implementation-report.md).
- Depends on: [task-05](task-05-tool-answer-and-run-hi.md).

## Цель

Собрать доказательства приёмки MVP и получить первые числа с настоящих solution: насколько ответ уже проекта
целиком, как часто он не сужается и сколько это стоит.

## Конкретный результат

**Сквозные сценарии** — одна таблица в отчёте со ссылками на тесты задач 03–05: правка тела, комментария,
константы, теста; удаление типа; снятый интерфейс; правка типа без тестов; правка без сборки; вторая правка
без сборки после первой собранной; сборка сразу после загрузки; reload; не-C# вход. Своей red-фазы у задачи
нет: сценарии написаны в задачах, которые реализуют поведение.

**Прогон на Windows.** Сценарий «сборка во время фонового чтения снимка» выполнен на Windows собранной версией
сервера: сборка агента не падает с ошибкой доступа к файлу, затронутые сборки помечены «неизвестна».

**Замер на этом репозитории** — исполнитель, собранной версией сервера:

- время чтения снимка при загрузке и память двух снимков;
- для 20 правок тел методов в разных проектах: размер каждой ступени в классах против проекта целиком, время
  ответа инструмента.

**Замер на solution владельца** — владелец или исполнитель на его машине, по короткой инструкции в отчёте:

- те же числа для нескольких правок, которые владелец считает обычными;
- сколько раз ответ не сузился и по какой причине, отдельно — по правилу гонки снимка со сборкой;
- сколько раз исход был «изменившиеся типы без тестов»;
- ширина ступени 3 считается по карте соседства M-06 (выходной каталог тестового проекта), не по `Deployed`
  спайка;
- время прогона выбранной ступени против проекта целиком хотя бы для трёх правок: проверка риска «экономия
  времени меньше экономии в классах».

Имена проектов, типов и тестов закрытого solution в репозиторий не попадают: только числа и причины.

**Документы.** Статусы задач и плана, строка Rapid TIA 2 в [docs/README.md](../../README.md), ограничения MVP в
README продукта: что инструмент не видит (типы по имени в строке, другой процесс, проекты вне уровня 0,
целевые платформы вне загруженного workspace — M-07) и когда
не сужает.

## Вне scope

- Сверка с покрытием по тестовым классам на solution владельца: по D-07 полнота проверена на открытых
  корпусах, для подсказки этого достаточно.
- Исправления по итогам замера: существенная находка возвращается владельцу и оформляется отдельной задачей.

## Проверки

- Таблица сценариев полна: у каждого есть тест и он зелёный на финальном коде.
- Числа замера на этом репозитории воспроизводятся по командам из отчёта.
- Замер на solution владельца записан с датой, версией сервера и числом правок; если он не сделан, задача и
  MVP не помечаются принятыми, причина записана.
- По [AGENTS.md](../../../AGENTS.md): Release build и полный main suite на финальном коде; `AnalyzerLifecycle`,
  если после task-03 менялся путь публикации workspace.
