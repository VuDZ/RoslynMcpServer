# Профилирование оценки Rapid TIA на Linux, этот репозиторий

**2026-11-19.** На этом репозитории синхронизация после внешней правки и сборки заняла десятки миллисекунд.
Основное время оценки ушло на ошибки компиляции, уровень 0 и чтение IL. Один этап, ошибки компиляции,
считается по всей компиляции изменённого проекта. Опытная замена на диагностику изменённых документов
сократила медиану ответа с **15,11 до 9,58 с** при побайтно совпавших ответах. Отдельно найден линейный поиск под
блокировкой сессии, стоимость которого растёт квадратично с числом путей за сессию.

Задачи по итогам:

- [ошибки компиляции только по изменённым документам](../../follow-up-estimate-compilation-errors.md);
- [индекс наблюдений и разрывов покрытия в сессии входов](../../follow-up-input-session-notice-index.md);
- [замер удержания блокировки на Windows](../../follow-up-watcher-lock-diagnostics.md).

## Методика

Linux x64, 2 ядра, 3 ГБ памяти, .NET SDK 10.0.114, Release. Сервер 1.8.1 из `3942c4e`. Машина заметно
медленнее Windows-машины прежних замеров: первое чтение пяти сборок заняло **4,6–6,4 с** против **1,2 с**
в task-06. Абсолютные времена с Windows не сравниваются, сравниваются доли этапов и пары на одной машине.

Использован [клиент task-06](measure-task06.py) с `--external-save` на отдельной копии исходников `3942c4e`.
Взяты три правки из [списка task-06](task-06-self-cases.json): № 01, 04 и 08. На каждую правку — новый
MCP-процесс, ожидание baseline и первого чтения сборок, внешняя запись, `dotnet build -c Release --no-restore -m:1`,
затем `estimate_affected_tests` с `depth: all`, `run: false`. Время ответа — часы клиента.

```bash
export TMPDIR=$HOME_DIR/testtmp NuGetAudit=false MSBUILDDISABLENODEREUSE=1
python3 docs/rapid-tia-2/mvp/evidence/measure-task06.py "$serverDll" "$copy/RoslynMcpServer.sln" \
    "$cases" "$results" --external-save
```

Стеки сняты `dotnet-stack report` примерно раз в 1,5 с во время отдельных прогонов. Прогоны со снятием
стеков в таблицу времени не включены: снятие останавливает процесс.

## Время по этапам

Серверный лог: `workspace_disk_sync ... elapsedMs=65` и `elapsedMs=44`. Синхронизация после сборки на этом
репозитории и Linux не является узким местом. Порядок этапов по стекам контрольной сборки:

| Этап | Примерно, с |
| --- | ---: |
| `TestImpactEstimator.DocumentsAsync`, `BaselineDocumentSnapshotBuilder.Build` | 1,5–2 |
| Уровень 0: `ProjectImpactMapper.FindTestProjectsAsync`, `VstestTestInventory.BuildAsync`; в стеках финализация компиляций Roslyn, повторный запуск генераторов, привязка ссылок | ~5 |
| `TestImpactEstimator.CompilationErrorsAsync` | 8–10 |
| `AssemblySnapshotSession.BuildPairAsync`, чтение IL текущих DLL | 2–3 |

`CompilationErrorsAsync` вызывает `compilation.GetDiagnostics()` для всей компиляции каждого проекта, где
есть изменённый документ, и затем оставляет ошибки изменённых файлов.

## Опыт: диагностика изменённых документов

В отдельной копии, не в репозитории, тело цикла заменено на `document.GetSemanticModelAsync()` и
`model.GetDiagnostics()` для каждого изменённого документа проекта, с тем же отбором ошибок.

```text
Правка   Контроль, мс   Опыт, мс   Ответ
01            15109,6      9582,6   совпал побайтно
04            15595,7      9379,3   совпал побайтно
08            15016,0     10021,5   совпал побайтно
```

Медиана — **15,11 → 9,58 с**, около **−37%**. По одному прогону на правку. Во всех трёх правках ошибок
компиляции не было, поэтому опыт не проверяет равенство списка ошибок.

## Линейный поиск в сессии входов

`WorkspaceInputSession.RememberNotices` ищет запись через `List.FindIndex`, `RememberGap` — через
`List.Exists`. Событие из `bin/obj` без роли в карте классифицируется как `Unknown` и добавляет новую
запись в оба списка. Списки не очищаются до конца сессии, работа выполняется под `_gate`.

Временный тест вызывал `NotePendingContent` и `RecordDiskEvent` через `TryRun`, по два события на путь,
для N уникальных путей вида `.../bin/Release/net10.0/*.dll`. Сравнение строк на Linux порядковое, на Windows
порядковое без учёта регистра.

```text
Путей   Первый проход, мс   Те же пути ещё раз, мс
 1000                 181                       38
 2000                 135                      109
 4000                 793                      484
 8000                2031                     1872
16000                7450                     6658
```

Инкрементальная сборка этого репозитория после правки тела в основном проекте тронула **47** файлов.
В профиле Jellyfin в очереди сверки было 169 путей. Для одного цикла в свежей сессии этот поиск основным
источником задержки не выглядит. В долгой сессии каждый новый путь из `obj`, `bin` или результатов тестов
остаётся в списках и увеличивает стоимость каждого следующего события.

Сырые логи, ответы и стеки хранятся локально и в репозиторий не добавлены.
