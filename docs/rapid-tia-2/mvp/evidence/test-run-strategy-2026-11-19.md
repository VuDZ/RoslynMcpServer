## Парные прогоны

На правках № 1 и № 3 из [профилирования Jellyfin](jellyfin-estimate-profile-2026-11-19.md) делали по две пары.
Перед каждым вариантом восстанавливали исходники, загружали полный workspace и ждали снимка 41 DLL.
Таймер полного цикла начинался до внешнего сохранения. После правки выполняли одну инкрементальную
сборку и вызывали `estimate_affected_tests` с `depth: all`, `run: false`. Таймер заканчивался после
последнего запуска и чтения счётчиков TRX. В каждой паре меняли порядок A и C между повторами.

```powershell
dotnet build $solution -c Release --no-restore -m:1
dotnet test $project -c Release --no-build --no-restore `
  --results-directory $projectResults --logger 'trx;LogFileName=tests.trx' --filter $filter
```

A запускает команды последовательно. C запускает те же команды параллельно, до числа запускаемых
проектов или числа физических ядер, в зависимости от того, что меньше. У каждого процесса собственный
каталог результатов. Фильтры для отдельных проектов передаются буквально из ответа MCP.

B (запуск DLL), D (единый процесс VSTest) и E (`run: true`) остались за пределами сокращённого замера.
Для правок № 1 и № 3 объединение фильтров для D с группировкой в скобки заняло бы 8511 и 6909 символов
соответственно. Это укладывается в предел 16 000 символов планировщика. Совпадение имён между проектами
при таком запуске отдельным прогоном не проверяли. Замер выполнен на Windows.

Проверка параллельного запуска охватывает два состава проектов на одной машине.

при параллельном — 42,24–46,02 с. Выигрыш получен за счёт одновременного выполнения остальных проектов
с этим процессом.
