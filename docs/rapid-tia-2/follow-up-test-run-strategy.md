# Замер способов запуска выбранных тестов

Статус **accepted 2026-11-19**. Разобраны 165 процессов. По доле времени в окне тестов второй шаг сокращён
до A и C. Параллельный запуск сэкономил 19,30 с на полном цикле по медиане четырёх пар с одинаковыми
исходами тестов. Измерены холостые запуски для всех 16 проектов обоих планов.
[Отчёт и сверка TRX](mvp/evidence/test-run-strategy-2026-11-19.md).
Менять инструкцию агенту или `run: true` владелец решает по цифрам отдельно.

## Почему

После [индекса переименований](mvp/evidence/jellyfin-watcher-rename-index-2026-11-19.md) оценка на полном
Jellyfin занимает 6,6–7,1 с, полный цикл с VSTest — 69–76 с. Основное время цикла теперь уходит на тесты.
В [замере всего цикла](mvp/evidence/jellyfin-edit-test-cycle-2026-11-19.md) было так:

| | Уровень 0 | Rapid TIA |
| --- | ---: | ---: |
| Тестов на пробу | 2637–4248 | 586–1013 |
| Процессов VSTest на пробу | 14–16 | 3–6 |
| Тестовый этап, с | 88,2–115,8 | 55,7–65,9 |
| Тестовый этап на процесс, с (проба 04) | ~6,7 | ~19,6 |

Rapid TIA выбрала в 3–7 раз меньше тестов, а тестовый этап сократился только в 1,4–1,8 раза. На процесс у
Rapid TIA приходится втрое больше времени, чем у уровня 0. Возможны две причины, и от них зависит решение:

- **Постоянные затраты процесса.** `dotnet test <csproj>` вычисляет проект в MSBuild даже с `--no-build`,
  запускает testhost и ищет тесты во всей сборке, какой бы ни был фильтр. Эти затраты снимаются иначе:
  запуском по DLL, одним процессом на несколько сборок, параллельными процессами.
- **Дорогие тестовые проекты.** Тесты, которые поднимают хост, выбираются почти для любого файла
  ([README](README.md), что вошло в план MVP). Если время уходит на подъём хоста в фикстурах, способ запуска даст мало, и выигрыш
  возможен только за счёт более узкого выбора.

## Шаг 1. Разбор уже собранных данных

Новые прогоны не нужны. Источник — `artifacts/rapid-tia-jellyfin-cycle/run` на домашней машине: 165 TRX,
логи процессов и `cycles-verified.jsonl`.

Для каждого процесса VSTest:
- длительность процесса от запуска до выхода (строка `test N/M ...s` в выводе скрипта или время файлов);
- время от запуска процесса до начала первого теста и от конца последнего теста до выхода;
- сумма длительностей тестов из `UnitTestResult/@duration` и окно `Times/@start`–`@finish`;
- проект, ветка (уровень 0 или Rapid TIA), число выполненных тестов.

Итог шага — таблица по тестовым проектам: доля накладных расходов процесса, доля самих тестов (с подъёмом
фикстур) и сколько раз проект попал в выбор Rapid TIA за девять проб. Если накладные расходы малы, шаг 2
сокращается до варианта A и проверки параллельного запуска, а итог передаётся владельцу с выводом «время
уходит на тесты, а не на запуск».

## Шаг 2. Варианты запуска

На тех же правках № 1 и № 3, что в [профилировании](mvp/evidence/jellyfin-estimate-profile-2026-11-19.md).
Каждый вариант запускает тот же план из живого ответа `estimate_affected_tests` (`depth: all`, `run: false`)
после одной сборки solution. Одинаковые правки и план, порядок вариантов меняется между повторами.

| Вариант | Как запускать |
| --- | --- |
| A, контроль | Как сейчас: `dotnet test <csproj> -c Release --no-build --no-restore`, проекты по очереди |
| B | `dotnet test <dll>` или `vstest.console <dll>` по очереди, без вычисления проекта в MSBuild |
| C | Варианты A или B, проекты параллельно; степень — число проектов плана, но не больше числа ядер |
| D | Один `vstest.console` со всеми DLL плана и `/Parallel`. Фильтры проектов объединяются через `\|`, если план это допускает; иначе записать, почему вариант неприменим |
| E, справочно | Встроенный `run: true` с той же `depth`: он сам собирает выбранные проекты по очереди |

Для каждого тестового проекта плана отдельно записать нижнюю границу: запуск с фильтром, который не
выбирает ни одного теста. Это время процесса без исполнения тестов.

## Что записать

Отчёт `mvp/evidence/test-run-strategy-<дата>.md`:
- машина, SDK, SHA сервера и Jellyfin, командные строки каждого варианта;
- итог шага 1;
- по вариантам: время тестового этапа и полного цикла, число процессов, выполненные, упавшие и
  пропущенные тесты;
- имена и исходы тестов в TRX каждого варианта сверены с вариантом A. Расхождение — отдельная строка с
  причиной: общие файлы, порты, `TestResults`, отличие поиска тестов при запуске по DLL;
- ограничения: длина объединённого фильтра (планировщик держит фильтр в пределах 16 000 символов),
  тестовые проекты, которые нельзя запускать параллельно, Linux не проверялся.

Сырые TRX и логи остаются локально, в репозиторий попадают только сводки.

## Вне задачи

  Это решение владельца по итогам замера.
- Сужение выбора и правила графа.
- Microsoft.Testing.Platform: MVP работает с VSTest.
