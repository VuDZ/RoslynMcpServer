<a id="p-01"></a>
## P-01 · Доверие к `RoslynMcp.jsonc` из рабочего каталога (AR-02)

Уточнено 2026-11-15. С 1.5.19 конфиг читается из каталога exe, каталога пользователя и
рабочего каталога; порядок задан решениями O-01 и O-02 темы
[user-data-directory](../user-data-directory/README.md#решения-владельца). Эти решения не
рассматривали, можно ли доверять рабочему каталогу. Вопрос ниже их не отменяет: он касается
только ключа `plugins` из рабочего каталога.

1. **Рекомендуется:** ключ `plugins` читается из каталога exe, каталога пользователя и
   `ROSLYN_MCP_PLUGINS`; в конфиге рабочего каталога он игнорируется с предупреждением в
   stderr и логе. Остальные ключи этого конфига (`configuration`, `max-results`, …) остаются.
2. Оставить как есть и записать в ARCHITECTURE (инвариант 12), что содержимое
   открываемого репозитория считается доверенным, включая загрузку плагинов при старте.
3. Разрешать `plugins` из рабочего каталога только при явном opt-in переменной окружения.

Решение (2026-11-21): вариант 1. Каталоги exe и пользователя остаются источниками `plugins`,
`ROSLYN_MCP_PLUGINS` остаётся явным источником. Отдельный конфиг рабочего каталога
сохраняет остальные настройки. [Условия приёмки](priority-fixes.md#ar-02-источники-настроек-плагинов).

<a id="p-02"></a>
## P-02 · Размещение экспериментального StateCache (AR-05)

1. **Рекомендуется, пока эксперименты продолжаются:** код не переносить; одна строка в
   ARCHITECTURE («`Services/Workspace/StateCache/` — эксперимент, production-вызовов
   нет»); структурный тест «из production-кода нет обращений к `StateCache`» — снимается
   осознанно при интеграции.
2. Вынести в отдельный проект, на который ссылаются только тесты. Чище, но требует
   переноса internals и правок структурных тестов, которые анализируют production-дерево.
3. Если направление закрывается — удалить код, сохранив выводы в
   `docs/workspace-state-cache/`.

Во всех вариантах: записать в теме, где эксперименты упёрлись и что продолжается.

## P-03 · Поддерживаемые платформы (AR-12)

1. **Рекомендуется:** Linux-job для шарда `unit` (WPF-тесты исключить категорией, а не
   skip'ом, чтобы не конфликтовать с `Assert-NoSkippedTests.ps1`); релиз Linux —
   отдельным решением позже.
2. Официально объявить продукт Windows-only и сократить `RuntimeIdentifiers`.
3. Оставить как есть, явно указав в README «не-Windows не тестируется».

Решение (2026-10-21): расширенный вариант 1 — поддерживаются `win-x64` и `linux-x64`; обе платформы в CI (`unit` и `lifecycle`), красный job любой из них блокирует релиз; релиз выкладывает архивы обеих; остальные RID собираются, но не поддерживаются (arm — позже); реализация — [linux-x64-support](../archive/linux-x64-support/README.md).

Реализовано 2026-10-22, находка AR-12 закрыта.

## P-04 · Учёт статусов и хранение evidence (AR-16, AR-21)

Уточнено 2026-11-15. После раунда 1 в `docs/` добавилось 356 файлов, а в индексе появились
ещё три ячейки статуса длиной от 359 до 1159 символов. Вопрос стал острее, варианты прежние.

1. **Рекомендуется:** один источник статуса на тему (README темы); индекс
   `docs/README.md` — одна короткая строка и ссылка; README эпох и validation ссылаются
   на README темы, а не повторяют статус.
2. Сырые evidence (json/txt/trx/binlog) хранить вне git (артефакты CI/релиза или
   внешнее хранилище) либо сжатыми; в git — сводки и хэши.
3. Выровнять имена `archive/` / `review/` в `workspace-state-cache` с правилом `_archive/`.

Пункты независимы; 1 сильнее всего снижает риск повторения AR-04 и AR-21.
