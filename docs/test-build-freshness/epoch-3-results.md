# Эпоха 3. Результаты прогона

Статус эпохи в [спеке](epoch-3-races-and-acceptance.md): **выполнена** (2026-10-01), после ревью. Версия в `RoslynMcpServer.csproj` — `1.5.3` / `1.5.3.0` / `1.5.3.0`. Постоянный кэш не добавлялся. Поле хеша входа и хранилище путь→хеш не добавлялись.

## Что сделано

`TestDllEnsure` по-прежнему один шаг DLL-маршрута. На одном ключе сборки (проект, Configuration, Platform, TFM, buildArgs, выходной путь) операции этого процесса выстраиваются в очередь. Очередь не останавливает сборку вне процесса и не является семафором workspace. Ожидающий использует остаток исходного `timeoutSeconds`. Неуспех той операции, которую он ждал, и смена поколения для него не доказательство: тесты он на этом не запускает. Истечение его срока очередь не снимает и чужой процесс не убивает.

Между успешной сборкой и стартом тестов допускается одна повторная сборка, если сдвинулись ревизии входа того же поколения и того же membership или изменилась отметка выхода (длина и время записи файла). Вторая неудачная проверка останавливает запуск. Третьей попытки нет. Обе сборки и тестовый процесс делят один бюджет. Если времени на повтор не осталось, тесты не стартуют и вторая сборка не начинается.

Семафор workspace на время CLI не удерживается. Короткая проверка поколения берёт `PullInputSnapshot` и не захватывает этот семафор повторно. `execute_dotnet_command` и внешний `dotnet build` доказательством не становятся. Два контекста с одним выходным путём остаются unknown, пока путь не уникален.

Пропуск сборки по-прежнему выключен: у снимка нет хеша содержимого входа, `EvaluateReuse` не возвращает current.

## Реальная фикстура

Один прогон `TestDllEnsureSolutionFixtureTests.Solution_target_build_produces_the_dll_and_tests_use_no_build` через MCP `run_specific_test`, конфигурация Release тестового проекта. Хост `C:\Program Files\dotnet\dotnet.exe`, процесс 64-bit. `dotnet --version`: **10.0.300**. Runtime прогона: **.NET 10.0.8**.

Фикстура — временный каталог `%TEMP%\RoslynMcpDllEnsure\<guid>`, не `RoslynMcpServer.sln`. В корне пустой `Directory.Build.props`, чтобы сборка не подхватила props выше по диску. Два SDK-проекта `net10.0`: библиотека `Lib` и `AppTests` с `ProjectReference` на неё. Решение `App.sln` с `Debug|Any CPU` и `Build.0` для обоих проектов. Сборку и тестовый процесс выполнял боевой `DotNetCliRunner.RunWithMetadataAsync` из `TestDllEnsure`.

Команда сборки (аргументы боевого `DotNetTestArguments.BuildPreTestBuild`, проверенные на этом прогоне):

`build "<App.sln>" -t:"AppTests" -p:Configuration="Debug" -p:TargetFramework="net10.0"`

Команда тестов:

`test "<AppTests.dll>" --logger "console;verbosity=normal" --verbosity normal -c "Debug" --no-build --no-restore`

После сборки на диске были `AppTests\bin\Debug\net10.0\AppTests.dll` и `Lib\bin\Debug\net10.0\Lib.dll`. Тестовая команда содержит `--no-build` и путь к `AppTests.dll` и не содержит `-t:`. `AppTests` — обычная библиотека с `Main`, не сборка VSTest. Критерий прогона — что процесс тестов стартовал по этой команде против DLL, которую записала сборка решения. Код выхода тестового процесса критерием не был.

Повторный вызов на том же снимке снова вызвал `build` решения, а не подтверждённый пропуск. Причина второго запуска: `coverage unknown`. `SkipAllowed` после первой сборки — false, состояние не `current`, среди блокировок `InputContentHashAbsent`. У `Lib` доказательства нет, состояние не `current`: успех цели `AppTests` ссылочный проект не подтверждает. `TryRecordInvocation("execute_dotnet_command")` остался false.

Снимок фикстуры синтетический: покрытие unknown, пробел `LoadIncomplete` на весь граф, два пользовательских входа (`Program.cs`, `Marker.cs`). Это не загрузка решения через `load_workspace` и не живой watcher.

Решение без секции конфигураций на том же боевом вызове завершалось с кодом 0 и не писало DLL. В зелёном прогоне секция `Debug|Any CPU` / `Build.0` есть. Это свойство фикстуры, не отдельное изменение команды.

## Измерение одного прогона

Численный бюджет заранее не задавался. Ниже время одного локального прогона той же фикстуры, не норма.

| Шаг | мс |
|---|---:|
| Проверка до сборки (`Observe` + `EvaluateReuse`) | 4 |
| `EvaluateReuse` после первой успешной ensure, входы не менялись | 0 |
| Первая ensure (сборка решения и старт тестового процесса) | 1564 |
| Вторая ensure (снова сборка, пропуск не включён) | 1338 |

Вторая сборка — решение MCP собрать снова, а не измерение того, сочёл ли MSBuild проекты актуальными внутри этого `dotnet build`.

## Что исполнялось

Проверки гонки и приёмки исполняют `TestDllEnsure` и `SessionBuildState` (и для own-write — `WorkspaceInputSession`). Живой `FileSystemWatcher` в этих тестах не поднимался. Существующие тесты доставки watcher не копировались.

- Правка до сборки, во время сборки и между успехом и стартом тестов не запускает неподтверждённую DLL. Одна повторная сборка есть. Следующее изменение после неё тесты не запускает.
- Замена файла выхода до старта тестов даёт одну повторную сборку. Повторная замена после неё останавливает запуск.
- Общий бюджет: если первая сборка уже исчерпала `timeoutSeconds`, повтор не начинается.
- Один ключ не перекрывается. Успех предыдущей операции не даёт ожидающему пропуск. Её неуспех и смена поколения для ожидающего не доказательство. Истечение срока ожидающего не отменяет уже идущую операцию.
- Разные Configuration на одном проекте друг друга не сериализуют.
- Проверка поколения во время ensure не берёт семафор workspace.
- Таймаут сборки оставляет уже лежащую DLL неизвестной.
- Покрытие unknown, pending и пробел только по метаданным после успешной сборки остаются непригодными для пропуска. `SkipAllowed` false.
- Успех цели с `ProjectReference` не помечает ссылочный проект current и не выводит `BuildProjectReferences` из кода 0.
- Ревизия только generated/output повторную сборку производящего проекта не вызывает. `*_wpftmp.csproj` отсекается уже существующим `WorkspaceDiskPathFilter.IsWpfTemporaryProject`; второго фильтра нет. Имя вроде generated без роли вход не выбрасывает.
- Own-write и семантический flush не снимают ревизию, которую pull ещё сообщает. Два pull видят одни и те же ревизии.
- Общий выходной путь оставляет оба контекста unknown.
- Результат старого поколения после reset новую сессию не подтверждает.

Нагрузка WPF не ставилась. Решение WPF, XAML и внешний проект этой матрицы не собирались. Связанный файл вне корней watcher, общий файл двух проектов на живом watcher и тихий пропуск события на живом профиле здесь не исполнялись.
