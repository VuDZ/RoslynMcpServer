# Ответы: Epoch 2

Исходные замечания: [review/epoch-2-conservative-disk-cache.md](../review/epoch-2-conservative-disk-cache.md). O/A: [основания](sources-and-scope.md).

## E2-01

**Вывод: PARTIALLY ACCEPT.**

**Основание.** Формула «любое сомнение → miss» не защищает от неучтённого входа, о котором алгоритм не знает. Это реальный C-01, препятствующий безопасному hit по O8. Но review предлагает ложный выбор между обязательной evaluation и удалением V12: закрытый распознаваемый профиль с известными negative dependencies остаётся вариантом для доказательства. Вызов самого MSBuild не тождествен запрещённому собственному общему интерпретатору. Evaluation-only не покрывает произвольное выполнение targets.

**Предлагаемые изменения.** Epoch 2 «Алгоритм load» п.3–4 должен ссылаться на конкретный admission/evidence protocol Epoch 0 и contract §3–§5, а не только на сохранённый список файлов. Отказ профиля — до публикации и загрузки analyzer из DTO. V12 сохраняется; positive hit с условными входами возможен только после доказательства, negative unsupported проверяется отдельно.

**Последствия.** Admission/probe DTO и reasons, V12/V13; возможная evaluation учитывается отдельно в DTB/e2e telemetry. Снятие гарантии ради hit нарушило бы O8. Само наличие old snapshot не доказывает право исполнять его DLL (N3).

## E2-02

**Вывод: REJECT.**

**Основание.** Отвергается утверждение о подмене критерия приёмки: Epoch 2 «Приёмка» прямо требует performance-gate Epoch 0 **и** V01–V18/V23, а verification «Измерения» включает e2e и предупреждает о недостаточности счётчика OpenSolution. Review цитирует perf gate в Claim, затем игнорирует его в Evidence. Нулевой DTB count и equivalence — разные необходимые проверки; проверять отсутствие ненужного DTB полезно даже у host, который сам обычно его не вызывает. Сценарий «закрыли по одному счётчику» был бы нарушением требований, а не разрешённой приёмкой.

**Предлагаемые изменения.** По этому finding новых критериев не требуется: предложенная конъюнкция уже задана. Наблюдаемость prepare и различие experiment/release уточняются R-04/E0-04/H-01; их нельзя считать подтверждением заявленной подмены. Полезность на смеси агентских сценариев рассматривается E2-04.

**Последствия.** Fresh MSBuild oracle, DTB instrumentation и полный e2e сохраняются. Никаких изменений storage/public API либо разрешения объявлять DTB-only тест достаточным.

## E2-03

**Вывод: ACCEPT.**

**Основание.** Включение политики reuse не означает наличие пригодной записи. Сохранение из непроверенной RAM-сессии нарушило бы O8, но молчаливое включение без объяснения capture status вводит пользователя в заблуждение. Само выражение «после reset может получить hit» корректно условно; проблема в недостаточной наблюдаемости условий.

**Предлагаемые изменения.** Contract §9 и Epoch 2 п.1–2/п.6: раздельно сообщать effective useDiskCache, load source и результат/причину сохранения (`not-attempted: unverified-ram`, written, skipped/failed). Не обещать наличие/валидность записи, если lookup не делался; допустимо `unknown`. Описать существующий forceReload+useDiskCache как способ заново получить проверенный capture.

**Последствия.** Bounded metadata/Description и V23 на false→true RAM-hit, reset и новый PID. Принудительный capture при каждом переключении не требуется; это добавило бы скрытую latency. Изменения ключа или миграции не нужны, persisted DTO должен по-прежнему проходить admission.

## E2-04

**Вывод: PARTIALLY ACCEPT.**

**Основание.** Относительно O5 v2 действительно сужает reuse после правок; его нельзя защищать только словами «безопасный baseline». Но O1 отдельно ставит unchanged restart, где консервативный cache потенциально полезен. Частота правок перед рестартом не измерена, поэтому нулевой hit-rate не установлен. SHA-256 источников — проверка пригодности, а не обязательно часть RequestIdentity; простое исключение её без модели DTB dependencies нарушит O8.

**Предлагаемые изменения.** README «Цель/Порядок работ», Epoch 2 «Задача/Приёмка/Handoff» и verification: явно отразить отклонение от O5, статус промежуточного результата, unchanged/edit/build workloads и hit-rate по всем попыткам. Если O5 обязателен для первого релиза, потребуются отдельное доказательство content-only reuse и изменение этапности до выпуска, не удаление хеша по умолчанию.

**Последствия.** Product scope/acceptance, telemetry, возможные новые cache validity rules и повторная V01–V18 matrix. Изменение текста и membership — разные задачи; 4C не единственный мыслимый путь оптимизации. Окончательное решение о достаточности Epoch 2 — A-01/A-02.

## E2-05

**Вывод: NEEDS CLARIFICATION.**

**Основание.** Review предполагает background capture после возврата load. Epoch 2 п.6 не задаёт этот порядок: capture может завершаться до ответа под manager boundary. Тогда последовательный следующий tool того же агента не пересекается с ним; независимый клиент или внешний writer всё равно может. Idle не доказывает отсутствия внешних изменений и может привести к starvation capture. Частота отказов не измерена.

**Что требуется уточнить.** A-05: foreground или background capture; момент успешного ответа; бюджет, cancellation/reset, допустимое отставание записи и способ измерить долю состоявшихся capture. До решения нельзя уверенно принять обязательный перенос на idle либо утверждение «кэш существует только в тестах».

**Затрагиваемые разделы и последствия.** Epoch 2 п.6, contract §7–§9, handoff metrics и V21/V23. Foreground увеличивает latency ответа; background требует ownership session/generation, shutdown handling и уведомления результата. Safety predicate одинаков для обоих; ни idle, ни отсутствие dirty сами по себе его не доказывают.

## E2-06

**Вывод: PARTIALLY ACCEPT.**

**Основание.** Разделить техническую реализацию store и разрешение публичного hit разумно: это уменьшает риск выпуска бесполезного API до C-01/V12. Но §8 не является излишней отдельной «продуктовой» системой: при нескольких MCP процессах аварийная публикация/cleanup обязаны быть безопасными уже при первом реальном использовании. Epoch 2 формально зависит от Epoch 0/1; незакрытые admission blockers нельзя законно перенести в production под этим условием.

**Предлагаемые изменения.** Epoch 2 «Реализация/Приёмка» и handoff: отдельные контрольные точки store correctness и product activation; public flags только после admission, equivalence и согласованного perf gate. Это может быть несколько изменений внутри эпохи, а не обязательная новая архитектура 2a/2b. Store не начинать ради самого store без feasibility.

**Последствия.** Release coordination, test-only paths, retention/fault tests; public compatibility появляется только при выпуске. Новый формат cache versioned, неизвестный старый payload → miss, без миграции исходников. Нельзя отложить reader protection или corruption fallback за публичный выпуск.
