# Workspace load cache — план v2

Статус: **proposed, не реализовано**. Этот каталог — самостоятельная альтернатива
плану в соседнем каталоге `workspace-load-cache`. Наличие файлов не означает, что исходный план принят,
отменён или что поведение runtime изменилось.

## Цель и критерий корректности

Ускорить первый полезный semantic-запрос после рестарта MCP на больших C#
решениях. Дисковый hit должен восстанавливать ту же семантику, что свежая загрузка
MSBuild при тех же входах. Быстрый `load_workspace`, переносящий всю задержку
в первый semantic-запрос, сам по себе не считается успехом.

Область первой версии намеренно ограничена явно поддерживаемыми проектами.
Для неподдерживаемого проекта или непроверяемой зависимости выполняется обычный
MSBuild load. Нельзя объявлять произвольный MSBuild-проект безопасным для кэша
только потому, что его `.csproj` не изменился.

## Текущее основание

На момент подготовки плана, версия репозитория 1.3.5:

- `SolutionManager` хранит один `MSBuildWorkspace`, RAM-ключ — путь и
  Configuration / Platform / TargetFramework; stale граф пропускает RAM-hit.
- Watcher обновляет сохранённые `.cs`; overflow перечитывает известные документы,
  но не восстанавливает полный состав проекта.
- Собственные записи MCP подавляют watcher-события. Для индекса необходим
  самостоятельный путь уведомления об успешной записи.
- Analyzer shadow-copy overlay существует только в памяти. Его нельзя передавать
  в `MSBuildWorkspace.TryApplyChanges` и сохранять в project-файлы.
- Дискового evaluation-кэша и универсального механизма гидрации нет.

## Порядок работ

| Эпоха | Результат | Зависимость | Статус |
|---|---|---|---|
| [0 — эксперимент](epoch-0-feasibility.md) | Доказательство возможности и границы поддержки | Нет | proposed |
| [1 — жизненный цикл](epoch-1-workspace-lifecycle.md) | Эквивалентная гидрация и безопасные записи, без disk-hit | 0: go | proposed |
| [2 — дисковый кэш](epoch-2-conservative-disk-cache.md) | Консервативный opt-in hit между процессами | 1 | proposed |
| [3 — живая сессия](epoch-3-live-consistency.md) | Индекс, RAM и диск согласуются при изменениях | 2 | proposed |
| [4 — оптимизации](epoch-4-measured-optimizations.md) | Только измеренные ускорения, отдельными изменениями | 3 | optional |

Эпохи 0–3 образуют основной маршрут. Metadata references, частичная загрузка,
Merkle и индекс символов не являются предварительными условиями дискового кэша.
Каждая эпоха завершается решением go / revise / stop и handoff. Stop означает
сохранение обычного MSBuild load, а не реализацию догадок ради продолжения плана.

## Ограничения

- Не читать VS `.vs` / `.dtbcache`, не использовать внутренние Roslyn storage API.
- Не сериализовать `Solution`, `Compilation`, `SyntaxTree`, исходные тексты или
  generated-тексты. Хранить свои DTO и ссылки на проверяемые файлы.
- Не вызывать git/ast для валидации. Не менять `get_changed_files` ради кэша.
- Не реализовывать собственный общий интерпретатор MSBuild.
- Не расширять сканирование на всю монорепу ради удобства.
- Не трактовать неполную загрузку с диагностикой как доказанно полный snapshot.
- Не выключать generators/analyzers для получения красивых результатов замеров.

Этот набор документов не меняет текущую документацию продукта. При будущей
реализации обновление README, AGENTS.md.sample, ARCHITECTURE и версии выполняется
по правилам репозитория, только для реально выпущенного поведения. Добавление
параметров и выбор версии релиза фиксируются в handoff, без обещания patch заранее.
