# Контракты кэша

Статус: **proposed**. Нормативные требования к реализации v2; доступность публичных
API для их выполнения проверяется в Epoch 0. Невыполнимое требование сужает
поддержку или останавливает disk-hit, но не заменяется эвристикой молча.

## 1. Семантическая идентичность

Snapshot описывает **результат design-time build, достаточный для Roslyn**, а не
только MSBuild evaluation. Evaluation и выполнение targets — разные этапы;
последний может добавлять документы и менять compiler inputs.

Сравнение холодного и восстановленного workspace нормализует случайные
ProjectId/DocumentId, порядок перечисления и разрешённые temp shadow-пути.
Пути, assembly identity, options, наборы документов и семантика не нормализуются
так, чтобы скрыть реальные расхождения.

## 2. Идентичность запроса и пригодность записи

`RequestIdentity` включает:

- Нормализованный абсолютный путь `.sln` / `.slnx` / `.csproj`.
- Все реально переданные global properties, включая различие между отсутствием
  значения и явным значением; нормализация — как в существующем API.
- `graphScope` и отсортированный набор абсолютных путей выбранных root-проектов.
  До реализации partial-load набор определяется обычным запросом загрузки.
- Режим metadata references; при его появлении он одинаково учитывается в RAM
  и на диске. Смена семантического режима не должна молча возвращать старый граф.

`CompatibilityFingerprint` включает schema/producer contract version, версии
Roslyn, выбранных SDK/MSBuild, ОС и правил сравнения путей, поддержку языка и
проверяемое окружение загрузки. Изменение отпечатка даёт miss.

Для multi-targeting запись каждого project instance имеет собственный inner TFM
и effective properties. Нельзя присвоить один TFM всем зависимостям механически.
Outer evaluation не гидратируется как обычный проект. Пока корректное сопоставление
instances не доказано, такой запрос не поддерживает disk-hit.

`buildArgs` остаётся сессионной настройкой CLI, если не влияет на DTB. Формат
вывода и логирование не меняют ключ. Overlay хранится как состояние сессии и
повторно применяется к базовой solution; temp-пути никогда не входят в snapshot.

Ключ адресует запись, но **не доказывает её свежесть**: входы проверяются отдельно.

## 3. Состав snapshot

Хранятся versioned DTO с явной схемой:

| Категория | Обязательные сведения |
|---|---|
| Граф | Root-проекты, instances, directed project refs, полнота загрузки |
| Project | Язык, имя/assembly name, file/output paths, effective properties |
| Options | Полные поддерживаемые ParseOptions и CompilationOptions, включая defines, nullable, language version |
| Documents | Все обычные compile documents, пути, folders/link identity, source kind, encoding при необходимости |
| Дополнительные входы | AdditionalDocuments и AnalyzerConfigDocuments, их пути и контекст проекта |
| References | Metadata/project references, aliases, EmbedInteropTypes и другие значимые свойства |
| Analyzers | Исходная identity, путь, проверяемые зависимости loader; без shadow-путей |
| Provenance | Способ получения DTB результата, профиль поддержки, manifests и fingerprints |

Один физический файл может иметь несколько DocumentId в разных проектах/TFM.
Это несколько членств; карта `path -> один DocumentId` недопустима.

Generated compile inputs на диске, включая необходимые файлы из `obj`, сохраняются
как ссылки на существующие проверяемые файлы. Generated editorconfig относится
к обязательным входам. Их отсутствие/изменение даёт miss, а не тихое исключение.
Результат source generators не сериализуется: generators запускаются в новом
workspace, их входы должны быть восстановлены. Непроверяемые внешние зависимости
генератора исключают проект из профиля поддержки.

## 4. Профиль поддержки

Первый профиль — allowlist проверенных сочетаний SDK/targets и возможностей C#
проектов, установленная Epoch 0. Недостаточно проверить только имя SDK.
Неизвестные imports/tasks/targets, непроверяемые property functions, внешние
процессы, сеть, время или неучтённые environment inputs означают `unsupported`.

Для профиля документируются все возможные влияющие входы, включая отсутствие
файлов в условных imports/Exists и создание новых файлов в допустимых wildcard
областях. Список уже разрешённых imports сам по себе недостаточен: новый import
или файл может изменить evaluation при неизменном `.csproj`.

В первой реализации любой неподдерживаемый проект в запрошенном графе отключает
disk-hit **для всего запроса**. Смешивание stale и hydrated проектов отложено.

## 5. Два вида проверки файлов

**Membership scan:** перечисление ограниченных областей, где профиль допускает
появление/удаление compile inputs и других значимых файлов. Области задаются
профилем и DTB provenance; это не автоматически весь каталог монорепы.
Сканирование находит также новые отрицательные зависимости и изменения imports.
Появление/удаление значимого файла в Epoch 2 означает полный miss запроса.

**Explicit dependency probes:** точечная проверка всех известных входов независимо
от ignore-list: `obj/project.assets.json`, NuGet-generated props/targets, configs,
linked sources, external imports, SDK inputs, metadata/analyzer DLL и зависимости.
Путь вне каталога проекта допустим, если зависимость явно известна и проверяема.

Prune ограничивает **рекурсивный обход**, а не отменяет explicit probes.
Игнорирование `obj`/`bin`/`node_modules` не разрешает пропускать явно подключённый
файл. Общая библиотека классификации может обслуживать watcher и scanner, но
политики рекурсии, probes и событий должны быть раздельными.

Linked inputs вне обычных корней проверяются точечно; внешние wildcard области
требуют ограниченного отдельного корня или `unsupported`. Symlink/junction не
проходятся рекурсивно без контроля: циклы исключаются, смена resolved target
инвалидирует запись. Сравнение путей следует платформе, без общего lower-case
для case-sensitive файловых систем.

## 6. Строгость

Epoch 2 хеширует содержимое **всех значимых файлов** при межпроцессной проверке,
включая sources, configs и DLL. SHA-256 из BCL — исходный алгоритм. Size/mtime
помогают обнаруживать нестабильное чтение, но не заменяют content hash.

Перенос проверки на size+mtime возможен лишь в optional Epoch 4 с отдельным
объявленным уровнем доверия; его нельзя называть строго эквивалентным режимом.
Для неизвестного/нечитаемого входа результат — miss, а не «файл не влияет».

## 7. Согласованность поколений

Disk snapshot и активная solution имеют generation. Запись индекса отдельно от
соответствующего DTB snapshot не публикуется как валидная пара.

При capture/hydration:

1. Начать наблюдение за покрываемыми входами, сохранить счётчик событий.
2. Получить проверенные manifests и входные тексты для кандидата.
3. Выполнить DTB/capture либо hydrate; тексты, использованные в кандидате,
   должны соответствовать проверенному поколению, не читаться позже вслепую.
4. Повторно проверить входы и счётчик событий до публикации кандидата.
5. Изменение/overflow/непокрытый источник событий — отвергнуть кандидата.
   Не более одной повторной попытки, затем обычный load без записи cache-hit.

Это optimistic validation, не транзакция файловой системы. Строгий hit требует
стабильных входов на период проверки; если это нельзя установить, hit запрещён.
Документировать остаточные ограничения внешних конкурентных записей, включая
изменение-и-возврат содержимого между проверками. Не обещать атомарный snapshot
произвольно изменяемого дерева без filesystem snapshot/кооперации писателей.

Кандидат строится отдельно и публикуется целиком под workspace lock. При ошибке
нельзя оставлять наполовину заменённый граф. Файловые события во время операции
не теряются: их очередь относится к соответствующему поколению.

## 8. Хранение и несколько процессов

Каталог: `Environment.SpecialFolder.LocalApplicationData/RoslynMcpServer/eval-cache/v2`.
Если ОС не предоставляет подходящий каталог или он недоступен — кэш отключён,
обычный load работает. Папки рядом с решением автоматически не создаются.

- Имена записей — digest нормализованной identity; исходные paths находятся в DTO.
- Каждый writer создаёт уникальное временное поколение в том же cache volume.
- Payload проверяется по схеме, размерным ограничениям и checksum; manifest
  ссылается только на полностью записанное immutable поколение.
- Публикация указателя выполняется атомарно поддерживаемым механизмом платформы,
  под краткой межпроцессной блокировкой ключа. Если гарантия недоступна — miss.
- Readers читают только опубликованные поколения; конфликт writer не блокирует
  workspace load надолго: допустим пропуск сохранения кэша.
- При crash, битом JSON, неизвестной схеме, checksum mismatch или пропавшем payload
  выполняется обычный load. Файлы проекта из кэша никогда не восстанавливаются.
- Cleanup не удаляет активные поколения: нужны reader leases или эквивалентная
  защита. Просроченные leases проверяются с учётом смерти процесса/PID reuse.
- Начальные пределы: 2 GiB на cache root, срок неиспользования 14 дней; cleanup
  best-effort и с ограниченным бюджетом, вне критического пути semantic call.
  Если безопасно освободить место нельзя, новая запись пропускается.

Cache payload — недоверенные данные: только DTO, без произвольной десериализации
типов и выполнения сохранённых команд. DLL загружаются после проверки provenance
текущего проекта; cache-файл сам по себе не разрешает загрузку произвольного пути.

## 9. Публичное поведение

Предложенные параметры Epoch 2:

- `useDiskCache=false` — opt-in чтение/запись межпроцессного кэша; RAM-кэш остаётся.
- `forceReload=false` — при true обходит **RAM и disk**, делает обычный MSBuild
  load; после успеха обновляет запись, если `useDiskCache=true` и профиль допустим.

`reset_workspace` очищает активную RAM-сессию, диск не удаляет. Это явно отражается
в Description. Удаление всего дискового кэша не добавляется в эту эпоху.

Ответ загрузки различает `ram`, `disk`, `msbuild`, сообщает фактические graph scope,
режим metadata references и причину fallback. Не печатать секретные environment
values. Причины: disabled / forced / absent / incompatible / unsupported /
inputs_changed / membership_changed / untrusted / corrupt / hydrate_failed.

Эффективное состояние возвращается даже при RAM-hit. Настройка useDiskCache и
CLI buildArgs обновляется без reopen; новая запись диска при RAM-hit не создаётся
из непроверенного старого provenance.
