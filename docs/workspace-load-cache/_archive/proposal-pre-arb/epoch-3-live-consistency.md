# Epoch 3 — Согласованность живой сессии

Статус: **proposed**. Требует Epoch 2.

## Задача

После внешней синхронизации или собственных записей MCP следующий semantic call
получает проверенное состояние либо явный ответ о невозможности обновления.
Не выдавать старый граф как актуальный. Это отдельное изменение lifecycle,
способное вызвать DTB перед semantic call; стоимость должна быть видна в логах.

## Состояния

| Состояние | Действие перед semantic call |
|---|---|
| trusted | Проверить входы по принятой политике, затем читать solution |
| content-dirty | Обновить тексты всех членств, configs/additional inputs; перепроверить generation |
| graph-dirty | Выполнить обычный load полного текущего scope |
| untrusted | Полная проверка manifests/probes; классифицировать изменения |
| refresh-failed | Ошибка/hint с причиной; не представлять прежний snapshot как свежий |

Для первой строгой реализации watcher — ускоритель классификации, а не
единственное доказательство свежести. Перед semantic call выполнять strict probes
значимых входов и membership scan; объединять параллельные запросы одного refresh.
Снижение этой цены возможно только в Epoch 4 с явно установленной моделью доверия.
Факт `trusted` не разрешает бесконечно пропускать проверки внешних изменений.

## Изменения

- Created/Deleted/Renamed, смена imports/configs/DLL, неизвестный путь и изменение
  членства консервативно дают graph-dirty. Не воспроизводить общий MSBuild glob.
- Content-only sync допускается лишь если профиль доказывает, что содержимое
  этого файла не влияет на DTB. Иначе полный load. Все linked memberships
  обновляются вместе; связанные generators/configs получают новые inputs.
- Overflow, ошибка/отказ запуска watcher, rename/delete директории дают untrusted.
  Обход включает новые и удалённые файлы, не ограничивается known documents.
- Наблюдать корни membership и explicit inputs вне них; родительские configs
  и imports не теряются при загрузке вложенного `.csproj`.
- Успешные собственные записи уведомляют индекс напрямую, даже при подавлении
  watcher. События дедуплицируются; suppress-window не используется для сокрытия
  последующих внешних изменений.
- Refresh и публикация сериализуются с semantic/edit lifecycle. Нельзя держать
  workspace lock и рекурсивно вызывать метод, который снова захватывает его.
- При content sync disk snapshot обновляется только после подтверждения нового
  целостного поколения. Untrusted/stale данные не публикуются как reusable cache.
- Не очищать dirty очередь целиком, если во время flush пришли новые события.
  Cancellation оставляет их для следующего refresh.

Для неподдерживаемого профиля невозможно обещать полную автоматическую свежесть
произвольных внешних входов. Сохранять обычный MSBuild путь и явно обозначать
ограничение; гарантия этой эпохи относится к профилям с полным покрытием входов.

## Приёмка

V07–V09, V19–V23. Сценарии: внешний sync, собственный edit, overflow с новым
файлом, удаление каталога, ancestor props, linked file, повторная запись во время
flush. Новый semantic call видит обновление или явную ошибку refresh.

Отдельно измерить unchanged semantic-call overhead. До выпуска зафиксировать
бюджет по реальной нагрузке; если строгая политика неприемлемо дорогая, сделать
revise, а не тихо заменить её доверием к watcher.
