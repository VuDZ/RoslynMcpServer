# Ответы: Epoch 4

Исходные замечания: [review/epoch-4-measured-optimizations.md](../review/epoch-4-measured-optimizations.md). O/A: [основания](sources-and-scope.md).

## E4-01

**Вывод: REJECT.**

**Основание.** Вывод о запрете любой ограниченной модели не следует из запрета собственного **общего** интерпретатора. O5 из первоначального плана прямо предусматривает reuse состава по glob; v2 предлагает ограничить его распознаваемым профилем. Closed subset с корректным отказом на custom Compile вне него не обязан поддерживать произвольный MSBuild. Это не доказательство реализуемости конкретного профиля, но опровергает тезис, что любой такой эксперимент уже нарушает запрет. «4C — единственный способ полезного hit-rate» также не установлено: есть unchanged restart O1, а обновление contents существующих documents не равнозначно изменению membership.

**Предлагаемые изменения.** Не снимать запрет общего интерпретатора и не удалять 4C на основании этого finding. Существующие prerequisite «доказанный профиль» и unknown→load требуют реального evidence по C-01, не allowlist имени SDK. Отклонение этапности от O5 должно решаться A-01, а не объявляться оправданным этим REJECT.

**Последствия.** Нет обязательного нового API или миграции. Если 4C будет реализовываться, новая модель профиля/инвалидации проходит полную equivalence matrix и отдельную приёмку. Если распознавание закрытости не удаётся, профиль не допускается независимо от этого вердикта.

## E4-02

**Вывод: PARTIALLY ACCEPT.**

**Основание.** Пользователь должен отличать strict/stat/watcher evidence; потерянные события и stat collisions не эквивалентны strict. Но v2 §6 и 4B уже прямо запрещают тихую замену, поэтому finding обнаруживает прежде всего пробел public representation. Отдельная disk schema не обязательна логически: валидный payload может быть проверен более строгим reader заново. Однако результат слабой проверки нельзя переиспользовать как доказательство сильной.

**Предлагаемые изменения.** 4B, contract §6/§7/§9: явный effective validation mode и границы свежести в load/semantic ответах; compatibility правила producer evidence → reader policy. Не смешивать semantic admission с freshness. Если данных для strict не хватает, miss. V10/V16/V19–V23 выполняются по отдельным ожидаемым гарантиям, без зелёного V10 в stat режиме по чужому strict прогону.

**Последствия.** Response metadata, producer version/admission fields, negative tests на переход non-strict→strict. Новый namespace/schema нужен при несовместимой форме evidence, а не автоматически при каждом runtime mode. Выбор допустимой live policy зависит от A-03; default не меняется молча.

## E4-03

**Вывод: PARTIALLY ACCEPT.**

**Основание.** Неполный поиск не может изображать полный; это O7/O8. Но разные keys по scope необходимы для корректности, а стоимость expand — допустимый trade-off явно частичного режима. O7 рассматривает metadata/partial как самостоятельное ускорение, поэтому требование запретить их до доказанного full disk-hit не выводится из исходных целей. V2 уже располагает 4A после основного маршрута. Неполный read-only список с понятным scope не обязательно ошибочен; требование отказа относится к операциям, для которых полнота необходима.

**Предлагаемые изменения.** 4A и V24/V25: инвентарь semantic tools — допустимый partial result с explicit scope либо отказ/запрос полного scope. Refactoring, которому нужен полный граф, не выполняется по одному hint. Смена scope не выдаёт прежний RAM snapshot. Полезность измерять отдельно для локальной работы и частых expand, не переносить один результат на другой.

**Последствия.** Query/refactoring response contract, roots в cache identities, отдельная доступность test discovery и compatibility клиентов. Автодогрузка/новый tool не требуются автоматически. Порядок независимых направлений O7 — A-01, не причина скрывать неполноту.

## E4-04

**Вывод: ACCEPT.**

**Основание.** [ARCHITECTURE](../../../ARCHITECTURE.md), «Build, test, run, and NuGet» различает syntax discovery по загруженным проектам и CLI по выбранному файлу. O7 требует не сужать CLI неявно. Проверить только успешный CLI exit недостаточно: get_test_list может дать неполный список при успешной полной сборке.

**Предлагаемые изменения.** 4A и V24/V25: явно определить scope get_test_list, requested roots, неполноту относительно solution и фильтры projectName. При partial graph ответ сообщает coverage; CLI использует явно запрошенную цель/сохранённый workspace path, не принудительно всегда один sln вопреки явному аргументу. Binary resolution не должен выбирать первый отсутствующий/неоднозначный проект.

**Последствия.** Bounded discovery metadata/help, tests discovery-vs-CLI при partial/metadata scope и фильтрах. Нельзя обещать VSTest completeness даже на полном source graph: текущий get_test_list — syntax scan. Миграция cache не нужна; public semantics раскрываются до выпуска 4A.
