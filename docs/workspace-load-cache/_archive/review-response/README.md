# Ответы на review: общие замечания

Это независимая оценка 50 замечаний, а не утверждение v2. [Основания и требования](sources-and-scope.md), [сводка и арбитраж](summary.md). Файлы ответов повторяют имена файлов review. Исходные планы, review и код не изменяются.

## R-01

**Вывод: PARTIALLY ACCEPT.**

**Основание.** O6 уже рассматривает Adhoc/ProjectInfo; требование эквивалентной семантики не равнозначно требованию того же типа host. Но A-WRITE и V07 требуют корректного persistence, которого одна гидрация ProjectInfo не обеспечивает. Adhoc сам не сохраняет изменения на диск ([API](https://learn.microsoft.com/en-us/dotnet/api/microsoft.codeanalysis.adhocworkspace?view=roslyn-dotnet-4.13.0)). Невыбранный host и граница записи — реальный незакрытый вопрос. Трилемма review неполна: отдельный persistence adapter или reload перед определёнными мутациями возможны как исследуемые варианты. Их совместимость и стоимость не доказаны. Пример `rename_project` неверен: [ProjectTools.cs:53](../../../../Tools/ProjectTools.cs:53) вызывает файловый helper, а не TryApplyChanges.

**Предлагаемые изменения.** Epoch 0 «Работа/Приёмка»: решение о host и карта операций read/text edit/add-remove document/project mutation с владельцем записи. Epoch 1 «Задача/Приёмка», contract §1/§3: отдельно определить семантическую и операционную эквивалентность. Не снимать V07 ради зелёной гидрации; вариант read-only или reload-on-write требует явного согласования ограничения.

**Последствия.** Внутренние loader/session/persistence API, capabilities host, fault tests и latency записи. Публичные инструменты не должны терять операции молча. Не вводить custom writer или внутренние Roslyn API без отдельного решения. Связанные более широкие риски: N2, N6 в summary.

## R-02

**Вывод: PARTIALLY ACCEPT.**

**Основание.** O2/O8 запрещают ложный hit: принятые Documents/imports не покрывают ранее отсутствовавшие входы. C-01 действительно блокирует admission до доказательства профиля. Но запрет v2 касается собственного **общего** интерпретатора, а не любого вызова MSBuild или ограниченной проверенной модели. Кроме того, A-PROVENANCE и [OpenAndCaptureAsync](../../../../Services/AnalyzerProvenanceCaptureService.cs:181) уже используют binlog. Полнота произвольных отрицательных зависимостей этим каналом не доказана; нельзя объявлять её обеспеченной одним включением logger. V2 не обещает произвольные проекты, однако сужение относительно O5 нельзя считать согласованным автоматически.

**Предлагаемые изменения.** Contract §3–§5 и Epoch 0 п.4–5: конкретный источник positive/negative/target dependencies, алгоритм отказа до hit, версия распознавателя и контрпримеры. Проверять пригодность существующего capture, не предполагать отсутствие канала. Если рассматривается evaluation-only, отдельно определить её стоимость и непокрытые target inputs; запрет полного собственного интерпретатора оставить.

**Последствия.** DTO provenance, admission, runtime-version matrix, V12/V13 и измерения. Новые логируемые properties затрагивают секреты и retention. Перенос session provenance — отдельный N2, доверие cache — N3. Наличие binlog не закрывает ни один из этих рисков само по себе.

## R-03

**Вывод: ACCEPT.**

**Основание.** Текущий `LoadCoreAsync`, A-LOAD/A-WRITE/A-ADMISSION существенно отличаются от 1.3.5. Перенос старых допущений способен вернуть уже устранённые raw publication и stale-write ошибки. В исходниках сейчас 1.3.21; runtime 1.3.20 из review не следует копировать как версию будущего исполнителя.

**Предлагаемые изменения.** V2 README «Текущее основание», Epoch 0 п.1, Epoch 1 lifecycle/write audit, Epoch 3 refresh: привязка к commit и принятому набору U-ARB-04/05, v3 S2–S5. При отдельной будущей правке ARCHITECTURE «Runtime composition/Workspace lifecycle» обозначить v1 и v2 как альтернативные планы до выбора, не объявлять v1 отменённым.

**Последствия.** Регрессионная матрица должна включать новые baseline guarantees. Source version и running binary version фиксируются отдельно. Сейчас изменения runtime, версии, схемы хранения и product docs не требуются.

## R-04

**Вывод: PARTIALLY ACCEPT.**

**Основание.** Точка capture и готовность semantic результата действительно недоопределены. A-LOAD требует prepare/gate до публикации, A-PROVENANCE требует same-session evidence. Но отсутствие флага после рестарта по A-STICKY означает честный no-overlay и при обычном MSBuild load: нельзя считать это само по себе нарушением эквивалентности кэша или автоматически включать overlay. Сравнение должно использовать одинаковый запрошенный и эффективный режим.

**Предлагаемые изменения.** Contract §2/§3/§7/§9: capture от явно определённой базы без temp paths; session state и готовность overlay отдельно от происхождения графа; disk source не означает semantic-ready. Epoch 1 и Epoch 2: hydrate → восстановление допустимого provenance → optional prepare/gate → publication в A-LOAD. Verification «Измерения»: prepare входит в e2e.

**Последствия.** DTO нужен переносимый доказательный контекст, не сериализация старых ProjectId/sessionId. Ответы load различают graph source, capture/prepare status и semantic availability. Матрица true/false/omitted/reset/restart; совместимость sticky сохраняется. Обязательность overlay в ключе базового DTO не доказана; общий DTO допустим только при доказанном разделении базы и session policy (N2).

## R-05

**Вывод: NEEDS CLARIFICATION.**

**Основание.** O1 прямо включает ускорение на неизменном дереве; из miss после edit не следует бесполезность этого сценария. O5 одновременно обещает reuse после изменения источников, а O4 требует live freshness. Следовательно, и утверждение review о невозможности полезного Epoch 2, и мой прежний совет просто исключить Epoch 3 недостаточно обоснованы. Реальная частота edit/build/restart и допустимость поэтапного сужения требований неизвестны.

**Что требуется уточнить.** A-01/A-02: является ли Epoch 2 самостоятельным промежуточным выпуском для unchanged restart; обязательно ли O5 для первого полезного релиза; когда должен быть закрыт O4. До решения нельзя ни считать 0–2 завершением всей задачи, ни объявлять обязательную live freshness optional.

**Затрагиваемые разделы и последствия.** README «Цель/Порядок работ», Epoch 2 «Задача/Приёмка», Epoch 3 статус и verification workloads. Меняются границы релиза и performance gates, потенциально refresh APIs; корректность hit не ослабляется. Нужны отдельные метрики unchanged/edit/build/restart и hot path. Более широкий риск — несанкционированная смена требований N1.

## R-06

**Вывод: NEEDS CLARIFICATION.**

**Основание.** O6 требует inner TFM и запрета outer capture, но не устанавливает поддержку всех сочетаний multi-targeting в первой версии. Размер решения не доказывает наличие нескольких TFM. В то же время доказательство на двух проектах не подтверждает полезность на целевой монорепе. Если её admission всегда unsupported, заявленная для неё цель не достигнута.

**Что требуется уточнить.** A-02: назвать целевое решение, его properties, обязательные TFM/ProjectReference contexts и минимальное покрытие первого релиза. Без этого нельзя уверенно принять ни обязательность универсального mapping уже в Epoch 0, ни достаточность одно-TFM fixture.

**Затрагиваемые разделы и последствия.** Epoch 0 п.1/п.5/«Приёмка», contract §2/§4, V03 и release gate должны ссылаться на выбранную нагрузку. При обязательном multi-targeting потребуются устойчивые project-instance identities, exact edge mapping, cross-process tests и версии профиля/DTO; иначе ограничение должно быть официально отражено в цели, без обещания поддержки целевого неподдержанного решения.
