# Эпоха 2 — Неизменяемые поколения и mapping

Статус: **принято** (файлы/mapping; CLR execution — эпоха 3). Зависимость: [эпоха 1](epoch-1-lifecycle-verification.md).
Приёмка: [epoch-2-acceptance.md](epoch-2-acceptance.md). Открыт A2-09 (stores).
Контракт mapping этого этапа обязателен для эпохи 4; файловая идентичность не
закрывает CLR binding gate эпохи 3.

## E2-S1. Модель и границы подготовки

Подготовка файлов отделена от преобразования `Solution`. Результат — неизменяемое
отображение с load/session identity, `ProjectId`, исходной analyzer reference,
shadow reference, generation ID и результатом подготовки каждой ссылки. Неуспешная
запись результата не содержит пригодной shadow reference. Mapping хранится в памяти;
project IDs другой сессии не подставляются автоматически.

Раздельно хранить requested mode, prepared mapping, активные поколения, результат
последней попытки refresh и наблюдаемое исполнение. Частичная подготовка отражается
по ссылкам, а не одним enabled bool. Mapping связан с базой операции эпохи 4;
старый mapping не отбрасывается, пока он нужен допустимой незавершённой операции.
Это не реестр произвольной истории `Solution`.

Подготовка разрешена при load/включении и явно определённой попытке artifact refresh
или reopen. При повторном load с `true` запрос подготовки сохраняется как существующая
точка; поддержанность свежего исполнения определяется U-ARB-02, а не cache hit.
Необслуживаемая попытка обновления должна явно отклоняться согласно эпохе 3.
Любая операция, обещающая refresh, перечитывает и хеширует обязательные байты
независимо от cache hit графа, timestamp и размера. Повторный `false`/omitted
на cached load сам не создаёт refresh и не выключает overlay: это принято как
session-sticky контракт U-ARB-05 в v1.3.13.

Document edit, watcher flush, reconciliation, post-apply publication и чтение
снимка используют готовый mapping без копирования, хеширования или чтения файлов
анализатора. Это ограничение относится к overlay reapply; текстовый disk sync
продолжает читать документы, а lazy compilation — загружать assemblies по эпохе 3.

## E2-S2. Идентичность и совместимость layout

Первый поддержанный набор обязательных файлов — только основная analyzer DLL
(политика main-only). Generation ID определяется версией формата/политики и
упорядоченным набором нормализованных относительных путей с хешами содержимого.
Одинаковый набор в той же политике переиспользует путь; изменённые обязательные
байты дают другой идентификатор даже при прежних timestamp и размере.

PDB необязателен: отсутствие или ошибка его копирования не отменяет пригодность
main DLL. Его можно включить только до публикации. Опубликованный каталог не
дополняется ради PDB; необязательный PDB не превращается в обязательный helper.

Будущая dependency-set политика эпохи 3 имеет отдельный versioned namespace/layout
и учитывает весь утверждённый обязательный набор. Нельзя считать main-only поколение
dependency-complete, дополнять его helpers или переиспользовать вместо dependency-set.
Проверка helper-only invalidation принадлежит эпохе 3.

Старые timestamp-каталоги без пригодного manifest не считаются готовыми поколениями
v2. Они не мигрируются перезаписью или дополнением; применяется новый namespace.
Автоматическая очистка старого layout и исторической порчи проектов не добавляется.

## E2-S3. Протокол публикации и проверки

1. Определить обязательный набор политики и создать уникальный собственный staging
   рядом с будущим каталогом поколения на том же томе.
2. Прочитать/скопировать обязательные байты, вычислить хеши подготовленных файлов.
   Обнаруживать смену источников контрольной проверкой; при нестабильности —
   ограниченный retry либо диагностируемая ошибка. Дождаться завершения всех записей
   и закрыть файлы, включая успешно добавленный необязательный PDB.
3. Последним записать и закрыть manifest: версия формата/политики, обязательные
   относительные пути, хеши, диагностическое происхождение. Абсолютный source path
   в диагностике не заменяет content validation.
4. Выполнить один move каталога в пределах тома без замены destination. При гонке
   использовать уже опубликованный результат только после полной проверки ниже.
   Ошибка move остаётся явной ошибкой; не обходить её overwrite.
5. Перед reuse проверить версию/политику, точный обязательный набор, допустимость
   относительных путей, containment и хеши всех обязательных файлов. Сопоставить
   результат с ожидаемой content identity, а не доверять одному полю manifest.
6. Только после успешной публикации/проверенного reuse создавать shadow
   `AnalyzerFileReference` и готовую запись mapping.

Существующий каталог без manifest, с неверной версией, набором или повреждёнными
байтами непригоден. Его не удаляют и не перезаписывают в рамках публикации.
Ссылки на staging или частично готовые файлы не публикуются.

Manifest — недоверенные данные cache: до чтения файлов и cleanup отклонять
абсолютные пути, traversal и resolved paths за пределами generation root, в том
числе выход через перенаправление пути. Хеши не являются аутентификацией каталога,
если посторонний может изменить и manifest, и данные; reuse предполагает локально
контролируемый root с проверенным владением. Новый sandbox генераторов не вводится.

Протокол обеспечивает логическую готовность поколения; не обещает устойчивую к
потере питания файловую транзакцию. Контроль отдельных файлов не доказывает
согласованность всей параллельной MSBuild-сборки. Поддерживаемый порядок — завершить
успешный build, затем запросить поддержанный refresh; конкурентный build даёт
диагностируемый результат без обещания транзакционного снимка output.

## E2-S4. Ошибки, владение и ресурсы

На первой подготовке при неудаче оставить исходную ссылку и сообщить причину;
это не успех генерации и не подтверждение anti-lock. При частичном результате
явно перечислить подготовленные/неподготовленные ссылки во внутреннем результате.
Ранее активный совместимый mapping допустимо сохранить после failed refresh
только с явным stale-generation результатом. Нельзя сообщить успешное обновление,
сбросить mapping на broken originals или перенести его в другую load session.
Обычный успешный edit не является попыткой refresh и не стирает последний его отказ.
Известно неподдержанное исполнение новой версии обрабатывается gate эпохи 3;
stale result подготовки не разрешает выдавать заведомо неверную семантику.

Сохраняется общий per-solution root, доступный нескольким владеющим процессам.
Уникальный staging принадлежит создавшему его участнику; опубликованные поколения
разделяются всеми участниками root. Во время работы разрешено удалять только свой
незавершённый staging после проверки абсолютного пути и владения. Ни
`ClearWorkspaceAsync`, ни dispose workspace не удаляют опубликованные поколения:
loader и старые compilation могут продолжать их использовать.

До приёмки измерить bytes каждого поколения, суммарный размер root и рост на серии
build/refresh, отдельно одинаковое и изменённое содержимое. Операционный бюджет
фиксируется по этим измерениям для поддержанной матрицы: существующие поколения
плюс ожидаемые новые уникальные поколения до плановой остановки и место под staging.
Универсальный численный лимит арбитражом не задан и здесь не выдумывается. Документ
приёмки должен содержать измеренные значения, выбранный бюджет и интервал плановой
проверки/очистки, а не обещание неограниченного хранения.

Disk-full при копировании, manifest или move — failed refresh с причиной и
generation/project correlation; partial staging не активируется. Старый mapping
сохраняется только по правилу stale выше. Автоматический GC не добавляется.

Поддержанный операторский cleanup: определить конкретный root и его владельцев;
остановить все использующие его серверные процессы и зависимые операции; проверить
resolved absolute target, containment и право владения; удалить только выбранный
cache root/поколения; при следующем opt-in load подготовить их заново из завершённого
build. Если остановка всех владельцев не подтверждена, опубликованные файлы не
удалять. Один reset или исчезнувший PID сами по себе не доказывают безопасность.

## E2-S5. Приёмка

- Повторный refresh загруженной DLL валидирует/reuses поколение без overwrite;
  несколько Consumer получают пригодные ссылки на один результат.
- Изменённые байты при том же размере и timestamp дают новую content identity на
  каждой обещающей refresh операции, включая cached graph.
- Два изолированных процесса используют один test-owned root: гонка публикации,
  прекращение одного publisher, успешная проверка/reuse выжившим. Тест потоков
  не заменяет межпроцессный.
- Interrupted staging, missing/corrupt manifest, corrupt required file, неверная
  политика/набор, unsafe path, конкурирующий publisher, move failure и disk-full
  не дают ссылки на непригодный каталог и не изменяют существующий destination.
- Изменение источника во время подготовки обнаруживается; PDB failure не ломает
  main-only пригодность и не приводит к дополнению опубликованного поколения.
- Edit, watcher flush, reconciliation и post-apply сохраняют mapping/маркер при
  нуле analyzer file I/O в reapply, включая недоступный исходный output.
- Сохранены измерения роста, бюджет, ownership и проверенная процедура cleanup.

Полноценная приёмка трёх путей записи и inverse mapping завершается в эпохе 4;
выполнение файловых тестов не объявляет поддержку helpers или свежего CLR исполнения.
