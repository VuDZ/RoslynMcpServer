# Эпоха 3 — Контракт загрузчика и зависимости

Статус: **планируется; выбор реализации зависит от эксперимента**.
Зависимости: эпохи 1–2.

## Проблема

Новый файловый путь сам по себе не доказывает, что в том же процессе будет
исполняться новая сборка. Текущий минимальный загрузчик использует
`Assembly.LoadFrom`, а shadow copy переносит только основную DLL и PDB.
Поддержка приватных зависимостей и изоляция разных версий не установлены
историческим repro.

## Требуемый контракт

Целевой сценарий: после успешной сборки и явного полного reload workspace
в том же процессе сервер исполняет новую версию генератора и его приватных
зависимостей. Автоматическое подхватывание незавершённой сборки не требуется.

Перед реализацией экспериментально проверить:

- Замена тела генератора без изменения assembly name/version: `V1` → `V2`.
- Изменение только helper DLL при неизменной основной DLL.
- Одновременная работа двух генераторов с конфликтующими версиями helper DLL.
- Поведение при отсутствующей или несовместимой зависимости.

Проверять исполняемый результат, а не только путь в `AnalyzerFileReference`.

## Решение по результатам

Зафиксировать отдельный design decision в этом документе: какие случаи
подтверждены текущим загрузчиком и нужна ли изоляция контекстов загрузки.
Кандидат — отдельный `AssemblyLoadContext` для поколения генератора с явной
политикой разделяемых контрактных сборок. Это направление исследования,
а не утверждённая без проверки реализация.

При изоляции необходимо сохранить совместимую идентичность типов Roslyn
между сервером и генератором. Нельзя без разбора загружать отдельные копии
контрактных сборок в каждый контекст. Политику разрешения framework/Roslyn
сборок и приватных зависимостей записать явно.

Если надёжное обновление в процессе не реализовано, допустим промежуточный
релиз с документированным требованием перезапуска и диагностикой устаревшего
поколения. Это не считается выполнением целевого контракта: оставшаяся часть
эпохи сохраняет статус deferred, а не complete.

## Подготовка зависимостей

- Определить поддерживаемый способ обнаружения приватных runtime DLL:
  build metadata, manifest или иной проверенный механизм. Не считать весь
  output-каталог корректным набором зависимостей без анализа.
- Переносить согласованный набор в поколение из эпохи 2 и включать обязательные
  зависимости в идентификатор содержимого.
- Не разрешать приватную зависимость из произвольного каталога другого
  генератора только по simple name.
- Не загружать приватные DLL из реального build output как fallback:
  это возвращает риск блокировки исходных файлов.
- При ошибке указывать генератор, поколение и отсутствующую/конфликтующую
  зависимость. Успех подготовки файлов не равен успеху загрузки генератора.

## Ресурсы и приёмка

Описать владельца загрузчика, время жизни контекстов и снятие глобальных
обработчиков при освобождении. Не обещать немедленную выгрузку: старые
`Solution`/compilation могут удерживать сборки. Измерить поведение серии reload
и зафиксировать ограничения памяти и диска.

Эпоха завершена, когда целевые проверки выше проходят, реальный build output
генератора и helper DLL доступен для принудительной пересборки, а документация
описывает ровно подтверждённый контракт. Нативные зависимости и отдельный
процесс исполнения генераторов остаются вне этой эпохи, если эксперимент
не покажет необходимость отдельной спецификации.
