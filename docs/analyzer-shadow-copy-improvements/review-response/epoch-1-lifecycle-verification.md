# Ответ: эпоха 1

Источники: [review](../review/epoch-1-lifecycle-verification.md),
[спецификация](../epoch-1-lifecycle-verification.md).
Обозначения U/H1/H2/H3/A/C/F/L/W/T раскрыты в [README ответа](README.md).

## E1-01 — ACCEPT

**Основание.** «Значение символа либо generated document» не задаёт исполняемый
test harness. Но отсутствие MCP инструмента не препятствует in-process проверке:
T и csproj допускают тестировать `SolutionManager` напрямую. U не требует
black-box-only тестирования; запрет нового public SG search из H3 не относится
к тестовому oracle.

**Изменение.** «Сценарий», «Воспроизводимость»: тестовый процесс с MSBuild
bootstrap получает один overlay `Project`, вызывает `GetCompilationAsync`,
находит известный generated type и читает `IFieldSymbol.ConstantValue` маркера.
Отсутствие типа/константы — fail; generated text можно сохранять как evidence.
Диагностика не является oracle версии. Harness проходит production lifecycle,
а не сам запускает отдельный GeneratorDriver вместо проверяемого loader.

**Последствия.** Тестовая инфраструктура, SDK/bootstrap и процессная изоляция;
новый public MCP API не нужен. Доступность конкретного oracle проверяется
компиляцией harness на закреплённом Roslyn до использования baseline.

## E1-02 — ACCEPT

**Основание.** C `LoadCoreAsync` возвращает RAM hit; W затем отдельно вызывает
copier при `true`. `ClearWorkspaceAsync` не сбрасывает L. Слово reload скрывает
три разные операции и делает результат эпохи 3 неоднозначным.

**Изменение.** «Сценарий» шаг 7: основной случай — `reset_workspace` плюс
`load_workspace(..., shadowCopyInSolutionAnalyzers: true)` в том же процессе.
Отдельно измерять same-key cache-hit load и новый процесс. Записывать свойства
загрузки, факт cache hit/reopen и смену процесса. Этот словарь перенести в
README и эпохи 2, 3, 6.

**Последствия.** Тестовая матрица и пользовательские инструкции. Нового
`forceReload` параметра не требуется; семантика обновления на RAM hit остаётся
отдельным решением, не выводится из названия операции.

## E1-03 — ACCEPT

**Основание.** Сброс полей overlay в C не очищает singleton loader. Проверка
только флагов пропускает исполнение чужой сборки. Точный эффект identity
коллизии пока не воспроизведён; review корректно задаёт сценарий риска.

**Изменение.** «Сценарий» шаг 8: solutions A/B с одинаковой assembly identity,
разными маркерами, реальным корректным analyzer path в B при выключенном флаге.
Проверять маркер B и пути/identity реально загруженных сборок, не только bool.
Вариант broken path + flag off должен ожидать отсутствие генерации, а не B.

**Последствия.** Изоляционные тесты и границы контракта L в эпохе 3;
reset workspace не документируется как unload CLR. Возможная необходимость
перезапуска — compatibility ограничение, не уже установленный дефект.

## E1-04 — ACCEPT

**Основание.** C cache-hit и W `if (shadowCopyInSolutionAnalyzers)` подтверждают:
same-path `false` не снимает ранее применённый overlay. Исходный opt-in не
определяет однозначно, означает ли default false «выключить» или «не включать
заново», поэтому нельзя молча выбрать desired-state semantics.

**Изменение.** Добавить true→false, true→omitted, false→true для того же ключа
и для reset+load. В эпохе 6 описать нынешнюю липкость и предложить решение
по семантике флага отдельно; значение по умолчанию в bool API не позволяет
отличить false от пропущенного аргумента внутри метода.

**Последствия.** Возможная смена поведения повторных вызовов и release notes;
при sticky контракте инструкция отключения через reset. Не объявлять
автоматическое выключение уже согласованным требованием U.

## E1-05 — ACCEPT

**Основание.** H1 Consumer использовал generated member. В новом тестовом
сценарии это не сформулировано обязательно. Пустые diagnostics не доказывают
даже запуск, не говоря о версии.

**Изменение.** «Сценарий»: Consumer обязательно обращается к маркеру; oracle
из E1-01 проверяет точное `V1`/`V2`. Между V1/V2 Consumer не меняется — так
изолируется изменение генератора. Негативный контроль с недоступным генератором
должен уронить oracle, даже если diagnostic list оказался пуст.

**Последствия.** Содержимое генерируемого fixture и assertions; production
diagnostics API не меняется. E1-01 задаёт механизм, E1-05 — обязательную
зависимость Consumer и контроль ложноположительного результата.

## E1-06 — PARTIALLY ACCEPT

**Основание.** Три пути действительно различаются в C. Однако исходный шаг 5
уже отдельно требует rename/overlay apply, а шаг 3 — edit и watcher; утверждение,
что спецификация разрешает заменить всё одним text edit, преувеличено.

**Изменение.** «Сценарий», «Критерии завершения»: дать три именованных subcase:
`UpdateDocumentInMemoryAsync`, `ApplySolutionChangesToDiskAsync` от overlay,
FSW→flush. Для каждого — точный маркер, новый текст и `.csproj` bytes;
fallback overlay apply описать отдельно по E4-04.

**Последствия.** Трассируемость тестов к call sites, без расширения MCP API.
Приёмка не может закрываться только чистой сборкой после одного выбранного
редактирования. Связанные обязанности распределены между эпохами 2 и 4.

## E1-07 — ACCEPT

**Основание.** H1 прямо включает existing correct output; fixture с отсутствующим
исходным путём не проверяет весь anti-lock контракт. Но сам факт
`TryApplyChanges` не доказывает, что Roslyn загрузил analyzer: это требует
наблюдения, а не превращения сценария review в подтверждённый MSB3027.

**Изменение.** Два обязательных fixture: missing resolved path и existing correct
resolved path. Forced rebuild после каждого из трёх write paths, с проверкой
новых байтов output и исполнения генератора перед сборкой; фиксировать
фактические пути загрузок. Тот же gate привязать к эпохам 3/4.

**Последствия.** Расширяется интеграционная матрица, а не исходная задача.
Если обнаружена загрузка из raw workspace, это отдельная граница чтения/загрузки
(N-04), которую один strip helper не исправит.

## E1-08 — ACCEPT

**Основание.** C watcher накапливает dirty paths; getter сам их не применяет.
Ожидать новый текст только через `GetCurrentSolution()` — неверный тест.

**Изменение.** «Воспроизводимость»: отдельно подтвердить доставку dirty event
ограниченным ожиданием, затем вызвать production flush через `FindDocumentAsync`
или `GetCurrentSolutionAfterDiskSyncAsync`, затем проверить текст и маркер.
Для детерминированного теста flush можно подавать dirty input через внутренний
test seam; такой тест не подменяет отдельную проверку реального FSW.

**Последствия.** Test harness и сообщения timeout различают event delivery,
flush и публикацию. Не вводится обещание фонового применения изменений или
глобальной синхронности с диском. Замечание о rename уточнено в R-02.

## E1-09 — ACCEPT

**Основание.** F при copy failure оставляет исходную ссылку, C reoverlay
выбрасывает `RewriteResult`. Это кодовый путь потери overlay без полезного
сообщения; воспроизведение именно lock на этой машине ещё не выполнено.

**Изменение.** «Сценарий», «Критерии завершения»: отдельный regression case
«loaded shadow → edit → reoverlay» с принудительной ошибкой подготовки и
реальным baseline после загрузки DLL. Эпоха 2 должна убрать prepare с edit;
до этого результаты reoverlay должны быть наблюдаемы и не теряться.

**Последствия.** Диагностика preparation/reapply и assertions на сохранение
маркерa/ссылок. Эпоха 1 по-прежнему может закончиться измеренным fail;
исправление не становится условием закрытия исследовательского baseline.

## E1-10 — PARTIALLY ACCEPT

**Основание.** Несколько Consumer нужно сделать обязательным случаем 1/2.
Но спецификация относит к эпохе 3 только последние два пункта списка — helpers
и version conflict. F обрабатывает Consumer последовательно; вызов копирования
сам по себе не запускает lazy load. Поэтому «lock уже на первом load» —
возможный interleaving, а не установленное следствие двух Consumer.

**Изменение.** «Дополнительные случаи»: several-Consumer в основной матрице
1/2; helper cases разделяют prepare/load/execute failure. Без oracle нельзя
делать вывод о версии. Измерять красный helper baseline до эпохи 2 допустимо,
если он не выдаётся за чистый binding experiment.

**Последствия.** Точная принадлежность failures; ALC не выбирается для
исправления файловой гонки. Безусловный запрет ранних helper экспериментов
не нужен и противоречил бы назначению baseline.
