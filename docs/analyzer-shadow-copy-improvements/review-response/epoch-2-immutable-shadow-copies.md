# Ответ: эпоха 2

Источники: [review](../review/epoch-2-immutable-shadow-copies.md),
[спецификация](../epoch-2-immutable-shadow-copies.md).
Обозначения источников — в [README ответа](README.md).

## E2-01 — PARTIALLY ACCEPT

**Основание.** Текст уже говорит «после эпохи 3», поэтому одновременное требование
helper discovery в эпохе 2 из него не следует. Но критерий hash domain и переход
от main-only к dependency-set недостаточно точен; reusable manifest не должен
выглядеть полным после расширения набора.

**Изменение.** «Требования», «Предлагаемый алгоритм»: эпоха 2 принимает список
подготовки, первая поддержанная политика — main-only. Идентификатор учитывает
версию формата/политику и упорядоченный набор относительных путей с хешами.
Helper-only acceptance принадлежит эпохе 3; новый dependency-set не переиспользует
main-only поколение как полный набор.

**Последствия.** Manifest schema и invalidation локального cache layout,
контракт между discovery и prepare. Старые каталоги не мигрируются на месте
и не дополняются; новый namespace избегает ложного reuse.

## E2-02 — ACCEPT

**Основание.** Уточнение reload по E1-02 обязательно: cached MSBuild graph не
доказывает неизменность build output. F ticks не являются content identity.
Оптимизация, которая пропускает hash на обещанном refresh, нарушит даже
уже заявленный тест изменённых байтов с тем же timestamp.

**Изменение.** «Ошибки и границы», «Критерии приёмки»: каждый путь, обещающий
проверку нового output, перечитывает/хеширует обязательные байты; cache hit
workspace не освобождает от проверки. Edit/watcher используют mapping и не
запускают hash вообще. Для same-key load определить refresh semantics в матрице,
а не считать его автоматически refresh или автоматически no-op.

**Последствия.** Стоимость load, тест same-size/same-timestamp mutation,
раздельные состояния graph cache и artifact generation. Нового MCP параметра
пока не требуется.

## E2-03 — ACCEPT

**Основание.** «Сформировать manifest» недостаточно точно для fail-safe публикации.
Нужен проверяемый readiness marker до выдачи ссылки. Существование каталога
не доказывает его пригодность. При этом гипотеза review о наблюдаемом «mid-move»
не является доказанным поведением данного filesystem.

**Изменение.** «Предлагаемый алгоритм»: полностью записать и закрыть файлы,
manifest записать последним в staging, затем один same-volume move без replace.
Reuse только после проверки формата, набора путей и хешей файлов. Каталог без
валидного manifest — отказ, не overwrite/delete чужого каталога; ошибка move
диагностируется, retries ограничены. Добавить interruption/corrupt-destination tests.

**Последствия.** Новый persistence protocol, совместимость layout, error codes.
Это логическая публикация, не гарантия crash durability при потере питания:
`Directory.Move` не документирует такую транзакцию.
[Microsoft: Directory.Move](https://learn.microsoft.com/en-us/dotnet/api/system.io.directory.move?view=net-10.0).
Отдельный вопрос безопасности путей manifest — N-05.

## E2-04 — ACCEPT

**Основание.** U предлагал убрать конфликт повторного копирования с загрузкой,
а эпоха 6 уже описывает reuse-on-edit. Оставлять prepare на document edit —
несогласованное распределение обязанностей и повторная точка потери генерации.

**Изменение.** «Требования», «Ошибки и границы»: prepare на первой загрузке,
включении и явно определённых refresh/reopen; edit/watcher только преобразуют
solution по готовому mapping. После graph change mapping пересоздаётся, не
переносится на произвольные ProjectId. Stale — результат неудавшейся попытки
обновления, а не штатное состояние после edit. Понятие отдельного public
«opt-in recopy» не вводить без необходимости.

**Последствия.** Внутренний state/mapping и diagnostics failed refresh.
Смена recopy-on-edit на reuse — наблюдаемая compatibility перемена E6-01.
Успешность document save и успешность обновления generator не смешиваются.

## E2-05 — ACCEPT

**Основание.** F root детерминирован по solution path, поэтому два серверных
процесса могут использовать один каталог. Изолированный test root не запрещает
дать его двум дочерним процессам, но спецификация этого не требует явно.
Одного unit-теста потоков недостаточно для заявленной межпроцессной поддержки.

**Изменение.** При сохранении shared root включить обязательный тест двух
процессов, работающих с одним root внутри изолированной тестовой директории:
race публикации, завершение одного процесса и повторное чтение другим.
Альтернатива per-session root требует отдельного решения и удаления ненужного
cross-process reuse из контракта, а не одновременных противоречивых обещаний.

**Последствия.** Процессный test harness, ownership и cache scope. Shared root
остаётся предложением, а не исходным требованием U; решение связано с E2-06.

## E2-06 — PARTIALLY ACCEPT

**Основание.** Бюджет диска и поведение при его исчерпании нужны раньше этапа 3.
Но F уже создаёт новый ticks-каталог при изменении timestamp: накопление не
впервые вводится content hash, а одинаковые rebuild bytes могут, наоборот,
дедуплицироваться. Предложенное удаление root в `ClearWorkspaceAsync` не является
надёжным решением: L остаётся жив, старые compilation и mapped DLL тоже могут
оставаться. Session/PID directory не доказывает, что файл больше никому не нужен.

**Изменение.** «Ошибки и границы»: измерение размера поколений и роста,
понятный отказ/stale при disk-full, ownership и поддержанный способ очистки
после остановки владельцев. Зафиксировать выбор shared или session root и
границу будущей retention работы. Не обещать успешное удаление при clear.

**Последствия.** Операционный контракт, telemetry размера/ошибок, disk-full
tests. Авто-GC требует отдельного решения о живых владельцах; нельзя добавлять
его как якобы бесплатное исправление. Арбитраж A-03 в сводке.

## E2-07 — REJECT

**Основание.** Контрпример «immutable, но id=ticks» прямо нарушает уже имеющиеся
«Идентификатор поколения зависит от содержимого» и acceptance «изменённая DLL
с сохранённым timestamp получает новое поколение». Нельзя закрыть эпоху только
по одному удобному критерию и считать это недостатком остальных требований.
Разделение file identity и CLR binding задано также эпохой 3 «Проблема».

**Изменение.** Новое требование по этому ID не нужно. Точность hash domain
улучшается по E2-01, refresh — по E2-02. Same content → reuse и different content
→ different path остаются обязательными, без обещания свежего CLR исполнения.

**Последствия.** Реализация с ticks-only должна провалить существующую приёмку;
это не основание усложнять архитектуру или переносить binding tests в этап 2.
