# Вердикты по findings

## E0-01 — ACCEPT WITH MODIFICATION

**Критика.** В [Stage 0](../proposal-v1/stage-0-hygiene.md) CI должен брать SDK из `global.json`, которого в репозитории нет. Это воспроизводимый сценарий отказа setup. Цель исходной задачи — работающий Windows test gate; обязательного pin-файла она не задаёт. [`ARCHITECTURE.md`](../../../ARCHITECTURE.md) прямо фиксирует отсутствие `global.json`, а удалённый workflow `bdc953d` использовал `dotnet-version: "10.0.x"`.

**Ответ автора.** Выбор SDK в workflow достаточен для текущей стадии; это принимается. Не принимается более сильное утверждение о точной воспроизводимости версии: `10.0.x` выбирает актуальный patch SDK. Для Stage 0 требуется воспроизводимость выбора семейства SDK и запуска gate на чистом runner, а не битовая идентичность среды.

**Граница.** Удалить «SDK из `global.json`», явно установить .NET 10 SDK в workflow, зафиксировать фактически выбранную версию в логах и выполнить тестовые jobs на чистом runner. Не добавлять `global.json` только ради этого finding. Причину revert `b9f2e02` выяснить по прежнему требованию Stage 0; сам revert не доказывает причину.

## E2-01 — ACCEPT WITH MODIFICATION

**Критика.** Stage 2 требует прямых `SymbolKey.Create/Resolve`, но тип `SymbolKey` в используемом Roslyn 5.9.0 непубличен. Предписанная реализация не компилируется. Внешний [§6](../roslyn_mcp_tool_review.md) допускает opaque server-side handle и не требует экспортировать внутренности Roslyn.

**Ответ автора.** Непрозрачный session handle на публичных API — обоснованный выбор для 1.x; internal adapter с контролем версии не нужен. Но перечисление `ProjectId + DocumentId + span/kind + checksum` нельзя объявить доказанной схемой долговременной идентичности: одинаковые декларации могут менять положение, а равный текст не доказывает непрерывность объекта после удаления и повторного создания.

**Граница.** `symbolId` непрозрачен, действует только в текущей load-сессии процесса и не сериализует internal `SymbolKey`. Сервис хранит контекст опубликованной сессии, проекта и декларации; новый load, reset или новый процесс инвалидируют ID. Повторное использование после sync подчинено E2-04. Проверить компиляцию сервиса против публичных API Roslyn 5.9.0 до внедрения tools.

## E2-02 — ACCEPT WITH MODIFICATION

**Критика.** Сейчас `find_usages` требует `symbolName`; `find_symbol_references`, `get_method_body`, `get_call_graph`, `rename_symbol` требуют старые аргументы адресования. Добавление `symbolId?` не позволяет обещанные ID-only вызовы. Схема MCP выводит required из сигнатур, что отражено в [`McpToolCatalogTests`](../../../../RoslynMcpServer.Tests/McpToolCatalogTests.cs).

**Ответ автора.** Верно, совместимость 1.x следует определять сохранением всех ранее валидных вызовов, а не неизменностью набора `required`. Однако response расширяет location-only режим на каждый старый tool без необходимости: Stage 2 обещает его для `find_usages` и нового `get_symbol_info`, а остальные четыре старых tool получают ID дополнительно к legacy-вызову.

**Граница.** Для пяти старых tools: `symbolId` без старых полей адресования либо прежний набор аргументов. Для `find_usages` также `filePath+line+column`; для `get_symbol_info` — ID, полная location или query с явной неоднозначностью. `get_symbol_source` принимает ID. При нескольких заполненных селекторах — ошибка, даже если они случайно указывают на один символ: это простой и проверяемый контракт. `newName` required во всех режимах rename; `scope` и `previewOnly` сохраняют значения по умолчанию. Порядок C# параметров можно изменить, но JSON-имена MCP и поведение прежних вызовов должны сохраниться.

## E2-03 — ACCEPT WITH MODIFICATION

**Критика.** `SymbolKey` разрешается против конкретной компиляции. Два проекта с одинаковой assembly identity могут иметь одинаковые ключи. [`FindDocumentAsync`](../../../../Services/SolutionManager.cs) по file path выбирает первый `Document`, поэтому linked-файл неоднозначен.

**Ответ автора.** Проектный контекст в ID и возврат project candidates в location-режиме принимаются. `ProjectId` нужен именно как часть текущей load-сессии, не как обещание переносимости между загрузками. Находить верный проект до semantic read недостаточно для edit: shared physical path может затронуть другой проект (NEW-ARB-001).

**Граница.** Для нового ID/location-режима никакого first-hit выбора документа. При нескольких memberships и отсутствии project selector вернуть кандидатов с различимым project context; адресовать только выбранный `Document`/`Project`. Legacy-вызовы сохраняют прежнюю семантику, но документация не должна обещать им точность для linked-файла. Для ID-based rename дополнительно выполнить preflight физического пути.

## E2-04 — ACCEPT WITH MODIFICATION

**Критика.** Probe ревью показывает, что после вставки соседней одноимённой local function старый ключ однозначно выбирает новую функцию. Отсутствие `missing`/`ambiguous` не означает правильную цель. [`GetPublishedSolutionAfterDiskSyncAsync`](../../../../Services/SolutionManager.cs) подставляет свежий snapshot.

**Ответ автора.** Fail-closed для locals принимается. Деление на «именованные декларации с checksum — durable» и «locals — stale» отвергается: checksum сохранённой декларации может совпасть у другого экземпляра, а замена декларации тем же текстом неотличима без истории правок. Исходный §3 требует читать local function, но не обещает устойчивый ID после произвольных изменений.

**Граница.** В Stage 2 ID переживает sync, если текст всех документов, содержащих объявления выбранного символа, не изменился и сохранились load-сессия и project context. Любое изменение такого документа делает ID `stale-id` до нового разрешения символа; это относится и к методам, типам, полям, и к local functions. Изменение иных документов само по себе ID не инвалидирует. Более тонкий tracking после правок своего документа допустим в будущей ревизии лишь при доказанной сохранности цели и специальных тестах; не является условием Stage 2. Freshness gate записи остаётся отдельной проверкой уже после identity validation.

## NEW-ARB-001 — linked-файл и физическая запись

**Новый существенный риск.** В текущем [`PersistDocumentChangesAsync`](../../../../Services/SolutionManager.cs) изменения обходятся по `Project.Documents` и записываются по `FilePath`. Один путь, входящий в два проекта, может быть записан несколько раз или иметь разные тексты в двух `Document`. Ответ на E2-03 выбирает проект для символа, но не гарантирует единственный согласованный результат для общего физического файла. `rename_symbol(scope="project")` особенно опасен: изменение физического файла видят оба проекта, даже если семантический scope ограничен одним.

**Решение.** До любой ID/location-based записи по пути с несколькими memberships сгруппировать все затронутые `Document` по нормализованному физическому пути и проверить, что предлагаемый итоговый текст одинаков во всех контекстах и не оставляет их расходящимися. Если это не доказано, отклонить операцию до первой записи с явной ошибкой `shared-path-conflict`. `scope="project"` не может обещать изоляцию для общего физического файла. При успешной записи писать путь один раз и согласовать опубликованные документы. Приёмка: два проекта с linked-файлом, разные контексты, preview и apply; ни silent retarget, ни last-writer-wins.
