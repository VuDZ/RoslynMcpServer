# task-04. Ревью варианта D

Дата: 2026-11-26. Проверено предложение из `2c38b04` и соответствующие пути записи в `3be841d`. Ревьюер: Codex (GPT-6). [Постановка task-04](../task-04-source-write-editor-semantics-hi.md)

Сохранение UTF-8 без BOM возвращает обычные патчи для 54 production-файлов с не-ASCII, включая `SolutionManager.cs`. Проверки можно делать на исходных и готовых байтах под существующей блокировкой. Для типичной локальной MCP-сессии это позволяет сохранить выигрыш task-01 от удаления повторной оценки MSBuild. Вариант D стоит начинать с ограниченного сценария после уточнения гарантий ниже.

## Что исправить в правиле D

1. **Проверять смену автоопределения по байтам для любой загруженной `CodePage`.** В F-01 исходные байты `D0 96` литерала `Keep` читаются как `Р–` в Windows-1251. Соседний литерал с байтом `DF` делает файл невалидным UTF-8. После замены `DF` на ASCII `X` файл становится валидным UTF-8. При явной `CodePage=1251` `Keep` по-прежнему содержит `Р–`, а обычная сборка с автоопределением получает `Ж`. Ограничение проверки загруженным `CodePage=0` пропускает этот случай, если 1251 задана только для design-time. Перед записью без BOM сравнивать валидность UTF-8 исходных и готовых байтов, включая обратный переход. При смене и сохранении нетронутых не-ASCII байтов отклонять патч до записи. [Правило D](../task-04-source-write-editor-semantics-hi.md#правило-d) · [P1-44](../../project-review-2026-11-25/task-44-p1-source-write-reader-encoding-hi.md)
2. **Проверять согласие всех известных читателей после патча.** В F-02 Windows-1251 и Windows-1252 одинаково читают исходный `§` (`A7`). После замены соседнего `X` на `Ж` в Windows-1251 новый байт `C6` означает `Ж` для первого проекта и `Æ` для второго. Обе страницы прежде могли загрузить один и тот же исходный текст. Проверка представимости в выбранной странице пропускает расхождение. Сформировать готовые байты один раз и строго декодировать их каждой известной кодировкой. Сравнить полный текст с запросом до записи и публикации снимка. [Текущая проверка при чтении](../../../Services/Workspace/SolutionManager.cs#L2093)

## Изменение гарантии P1-49

Уже имеющийся не-ASCII может встречаться только в комментарии. В F-03 UTF-8-комментарий `// Café` остаётся на месте, а патч меняет строковый литерал `X` на `Café`. С UTF-8 обычная сборка получает `Café`, с Latin-1 — `CafÃ©`. BOM в контрольном опыте восстанавливает `Café` для Latin-1 сборки. Поэтому наличие нетронутого не-ASCII не подтверждает пригодность кодировки для нового литерала. Другая `CodePage` обычной сборки может по-прежнему изменить поведение программы после успешной записи. [P1-49](../../project-review-2026-11-25/task-49-p1-build-source-encoding-hi.md)

Тот же случай воспроизведён в файловом C#-скрипте с `#!`, директивой `#:property CodePage=28591` и UTF-8 без BOM. `dotnet run --file` успешно завершился и напечатал кодовые единицы `0043 0061 0066 00C3 00A9`. Критерий для shebang должен проверять и прямой запуск на Linux, и значение строки. Возможность задать `CodePage` в скрипте нужно учитывать отдельно. [Директивы файловых приложений .NET](https://learn.microsoft.com/en-us/dotnet/core/sdk/file-based-apps#property)

## Рекомендуемый объём первой реализации

- Возвращать `apply_patch` для ASCII-замен в существующем валидном UTF-8 без BOM. Сохранять байты вне фактических диапазонов замены. Проверять чтение результата всеми известными читателями и учитывать смену автоопределения. Для неустановленной кодировки уцелевших байтов сохранять явный отказ.
- Разрешать внесение нового не-ASCII без BOM при явном контракте проекта на UTF-8 для design-time и обычной сборки. Загруженные метаданные и наличие не-ASCII в комментарии сами по себе такой контракт не задают. До этого выбора сохранять защиту варианта B в рискованных сценариях.
- Для полной записи отдельно определить случаи ошибочного декодирования старого файла и несогласия читателей. `update_file_content` получает полный новый текст, а границ нетронутой части у него нет. Для `#!` отдельно проверить неподдерживаемую и явно заданную `CodePage`, сохранив требование `#!` с первого байта.

## Проверенные примеры

Проверки выполнены на Windows с ANSI-страницей 1251 и .NET SDK 11.0.100. Минимальные программы компилировались штатным `csc` с указанными страницами, затем выводили кодовые единицы строк из собранных программ. В отдельном опыте использовался `dotnet run --file`.

- **F-01.** Нетронутые `D0 96` дают `0420 2013` при явной 1251 до и после патча. При автоопределении результат меняется с `0420 2013` на `0416`.
- **F-02.** Исходный `A7` даёт `00A7` при обеих страницах. Добавленный `C6` даёт `0416` при 1251 и `00C6` при 1252.
- **F-03.** UTF-8-байты `43 61 66 C3 A9` дают `0043 0061 0066 00E9` при 65001 и `0043 0061 0066 00C3 00A9` при 28591. При 28591 с UTF-8 BOM результат `0043 0061 0066 00E9`.

Эти проверки воспроизводят чтение исходника компилятором для предлагаемых байтов. Критерии приёмки реализации и запуск shebang в Linux остаются проверками task-04.
