# task-01. Замеры и проверка варианта B

Дата: 2026-11-26. Статус: **accepted**. Приняты вариант O-01/B для явной записи C# через `update_file_content` и `apply_patch`, сообщение агенту с вариантами действий и отказ от повторной оценки читателей при этих операциях.

## Исходный замер

Измерены публичные `update_file_content` и `apply_patch` через MCP stdio в Release-сборке `d8eb8da` (`main`, 1.6.5) на Windows 11 и SDK 11.0.100. Для каждого решения использовалась отдельная локальная копия. До загрузки решения в один из SDK-проектов добавлялся короткий ASCII-файл без BOM. После загрузки один вызов задавал полный текст с новым числом, следующий заменял только число. Время включает получение ответа MCP. После каждого вызова отдельно сверялись байты. Время загрузки исключено. По восемь вызовов каждого инструмента, первый вызов отброшен из медианы.

- RoslynMcpServer (`d8eb8da`, 5 загруженных проектов). Медианы 859,62 мс для полной записи и 837,25 мс для патча.
- LifeBackend (`b974785`, 18 загруженных проектов). 729,75 мс и 739,08 мс. Локальный кэш не содержал пакетов .NET 9.0.23 для одного вспомогательного проекта `ReportGenerator`. Workspace загрузил все 18 проектов.
- LifeBackend Selectel (`44643de`, 45 загруженных проектов). 1 212,15 мс и 1 160,75 мс. Зависимости восстановлены из локального кэша.

В исходной версии все 48 запросов проверки завершились отказом подтвердить читателей исходника. Байты остались прежними. Числа показывают время ответа при отказе.

## Повторный замер

На тех же копиях и с той же процедурой вариант B выполнил все 48 записей. После каждого запроса получены ожидаемые ASCII-байты без BOM. Медианы `update_file_content` и `apply_patch` соответственно:

- RoslynMcpServer, 5 проектов — 13,87 мс и 12,13 мс.
- LifeBackend, 18 проектов — 7,44 мс и 8,13 мс.
- LifeBackend Selectel, 45 проектов — 12,32 мс и 12,43 мс.

В исходном замере учитывались отказы, а в повторном — успешные записи. Замер показывает стоимость двух вариантов ответа на один и тот же запрос.

## Red

На исходном коде прогнаны 11 случаев новых регрессий в `WorkspaceWriteEncodingTests`. Девять упали на ожидаемых различиях поведения, два контроля прошли. Проверка ASCII зависела от повторной оценки или доступности SDK, патч мог изменять файл с нетронутым не-ASCII, полная запись могла оставлять не-ASCII без BOM. ## Реализация и ревью

Удалена повторная оценка design-time и обычных читателей при явной записи C#-файлов. Для ASCII используются сведения загруженных проектов и проверяется буквальное чтение результата. Связанный исходник с несколькими загруженными кодировками патчится только при одинаковом чтении его текущих байтов. Кодировки обычной сборки, которые отличаются от загруженных, больше не сверяются при записи. Для чтения патча сохранены распознавание BOM, строгий декодер и сравнение под блокировкой.

Если предлагаемая правка потребовала бы конвертации файла без BOM с нетронутым не-ASCII, `apply_patch` останавливается до записи. Сообщение предлагает подтвердить исходную кодировку и получить согласие на полную конвертацию либо применить редактор с явно выбранной кодировкой. Позиции нетронутого текста берутся из тех же диапазонов, которые использует сопоставление патча.

Один независимый ревьюер нашёл два замечания. Исправлены и перепроверены общее чтение ASCII с разными загруженными CodePage и переносимость shebang без известного проекта. Сохранена дешёвая проверка ISO-646 и кодировок со сменой состояния для патчей и shebang без загруженного владельца. Она защищает фактический результат чтения, например `$` в IA5 и `~{VP~}` в HZ. Повторная оценка MSBuild ей не нужна.

## Проверки

- Целевой Release-прогон после реализации и ревью: 148 тестов записи, атомарности и сопоставления патчей прошли. В финальную серию добавлены два случая отказа для непереносимого ASCII в shebang без загруженного владельца и сверка двух литералов P1-44 из DLL свежей сборки.
- C#-скрипт, записанный через `update_file_content`, запущен непосредственно по `#!` в Ubuntu 24.04 под WSL с .NET SDK 10.0.115. Процесс вывел `Task-01 shebang launched` и завершился с кодом 0.
- Отдельный вызов `apply_patch` по MCP stdio попытался изменить ASCII рядом с нетронутым `Café` в загруженном `.cs` без BOM. Ответ подтвердил сохранность файла и предложил согласовать конвертацию либо править с явной исходной кодировкой. SHA-256 до и после вызова совпал.
- Первый полный прогон выявил два несоответствия ожидаемых формулировок в тестах shebang и два несоответствия ограничений каталога MCP. Тесты shebang теперь сверяют фактическую причину отказа. Подробные подсказки оставлены в `get_tool_help`, а краткие описания инструментов уложены в текущий лимит. Записанные размеры `tools/list` обновлены для затронутых профилей.
- Финальная сборка `RoslynMcpServer.sln` в Release прошла. Повторный целевой прогон после исправлений — 42 из 42.
- Полная основная серия Windows `Category!=AnalyzerLifecycle` — 2 897 из 2 897 в Release, в том числе все 128 `SourceStructure`. Ноль ошибок и пропусков по TRX и проверке CI `Assert-NoSkippedTests.ps1`.
- Отдельная серия `Category=AnalyzerLifecycle` с `ROSLYN_MCP_ANALYZER_LIFECYCLE=1` — 13 из 13 в Release. Ноль ошибок и пропусков по TRX и той же проверке CI.
