## F-4

**Открыта повторно 2026-11-26.** Независимая проверка на Linux: при тестовом проекте с `Microsoft.NET.Test.Sdk` в репозитории патч без загрузки отклоняется, а после загрузки проходит. Отказ на репозитории с 26 проектами затрагивает и целевые решения. [R-1 и R-2](mcp-followups-review-claude-2026-11-26.md#замечания)

Дата 2026-11-26. Приёмка охватывает патчи C# без BOM и объявления кодировки. Сервер вычисляет членство в `Compile` и `CodePage` без загрузки workspace. Он учитывает прямые и связанные исходники, `ProjectReference`, фактические конфигурации проектов из решения и внутренние TFM. Перед записью оценка повторяется, чтобы учитывать изменения проекта и импортов между поиском и записью.

Поиск ограничен репозиторием или найденным деревом проекта и явно связанными проектами. Неизвестная конфигурация компилятора, неоднозначный алиас или неполная оценка приводят к отказу для неоднозначного фрагмента. Бюджет одного прохода проверяется между операциями и включает 256 каталогов, 24 проекта, 96 оценок и 8 192 проверяемых пути. Синхронная оценка MSBuild может выйти за отведённые три секунды между проверками. Обычные записи с объявленной кодировкой следуют правилу D, а уже известные читатели участвуют в проверке.

Через MCP 1.7.0 на собранном Release проверены обычный и связанный `Compile` без workspace, совпадение результата после загрузки владельца, исключённый и бесхозный файл, конфликты во внешнем `ProjectReference` и конфигурации из `.sln`, разные отображения конфигураций зависимых проектов, экспорт без Git, нестандартный `CoreCompile` и Windows junction. В каждом сценарии отказа сверили исходные байты. Копия репозитория с 26 проектами без объявления получила безопасный отказ. Файловый symlink на Windows требует привилегии, которую система не выдала даже вне песочницы. Полевую проверку алиасов выполнили на реальном junction.


Отдельная проба с путём пространства имён Windows `\\.\` воспроизвела отказ после исправления. Ревьюер сравнил SHA-256 файла до и после. Проверки файлового junction и альтернативного написания пути покрывают разные случаи Windows.

Две промежуточные полные серии дали по одному падению в проверках Rapid TIA (`Restored_source_and_trivia_only_edits_are_unchanged` и `Analyzer_config_with_a_pending_revision_is_not_suppressed_until_reconciled`). Оба сценария прошли в целевой проверке после последней правки. Финальная сборка Windows Release, 132 целевых теста, включая все 128 `SourceStructure`, и полная серия `Category!=AnalyzerLifecycle` прошли. В полной серии **2 834 из 2 834**.

Первый вызов `publish --no-restore` дал `NETSDK1047` для BuildHost. Публикация прошла после штатного restore. Проверка однофайлового варианта охватывала отчёт о сервере.

В первом целевом прогоне тест точного размера каталога обнаружил увеличение на 27 байт из-за нового описания инструмента. Ожидаемые значения сверены по всем профилям. ## M-1

Дата 2026-11-26. Независимое ревью приняло маршрутизацию обычного VSTest, сохранение маршрута DLL и результатов TRX. Если `run_test_by_filter` вызван без `noBuild` и без явной или загруженной конфигурации, он сначала собирает проект. Известная конфигурация сохраняет прежний пропуск сборки. Явные `noBuild=true` и `noBuild=false` сохраняют своё значение.

На Windows с SDK 11.0.100 через публичные инструменты Roslyn MCP 1.7.0 проверены следующие случаи.

- При готовой Release DLL и отсутствующей Debug DLL все три тестовых инструмента с `noBuild=true` указывают вычисленный путь, фактическую конфигурацию, платформу и TFM и предлагают `noBuild=false`. Без `noBuild` и конфигурации `run_test_by_filter` собирает Debug. С явным Release все три инструмента переиспользуют существующую DLL с тем же временем изменения. Фильтр без совпадений получает отдельный отчёт VSTest.
- Предварительная проверка нашла нестандартный выход `out/payload/RenamedTests.dll`. Фильтры поверх `.sln` и `.slnx` выполняют только тесты выбранного проекта. Некорректный `.slnf` с неизвестным проектом сохраняет ошибку MSBuild `MSB4025`.
- Рабочие запуски с `Directory.Build.rsp`, пользовательскими `InitialTargets`, `BeforeTargets="VSTest"`, свойством `VSTestTestCaseFilter` и неявной конфигурацией `Configuration=Release` из окружения передаются штатному VSTest. При неоднозначной конфигурации или переопределении целей он также сохраняет свою диагностику.
- Полевой тест со штатным Microsoft.NET.Test.Sdk 17.14.1 выявил слишком широкую проверку `InitialTargets`. Финальная версия распознаёт безопасную форму цели `GenerateProgramFile` из пакета и оставляет штатный запуск при пользовательском переопределении или хуке. Регрессионный тест использует реальный восстановленный пакет.

Контекст оценки MSBuild общий только внутри одного вызова. При исчерпании конечного бюджета VSTest не запускается. Отмена и дедлайн проверяются на границах синхронной оценки проекта.

Замер через `run_test_by_filter` на `RoslynMcpServer.sln` сравнивал сервер из `0a8800f` и сервер с M-1 на одних Release-бинарниках с `noBuild=true` и `noRestore=true`. После начального вызова для каждого сервера измерены три запуска на сценарий.

- Один тест. До исправления `1,306 / 1,308 / 1,292 с`, после `2,063 / 1,937 / 1,859 с`. Медиана `1,306 → 1,937 с`, прирост `0,631 с`.
- 128 тестов `SourceStructure`. До исправления `7,390 / 7,423 / 7,393 с`, после `7,914 / 7,961 / 8,023 с`. Медиана `7,393 → 7,961 с`, прирост `0,568 с`.

Владелец согласовал приёмку M-1 с этой измеренной задержкой.

Финальная Release-сборка `RoslynMcpServer.sln` прошла. В целевой серии, включающей все `SourceStructure` и регрессии TRX, прошло **243 из 243**. В основной серии `Category!=AnalyzerLifecycle` прошли **2 875 из 2 875**.

### R-1 и R-2 · F-4

**Заменено 2026-11-27** [решением владельца](../mcp-followups-plan.md#решение-владельца-2026-11-27): поиск читателей без загрузки убирается, при неизвестном читателе патч отклоняется сразу. Результаты ниже остаются основанием этого решения.

- По происхождению и фактическому содержимому цели F-4 распознаёт штатный `GenerateProgramFile` из Microsoft.NET.Test.Sdk. Стандартный исходник пакета не мешает определить читателя другого файла. Пользовательский путь, хук, переопределение или совпадающее имя вытесняемой заглушки сохраняют консервативный отказ. Регрессии используют восстановленный пакет 17.14.1.
- Поиск сохраняет границу checkout и повторную проверку читателей при записи. Пределы подняты до 4 096 каталогов, 128 проектов и 128 решений, 1 024 оценок и 65 536 проверок путей. Бюджет составляет 10 секунд на один проход и проверяется между операциями. Оба прохода идут под блокировкой workspace. При неполном результате сервер сохраняет исходные байты. Отдельные оценки разрешают SDK изолированно, поскольку кэш MSBuild на общем контексте учитывает имя SDK без версии. [Кэш разрешения SDK в MSBuild](https://github.com/dotnet/msbuild/blob/main/src/Build/BackEnd/Components/SdkResolution/CachingSdkResolverService.cs)
- На Windows исходный сервер отказал в обеих фикстурах, сохранив исходные байты. 1.7.1 применил патчи в решении с обычным Test SDK и в решении из 61 проекта с 1 100 дополнительными каталогами. После загрузки малого решения патч тоже прошёл. Оба вызова на большом решении заняли 12,445 и 6,852 с. На копии самого репозитория с отключённым объявлением кодировки сохранился безопасный отказ. Отдельная проверка вложенного upstream-проекта BuildHost в этой копии дала `NU1015` из-за неполных данных о пакетах. Эта копия остаётся за пределами подтверждённого случая обычного решения.
- Наличие вариантного байта в неизменённой части не доказывает совпадение текста. В проекте с `CodePage=20105`, где байт `$` уже был в комментарии, побайтовая вставка `"$"` прошла компиляцию и напечатала `¤`. .NET подтвердил также `0x7B → ä` для `20106`. В CP932 байт `0x7B` может быть частью двухбайтового символа. Нынешний контракт F-4 требует точного чтения и сохранения запрошенного текста.

## Проверка исправлений N-1 и N-2

Дата 2026-11-27. На Windows семь целевых проверок воспроизвели прежние сообщения. После исправления прошли все 152 теста `WorkspaceWriteEncodingTests`, Release-сборка решения, все 128 тестов `SourceStructure` и все 2 864 теста основной серии `Category!=AnalyzerLifecycle`.

- **N-1.** Полевые `apply_patch` и `update_file_content` через MCP предложили объявить кодировку для скрипта с `#!` и для файла, который не читает ни один проект загруженного решения. Для скрипта также указан `#:property CodePage`. Для файла из другого дерева подсказка сохранила `load_workspace` и путь загруженного решения. Во всех отказах проверены исходные байты.
