# task-03. Реализация варианта B для переименования проекта

Дата 2026-11-26. Статус **accepted**. Вариант B принят для `.slnx`, `.sln` и файлов проектов MSBuild. [Постановка](../task-03-project-rename-sdk-models-med.md) · [Spike](task-03-project-rename-sdk-spike.md)

## Реализация

- Решения читаются библиотекой SolutionPersistence из исходных байтов. Для `.slnx` расположение ссылок определяет XML-ридер, а принадлежность `Project` и `BuildDependency` проверяется по модели. Полные XML-имена позволяют сохранить элементы расширений с похожими именами. `BuildDependency` сохраняет связь, даже если регистр или разделители отличаются от записи проекта. Для `.sln` заголовок сверяется по GUID и пути из модели. Меняются только значения пути и, где применимо, имени проекта.
- Файлы `.csproj`, `.fsproj` и `.vbproj` читаются моделью `ProjectRootElement`. Координаты `Include`, `Exclude`, `Update` и `Remove` сверяются с исходным XML. `AssemblyName` и `RootNamespace` в переименовываемом проекте меняются по прежнему правилу при совпадении со старым именем. Порядок операций MSBuild, условия и данные расширений сохраняются. [Правки решений](../../../Services/Editing/ProjectRenameSolution.cs) · [Правки файлов проектов](../../../Services/Editing/ProjectRenameProject.cs)
- Каждый план хранит прочитанные байты и кодировку изменяемых файлов. Проверка перед переносом обнаруживает устаревший план. Повторная сверка перед записью сохраняет отчёт о частичном сбое, если файл изменился уже после переноса. Вычисляемые и неоднозначные ссылки отклоняются при планировании. [Исполнение плана](../../../Services/Editing/ProjectRenameHelper.cs)

Проверка диапазона исключает координаты, которые XML-ридер возвращает из объявления DTD для развёрнутого элемента. Обычные XML-сущности внутри литерального значения поддерживаются. Итоговые байты вне подтверждённых диапазонов сохраняются вместе с BOM и окончаниями строк. [Снимок файла](../../../Services/Editing/ProjectRenameFile.cs) · [Точечные правки](../../../Services/Editing/ProjectRenameTextEdits.cs)

Для свойств, разбитых комментариями, сравнение имени использует обычную нормализацию пробелов MSBuild. Если пробел был частью исходного `AssemblyName`, он заменяется вместе с именем. Если MSBuild отбрасывает отдельный пробел между комментариями и вычисленное имя отличается от имени файла, свойство сохраняется побайтно.

Повторное чтение подготовленных байтов через SDK обнаруживает ошибки, которые появляются только в будущем решении. Проверен случай, когда проект `Shared/New.csproj` уже присутствует в той же папке решения и переименование `Old` в `New` создало бы дубликат имени. Случай отклоняется до переноса как для `.sln`, так и для `.slnx`. Отдельно проверяются совпадения конечных путей на диске.

## Проверки

- Сабагент валидации проверил итоговую Release DLL на копиях реальных фикстур. Совпали байты 9 из 9 файлов в трёх профилях UTF-8 и UTF-16, LF и CRLF, с BOM и без BOM. Прошли 6 комбинаций `dotnet sln list` и `dotnet build` и 6 проверок `dotnet msbuild -getItem:ProjectReference` в `Debug` и `Release`. Столько же проверок прошли в исходных контрольных копиях.
- Отдельный прогон через MCP и `dotnet msbuild -getProperty:AssemblyName` подтвердил 3 сценария с UTF-16 BOM, XML-сущностью, комментариями и пробелами в свойствах.
- Сборка Windows Release прошла с нулём ошибок. Прошли 77 целевых тестов и отдельно все 128 `SourceStructure`. Целевые проверки покрыли перенос владельца, отказ до переноса, точность записи и частичный сбой записи с `success=false` в телеметрии (P2-27).
- Полная основная серия `Category!=AnalyzerLifecycle` прошла **2 945 из 2 945**. В трёх TRX суммарно 3 150 выполненных тестов. `Assert-NoSkippedTests.ps1` подтвердил ноль ошибок и пропусков.

- После интеграции `fix/task-02-followups` (`92d1112`) повторный прогон через Roslyn MCP 1.7.0 подтвердил сборку Windows Release, **128 из 128** `SourceStructure` и **2 799 из 2 799** тестов `Category!=AnalyzerLifecycle`. Уменьшение числа тестов на 146 связано с удалением проверок консольных эвристик в task-02. [Отчёт об изменениях Rapid TIA](task-02-followups-g2-g3.md).

Исполнительные журналы и фикстуры сохранены локально в `artifacts/bin/task-03`, вне поиска проектов инструментом переименования.
