# task-03. Spike моделей переименования проекта

Дата 2026-11-26. База `3f0427b`, Windows x64, SDK `11.0.100`, MSBuild `18.12.2`, SolutionPersistence `1.0.52`. Статус **spike завершён, владелец выбрал B для O-03**. [Постановка](../task-03-project-rename-sdk-models-med.md) · [Приёмка реализации](task-03-project-rename-validation.md)

## Фикстуры и проверки

Одна и та же операция `Old/Old.csproj → New/New.csproj` выполнена в независимых копиях. Для каждого варианта проверены UTF-8 без BOM с LF, UTF-8 с BOM и CRLF, UTF-16 LE с BOM и CRLF.

- В `.slnx` использованы папка `/Group/Subgroup/`, смешанный регистр имён элементов, пространство имён по умолчанию и префикс с тем же URI. У переименовываемого проекта были комментарий, пользовательский атрибут и вложенное расширение. Тот же путь повторялся в настоящем `BuildDependency`, в элементах расширений с похожими именами и в данных чужого блока. Два настоящих значения содержали экранированный разделитель `&#x2F;`.
- В `.sln` были явные GUID, `ProjectDependencies`, `NestedProjects`, конфигурации решения, комментарий и пользовательские секции проекта и решения. Старый путь также присутствовал в пользовательском тексте секций.
- В `App.csproj` были литеральные `Include`, `Exclude`, `Update` и `Remove`, многострочный атрибут, разные кавычки, XML-сущность и имитация `ProjectReference` внутри `ProjectExtensions`. В `Release` условная ветка `Choose` задавала `ReferenceOutputAssembly=false`. В `Debug` у ссылки эти метаданные отсутствовали.

Подготовлены 12 копий. Для каждого профиля были исходный контроль, A с сериализацией, B с проверкой модели и точечными заменами, C с действующим `ProjectRenameHelper.CreatePlan` и `Apply`. Ожидаемые байты каждого изменённого файла строились из шаблона, где менялись только конкретные значения. Прототип и журналы архивированы локально в `artifacts/bin/task-03/task-03-spike`.

На каждой копии выполнены следующие команды с соответствующими путями. Список проектов и состав вычисленных элементов сверялись с ожидаемыми.

```text
dotnet sln Demo.slnx list
dotnet sln Demo.sln list
dotnet build Demo.slnx -c Release
dotnet build Demo.sln -c Release
dotnet msbuild App/App.csproj -getItem:ProjectReference -p:Configuration=Debug
dotnet msbuild App/App.csproj -getItem:ProjectReference -p:Configuration=Release
```

Прошли все 24 пары `list` / `build` и все 24 проверки вычисленных ссылок. `App` в каждой конфигурации получал ровно один ожидаемый проект. `Exclude` и `Remove` сохраняли результат, а `ReferenceOutputAssembly=false` оставалось только в `Release`. Отдельный прогон действующих `ProjectRenameHelperTests` в Windows Release дал 34 из 34 без пропусков. Он включает переезд владельца ссылки и решение внутри перемещаемого каталога.

## A. Модели SDK читают и записывают

- **`.slnx`.** Смена `SolutionProjectModel.FilePath` обновила настоящий `BuildDependency`. Во всех трёх профилях сохранение удалило атрибут и вложенное расширение переименованного проекта и потеряло связанный комментарий. Соседний блок `TelemetryExtension` сохранился, но его кавычки и пробелы изменились. Даже сохранение без изменений добавило родительскую папку `/Group/` и нормализовало текст. У расширения модели, полученного при чтении, `PreserveWhitespace` уже был `true`.
- **`.sln`.** GUID, секции зависимостей и пользовательские секции сохранились. Комментарий исчез, отступы поменялись, появилась стандартная `SolutionProperties`. Сохранение без изменения также дало другой файл во всех профилях.
- **`.csproj`.** `ProjectRootElement.Open(..., preserveFormatting: true)` и `Save()` сохранили метаданные, условие и комментарий. Сериализация поменяла одинарные кавычки, убрала пробелы вокруг `=` и свернула многострочный атрибут. Принудительное сохранение исходной модели через `Save(TextWriter)` тоже дало другой текст.

Результат A — **0 из 9** точных совпадений с ожидаемыми байтами. Для `.slnx` потеря данных нарушает критерий приёмки даже при успешной сборке. [SolutionPersistence](https://github.com/microsoft/vs-solutionpersistence) · [ProjectRootElement.Open](https://learn.microsoft.com/en-us/dotnet/api/microsoft.build.construction.projectrootelement.open?view=msbuild-18-netcore)

## B. Модели SDK подтверждают правки исходного текста

- **`.slnx`.** У публичного `SolutionProjectModel` нет координат. Прототип сверял проект по нормализованному пути, зависимость по её владельцу и цели в `Dependencies`. Координаты атрибутов дал `XmlReader` через `IXmlLineInfo`. При поиске использовались полные имена с префиксами. Благодаря этому `ext:Project` отличался от настоящего `Project` даже при одном URI. Старая строка из диапазона декодировалась и сравнивалась со значением, полученным при чтении.
- **`.sln`.** Прототип нашёл одну запись проекта по GUID и пути из модели SDK, затем поменял только отображаемое имя и путь в заголовке. Остались исходные секции, GUID, комментарии и переносы строк. Поддержку токенизации заголовка можно оставить в существующем узком преобразователе.
- **`.csproj`.** `IncludeLocation`, `ExcludeLocation`, `UpdateLocation` и `RemoveLocation` указывали на начало соответствующего атрибута во всех профилях. Из исходного текста получен диапазон между его реальными кавычками, а старое значение сверено после XML-декодирования. `ProjectRootElement` перечислил настоящие объявления, включая `Choose`, и оставил текст в `ProjectExtensions` вне списка правок. [Координаты ProjectItemElement](https://learn.microsoft.com/en-us/dotnet/api/microsoft.build.construction.projectitemelement?view=msbuild-18-netcore) · [Контракт ElementLocation](https://learn.microsoft.com/en-us/dotnet/api/microsoft.build.construction.elementlocation?view=msbuild-18-netcore)

Результат B — **9 из 9** точных совпадений. Проверялось полное восстановление исходной кодировки, включая BOM, и отсутствие пересечения диапазонов. При отсутствии ожидаемого подтверждённого диапазона зависимости прототип отказал до переноса. Действующий планировщик отдельно отказал до переноса при `$(ProjectDir)` в ссылке.

## C. Текущая реализация

Все решения открывались и собирались. Семантика ссылок сохранилась в проверенных конфигурациях. `.slnx` сохранил расширения по смыслу, но изменил оформление их XML. `.csproj` также изменил оформление. `.sln` совпал с ожидаемыми байтами в двух профилях с CRLF и поменял LF на CRLF на Windows. Итого **2 из 9** точных совпадений.

## Рекомендация O-03

Выбрать **B для всех трёх форматов**. Для `.slnx` использовать модель графа SolutionPersistence и координаты XML-атрибутов из исходного текста. Для `.sln` совместить проверку идентичности по GUID и пути с существующим разбором заголовка. Для `.csproj` брать объявления и координаты из `ProjectRootElement`. Использовать имеющийся расчёт конечного пути владельца и цели ссылки и сохранить отказ при неоднозначных операциях.

В реальной реализации каждому ожидаемому изменению должен соответствовать один проверенный диапазон исходного файла. Для `.slnx` сопоставление учитывает границы настоящих узлов. Для файлов проектов остаются существенными порядок операций `ProjectReference` и правила совпадения литералов. Модель Construction предоставляет объявления. Поведение условий, импортов и `Update` / `Remove` / `Exclude` проверяется вычислением MSBuild. Результат spike подтверждает сопоставление на фикстурах, в том числе на XML-сущностях. В регрессионной проверке реализации нужно охватить перенос владельца, target-time операции, нестандартные варианты заголовков и частичный сбой записи. Прототип проверен на Windows.

Прототип собрался со ссылкой на проект сервера без отдельного пакета SolutionPersistence. Явная зависимость при прямом использовании его публичного API остаётся решением реализации.
