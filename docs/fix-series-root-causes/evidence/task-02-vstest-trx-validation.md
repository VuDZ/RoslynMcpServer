# task-02. Проверка итога VSTest по TRX

Дата: 2026-11-26. Статус: **accepted**. Проверен вариант A для `run_dotnet_test`, `run_specific_test` и `run_test_by_filter`. [Постановка](../task-02-test-results-from-trx-hi.md)

## Эксперимент с VSTest

На Windows с SDK 11.0.100, `Microsoft.NET.Test.Sdk` 17.14.1 и адаптером xUnit 3.1.0 решение `.slnx` запускало проект A на `net10.0` и `net11.0`, проект B на `net11.0`. Каждый запуск создал отдельный TRX. При совпавшем имени VSTest добавил суффикс `[1]`. Путь DLL с исходным регистром был в `TestMethod.codeBase`. `UnitTest.storage` содержал тот же путь в нижнем регистре.

- Совпадение на одной цели и ноль результатов на двух соседних дали код выхода `0`. Два пустых TRX имели `outcome="Completed"` и `RunInfo` с точным фильтром и полным путём DLL. Прямой запуск DLL с фильтром без совпадений дал такой же отчёт.
- Контролируемая авария двух процессов testhost дала код `1`. Один TRX сохранил прошедший тест, два аварийных содержали `outcome="Failed"` и сообщение об аварии. У аварийного отчёта без тестовых строк мог отсутствовать путь DLL в определениях тестов.
- При `CI-001` в цели MSBuild после VSTest отчёты тестов сохранились, а команда вернула `1`. Событие MSBuild содержало пользовательский код ошибки.
- xUnit записал пропуск как строку `NotExecuted`, хотя счётчик `notExecuted` был равен нулю. Две строки одного параметризованного теста считались отдельными случаями. Три прогона с большими сообщениями об ошибках дали свыше 2,5 МБ консольного журнала.

## Решение и границы

Для проекта и решения ожидаемые сборки извлекаются из фактически запущенных задач VSTest и их входных параметров в бинарном журнале MSBuild. Для прямого запуска DLL ожидаемая сборка известна из вызова. Сопоставление учитывает полный путь, кратность запусков и уникальность идентификаторов TRX. Пустой отфильтрованный отчёт связывается с DLL по подтверждённому сообщению в TRX. Это сохраняет успех при пустом фильтре в соседней сборке и корректно отличает общие ноль совпадений.

Суммы и сведения об упавших тестах читаются из TRX. Код выхода и диагностика MSBuild по-прежнему определяют исход команды. Ненулевой код при прошедших тестах и без установленной ошибки даёт `partial`. Отсутствующий, повреждённый или несопоставимый отчёт исключает успех. При подключении несовместимого логгера или превышении предела чтения в 64 × 1024² символов полнота отчёта остаётся неподтверждённой.

Каталог результатов уникален для каждого вызова и удаляется при выходе из исполнителя. Распознавание консольных сводок и нижних границ больше не определяет итог трёх инструментов. Оно остаётся в Rapid TIA, где отчёт по-прежнему строится из консоли. Три инструмента используют консоль для ограниченного диагностического хвоста и подсказок о прерывании команды.

## Финальные проверки

- Десять вызовов через MCP stdio прошли на итоговой Release-сборке. Проверены три одинаковых успешных итога, смешанный и полностью пустой фильтр, `CI-001` после VSTest, авария testhost, пропуски, точные счётчики при усечении вывода и запуск DLL через `binariesPath`. После каждого вызова проверено отсутствие временных каталогов результатов.
- В первой полной попытке два теста выявили рост бюджета описаний MCP. Короткие описания про TRX теперь занимают столько же места, сколько прежние. Оба теста прошли при повторной целевой проверке.
- Сборка `RoslynMcpServer.sln` в Release на Windows прошла с нулём ошибок и 10 предупреждениями в существующем коде.
- Целевые проверки `TestRunner`, `BoundedProcessOutputTests` и `McpToolCatalogTests` прошли 340 из 340. Отдельный прогон `SourceStructure` прошёл 128 из 128. Проверки исполнителя покрыли удаление временного каталога после успеха, отмены и таймаута.
- Полная основная серия `Category!=AnalyzerLifecycle` прошла 2 933 из 2 933. В трёх TRX суммарно 3 401 выполненный тест, ноль ошибок и пропусков по `Assert-NoSkippedTests.ps1`.
