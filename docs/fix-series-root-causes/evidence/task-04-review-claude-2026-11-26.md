# task-04. Независимая проверка реализации `7265817`

Дата: 2026-11-26. Проверяющий: Claude Opus 5.5 (`claude-opus-5-5`) в отдельной сессии Claude Code. Объект — коммит `7265817` «fix: preserve declared C# source encodings», вариант D и объявленная кодировка.

Итог: реализация соответствует [task-04](../task-04-source-write-editor-semantics-hi.md). Найдены ложный отказ при полной записи (F-1) и неточное сообщение (F-2). Оба исправлены в этом раунде с регрессионными тестами. Отдельно замерена производительность записи: заметной потери нет.

## Что проверено

- Diff production-кода: `SourceEncodingSettings`, `PrepareExplicitWriteUnderLock`, `SelectUndeclaredWriteEncoding`, `ValidateDeclarationUnderLock`, `ValidateBomFreeWrite`, чтение для патча, `#:property CodePage`, передача готовых байтов в атомарную запись.
- Разрешение `charset`. Поиск идёт от каталога файла вверх. Используется ближайший `.editorconfig` со значением, на `root = true` поиск останавливается, `unset` передаёт решение `sourceEncoding`. Порядок `RoslynMcp.jsonc`: cwd → каталог пользователя → exe. Кэш разобранных файлов вызывается только под блокировкой записи.
- Как компилятор выбирает кодировку для файла без BOM, если байты не являются валидным UTF-8. По декомпиляции Roslyn 5.12 (`EncodedStringText.CreateFallbackEncoding`) это `Encoding.GetEncoding(0)`, затем 1252, затем Latin1. На Linux `GetEncoding(0)` возвращает UTF-8 (65001), и `DetectBomFreeCodePage` сервера даёт тот же результат. Расхождения с компилятором нет.
- Release-прогоны на Linux и замер записи через MCP stdio, см. ниже.

## Замечания

### F-1

**Ложный отказ при полной записи ASCII-текста в файл в устаревшей кодировке.** Исправлено.

Пример: проект с `CodePage=28591`, файл в Latin-1 без BOM с литералом `Café`. `update_file_content` с полным текстом только из ASCII (`Cafe`) отклонялся с сообщением «would change UTF-8 auto-detection and could change untouched text». Это подтверждено временным тестом на `7265817`.

Причина: при полной записи `hasUntouchedNonAscii` означает не-ASCII в старом файле. Проверка R-1 срабатывала, когда байты ASCII-результата становились валидным UTF-8. Но ASCII все совместимые с ASCII читатели читают одинаково, а нетронутого текста при полной записи нет. Для патча условие не меняется: при нетронутом не-ASCII готовые байты не бывают чистым ASCII.

Исправление: проверка смены автоопределения пропускается, если готовые байты целиком ASCII. Регрессия `Full_ASCII_rewrite_of_a_legacy_source_is_not_rejected_as_an_auto_detection_change` проверяет байты, опубликованный снимок и значение из свежей сборки.

### F-2

**Отказ называл «CodePage 65001» для проекта без `CodePage`.** Исправлено.

Пример: объявлен `charset = latin1`, у проекта `CodePage` по умолчанию, запрошенный текст в Latin-1 даёт валидный UTF-8. Компилятор определит кодировку файла как UTF-8, и отказ верен. Но сообщение называло это `CodePage` проекта, хотя такой настройки пользователь не задавал.

Исправление: для читателя без `CodePage` сообщение говорит, что компилятор определит кодировку автоматически, и называет найденную кодовую страницу. Регрессия: `Default_CodePage_rejection_names_auto_detection_instead_of_a_project_CodePage`, для патча и полной записи.

### F-3

**`main` (1.6.5) отклоняет любую запись в `.cs` без BOM.** Для `main`, не для этой ветки.

В замере ниже сборка `d8eb8da` отклонила все 84 вызова `apply_patch` и `update_file_content` на Linux, в среднем 1,66 с на отказ. На Windows то же видел исходный замер task-01. Исправление есть только в ветке `docs/fix-series-root-causes`.

## Производительность записи

Замер выполнен через MCP stdio на Linux (x64, SDK 11.0.100). Три опубликованные Release-сборки linux-x64 загружали одинаковую копию этого репозитория, 5 проектов. Для каждого сценария выполнено 21 или 41 вызов, первый отброшен. Проходов: 2 для `d8eb8da`, по 4 для B и D, последние два в чередующемся порядке. Время включает ответ MCP. В таблице медианы в миллисекундах, диапазон по проходам.

| Сценарий | 1.6.5 `d8eb8da` | B `3be841d` | D `7265817` |
|---|---|---|---|
| `update_file_content`, ASCII-файл без BOM | ~1 660, отказ | 5,4–6,6 | 5,8–7,1 (один проход 24,4, повтор 5,8 и 6,0) |
| `apply_patch`, ASCII-файл без BOM | ~1 680, отказ | 9,0–34,4 | 11,5–33,2 |
| `update_file_content`, `SolutionManager.cs` (UTF-8 без BOM, не-ASCII) | ~1 665, отказ | 21,3–35,0, добавляет BOM | 21,7–40,2, без BOM |
| `apply_patch`, `SolutionManager.cs` | ~1 655, отказ | 2,9–4,2, отказ B | 9,8–13,9, успех |

Полная запись в B и D совпадает. Для патча ASCII-файла медианы D в повторных проходах на 2–7 мс выше, это в пределах разброса между проходами. Новые затраты D по коду:

- проверка наличия `.editorconfig` по каталогам вверх и трёх `RoslynMcp.jsonc`;
- разбор `.editorconfig` с кэшем по времени изменения;
- линейные проверки и декодирование готовых байтов каждым известным читателем;
- разбор синтаксиса — только для скриптов с `#!`.

По сравнению с 1.6.5 запись стала примерно в 100 раз быстрее: при каждой записи больше не вычисляется MSBuild.
