## Серия

P2-17, P2-25, P1-33, P2-35, P1-40, P2-41, P1-45, P2-46, P2-48, P2-52 из [ревью 25 ноября](../project-review-2026-11-25/README.md). Восемь коммитов этого диапазона меняли [VstestOutputParser.cs](../../Diagnostics/VstestOutputParser.cs). Сейчас в нём 1 643 строки и около двадцати регулярных выражений.

Каждая карточка добавляла эвристику для очередного варианта текста:

- потеря имени теста;
- `Total tests: Unknown`;
- несовпадение фильтра рядом с ошибкой MSBuild;
- смешанные форматы сводки;
- равные итоги разных последовательных запусков;
- полный путь сборки в сообщении о несовпадении;
- сводка без строк с именами тестов.

## Причина серии

Итог запуска выводится из текста, предназначенного для человека. Формат зависит от версии VSTest, адаптера, числа TFM и порядка запусков. После P2-07 вывод хранится в ограниченном объёме, поэтому итоги частично восстанавливаются как нижние границы (`ReadRetainedLowerBounds`).

Структурированный результат в проекте уже есть, но не используется для итога:

- [TestImpactRunner.cs:181](../../Services/Testing/TestImpactRunner.cs) передаёт `--logger trx`, но TRX не читает и удаляет каталог результатов;
- [TrxResults.cs](../../spikes/AffectedTestsProbe/Oracle/TrxResults.cs) в spike уже читает `UnitTestResult`;
- [EstimateAffectedTestsParallelRunTests.cs](../../RoslynMcpServer.Tests/Testing/EstimateAffectedTestsParallelRunTests.cs) разбирает TRX в тестах.

## Варианты

| | A. TRX | B. Собственный логгер | C. Оставить разбор консоли |
|---|---|---|---|
| Суть | `--logger trx --results-directory <tmp>`. Итог и падения читаются из `ResultSummary` и `UnitTestResult` каждого файла. Консоль используется только для ошибок до testhost: сборка, restore, сообщение о несовпадении фильтра | Логгер VSTest (`ITestLoggerWithParameters`) поставляется с сервером и пишет JSON. Подключается через `--test-adapter-path` | Новые форматы закрываются новыми эвристиками |
| Плюсы | Штатный формат, один файл на сборку и TFM. Не зависит от ограничения вывода. Читатель TRX уже существует | Полный контроль над данными | Нет изменений |
| Минусы | Нужно сопоставлять файлы с проектами и TFM. Поведение при аварии testhost нужно проверить | Ещё одна поставляемая сборка и её совместимость с версиями VSTest | Серия продолжится |

**Рекомендация:** A.

### Вопросы для spike варианта A

Проверить на реальных проектах до реализации:

1. Какой TRX остаётся после аварии testhost. Есть ли файл, какой `outcome` у `ResultSummary`. Сценарий P1-33.
2. Имена файлов при нескольких TFM без `LogFileName`, чтобы файлы не перезаписывали друг друга. Сценарии P2-41 и P2-46.
3. Как сопоставить TRX с проектом и TFM: элемент `TestRun` и путь `storage` у `UnitTest`. Сценарий P2-48.
4. Фильтр без совпадений: создаётся ли TRX с нулём тестов. Сценарии P1-40 и P1-45.

### Правило итога для варианта A

- TRX есть у каждого ожидаемого запуска → итог и падения из TRX. Консоль добавляет только диагностику.
- TRX отсутствует у какого-либо запуска → инструмент не сообщает успех. Причина берётся из кода выхода и хвоста консоли.
- Ненулевой код выхода при успешных TRX → итог `partial` с причиной.

## Граница

- Только VSTest. Microsoft Testing Platform пишет TRX через `--report-trx` и расширение `Microsoft.Testing.Extensions.TrxReport`. Это относится к теме [test-runner-selection](../test-runner-selection/README.md).
- `get_test_list` и Rapid TIA не меняются. Чтение TRX в `TestImpactRunner` допустимо отдельной задачей после этой.
