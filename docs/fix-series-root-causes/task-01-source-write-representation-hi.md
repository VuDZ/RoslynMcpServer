## Серия

P1-44 задала верный контракт: записанные байты при свежем чтении с настройками проекта дают запрошенный текст. Сохранять кодировку и BOM нужно, когда это не противоречит контракту.

## Причина серии

Код пытается **доказать**, что файл без BOM каждый читатель прочтёт одинаково. Для этого он:

- сверяет метаданные загрузки с повторной design-time оценкой ([SolutionManager.cs](../../Services/Workspace/SolutionManager.cs), `EnsureSourceReadersAreCurrentUnderLockAsync`);
- статически разбирает обычную сборку MSBuild по белым и чёрным спискам: свойства, цели, `.rsp`, точки входа Test SDK, элементы диспетчеризации TFM (`WorkspaceBuildSourceReaders.cs` в исходном `d8eb8da`);
- отдельно учитывает национальные варианты 7-битного ASCII по ISO-646 (`SourceTextEncoding.IsInvariantAscii`).

Пространство способов, которыми MSBuild может задать `CodePage` для Csc, не ограничено. Каждый раунд находил новый способ: смена `CodePage` после загрузки (P1-47), условие на `DesignTimeBuild` (P1-49). Исправление P1-49 затем сломало Windows CI: импорты workloads загружаются в режиме read-only, упали 75 unit-тестов, 25 TIA и 3 AnalyzerLifecycle ([отчёт](../project-review-2026-11-25/evidence/tasks-49-54-validation.md#windows-ci-и-импорты-msbuild-в-режиме-read-only)).

### Стоимость текущего подхода

По коду, без замера. Проверка запускается при каждой записи `.cs` без BOM, включая текст только из ASCII:

- полная запись — `SolutionManager.cs:2392` и `:2643`;
- патч — `SolutionManager.cs:2077`.

Каждый раз выполняются `dotnet --version` с трассировкой хоста (`DotNetSdkResolver.ResolveAsync`) и вычисление MSBuild для всех C#-проектов решения. Любой сбой этой проверки отклоняет правку.

### Что уже работает в пользу простого правила

BOM — единственное представление, которое Csc читает одинаково при любой `CodePage`. Код уже переходит на UTF-8 с BOM, когда доказательство не удалось (`SolutionManager.cs:2272`).

## Варианты

Общее для A и B:

1. Результат целиком из ASCII и `CodePage` читающих проектов совместима с ASCII → писать без BOM, без вычисления MSBuild. Значение `CodePage` берётся из метаданных загрузки.
2. В результате есть не-ASCII → сохранить существующий BOM или записать UTF-8 с BOM.
3. Файл начинается с `#!` и содержит не-ASCII → явный отказ до записи. Shebang требует байтов `23 21` в начале файла (P1-44).
4. Чтение текущих байтов для патча остаётся дешёвым: BOM, затем `CodePage` из метаданных загрузки или определение, как у Roslyn (P1-29, P1-37). Вычисление MSBuild здесь не нужно.

Варианты различаются только случаем устаревшего файла без BOM, в котором не-ASCII байты остаются вне правки.

| | A. Конвертировать | B. Отказывать | C. Сузить доказательство |
|---|---|---|---|
| Устаревший файл без BOM с не-ASCII вне правки | Весь файл переписывается в UTF-8 с BOM. Текст берётся из прочитанного под замком представления | Явный отказ до записи с причиной. Агент может попросить пользователя конвертировать файл | Как сейчас |
| Что удаляется | `WorkspaceBuildSourceReaders`, сверка читателей, проверки ISO-646 | То же | Ничего. Добавляются исключение для ASCII и кэш оценки по отметкам времени файлов проекта |
| Плюсы | Правка всегда возможна. Код короче | Нет неожиданного изменения всех байтов файла | Сохраняется текущее поведение для файлов без BOM |
| Минусы | Шум в diff: BOM в новых файлах и полная конвертация устаревших. Отменяет пункт P1-44 о сохранении представления | Правка таких файлов недоступна без участия человека | Серия продолжится. Каждый новый способ задать `CodePage` — новая карточка |

**Рекомендация:** A или B. Выбор — решение владельца O-01: допустима ли полная конвертация устаревшего файла.

**O-01, 2026-11-26.** Выбран вариант B. При отказе `apply_patch` объясняет риск интерпретации нетронутого не-ASCII в файле без BOM и сообщает, что файл остался без изменений. Агент может уточнить исходную кодировку и согласовать конвертацию с пользователем. После согласия он может передать проверенный полный текст в `update_file_content`. Если нужно сохранить старую кодировку, сообщение предлагает явно выбрать её в редакторе.

**Пересмотр O-01, 2026-11-26.** Выбран вариант D. [Независимая проверка](evidence/task-01-review-2026-11-26.md#f-01) показала, что B отклоняет патчи и в обычных UTF-8 файлах без BOM. В этом репозитории так ведут себя 54 production-файла. Причина отказа — добавление BOM. Без BOM байты вне замены сохраняют смысл для любого читателя. Вариант D сохраняет кодировку файла без BOM, если в нём уже есть не-ASCII, как это делает редактор. UTF-8 с BOM остаётся для первого не-ASCII в файле без других признаков кодировки. Правило, ограничения и критерии — в [task-04](task-04-source-write-editor-semantics-hi.md).

Ограничение вариантов A и B: `CodePage`, несовместимая с ASCII (UTF-16, EBCDIC), считается неподдерживаемой, запись без BOM для неё отклоняется. Изменение `CodePage` после загрузки до значения, несовместимого с ASCII, не отслеживается.
