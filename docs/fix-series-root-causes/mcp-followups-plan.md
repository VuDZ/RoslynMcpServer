# План исправлений M-1–M-4 и F-4

Дата 2026-11-26. Статус **запланировано**. База проверки `8594643`. Все пять сценариев подтверждены на Windows через Roslyn MCP 1.7.0. [Замечания M-1–M-4](evidence/task-03-review-claude-2026-11-26.md#замечания-к-mcp) · [Замечание F-4](evidence/task-04-review-claude-2026-11-26.md#f-4)

Сначала M-3 и F-4, затем M-1 и M-4, затем M-2. M-1, M-4 и M-2 можно выполнять параллельно. Для M-3 и F-4 предусмотрены отдельные изменения политики репозитория и диагностики сервера.

## 1. M-3 и F-4. Кодировка C# и подсказка при отказе

- **M-3.** Добавить в корневой `.editorconfig` секцию `[*.cs]` с `charset = utf-8`. В проверенной базе вне `forks/` 933 отслеживаемых `.cs` в UTF-8 без BOM и 40 с BOM. Корневая настройка задаёт формат для будущих записей, а изменения байтов существующих исходников оформляются отдельной работой при необходимости. Вложенные правила `.editorconfig` в `forks/` имеют собственную область действия.
- **F-4.** Сохранить проверку неоднозначных байтов для неизвестного читателя. В диагностике на этапах сопоставления и записи объяснить, что кодировка исходника без BOM неизвестна. Предложить загрузить проект-владелец или объявить известную кодировку через `charset` или `sourceEncoding`. Разрешение операции по-прежнему опирается на проверки кодировки и итоговых байтов. [Чтение фрагмента](../../Services/Workspace/SolutionManager.cs#L2043) · [Выбор кодировки записи](../../Services/Workspace/SolutionManager.cs#L2348)
- **Приёмка через MCP.** Без загруженного решения `update_file_content` создаёт новый `.cs` без BOM при объявленном UTF-8. `apply_patch` применяет фрагмент с фигурными скобками к существующему UTF-8 без BOM, а при правке файла с BOM сохраняет его. На копии без объявления и загруженного владельца тот же патч возвращает обе подсказки и сохраняет исходные байты. После загрузки владельца с совместимой кодировкой патч проходит. Регрессии для конфликтующего `CodePage` и файла с `#!` подтверждают действующий контракт.

## 2. M-1. Диагностика отсутствующей тестовой сборки

- Воспроизвести `run_test_by_filter` без загруженного решения на тестовом проекте, у которого собран только `Release`. В общей обработке запуска без сборки выделить подтверждённое отсутствие тестовой сборки из уже имеющихся данных запуска. Использовать точный путь из диагностики VSTest или данные ожидаемого запуска, когда они доступны. Если причина неизвестна, использовать общую диагностику.
- В основном сообщении показать отсутствующий файл и эффективную конфигурацию. Предложить передать `noBuild=false` либо выбрать конфигурацию, в которой сборка уже существует. Использовать действующие значения по умолчанию и считать результаты по TRX. [Вход `run_test_by_filter`](../../Tools/TestTools.cs#L331)
- **Приёмка через MCP.** При отсутствии DLL сообщение называет `Debug` и файл, запуск остаётся ошибкой. Повтор с `configuration = Release` проходит. Обычное падение теста, фильтр без совпадений, отсутствующий TRX и частичный результат нескольких запусков сохраняют собственную диагностику и корректные счётчики.

## 3. M-4. Сборка фильтра решения

- Принять `.slnf` как цель `run_dotnet_build` и передавать сам фильтр штатному `dotnet build` с обычными настройками этого инструмента. Область работы — сборка всего фильтра. При `projectName` вернуть явную подсказку убрать параметр или передать `.sln` либо `.slnx`.
- **Приёмка через MCP.** Вызов `run_dotnet_build` собирает валидные `.slnf` над `.sln` и `.slnx` на SDK репозитория. Проверить, что проект вне фильтра не попадает в сборку, а отсутствующий или повреждённый фильтр выдаёт понятную ошибку. Контрольные прогоны покрывают обычную сборку `.sln` и `.slnx` и обработку `projectName`. [Проверка расширения и сборка](../../Tools/BuildTools.cs#L76)

## 4. M-2. Идентификация запущенной сборки

- В `get_mcp_server_info` отдельно вывести путь процесса и путь загруженной сборки. Показать время изменения файла сборки на диске и информационную версию, которая различает сборки с одной версией `AssemblyVersion`. Для однофайлового пакета использовать время исполняемого файла пакета, если он несёт сборку, и явно указать этот случай. Если путь определить невозможно, показать, что данные недоступны. [Формирование отчёта](../../Services/McpServerInfoHelper.cs#L93)
- **Приёмка через MCP.** Проверить запуск через опубликованный `.exe` и через `dotnet RoslynMcpServer.dll`. При запуске DLL путь процесса указывает на `dotnet.exe`, а путь и время сборки совпадают с DLL. Версия и идентификатор сборки берутся из загруженного сервера.
