## 1. M-3. Объявленная кодировка C# в репозитории

- **Причина.** Сервер работает по правилу D: без объявления новый `.cs` получает BOM. В репозитории нет объявления, хотя вне `forks/` 933 отслеживаемых `.cs` записаны в UTF-8 без BOM и только 40 с BOM. Это не дефект сервера, а отсутствие объявления.
- **Исправление.** Создать корневой `.editorconfig` с секцией `[*.cs]` и `charset = utf-8`. Существующие 40 файлов с BOM не переписывать, при необходимости это отдельная работа. `dotnet format` в CI не запускается, поэтому существующие файлы проверку не сломают. У `forks/roslyn-buildhost/upstream/.editorconfig` свой `root = true` и `charset = utf-8-bom`, его область не меняется.
- **Следствие для полевых проверок.** С объявлением F-4 в этом репозитории больше не проявится. Сценарии F-4 проверяются на отдельной фикстуре без объявления.
- **Приёмка через MCP.** Без загруженного решения `update_file_content` создаёт новый `.cs` без BOM. `apply_patch` применяет фрагмент с фигурными скобками к существующему UTF-8 без BOM, а при правке файла с BOM сохраняет BOM.

## 2. F-4. Кодировка читателя без загруженного решения

- **Причина.** Сервер узнаёт `CodePage` владельца только из метаданных загруженного решения: [GetSourceCodePagesUnderLock](../../Services/Workspace/SolutionManager.cs#L2194). Без загрузки читатель неизвестен, и `apply_patch` отклоняет любой фрагмент со скобками в BOM-free файле: [чтение фрагмента](../../Services/Workspace/SolutionManager.cs#L2043), [запись без владельца](../../Services/Workspace/SolutionManager.cs#L2348). Подсказка в сообщении не убирает отказ, а только объясняет его.
- **Исправление.** Для неоднозначного патча C# без BOM и объявления кодировки при незагруженном workspace вычислять `Compile` и `CodePage` через MSBuild `ProjectCollection`. [Поиск читателей](../../Services/Workspace/UnloadedSourceReaders.cs)
  - Граница поиска проходит по ближайшему checkout Git или найденному дереву решения либо проекта. Учитываются вычисленные `Compile Include`, ссылки `ProjectReference`, проекты из решений и их отображения конфигураций, платформ и TFM.
  - Перед записью повторно проверить байты и актуальных читателей. Известные читатели проходят общую проверку, включая конфликт с появившимся объявлением. Обычный патч с объявленной кодировкой опирается на правило D.
- **Неопределённость.** При неполном поиске, нестандартной компиляции, сомнительном алиасе или конфликте читателей сервер сохраняет исходные байты. Для неизвестного читателя сообщает, как загрузить владельца или объявить кодировку через `charset` либо `sourceEncoding`. Скрипты с `#!` следуют своему контракту.
- **Приёмка через MCP.** Фикстура без объявления кодировки, решение не загружено:
  - `apply_patch` с фигурными скобками в проекте без `CodePage` проходит;
  - в проекте с конфликтующим `CodePage` и в файле с `#!` действует прежний контракт;
  - для `.cs` вне любого проекта возвращается подсказка, исходные байты сохраняются.
  - После загрузки владельца результат тот же, что и без загрузки.

### Решение владельца 2026-11-27

Решение заменяет пункты «Исправление», «Неопределённость» и «Приёмка через MCP» выше. Они остаются как история.

- **Основание.** Поиск читателей без загрузки обходит checkout и дважды вычисляет проекты в MSBuild на каждый неоднозначный патч. На решении из 61 проекта это 5–12 с на одну правку. Целевые репозитории коллег значительно больше лимитов 128 проектов и 4 096 каталогов, поэтому там отказ приходит после того же ожидания. Правило по самому фрагменту («вариантный байт уже есть в файле») отклонено: в проекте с `CodePage=20105` вставленный `$` читается как `¤`, а контракт требует точного чтения запрошенного текста. [Повторная проверка](evidence/mcp-followups-validation.md#повторная-проверка-2026-11-27)
- **Решение.** Если читатель файла неизвестен, правка отклоняется сразу, без вычислений MSBuild. Сообщение явно говорит агенту сначала загрузить решение.
- **Когда читатель неизвестен.** Одновременно выполнены все условия: файл C# без BOM, нет объявления `charset` или `sourceEncoding`, нет загруженного проекта, в который входит файл. Последнее условие означает, что решение не загружено или загружено другое. Фрагмент или файл неоднозначны по нынешним правилам: вариантные символы ISO-646, не-ASCII в файле, переключающие последовательности HZ или UTF-7.
- **Что не меняется.** Без загрузки по-прежнему выполняются правки файлов с BOM, файлов с объявленной кодировкой, файлов не на C#, патчи из инвариантного ASCII и создание новых файлов по правилу D. Скрипты с `#!` следуют своему контракту.
- **Сообщение.** Первым действием называется `load_workspace` для решения, которое содержит файл. Если загружено другое решение, сообщение называет его путь и говорит, что файл в него не входит. Вторым вариантом, для владельцев репозитория, указывается постоянное объявление: секция `[*.cs]` с `charset` в корневом `.editorconfig` или `sourceEncoding` в `RoslynMcp.jsonc`. Исходные байты не меняются.
- **Объём.**
  - Убрать `UnloadedSourceReaders` и его вызовы на пути записи вместе с тестами, которые проверяют только поиск: `UnloadedSourceReaderBudgetTests`, `UnloadedTestSdkSourceReaderTests` и сценарии поиска в `WorkspaceWriteEncodingTests`. `MicrosoftTestSdkProgramTarget` остаётся для M-1.
  - Проверить `update_file_content` для существующего файла без BOM с неизвестным читателем. По коду (`SelectUndeclaredWriteEncoding`) такая запись получает BOM. Привести её к тому же правилу или, если это меняет принятый контракт task-04, вынести вопрос владельцу до реализации.
  - Исправить запись F-4 в `CHANGELOG.md` для 1.7.1, версия ещё не выпущена.
- **Приёмка через MCP.** Фикстура без объявления кодировки:
  - без загрузки `apply_patch` с `{ }` отклоняется за миллисекунды, байты сохраняются, сообщение называет `load_workspace`. Это проверяется и в репозитории с Test SDK, и в репозитории больше 128 проектов;
  - при загруженном другом решении отказ называет загруженное решение;
  - после `load_workspace` владельца тот же патч проходит;
  - с `charset = utf-8` в `.editorconfig` патч проходит без загрузки;
  - файлы с BOM, `CodePage=1251` с ASCII-фрагментом, `#!` и патчи из инвариантного ASCII ведут себя как раньше.

## 3. M-1. Отсутствующая тестовая сборка

- **Причина.** Причин две.
  - **Разные значения по умолчанию.** Без `noBuild` `run_test_by_filter` пропускает сборку, а `run_dotnet_test` и `run_specific_test` пересобирают: [TestTools.cs](../../Tools/TestTools.cs#L39). Без загруженного решения конфигурация не наследуется, и у пропуска сборки нет основания.
  - **Нет проверки до запуска.** Маршрут через DLL проверяет выход до запуска и возвращает отказ `output missing`: [TestDllEnsure.cs](../../Services/Build/TestDllEnsure.cs#L370) с `TestAssemblyPathResolver.FormatAssemblyNotFound`. Обычный маршрут такой проверки не имеет, поэтому до пользователя доходит «The argument … is invalid» от VSTest.
- **Исправление.**
  - На обычном маршруте с пропуском сборки до запуска определить ожидаемые тестовые сборки. Для проекта это вычисленный `TargetPath` для эффективной конфигурации, платформы и TFM, для решения — по каждому тестовому проекту. Если какой-то сборки нет, вернуть тот же отказ, что и маршрут через DLL: файл, эффективная конфигурация, `noBuild=false` или конфигурация с готовой сборкой. Тесты не запускаются.
  - Решить и записать, какое значение по умолчанию у `noBuild` в `run_test_by_filter`, когда конфигурация не передана и не унаследована от `load_workspace`. Вариант: в этом случае собирать, как два других инструмента.
  - Разбор вывода VSTest после запуска не вводить. Серия task-02 перешла на TRX и опись запусков, консольный текст остаётся только для показа.
- **Приёмка через MCP.** Без загруженного решения, когда собран только `Release`:
  - `run_test_by_filter`, `run_specific_test` и `run_dotnet_test` с пропуском сборки называют файл и `Debug`, и тесты не запускаются;
  - повтор с `configuration = Release` проходит.
  - Обычное падение теста, фильтр без совпадений, отсутствующий TRX и частичный результат нескольких запусков сохраняют собственную диагностику и счётчики.
  - Замер: проверка до запуска не добавляет заметного времени к прогону на решении владельца.

## 4. M-4. Фильтр решения как вход

- **Причина.** Нет единого определения входа «решение». Проверка `.sln`/`.slnx` написана независимо примерно в 13 местах, `.slnf` знает только [BuildHostOptimizations](../../Services/Workspace/BuildHostOptimizations.cs#L95). Среди этих мест:
  - [BuildTools.cs](../../Tools/BuildTools.cs#L81) и [TestTools.cs](../../Tools/TestTools.cs#L588) — `run_dotnet_build` и `run_dotnet_test` отклоняют `.slnf`;
  - [DotNetConfigurationArguments.UsesSolutionPlatformNaming](../../Services/Build/DotNetConfigurationArguments.cs#L59) — `.slnf` получит правила имён платформ проекта;
  - `TestAssemblyPathResolver`, `SolutionConfigurationCatalog`, `WorkspaceInputMapBuilder`, `WorkspaceDiskPathFilter`, `WorkspaceLoadGuidance`, `SolutionProjectTargetResolver`, `AnalyzerProvenanceCaptureService`.
  Если добавить `.slnf` только в список `run_dotnet_build`, унаследованная платформа `Any CPU` превратится в `AnyCPU`, и MSBuild отклонит конфигурацию решения (MSB4126).
- **Исправление.** Ввести одно определение вида входа: проект, решение или фильтр решения. Перевести на него все перечисленные проверки. Для каждого места записать, как оно обрабатывает фильтр:
  - имена платформ — как у решения;
  - сборка и тесты — сам фильтр передаётся `dotnet build` и `dotnet test`;
  - `projectName` и маршрут `binariesPath` используют полное решение, а вызов с фильтром возвращает подсказку передать подходящую цель или собрать весь фильтр;
  - конфигурации — из фильтруемого решения.
  Для семантической работы `load_workspace` принимает полное решение из `solution.path`. Запрос с `.slnf` отклоняется до изменения загруженного решения. При отсутствии совпадений тестов подсказка просит сначала сверить выбранные проекты и их зависимости.
- **Приёмка через MCP.**
  - `run_dotnet_build` и `run_dotnet_test` работают с `.slnf` над `.sln` и `.slnx`, в том числе с унаследованной от `load_workspace` платформой `Any CPU`.
  - Проект вне фильтра не собирается.
  - Отсутствующий или повреждённый фильтр даёт понятную ошибку.
  - Контрольные прогоны покрывают `.sln`, `.slnx`, `.csproj` и `projectName`.

## 5. M-2. Идентификация запущенной сборки

- **Причина.** [McpServerInfoHelper.cs](../../Services/McpServerInfoHelper.cs#L92) показывает `Environment.ProcessPath` и его время как данные сервера. При запуске через `dotnet <dll>` это хост `dotnet`.
- **Исправление.**
  - Раздельно вывести путь процесса и путь загруженной сборки сервера.
  - Показать время изменения файла сборки и информационную версию, которая различает сборки с одной `AssemblyVersion`.
  - Для однофайлового пакета взять время исполняемого файла пакета и явно указать этот случай. Если путь определить нельзя, показать, что данные недоступны.
  - В том же отчёте заменить жёсткую подсказку «run `dotnet publish -c Release -r linux-x64`, then Reload MCP in Cursor» на нейтральную: опубликовать сервер и переподключить MCP-клиент, без привязки к RID и клиенту.
- **Приёмка через MCP.** Запуск через опубликованный исполняемый файл и через `dotnet RoslynMcpServer.dll`. При запуске DLL путь процесса указывает на `dotnet`, а путь и время сборки совпадают с DLL. Версия и идентификатор сборки берутся из загруженного сервера.
