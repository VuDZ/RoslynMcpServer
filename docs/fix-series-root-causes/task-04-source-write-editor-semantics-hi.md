## Основание

Вариант B из task-01 отклоняет `apply_patch`, когда в `.cs` без BOM вне замены остаётся не-ASCII. Это касается и обычного UTF-8 файла в SDK-проекте с `CodePage` по умолчанию: так ведёт себя `ApplyPatch_requires_explicit_conversion_when_non_ASCII_stays_outside_the_matches`.

В этом репозитории 921 из 959 файлов `.cs` вне `forks/` записаны без BOM. В 54 production-файлах есть не-ASCII, в основном `—`, `→` и кириллица в комментариях. Среди них `SolutionManager.cs`, `UtilityTools.cs`, `TestTools.cs`, `VstestOutputParser.cs`. Для этих файлов `apply_patch` практически недоступен. Обход через `update_file_content` молча добавляет BOM. [Проверка task-01](evidence/task-01-review-2026-11-26.md#f-01).

### Почему отказ B не нужен для нетронутого текста

Причина отказа в B — сам BOM. Комментарий в коде: «Adding a BOM would commit one interpretation of text the caller did not replace». Если оставить файл без BOM и в той же кодировке, байты вне замены не меняются. Любой читатель прочтёт их так же, как до правки: Roslyn, обычная сборка, сборка с другой `CodePage` из P1-49. Единственное исключение — автоопределение при `CodePage=0`, когда правка меняет валидность UTF-8 всего файла (сценарий 2 из P1-44). Это проверяется по байтам.

Риск P1-49 остаётся только для нового не-ASCII текста. Если сборка читает файл не так, как Roslyn, его существующий не-ASCII текст уже читается так же неверно. Правка в той же кодировке ведёт себя как сохранение файла в VS, Rider или VS Code: эти редакторы сохраняют кодировку файла и не добавляют BOM.

## Правило D

«Нетронутый не-ASCII» — не-ASCII в тексте вне заменённых диапазонов патча (`hasUntouchedNonAscii` из task-01). Для `update_file_content` — не-ASCII в текущем содержимом существующего файла без BOM.

| Файл | Запись |
|---|---|
| С BOM | Сохранять кодировку и BOM, как сейчас. |
| Без BOM, есть нетронутый не-ASCII | Та же кодировка, в которой файл прочитан под замком, без BOM. Отказа нет. Если новый текст в ней непредставим: патч отклоняется до записи (P1-30), полная запись переводит файл в UTF-8 с BOM, как в B. |
| Без BOM, нетронутого не-ASCII нет, результат из ASCII | Без BOM, как в task-01. |
| Без BOM, нетронутого не-ASCII нет, результат с не-ASCII | UTF-8 с BOM, как в B. Других признаков кодировки у файла нет, а BOM снимает риск P1-49. |
| Скрипт с `#!` в начале | Всегда без BOM. Если есть нетронутый не-ASCII, кодировка сохраняется. Если не-ASCII вносится впервые, запись в UTF-8 без BOM. Отказ task-01 для не-ASCII скрипта снимается. |
| `CodePage=0`, файл прочитан в кодировке системы (не UTF-8) | Отказ до записи, если результат в этой кодировке стал бы валидным UTF-8 с байтами ≥ `0x80`. Компилятор прочитал бы весь файл иначе (сценарий 2 из P1-44). |

Не меняется:

- чтение для патча: BOM, `CodePage` загрузки, автоопределение, строгий декодер, отказ при разном тексте у нескольких загруженных читателей;
- вычисление MSBuild при записи не возвращается;
- дешёвые проверки национальных вариантов ASCII (ISO-646, HZ) для файлов без известного владельца;
- атомарность, жёсткие ссылки, устаревший снимок (P2-13, P1-28, P2-53).

## Принятые ограничения

- Сборка читает файл не в той кодировке, что Roslyn (P1-49). Новый не-ASCII в файле, где не-ASCII уже есть, сборка прочтёт так же, как существующий.
- Файл в кодировке системы при `CodePage=0`: новые символы кодируются кодовой страницей машины, где работает сервер. На машине сборки с другой кодовой страницей текст прочтётся иначе.
- Наличие не-ASCII в файле — слабое свидетельство того, как сборка его читает: неверно прочитанный комментарий ничего не ломает. Правило опирается на семантику редактора, а не на доказательство.
- Запрет записи без BOM для `CodePage`, несовместимой с ASCII, сохраняется из task-01.

## Вне объёма

- Семантические правки (`update_method_body`, `rename_symbol`, `add_method_to_class`, исправления кода) пишут через `SourceTextEncoding.ResolveForWrite` и в task-01 не менялись. Если правило D нужно и для них, это отдельная задача.
- Флаг «никогда не добавлять BOM» для репозиториев, которые гарантируют UTF-8, можно добавить позже как необязательное ужесточение. Основное поведение работает без него.
