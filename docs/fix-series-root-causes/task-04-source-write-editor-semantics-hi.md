## Основание

Вариант B из task-01 отклоняет `apply_patch`, когда в `.cs` без BOM вне замены остаётся не-ASCII. Это касается и обычного UTF-8 файла в SDK-проекте с `CodePage` по умолчанию: так ведёт себя `ApplyPatch_requires_explicit_conversion_when_non_ASCII_stays_outside_the_matches`.

В этом репозитории 921 из 959 файлов `.cs` вне `forks/` записаны без BOM. В 54 production-файлах есть не-ASCII, в основном `—`, `→` и кириллица в комментариях. Среди них `SolutionManager.cs`, `UtilityTools.cs`, `TestTools.cs`, `VstestOutputParser.cs`. Для этих файлов `apply_patch` практически недоступен. Обход через `update_file_content` молча добавляет BOM. [Проверка task-01](evidence/task-01-review-2026-11-26.md#f-01).

### Почему отказ B не нужен для нетронутого текста

Причина отказа в B — сам BOM. Комментарий в коде: «Adding a BOM would commit one interpretation of text the caller did not replace». Если оставить файл без BOM и в той же кодировке, байты вне замены не меняются. Читатель с фиксированной кодировкой прочтёт их так же, как до правки: Roslyn, обычная сборка, сборка с другой `CodePage` из P1-49.

Исключение — читатель с автоопределением. Он читает весь файл как UTF-8, если байты валидны, и в кодировке системы, если нет. Правка, которая меняет валидность UTF-8 всего файла, меняет и смысл нетронутых байтов. Это возможно при любой загруженной `CodePage`: обычная сборка может использовать автоопределение, даже если design-time задаёт явную страницу (сценарий 2 из P1-44, R-1 ревью). Это проверяется по байтам, см. [Проверки готовых байтов](#проверки-готовых-байтов).

Риск P1-49 остаётся для нового не-ASCII текста. Если сборка читает файл не так, как Roslyn, его существующий не-ASCII текст уже читается так же неверно. Правка в той же кодировке ведёт себя как сохранение файла в VS, Rider или VS Code: эти редакторы сохраняют кодировку файла и не добавляют BOM. Снять этот риск может только явное [объявление кодировки](#объявленная-кодировка).

## Правило D

«Нетронутый не-ASCII» — не-ASCII в тексте вне заменённых диапазонов патча (`hasUntouchedNonAscii` из task-01). Для `update_file_content` — не-ASCII в текущем содержимом существующего файла без BOM.

Правило действует, если для файла не объявлена кодировка. Объявленная кодировка имеет приоритет.

| Файл | Запись |
|---|---|
| С BOM | Сохранять кодировку и BOM, как сейчас. |
| Без BOM, есть нетронутый не-ASCII | Та же кодировка, в которой файл прочитан под замком, без BOM. Если новый текст в ней непредставим: патч отклоняется до записи (P1-30), полная запись переводит файл в UTF-8 с BOM, как в B. |
| Без BOM, нетронутого не-ASCII нет, результат из ASCII | Без BOM, как в task-01. |
| Без BOM, нетронутого не-ASCII нет, результат с не-ASCII | UTF-8 с BOM, как в B. Других признаков кодировки у файла нет, а BOM снимает риск P1-49. Ответ инструмента сообщает о добавленном BOM и о том, как объявить кодировку, чтобы его не было. |
| Скрипт с `#!` в начале | См. [Скрипты](#скрипты-с-). |

В каждой строке, где запись идёт без BOM, перед записью выполняются [проверки готовых байтов](#проверки-готовых-байтов).

Не меняется:

- чтение для патча: BOM, `CodePage` загрузки, автоопределение, строгий декодер, отказ при разном тексте у нескольких загруженных читателей;
- вычисление MSBuild при записи не возвращается;
- дешёвые проверки национальных вариантов ASCII (ISO-646, HZ) для файлов без известного владельца;
- атомарность, жёсткие ссылки, устаревший снимок (P2-13, P1-28, P2-53).

## Проверки готовых байтов

Готовые байты формируются один раз и проверяются до записи на диск и до публикации снимка. Обе проверки дешёвые и не требуют MSBuild. Они действуют при любом источнике кодировки: правило D, объявление, директива скрипта.

1. **Смена автоопределения (R-1).** Сравнить валидность UTF-8 исходных и готовых байтов без BOM в обе стороны. Это выполняется независимо от загруженной `CodePage`. Если валидность меняется, а нетронутый не-ASCII есть, отказ до записи.
2. **Согласие известных читателей (R-2).** Строго декодировать готовые байты кодировкой каждого известного читателя: `CodePage` загрузки, для 0 — автоопределение по готовым байтам. Сравнить полный текст с запрошенным. Пример из ревью: `A7` одинаков в 1251 и 1252, а новый `C6` — это `Ж` в 1251 и `Æ` в 1252. При расхождении отказ до записи. Проверка распространяется на `update_file_content` и на ASCII-ветку task-01 (`ReadsLiteralAscii`).

Текст отказа называет конкретную причину. Он предлагает объявить кодировку или привести `CodePage` проектов к одной и выполнить `load_workspace`.

## Объявленная кодировка

Решение владельца 2026-11-26 по R-3. Сервер не может дёшево проверить, как файл прочтёт обычная сборка. Вместо этого пользователь или агент объявляют кодировку, в которой сохраняются исходники. Сервер следует объявлению и сверяет его с тем, что видно дёшево.

### Источники

Используется первый найденный источник, без смешивания:

1. **`.editorconfig`, ключ `charset`** для данного файла: `utf-8`, `utf-8-bom`, `latin1`, `utf-16le`, `utf-16be`. Это стандартный способ объявить кодировку сохранения. Его соблюдают VS, Rider и VS Code, а действие по каталогам поддерживает смешанные репозитории. [Spike](evidence/task-04-source-encoding-spike.md) подтвердил доступность `charset` в снимке. При записи Roslyn сопоставляет секции актуальной цепочки `.editorconfig` на диске одинаково для загруженных и новых файлов.
2. **`RoslynMcp.jsonc`, ключ `sourceEncoding`** по существующему порядку источников: exe → каталог пользователя → cwd ([user-data-directory](../user-data-directory/README.md#решения-владельца)). Значения: `utf-8`, `utf-8-bom` или имя либо номер кодовой страницы, например `windows-1251` или `1251`. Ключ нужен для кодировок, которых нет в `charset`, для глобального значения по умолчанию и для репозиториев, где менять `.editorconfig` нежелательно.

Объявление читается при каждой записи с кэшем по времени изменения файла. Перезагрузка решения нужна только при изменении `CodePage` в проекте. Неизвестное значение отклоняется с указанием файла и ключа.

### Поведение

| Случай | Запись |
|---|---|
| Файл с BOM | Сохранять кодировку и BOM. Объявление не переписывает BOM существующего файла. |
| Файл без BOM или новый файл | Объявленная кодировка: `utf-8` и кодовые страницы — без BOM, `utf-8-bom` и `utf-16*` — с BOM. BOM для первого не-ASCII не добавляется. |
| Существующий файл без BOM не декодируется строго в объявленной кодировке | Отказ до записи: файл не в объявленной кодировке. Исправить объявление или сконвертировать файл. |
| Явная `CodePage` загруженного проекта противоречит объявлению | Отказ до записи. Привести объявление и `CodePage` к одной кодировке и выполнить `load_workspace`. Обнаруживается проверкой 2. |
| Текст непредставим в объявленной кодировке | Отказ до записи (P1-30). |

[Проверки готовых байтов](#проверки-готовых-байтов) выполняются и при объявлении.

## Скрипты с `#!`

Shebang требует `#!` с нулевого байта, поэтому BOM в скрипте недопустим.

- Файловое приложение может задать кодировку директивой `#:property CodePage=N` (R-4). Директива читается из текста файла и для скрипта имеет приоритет над объявлением. Скрипт записывается в этой кодировке без BOM. Если кодировка несовместима с ASCII, отказ.
- Без директивы: объявленная кодировка, если она без BOM. Иначе UTF-8 без BOM. Если не-ASCII уже есть, кодировка файла сохраняется.
- Отказ task-01 для не-ASCII скрипта снимается. Проверки готовых байтов действуют.

## Принятые ограничения

- Сборка читает файл не в той кодировке, что Roslyn (P1-49). Без объявления новый не-ASCII в файле, где не-ASCII уже есть, сборка прочтёт так же, как существующий. Нетронутый не-ASCII может быть только в комментарии, поэтому его наличие — слабое свидетельство (пример F-03 в ревью). При объявлении ответственность за соответствие обычной сборки лежит на объявившем. `CodePage`, заданная только для обычной сборки, не обнаруживается.
- Файл в кодировке системы при `CodePage=0`: новые символы кодируются кодовой страницей машины, где работает сервер. На машине сборки с другой кодовой страницей текст прочтётся иначе.
- Запрет записи без BOM для `CodePage`, несовместимой с ASCII, сохраняется из task-01.

## Вне объёма

- Семантические правки (`update_method_body`, `rename_symbol`, `add_method_to_class`, исправления кода) пишут через `SourceTextEncoding.ResolveForWrite`. Применение к ним правила D и объявленной кодировки — отдельная задача.
- Автоматическое изменение `.editorconfig` или `RoslynMcp.jsonc` сервером. Объявление пишут пользователь или агент.
