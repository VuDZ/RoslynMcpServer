# Сборка и публикация бинарных релизов в GitHub

Дата: 2026-09-21. Статус: **реализация начата**.
O-01 закрыт (`workflow_dispatch` + тег со стороны Actions). O-02 / O-03 и
унификация версий (O-04) по-прежнему открыты. Согласованный объём — раздел 3.

## 1. Задача

Собирать RoslynMcpServer в GitHub Actions и автоматически выкладывать готовые
дистрибутивы в GitHub Releases. Пользователю не должно требоваться собирать
сервер из исходников.

Нужно учитывать два сценария разработки:

- **Реализация по спеке:** несколько итераций и потенциально много коммитов,
  включая исправления после основной реализации.
- **Багфикс:** как правило, один законченный коммит.

Промежуточный коммит реализации не означает готовность к выпуску. Сигнал
готовности — ручной запуск workflow Release на SHA, уже лежащем в `main`
(см. решение O-01). Правила worktree (O-02) этим не закрываются.

## 2. Текущее состояние

Факты на дату документа, а не гарантия уже работающей релизной инфраструктуры:

- Есть [`.github/workflows/ci.yml`](../../.github/workflows/ci.yml) (сборка и
  тесты на `push`/`pull_request`, без публикации) и
  [`.github/workflows/release.yml`](../../.github/workflows/release.yml)
  (`workflow_dispatch`, `win-x64` self-contained и framework-dependent).
  Первый успешный публичный выпуск этим ещё не подтверждён.
- В [`RoslynMcpServer.csproj`](../../RoslynMcpServer.csproj) указаны `net10.0`,
  `PublishSelfContained=true`, `PublishSingleFile=false` и
  `PublishReadyToRun=true`. Обычная сборка имеет `SelfContained=false`.
- Там же перечислены RID: `win-x64`, `win-arm64`, `osx-arm64`, `linux-x64`,
  `linux-arm64`, `linux-musl-x64`. Наличие RID не подтверждает проверенную
  поддержку платформы.
- [`publish-and-verify.ps1`](../../publish-and-verify.ps1) публикует `win-x64`
  и формирует ZIP с корнем `RoslynMCP/`, README и исключением `logs/`.
  Проверку MCP после публикации скрипт предлагает выполнить вручную.
- Версия задаётся несколькими свойствами; `PackageVersion` отличается от
  `Version`. Унификация версий уже запланирована отдельно.
- [`Program.cs`](../../Program.cs) вызывает
  [`MsBuildBootstrapper.Register`](../../Diagnostics/MsBuildBootstrapper.cs)
  при старте. Сервер ищет установленный MSBuild/SDK; упаковка runtime сама
  по себе не устраняет эту зависимость.

## 3. Согласованные требования

### R-01. Сборка и размещение

Сборка дистрибутивов выполняется в GitHub Actions. После установленного сигнала
готовности автоматизация должна создать GitHub Release и приложить архивы.
Ручная локальная сборка и ручная загрузка файлов не должны быть обязательными
шагами штатного выпуска. Сигнал готовности — O-01.

### R-02. Платформы

Первый этап поддерживает **Windows x64 (`win-x64`)**.
Процесс должен допускать добавление других ОС и архитектур без отдельной
несвязанной схемы выпуска для каждой платформы.

Долгосрочная цель — расширить поддержку платформ. Точный список, минимальные
версии ОС и порядок подключения ещё не согласованы. Перечень RID в проекте
служит исходным списком кандидатов, а не обещанием поддержки всех окружений.

### R-03. Два варианта поставки

Для каждой платформы, включённой в выпуск, нужны два архива одной версии:

- **Self-contained (standalone):** исполняемый файл сервера, его зависимости
  и runtime .NET 10. Отдельная установка .NET 10 для выполнения самого
  сервера не требуется.
- **Framework-dependent:** исполняемый файл сервера и его зависимости без
  встроенного runtime. Требуется совместимый .NET 10 Runtime соответствующей
  архитектуры; установленный SDK 10 с этим runtime также удовлетворяет
  требованию.

В обоих вариантах на Windows сервер должен запускаться через поставляемый
`RoslynMcpServer.exe`. «Бинарная поставка» не означает обязательный один EXE:
архив содержит необходимые для работы файлы, включая зависимости Roslyn и
BuildHost. Single-file и Native AOT не являются требованиями этой задачи.

### R-04. SDK потребителя

Потребитель устанавливает SDK, необходимый для его проектов, включая
требования `global.json` и нужные workloads. Это ожидаемое условие работы
сервера, а не недостаток поставки.

Не требуется включать SDK в архивы или обеспечивать полноценную работу
с проектами на машине без SDK. Self-contained устраняет необходимость
устанавливать runtime .NET 10 для сервера, но не SDK проекта.

Целевой сценарий: сервер со встроенным runtime 10 работает с проектом,
использующим другую поддерживаемую версию SDK, без установки SDK/runtime 10
в систему. Совместимость Roslyn, BuildHost и MSBuild для конкретных версий
должна быть проверена; совместимость с любым существующим SDK не обещается.

### R-05. Завершённость изменения

Процесс выпуска должен позволять завершить многокоммитную реализацию до
публикации релиза. Не требуется создавать релиз для каждого промежуточного
коммита. Одиночный багфикс также должен проходить определённый путь выпуска.
Обязательность PR, squash, worktree и релиза после каждого merge не утверждена.

### R-06. Версии

Оба варианта поставки одного выпуска должны соответствовать одной версии
сервера и одному исходному коммиту. Версия GitHub Release, тега и дистрибутивов
должна быть согласована с результатом отдельно запланированной унификации
версий. Этот документ не выбирает новый источник версии или алгоритм её
увеличения.

## 4. Предлагаемое устройство выпуска

Этот раздел — исходное предложение для реализации; детали можно уточнить
без изменения согласованного объёма.

- Разделить проверки промежуточных изменений и публикацию готового выпуска.
  Успешная промежуточная сборка сама по себе не является сигналом релиза.
- Собирать оба варианта из одного зафиксированного commit SHA в конфигурации
  Release. Добавление платформ оформлять расширением матрицы сборок.
- Использовать однозначные имена, например
  `RoslynMcpServer-1.4.0-win-x64-self-contained.zip` и
  `RoslynMcpServer-1.4.0-win-x64-framework-dependent.zip`.
- Сохранять полную папку публикации с необходимыми зависимостями, README,
  лицензией и применимыми файлами установки; исключать логи и временные файлы.
- Публиковать релиз после успешных проверок и готовности всех обязательных
  архивов. Ошибка одного варианта не должна давать видимость полного выпуска.
  При использовании draft release переводить его в опубликованное состояние
  только после загрузки всех обязательных файлов.
- При повторном запуске идентифицировать тот же выпуск по версии и коммиту;
  не подменять опубликованные файлы другой сборкой молча. Уже опубликованный
  GitHub Release с тем же тегом — ошибка; черновик на том же SHA можно
  дописать и опубликовать.
- Текст GitHub Release собирается из сообщений коммитов после предыдущего
  тега `v*` (subject и body), не больше **16** самых новых; если коммитов
  больше, в notes это указывается. Доки/rules-only деревья по умолчанию не
  выпускаются.
- В описании скачивания рекомендовать self-contained для простой установки;
  framework-dependent предлагать как более компактный вариант при наличии
  .NET 10 Runtime.
- Zip выпуска получают GitHub Artifact Attestation (SLSA provenance) на job
  `publish`. Это не Authenticode. TRX из CI не аттестовать.
- Предусмотреть обслуживание встроенного runtime: нужные обновления .NET
  требуют новой self-contained поставки, даже если код сервера не менялся.

## 5. Предлагаемые критерии приёмки первого этапа

1. GitHub Actions собирает `win-x64` в обоих режимах из одного коммита.
2. Автоматически созданный опубликованный GitHub Release содержит два
   различимо названных архива с согласованной версией.
3. Проверяется именно распакованный дистрибутив за пределами исходного дерева,
   а не только результат `dotnet build` или запуск из каталога проекта.
4. Self-contained проверяется в окружении без установленного SDK/runtime 10,
   но с выбранным поддерживаемым SDK проекта другой версии. Конкретную версию
   SDK закрепить до реализации проверки. Обычный runner с SDK 10 не доказывает
   независимость дистрибутива от системного .NET 10.
5. Framework-dependent проверяется с установленными .NET 10 Runtime и SDK
   тестового проекта. Отсутствие runtime в архиве проверяется отдельно.
6. В обоих режимах проходят запуск процесса, MCP initialization, получение
   сведений о сервере, загрузка небольшого C#-проекта, семантический запрос и
   сборка проекта через инструмент сервера. Ошибки дочернего BuildHost также
   считаются неуспехом проверки.
7. Выполняются применимые проверки проекта; сбой обязательной проверки или
   сборки блокирует публикацию готового релиза.
8. Промежуточные коммиты и push в `main` не создают публичные релизы.
   Нужен `workflow_dispatch` (O-01). Проверяются сценарии многокоммитной
   задачи, пачки багфиксов и docs-only.
9. README выпуска объясняет различие архивов, требование SDK проекта и
   дополнительные требования framework-dependent варианта.

## 6. Открытые решения перед реализацией

### O-01. Сигнал выпуска — решено

Основной сигнал: ручной **Actions → Release → Run workflow**
(`workflow_dispatch`) на SHA, который уже есть в `origin/main`.
Workflow ставит тег `v{Version}` из `RoslynMcpServer.csproj` того коммита
(`GITHUB_TOKEN`) и публикует оба архива. Агент **не** пушит тег: SSH-ключ
с паролем недоступен из чата.

| Сценарий | Релиз |
|---|---|
| Merge фичи в `main` | Нет, пока не запущен workflow |
| Несколько багфиксов подряд | Один dispatch на последний SHA пачки |
| Только docs/rules | Нет (нужен `force=true`, если всё же нужен бинарь) |
| Ручной выпуск | `workflow_dispatch`; опционально поле `commit_sha` |

Локальный dogfood-bump `Version` не равен GitHub Release: тег ставится только
при dispatch. Подготовка без push: скилл
[`prepare-github-release`](../../.cursor/skills/prepare-github-release/SKILL.md).

Push в `main` и merge сами по себе релиз не открывают (CI только проверяет).

### O-02. Ветки и worktree

Обсудить отдельно до внедрения рабочего процесса. Предпочтительный кандидат
для многокоммитной реализации — ветка задачи в отдельном worktree. Это
позволяет оставить незакоммиченные файлы основного рабочего каталога на месте.
Worktree дополняет ветку отдельной папкой и не переносит в неё автоматически
незакоммиченные или untracked-файлы.

Нужно решить:

- Создавать ли worktree на каждую спеку и от какого состояния `main`.
- Делать ли короткую ветку/PR для одиночного багфикса или разрешить прямой
  коммит в `main` с обязательными проверками до публикации.
- Нужен ли squash при merge; число коммитов не определяет число релизов.
- Как переносить нужные незакоммиченные материалы и оформлять зависимости
  между параллельными задачами.
- Как направлять агент, IDE и MCP на нужный worktree, разделять результаты
  сборки и установку сервера, используемого для повседневной работы.
- Как синхронизировать основное дерево после merge и удалять завершённые
  worktree без потери оставшихся незакоммиченных файлов.

До решения этих вопросов документ не предписывает создавать worktree,
переносить текущие изменения или менять правила коммитов.

### O-03. Совместимость и расширение платформ

Определить проверяемые версии SDK проекта, минимальную ОС, архитектуры
и среду исполнения smoke-тестов. Для каждой новой платформы подтвердить
работу обоих вариантов, загрузку проекта и BuildHost; одной кросс-сборки
недостаточно. Решить порядок подключения RID, перечисленных в проекте,
и необходимость дополнительных RID.

### O-04. Интеграция с версиями и обслуживание

Согласовать источник версии с отдельной задачей унификации и порядок
выпусков с обновлённым встроенным runtime. Не вводить параллельный механизм
версионирования. Тег `v{Version}`, повторные запуски и текст notes из
коммитов (≤16) зафиксированы вместе с O-01.
